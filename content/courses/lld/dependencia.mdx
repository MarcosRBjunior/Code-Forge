**Dependência** é a relação mais fraca entre classes: uma classe **usa** outra de forma temporária, sem guardá-la como parte do seu estado. Isso acontece quando a outra classe aparece como parâmetro de um método, como variável local ou como tipo de retorno. A frase que resume é "A usa B por um momento".

## Como reconhecer

| Onde B aparece em A | Relação |
| --- | --- |
| atributo guardado no objeto | associação (ou agregação/composição) |
| parâmetro de um método | dependência |
| variável local criada dentro de um método | dependência |
| tipo de retorno | dependência |
| chamada a método estático ou função de B | dependência |

Em UML, a dependência é uma **seta tracejada** apontando para a classe usada:

```text
GeradorDeRecibo - - - - -> Pagamento
```

## Exemplo

```python
from dataclasses import dataclass
from datetime import date


@dataclass(frozen=True)
class Pagamento:
    pagador: str
    valor: float
    data: date


@dataclass(frozen=True)
class Recibo:
    texto: str


class GeradorDeRecibo:
    """Depende de Pagamento (parâmetro) e de Recibo (retorno), sem guardar nenhum."""

    def __init__(self, empresa: str) -> None:
        self.empresa = empresa

    def gerar(self, pagamento: Pagamento) -> Recibo:
        texto = (
            f"{self.empresa} recebeu de {pagamento.pagador} "
            f"R$ {pagamento.valor:.2f} em {pagamento.data:%d/%m/%Y}"
        )
        return Recibo(texto)


gerador = GeradorDeRecibo("Oficina Bom Reparo")
recibo = gerador.gerar(Pagamento("Carla", 350.0, date(2026, 3, 14)))
print(recibo.texto)
```

`GeradorDeRecibo` não guarda nenhum pagamento. Cada chamada recebe um, usa e descarta. Se `Pagamento` mudar o nome de um campo, o gerador quebra, por isso ainda é uma dependência real, mas o acoplamento é pequeno e localizado.

## Dependência escondida vs explícita

A dependência mais perigosa é a que não aparece na assinatura. Compare:

```python
import random


class SorteioOculto:
    def sortear(self, participantes: list[str]) -> str:
        return random.choice(participantes)  # depende do gerador global


class SorteioExplicito:
    def sortear(self, participantes: list[str], rng: random.Random) -> str:
        return rng.choice(participantes)  # dependência visível e substituível


nomes = ["Ana", "Bia", "Caio", "Davi"]
print(SorteioOculto().sortear(nomes))
r1 = SorteioExplicito().sortear(nomes, random.Random(7))
r2 = SorteioExplicito().sortear(nomes, random.Random(7))
assert r1 == r2  # resultado reprodutível em teste
print(r1)
```

A versão explícita pode ser testada de forma determinística passando um gerador com semente fixa. O mesmo vale para relógio (`datetime.now()`), acesso a arquivos e chamadas de rede: quando estão escondidos dentro do método, testar fica difícil.

## Por que a força da relação importa

Quanto mais fraca a relação, menor o impacto de mudanças. A escala aproximada é:

```text
mais fraca                                              mais forte
dependência < associação < agregação < composição < herança
```

Um bom hábito é usar a relação **mais fraca que resolve o problema**. Se uma classe só precisa de outra dentro de um método, não a guarde como atributo.

<Callout type="tip" title="Dependa de abstrações">
Quando o parâmetro é uma interface (`Notificador`) e não uma classe concreta (`EmailSmtp`), a dependência fica ainda mais leve: qualquer implementação serve. Essa ideia é aprofundada no princípio da inversão de dependência.
</Callout>

## Armadilhas

- **Instanciar dependências pesadas dentro do método.** `RepositorioPostgres()` criado no meio da regra de negócio amarra a classe ao banco. Receba de fora.
- **Dependências globais.** Variáveis de módulo e singletons não aparecem na assinatura e surpreendem nos testes.
- **Promover sem motivo a associação.** Guardar como atributo algo usado uma única vez aumenta o estado e o acoplamento.
