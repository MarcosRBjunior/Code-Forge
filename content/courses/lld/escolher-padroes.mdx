Conhecer vinte padrões não ajuda se você não sabe **quando usar cada um**. O erro clássico é o contrário: abrir o problema já procurando onde encaixar um padrão. O caminho certo parte do **sintoma** no seu design e só então busca o padrão que o resolve.

## Do sintoma ao padrão

| Sintoma no design | Padrão provável |
| --- | --- |
| Vários algoritmos intercambiáveis (preço, rota, ordenação) | Strategy |
| Comportamento muda conforme o estado interno, com muitos ifs | State |
| Criar objetos de tipos diferentes sem acoplar ao concreto | Factory Method / Abstract Factory |
| Objeto com muitos parâmetros opcionais | Builder |
| Quando A muda, vários objetos precisam ser avisados | Observer |
| Adicionar responsabilidades por camadas (compressão, log) | Decorator |
| Integrar uma interface incompatível | Adapter |
| Simplificar um subsistema complicado | Facade |
| Tratar item único e grupo da mesma forma | Composite |
| Pedido como objeto (desfazer, fila, histórico) | Command |
| Passos fixos com detalhes que variam | Template Method |
| Uma única instância compartilhada | Singleton (com cautela) |
| Pedido passa por vários possíveis tratadores | Chain of Responsibility |
| Ausência de objeto gera ifs de None | Null Object |

## Raciocínio na prática

Imagine um sistema de notificação em que o usuário pode escolher e-mail, SMS ou push, e o texto pode ganhar prefixo de urgência ou assinatura. Dois sintomas distintos:

1. Canal de envio varia: **Strategy** (ou uma hierarquia simples com interface).
2. Adornos opcionais no texto: **Decorator**.

```python
from abc import ABC, abstractmethod


class Canal(ABC):
    @abstractmethod
    def enviar(self, texto: str) -> str: ...


class Email(Canal):
    def enviar(self, texto: str) -> str:
        return f"email:{texto}"


class Sms(Canal):
    def enviar(self, texto: str) -> str:
        return f"sms:{texto}"


class Urgente(Canal):  # decorator: embrulha outro canal
    def __init__(self, interno: Canal) -> None:
        self.interno = interno

    def enviar(self, texto: str) -> str:
        return self.interno.enviar(f"[URGENTE] {texto}")


class Notificador:
    def __init__(self, canal: Canal) -> None:  # strategy: canal intercambiável
        self.canal = canal

    def avisar(self, texto: str) -> str:
        return self.canal.enviar(texto)


assert Notificador(Email()).avisar("oi") == "email:oi"
assert Notificador(Urgente(Sms())).avisar("caiu") == "sms:[URGENTE] caiu"
print("dois padrões, dois sintomas")
```

```go
import "fmt"

type Canal interface {
	enviar(texto string) string
}

type Email struct{}

func (Email) enviar(texto string) string { return "email:" + texto }

type Sms struct{}

func (Sms) enviar(texto string) string { return "sms:" + texto }

type Urgente struct{ interno Canal } // decorator: embrulha outro canal

func (u Urgente) enviar(texto string) string { return u.interno.enviar("[URGENTE] " + texto) }

type Notificador struct{ canal Canal } // strategy: canal intercambiável

func (n Notificador) avisar(texto string) string { return n.canal.enviar(texto) }

func main() {
	if (Notificador{Email{}}).avisar("oi") != "email:oi" {
		panic("falhou")
	}
	if (Notificador{Urgente{Sms{}}}).avisar("caiu") != "sms:[URGENTE] caiu" {
		panic("falhou")
	}
	fmt.Println("dois padrões, dois sintomas")
}
```

</CodeTabs>

Dois padrões convivem sem esforço porque cada um resolve um problema diferente e ambos giram em torno da mesma interface.

<Callout type="warning" title="Sem padrão também é resposta">
Se o código é simples e não varia, não use padrão. Padrões acrescentam classes e indireção, e isso só se paga quando há variação real. Dizer "aqui basta uma função" é uma resposta madura.
</Callout>

## Perguntas para decidir

- O que **varia** neste problema? Encapsule isso.
- Quem precisa **saber** da mudança? Se muitos, pense em Observer.
- Estou criando objetos de forma **rígida**? Considere fábrica ou builder.
- A hierarquia está crescendo por **combinações**? Prefira composição (Decorator, Strategy).
- Será que isso é só uma **função** com um parâmetro?

## Armadilhas

- Singleton em tudo: vira estado global disfarçado.
- Padrão em cima de padrão sem necessidade (overengineering).
- Decorar o código com nomes do padrão (`FabricaDeCoisas`) sem a estrutura correspondente.
- Forçar o padrão do livro quando a linguagem tem solução nativa (funções, decoradores, enums).

## Na entrevista

Nomeie o sintoma antes do padrão: "aqui o cálculo de preço varia, então uso Strategy". Isso prova que você entende a motivação. Follow-ups: "por que não herança?", "o que muda se surgir um novo tipo?", "essa abstração é necessária agora?".
