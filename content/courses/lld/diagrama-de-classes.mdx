O diagrama de classes é o desenho mais pedido em entrevistas de LLD. Ele mostra a **estrutura estática** do sistema: quais classes existem, o que cada uma guarda, o que sabe fazer e como se relacionam. Não mostra a ordem das chamadas (isso é papel do diagrama de sequência), apenas o mapa do que existe.

## Anatomia de uma classe

Cada classe é uma caixa com três compartimentos: nome, atributos e métodos.

```text
+---------------------------+
|        ContaBancaria      |
+---------------------------+
| - titular: str            |
| - saldo: float            |
+---------------------------+
| + depositar(valor): None  |
| + sacar(valor): bool      |
| # auditar(): None         |
+---------------------------+
```

Os sinais de visibilidade são: `+` público, `-` privado, `#` protegido. Em Python eles são convenção (`_saldo`, `__saldo`), mas no diagrama vale mostrar a intenção.

## Relações e suas setas

| Relação | Notação | Significado |
| --- | --- | --- |
| Herança | seta com triângulo vazado | "é um" |
| Realização | tracejada com triângulo vazado | classe implementa interface |
| Composição | losango preenchido | parte não vive sem o todo |
| Agregação | losango vazado | todo tem partes que existem sozinhas |
| Associação | linha simples | uma conhece a outra |
| Dependência | tracejada com seta aberta | usa temporariamente |

Em texto, você pode improvisar com a mesma ideia da sintaxe de ferramentas como Mermaid:

```text
Animal <|-- Cachorro
Pedido *-- ItemPedido
Time o-- Jogador
Pedido ..> Pagamento
```

## Multiplicidade

Nas pontas da linha você anota quantos objetos participam: `1`, `0..1`, `*` (muitos), `1..*`. Um `Pedido` tem `1..*` itens; um `Item` pertence a exatamente `1` pedido. Esse detalhe responde a perguntas de entrevista sem você falar nada: "pode existir pedido vazio?" Não.

## Do diagrama para o código

O bom diagrama é traduzível em código quase mecanicamente. Veja o mesmo modelo em Python:

```python
from abc import ABC, abstractmethod


class Pagamento(ABC):
    @abstractmethod
    def pagar(self, valor: float) -> bool: ...


class Pix(Pagamento):
    def pagar(self, valor: float) -> bool:
        return valor > 0


class ItemPedido:
    def __init__(self, nome: str, preco: float) -> None:
        self.nome = nome
        self.preco = preco


class Pedido:
    def __init__(self) -> None:
        self._itens: list[ItemPedido] = []  # composição: itens morrem com o pedido

    def adicionar(self, item: ItemPedido) -> None:
        self._itens.append(item)

    def total(self) -> float:
        return sum(i.preco for i in self._itens)

    def fechar(self, forma: Pagamento) -> bool:  # dependência: só usa no método
        return forma.pagar(self.total())


p = Pedido()
p.adicionar(ItemPedido("Livro", 50.0))
p.adicionar(ItemPedido("Caneta", 5.0))
assert p.fechar(Pix()) is True
print("Total:", p.total())
```

Repare no mapeamento: `Pagamento` é interface (realização por `Pix`), `ItemPedido` é composição dentro de `Pedido` (campo da instância) e `Pagamento` aparece só como parâmetro (dependência).

## Armadilhas

- **Desenhar tudo**: não liste getters, construtores nem classes triviais. Mostre o que sustenta a decisão de design.
- **Setas decorativas**: cada seta deve ter um motivo. Se você não sabe dizer se é composição ou agregação, pergunte sobre o ciclo de vida.
- **Misturar níveis**: diagrama de domínio e detalhes de infraestrutura no mesmo desenho confundem. Separe.

<Callout type="tip" title="Quanto detalhe?">
Em entrevista, comece com nomes de classes e relações; só adicione atributos e métodos das classes centrais. Refine conforme o entrevistador pedir.
</Callout>

## Na entrevista

Depois de levantar requisitos e entidades, desenhe o diagrama de classes antes de codar. Follow-ups comuns: "por que composição aqui?", "essa seta é herança ou realização?", "onde entra a interface?". Se alterar o modelo no meio da conversa, atualize o desenho em voz alta.
