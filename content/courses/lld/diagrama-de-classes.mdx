O diagrama de classes é o desenho mais pedido em entrevistas de LLD. Ele mostra a **estrutura estática** do sistema: quais classes existem, o que cada uma guarda, o que sabe fazer e como se relacionam. Não mostra a ordem das chamadas (isso é papel do diagrama de sequência), apenas o mapa do que existe.

## Anatomia de uma classe

Cada classe é uma caixa com três compartimentos: nome, atributos e métodos.

```text
+---------------------------+
|        ContaBancaria      |
+---------------------------+
| - titular: str            |
| - saldo: float            |
+---------------------------+
| + depositar(valor): None  |
| + sacar(valor): bool      |
| # auditar(): None         |
+---------------------------+
```

Os sinais de visibilidade são: `+` público, `-` privado, `#` protegido. Em Python eles são convenção (`_saldo`, `__saldo`), mas no diagrama vale mostrar a intenção.

## Relações e suas setas

| Relação | Notação | Significado |
| --- | --- | --- |
| Herança | seta com triângulo vazado | "é um" |
| Realização | tracejada com triângulo vazado | classe implementa interface |
| Composição | losango preenchido | parte não vive sem o todo |
| Agregação | losango vazado | todo tem partes que existem sozinhas |
| Associação | linha simples | uma conhece a outra |
| Dependência | tracejada com seta aberta | usa temporariamente |

Em texto, você pode improvisar com a mesma ideia da sintaxe de ferramentas como Mermaid:

```text
Animal <|-- Cachorro
Pedido *-- ItemPedido
Time o-- Jogador
Pedido ..> Pagamento
```

## Multiplicidade

Nas pontas da linha você anota quantos objetos participam: `1`, `0..1`, `*` (muitos), `1..*`. Um `Pedido` tem `1..*` itens; um `Item` pertence a exatamente `1` pedido. Esse detalhe responde a perguntas de entrevista sem você falar nada: "pode existir pedido vazio?" Não.

## Do diagrama para o código

O bom diagrama é traduzível em código quase mecanicamente. Veja o mesmo modelo em Python:

<CodeTabs>

```python
from abc import ABC, abstractmethod


class Pagamento(ABC):
    @abstractmethod
    def pagar(self, valor: float) -> bool: ...


class Pix(Pagamento):
    def pagar(self, valor: float) -> bool:
        return valor > 0


class ItemPedido:
    def __init__(self, nome: str, preco: float) -> None:
        self.nome = nome
        self.preco = preco


class Pedido:
    def __init__(self) -> None:
        self._itens: list[ItemPedido] = []  # composição: itens morrem com o pedido

    def adicionar(self, item: ItemPedido) -> None:
        self._itens.append(item)

    def total(self) -> float:
        return sum(i.preco for i in self._itens)

    def fechar(self, forma: Pagamento) -> bool:  # dependência: só usa no método
        return forma.pagar(self.total())


p = Pedido()
p.adicionar(ItemPedido("Livro", 50.0))
p.adicionar(ItemPedido("Caneta", 5.0))
assert p.fechar(Pix()) is True
print("Total:", p.total())
```

```java
import java.util.*;

interface Pagamento {
    boolean pagar(double valor);
}

class Pix implements Pagamento {
    public boolean pagar(double valor) { return valor > 0; }
}

class ItemPedido {
    final String nome;
    final double preco;

    ItemPedido(String nome, double preco) {
        this.nome = nome;
        this.preco = preco;
    }
}

class Pedido {
    private final List<ItemPedido> itens = new ArrayList<>();   // composição: itens morrem com o pedido

    void adicionar(ItemPedido item) { itens.add(item); }

    double total() {
        double soma = 0;
        for (ItemPedido i : itens) soma += i.preco;
        return soma;
    }

    boolean fechar(Pagamento forma) { return forma.pagar(total()); }   // dependência: só usa no método
}

public static void main(String[] args) {
    Pedido p = new Pedido();
    p.adicionar(new ItemPedido("Livro", 50.0));
    p.adicionar(new ItemPedido("Caneta", 5.0));
    if (!p.fechar(new Pix())) throw new AssertionError();
    System.out.println("Total: " + p.total());
}
```

#include <cassert>
#include <iostream>
#include <string>
#include <vector>
using namespace std;

class Pagamento {
public:
    virtual ~Pagamento() = default;
    virtual bool pagar(double valor) const = 0;
};

class Pix : public Pagamento {
public:
    bool pagar(double valor) const override { return valor > 0; }
};

struct ItemPedido {
    string nome;
    double preco;
};

class Pedido {
    vector<ItemPedido> itens;   // composição: itens morrem com o pedido

public:
    void adicionar(const ItemPedido& item) { itens.push_back(item); }

    double total() const {
        double soma = 0;
        for (const auto& i : itens) soma += i.preco;
        return soma;
    }

    bool fechar(const Pagamento& forma) const { return forma.pagar(total()); }   // dependência: só usa no método
};

int main() {
    Pedido p;
    p.adicionar({"Livro", 50.0});
    p.adicionar({"Caneta", 5.0});
    assert(p.fechar(Pix()) == true);
    cout << "Total: " << p.total() << endl;

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

interface IPagamento
{
    bool Pagar(double valor);
}

class Pix : IPagamento
{
    public bool Pagar(double valor) { return valor > 0; }
}

class ItemPedido
{
    public readonly string Nome;
    public readonly double Preco;

    public ItemPedido(string nome, double preco)
    {
        Nome = nome;
        Preco = preco;
    }
}

class Pedido
{
    private readonly List<ItemPedido> itens = new List<ItemPedido>();   // composição: itens morrem com o pedido

    public void Adicionar(ItemPedido item) { itens.Add(item); }

    public double Total() { return itens.Sum(i => i.Preco); }

    public bool Fechar(IPagamento forma) { return forma.Pagar(Total()); }   // dependência: só usa no método
}

static void Main()
{
    var p = new Pedido();
    p.Adicionar(new ItemPedido("Livro", 50.0));
    p.Adicionar(new ItemPedido("Caneta", 5.0));
    if (!p.Fechar(new Pix())) throw new Exception("falhou");
    Console.WriteLine("Total: " + p.Total());
}
```

```go
import "fmt"

type Pagamento interface {
	pagar(valor float64) bool
}

type Pix struct{}

func (Pix) pagar(valor float64) bool { return valor > 0 }

type ItemPedido struct {
	nome  string
	preco float64
}

type Pedido struct {
	itens []ItemPedido // composição: itens morrem com o pedido
}

func (p *Pedido) adicionar(item ItemPedido) { p.itens = append(p.itens, item) }

func (p *Pedido) total() float64 {
	soma := 0.0
	for _, i := range p.itens {
		soma += i.preco
	}
	return soma
}

func (p *Pedido) fechar(forma Pagamento) bool { return forma.pagar(p.total()) } // dependência: só usa no método

func main() {
	p := &Pedido{}
	p.adicionar(ItemPedido{"Livro", 50.0})
	p.adicionar(ItemPedido{"Caneta", 5.0})
	if !p.fechar(Pix{}) {
		panic("falhou")
	}
	fmt.Println("Total:", p.total())
}
```

</CodeTabs>

Repare no mapeamento: `Pagamento` é interface (realização por `Pix`), `ItemPedido` é composição dentro de `Pedido` (campo da instância) e `Pagamento` aparece só como parâmetro (dependência).

## Armadilhas

- **Desenhar tudo**: não liste getters, construtores nem classes triviais. Mostre o que sustenta a decisão de design.
- **Setas decorativas**: cada seta deve ter um motivo. Se você não sabe dizer se é composição ou agregação, pergunte sobre o ciclo de vida.
- **Misturar níveis**: diagrama de domínio e detalhes de infraestrutura no mesmo desenho confundem. Separe.

<Callout type="tip" title="Quanto detalhe?">
Em entrevista, comece com nomes de classes e relações; só adicione atributos e métodos das classes centrais. Refine conforme o entrevistador pedir.
</Callout>

## Na entrevista

Depois de levantar requisitos e entidades, desenhe o diagrama de classes antes de codar. Follow-ups comuns: "por que composição aqui?", "essa seta é herança ou realização?", "onde entra a interface?". Se alterar o modelo no meio da conversa, atualize o desenho em voz alta.
