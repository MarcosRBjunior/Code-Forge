**YAGNI** significa *You Aren't Gonna Need It*, "você não vai precisar disso". O princípio diz: não implemente uma funcionalidade ou um ponto de extensão até que exista uma necessidade concreta. Construir para um futuro imaginado parece prudente, mas na prática quase sempre custa mais do que construir quando o futuro chega.

## O problema

Todo desenvolvedor já pensou "e se um dia precisarmos suportar várias moedas?" e saiu criando tabelas de câmbio, interfaces de conversão e testes para um sistema que só vende em reais. Esse código especulativo tem custos reais:

- **Custo de construir**: tempo que não foi para o que o usuário pediu.
- **Custo de carregar**: cada leitor precisa entender as camadas extras; cada refatoração precisa atualizá-las.
- **Custo de errar**: quando a necessidade real chega, ela raramente tem o formato que você imaginou, e a abstração antiga atrapalha.
- **Custo de atraso**: o que realmente importava foi entregue depois.

## Exemplo especulativo

Pediram um serviço que envia e-mail de boas-vindas:

```python
from abc import ABC, abstractmethod


class Canal(ABC):
    @abstractmethod
    def enviar(self, destino: str, msg: str, prioridade: int, tentativas: int, idioma: str) -> bool: ...


class CanalEmail(Canal):
    def enviar(self, destino: str, msg: str, prioridade: int, tentativas: int, idioma: str) -> bool:
        # prioridade, tentativas e idioma são ignorados: ninguém pediu ainda
        print(f"[email:{destino}] {msg}")
        return True


class FabricaDeCanais:
    def criar(self, tipo: str) -> Canal:
        if tipo == "email":
            return CanalEmail()
        raise NotImplementedError("SMS, push e pombo-correio virão um dia")


FabricaDeCanais().criar("email").enviar("ana@x.com", "Bem-vinda!", 1, 3, "pt")
```

Fábrica, interface e três parâmetros que ninguém usa. Tudo para uma única operação.

## Versão YAGNI

```python
class BoasVindas:
    def __init__(self) -> None:
        self.enviados: list[str] = []

    def enviar(self, email: str, nome: str) -> None:
        msg = f"Olá, {nome}! Que bom ter você aqui."
        self.enviados.append(email)
        print(f"[email:{email}] {msg}")


servico = BoasVindas()
servico.enviar("ana@x.com", "Ana")
assert servico.enviados == ["ana@x.com"]
```

Se amanhã chegar o pedido de SMS, você extrai uma interface nesse momento, com dois casos reais para guiar o desenho. O refactor é pequeno porque o código é pequeno.

## YAGNI não é desculpa para código ruim

YAGNI corta **funcionalidade especulativa**, não qualidade. Continue escrevendo testes, nomes claros e classes coesas: são eles que tornam barato adicionar a funcionalidade depois. A aposta do YAGNI só compensa se o código atual for fácil de mudar.

| Faça agora | Adie (YAGNI) |
| --- | --- |
| Testes do comportamento atual | Suporte a formatos que ninguém pediu |
| Separação clara de responsabilidades | Plugins e pontos de extensão sem cliente |
| Tratamento de erros reais | Parâmetros "para o caso de precisar" |
| Nomes e estrutura legíveis | Cache para um gargalo que não foi medido |

<Callout type="warning" title="Exceções legítimas">
Algumas decisões são caras de reverter: formato de API pública, esquema de dados persistido, protocolo entre serviços. Nesses pontos vale pensar mais à frente. YAGNI se aplica melhor ao que é barato de mudar depois.
</Callout>

## Na entrevista

Entrevistas de LLD costumam ter requisitos explícitos. Use YAGNI para justificar o que você **não** vai modelar: "não vou implementar reservas antecipadas porque não estão no escopo, mas a classe `Vaga` permite adicionar isso". Isso mostra foco e consciência de extensibilidade ao mesmo tempo. Follow-ups comuns: "e se o requisito mudar?", "como você equilibra YAGNI e OCP?". Resposta: o OCP se aplica onde a variação já é conhecida ou muito provável; o YAGNI vale para o resto.
