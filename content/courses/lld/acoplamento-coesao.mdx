Acoplamento e coesão são as duas métricas mais úteis para avaliar um design, e quase todos os princípios que você estuda neste curso existem para melhorar uma delas. O objetivo clássico é **baixo acoplamento e alta coesão**.

- **Acoplamento** mede o quanto um módulo depende de outros. Quanto mais um sabe sobre o outro, mais uma mudança em um obriga mudanças no outro.
- **Coesão** mede o quanto os elementos de um módulo pertencem juntos. Uma classe coesa tem atributos e métodos que trabalham pelo mesmo propósito.

## Uma analogia

Pense numa cozinha de restaurante. Alta coesão é cada estação ter tudo de que precisa: a de massas tem panelas, massas e molhos à mão. Baixo acoplamento é o chef da massa não precisar entrar na estação de sobremesas para terminar um prato: ele só passa o pedido pelo balcão.

## Tipos de acoplamento (do pior ao melhor)

| Tipo | Exemplo |
| --- | --- |
| Conteúdo | Uma classe altera atributos privados de outra |
| Comum | Várias classes leem e escrevem uma variável global |
| Controle | Você passa uma flag que diz ao outro módulo o que fazer |
| Estampa | Você passa um objeto inteiro quando só precisa de um campo |
| Dados | Você passa apenas os valores necessários |
| Mensagem | Os módulos se comunicam por uma interface ou eventos |

## Exemplo com acoplamento alto e coesão baixa

```python
ESTADO_GLOBAL = {"ultimo_pedido": None}


class Utilidades:
    def calcular_frete(self, peso: float) -> float:
        return 10 + peso * 2

    def formatar_cpf(self, cpf: str) -> str:
        return f"{cpf[:3]}.{cpf[3:6]}.{cpf[6:9]}-{cpf[9:]}"

    def registrar_pedido(self, pedido: dict, modo: str) -> None:
        if modo == "rapido":
            pedido["frete"] = self.calcular_frete(pedido["peso"]) * 1.5
        else:
            pedido["frete"] = self.calcular_frete(pedido["peso"])
        ESTADO_GLOBAL["ultimo_pedido"] = pedido


u = Utilidades()
u.registrar_pedido({"peso": 2.0}, "rapido")
print(ESTADO_GLOBAL, u.formatar_cpf("12345678901"))
```

Problemas: `Utilidades` junta frete, CPF e pedidos (coesão baixa); o estado global cria acoplamento comum; a string `modo` é acoplamento de controle.

## Versão melhorada

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass


class Frete(ABC):
    @abstractmethod
    def valor(self, peso: float) -> float: ...


class FreteNormal(Frete):
    def valor(self, peso: float) -> float:
        return 10 + peso * 2


class FreteRapido(Frete):
    def valor(self, peso: float) -> float:
        return FreteNormal().valor(peso) * 1.5


@dataclass
class Pedido:
    peso: float
    frete: float = 0.0


class RegistroDePedidos:
    def __init__(self, frete: Frete) -> None:
        self._frete = frete
        self._pedidos: list[Pedido] = []

    def registrar(self, pedido: Pedido) -> Pedido:
        pedido.frete = self._frete.valor(pedido.peso)
        self._pedidos.append(pedido)
        return pedido

    def ultimo(self) -> Pedido | None:
        return self._pedidos[-1] if self._pedidos else None


registro = RegistroDePedidos(FreteRapido())
registro.registrar(Pedido(peso=2.0))
assert registro.ultimo().frete == 21.0
print(registro.ultimo())
```

`RegistroDePedidos` depende apenas da interface `Frete` (acoplamento por mensagem), não há estado global, e cada classe tem um propósito só (coesão alta). A formatação de CPF iria para outro módulo, junto de coisas sobre documentos.

## Como medir na prática

- **Acoplamento**: quantas classes você precisa importar ou instanciar para testar esta? Quantos arquivos mudam numa alteração típica?
- **Coesão**: os métodos usam os mesmos atributos? Dá para dar um nome específico para a classe sem usar "e", "Utils" ou "Manager"?

## Trade-offs

Acoplamento zero é impossível: módulos precisam colaborar para o sistema fazer algo. O que se busca é acoplamento **explícito, estreito e estável**, de preferência a abstrações. E coesão extrema pode virar fragmentação; agrupe pelo que muda junto.

<Callout type="tip" title="Uma frase para lembrar">
Coisas que mudam juntas devem ficar juntas; coisas que mudam por motivos diferentes devem ficar separadas e conversar por interfaces.
</Callout>

## Na entrevista

Use esse vocabulário para justificar decisões: "deixei `Elevador` desacoplado de `Painel` porque eles conversam por requisições; assim posso trocar o algoritmo de despacho sem mexer nos botões". Follow-ups comuns: "como você reduziria o acoplamento aqui?" (interfaces, injeção, eventos) e "essa classe está coesa?" (verifique se todos os métodos usam o mesmo estado).
