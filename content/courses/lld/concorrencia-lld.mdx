Boa parte dos problemas de LLD parece sequencial até o entrevistador perguntar: "e se duas pessoas tentarem reservar o último assento ao mesmo tempo?". Essa pergunta testa se você entende **condições de corrida** e sabe proteger o estado compartilhado sem destruir o desempenho.

## O que dá errado

Uma condição de corrida acontece quando o resultado depende da ordem em que threads executam. O exemplo clássico é "verificar e depois agir":

```python
class AssentoInseguro:
    def __init__(self) -> None:
        self.reservado_por: str | None = None

    def reservar(self, quem: str) -> bool:
        if self.reservado_por is None:   # verifica
            # outra thread pode entrar aqui!
            self.reservado_por = quem    # age
            return True
        return False
```

Entre a verificação e a atribuição, outra thread pode passar na mesma verificação. Resultado: duas pessoas "reservam" o mesmo assento.

## A correção: seção crítica com lock

```python
import threading


class Assento:
    def __init__(self) -> None:
        self._trava = threading.Lock()
        self.reservado_por: str | None = None

    def reservar(self, quem: str) -> bool:
        with self._trava:  # verificar e agir viram uma operação indivisível
            if self.reservado_por is None:
                self.reservado_por = quem
                return True
            return False


assento = Assento()
sucessos: list[str] = []


def tentar(nome: str) -> None:
    if assento.reservar(nome):
        sucessos.append(nome)


threads = [threading.Thread(target=tentar, args=(f"p{i}",)) for i in range(50)]
for t in threads:
    t.start()
for t in threads:
    t.join()

assert len(sucessos) == 1  # exatamente um vencedor
print("vencedor:", sucessos[0])
```

A trava transforma "verificar e agir" numa seção crítica: só uma thread por vez entra.

## Ferramentas e quando usar

| Ferramenta | Uso |
| --- | --- |
| `Lock` | Exclusão mútua simples sobre um recurso |
| `RLock` | Lock reentrante, quando o mesmo código se chama recursivamente |
| `Semaphore` | Limitar a N acessos simultâneos (vagas de estacionamento) |
| `Condition` / `Event` | Esperar por uma condição ou sinal |
| `queue.Queue` | Passar dados entre threads com segurança (produtor-consumidor) |
| Imutabilidade | Objetos que não mudam não precisam de trava |

## Decisões de design

- **Granularidade**: uma trava global é simples, mas serializa tudo. Uma trava por recurso (por assento, por conta) permite paralelismo.
- **Deadlock**: ao adquirir duas travas, sempre na mesma ordem. Numa transferência entre contas, ordene pelo id.
- **Onde ficam as travas**: dentro da classe que protege o estado, não espalhadas pelos chamadores. Isso é encapsulamento aplicado à concorrência.
- **Mantenha seções críticas curtas**: nunca faça I/O lento segurando uma trava.

<Callout type="warning" title="Ordem de aquisição">
Se a thread A pega a conta 1 e espera a 2, enquanto a B pega a 2 e espera a 1, ninguém avança. Ordenar as travas por id elimina esse ciclo.
</Callout>

## Onde costuma aparecer

Reserva de assentos e salas, saldo de conta, estoque, contador de limite de requisições, cache e pools de recursos. Em muitos problemas, bastar dizer onde você colocaria travas já demonstra a consciência necessária; implemente quando o entrevistador pedir.

## Na entrevista

Primeiro faça a versão correta em thread única; depois, ao ser perguntado, aponte as seções críticas, adicione locks e discuta granularidade. Follow-ups: "como evitaria deadlock?", "um lock global é aceitável?", "como escalaria em várias máquinas?" (a resposta sai da memória e vai para transações de banco ou travas distribuídas).
