Low Level Design (LLD) é a parte do trabalho de engenharia em que você decide **quais classes existem, o que cada uma sabe, o que cada uma faz e como elas conversam**. Diferente de algoritmos, aqui não existe uma resposta única certa: existe um design que aguenta mudanças com pouco sofrimento e outro que desmorona na primeira feature nova. Este capítulo mostra como organizar o estudo para chegar nesse nível sem decorar receitas.

## O problema de estudar LLD do jeito errado

O erro mais comum é começar decorando os 23 padrões de projeto. Você aprende o nome "Strategy", memoriza um diagrama e, na hora de modelar um estacionamento, não sabe onde ele se encaixa. Padrões são **soluções para tensões específicas** entre classes. Sem entender a tensão (acoplamento demais, uma classe fazendo tudo, um `if` que cresce a cada requisito), o padrão vira enfeite.

Outro erro é estudar só lendo. LLD é habilidade motora: você precisa escrever classes, sentir o atrito de mudar um requisito e refatorar.

## Uma trilha em camadas

Pense no estudo como camadas que se apoiam:

| Camada | O que você aprende | Sinal de que dominou |
| --- | --- | --- |
| Fundamentos de OOP | classes, encapsulamento, herança, polimorfismo | explica quando **não** usar herança |
| Relações entre classes | associação, agregação, composição, dependência | sabe dizer quem cria e quem destrói cada objeto |
| Princípios (SOLID, DRY, KISS) | critérios para julgar um design | aponta qual princípio um trecho viola |
| Padrões de projeto | soluções nomeadas para tensões recorrentes | reconhece o problema antes de lembrar o nome |
| Problemas completos | estacionamento, elevador, biblioteca | entrega um design coerente em 45 minutos |

Cada camada depende da anterior. Pular direto para problemas completos funciona mal porque você não tem vocabulário para justificar escolhas.

## O ciclo de prática

Para cada conceito novo, siga quatro passos:

1. **Entenda a dor.** Escreva a versão ingênua do código e veja onde ela quebra.
2. **Aplique a ideia.** Reescreva usando o conceito.
3. **Mude um requisito.** Invente uma feature nova e veja qual versão absorve melhor.
4. **Explique em voz alta.** Se você não consegue justificar em duas frases, ainda não entendeu.

Veja um exemplo mínimo do passo 3. Comece com um cálculo de frete rígido:

<CodeTabs>

```python
class Frete:
    def calcular(self, tipo: str, peso_kg: float) -> float:
        if tipo == "padrao":
            return 10 + peso_kg * 2
        if tipo == "expresso":
            return 25 + peso_kg * 3
        raise ValueError(f"tipo desconhecido: {tipo}")


print(Frete().calcular("expresso", 2))  # 31
```

Agora o requisito muda: "adicione retirada na loja, com frete zero". Você precisa abrir a classe e enfiar mais um `if`. Compare com uma versão em que cada modalidade é um objeto:

```python

        return 10 + peso_kg * 2

        return 25 + peso_kg * 3
```

```cpp
#include <memory>
#include <string>
#include <vector>
using namespace std;

class Modalidade {
public:
    virtual ~Modalidade() = default;
    virtual double calcular(double pesoKg) const = 0;
    virtual string nome() const = 0;
};

class FretePadrao : public Modalidade {
public:
    double calcular(double pesoKg) const override { return 10 + pesoKg * 2; }
    string nome() const override { return "FretePadrao"; }
};

class FreteExpresso : public Modalidade {
public:
    double calcular(double pesoKg) const override { return 25 + pesoKg * 3; }
    string nome() const override { return "FreteExpresso"; }
};

class RetiradaNaLoja : public Modalidade {
public:
    double calcular(double pesoKg) const override { return 0.0; }
    string nome() const override { return "RetiradaNaLoja"; }
};

int main() {
    vector<unique_ptr<Modalidade>> modalidades;
    modalidades.push_back(make_unique<FretePadrao>());
    modalidades.push_back(make_unique<FreteExpresso>());
    modalidades.push_back(make_unique<RetiradaNaLoja>());
    for (const auto& m : modalidades) {
        cout << m->nome() << " " << m->calcular(2) << endl;
    }
}
```

## Armadilhas comuns

- **Overengineering.** Criar interfaces, fábricas e camadas para um problema de 30 linhas. Design bom é proporcional ao problema.
- **Copiar soluções prontas.** Ver o design "oficial" de um elevador antes de tentar o seu tira o aprendizado. Tente primeiro, compare depois.
- **Ignorar o código.** Diagramas bonitos que não viram código executável escondem furos. Sempre implemente pelo menos o fluxo principal.

<Callout type="tip" title="Use uma linguagem só">
Escolha uma linguagem orientada a objetos (aqui usamos Python) e fique nela durante todo o estudo. Trocar de linguagem no meio desvia sua atenção para sintaxe em vez de design.
</Callout>

## Na entrevista

O entrevistador quer ver **raciocínio**, não um diagrama decorado. Você vai se sair melhor se:

- esclarecer requisitos antes de desenhar classes;
- nomear trade-offs ("usei composição aqui porque o comportamento muda em tempo de execução");
- evoluir o design quando ele pedir um requisito extra, sem reescrever tudo.

Follow-ups comuns: "e se surgir um novo tipo de X?", "como você testaria essa classe?", "o que acontece com acesso concorrente?". Todas essas perguntas testam se seu design tolera mudança.
