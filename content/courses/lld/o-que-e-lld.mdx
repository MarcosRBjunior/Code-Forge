Low Level Design é o desenho **interno** de um componente de software: as classes, seus atributos, seus métodos, as interfaces entre elas e as regras que governam essas interações. Se o High Level Design responde "quais serviços existem e como se comunicam", o LLD responde "dentro deste serviço, como o código está organizado".

## O problema que o LLD resolve

Todo sistema começa pequeno. Um script de 200 linhas resolve o problema e ninguém pensa em design. Aí chegam os requisitos novos: outro meio de pagamento, outro tipo de usuário, uma regra de desconto sazonal. Sem um desenho intencional, cada mudança vira um remendo, e em poucos meses o código é uma teia em que mexer num lugar quebra três outros.

LLD é a disciplina de organizar o código para que:

- cada parte tenha uma **responsabilidade clara**;
- as dependências entre partes sejam **poucas e explícitas**;
- mudanças previsíveis exijam **edições localizadas**;
- o código seja **testável** sem montar o sistema inteiro.

## O que faz parte de um LLD

| Elemento | Pergunta que responde |
| --- | --- |
| Entidades (classes) | quais "coisas" o domínio tem? |
| Atributos | o que cada coisa sabe? |
| Métodos | o que cada coisa faz? |
| Relações | quem conhece quem, quem cria quem? |
| Interfaces | quais contratos permitem trocar implementações? |
| Padrões | quais soluções conhecidas resolvem tensões do design? |
| Tratamento de erros e concorrência | o que acontece em casos de borda e acesso simultâneo? |

## Exemplo concreto: um sistema de reservas de sala

Imagine o requisito: "funcionários reservam salas de reunião em horários; uma sala não pode ter duas reservas sobrepostas". Um LLD enxuto identifica três entidades (`Sala`, `Reserva`, `Agenda`) e coloca a regra de sobreposição no lugar certo.

```python
from dataclasses import dataclass, field


@dataclass(frozen=True)
class Reserva:
    responsavel: str
    inicio: int  # hora cheia, 0 a 23
    fim: int

    def conflita_com(self, outra: "Reserva") -> bool:
        return self.inicio < outra.fim and outra.inicio < self.fim


@dataclass
class Sala:
    nome: str
    capacidade: int
    reservas: list[Reserva] = field(default_factory=list)

    def reservar(self, reserva: Reserva) -> None:
        if any(reserva.conflita_com(r) for r in self.reservas):
            raise ValueError(f"{self.nome} ocupada nesse horário")
        self.reservas.append(reserva)


class Agenda:
    def __init__(self) -> None:
        self._salas: dict[str, Sala] = {}

    def adicionar_sala(self, sala: Sala) -> None:
        self._salas[sala.nome] = sala

    def reservar(self, nome_sala: str, reserva: Reserva) -> None:
        self._salas[nome_sala].reservar(reserva)


agenda = Agenda()
agenda.adicionar_sala(Sala("Aurora", 6))
agenda.reservar("Aurora", Reserva("Ana", 9, 10))
try:
    agenda.reservar("Aurora", Reserva("Bruno", 9, 11))
except ValueError as erro:
    print(erro)  # Aurora ocupada nesse horário
```

import java.util.*;

class Reserva {
    final String responsavel;
    final int inicio, fim;   // hora cheia, 0 a 23

    Reserva(String responsavel, int inicio, int fim) {
        this.responsavel = responsavel;
        this.inicio = inicio;
        this.fim = fim;
    }

    boolean conflitaCom(Reserva outra) { return inicio < outra.fim && outra.inicio < fim; }
}

class Sala {
    final String nome;
    final int capacidade;
    final List<Reserva> reservas = new ArrayList<>();

    Sala(String nome, int capacidade) {
        this.nome = nome;
        this.capacidade = capacidade;
    }

    void reservar(Reserva reserva) {
        for (Reserva r : reservas) {
            if (reserva.conflitaCom(r)) throw new IllegalStateException(nome + " ocupada nesse horário");
        }
        reservas.add(reserva);
    }
}

class Agenda {
    private final Map<String, Sala> salas = new HashMap<>();

    void adicionarSala(Sala sala) { salas.put(sala.nome, sala); }

    void reservar(String nomeSala, Reserva reserva) { salas.get(nomeSala).reservar(reserva); }
}

public static void main(String[] args) {
    Agenda agenda = new Agenda();
    agenda.adicionarSala(new Sala("Aurora", 6));
    agenda.reservar("Aurora", new Reserva("Ana", 9, 10));
    try {
        agenda.reservar("Aurora", new Reserva("Bruno", 9, 11));

    }

```go
import (
	"errors"
	"fmt"
)

type Reserva struct {
	responsavel string
	inicio, fim int // hora cheia, 0 a 23
}

func (r Reserva) conflitaCom(outra Reserva) bool { return r.inicio < outra.fim && outra.inicio < r.fim }

type Sala struct {
	nome       string
	capacidade int
	reservas   []Reserva
}

func (s *Sala) reservar(reserva Reserva) error {
	for _, r := range s.reservas {
		if reserva.conflitaCom(r) {
			return errors.New(s.nome + " ocupada nesse horário")
		}
	}
	s.reservas = append(s.reservas, reserva)
	return nil
}

type Agenda struct {
	salas map[string]*Sala
}

func (a *Agenda) adicionarSala(sala *Sala) { a.salas[sala.nome] = sala }

func (a *Agenda) reservar(nomeSala string, reserva Reserva) error {
	return a.salas[nomeSala].reservar(reserva)
}

func main() {
	agenda := &Agenda{map[string]*Sala{}}
	agenda.adicionarSala(&Sala{nome: "Aurora", capacidade: 6})
	agenda.reservar("Aurora", Reserva{"Ana", 9, 10})
	if erro := agenda.reservar("Aurora", Reserva{"Bruno", 9, 11}); erro != nil {
		fmt.Println(erro) // Aurora ocupada nesse horário
	}
}
```

Repare nas decisões de design embutidas:

- A regra "duas reservas conflitam" mora em `Reserva`, porque só depende dos dados dela.
- A regra "a sala não aceita conflito" mora em `Sala`, que é dona da lista de reservas.
- `Agenda` apenas coordena; não sabe nada sobre horários.

Se amanhã surgir "reservas recorrentes", você sabe exatamente onde mexer.

## LLD não é só diagrama

Muita gente associa LLD a diagramas UML. Diagramas ajudam a comunicar, mas o produto final é **código**. Um bom LLD precisa:

1. compilar ou rodar;
2. expressar o domínio com nomes que o negócio reconhece;
3. aguentar os casos de borda (sala inexistente, horário inválido).

<Callout type="note" title="Nível de detalhe">
LLD não define banco de dados, filas ou número de servidores. Quando a conversa vai para esses temas, você saiu do LLD e entrou no HLD.
</Callout>

## Trade-offs

Design demais tem custo. Cada interface extra é mais um arquivo para ler, cada camada é mais um salto ao depurar. O objetivo não é o design mais "elegante", e sim o **mais simples que absorve as mudanças prováveis**. Saber o que é provável exige conversar com quem pediu o sistema.

## Na entrevista

Quando pedirem "projete X", o entrevistador quer ver você:

- listar requisitos e casos de uso antes de qualquer classe;
- identificar entidades a partir dos substantivos do problema;
- distribuir responsabilidades e justificar cada uma;
- escrever o código das classes centrais.

Follow-ups típicos: "onde fica a validação?", "como adicionar um novo tipo de sala?", "e se dois usuários reservarem ao mesmo tempo?".
