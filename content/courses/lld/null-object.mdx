Quantas vezes você já escreveu `if cliente is not None:` antes de cada uso? Esses testes se espalham pelo código, e um esquecido vira um `AttributeError` em produção. O padrão **Null Object** troca a ausência (`None`) por um objeto real que implementa a mesma interface e **não faz nada** (ou faz o padrão neutro). O chamador deixa de perguntar "existe?" e simplesmente usa.

## O problema

Considere um serviço que notifica o usuário, mas o logger é opcional:

```python
class Servico:
    def __init__(self, logger=None):
        self.logger = logger

    def executar(self):
        if self.logger is not None:
            self.logger.info("iniciando")
        # ... trabalho ...
        if self.logger is not None:
            self.logger.info("terminado")
```

Cada ponto de uso repete o teste. Se você esquecer um, o código quebra apenas quando não há logger, o caso menos testado.

## A solução

Crie uma implementação "nula" da interface e use-a como padrão:

```python
from abc import ABC, abstractmethod


class Logger(ABC):
    @abstractmethod
    def info(self, msg: str) -> None: ...


class LoggerConsole(Logger):
    def info(self, msg: str) -> None:
        print(f"[INFO] {msg}")


class LoggerNulo(Logger):
    def info(self, msg: str) -> None:
        pass  # não faz nada, de propósito


class Servico:
    def __init__(self, logger: Logger | None = None) -> None:
        self.logger = logger or LoggerNulo()

    def executar(self) -> str:
        self.logger.info("iniciando")
        resultado = "ok"
        self.logger.info("terminado")
        return resultado


assert Servico().executar() == "ok"            # sem logger, sem ifs
assert Servico(LoggerConsole()).executar() == "ok"
```

A decisão de "ter ou não ter logger" acontece uma única vez, no construtor. O restante do código é linear e mais fácil de ler.

## Exemplo com retorno de dados

O Null Object também serve para buscas que podem não achar nada:

```python
class Cliente:
    def __init__(self, nome: str, desconto: float) -> None:
        self.nome = nome
        self.desconto = desconto


class ClienteAnonimo(Cliente):
    def __init__(self) -> None:
        super().__init__("visitante", 0.0)


class Cadastro:
    def __init__(self) -> None:
        self._dados = {1: Cliente("Ana", 0.1)}

    def buscar(self, id_: int) -> Cliente:
        return self._dados.get(id_, ClienteAnonimo())


def preco_final(cadastro: Cadastro, id_: int, preco: float) -> float:
    return preco * (1 - cadastro.buscar(id_).desconto)


assert preco_final(Cadastro(), 1, 100) == 90
assert preco_final(Cadastro(), 99, 100) == 100  # anônimo: sem desconto, sem if
```

## Quando usar e quando evitar

| Use quando | Evite quando |
| --- | --- |
| Existe um comportamento neutro óbvio (não logar, desconto zero) | A ausência é um erro que deve ser tratado explicitamente |
| O mesmo teste de None se repete em muitos lugares | Esconder a falta mascararia um bug (ex.: pagamento sem conta) |
| A interface é pequena | A interface é grande e o "nulo" exigiria dezenas de métodos vazios |

<Callout type="warning" title="Não esconda erros">
Se um pedido sem cliente é um bug, lance uma exceção. Null Object é para ausências legítimas, não para silenciar falhas.
</Callout>

## Relação com outros padrões

É uma forma especial de **Strategy** (a estratégia "não fazer nada") e costuma ser usado junto com **State** (um estado "vazio") e **Factory** (que decide devolver o real ou o nulo). Em Python também há o `None` como valor, mas ele não possui os métodos da interface, o que é justamente o problema.

## Na entrevista
