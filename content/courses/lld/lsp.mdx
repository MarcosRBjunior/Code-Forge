title: Princípio de substituição de Liskov
kind: lesson

O **Liskov Substitution Principle (LSP)** diz que, se `S` é subtipo de `T`, objetos de `S` devem poder ser usados em qualquer lugar onde `T` é esperado **sem que o programa se comporte de forma errada**. Não basta ter os mesmos métodos: a subclasse precisa honrar o **comportamento prometido** pela base.

## O problema

Herança cria uma promessa: "pode me usar como se eu fosse a base". Quando a subclasse quebra essa promessa, o código cliente precisa de `isinstance` e tratamentos especiais, e o polimorfismo deixa de funcionar.

## As regras do contrato

Uma subclasse respeita o LSP quando:

| Regra | Significado |
| --- | --- |
| Pré-condições não ficam mais fortes | a subclasse aceita pelo menos tudo o que a base aceitava |
| Pós-condições não ficam mais fracas | a subclasse entrega pelo menos o que a base garantia |
| Invariantes são preservadas | o que era sempre verdade na base continua sendo |
| Sem exceções novas inesperadas | não lança erros que o cliente da base não conhece |

## Exemplo que viola o LSP

Uma conta de poupança "é uma" conta? No mundo real parece que sim. Mas veja:

<CodeTabs>

```python
class Conta:
    def __init__(self, saldo: float = 0.0) -> None:
        self.saldo = saldo

    def depositar(self, valor: float) -> None:
        self.saldo += valor

    def sacar(self, valor: float) -> None:
        if valor > self.saldo:
            raise ValueError("saldo insuficiente")
        self.saldo -= valor


class ContaInvestimentoPrazoFixo(Conta):
    def sacar(self, valor: float) -> None:
        raise PermissionError("saque bloqueado até o vencimento")


def pagar_boleto(conta: Conta, valor: float) -> str:
    conta.sacar(valor)  # o contrato de Conta diz: com saldo, o saque funciona
    return "pago"


for c in [Conta(500), ContaInvestimentoPrazoFixo(500)]:
    try:
        print(pagar_boleto(c, 100))
    except PermissionError as e:
        print("surpresa:", e)
```

</CodeTabs>

`pagar_boleto` foi escrito para `Conta`. Com saldo suficiente, o contrato da base garante o saque. A subclasse lança um erro novo e quebra o cliente. Para "consertar", o cliente teria que testar o tipo, que é exatamente o que o LSP quer evitar.

## Versão corrigida

O problema é a hierarquia: nem toda conta permite saque. Modele as capacidades separadamente:

<CodeTabs>

```python
from abc import ABC, abstractmethod


class Conta(ABC):
    def __init__(self, saldo: float = 0.0) -> None:
        self.saldo = saldo

    def depositar(self, valor: float) -> None:
        self.saldo += valor

    @abstractmethod
    def resumo(self) -> str: ...


class ContaSacavel(Conta):
    def sacar(self, valor: float) -> None:
        if valor > self.saldo:
            raise ValueError("saldo insuficiente")
        self.saldo -= valor


class ContaCorrente(ContaSacavel):
    def resumo(self) -> str:
        return f"Corrente: R$ {self.saldo:.2f}"


class ContaInvestimentoPrazoFixo(Conta):
    def __init__(self, saldo: float, vencimento: str) -> None:
        super().__init__(saldo)
        self.vencimento = vencimento

    def resumo(self) -> str:
        return f"Prazo fixo até {self.vencimento}: R$ {self.saldo:.2f}"


def pagar_boleto(conta: ContaSacavel, valor: float) -> str:
    conta.sacar(valor)
    return "pago"


corrente = ContaCorrente(500)
investimento = ContaInvestimentoPrazoFixo(500, "2027-01")
print(pagar_boleto(corrente, 100))
for c in (corrente, investimento):  # ambas são Conta e funcionam onde Conta é esperada
    c.depositar(10)
    print(c.resumo())
```

## Outro sinal clássico: subclasse que restringe a base

Se `Quadrado` herda de `Retangulo` e alterar a largura também altera a altura, um código que faz `r.largura = 5; r.altura = 2` e espera área 10 quebra. A geometria diz "é um", mas o **comportamento** não é substituível. Em geral, isso se resolve com objetos imutáveis ou abandonando a herança.

<Callout type="warning" title="'É um' no mundo real não basta">
O teste do LSP é comportamental: o cliente da base continua correto com a subclasse? Se a resposta exige `isinstance`, a hierarquia está errada.
</Callout>
