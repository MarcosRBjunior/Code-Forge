## O problema que os padrões resolvem

Depois de algum tempo programando orientado a objetos, você percebe que certos problemas voltam sempre: "preciso trocar o algoritmo de cálculo de frete sem mexer no checkout", "preciso criar objetos com vinte campos opcionais", "preciso avisar três módulos quando um pedido muda de status". Cada time pode reinventar a solução, mas isso custa tempo e gera nomes diferentes para a mesma ideia.

Um **padrão de projeto** é uma solução recorrente, com nome, para um problema recorrente de organização de classes. Não é uma biblioteca nem um trecho de código para copiar: é um **molde** de colaboração entre objetos que você adapta ao seu contexto. O valor está em dois pontos:

- **Vocabulário comum.** Dizer "aqui eu usaria um Observer" comunica em três palavras o que levaria um parágrafo para explicar.
- **Trade-offs conhecidos.** Cada padrão já vem com o que ele resolve e o que ele custa (mais classes, mais indireção, mais difícil de depurar).

## As três famílias

| Família | Pergunta que responde | Exemplos neste curso |
| --- | --- | --- |
| Criacionais | Como criar objetos sem acoplar quem usa a quem constrói? | Singleton, Builder, Factory Method, Abstract Factory, Prototype |
| Estruturais | Como montar objetos e classes em estruturas maiores mantendo-as flexíveis? | Adapter, Facade, Decorator, Composite, Proxy, Bridge, Flyweight |
| Comportamentais | Como distribuir responsabilidades e comunicação entre objetos? | Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Visitor, Mediator, Memento, Iterator |

## Como um padrão aparece no código

Veja um exemplo pequeno, antes e depois. Um serviço de envio de recibos começa com um `if` por canal:

```python
class ServicoDeRecibos:
    def enviar(self, canal: str, destino: str, texto: str) -> str:
        if canal == "email":
            return f"[email para {destino}] {texto}"
        elif canal == "sms":
            return f"[sms para {destino}] {texto[:30]}"
        raise ValueError(f"canal desconhecido: {canal}")


print(ServicoDeRecibos().enviar("sms", "+55 11 99999-0000", "Seu pagamento de R$ 120,00 foi aprovado"))
```

Cada novo canal obriga a editar a mesma classe. Reorganizando com uma interface e objetos intercambiáveis (a ideia do Strategy), o serviço passa a depender de uma abstração:

```python
from abc import ABC, abstractmethod


class Canal(ABC):
    @abstractmethod
    def enviar(self, destino: str, texto: str) -> str: ...


class Email(Canal):
    def enviar(self, destino: str, texto: str) -> str:
        return f"[email para {destino}] {texto}"


class Sms(Canal):
    LIMITE = 30

    def enviar(self, destino: str, texto: str) -> str:
        return f"[sms para {destino}] {texto[: self.LIMITE]}"


class ServicoDeRecibos:
    def __init__(self, canal: Canal) -> None:
        self._canal = canal

    def enviar(self, destino: str, texto: str) -> str:
        return self._canal.enviar(destino, texto)


for canal in (Email(), Sms()):
    print(ServicoDeRecibos(canal).enviar("cliente", "Seu pagamento de R$ 120,00 foi aprovado"))
```

Agora adicionar WhatsApp é criar uma classe nova, sem tocar no serviço. Repare que o padrão é a **forma da colaboração** (serviço conhece só a interface `Canal`), não o código específico.

## Como estudar cada padrão

Para cada padrão dos próximos capítulos, fixe cinco coisas:

1. **O sintoma**: qual dor no código sugere o padrão.
2. **Os papéis**: quais classes participam e quem conhece quem.
3. **Uma implementação mínima** que você consiga escrever de memória em 10 minutos.
4. **Quando não usar**: todo padrão tem um custo de complexidade.
5. **Os vizinhos**: padrões com estrutura parecida e o critério que os diferencia (Decorator e Proxy, Strategy e State, Factory Method e Abstract Factory).

## Armadilhas comuns

- **Padrão como objetivo.** Aplicar padrões para "parecer sênior" gera código cheio de interfaces com uma única implementação. Comece simples e refatore para o padrão quando a dor aparecer.
- **Copiar a estrutura de Java para Python.** Em Python, funções são objetos de primeira classe e módulos já são singletons. Muitos padrões ficam menores: um Strategy pode ser apenas uma função passada como argumento.
- **Confundir nome com intenção.** Dois padrões podem ter o mesmo diagrama de classes e intenções diferentes. O que define o padrão é o problema que ele resolve.

<Callout type="tip" title="Regra prática">
Se você não consegue explicar em uma frase qual mudança futura o padrão torna barata, provavelmente ele não é necessário ainda.
</Callout>

## Na entrevista

Em entrevistas de LLD, o avaliador quer ver padrões surgindo **naturalmente** do problema, não uma lista decorada. Uma boa forma é narrar: "o cálculo de tarifa varia por tipo de veículo e vai ganhar novas regras, então vou isolar isso atrás de uma interface `PoliticaDeTarifa`; isso é um Strategy". Follow-ups comuns:

- "Por que não um `if` simples?" Responda com o eixo de mudança esperado.
- "Qual a diferença entre esse padrão e outro parecido?" Tenha o critério de distinção pronto.
- "Isso não é over-engineering?" Mostre que você sabe o custo e quando recuaria.
