O **Interface Segregation Principle (ISP)** diz que nenhum cliente deve ser obrigado a depender de métodos que não usa. Em vez de uma interface grande que tenta servir a todos, prefira várias interfaces pequenas, cada uma focada em um papel. Assim, cada implementação cumpre só os contratos que fazem sentido para ela.

## O problema

Interfaces "gordas" causam dois tipos de dor:

1. **Implementações forçadas.** A classe precisa implementar métodos que não fazem sentido, normalmente lançando erro ou deixando vazio, o que ainda viola o LSP.
2. **Acoplamento desnecessário.** Um cliente que só lê dados passa a depender de uma interface que também tem métodos de escrita e administração. Qualquer mudança neles pode forçar mudanças no cliente.

## Exemplo que viola o ISP

```python
from abc import ABC, abstractmethod


class Dispositivo(ABC):
    @abstractmethod
    def imprimir(self, doc: str) -> str: ...

    @abstractmethod
    def digitalizar(self) -> str: ...

    @abstractmethod
    def enviar_fax(self, numero: str, doc: str) -> str: ...


class Multifuncional(Dispositivo):
    def imprimir(self, doc: str) -> str:
        return f"imprimindo {doc}"

    def digitalizar(self) -> str:
        return "imagem.png"

    def enviar_fax(self, numero: str, doc: str) -> str:
        return f"fax para {numero}"


class ImpressoraSimples(Dispositivo):
    def imprimir(self, doc: str) -> str:
        return f"imprimindo {doc}"

    def digitalizar(self) -> str:
        raise NotImplementedError("não tenho scanner")

    def enviar_fax(self, numero: str, doc: str) -> str:
        raise NotImplementedError("não tenho fax")


print(ImpressoraSimples().imprimir("contrato.pdf"))
try:
    ImpressoraSimples().digitalizar()
except NotImplementedError as e:
    print("método inútil:", e)
```

`ImpressoraSimples` é obrigada a carregar dois métodos que só existem para lançar erro. Pior: o tipo `Dispositivo` promete digitalização, então um cliente pode chamar `digitalizar` e quebrar em tempo de execução.

## Versão corrigida

Separe a interface por papel. Cada classe realiza só os papéis que cumpre, e cada cliente depende só do papel que usa:

```python
from abc import ABC, abstractmethod


class Impressora(ABC):
    @abstractmethod
    def imprimir(self, doc: str) -> str: ...


class Scanner(ABC):
    @abstractmethod
    def digitalizar(self) -> str: ...


class Fax(ABC):
    @abstractmethod
    def enviar_fax(self, numero: str, doc: str) -> str: ...


class ImpressoraSimples(Impressora):
    def imprimir(self, doc: str) -> str:
        return f"[simples] imprimindo {doc}"


class Multifuncional(Impressora, Scanner, Fax):
    def imprimir(self, doc: str) -> str:
        return f"[multi] imprimindo {doc}"

    def digitalizar(self) -> str:
        return "imagem.png"

    def enviar_fax(self, numero: str, doc: str) -> str:
        return f"[multi] fax para {numero}"


class FilaDeImpressao:
    """Cliente que só precisa imprimir."""

    def __init__(self, impressora: Impressora) -> None:
        self.impressora = impressora

    def processar(self, docs: list[str]) -> list[str]:
        return [self.impressora.imprimir(d) for d in docs]


class Digitalizacao:
    """Cliente que só precisa digitalizar."""

    def __init__(self, scanner: Scanner) -> None:
        self.scanner = scanner

    def capturar(self) -> str:
        return self.scanner.digitalizar()


print(FilaDeImpressao(ImpressoraSimples()).processar(["a.pdf", "b.pdf"]))
print(FilaDeImpressao(Multifuncional()).processar(["c.pdf"]))
print(Digitalizacao(Multifuncional()).capturar())
```

Nenhuma classe tem método inútil. `FilaDeImpressao` aceita qualquer impressora, simples ou multifuncional, e `Digitalizacao` nem sabe que impressoras existem.

## Como dividir uma interface

- Agrupe métodos pelo **cliente que os usa**, não pela implementação que os oferece.
- Desconfie de interfaces com nomes genéricos (`Gerenciavel`, `Servico`) e muitos métodos.
- Um bom indício: se clientes diferentes usam subconjuntos disjuntos dos métodos, há interfaces escondidas ali.

| Interface gorda | Interfaces segregadas |
| --- | --- |
| `Repositorio` com ler, escrever, apagar, migrar, fazer backup | `Leitor`, `Escritor`, `Administracao` |
| `Funcionario` com trabalhar, receber salário, comer no refeitório | `Trabalhador`, `Remunerado` |

<Callout type="note" title="ISP em Python com Protocol">
Com `typing.Protocol`, o próprio cliente pode declarar a interface mínima de que precisa, mesmo que a classe concreta tenha muitos métodos. É uma forma leve de aplicar o ISP sem mexer nas classes existentes.
</Callout>

## Trade-offs

Segregar demais gera uma poeira de interfaces de um método cada, difícil de navegar. O ponto de equilíbrio é o **papel**: métodos que sempre são usados juntos pelo mesmo cliente ficam juntos.

## Na entrevista

O ISP aparece quando há capacidades opcionais: veículos que voam ou não, usuários com permissões diferentes, dispositivos com recursos variados. Diga: "em vez de uma interface `Veiculo` com `voar`, separo `Terrestre` e `Voador`".
