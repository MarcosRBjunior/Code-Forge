Boa parte de um design bom nasce de uma pergunta simples: **quais são as classes?** Errar aqui custa caro, porque tudo depois (relações, padrões, código) se apoia nessa escolha. Há uma técnica prática: ler o enunciado como um texto, marcar substantivos e verbos, e filtrar o que realmente merece virar uma classe.

## Substantivos, verbos e adjetivos

Considere o enunciado: "Uma biblioteca empresta livros a membros. Cada empréstimo tem prazo de 14 dias e gera multa se atrasar."

- **Substantivos** (candidatas a classes): biblioteca, livro, membro, empréstimo, prazo, multa.
- **Verbos** (candidatos a métodos): emprestar, devolver, calcular multa.
- **Adjetivos e valores** (candidatos a atributos): prazo de 14 dias, atrasado.

Nem todo substantivo vira classe. Aplique o filtro:

| Pergunta | Se a resposta for sim |
| --- | --- |
| Tem estado próprio que muda? | Provável classe |
| Tem comportamento (regras)? | Provável classe |
| É só um dado simples (número, texto)? | Atributo |
| É um conjunto fixo de opções? | Enum |
| É o sistema inteiro? | Classe orquestradora (fachada) |

Aqui: `Livro`, `Membro` e `Emprestimo` são classes; `prazo` é um atributo do empréstimo; `multa` pode ser um método que calcula um valor (ou uma classe, se houver políticas diferentes).

## Quem é dono de cada coisa

Depois de listar as classes, atribua cada comportamento à classe que **tem os dados necessários**. Calcular multa depende de data de devolução e prazo, ambos do empréstimo, então o método vive em `Emprestimo`. Essa heurística, conhecida como *information expert*, evita que lógica vá parar numa classe gerente gigante.

```python
from dataclasses import dataclass
from enum import Enum


class StatusLivro(Enum):
    DISPONIVEL = 1
    EMPRESTADO = 2


@dataclass
class Livro:
    titulo: str
    status: StatusLivro = StatusLivro.DISPONIVEL


@dataclass
class Membro:
    nome: str


class Emprestimo:
    PRAZO_DIAS = 14
    MULTA_DIA = 2.0

    def __init__(self, livro: Livro, membro: Membro, dia_retirada: int) -> None:
        self.livro = livro
        self.membro = membro
        self.dia_retirada = dia_retirada

    def multa(self, dia_devolucao: int) -> float:
        atraso = dia_devolucao - self.dia_retirada - self.PRAZO_DIAS
        return max(0, atraso) * self.MULTA_DIA


class Biblioteca:
    def __init__(self) -> None:
        self.emprestimos: list[Emprestimo] = []

    def emprestar(self, livro: Livro, membro: Membro, dia: int) -> Emprestimo:
        if livro.status is not StatusLivro.DISPONIVEL:
            raise ValueError("livro indisponível")
        livro.status = StatusLivro.EMPRESTADO
        e = Emprestimo(livro, membro, dia)
        self.emprestimos.append(e)
        return e

    def devolver(self, e: Emprestimo, dia: int) -> float:
        e.livro.status = StatusLivro.DISPONIVEL
        return e.multa(dia)


b = Biblioteca()
livro, ana = Livro("Clean Code"), Membro("Ana")
emp = b.emprestar(livro, ana, dia=1)
assert b.devolver(emp, dia=20) == 10.0  # atraso de 20 - 1 - 14 = 5 dias, a 2.0 por dia
```

Cada comportamento ficou na classe que tem os dados: `Emprestimo` calcula a multa e `Biblioteca` coordena o fluxo.

## Armadilhas

- **Classes que são verbos disfarçados**: `CalculadorDeMulta` com um único método, sem estado, costuma ser só uma função ou um método da entidade.
- **Classe-deus**: `Sistema` ou `Gerenciador` que faz tudo. Distribua responsabilidades.
- **Entidades demais**: modelar cada detalhe (como `Prazo`) quando um atributo basta.
- **Entidades de menos**: usar dicionários e listas soltas onde existe um conceito de negócio com regras.

<Callout type="tip" title="Teste do porquê">
Para cada classe, complete a frase: "Esta classe existe para ___." Se a resposta for vaga ou tiver um "e" no meio, provavelmente são duas classes.
</Callout>
