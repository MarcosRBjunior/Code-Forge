Duas partes do sistema trabalham em ritmos diferentes: uma gera trabalho (pedidos chegando, linhas lidas de um arquivo) e outra o processa (cobrança, gravação). Se a geradora chamasse a processadora diretamente, qualquer lentidão de uma travaria a outra. **Produtor-consumidor** coloca entre elas um **buffer compartilhado**: produtores colocam itens, consumidores retiram, e os dois lados evoluem de forma independente.

## O problema de coordenar

Um buffer compartilhado exige regras:

- Se o buffer está **cheio**, o produtor precisa esperar.
- Se está **vazio**, o consumidor precisa esperar.
- Acessos simultâneos não podem corromper a estrutura.

Implementar isso com travas e variáveis de condição é clássico e fácil de errar. Em Python, `queue.Queue` entrega tudo isso pronto: é thread-safe e bloqueia sozinha quando cheia ou vazia.

## Exemplo

```python
import queue
import threading

SENTINELA = None  # sinaliza fim da produção

buffer: queue.Queue = queue.Queue(maxsize=3)  # limitado: contrapressão
resultados: list[int] = []
trava = threading.Lock()


def produtor(n: int) -> None:
    for i in range(n):
        buffer.put(i)  # bloqueia se o buffer estiver cheio
    buffer.put(SENTINELA)


def consumidor() -> None:
    while True:
        item = buffer.get()  # bloqueia se estiver vazio
        if item is SENTINELA:
            break
        with trava:
            resultados.append(item * 10)


t1 = threading.Thread(target=produtor, args=(8,))
t2 = threading.Thread(target=consumidor)
t1.start()
t2.start()
t1.join()
t2.join()

assert resultados == [0, 10, 20, 30, 40, 50, 60, 70]
print(resultados)
```

Com um único produtor e um consumidor a ordem é preservada. Com vários consumidores, você coloca uma sentinela por consumidor, e a ordem de saída deixa de ser garantida.

## Variações

| Cenário | Ajuste |
| --- | --- |
| Vários produtores | Contar quantos terminaram antes de enviar as sentinelas |
| Vários consumidores | Uma sentinela para cada consumidor |
| Itens com prioridade | `queue.PriorityQueue` |
| Buffer ilimitado | `Queue()` sem `maxsize`: cuidado com memória |
| Processos em vez de threads | `multiprocessing.Queue` |

<Callout type="tip" title="Contrapressão">
Um buffer limitado é uma ferramenta, não um incômodo. Quando o consumidor é mais lento, o produtor desacelera em vez de encher a memória. Em sistemas distribuídos, o equivalente é uma fila de mensagens com limite.
</Callout>

## Onde aparece

- **Thread pool**: a fila de tarefas é o buffer; quem chama `submit` é o produtor e os workers são os consumidores.
- **Logging assíncrono**: a aplicação produz mensagens e uma thread de log as grava.
- **Pipelines**: a saída de um estágio é a entrada do próximo, encadeando buffers.
- **Sistemas de mensagens**: o broker é o buffer entre serviços.

## Armadilhas

- **Deadlock por término**: consumidores que ficam esperando para sempre porque ninguém enviou a sentinela.
- **Perda de itens** ao encerrar abruptamente: decida se descarta ou esvazia a fila.
- **Contenção**: um único buffer disputado por muitas threads vira gargalo.
- **Esquecer a trava** ao atualizar estado compartilhado fora da fila (como a lista de resultados acima).
