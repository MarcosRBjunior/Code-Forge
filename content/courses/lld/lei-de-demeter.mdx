A **Lei de Demeter**, também chamada de *princípio do menor conhecimento*, diz que um objeto deve conversar apenas com seus "amigos próximos" e não com os amigos dos amigos. Em termos práticos: evite cadeias como `pedido.cliente.endereco.cidade.nome`. Cada ponto a mais é uma dependência a mais da estrutura interna de outro objeto.

## A regra formal

Dentro de um método `m` de um objeto `O`, você só deveria chamar métodos de:

1. o próprio `O` (`self`);
2. objetos recebidos como parâmetro de `m`;
3. objetos criados dentro de `m`;
4. atributos diretos de `O`.

Chamar um método do objeto **retornado** por outro método já é falar com um estranho.

## O problema

Considere um caixa de padaria cobrando um cliente:

```python
class Carteira:
    def __init__(self, saldo: float) -> None:
        self.saldo = saldo


class Cliente:
    def __init__(self, nome: str, carteira: Carteira) -> None:
        self.nome = nome
        self.carteira = carteira


class Caixa:
    def cobrar(self, cliente: Cliente, valor: float) -> bool:
        # o caixa mexe direto na carteira do cliente
        if cliente.carteira.saldo >= valor:
            cliente.carteira.saldo -= valor
            return True
        return False


c = Cliente("Rui", Carteira(20.0))
print(Caixa().cobrar(c, 7.5), c.carteira.saldo)
```

O `Caixa` sabe que o cliente tem uma carteira, que a carteira tem um saldo e como o saldo é debitado. Se amanhã o cliente puder pagar com cartão ou a carteira passar a registrar extrato, o `Caixa` quebra. Na vida real, o caixa não enfia a mão no bolso de ninguém: ele pede o pagamento.

## Versão que respeita Demeter

```python
class Carteira:
    def __init__(self, saldo: float) -> None:
        self._saldo = saldo
        self.extrato: list[float] = []

    def debitar(self, valor: float) -> bool:
        if valor > self._saldo:
            return False
        self._saldo -= valor
        self.extrato.append(-valor)
        return True

    @property
    def saldo(self) -> float:
        return self._saldo


class Cliente:
    def __init__(self, nome: str, carteira: Carteira) -> None:
        self.nome = nome
        self._carteira = carteira

    def pagar(self, valor: float) -> bool:
        return self._carteira.debitar(valor)


class Caixa:
    def cobrar(self, cliente: Cliente, valor: float) -> bool:
        return cliente.pagar(valor)


carteira = Carteira(20.0)
rui = Cliente("Rui", carteira)
assert Caixa().cobrar(rui, 7.5)
assert not Caixa().cobrar(rui, 50)
print(carteira.saldo, carteira.extrato)
```

Agora o `Caixa` depende só de `Cliente.pagar`. Como o cliente paga é problema dele. Esse estilo também é conhecido como **Tell, Don't Ask**: em vez de perguntar o estado e decidir por fora, você diz ao objeto o que fazer.

## Quando a cadeia não é violação

- **Estruturas de dados puras**: `config["db"]["host"]` ou um DTO sem comportamento. Demeter fala de objetos com comportamento e encapsulamento.
- **Interfaces fluentes**: `consulta.filtrar(x).ordenar(y).limitar(10)` retorna sempre o mesmo tipo de objeto; você não está navegando por estranhos.
- **Value objects estáveis**: `data.ano` em um objeto de data padrão da linguagem dificilmente vai mudar.

## Trade-offs

Seguir Demeter à risca pode gerar **métodos de repasse** demais: `Cliente.cidade()` que chama `endereco.cidade()`, que chama outro método. Se o objeto do meio só repassa chamadas, talvez o modelo esteja errado ou o cliente realmente precise conhecer o endereço. Use a regra como alerta, não como lei absoluta.

| Benefício | Custo |
| --- | --- |
| Menos acoplamento à estrutura interna | Métodos de delegação extras |
| Mudanças internas não se propagam | Interfaces maiores nos objetos do meio |
| Testes com menos mocks encadeados | Pode esconder modelagem ruim |

<Callout type="tip" title="Conte os pontos">
Um atalho útil durante uma revisão: se uma linha tem mais de um ponto navegando entre objetos de domínio diferentes, pergunte se o primeiro objeto não deveria oferecer esse comportamento.
</Callout>
