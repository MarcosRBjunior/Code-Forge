## O problema

Imagine o cálculo de frete de uma loja virtual. No começo existe só "transportadora padrão". Depois chegam retirada na loja, entrega expressa por motoboy e frete grátis acima de certo valor. A primeira versão costuma virar um `if/elif` gigante dentro do método `calcular_frete`. Cada nova modalidade obriga você a abrir a mesma função, mexer em código que já funciona e retestar tudo.

O Strategy resolve exatamente isso: **separar uma família de algoritmos intercambiáveis em objetos próprios**, para que o código que usa o algoritmo (o contexto) não precise saber qual variação está rodando. Trocar o comportamento vira trocar um objeto, não editar um condicional.

## Estrutura

```text
+------------------+         usa         +----------------------+
|  Contexto        |-------------------->|  Estrategia (iface)  |
|------------------|                     |----------------------|
| - estrategia     |                     | + executar(dados)    |
| + operar()       |                     +----------------------+
+------------------+                        ^      ^       ^
                                            |      |       |
                              EstrategiaA  EstrategiaB  EstrategiaC
```

- **Estratégia**: interface comum a todos os algoritmos.
- **Estratégias concretas**: cada uma implementa uma variação.
- **Contexto**: guarda uma referência para a estratégia e delega o trabalho a ela. Recebe a estratégia pelo construtor ou por um setter.

## Implementação em Python

Vamos modelar o frete de um pedido. O pedido não sabe como o frete é calculado; ele só pede para a estratégia.

```python
from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass
class Pedido:
    valor_itens: float
    peso_kg: float
    distancia_km: float


class EstrategiaFrete(ABC):
    @abstractmethod
    def calcular(self, pedido: Pedido) -> float: ...


class FretePadrao(EstrategiaFrete):
    def calcular(self, pedido: Pedido) -> float:
        return round(8.0 + pedido.peso_kg * 1.5 + pedido.distancia_km * 0.10, 2)


class FreteExpresso(EstrategiaFrete):
    def calcular(self, pedido: Pedido) -> float:
        base = FretePadrao().calcular(pedido)
        return round(base * 1.8, 2)


class RetiradaNaLoja(EstrategiaFrete):
    def calcular(self, pedido: Pedido) -> float:
        return 0.0


class FreteGratisAcimaDe(EstrategiaFrete):
    """Envolve outra estratégia e zera o frete acima de um limite."""

    def __init__(self, limite: float, senao: EstrategiaFrete):
        self.limite = limite
        self.senao = senao

    def calcular(self, pedido: Pedido) -> float:
        if pedido.valor_itens >= self.limite:
            return 0.0
        return self.senao.calcular(pedido)


class Checkout:
    def __init__(self, estrategia: EstrategiaFrete):
        self._estrategia = estrategia

    def trocar_frete(self, estrategia: EstrategiaFrete) -> None:
        self._estrategia = estrategia

    def total(self, pedido: Pedido) -> float:
        return round(pedido.valor_itens + self._estrategia.calcular(pedido), 2)


pedido = Pedido(valor_itens=180.0, peso_kg=2.0, distancia_km=40)
checkout = Checkout(FretePadrao())
print("padrão:", checkout.total(pedido))

checkout.trocar_frete(FreteExpresso())
print("expresso:", checkout.total(pedido))

checkout.trocar_frete(RetiradaNaLoja())
print("retirada:", checkout.total(pedido))

checkout.trocar_frete(FreteGratisAcimaDe(150.0, FretePadrao()))
print("promo:", checkout.total(pedido))
```

Repare que adicionar "frete por drone" é só criar uma classe nova. `Checkout` não muda. Isso é o princípio aberto/fechado na prática.

### Versão enxuta com funções

Em Python, funções são objetos de primeira classe. Quando a estratégia não tem estado nem precisa de vários métodos, uma função basta:

```python
from typing import Callable

Desconto = Callable[[float], float]

def sem_desconto(valor: float) -> float:
    return valor

def black_friday(valor: float) -> float:
    return valor * 0.7

def cupom_fixo(valor_cupom: float) -> Desconto:
    return lambda valor: max(0.0, valor - valor_cupom)

def aplicar(valor: float, regra: Desconto) -> float:
    return round(regra(valor), 2)

for regra in (sem_desconto, black_friday, cupom_fixo(25)):
    print(aplicar(200.0, regra))
```

Mencione essa alternativa na entrevista: mostra que você conhece o padrão e também sabe quando ele é cerimônia demais.

## Quando usar e quando evitar

**Use quando:**

- Existem várias formas de fazer a mesma tarefa e a escolha acontece em tempo de execução (configuração, perfil do cliente, flag de feature).
- Um condicional sobre "tipo de algoritmo" aparece em vários lugares.
- Você quer testar cada algoritmo isoladamente.

**Evite quando:**

- Há só duas variações estáveis que nunca vão mudar. Um `if` é mais legível.
- As variações dependem de muitos dados internos do contexto. Você acabaria expondo tudo para a estratégia, quebrando o encapsulamento.

<Callout type="tip" title="Quem escolhe a estratégia?">
O padrão não diz quem decide qual estratégia usar. Normalmente é o código que monta o objeto (uma fábrica, a configuração ou a injeção de dependência). Deixar o contexto escolher sozinho com um if traz o problema de volta.
</Callout>

## Padrões parecidos

| Padrão | Diferença principal |
| --- | --- |
| State | A estrutura é quase igual, mas no State os próprios estados trocam o objeto atual. No Strategy, quem troca é o cliente, e as estratégias não se conhecem. |
| Template Method | Varia partes de um algoritmo via herança. Strategy troca o algoritmo inteiro via composição. |
| Command | Encapsula uma ação a executar (com desfazer, fila, histórico). Strategy encapsula **como** fazer algo, não **o que** fazer. |
| Decorator | Adiciona comportamento em volta do objeto; Strategy substitui o miolo. O `FreteGratisAcimaDe` acima é uma estratégia que se parece com decorator, e tudo bem. |

## Na entrevista

- Em problemas como estacionamento (tarifa por hora, diária, mensalista), carrinho (descontos) ou ride-sharing (preço dinâmico), diga em voz alta: "o cálculo de preço vai ser uma estratégia, assim posso adicionar novas regras sem mexer na classe principal".
- Follow-ups comuns: "como você escolheria a estratégia?" (fábrica ou mapa de nome para classe), "e se precisar combinar duas regras?" (composição de estratégias, como no exemplo do frete grátis), "qual a diferença para State?".
- Não crie uma estratégia para tudo. Entrevistadores percebem quando o padrão está ali só para aparecer.
