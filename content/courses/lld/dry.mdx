**DRY** vem de *Don't Repeat Yourself*: cada pedaço de **conhecimento** do sistema deve ter uma representação única e autoritativa. A palavra importante é conhecimento. DRY não é uma caça a linhas parecidas; é garantir que uma regra de negócio, um formato ou uma constante more em um lugar só, para que mudar essa regra exija mudar um único ponto.

## O problema

Imagine que a regra "cliente VIP tem 10% de desconto" aparece no carrinho, no cálculo da nota fiscal e no relatório de vendas. Um dia o desconto vira 12%. Você atualiza dois dos três lugares, esquece o terceiro, e agora o relatório diverge do que o cliente pagou. Esse é o custo real da duplicação: **inconsistência silenciosa**, não apenas digitação extra.

## Versão DRY

Extraia o conhecimento para um único dono e faça os outros consultarem esse dono:

<CodeTabs>

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class PoliticaDesconto:
    percentual_vip: float = 0.10

    def aplicar(self, valor: float, vip: bool) -> float:
        fator = 1 - self.percentual_vip if vip else 1
        return round(valor * fator, 2)


class Carrinho:
    def __init__(self, politica: PoliticaDesconto) -> None:
        self.politica = politica

    def total(self, itens: list[float], vip: bool) -> float:
        return self.politica.aplicar(sum(itens), vip)


class RelatorioVendas:
    def __init__(self, politica: PoliticaDesconto) -> None:
        self.politica = politica

    def receita(self, pedidos: list[tuple[list[float], bool]]) -> float:
        return round(sum(self.politica.aplicar(sum(i), v) for i, v in pedidos), 2)


politica = PoliticaDesconto()
assert Carrinho(politica).total([100, 50], True) == 135.0
assert RelatorioVendas(politica).receita([([100, 50], True), ([20], False)]) == 155.0
print("Desconto centralizado: mudar 10% para 12% é editar um lugar só")
```

import java.util.*;

class PoliticaDesconto {
    final double percentualVip;

    PoliticaDesconto(double percentualVip) { this.percentualVip = percentualVip; }

    PoliticaDesconto() { this(0.10); }

    double aplicar(double valor, boolean vip) {
        double fator = vip ? 1 - percentualVip : 1;
        return Math.round(valor * fator * 100) / 100.0;
    }
}

class Pedido {
    final double[] itens;
    final boolean vip;

    Pedido(double[] itens, boolean vip) {
        this.itens = itens;
        this.vip = vip;
    }
}

class Util {
    static double soma(double[] xs) {
        double s = 0;
        for (double x : xs) s += x;
        return s;
    }
}

class Carrinho {
    private final PoliticaDesconto politica;

    Carrinho(PoliticaDesconto politica) { this.politica = politica; }

    double total(double[] itens, boolean vip) { return politica.aplicar(Util.soma(itens), vip); }
}

class RelatorioVendas {
    private final PoliticaDesconto politica;

    RelatorioVendas(PoliticaDesconto politica) { this.politica = politica; }

    double receita(List<Pedido> pedidos) {
        double total = 0;
        for (Pedido p : pedidos) total += politica.aplicar(Util.soma(p.itens), p.vip);
        return Math.round(total * 100) / 100.0;
    }
}

## Duplicação acidental versus duplicação real

Nem todo código parecido é violação de DRY. Duas funções podem ter o mesmo corpo hoje e representar conhecimentos diferentes, que vão evoluir separadamente. Por exemplo, "prazo de devolução de 30 dias" e "validade do cupom de 30 dias" usam o mesmo número, mas são regras de áreas distintas. Uni-las numa constante `TRINTA_DIAS` cria um acoplamento falso: quando o marketing mudar a validade do cupom, a devolução muda junto sem ninguém perceber.

| Situação | Aplicar DRY? |
| --- | --- |
| Mesma regra de negócio em vários lugares | Sim, extraia para um dono |
| Mesmo formato de data ou moeda espalhado | Sim, crie um formatador |
| Código parecido com motivos de mudança diferentes | Não, mantenha separado |
| Duas linhas iguais em testes, por legibilidade | Geralmente não |

<Callout type="tip" title="Regra de três">
Uma heurística prática: tolere a primeira repetição e extraia na terceira. Com três ocorrências você já entende o que é comum e o que varia, e a abstração sai melhor do que uma extraída às pressas.
</Callout>

## Armadilhas

- **Abstração errada**: uma função genérica cheia de flags (`processar(x, modo=1, ignorar=True)`) para atender casos que só pareciam iguais. Às vezes, duplicar é mais barato que manter a abstração errada.
- **DRY além do código**: o princípio vale também para esquemas, documentação e configuração. Se a mesma lista de status está no banco, no front e no back, gere uma a partir da outra ou use um enum compartilhado.
