Enquanto o diagrama de classes mostra *quem existe*, o de sequência mostra *quem conversa com quem, e em que ordem*. Ele é a melhor forma de explicar um fluxo, como "finalizar compra", e de validar se as responsabilidades do seu design estão bem distribuídas: se uma classe precisa chamar dez outras, algo está errado.

## Elementos

- **Participante** (linha de vida): objeto ou componente, desenhado no topo com uma linha vertical tracejada descendo.
- **Mensagem**: seta horizontal de um participante para outro, de cima para baixo na ordem em que ocorre. Seta cheia é chamada síncrona; tracejada é retorno.
- **Ativação**: barra estreita sobre a linha de vida enquanto o objeto está trabalhando.
- **Fragmentos**: caixas `alt` (se/senão), `loop` (repetição) e `opt` (opcional).

## Exemplo: finalizar pedido

```text
Cliente      Pedido        Estoque      Pagamento
  |  fechar()  |              |             |
  |----------->|              |             |
  |            | reservar()   |             |
  |            |------------->|             |
  |            |    ok        |             |
  |            |<-------------|             |
  |            | cobrar(total)              |
  |            |--------------------------->|
  |            |          aprovado          |
  |            |<---------------------------|
  |  confirmado|              |             |
  |<-----------|              |             |
```

Leia de cima para baixo: o `Pedido` orquestra, o `Estoque` reserva e o `Pagamento` cobra. Se a cobrança falhasse, um fragmento `alt` mostraria o caminho de liberar a reserva.

## Do diagrama ao código

Cada seta vira uma chamada de método. O código abaixo reproduz a sequência, incluindo o caminho alternativo:

```python
class Estoque:
    def __init__(self, qtd: int) -> None:
        self.qtd = qtd

    def reservar(self, n: int) -> bool:
        if self.qtd >= n:
            self.qtd -= n
            return True
        return False

    def liberar(self, n: int) -> None:
        self.qtd += n


class Pagamento:
    def cobrar(self, valor: float) -> bool:
        return valor <= 100


class Pedido:
    def __init__(self, estoque: Estoque, pagamento: Pagamento) -> None:
        self.estoque = estoque
        self.pagamento = pagamento

    def fechar(self, qtd: int, total: float) -> str:
        if not self.estoque.reservar(qtd):
            return "sem estoque"
        if not self.pagamento.cobrar(total):  # fragmento alt
            self.estoque.liberar(qtd)
            return "pagamento recusado"
        return "confirmado"


estoque = Estoque(5)
pedido = Pedido(estoque, Pagamento())
assert pedido.fechar(2, 80) == "confirmado"
assert pedido.fechar(2, 500) == "pagamento recusado"
assert estoque.qtd == 3  # a reserva foi devolvida
print("fluxo ok")
```

## Quando usar cada diagrama

| Pergunta | Diagrama |
| --- | --- |
| Quais classes e relações? | Classes |
| Em que ordem as coisas acontecem entre objetos? | Sequência |
| Qual o fluxo de decisões de um processo? | Atividades |
| Como um objeto muda de estado? | Máquina de estados |

## Armadilhas

- **Participantes demais**: mostre só os que importam para o fluxo. Mais de cinco já pesa.
- **Esquecer o caminho de erro**: o entrevistador quase sempre pergunta "e se falhar?".
- **Misturar fluxos**: um diagrama por cenário (sucesso, falha), em vez de tudo junto.

## Na entrevista

Desenhe um sequência para o fluxo mais crítico depois de definir as classes. Ele revela métodos que faltam: toda seta que chega num participante precisa de um método correspondente. Follow-ups: "e se o pagamento falhar?", "isso é síncrono?", "quem é o dono da transação?".
