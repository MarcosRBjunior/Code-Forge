Regras de filtragem tendem a crescer de forma desorganizada: "produtos ativos, com estoque, abaixo de 100 reais ou em promoção". Se cada combinação vira um `if` gigante ou um método novo (`buscar_ativos_baratos_em_promocao`), o código explode. O padrão **Specification** encapsula cada critério num objeto pequeno com um método `satisfeito_por(objeto)`, e permite **combinar** critérios com E, OU e NÃO.

## A ideia

Cada regra é uma peça reutilizável. Combinar peças gera regras novas sem escrever lógica nova:

```text
ativo E (barato OU promocao) E NÃO esgotado
```

## Implementação

```python
from __future__ import annotations
from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass
class Produto:
    nome: str
    preco: float
    estoque: int
    ativo: bool = True
    promocao: bool = False


class Especificacao(ABC):
    @abstractmethod
    def satisfeita_por(self, p: Produto) -> bool: ...

    def e(self, outra: Especificacao) -> Especificacao:
        return E(self, outra)

    def ou(self, outra: Especificacao) -> Especificacao:
        return Ou(self, outra)

    def nao(self) -> Especificacao:
        return Nao(self)


class E(Especificacao):
    def __init__(self, a: Especificacao, b: Especificacao) -> None:
        self.a, self.b = a, b

    def satisfeita_por(self, p: Produto) -> bool:
        return self.a.satisfeita_por(p) and self.b.satisfeita_por(p)


class Ou(Especificacao):
    def __init__(self, a: Especificacao, b: Especificacao) -> None:
        self.a, self.b = a, b

    def satisfeita_por(self, p: Produto) -> bool:
        return self.a.satisfeita_por(p) or self.b.satisfeita_por(p)


class Nao(Especificacao):
    def __init__(self, a: Especificacao) -> None:
        self.a = a

    def satisfeita_por(self, p: Produto) -> bool:
        return not self.a.satisfeita_por(p)


class Ativo(Especificacao):
    def satisfeita_por(self, p: Produto) -> bool:
        return p.ativo


class PrecoAte(Especificacao):
    def __init__(self, limite: float) -> None:
        self.limite = limite

    def satisfeita_por(self, p: Produto) -> bool:
        return p.preco <= self.limite


class EmPromocao(Especificacao):
    def satisfeita_por(self, p: Produto) -> bool:
        return p.promocao


class Esgotado(Especificacao):
    def satisfeita_por(self, p: Produto) -> bool:
        return p.estoque == 0


catalogo = [
    Produto("Mouse", 50, 10),
    Produto("Teclado", 250, 5, promocao=True),
    Produto("Monitor", 900, 0),
    Produto("Cabo", 20, 0),
    Produto("Webcam", 300, 3, ativo=False, promocao=True),
]

regra = Ativo().e(PrecoAte(100).ou(EmPromocao())).e(Esgotado().nao())
nomes = [p.nome for p in catalogo if regra.satisfeita_por(p)]
assert nomes == ["Mouse", "Teclado"]
print(nomes)
```

A regra final lê quase como a frase original, e cada peça tem um teste simples e isolado.

## Quando vale a pena

| Situação | Specification? |
| --- | --- |
| Filtros combináveis em tempo de execução (busca avançada) | Sim |
| Regras de elegibilidade reutilizadas em vários lugares | Sim |
| Um único filtro fixo | Não, uma função basta |
| Consultas pesadas em banco | Cuidado: traduza para a consulta, não filtre tudo em memória |

Em Python, funções de ordem superior (`lambda`) resolvem casos simples. A classe vale quando a regra tem nome de negócio, parâmetros e será combinada ou testada em separado.

<Callout type="tip" title="Parentes próximos">
Specification lembra Strategy (um critério intercambiável) e Composite (E e OU compõem outras especificações como uma árvore). A combinação dos dois é a essência do padrão.
</Callout>

## Armadilhas

- **Explosão de classes** para regras triviais: use funções quando bastar.
- **Filtrar em memória** o que o banco faria melhor: com muitos dados, converta a especificação em consulta.
- **Estado escondido**: especificações devem ser puras, sem efeitos colaterais.

## Na entrevista

Aparece em sistemas de busca e filtro: estacionamento por tipo de vaga, catálogo de produtos, regras de promoção. Follow-ups: "como adicionar um novo filtro sem mudar o código existente?" (resposta: nova classe, princípio aberto/fechado) e "como combinaria regras?".
