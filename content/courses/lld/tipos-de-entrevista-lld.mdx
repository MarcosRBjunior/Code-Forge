"Entrevista de LLD" é um rótulo guarda-chuva. Empresas diferentes usam formatos diferentes, e o que conta como uma boa resposta muda bastante entre eles. Saber qual formato você vai enfrentar define como gastar os 45 a 90 minutos disponíveis.

## Os quatro formatos mais comuns

| Formato | Duração típica | O que entregar | Peso do código |
| --- | --- | --- | --- |
| Object-Oriented Design (OOD) | 45–60 min | classes, relações e fluxo principal discutidos | médio |
| Machine coding | 90–120 min | código funcional, rodando, com testes simples | alto |
| Design de API/biblioteca | 45 min | interface pública, contratos e exemplos de uso | médio |
| Revisão/refatoração de código | 45 min | diagnóstico de problemas e versão melhorada | alto |

### 1. Object-Oriented Design

O formato clássico: "projete um estacionamento", "projete um sistema de biblioteca". Você conversa com o entrevistador, levanta requisitos, propõe entidades, desenha relações e escreve o código das classes centrais. O foco é o **raciocínio**: por que essa classe existe, por que essa relação é composição e não herança.

### 2. Machine coding

Comum em empresas que querem ver código de produção. Você recebe um enunciado detalhado e precisa entregar algo que **roda**, normalmente em uma IDE, às vezes com testes. Aqui um design lindo que não executa vale pouco. Priorize o fluxo principal funcionando e depois estenda.

### 3. Design de API ou biblioteca

Pedem algo como "projete uma biblioteca de rate limiting que outros times vão usar". O centro é a **interface pública**: nomes, parâmetros, erros, extensibilidade. Pense em quem chama seu código.

### 4. Revisão e refatoração

Você recebe um trecho de código problemático e precisa apontar o que está errado e melhorar. É o formato que mais cobra princípios (SOLID, coesão, acoplamento) explicitamente.

## Exemplo: o mesmo enunciado em dois formatos

Enunciado: "um sistema de pedidos aplica descontos".

Num **OOD**, você discutiria uma hierarquia de descontos e mostraria o esqueleto. Num **machine coding**, você precisa disto rodando, com uma verificação mínima:

```python
from abc import ABC, abstractmethod


class Desconto(ABC):
    @abstractmethod
    def aplicar(self, valor: float) -> float: ...


class Percentual(Desconto):
    def __init__(self, pct: float) -> None:
        if not 0 <= pct <= 100:
            raise ValueError("percentual inválido")
        self.pct = pct

    def aplicar(self, valor: float) -> float:
        return round(valor * (1 - self.pct / 100), 2)


class ValorFixo(Desconto):
    def __init__(self, abatimento: float) -> None:
        self.abatimento = abatimento

    def aplicar(self, valor: float) -> float:
        return max(0.0, valor - self.abatimento)


class Pedido:
    def __init__(self, valor: float) -> None:
        self.valor = valor
        self._descontos: list[Desconto] = []

    def adicionar_desconto(self, desconto: Desconto) -> None:
        self._descontos.append(desconto)

    def total(self) -> float:
        total = self.valor
        for d in self._descontos:
            total = d.aplicar(total)
        return total


pedido = Pedido(200)
pedido.adicionar_desconto(Percentual(10))
pedido.adicionar_desconto(ValorFixo(30))
assert pedido.total() == 150
print("ok", pedido.total())
```

Repare no `assert` no final: em machine coding, uma checagem rápida mostra que você valida o próprio trabalho.

## Como identificar o formato

Pergunte ao recrutador antes. Se não der, observe os sinais no início da entrevista:

- "Vamos conversar sobre como você projetaria..." → OOD.
- "Você tem 90 minutos, use sua IDE..." → machine coding.
- "Outros times vão consumir isso..." → design de API.
- "Dê uma olhada neste código..." → revisão.

<Callout type="tip" title="Gerencie o relógio">
Em OOD, gaste uns 5–10 minutos com requisitos, 10 com entidades e relações, e o resto com código e follow-ups. Em machine coding, tenha algo rodando na metade do tempo, mesmo que incompleto.
</Callout>

## Armadilhas por formato

- **OOD:** pular requisitos e sair desenhando classes. Você acaba resolvendo o problema errado.
- **Machine coding:** perfeccionismo. Abstrações elegantes sem nada executando é reprovação certa.
- **API:** esquecer erros e casos de borda da interface pública.
- **Revisão:** criticar estilo (espaços, nomes) e deixar passar o problema estrutural.

## Na entrevista

Independente do formato, os critérios de avaliação se repetem: clareza de requisitos, distribuição de responsabilidades, extensibilidade, qualidade do código e comunicação. Follow-ups comuns: "adicione um novo tipo de X", "como você testaria isso?", "o que acontece se duas threads chamarem esse método?".
