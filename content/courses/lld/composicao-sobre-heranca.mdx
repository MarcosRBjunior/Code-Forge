**Prefira composição a herança** é um dos conselhos mais repetidos em orientação a objetos. Herança cria uma relação "é um" fixa em tempo de definição da classe; composição cria uma relação "tem um" que pode ser montada e trocada em tempo de execução. Na maioria dos casos em que você quer **reaproveitar comportamento**, compor é mais flexível e menos frágil.

## O problema da herança para reuso

Herança parece o caminho natural para evitar repetição: "todo robô anda, então crio `Robo` com `andar` e herdo". O problema surge quando as capacidades se combinam:

```text
              Robo
         /      |       \
 RoboQueAnda RoboQueVoa RoboQueNada
       \        /
   RoboQueAndaEVoa   RoboQueAndaENada  RoboQueVoaENada  ...
```

Com três capacidades independentes você precisa de até sete subclasses; com quatro, quinze. Isso é a **explosão de subclasses**. Além disso:

- **Classe base frágil**: mudar um método da base pode quebrar subclasses que dependiam de detalhes dela.
- **Herança expõe demais**: a subclasse herda métodos que talvez não façam sentido (lembre do pinguim que "voa").
- **Decisão estática**: um objeto não muda de classe depois de criado.

## Exemplo com herança

```python
class Robo:
    def __init__(self, nome: str) -> None:
        self.nome = nome

    def mover(self) -> str:
        return f"{self.nome} anda sobre rodas"


class RoboVoador(Robo):
    def mover(self) -> str:
        return f"{self.nome} voa com hélices"


class RoboAnfibio(Robo):
    def mover(self) -> str:
        return f"{self.nome} nada e depois anda"


# E se o robô voador perder a hélice e precisar andar? Não dá para trocar a classe.
print(RoboVoador("R2").mover())
```

## Versão com composição

Extraia a capacidade variável para objetos próprios e faça o robô **ter** uma:

```python
from typing import Protocol


class Locomocao(Protocol):
    def mover(self, nome: str) -> str: ...


class Rodas:
    def mover(self, nome: str) -> str:
        return f"{nome} anda sobre rodas"


class Helices:
    def mover(self, nome: str) -> str:
        return f"{nome} voa com hélices"


class Nadadeiras:
    def mover(self, nome: str) -> str:
        return f"{nome} nada"


class Robo:
    def __init__(self, nome: str, locomocao: Locomocao, sensores: list[str] | None = None) -> None:
        self.nome = nome
        self.locomocao = locomocao
        self.sensores = sensores or []

    def mover(self) -> str:
        return self.locomocao.mover(self.nome)

    def trocar_locomocao(self, nova: Locomocao) -> None:
        self.locomocao = nova


r2 = Robo("R2", Helices(), ["câmera"])
print(r2.mover())
r2.trocar_locomocao(Rodas())  # hélice quebrou
assert r2.mover() == "R2 anda sobre rodas"
print(r2.mover(), Robo("Bolha", Nadadeiras()).mover())
```

Com N tipos de locomoção e M conjuntos de sensores, você escreve N + M classes pequenas, não N vezes M subclasses. E o comportamento pode mudar em tempo de execução. Repare que isso é exatamente o padrão Strategy.

## Quando herança ainda é a escolha certa

| Use herança quando | Use composição quando |
| --- | --- |
| Existe um "é um" verdadeiro e estável | Você só quer reaproveitar código |
| A subclasse respeita o LSP integralmente | As capacidades se combinam livremente |
| Você implementa uma interface ou classe abstrata pensada para extensão | O comportamento precisa mudar em execução |
| A hierarquia é rasa (um ou dois níveis) | A base é de terceiros e pode mudar |

Herança de **interface** (implementar uma ABC ou Protocol) é saudável e comum. O alerta é contra herança de **implementação** usada só para economizar linhas.

<Callout type="note" title="O custo da composição">
Composição exige mais objetos e um pouco de código de delegação. Também é preciso montar os objetos em algum lugar, geralmente uma fábrica ou o ponto de entrada. É um custo pequeno comparado ao de desfazer uma hierarquia profunda.
</Callout>

## Na entrevista

Quando o entrevistador perguntar "e se um veículo for elétrico e também de carga?", isso é a deixa para compor: `Veiculo` com `Motor` e `Carroceria` em vez de `CaminhaoEletrico`. Follow-ups comuns: "quando você usaria herança?", "como isso se relaciona com Strategy e Decorator?". Ambos os padrões são aplicações diretas de composição sobre herança.
