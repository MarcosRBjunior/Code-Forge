**Polimorfismo** é a capacidade de tratar objetos de tipos diferentes por meio de uma mesma interface, e cada um responder do seu jeito. Você chama `forma.area()` sem saber se é um círculo ou um retângulo, e o objeto certo faz o cálculo certo. É o mecanismo que permite eliminar cadeias de `if tipo == ...` e adicionar comportamentos novos sem editar o código existente.

## O problema: decisões por tipo espalhadas

## Polimorfismo por subtipos

Cada tipo vira uma classe que implementa o mesmo contrato:

<CodeTabs>

```python
from abc import ABC, abstractmethod


class Veiculo(ABC):
    @abstractmethod
    def tarifa(self) -> float: ...

    @abstractmethod
    def vagas(self) -> int: ...


class Moto(Veiculo):
    def tarifa(self) -> float:
        return 5.0

    def vagas(self) -> int:
        return 1


class Carro(Veiculo):
    def tarifa(self) -> float:
        return 10.0

    def vagas(self) -> int:
        return 1


class Caminhao(Veiculo):
    def __init__(self, eixos: int) -> None:
        self.eixos = eixos

    def tarifa(self) -> float:
        return 10.0 * self.eixos

    def vagas(self) -> int:
        return 3


class Pedagio:
    def __init__(self) -> None:
        self.arrecadado = 0.0

    def cobrar(self, veiculo: Veiculo) -> float:
        valor = veiculo.tarifa()  # despacho dinâmico: cada objeto decide
        self.arrecadado += valor
        return valor


pedagio = Pedagio()
for v in [Moto(), Carro(), Caminhao(eixos=3)]:
    print(type(v).__name__, pedagio.cobrar(v), v.vagas())
print("total", pedagio.arrecadado)
```

`Pedagio` não conhece nenhum tipo concreto. Adicionar `Onibus` é criar uma classe; nenhum código existente muda. A decisão de "qual comportamento executar" acontece em tempo de execução, com base no tipo real do objeto: isso se chama **despacho dinâmico**.

## Duck typing: polimorfismo sem herança

Em Python, nem é preciso herança. Se o objeto tem o método, funciona:

<CodeTabs>

```python
class Pato:
    def falar(self) -> str:
        return "quack"


class Robo:
    def falar(self) -> str:
        return "bip"


for coisa in (Pato(), Robo()):
    print(coisa.falar())
```

## Outras formas de polimorfismo

| Forma | Ideia | Em Python |
| --- | --- | --- |
| De subtipo | subclasses respondem diferente ao mesmo método | sobrescrita de métodos |
| Paramétrico | código genérico que funciona para qualquer tipo | `list[T]`, `TypeVar` |
| Ad hoc (sobrecarga) | mesma operação com tipos diferentes de argumento | `functools.singledispatch`, métodos mágicos como `__add__` |

Sobrecarga de operadores também é polimorfismo. Veja um valor monetário que soma com `+`:

<CodeTabs>

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Dinheiro:
    centavos: int

    def __add__(self, outro: "Dinheiro") -> "Dinheiro":
        return Dinheiro(self.centavos + outro.centavos)

    def __str__(self) -> str:
        return f"R$ {self.centavos / 100:.2f}"


print(Dinheiro(1050) + Dinheiro(225))  # R$ 12.75
```

```javascript
// JavaScript não sobrecarrega operadores: o "+" vira um método somar().
class Dinheiro {
  constructor(centavos) {
    this.centavos = centavos;
    Object.freeze(this);
  }

  somar(outro) {
    return new Dinheiro(this.centavos + outro.centavos);
  }

  toString() {
    return `R$ ${(this.centavos / 100).toFixed(2)}`;
  }
}

console.log(String(new Dinheiro(1050).somar(new Dinheiro(225)))); // R$ 12.75
```

## Armadilhas

- **Checar tipo dentro do polimorfismo.** Se você escreve `if isinstance(v, Caminhao)` em `Pedagio`, o polimorfismo foi derrotado. Mova o comportamento para a classe.
- **Subclasses que lançam "não suportado".** Se `Moto.reboque()` lança `NotImplementedError`, o contrato da base está largo demais.
- **Polimorfismo para dois casos que nunca vão crescer.** Um `if` simples pode ser mais legível.

<Callout type="tip" title="Substitua condicional por polimorfismo">
Quando a mesma cascata de `if` por tipo aparece em mais de um lugar, é sinal forte de que cada ramo deveria virar uma classe com um método comum.
</Callout>

## Na entrevista

Polimorfismo é a resposta padrão para "e se surgir um novo tipo de X?". Mostre que o código cliente depende da abstração e que um novo tipo é só uma nova classe. (não nativamente; usa argumentos padrão ou `singledispatch`), "o que é despacho dinâmico?".
