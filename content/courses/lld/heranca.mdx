**Herança** permite que uma classe (subclasse) reaproveite e especialize o comportamento de outra (superclasse). É a ferramenta mais famosa da OOP e, ao mesmo tempo, a mais mal usada. Usada para modelar uma relação genuína de "é um", ela simplifica o código. Usada só para reaproveitar algumas linhas, ela cria acoplamentos difíceis de desfazer.

## Como funciona

A subclasse herda atributos e métodos da superclasse e pode **estender** (adicionar) ou **sobrescrever** (substituir) comportamentos:

```python
class Funcionario:
    def __init__(self, nome: str, salario_base: float) -> None:
        self.nome = nome
        self.salario_base = salario_base

    def salario(self) -> float:
        return self.salario_base

    def descricao(self) -> str:
        return f"{self.nome}: R$ {self.salario():.2f}"


class Gerente(Funcionario):
    def __init__(self, nome: str, salario_base: float, bonus: float) -> None:
        super().__init__(nome, salario_base)  # reaproveita a inicialização
        self.bonus = bonus

    def salario(self) -> float:  # sobrescreve
        return super().salario() + self.bonus


class Estagiario(Funcionario):
    def salario(self) -> float:
        return self.salario_base * 0.5


equipe = [Funcionario("Caio", 4000), Gerente("Bia", 7000, 1500), Estagiario("Duda", 3000)]
for f in equipe:
    print(f.descricao())
```

Note que `descricao` está só na superclasse, mas chama `self.salario()`, que resolve para a versão da subclasse. Esse é o ponto de encontro entre herança e polimorfismo.

`super()` chama a implementação da superclasse. Esquecer `super().__init__` é um bug clássico: os atributos da superclasse nunca são criados.

## Quando herança faz sentido

Use herança quando **todas** estas condições valem:

1. A relação é "é um" de verdade: um gerente **é um** funcionário em qualquer contexto.
2. A subclasse pode ser usada em qualquer lugar onde a superclasse é esperada, sem surpresas (isso é o princípio de Liskov, que você verá em SOLID).
3. A hierarquia é rasa e estável.

## O problema clássico: herança para reaproveitar código

```python
class Lista:
    def __init__(self) -> None:
        self._itens: list = []

    def adicionar(self, item) -> None:
        self._itens.append(item)

    def remover(self, item) -> None:
        self._itens.remove(item)


class Pilha(Lista):  # "reaproveita" a lista
    def empilhar(self, item) -> None:
        self.adicionar(item)

    def desempilhar(self):
        return self._itens.pop()


p = Pilha()
p.empilhar(1)
p.empilhar(2)
p.remover(1)        # remover do meio de uma pilha? A herança permitiu.
print(p._itens)     # [2]
```

`Pilha` herdou operações que violam a ideia de pilha. Ela não **é uma** lista genérica; ela **usa** uma lista. A solução é composição:

```python
class Pilha:
    def __init__(self) -> None:
        self._itens: list = []

    def empilhar(self, item) -> None:
        self._itens.append(item)

    def desempilhar(self):
        if not self._itens:
            raise IndexError("pilha vazia")
        return self._itens.pop()

    def __len__(self) -> int:
        return len(self._itens)


p = Pilha()
p.empilhar("a")
p.empilhar("b")
print(p.desempilhar(), len(p))  # b 1
```

A interface pública agora contém só o que faz sentido.

## Riscos da herança

| Risco | O que acontece |
| --- | --- |
| Classe base frágil | mudar a superclasse quebra subclasses que dependiam de detalhes internos |
| Hierarquias profundas | entender um método exige subir cinco níveis |
| Explosão de combinações | `CarroEletricoAutomatico`, `CarroFlexManual`... uma subclasse por combinação |
| Herança de coisas indesejadas | a subclasse ganha métodos que não deveria ter |

<Callout type="warning" title="Herança múltipla">
Python permite herdar de várias classes e resolve conflitos pela MRO (method resolution order). Use com parcimônia, de preferência só com mixins pequenos e sem estado. Em entrevista, quase sempre composição é a resposta mais segura.
</Callout>

## Na entrevista

Quando propuser herança, justifique com "é um" e mostre que a subclasse respeita o contrato da base. Se o entrevistador perguntar "por que não composição?", tenha uma resposta. Follow-ups comuns: "o que é o problema da classe base frágil?", "como modelar veículos com motor e câmbio variados sem explosão de subclasses?", "o que é MRO?".
