O diagrama de atividades é um **fluxograma da UML**: descreve o passo a passo de um processo, com decisões, caminhos paralelos e fim. Ele não se preocupa com objetos, e sim com o *trabalho* a fazer. Por isso funciona bem para explicar regras de negócio, como o fluxo de aprovação de um empréstimo, antes de transformá-las em código.

## Elementos

- **Nó inicial**: círculo preenchido.
- **Ação**: retângulo arredondado com um verbo ("Validar CPF").
- **Decisão**: losango com condições nas saídas, escritas entre colchetes: `[saldo suficiente]`, `[senão]`.
- **Fork e join**: barra grossa que divide em caminhos paralelos e outra que os reúne.
- **Nó final**: círculo com borda dupla.
- **Raias (swimlanes)**: colunas que indicam quem executa cada ação (cliente, sistema, banco).

## Exemplo: compra online

```text
(inicio)
   |
[Validar carrinho]
   |
<carrinho vazio?> --sim--> [Mostrar erro] --> (fim)
   | nao
[Calcular total]
   |
=====fork=====
   |          |
[Reservar    [Calcular
 estoque]     frete]
   |          |
=====join=====
   |
[Cobrar pagamento]
   |
<aprovado?> --nao--> [Liberar estoque] --> (fim)
   | sim
[Enviar confirmação] --> (fim)
```

O fork mostra que reservar estoque e calcular frete são independentes, então podem rodar ao mesmo tempo; o join espera as duas terminarem.

## Do fluxo ao código

Cada decisão vira um `if`, cada ação vira um método pequeno e cada fork pode virar execução concorrente. Uma tradução fiel:

```python
from concurrent.futures import ThreadPoolExecutor


def reservar_estoque(itens: list[str]) -> bool:
    return True


def calcular_frete(itens: list[str]) -> float:
    return 10.0 * len(itens)


def cobrar(total: float) -> bool:
    return total < 200


def finalizar(itens: list[str], preco: float) -> str:
    if not itens:                                  # decisão: carrinho vazio
        return "erro: carrinho vazio"
    with ThreadPoolExecutor() as pool:             # fork
        f_estoque = pool.submit(reservar_estoque, itens)
        f_frete = pool.submit(calcular_frete, itens)
        ok_estoque, frete = f_estoque.result(), f_frete.result()  # join
    if not ok_estoque:
        return "erro: sem estoque"
    if not cobrar(preco + frete):                  # decisão: aprovado?
        return "erro: pagamento recusado"
    return "confirmado"


assert finalizar([], 0) == "erro: carrinho vazio"
assert finalizar(["a", "b"], 100) == "confirmado"
assert finalizar(["a"], 500) == "erro: pagamento recusado"
print("ok")
```

```javascript
function reservarEstoque(itens) { return true; }

function calcularFrete(itens) { return 10.0 * itens.length; }

function cobrar(total) { return total < 200; }

async function finalizar(itens, preco) {
  if (itens.length === 0) {                                   // decisão: carrinho vazio
    return "erro: carrinho vazio";
  }
  const [okEstoque, frete] = await Promise.all([            // fork + join
    Promise.resolve().then(() => reservarEstoque(itens)),
    Promise.resolve().then(() => calcularFrete(itens)),
  ]);
  if (!okEstoque) {
    return "erro: sem estoque";
  }
  if (!cobrar(preco + frete)) {                               // decisão: aprovado?
    return "erro: pagamento recusado";
  }
  return "confirmado";
}

(async () => {
  console.assert((await finalizar([], 0)) === "erro: carrinho vazio");
  console.assert((await finalizar(["a", "b"], 100)) === "confirmado");
  console.assert((await finalizar(["a"], 500)) === "erro: pagamento recusado");
  console.log("ok");
})();
```

```java
import java.util.*;
import java.util.concurrent.*;

static boolean reservarEstoque(List<String> itens) { return true; }

static double calcularFrete(List<String> itens) { return 10.0 * itens.size(); }

static boolean cobrar(double total) { return total < 200; }

static String finalizar(List<String> itens, double preco) throws Exception {
    if (itens.isEmpty()) {                                         // decisão: carrinho vazio
        return "erro: carrinho vazio";
    }
    ExecutorService pool = Executors.newCachedThreadPool();
    try {
        Future<Boolean> fEstoque = pool.submit(() -> reservarEstoque(itens));   // fork
        Future<Double> fFrete = pool.submit(() -> calcularFrete(itens));
        boolean okEstoque = fEstoque.get();                         // join
        double frete = fFrete.get();
        if (!okEstoque) {
            return "erro: sem estoque";
        }
        if (!cobrar(preco + frete)) {                               // decisão: aprovado?
            return "erro: pagamento recusado";
        }
        return "confirmado";
    } finally {
        pool.shutdown();
    }
}

public static void main(String[] args) throws Exception {
    if (!finalizar(List.of(), 0).equals("erro: carrinho vazio")) throw new AssertionError();
    if (!finalizar(List.of("a", "b"), 100).equals("confirmado")) throw new AssertionError();
    if (!finalizar(List.of("a"), 500).equals("erro: pagamento recusado")) throw new AssertionError();
    System.out.println("ok");
}
```

```go
import "fmt"

func reservarEstoque(itens []string) bool { return true }

func calcularFrete(itens []string) float64 { return 10.0 * float64(len(itens)) }

func cobrar(total float64) bool { return total < 200 }

func finalizar(itens []string, preco float64) string {
	if len(itens) == 0 { // decisão: carrinho vazio
		return "erro: carrinho vazio"
	}
	chEstoque := make(chan bool, 1)
	chFrete := make(chan float64, 1)
	go func() { chEstoque <- reservarEstoque(itens) }() // fork
	go func() { chFrete <- calcularFrete(itens) }()
	okEstoque, frete := <-chEstoque, <-chFrete // join
	if !okEstoque {
		return "erro: sem estoque"
	}
	if !cobrar(preco + frete) { // decisão: aprovado?
		return "erro: pagamento recusado"
	}
	return "confirmado"
}

func main() {
	if finalizar(nil, 0) != "erro: carrinho vazio" ||
		finalizar([]string{"a", "b"}, 100) != "confirmado" ||
		finalizar([]string{"a"}, 500) != "erro: pagamento recusado" {
		panic("falhou")
	}
	fmt.Println("ok")
}
```

## Atividades versus sequência

O diagrama de sequência foca em *quem chama quem*. O de atividades foca em *o que acontece e em que condições*. Se o entrevistador pergunta sobre regras e ramificações, use atividades; se pergunta sobre colaboração entre classes, use sequência.

<Callout type="tip" title="Cuidado com o excesso">
Um fluxograma com trinta caixas não ajuda ninguém. Mostre o caminho principal e os dois ou três desvios mais relevantes.
</Callout>

## Armadilhas

- Decisões sem todas as saídas rotuladas deixam o fluxo ambíguo.
- Esquecer o caminho de falha, que costuma ser onde mora a complexidade.
- Usar o diagrama para algo que é estado de objeto: nesse caso, o certo é a máquina de estados.

## Na entrevista

É útil quando o problema tem um processo bem definido, como pedido, reserva ou aprovação. Desenhe o caminho feliz primeiro e depois pergunte "quais falhas tratamos?". Follow-ups: "o que roda em paralelo?", "o que acontece se a cobrança falhar depois de reservar?".
