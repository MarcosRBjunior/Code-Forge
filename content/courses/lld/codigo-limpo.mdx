Em entrevista de LLD, o entrevistador lê seu código como um colega leria num code review. Código limpo não é estética: é a capacidade de outra pessoa entender e alterar o que você escreveu sem precisar perguntar. Aqui estão os hábitos que mais pesam, com um antes e depois.

## Nomes que revelam intenção

Um nome bom dispensa comentário. Prefira `dias_de_atraso` a `d`, `calcular_multa` a `processar`, `esta_vencido` a `flag`. Nomes de classe são substantivos; de método, verbos; de booleanos, perguntas (`tem_saldo`, `esta_ativo`).

## Funções pequenas e com um propósito

Uma função deve fazer uma coisa e estar em um único nível de abstração. Se você precisa de um comentário para separar "partes" dentro dela, cada parte provavelmente é uma função.

## Antes e depois

```python
# antes: faz tudo, nomes vagos, números mágicos
def proc(l, t):
    r = 0
    for i in l:
        if i[1] == 1:
            r += i[0] * 0.9
        else:
            r += i[0]
    if t == "A":
        r = r + 15
    return r
```

```python
# depois: cada conceito tem nome
from dataclasses import dataclass

DESCONTO_VIP = 0.10
FRETE_ENTREGA = 15.0


@dataclass
class Item:
    preco: float
    vip: bool


def preco_com_desconto(item: Item) -> float:
    return item.preco * (1 - DESCONTO_VIP) if item.vip else item.preco


def total_do_pedido(itens: list[Item], entrega: bool) -> float:
    subtotal = sum(preco_com_desconto(i) for i in itens)
    return subtotal + (FRETE_ENTREGA if entrega else 0)


assert total_do_pedido([Item(100, True), Item(50, False)], entrega=True) == 155.0
print("limpo e testável")
```

A segunda versão é maior em linhas, mas cada linha comunica algo. Mudar o desconto ou o frete é editar uma constante.

## Princípios que se aplicam diretamente

| Hábito | Por que importa |
| --- | --- |
| Sem números e strings mágicos | Constantes e enums explicam o significado |
| Poucos parâmetros (até 3 ou 4) | Muitos parâmetros sugerem um objeto de dados |
| Retornos antecipados (guard clauses) | Evitam aninhamento profundo de `if` |
| Sem efeitos colaterais surpresa | Funções que mudam estado global confundem |
| Tratar erros com exceções claras | Não retorne códigos como `-1` |
| Comentários explicam o porquê | O quê e o como o código já diz |

## Guard clauses

```python
def sacar(saldo: float, valor: float) -> float:
    if valor <= 0:
        raise ValueError("valor deve ser positivo")
    if valor > saldo:
        raise ValueError("saldo insuficiente")
    return saldo - valor


assert sacar(100, 30) == 70
```

As condições inválidas saem logo no começo, e o caminho feliz fica sem recuos.

<Callout type="note" title="Relação com os princípios">
Código limpo é a prática diária dos princípios que você já viu: SRP deixa classes pequenas, DRY remove repetição, KISS evita complexidade desnecessária e YAGNI corta o que ninguém pediu.
</Callout>

## Armadilhas

- **Abreviações obscuras**: `mgr`, `tmp2`, `dt`.
- **Comentários que repetem o código** (`i += 1  # incrementa i`).
- **Código morto** e trechos comentados: apague, o controle de versão guarda o histórico.
- **Funções que fazem e respondem**: separar consulta de comando facilita o raciocínio.
- **Exagero**: fragmentar demais em dezenas de funções de uma linha também prejudica a leitura.

## Na entrevista

Reserve dois minutos finais para revisar o código em voz alta: renomear o que ficou confuso, extrair um método longo, remover sobras. Isso mostra cuidado com quem vai manter o sistema. Follow-ups: "como você deixaria isso mais legível?", "esse método faz mais de uma coisa?".
