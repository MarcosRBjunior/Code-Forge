Uma **interface** é um contrato: ela diz *quais* operações um objeto oferece, sem dizer *como* ele as executa. Quem usa o objeto depende só do contrato, e qualquer classe que cumpra o contrato pode ser plugada no lugar. É a ferramenta central para trocar implementações, testar com dublês e manter módulos desacoplados.

## O problema: depender de uma classe concreta

Imagine um serviço de cadastro que envia boas-vindas por e-mail:

```python
class EmailSmtp:
    def enviar(self, destino: str, texto: str) -> None:
        print(f"[SMTP] {destino}: {texto}")


class Cadastro:
    def __init__(self) -> None:
        self.email = EmailSmtp()  # amarrado a uma implementação

    def registrar(self, usuario: str) -> None:
        self.email.enviar(usuario, "Bem-vindo!")


Cadastro().registrar("ana@ex.com")
```

Agora o produto quer mandar SMS em alguns casos, e os testes não podem disparar e-mail de verdade. Como `Cadastro` cria e conhece `EmailSmtp` diretamente, cada mudança exige editar `Cadastro`.

## Interfaces em Python

Python não tem a palavra-chave `interface`, mas oferece dois mecanismos.

### Classes base abstratas (ABC)

Herança nominal: a implementação declara explicitamente que cumpre o contrato.

```python
from abc import ABC, abstractmethod


class Notificador(ABC):
    @abstractmethod
    def enviar(self, destino: str, texto: str) -> None: ...


class NotificadorEmail(Notificador):
    def enviar(self, destino: str, texto: str) -> None:
        print(f"[email] {destino}: {texto}")


class NotificadorSms(Notificador):
    def enviar(self, destino: str, texto: str) -> None:
        print(f"[sms] {destino}: {texto[:20]}")


class Cadastro:
    def __init__(self, notificador: Notificador) -> None:
        self.notificador = notificador

    def registrar(self, usuario: str) -> None:
        self.notificador.enviar(usuario, "Bem-vindo à plataforma!")


Cadastro(NotificadorEmail()).registrar("ana@ex.com")
Cadastro(NotificadorSms()).registrar("+55 81 99999-0000")

try:
    Notificador()
except TypeError as e:
    print("não dá para instanciar o contrato:", type(e).__name__)
```

Se uma subclasse esquecer de implementar `enviar`, o Python recusa criar a instância. O erro aparece cedo.

### Protocolos (tipagem estrutural)

Com `typing.Protocol`, basta ter os métodos certos; não é preciso herdar. É o "duck typing" com verificação de tipos estática:

```python
from typing import Protocol, runtime_checkable


@runtime_checkable
class Notificador(Protocol):
    def enviar(self, destino: str, texto: str) -> None: ...


class NotificadorFalso:
    """Dublê para testes: não herda de nada."""

    def __init__(self) -> None:
        self.enviados: list[tuple[str, str]] = []

    def enviar(self, destino: str, texto: str) -> None:
        self.enviados.append((destino, texto))


class Cadastro:
    def __init__(self, notificador: Notificador) -> None:
        self.notificador = notificador

    def registrar(self, usuario: str) -> None:
        self.notificador.enviar(usuario, "Bem-vindo!")


falso = NotificadorFalso()
Cadastro(falso).registrar("teste@ex.com")
assert falso.enviados == [("teste@ex.com", "Bem-vindo!")]
print(isinstance(falso, Notificador))  # True
```

## ABC ou Protocol?

| Critério | ABC | Protocol |
| --- | --- | --- |
| Precisa herdar? | sim | não |
| Erro se faltar método | ao instanciar | no verificador de tipos (mypy, pyright) |
| Pode ter código compartilhado | sim, métodos concretos | não é o objetivo |
| Bom para | hierarquias que você controla | integrar classes de terceiros, dublês de teste |

Em entrevistas, ABC costuma ser mais claro porque mostra a intenção de forma explícita, parecida com `interface` em Java ou C#.

## Princípios para boas interfaces

- **Pequenas e focadas.** Uma interface com 15 métodos obriga cada implementação a lidar com todos. Prefira várias interfaces pequenas.
- **Nomeadas pelo papel, não pela tecnologia.** `Notificador`, não `ServicoSmtp`.
- **Definidas por quem consome.** O contrato deve refletir o que o cliente precisa, não tudo o que a implementação sabe fazer.

<Callout type="warning" title="Interface sem segunda implementação">
Criar interface para uma classe que nunca terá alternativa nem precisa de dublê em teste é cerimônia. Extraia o contrato quando houver um motivo concreto: variação real, testes ou fronteira entre módulos.
</Callout>

## Na entrevista

Interfaces aparecem sempre que há variação: meios de pagamento, estratégias de preço, canais de notificação. Diga explicitamente: "vou definir uma interface `MeioDePagamento` com `cobrar(valor)`, assim adicionar Pix não muda o `Checkout`". Follow-ups: "qual a diferença entre classe abstrata e interface?", "como você testaria `Cadastro` sem enviar e-mails?".
