**KISS** é a sigla de *Keep It Simple, Stupid*, ou numa versão mais gentil, "mantenha simples". A ideia: entre duas soluções que resolvem o problema, prefira a mais simples de entender, testar e mudar. Simplicidade aqui não é "menos linhas" nem "mais esperto"; é **menos coisas que o leitor precisa segurar na cabeça** para entender o código.

## O problema

Código complexo custa caro de três formas: demora mais para ler, esconde bugs em caminhos raros e assusta quem precisa alterar. Boa parte da complexidade não vem do problema, e sim de escolhas do autor: camadas de abstração sem uso, truques de linguagem, generalização prematura. Essa é a **complexidade acidental**, e o KISS é um convite a eliminá-la.

## Exemplo complicado demais

Precisamos decidir se um ano é bissexto:

```python
from abc import ABC, abstractmethod


class Regra(ABC):
    @abstractmethod
    def avaliar(self, ano: int) -> bool | None: ...


class RegraDivisivel(Regra):
    def __init__(self, divisor: int, resultado: bool) -> None:
        self.divisor, self.resultado = divisor, resultado

    def avaliar(self, ano: int) -> bool | None:
        return self.resultado if ano % self.divisor == 0 else None


class MotorDeRegras:
    def __init__(self, regras: list[Regra], padrao: bool) -> None:
        self.regras, self.padrao = regras, padrao

    def executar(self, ano: int) -> bool:
        for r in self.regras:
            res = r.avaliar(ano)
            if res is not None:
                return res
        return self.padrao


motor = MotorDeRegras([RegraDivisivel(400, True), RegraDivisivel(100, False), RegraDivisivel(4, True)], False)
print(motor.executar(2024), motor.executar(1900))
```

Funciona, mas um motor de regras genérico para uma regra que não muda há séculos é puro custo.

## Versão simples

```python
def eh_bissexto(ano: int) -> bool:
    return ano % 4 == 0 and (ano % 100 != 0 or ano % 400 == 0)


assert eh_bissexto(2024)
assert not eh_bissexto(1900)
assert eh_bissexto(2000)
print("ok")
```

Uma linha, legível por qualquer pessoa, fácil de testar.

## Sinais de que você fugiu do KISS

- Você precisa de um diagrama para explicar um fluxo que tem três passos.
- Existe uma interface com uma única implementação e nenhuma perspectiva de segunda.
- Há um "framework interno" usado em um lugar só.
- One-liners engenhosos com compreensões aninhadas, `lambda` dentro de `reduce` e operadores ternários encadeados.
- Configurações para comportamentos que ninguém pediu para configurar.

## Simples não é simplório

KISS não significa ignorar requisitos. Se o problema é genuinamente complexo, como calcular impostos de vários estados, a solução terá complexidade. O objetivo é que ela seja **proporcional** ao problema. Também não significa evitar padrões de projeto: um Strategy bem aplicado simplifica um `if/elif` de quinze ramos. O teste é sempre: "o próximo desenvolvedor vai entender isso mais rápido?".

| Escolha | Mais simples | Mais complexa |
| --- | --- | --- |
| Guardar 50 itens em memória | `list` ou `dict` | árvore balanceada própria |
| Três tipos de notificação fixos | `if` ou dicionário de funções | sistema de plugins |
| Validar um e-mail no cadastro | uma função | biblioteca de validação genérica |

<Callout type="note" title="KISS e YAGNI andam juntos">
YAGNI evita construir o que não é necessário agora; KISS evita construir de forma complicada o que é necessário. Um corta escopo, o outro corta complexidade da implementação.
</Callout>

## Na entrevista

Em LLD, KISS é seu aliado contra o tempo. Comece com o modelo mais direto que atende aos requisitos e diga explicitamente: "vou começar simples e mostro onde estenderia". Entrevistadores costumam penalizar candidatos que despejam cinco padrões num estacionamento de um andar. Follow-ups comuns: "como você decide que algo está complexo demais?", "quando vale a pena adicionar uma abstração?".
