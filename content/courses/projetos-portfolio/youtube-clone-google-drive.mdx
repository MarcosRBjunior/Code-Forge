**Em uma frase:** uma plataforma de armazenamento em que a pessoa entra com um código enviado por e-mail, sobe arquivos, organiza por tipo, busca, renomeia, compartilha com outras pessoas e vê quanto espaço já usou.

**Nível:** intermediário · **Duração do vídeo:** cerca de 5h20 · **Canal:** JavaScript Mastery · **Publicado em:** novembro de 2024

## Assista

[Build and Deploy a Full Stack Google Drive Clone with Next.js 15](https://www.youtube.com/watch?v=lie0cr3wESQ)

O tutorial constrói uma "plataforma de gestão de armazenamento inspirada no Google Drive, Dropbox e OneDrive", com o Appwrite fazendo o papel de back-end (autenticação, banco e storage) e Server Actions do Next.js no meio. Serve para quem já conhece React e quer praticar upload de arquivos, rotas dinâmicas e um back-end como serviço sem escrever uma API do zero. O canal oferece um kit com o código e os assets (jsm.dev/gdrive-kit); o repositório é a melhor fonte para as versões exatas.

## O que você vai construir

- Cadastro e login sem senha, com código de uso único (OTP) enviado por e-mail pelo Appwrite.
- Layout com barra lateral, cabeçalho e navegação móvel.
- Upload de arquivos para o storage do Appwrite, com registro de cada arquivo no banco.
- Páginas por tipo de arquivo (documentos, imagens, mídia, outros) em rotas dinâmicas.
- Cartão de arquivo com menu de ações: renomear, ver detalhes, compartilhar por e-mail, baixar e apagar.
- Filtro, busca global e ordenação.
- Dashboard com o espaço usado no total e por tipo.
- Deploy do app.

## Stack do vídeo e o que usar hoje

| Camada | No vídeo | Em 2026 |
|---|---|---|
| Framework | Next.js 15 com App Router e Server Actions | Next.js 16. As mudanças de API do 15 (`params` e `cookies()` assíncronos) já estão no vídeo; no 16, `middleware.ts` passou a se chamar `proxy.ts` |
| UI | React 19 (ainda em release candidate na época), Tailwind CSS 3 com `tailwind.config.ts`, provavelmente shadcn/ui | React 19 estável, Tailwind 4 com configuração no CSS (`@theme`), shadcn/ui atual |
| Back-end | Appwrite Cloud: Auth, Databases e Storage, acessados pelo SDK `node-appwrite` | Mesmo serviço; confira a versão do SDK, porque nomes de métodos mudam entre versões maiores |
| Qualidade | ESLint e Prettier | ESLint 9 com configuração em arquivo plano (`eslint.config.mjs`) |
| Deploy | Vercel (provável) | Vercel ou qualquer hospedagem Node |

<Callout type="warning" title="O que mudou desde a gravação">
- **Tailwind 4.** O vídeo monta o design system (cores, fontes, sombras) no `tailwind.config.ts`. No Tailwind 4 isso vai para o CSS, dentro de `@theme`, e um projeto Next novo já vem sem o arquivo de configuração. Se for usar a versão nova, traduza os tokens do vídeo para variáveis CSS em vez de procurar o arquivo.
- **ESLint 9.** Se o vídeo configurar o ESLint com `.eslintrc`, saiba que o formato padrão agora é o `eslint.config.mjs`. Os plugins de Prettier e Next continuam existindo, com outra forma de declarar.
- **SDK do Appwrite.** O fluxo de OTP usa métodos de token por e-mail e criação de sessão que mudaram de nome em versões anteriores do SDK. Se um método do vídeo não existir, procure "Email OTP" na documentação da versão que você instalou.
- **Painel do Appwrite.** A interface do console mudou; procure as configurações pelo nome (permissões do bucket, chave de API, atributos da coleção), não pela posição.

Duas formas de seguir: instalar exatamente as versões do `package.json` do repositório oficial e atualizar depois numa branch própria, ou começar com Next 16 e Tailwind 4 sabendo destas diferenças. A primeira é mais tranquila; a segunda obriga você a ler documentação, o que é justamente o que se faz no trabalho.
</Callout>

## Roteiro de estudo

Assista em blocos, pause antes de cada um e tente escrever o código sozinho primeiro. Volte ao vídeo para comparar, não para copiar.

### 1. Base do projeto e design system (00:00:00 a 00:22:22)

**Construa:** o projeto Next.js com metadados, ESLint e Prettier, e o tema (cores, fontes, espaçamentos) que o resto do app vai usar.

**Conceito:** decidir os tokens de design antes das telas evita cores e tamanhos soltos espalhados pelo código.

**Pergunte-se:** se você trocar a cor principal do app, quantos arquivos precisa mexer? A resposta deveria ser um.

### 2. Autenticação com OTP (00:22:22 a 01:41:35)

**Construa:** o layout das telas de autenticação, um formulário reutilizável para cadastro e login, a configuração do Appwrite (a partir de 00:51:03) e o modal de código OTP (01:20:26).

**Conceito:** login sem senha troca o problema de guardar senhas pelo problema de entregar e validar um código de uso único. A sessão resultante fica num cookie `httpOnly`, lido pelas Server Actions.

**Pergunte-se:** o que impede alguém de tentar todos os códigos possíveis? Onde esse limite deveria ficar, no seu código ou no Appwrite?

### 3. Layout do app e finalização da autenticação (01:41:35 a 02:27:31)

**Construa:** barra lateral, cabeçalho, navegação móvel (02:07:39) e a proteção das páginas para quem não está logado (02:17:08).

**Conceito:** buscar o usuário atual no servidor, no layout, e redirecionar para o login se não houver sessão.

**Pergunte-se:** se a verificação de sessão está só no layout, uma Server Action chamada diretamente também está protegida? (Não está: cada ação precisa conferir a sessão por conta própria.)

### 4. Upload e listagem de arquivos (02:27:31 a 03:32:49)

**Construa:** o upload (02:27:31), as rotas dinâmicas por tipo de arquivo (03:10:56) e o cartão de arquivo (03:25:08).

**Conceito:** o arquivo vai para o storage, e um documento no banco guarda os metadados (nome, tipo, tamanho, dono, URL). Toda listagem consulta o banco, não o storage.

**Pergunte-se:** se o upload para o storage der certo e a gravação no banco falhar, o que sobra? Como você limparia esse arquivo órfão?

### 5. Ações sobre arquivos (03:32:49 a 04:26:48)

**Construa:** o menu de ações (03:32:49), renomear (03:50:01), detalhes (03:55:49), compartilhar (04:02:41) e apagar (04:18:17).

**Conceito:** cada ação é uma operação que muda dados de um arquivo específico, então cada uma precisa responder: quem está pedindo pode fazer isso com este arquivo?

**Pergunte-se:** uma pessoa com quem o arquivo foi compartilhado consegue renomeá-lo ou apagá-lo? Ela deveria conseguir? Teste chamando a ação com o id do arquivo de outra conta.

### 6. Busca, ordenação, dashboard e deploy (04:26:48 ao fim)

**Construa:** filtro e busca global (04:26:48), ordenação (04:57:00), a página de dashboard com o espaço usado (05:03:03) e o deploy (05:09:05).

**Conceito:** busca e ordenação devem acontecer na consulta ao banco, com os parâmetros vindos da URL, para que o resultado possa ser compartilhado por link e a página não carregue tudo para filtrar no navegador.

**Pergunte-se:** como o dashboard calcula o espaço usado? Somar o tamanho de todos os arquivos a cada visita continua razoável com 50 mil arquivos?

## Torne o projeto seu

Um clone de Drive com o mesmo layout, as mesmas cores e o mesmo nome do tutorial é reconhecido na hora. Use nome, logo e identidade visual próprios: Google Drive é marca registrada, e o projeto publicado não pode parecer o produto do Google. O que o avaliador procura é o que o vídeo não mostra: regras de acesso bem pensadas, limites, falhas tratadas e decisões explicadas.

**Um nicho.** "Drive para estúdio de fotografia entregar ensaios ao cliente", "pasta compartilhada de documentos de um condomínio", "cofre de comprovantes para declarar imposto". O nicho decide quais features fazem sentido.

**Uma feature que o vídeo não tem.** Escolha uma ou duas:

- **Pastas aninhadas.** Exige modelar a hierarquia (id do pai em cada item), mover itens entre pastas e evitar ciclos. É o que mais aproxima o projeto de um Drive de verdade.
- **Link público com expiração.** Compartilhar com quem não tem conta, por um link que vence em 24 horas ou depois de N downloads, gerado e validado no servidor.
- **Papéis no compartilhamento.** Leitor e editor, com a regra aplicada no servidor e mostrada na UI.
- **Lixeira com restauração.** Apagar marca o arquivo e um job remove de verdade depois de 30 dias.
- **Cota por usuário.** Limite de espaço verificado antes do upload, com aviso perto do limite.
- **Pré-visualização.** PDF e imagens abertos no próprio app, com miniaturas geradas pelo storage.

**Autorização no servidor, sempre.** Esconder o botão "apagar" para quem não é dono não protege nada. Toda Server Action que mexe num arquivo deve buscar o arquivo, comparar o dono (ou o papel) com o usuário da sessão e só então agir. Atenção a um detalhe: se as Server Actions usam um cliente Appwrite com chave de API (o cliente administrativo), as permissões do Appwrite são ignoradas e a checagem fica inteiramente por conta do seu código. A alternativa é usar o cliente com a sessão do usuário e configurar permissões por documento e por arquivo no Appwrite. Escreva no README qual das duas você escolheu e por quê.

**Validação do upload.** Limite de tamanho e lista de tipos aceitos verificados no servidor e também nas configurações do bucket. Não confie na extensão do nome do arquivo. Valide os outros campos (novo nome, e-mails de compartilhamento) com Zod.

**Segredos.** A chave de API do Appwrite tem poder total sobre o projeto. Ela nunca pode ter o prefixo `NEXT_PUBLIC_` nem aparecer em código de Client Component. No repositório vai só o `.env.example`.

**Tratamento de erros.** Upload que falha no meio, arquivo maior que o permitido, sessão expirada durante uma ação, e-mail de compartilhamento que não pertence a ninguém. Cada caso merece uma mensagem clara, não um erro genérico.

**Testes.** Teste as regras de acesso (dono, compartilhado, estranho) contra cada ação, o cálculo de espaço e um fluxo de ponta a ponta com Playwright: entrar, enviar arquivo, compartilhar, conferir com a segunda conta.

**Acessibilidade.** Menu de ações operável por teclado, área de upload que também funciona com um botão comum (não só arrastar e soltar), progresso de upload anunciado para leitores de tela, contraste conferido.

**README com decisões.** Modelo de dados, diagrama do fluxo de upload, como a autorização funciona, limites escolhidos e o que mudaria com milhões de arquivos. Diga que partiu do tutorial e liste o que você mudou.

## Armadilhas comuns

- **Upload grande que falha em produção.** Server Actions têm limite de tamanho do corpo (1 MB por padrão, ajustável em `serverActions.bodySizeLimit`), e funções serverless na Vercel recusam corpos acima de cerca de 4,5 MB, seja qual for a configuração. Se o vídeo envia o arquivo pela Server Action, arquivos maiores vão falhar no deploy mesmo funcionando local. A saída é enviar direto do navegador para o storage, com permissões adequadas.
- **Chave de API no navegador.** Usar a chave administrativa num Client Component para "fazer funcionar rápido" entrega controle total do projeto a qualquer visitante.
- **Domínio não cadastrado no Appwrite.** O Appwrite só aceita requisições de plataformas registradas no projeto. Depois do deploy, cadastre o domínio de produção (e o de preview, se usar) ou o login para de funcionar.
- **Atributos e índices faltando.** Busca e ordenação no Appwrite exigem atributos criados na coleção e, para várias consultas, índices. O erro aparece só na hora de consultar.
- **Limites do plano gratuito.** O plano gratuito do Appwrite Cloud tem limites de armazenamento, banda e tamanho de arquivo. Confira os números atuais antes de prometer uma cota no seu app.
- **Arquivos órfãos.** Apagar o documento do banco sem apagar o arquivo do storage (ou o contrário) deixa lixo que ocupa espaço e não aparece em lugar nenhum.
