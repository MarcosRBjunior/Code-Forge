**Em uma frase:** um app de celular em que a pessoa faz login, escolhe origem e destino no mapa, vê motoristas disponíveis com preço e tempo estimados, paga a corrida com cartão e consulta o histórico de viagens.

**Nível:** intermediário · **Duração do vídeo:** cerca de 5,5 h · **Canal:** JavaScript Mastery · **Publicado em:** agosto de 2024

## Assista

[Build a Full Stack React Native App with Payments | PostgreSQL, TypeScript, Stripe, Tailwind](https://www.youtube.com/watch?v=kmy_YNhl0mw)

O tutorial monta um app mobile completo com Expo e TypeScript: telas de onboarding, autenticação com Clerk, mapa, busca de endereço, escolha de motorista, pagamento com Stripe e histórico de corridas salvo num Postgres serverless da Neon. Serve bem para quem já sabe React e quer o primeiro app mobile de verdade, com back-end e pagamento. O canal oferece um kit com os assets e o código do projeto (jsm.dev/uber-kit); o repositório do vídeo é a sua referência de versões.

## O que você vai construir

- Telas de onboarding em carrossel e telas de cadastro e login.
- Autenticação por e-mail com código de verificação e login social (OAuth) com Clerk.
- Navegação com Expo Router: grupos de rotas para autenticação e uma barra de abas inferior.
- API routes do próprio Expo conversando com um Postgres na Neon (usuários, motoristas, corridas).
- Mapa com a localização atual e marcadores dos motoristas.
- Busca de endereço com autocompletar para origem e destino.
- Fluxo de corrida em etapas: encontrar corrida, confirmar motorista, reservar.
- Estado global com Zustand (localização, destino, motorista escolhido).
- Pagamento com Stripe e traçado da rota no mapa.
- Histórico de corridas, tela de perfil e tela de mensagens.

Os motoristas do vídeo são dados fixos no banco: não há motorista real aceitando a corrida nem posição em tempo real. Isso é ótimo para estudar e é justamente o espaço para você fazer o projeto ser seu.

## Stack do vídeo e o que usar hoje

| Camada | No vídeo | Em 2026 |
|---|---|---|
| Framework mobile | Expo (SDK da época, por volta do 51) com React Native | Expo com o SDK atual; a Nova Arquitetura do React Native é o padrão e a antiga não é mais suportada |
| Navegação | Expo Router | Expo Router (mesma ideia de rotas por arquivo; confira mudanças de API nas notas de versão) |
| Estilo | Tailwind no React Native (provavelmente NativeWind) | NativeWind; confira qual versão do Tailwind a sua versão do NativeWind suporta antes de atualizar |
| Autenticação | Clerk para Expo | Clerk (SDK de Expo atualizado; a configuração de OAuth com redirect continua sendo o ponto sensível) |
| Banco | Neon (Postgres serverless) com o driver serverless | Neon ou qualquer Postgres; o driver `@neondatabase/serverless` continua sendo a opção simples |
| Back-end | API routes do Expo (arquivos `+api.ts`) | API routes do Expo com deploy no EAS Hosting, ou uma API separada (Node, Hono, Fastify) |
| Estado | Zustand | Zustand |
| Mapas | Provavelmente `react-native-maps` com APIs do Google | `react-native-maps` ou `expo-maps`; APIs do Google na versão nova (Places API New, Routes API) |
| Pagamento | Stripe (`@stripe/stripe-react-native`) | Stripe com PaymentSheet, criando o PaymentIntent no servidor |

<Callout type="warning" title="O que mudou desde a gravação">
**Expo Go só roda o SDK mais recente.** Se você clonar o repositório do vídeo com o SDK antigo e abrir no Expo Go da loja, ele recusa o projeto. Ou você atualiza o SDK (`npx expo install expo@latest` e depois `npx expo install --fix`), ou usa um development build (`npx expo run:android` / `run:ios` ou EAS Build), que roda qualquer SDK.

**Nova Arquitetura obrigatória.** Bibliotecas nativas antigas que não foram atualizadas podem quebrar no build. Rode `npx expo-doctor` e troque o que ele apontar.

**APIs do Google Maps.** Em 2025 o Google passou a Places API antiga e a Directions API para o status de legado: projetos novos no Google Cloud não conseguem mais ativá-las. Se o vídeo usar uma biblioteca de autocompletar ou de rotas que chama essas APIs, ela pode falhar com uma conta nova. Procure a versão que usa Places API (New) e Routes API, ou chame as APIs novas você mesmo pelo seu servidor.

**API routes em produção.** As rotas `+api.ts` rodam no servidor de desenvolvimento do Expo. Para o app publicado chamar essas rotas, você precisa hospedá-las (EAS Hosting ou outro servidor) e apontar a URL base para lá.

Dois caminhos honestos: seguir o vídeo com as versões exatas do `package.json` do repositório oficial (usando development build) e atualizar no fim, como um exercício de migração; ou começar no SDK atual já sabendo dessas diferenças e consultando a documentação quando o código do vídeo não bater.
</Callout>

## Roteiro de estudo

Não copie no automático. Antes de cada bloco, leia o título e tente prever o que vai ser feito; depois de cada bloco, feche o vídeo e explique em voz alta o que mudou no código.

### 1. Base do projeto e navegação (00:06:04 a 00:47:50)

Ambiente, criação do projeto, estrutura de pastas e configuração do Expo Router.

- **O que construir:** o projeto rodando no seu celular ou emulador, com grupos de rotas para autenticação e área logada.
- **Conceito:** roteamento por arquivo. Pastas entre parênteses agrupam telas sem aparecer na URL; `_layout.tsx` define a navegação daquele grupo.
- **Responda sozinho:** como o app decide se mostra a tela de login ou a home quando abre? Onde está essa decisão?

### 2. Onboarding, autenticação e abas (00:47:50 a 02:10:10)

Telas de onboarding, telas de cadastro e login, autenticação por e-mail com Clerk e a barra de abas.

- **O que construir:** cadastro com código de verificação por e-mail e redirecionamento para as abas depois do login.
- **Conceito:** o Clerk guarda a sessão no aparelho (em armazenamento seguro, se configurado com o `tokenCache`) e emite um token que o seu servidor deve validar.
- **Responda sozinho:** se alguém chamar a sua API route sem estar logado, o que acontece? A rota confere o usuário ou confia no que o app mandou?

### 3. Banco e API routes (02:10:10 a 02:57:25)

Integração com a Neon, rotas de API e a UI da home.

- **O que construir:** a tabela de usuários e a rota que grava o usuário depois do cadastro; depois, a home lendo dados reais.
- **Conceito:** a API route roda no servidor, então é ali que fica a string de conexão do banco. Nada que comece com `EXPO_PUBLIC_` é segredo: essas variáveis vão embutidas no app.
- **Responda sozinho:** desenhe as tabelas (usuários, motoristas, corridas) com as chaves estrangeiras. Que índice a consulta de histórico precisa?

### 4. Mapa, estado e busca de endereço (02:57:25 a 03:28:22)

Mapa com a localização, Zustand e autocompletar de endereço.

- **O que construir:** o mapa centrado no usuário, com permissão de localização pedida no momento certo, e origem e destino guardados no store.
- **Conceito:** estado global só para o que várias telas compartilham. Localização e motorista escolhido atravessam o fluxo; o texto digitado no campo não precisa.
- **Responda sozinho:** o que o app mostra se a pessoa negar a permissão de localização? E se o GPS demorar 10 segundos?

### 5. Fluxo da corrida e pagamento (03:28:22 a 04:48:00)

Telas de encontrar, confirmar e reservar a corrida, e a integração com o Stripe.

- **O que construir:** a escolha do motorista com preço calculado e o pagamento com PaymentSheet.
- **Conceito:** o app nunca vê a chave secreta do Stripe. O servidor cria o PaymentIntent com o valor e devolve só o `client_secret`; o app apresenta a folha de pagamento. A confirmação confiável chega por webhook no servidor.
- **Responda sozinho:** quem calcula o preço da corrida no vídeo, o app ou o servidor? O que impede alguém de alterar o valor antes de pagar?

### 6. Rota, dados reais, OAuth e telas finais (04:48:00 ao fim)

Traçado da rota, dados dinâmicos, login com Google, histórico, correções de redirecionamento do OAuth, perfil e mensagens.

- **O que construir:** a corrida gravada no banco depois do pagamento e listada no histórico; login social funcionando.
- **Conceito:** OAuth no celular depende de um esquema de URL do app (`scheme` no `app.json`) para o provedor devolver a pessoa ao app. O próprio vídeo tem um bloco só para o problema de redirecionamento.
- **Responda sozinho:** se o pagamento for aprovado mas a gravação da corrida falhar, o que o usuário vê? Como você garantiria que toda corrida paga aparece no histórico?

## Torne o projeto seu

O app do vídeo vai existir em milhares de repositórios com o mesmo nome, as mesmas telas e os mesmos motoristas de exemplo. O objetivo aqui é que quem abrir o seu veja decisões suas.

**Nome e identidade próprios.** "Uber" é marca registrada: no projeto publicado, use outro nome, outro logo, outras cores e ícones próprios ou com licença livre. Escolha um nicho e deixe o app com a cara dele: corrida de bicicleta, frete de pequenas mudanças, carona para eventos, transporte de pets. Um nicho dá sentido às features que você vai criar.

**Uma feature que o vídeo não tem.** Escolha uma ou duas e faça bem feito:

- **Lado do motorista.** Um segundo app (ou um modo no mesmo app) em que o motorista fica online, recebe a solicitação e aceita ou recusa. A corrida passa a ter estados reais: solicitada, aceita, a caminho, em andamento, concluída, cancelada.
- **Posição em tempo real.** O motorista envia a localização a cada poucos segundos e o passageiro vê o carro andar no mapa, via WebSocket ou Server-Sent Events.
- **Motoristas próximos de verdade.** Busque motoristas num raio usando PostGIS ou geohash, em vez de listar todos do banco.
- **Preço calculado no servidor.** Distância e duração vêm da Routes API chamada pelo servidor, com tarifa base, preço por km e multiplicador por horário. O app só exibe.
- **Cancelamento e reembolso.** Regras de cancelamento com taxa depois de X minutos e reembolso parcial via Stripe.
- **Avaliação da corrida** com nota e comentário, e média exibida no perfil do motorista.

**Testes.** Teste as regras de negócio fora da UI: cálculo de preço, transições de estado da corrida (não dá para concluir uma corrida que não começou), validação das rotas de API. Para componentes, React Native Testing Library. Um teste de ponta a ponta do fluxo principal com Maestro já impressiona.

**Tratamento de erros.** Sem internet, permissão negada, cartão recusado, servidor fora: cada um com uma mensagem clara e um caminho de volta. Nada de tela branca ou spinner eterno.

**Acessibilidade.** `accessibilityLabel` em botões que só têm ícone, tamanho mínimo de toque, contraste adequado e textos que respeitam o tamanho de fonte do sistema. Teste com TalkBack ou VoiceOver ao menos o fluxo de pedir corrida.

**Segurança.**

- Chave secreta do Stripe, string de conexão do banco e chave de servidor do Google só no servidor. No app, apenas chaves públicas.
- Restrinja a chave do Google Maps usada no app ao pacote Android e ao bundle iOS no console do Google Cloud.
- Toda API route valida o token do Clerk e usa o id do usuário do token, nunca um `userId` vindo do corpo da requisição. Sem isso, qualquer um lê o histórico de qualquer um.
- Valide entradas com Zod (coordenadas, ids, valores) e use consultas parametrizadas.
- Confirme o pagamento por webhook do Stripe com verificação de assinatura, e grave a corrida de forma idempotente (o mesmo evento pode chegar duas vezes).

**README com decisões.** Diagrama do fluxo app, API, banco e Stripe; por que Expo e não React Native puro; como o preço é calculado; o que foi mudado em relação ao tutorial e por quê; como rodar localmente com chaves de teste. Um GIF do fluxo completo e um APK ou link do Expo para testar.

O que um avaliador procura: crédito ao tutorial no README (esconder a origem pega mal quando ele reconhece as telas), commits seus depois do tutorial, ao menos uma parte difícil feita sem guia (o lado do motorista ou o tempo real) e a capacidade de explicar na entrevista por que o preço não pode ser calculado no celular.

## Armadilhas comuns

- **Expo Go incompatível.** O projeto do vídeo num SDK antigo não abre no Expo Go atual. Use development build ou atualize o SDK antes de começar a mexer.
- **Variáveis de ambiente.** No app, só variáveis com prefixo `EXPO_PUBLIC_` ficam disponíveis, e elas são públicas. Colocar a chave secreta com esse prefixo "para funcionar" é vazar a chave. Depois de mudar o `.env`, reinicie o bundler com cache limpo (`npx expo start -c`).
- **`localhost` no celular.** Do aparelho físico, `localhost` é o próprio celular. Use o IP da sua máquina na rede, ou a URL que o Expo mostra, para chamar as API routes em desenvolvimento.
- **Webhook do Stripe local.** O Stripe não alcança a sua máquina. Use `stripe listen --forward-to` com a Stripe CLI e o segredo de webhook que ela gera, diferente do de produção.
- **Cobrança no Google Cloud.** As APIs de mapas pedem conta de faturamento. Defina orçamento com alerta e cotas por API para que um loop de autocompletar não vire fatura.
- **Redirecionamento do OAuth.** Login social que funciona no emulador e falha no aparelho quase sempre é `scheme` errado ou URL de redirecionamento não cadastrada no Clerk.
