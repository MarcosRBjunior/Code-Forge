Currículo é promessa; projeto é prova. Quando você escreve "sei React e PostgreSQL", quem lê precisa acreditar. Quando você mostra um app no ar, com código público, histórico de commits e um README que explica as decisões, a pessoa não precisa acreditar em nada: ela vê.

Esta trilha existe para isso. Cada capítulo descreve um projeto com escopo fechado, que você consegue terminar sozinho em dias ou poucas semanas, e que deixa no seu GitHub algo que vale a pena abrir.

## Para que serve um projeto de portfólio

Um bom projeto de portfólio faz três coisas ao mesmo tempo:

- **Prova habilidade concreta.** Não "estudei APIs", mas "integrei uma API externa, tratei limite de requisições e coloquei cache na frente".
- **Dá assunto para a entrevista.** Projeto bem feito rende perguntas como "por que você escolheu isso?", e você tem a resposta, porque foi você quem escolheu.
- **Mostra que você termina coisas.** Muita gente começa; pouca gente publica, documenta e mantém. Um MVP no ar vale mais que uma ideia ambiciosa pela metade.

## Como a trilha está organizada

| Módulo | Para quem | O que você pratica |
|---|---|---|
| Fase 1: primeiros projetos | Iniciante | CRUD, formulários, autenticação, deploy |
| Fase 2: projetos intermediários | Já fez um app completo | APIs externas, gráficos, upload de mídia, CI |
| Fase 3: projetos avançados | Quer mirar vagas pleno ou sênior | Arquitetura, filas, escala, tempo real |
| IA aplicada | Quer trabalhar com LLMs | 5 projetos incrementais que viram um só produto |
| Machine Learning | Quer treinar e avaliar modelos | Dados, treino, métricas, servir o modelo |
| Web3 | Curioso por contratos inteligentes | Carteiras, contratos, transações |
| Dados | Quer ir para análise ou engenharia de dados | Limpeza, análise, visualização, detecção |

O módulo de IA aplicada é diferente dos outros: os cinco projetos se somam. O chat com streaming ganha RAG, depois memória, depois imagens, depois um agente com busca. No final você tem um produto só, com história de evolução, em vez de cinco demos soltas.

## Como escolher seus projetos

**Poucos e bem feitos.** Dois a quatro projetos completos valem mais que quinze tutoriais copiados. Recrutador reconhece clone de tutorial em segundos: mesmo nome, mesmo layout, nenhuma decisão própria.

**Pelo cargo que você quer.** Mirando front-end? Priorize projetos com UI rica, acessibilidade e performance. Back-end? Projetos com banco, filas, autenticação e testes. Dados ou IA? Os módulos específicos. Leia a descrição da vaga dos seus sonhos e escolha projetos que provem os itens dela.

**Termine o MVP antes dos extras.** Cada capítulo separa o que é obrigatório do que é bônus. A tentação de adicionar "só mais uma feature" é o principal motivo de projetos nunca saírem do ar. Publique o MVP, depois melhore.

<Callout type="tip" title="Uma regra simples">
Se você não consegue explicar em uma frase o que o projeto faz, o escopo está grande demais. Corte até caber.
</Callout>

## Como usar cada capítulo

Todos os capítulos de projeto seguem a mesma estrutura:

1. **Em uma frase, nível e tempo:** para você decidir rápido se é o projeto certo agora.
2. **MVP:** a lista de tarefas que define "pronto". Copie para o seu README ou para as issues do repositório.
3. **Stack sugerida e fora do escopo:** sugestões, não regras. O "fora do escopo" é tão importante quanto o MVP: ele protege seu prazo.
4. **Etapas:** a ordem que reduz o risco, com o porquê de cada passo.
5. **Extras:** o que fazer depois que o MVP estiver no ar, se quiser se destacar.
6. **Base no CodeForge:** os capítulos de outros cursos que explicam a teoria por trás.

Quando terminar um projeto, marque o capítulo como concluído. E use as notas do CodeForge como diário de bordo: anote decisões, erros que custaram uma tarde, links úteis. Essas notas viram matéria-prima para o README e para as respostas na entrevista.

## Recomendações gerais

- **Repositório público desde o dia 1.** O histórico mostra como você trabalha, não só o resultado.
- **Commits pequenos com mensagens claras.** "Adiciona paginação na listagem" diz muito mais que "ajustes".
- **Deploy cedo.** Coloque um "olá mundo" no ar no primeiro dia. Problemas de deploy descobertos no fim custam caro.
- **Segredos fora do Git.** Chaves ficam em variáveis de ambiente; no repositório vai só um `.env.example`.
- **README antes de dizer que terminou.** Projeto sem README, para quem visita, é projeto que não existe.
