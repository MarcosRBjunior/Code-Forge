**Em uma frase:** uma Action própria, configurável por inputs, testada e publicada no Marketplace, que automatiza uma tarefa útil em pull requests.

**Nível:** intermediário · **Tempo:** 1 semana · **Pré-requisito:** saber usar Git e GitHub e ter escrito algum workflow simples

## O que você vai construir

Uma Action que outras pessoas podem usar com uma linha `uses:` no workflow delas. Escolha uma tarefa pequena e realmente útil, por exemplo:

- comentar no PR um resumo das mudanças (arquivos por pasta, linhas adicionadas e removidas);
- procurar links quebrados nos arquivos Markdown alterados;
- medir o tamanho do bundle e avisar quando ele crescer acima de um limite.

O projeto é diferente de um app: o "usuário" é outro desenvolvedor, a "interface" é o arquivo `action.yml` e o README, e a qualidade aparece em inputs bem nomeados, mensagens de erro claras, versionamento e segurança. Ferramenta de desenvolvedor publicada e usada por terceiros chama muita atenção em portfólio.

## MVP

- [ ] `action.yml` com nome, descrição, inputs com valores padrão e pelo menos um output
- [ ] Lógica em JavaScript/TypeScript (ou composite) que resolve a tarefa escolhida
- [ ] Testes unitários da lógica e um workflow que usa a própria Action no repositório
- [ ] Permissões mínimas documentadas para o `GITHUB_TOKEN`
- [ ] Versão por tag (`v1.0.0` e a tag móvel `v1`)
- [ ] README com exemplo de uso copiável, tabela de inputs e outputs, GIF ou print do resultado e publicação no Marketplace

## Stack sugerida

| Parte | Opção principal | Alternativa |
|---|---|---|
| Tipo de Action | JavaScript/TypeScript com o toolkit oficial | Composite (sequência de passos em shell) |
| Bibliotecas | `@actions/core` e `@actions/github` | Chamadas diretas à API REST |
| Empacotamento | Bundle num único arquivo `dist` | Composite sem build |
| Testes | Vitest ou Jest | Testes do script em shell com bats |

## Fora do escopo

Action em container Docker, suporte a dezenas de configurações, GitHub App própria com servidor e painel web. Uma tarefa, bem feita, com documentação impecável.

## Etapas

1. **Defina o contrato.** Escreva o `action.yml` e o README de uso antes do código. Se o exemplo no README parecer confuso, os inputs estão mal pensados.
2. **Separe a lógica da integração.** Coloque a regra (calcular o resumo, achar links, comparar tamanhos) em funções puras que recebem dados e devolvem resultado. A parte que lê inputs e chama a API do GitHub fica fina. Assim você testa sem rede.
3. **Teste.** Testes unitários para as funções puras e um workflow no próprio repositório que roda a Action em PRs de teste, usando `uses: ./`.
4. **Empacote.** Actions JavaScript rodam sem `npm install` no runner, então gere um bundle em `dist` e faça o CI falhar se o `dist` commitado estiver desatualizado.
5. **Versione e publique.** Crie uma release com tag semântica e mova a tag principal (`v1`) para ela. Quem usa `@v1` recebe correções sem mudar nada; mudanças incompatíveis vão para `v2`.
6. **Documente a segurança.** Diga no README quais permissões a Action precisa e mostre o bloco `permissions` no exemplo.

Um `action.yml` mínimo:

```yaml
name: "Resumo do PR"
description: "Comenta no pull request um resumo dos arquivos alterados"
inputs:
  github-token:
    description: "Token com permissão para comentar no PR"
    default: ${{ github.token }}
  max-files:
    description: "Quantos arquivos listar no comentário"
    default: "20"
outputs:
  changed-files:
    description: "Número de arquivos alterados"
runs:
  using: "node20"
  main: "dist/index.js"
```

Confira na documentação qual versão de runtime Node está disponível quando você publicar; ela muda com o tempo.

<Callout type="warning" title="Cuidado com pull_request_target">
O evento `pull_request_target` roda com permissões e segredos do repositório de destino, mesmo em PRs vindos de forks. Se o workflow fizer checkout e executar o código do PR nesse evento, qualquer pessoa pode rodar código com seus segredos. Prefira `pull_request`, declare `permissions` com o mínimo (por exemplo, `contents: read` e `pull-requests: write`) e nunca interpole título ou corpo do PR direto num comando shell.
</Callout>

## Extras para se destacar

- Atualizar o mesmo comentário em vez de criar um novo a cada push.
- Escrever um resumo no job summary, além do comentário.
- Matriz de testes em Linux, macOS e Windows.
- Changelog gerado automaticamente a cada release.
