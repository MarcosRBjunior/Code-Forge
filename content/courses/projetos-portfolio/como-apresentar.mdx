Um projeto excelente que ninguém entende em 30 segundos tem o mesmo efeito de um projeto que não existe. Quem avalia portfólio abre dezenas de repositórios por semana e decide rápido. Este capítulo mostra como empacotar o que você construiu para quatro públicos: quem abre o repositório, quem clica no link do app, quem vê seu LinkedIn e quem entrevista você.

## O README que vende

O README é a página inicial do projeto. Escreva para alguém com pressa, na ordem em que essa pessoa vai procurar as coisas:

1. **O que é, em uma frase.** "Dashboard que mostra indicadores de saneamento por município num mapa interativo." Nada de "projeto feito para estudar".
2. **Um GIF ou screenshot logo abaixo.** 10 a 20 segundos mostrando o fluxo principal. É a parte mais vista do README inteiro.
3. **Link do deploy**, se houver, em destaque.
4. **Como rodar localmente.** Comandos copiáveis, do clone ao app no ar, incluindo a cópia do `.env.example`.
5. **Decisões técnicas e trade-offs.** Por que Postgres e não MongoDB? Por que cache de 24 horas? Duas ou três decisões com o motivo e o que você abriu mão.
6. **O que você faria diferente** ou faria a seguir. Mostra maturidade: você sabe onde estão os limites do que entregou.

Um esqueleto que funciona:

```text
# Nome do projeto
Uma frase dizendo o que faz e para quem.

[GIF]   Demo: https://...

## Como rodar
## Stack
## Decisões e trade-offs
## Próximos passos
```

## Repositório público e segredos

O repositório precisa estar público para servir como prova. Isso torna obrigatório um cuidado: **nunca commite chaves, senhas ou tokens**. Coloque os valores reais num `.env` ou `.env.local` listado no `.gitignore` e publique um `.env.example` só com os nomes das variáveis e valores falsos.

<Callout type="warning" title="Chave commitada é chave vazada">
Apagar o arquivo num commit seguinte não resolve: o valor continua no histórico. Se isso acontecer, revogue a chave no provedor imediatamente e gere outra.
</Callout>

Outros sinais de cuidado que contam pontos: licença no repositório, descrição e tópicos preenchidos no GitHub, issues abertas para os próximos passos e um workflow de CI simples rodando lint e testes.

## Deploy

Um link que funciona vale mais que qualquer descrição. Há várias plataformas com plano gratuito ou de baixo custo para front-end estático, apps full-stack, containers e bancos gerenciados. Os planos e limites mudam com frequência, então confira as condições atuais antes de escolher e evite depender de um recurso que pode sumir.

Cuidados práticos:

- Se o app depende de uma API paga, coloque limite de uso por visitante ou um modo demonstração, para um acesso inesperado não virar uma conta alta.
- Se o banco gratuito "dorme" após inatividade, avise no README que o primeiro acesso pode demorar.
- Tenha dados de exemplo. Um app vazio não mostra nada.

## LinkedIn

Use a seção de **Projetos** ou de **Destaques** do perfil para fixar os dois ou três melhores, com link para o repositório e para o deploy.

Ao terminar um projeto, publique um post curto:

- uma linha com o problema que o projeto resolve;
- o GIF;
- uma ou duas coisas que você aprendeu (de preferência uma dificuldade real e como resolveu);
- os links.

Posts que contam uma dificuldade concreta ("descobri que o dia do usuário não é o dia do servidor") rendem mais conversa que listas de tecnologias.

## Na entrevista

Prepare uma versão de 2 minutos do projeto, nesta ordem:

1. **Problema:** o que o projeto resolve e para quem.
2. **Arquitetura:** os blocos principais e como os dados fluem entre eles.
3. **Uma decisão difícil:** as opções que você considerou e por que escolheu uma.
4. **Um bug interessante:** o sintoma, como você investigou e a causa.
5. **O que melhoraria:** com mais tempo ou com mais usuários.

Depois disso, o entrevistador escolhe onde aprofundar. Por isso, conheça cada parte do código, inclusive o que veio de biblioteca ou de IA: "não sei, foi gerado" é a pior resposta possível sobre o seu próprio projeto.

## Checklist de publicação

- [ ] README com frase de abertura, GIF, link do deploy e instruções para rodar
- [ ] Seção de decisões técnicas e próximos passos
- [ ] `.env.example` publicado e nenhum segredo no histórico do Git
- [ ] App no ar com dados de exemplo
- [ ] Descrição e tópicos preenchidos no GitHub
- [ ] Projeto fixado no perfil do GitHub e no LinkedIn
- [ ] Pitch de 2 minutos ensaiado em voz alta
