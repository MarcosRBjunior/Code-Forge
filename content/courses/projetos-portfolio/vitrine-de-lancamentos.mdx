**Em uma frase:** um site onde pessoas publicam produtos que lançaram, a comunidade vota e a página inicial mostra o ranking do dia.

**Nível:** iniciante · **Tempo:** 1 a 2 semanas · **Pré-requisito:** um CRUD com banco e login pronto (de uma biblioteca ou do seu projeto de autenticação)

## O que você vai construir

Uma página inicial com os lançamentos de hoje ordenados por votos, um formulário para publicar um produto (nome, frase de efeito, link, imagem) e um botão de voto em cada card. Cada pessoa logada vota uma vez por produto e pode retirar o voto. Dias anteriores ficam acessíveis num arquivo.

Inspire-se no formato, não na marca: crie nome, logo e identidade visual próprios, e use nos exemplos produtos fictícios ou seus, com imagens que você tem direito de usar.

## MVP

- [ ] Publicar um produto com nome, descrição curta, link e imagem
- [ ] Votar e retirar o voto, só com login
- [ ] Um voto por usuário por produto, garantido no banco
- [ ] Ranking do dia na página inicial e arquivo por data
- [ ] Página de cada produto
- [ ] Deploy gratuito e README com print do ranking

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Aplicação | Next.js | Rails ou Django |
| Banco | Postgres | SQLite |
| Login | Biblioteca de auth do framework | O seu projeto de autenticação |

## Fora do escopo

Comentários, perfis públicos completos, notificações, moderação elaborada e algoritmo de ranking com decaimento ao longo do tempo. Ranking do dia por total de votos já é o produto.

## Etapas

1. **Modele produtos e votos.** A tabela de votos tem `user_id` e `product_id` com chave primária composta. É isso que garante um voto por pessoa: o banco recusa a segunda linha, não importa quantas abas ou requisições simultâneas existam.
2. **Votar de forma idempotente.** Use `INSERT ... ON CONFLICT DO NOTHING`. Clicar duas vezes, ou a rede reenviar a requisição, não gera erro nem voto extra. Retirar o voto é um `DELETE` da linha.
3. **Contagem.** Comece contando com `COUNT` e `GROUP BY` na consulta do ranking. Se ficar lento, mantenha uma coluna `votes_count` no produto, atualizada na mesma transação do voto.
4. **"Hoje" tem fuso horário.** Defina o dia do ranking num fuso fixo (por exemplo, `America/Sao_Paulo`) e filtre por `published_at` dentro desse dia. Sem isso, o ranking "vira" às 21h para quem está no Brasil.
5. **Nunca confie no cliente.** O `user_id` do voto vem da sessão no servidor, nunca do corpo da requisição. Valide o link do produto (só `http` e `https`) para ninguém publicar um `javascript:` disfarçado.
6. **UI otimista.** Ao clicar, atualize o contador na hora e desfaça se o servidor responder com erro. A sensação de rapidez faz muita diferença.
7. **Deploy e README.** Explique como o banco garante o voto único. É a pergunta que todo entrevistador vai fazer.

As duas peças centrais em SQL:

```sql
CREATE TABLE votes (
  user_id INT NOT NULL REFERENCES users(id),
  product_id INT NOT NULL REFERENCES products(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, product_id)
);

INSERT INTO votes (user_id, product_id) VALUES ($1, $2)
ON CONFLICT DO NOTHING;
```

<Callout type="tip" title="Checar antes de inserir não basta">
Fazer um `SELECT` para ver se o voto existe e só então o `INSERT` deixa uma janela: duas requisições ao mesmo tempo passam pela checagem e as duas inserem. A restrição no banco fecha essa janela de vez.
</Callout>

## Extras para se destacar

- Comentários com uma resposta por nível.
- Ranking da semana e do mês usando a mesma consulta com outro intervalo.
- Limite de publicações por usuário por dia, para evitar spam.
- Imagem de prévia (Open Graph) gerada para cada produto, bonita quando alguém compartilha o link.

## O que este projeto mostra no portfólio

"Eu sei usar o banco para garantir regras de negócio, como um voto por pessoa, em vez de confiar em checagens que quebram com requisições simultâneas."
