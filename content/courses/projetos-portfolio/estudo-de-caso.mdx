**Em uma frase:** resolver um problema real de alguém de verdade com uma solução pequena e documentar todo o raciocínio, do problema ao resultado medido.

**Nível:** intermediário · **Tempo:** 2 a 4 semanas · **Pré-requisito:** já ter publicado pelo menos um app completo

## O que você vai construir

Diferente dos outros capítulos, aqui o app não é definido de antemão. Você encontra um "cliente" real: a padaria do bairro que anota encomendas no caderno, a ONG que controla voluntários numa planilha caótica, o familiar que agenda pacientes pelo WhatsApp. Conversa com essa pessoa, descobre o problema que mais dói e constrói a menor solução que resolve esse problema.

O entregável principal não é só o código: é o **estudo de caso**, um documento que conta problema → pesquisa → decisões → resultado. É o tipo de projeto que mostra raciocínio de produto e de engenharia, e não apenas domínio de uma biblioteca. Quase ninguém tem um no portfólio, e por isso ele se destaca.

## MVP

- [ ] Anotações da entrevista com o cliente, com o problema descrito nas palavras dele
- [ ] Lista de requisitos priorizada (o que entra, o que fica para depois e por quê)
- [ ] Solução funcionando, usada pelo cliente por pelo menos uma ou duas semanas
- [ ] Uma métrica medida antes e depois (tempo gasto, erros, pedidos perdidos)
- [ ] Estudo de caso escrito no README ou numa página, com prints e o resultado
- [ ] Deploy e GIF do fluxo principal

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| App | A stack que você já domina | Ferramenta no-code, se resolver melhor |
| Dados | PostgreSQL ou SQLite | Planilha com uma API em cima |
| Documentação | README com seções do estudo de caso | Página própria no seu site |

A stack aqui é a decisão menos importante. Escolher a ferramenta mais simples que resolve, e justificar, já conta pontos no estudo de caso.

## Fora do escopo

Virar um produto para vender, atender vários clientes, app nativo de celular e qualquer funcionalidade que o cliente não pediu nem precisa. Também fica de fora lidar com dados sensíveis sem necessidade: se puder resolver sem guardar CPF ou dados de saúde, resolva.

## Etapas

1. **Escolha o cliente e o problema.** Procure um processo repetitivo, manual e frequente. Problemas que acontecem toda semana dão métricas melhores que os que acontecem uma vez por ano.
2. **Entreviste antes de propor.** Pergunte como a pessoa faz hoje, o que dá errado, quanto tempo leva, o que acontece quando falha. Evite perguntas que já sugerem a solução ("você usaria um app?"). Acompanhe a tarefa sendo feita, se puder.
3. **Escreva requisitos e corte.** Liste tudo o que apareceu, priorize pelo impacto no problema principal e defina o MVP. Registre o que ficou de fora e o motivo; isso vira uma das partes mais interessantes do estudo de caso.
4. **Meça o "antes".** Escolha uma métrica simples e anote o valor atual: minutos por dia gastos na tarefa, encomendas esquecidas por mês, mensagens trocadas para marcar um horário.
5. **Construa pequeno e entregue cedo.** Uma primeira versão em poucos dias, usada de verdade, ensina mais que um mês de desenvolvimento no escuro. Ajuste com base no uso real.
6. **Meça o "depois" e escreva.** Compare a métrica, colete uma frase do cliente (com permissão) e escreva o estudo de caso seguindo a estrutura abaixo.

```text
1. Contexto: quem é o cliente e como o processo funcionava
2. Problema: o que doía, com números
3. Pesquisa: o que a entrevista e a observação revelaram
4. Decisões: o que entrou, o que ficou de fora e por quê
5. Solução: arquitetura, telas, trade-offs técnicos
6. Resultado: métrica antes e depois, feedback do cliente
7. Aprendizados: o que faria diferente
```

<Callout type="note" title="Privacidade do cliente">
Peça autorização antes de publicar qualquer coisa. Troque nomes, use dados fictícios nos prints e nunca coloque dados reais de clientes do seu cliente no repositório.
</Callout>

## Extras para se destacar

- Uma segunda rodada de melhoria guiada por feedback, documentada como "versão 2".
- Um pequeno manual de uso escrito para o cliente, em linguagem não técnica.
- Backup automático e exportação dos dados, para o cliente não ficar refém do seu app.

## O que este projeto mostra no portfólio

"Eu sei ouvir um problema real, decidir o que construir e o que não construir, entregar e provar com números que melhorou a vida de alguém."
