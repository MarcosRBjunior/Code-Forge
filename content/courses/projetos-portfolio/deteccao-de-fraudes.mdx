**Em uma frase:** um modelo que dá a cada transação uma probabilidade de fraude, com o limiar de bloqueio escolhido pelo custo dos erros e servido por uma API.

**Nível:** intermediário a avançado em ML · **Tempo:** 2 semanas · **Pré-requisito:** Python, scikit-learn e uma API simples

## O que você vai construir

Um sistema de ponta a ponta com um dataset público de transações de cartão anonimizadas: análise do desbalanceamento, modelos comparados com as métricas certas, escolha do limiar de decisão a partir de custos e uma API que recebe uma transação e devolve um score e uma decisão (aprovar, revisar ou bloquear).

Fraude é o exemplo clássico de classes desbalanceadas: em muitos datasets públicos, menos de 1% das transações são fraudes. Um modelo que responde "não é fraude" para tudo tem acurácia de 99% e não serve para nada. Mostrar que você entende isso é o coração do projeto.

## MVP

- [ ] Dataset público e anonimizado, com a licença citada no README
- [ ] Divisão treino, validação e teste estratificada (ou temporal, se houver coluna de tempo) feita antes da exploração
- [ ] Baseline (regressão logística) e um modelo mais forte (gradient boosting), comparados por PR-AUC, precision e recall
- [ ] Limiar escolhido na validação a partir de uma tabela de custos de falso positivo e falso negativo
- [ ] API que recebe uma transação e devolve score, decisão e versão do modelo
- [ ] README com as métricas no teste, a curva precision-recall e as instruções para rodar a API

## Fora do escopo

Dados reais de clientes, streaming de eventos em tempo real, regras de negócio complexas e retreino automático. O MVP é um modelo bem avaliado atrás de uma API.

## Etapas

1. **Separe antes de olhar.** Se o dataset tem coluna de tempo, use divisão temporal: treine no passado e teste no futuro, como acontece em produção. Caso contrário, estratifique para manter a proporção de fraudes nos três conjuntos.
2. **Esqueça a acurácia.** Use PR-AUC como métrica principal e olhe precision e recall em limiares concretos. A ROC-AUC tende a parecer otimista quando os positivos são raros.
3. **Baseline e modelo forte.** Regressão logística com pesos de classe primeiro; depois gradient boosting. Se usar oversampling (como SMOTE), aplique só dentro do treino de cada fold; aplicar antes da divisão vaza informação para a validação.
4. **Limiar pelo custo.** Defina custos simples, por exemplo: deixar passar uma fraude custa o valor da transação; bloquear um cliente legítimo custa um valor fixo de atendimento e desgaste. Na validação, escolha o limiar que minimiza o custo total. O limiar padrão de 0,5 quase nunca é o certo.
5. **Avalie no teste uma vez.** Reporte PR-AUC, precision e recall no limiar escolhido e o custo total, comparando com "não bloquear nada".
6. **API.** Carregue o modelo e o limiar salvos, valide a entrada e devolva o score, a decisão e a versão do modelo. Escreva um teste com uma transação de exemplo.

A escolha do limiar pelo custo fica assim:

```python
import numpy as np
from sklearn.metrics import precision_recall_curve, average_precision_score

scores = modelo.predict_proba(X_val)[:, 1]
print("PR-AUC:", average_precision_score(y_val, scores))

CUSTO_FN, CUSTO_FP = 100.0, 5.0  # fraude que passa vs cliente bloqueado à toa
limiares = np.linspace(0.01, 0.99, 99)
custos = [CUSTO_FN * ((scores < t) & (y_val == 1)).sum()
          + CUSTO_FP * ((scores >= t) & (y_val == 0)).sum() for t in limiares]
melhor = limiares[int(np.argmin(custos))]
```

<Callout type="note" title="Cuidado com o vazamento">
Features como "número de transações do cartão nas últimas 24 horas" só podem usar transações anteriores à atual. Se usarem o dia inteiro, o modelo enxerga o futuro e brilha no teste para depois falhar em produção.
</Callout>

## Extras para se destacar

- Monitoramento de drift: comparar a distribuição dos scores e das principais features entre semanas e alertar quando mudar.
- Explicação por transação (valores SHAP) devolvida junto com o score.
- Três faixas de decisão (aprovar, revisar, bloquear) com capacidade limitada de revisão manual.
- Calibração das probabilidades para que o score possa ser lido como chance real.
