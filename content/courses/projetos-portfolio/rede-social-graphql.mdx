**Em uma frase:** a API de uma rede social pequena (perfis, posts, comentários, seguidores) exposta em GraphQL, sem o problema N+1 e com regras de acesso por campo.

**Nível:** avançado · **Tempo:** 3 a 4 semanas · **Pré-requisito:** uma API REST com banco relacional e autenticação já feita

## O que você vai construir

Uma API GraphQL em que o cliente pede exatamente os dados de que precisa, numa só requisição: o perfil, os últimos posts e, de cada post, os três primeiros comentários com o nome do autor. Um front-end simples consome essa API, mas a estrela é o back-end.

GraphQL é fácil de começar e fácil de fazer mal. Uma consulta inocente pode disparar centenas de idas ao banco, um campo privado pode vazar porque ninguém conferiu quem está pedindo e um cliente malicioso pode mandar uma consulta aninhada que derruba o servidor. Este projeto é sobre resolver essas três coisas.

## MVP

- [ ] Schema com `User`, `Post`, `Comment`, seguir e curtir, documentado com descrições nos tipos
- [ ] Queries para perfil, feed e post; mutations para criar post, comentar, seguir e curtir
- [ ] DataLoader em todas as relações, com teste que conta as consultas ao banco
- [ ] Autenticação por token e autorização por campo (e-mail visível só para o próprio usuário)
- [ ] Paginação por cursor no padrão de conexões (`edges`, `node`, `pageInfo`)
- [ ] Limite de profundidade e de complexidade das consultas
- [ ] README com exemplos de consultas e um GIF do front-end ou do playground

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Servidor GraphQL | GraphQL Yoga ou Apollo Server (Node.js) | Strawberry (Python) ou gqlgen (Go) |
| Batching | DataLoader | Batching nativo da biblioteca escolhida |
| Banco | PostgreSQL | MySQL |
| Cliente | Next.js com urql ou Apollo Client | React + Vite |

## Fora do escopo

Federação de vários serviços, upload de mídia, busca, recomendação e cache persistente de consultas. Subscriptions ficam como extra.

## Etapas

1. **Schema primeiro.** Escreva o schema antes dos resolvers e pense nele como contrato público: nomes claros, campos não nulos onde a regra garante o valor e descrições em cada tipo.
2. **Resolvers ingênuos.** Implemente cada relação da forma óbvia e ative o log de SQL. Peça 20 posts com o autor de cada um e conte: 1 consulta para os posts e mais 20 para os autores. Esse é o N+1, e você acabou de vê-lo acontecer.
3. **DataLoader por requisição.** Crie os loaders no contexto de cada requisição (nunca globais, para não misturar dados entre usuários). O loader junta os ids pedidos no mesmo ciclo e faz uma só consulta com `WHERE id = ANY(...)`. Escreva um teste que garante o número fixo de consultas.

```text
Sem DataLoader                     Com DataLoader
posts (1 consulta)                 posts (1 consulta)
 ├─ autor do post 1 (1)            └─ autores dos 20 posts (1 consulta)
 ├─ autor do post 2 (1)
 └─ ... 20 consultas               total: 2 consultas
```

4. **Autorização por campo.** A autenticação acontece uma vez, ao montar o contexto. A autorização acontece no resolver de cada campo sensível: `email` só para o próprio usuário, posts de conta privada só para seguidores aprovados. Centralize essas regras numa camada de serviço, não espalhadas por todo resolver.
5. **Paginação por cursor.** Siga o padrão de conexões: o cursor é um valor opaco (por exemplo, `created_at` e `id` em base64), e `pageInfo.hasNextPage` diz ao cliente se há mais. Limite `first` a um máximo, como 50.
6. **Proteja o servidor.** Rejeite consultas acima de uma profundidade e de um custo calculado, desative a introspecção em produção se fizer sentido e aplique rate limiting por usuário.
7. **Erros com significado.** Devolva erros com códigos (`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`) em vez de mensagens soltas, e nunca exponha detalhes internos do banco.

<Callout type="note" title="Subscriptions são opcionais">
Notificar novos comentários em tempo real via subscriptions (sobre WebSockets) é um ótimo extra, mas traz autenticação na conexão, reconexão e escala horizontal. Termine o MVP antes.
</Callout>

## Extras para se destacar

- Subscription para novos comentários num post.
- Consultas persistidas: o cliente envia só o hash de consultas aprovadas.
- Cache de respostas em campos públicos com controle de expiração.
- Comparação no README: a mesma tela feita com REST e com GraphQL, contando requisições e bytes.
