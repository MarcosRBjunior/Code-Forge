**Em uma frase:** o usuário fecha o navegador, volta no dia seguinte e retoma a conversa antiga de onde parou.

**Nível:** intermediário em IA · **Tempo:** 3 a 4 dias · **Pré-requisito:** [Projeto 2: RAG sobre documentos](/learn/projetos-portfolio/rag-sobre-documentos) (ou pelo menos o Projeto 1)

## O que você vai construir

Até aqui, o histórico da conversa vive no estado do front-end: recarregou a página, perdeu tudo. Neste projeto, as conversas passam a ser dados do produto. Cada uma tem um id, um título e uma lista de mensagens gravadas no banco, e a tela ganha uma barra lateral para criar uma conversa nova ou abrir uma antiga.

O que muda no código existente: o front deixa de mandar o histórico inteiro a cada pergunta e passa a mandar só o `session_id` e a mensagem nova. Quem monta o contexto agora é o servidor, que carrega a thread do banco antes de chamar o modelo. Isso vale tanto para o chat simples quanto para o RAG: a pergunta de acompanhamento ("e no capítulo 3?") só faz sentido se o modelo enxergar as mensagens anteriores.

## MVP

- [ ] Lista de conversas com título e data da última mensagem
- [ ] Botão de nova conversa e clique para abrir uma existente
- [ ] Mensagens do usuário e do assistente gravadas no banco
- [ ] Ao retomar, o histórico entra no contexto da próxima pergunta
- [ ] Funciona com o chat do Projeto 1 e com o RAG do Projeto 2 (a conversa lembra qual documento está em uso)

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Banco | Postgres (o mesmo do pgvector) | SQLite ou Supabase |
| Modelo de dados | Tabelas `sessions` e `messages` | Checkpointer do LangGraph |
| Front | `session_id` na URL da conversa | `session_id` no estado da página |
| Back | Rota carrega a thread antes de chamar o LLM | — |

Guardar o `session_id` na URL (por exemplo, `/chat/abc123`) é um detalhe pequeno que melhora muito o produto: o usuário pode favoritar uma conversa e o botão de voltar do navegador funciona.

## Fora do escopo

Memória de longo prazo entre conversas (o app lembrar fatos do usuário de uma sessão para outra) e resumo automático de threads gigantes. Ambos são decisões de produto com custo e riscos próprios; aqui basta persistir e retomar.

## Etapas

1. **Esquema do banco.** Crie as duas tabelas e uma migração versionada no repositório. Uma mensagem pertence a uma sessão e tem papel, conteúdo e data.
2. **Gravar antes e depois.** Grave a mensagem do usuário assim que ela chega e a do assistente quando o streaming terminar. Se o stream cair no meio, decida o que fazer (gravar o parcial ou marcar como incompleta) e documente a escolha.
3. **Carregar a thread no servidor.** Na rota de chat, busque as mensagens da sessão em ordem, acrescente a nova e só então chame o modelo. O front não é mais a fonte da verdade do histórico.
4. **Limitar o contexto.** Uma conversa longa estoura a janela de contexto e encarece cada chamada. No MVP, mande só as últimas N mensagens e deixe isso explícito no código.
5. **Lista de conversas.** Monte a barra lateral ordenada pela última atividade. O título pode ser as primeiras palavras da primeira pergunta.
6. **Integrar com o RAG.** Guarde na sessão o id do documento em uso, para que a recuperação continue no mesmo PDF quando a conversa for retomada.

O esquema mínimo cabe em poucas linhas:

```sql
CREATE TABLE sessions (
  id          uuid PRIMARY KEY,
  title       text NOT NULL,
  document_id uuid,
  updated_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE messages (
  id         bigserial PRIMARY KEY,
  session_id uuid NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  role       text NOT NULL,
  content    text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

<Callout type="tip" title="Pense no dono da conversa">
Se o app for público, toda consulta por sessão precisa conferir que ela pertence ao usuário logado. Sem isso, trocar o id na URL abre a conversa de outra pessoa. O projeto [Sistema de autenticação de usuários](/learn/projetos-portfolio/autenticacao-de-usuarios), da Fase 1, resolve essa parte.
</Callout>

## Extras para se destacar

- Título gerado pelo próprio modelo depois da primeira resposta.
- Renomear, apagar e buscar conversas.
- Resumo das mensagens antigas quando a thread passa de um limite, mantendo as recentes na íntegra.
- Exportar a conversa em Markdown.
