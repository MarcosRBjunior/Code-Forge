Os cinco projetos desta trilha não são cinco apps soltos. São cinco etapas do mesmo produto: um assistente que conversa com streaming, consulta documentos, lembra das conversas, enxerga imagens e busca na web. Esta aula mostra como apresentar isso para que quem abre o seu GitHub (ou te entrevista) enxergue a progressão, e não só o resultado final.

## Ordem e dependências

Cada etapa só acrescenta uma capacidade e reaproveita tudo o que veio antes:

```text
[1] Chat com streaming        UI, rota de API, chave no servidor
        │
        ▼
[2] + RAG sobre documentos    upload, chunks, embeddings, pgvector, citação
        │
        ▼
[3] + Memória de conversas    tabelas sessions e messages, retomada
        │
        ▼
[4] + Anexo de imagens        mensagem com várias partes, object storage
        │
        ▼
[5] + Agente com busca        loop de tool calling, fontes na resposta
```

Se você pular uma etapa, o projeto seguinte fica mais difícil, não impossível. O Projeto 4 sem o 3, por exemplo, funciona, mas a imagem some quando a página recarrega. A ordem existe para que cada mudança no código seja pequena e explicável.

## Como organizar o repositório

Você tem duas boas opções:

| Estratégia | Como fica | Quando escolher |
|---|---|---|
| Um repositório com tags | Um único app; cada projeto termina numa tag (`v1-streaming`, `v2-rag`, …) e num pull request | Quando o app é um só e você quer mostrar a evolução do código |
| Monorepo | Pastas como `apps/web` e `packages/rag`, com o README apontando para cada parte | Quando você separou back-end, front-end ou bibliotecas reaproveitáveis |

A opção com tags é a mais simples e conta melhor a história: quem quiser ver só o RAG faz checkout da `v2-rag`, e os pull requests mostram exatamente o que mudou em cada etapa. Escreva PRs com descrição de verdade: recrutadores técnicos leem.

## README em inglês

O README é a vitrine. Escreva em inglês, porque amplia quem pode avaliar o projeto, e siga esta estrutura:

1. Uma frase sobre o produto e o GIF logo abaixo.
2. Um parágrafo por projeto, cada um com o problema, a decisão técnica principal e a tag correspondente. Exemplo para o Projeto 2: "Answers questions about an uploaded PDF and cites the exact passage. Chunks and embeddings live in Postgres with pgvector, and the app refuses to answer when no passage is relevant."
3. Um diagrama de arquitetura simples.
4. Como rodar localmente, com o `.env.example`.
5. Limitações conhecidas e próximos passos. Admitir limites passa maturidade.

## O GIF ou vídeo de 30 segundos

Ninguém vai clonar o seu repositório só para testar. Grave um vídeo curto que passe pelos cinco fluxos, uns 6 segundos cada: a resposta aparecendo em streaming; um PDF enviado e a resposta com o trecho citado; a página recarregada e a conversa retomada; uma imagem anexada; uma pergunta sobre algo de hoje com o aviso de busca e o link da fonte. Comece já na ação.

<Callout type="tip" title="Deploy é opcional, custo não">
Se publicar o app, coloque login, um limite de uso por usuário e um teto de gasto no painel do provedor. Um link aberto para um chat com busca e visão pode gerar uma conta alta em poucas horas. Se não quiser esse risco, o vídeo resolve.
</Callout>

## Checklist de publicação

- [ ] Repositório público com nome claro e descrição de uma linha
- [ ] README em inglês com um parágrafo por projeto e o GIF ou vídeo no topo
- [ ] Tags ou pull requests marcando o fim de cada etapa
- [ ] `.env.example` com os nomes das variáveis e nenhuma chave de API no histórico do Git
- [ ] Defesas mínimas documentadas: validação de upload, limite de uso, prompt injection
- [ ] Deploy (opcional) com limite de uso e teto de gasto
- [ ] Post no LinkedIn com o vídeo, 3 a 5 linhas sobre o que você aprendeu e o link do repositório

## Como contar essa trilha na entrevista

A pergunta "me fala de um projeto seu" é a sua chance. Não descreva as telas; conte decisões. Uma boa estrutura é escolher um momento de cada etapa e explicar o trade-off: por que pgvector em vez de um banco vetorial à parte, como você limitou o contexto das conversas longas, onde guardou as imagens, por que o loop do agente tem um limite de passos.

Prepare-se para os follow-ups. Se falar de RAG, vão perguntar sobre chunking e o que acontece quando a busca não acha nada. Se falar do agente, vão perguntar sobre prompt injection e custo. Os capítulos abaixo preparam essas respostas, e o [framework de entrevista de GenAI System Design](/learn/genai-system-design/framework-de-entrevista) ajuda a transformar o seu projeto num desenho de sistema em escala.

Para a parte comportamental, este é o candidato natural para [O projeto de que mais se orgulha](/learn/behavioral/projeto-mais-orgulhoso): situação (queria aprender IA aplicada de verdade), ação (cinco etapas incrementais), resultado (um produto funcionando e o que você aprendeu com cada decisão).
