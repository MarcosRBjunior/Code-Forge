**Em uma frase:** um app em que o usuário envia vídeos direto para um object storage, vê a miniatura gerada e assiste num player, numa galeria paginada.

**Nível:** intermediário · **Tempo:** 1 a 2 semanas · **Pré-requisito:** já ter feito um app com login e banco de dados

## O que você vai construir

Uma galeria em que a pessoa escolhe um arquivo de vídeo, acompanha uma barra de progresso do envio e, minutos depois, vê o vídeo listado com miniatura, título e duração. Ao clicar, ele toca num player na própria página.

O ponto central do projeto é o caminho do arquivo: ele **não passa pelo seu servidor**. O servidor só autoriza o envio, gerando uma URL pré-assinada de curta duração, e o navegador manda os bytes direto para o storage. É assim que aplicações reais lidam com arquivos grandes sem estourar memória, timeout e banda do back-end.

## MVP

- [ ] Rota que valida o pedido e devolve uma URL pré-assinada de upload
- [ ] Upload pelo navegador direto para o storage, com barra de progresso
- [ ] Limites de tipo e tamanho validados no servidor, não só no formulário
- [ ] Miniatura gerada a partir do vídeo
- [ ] Listagem paginada e página com player
- [ ] Deploy e README com GIF do envio até a reprodução

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Front-end | Next.js | React + Vite |
| Back-end | Route handlers do Next.js | Express ou FastAPI |
| Storage | Bucket compatível com S3 | Azure Blob Storage ou Google Cloud Storage |
| Miniatura | FFmpeg num job separado | Captura de quadro no navegador com `canvas` |
| Banco | PostgreSQL | SQLite |

Credenciais do storage ficam só no servidor, em variáveis de ambiente, com um `.env.example` no repositório. O bucket não precisa (nem deve) ser público para escrita.

## Fora do escopo

Transcodificação em várias resoluções, streaming adaptativo (HLS ou DASH), comentários, curtidas e recomendação. Isso é assunto do projeto de streaming da Fase 3.

## Etapas

1. **Modele o vídeo como um registro com estado.** Antes de gerar a URL, crie no banco um registro com status `pendente`, dono, nome original e chave do objeto. O estado deixa claro o que já chegou e o que ficou pela metade.
2. **Gere a URL pré-assinada com regras.** A rota confere se o usuário está logado, se o tipo declarado é de vídeo e se o tamanho está dentro do limite. A URL expira em poucos minutos e aponta para uma chave que **você** escolhe (um id aleatório), nunca para o nome que o cliente mandou.
3. **Envie do navegador.** Use `XMLHttpRequest` ou uma biblioteca de upload para ter evento de progresso. Ao terminar, chame uma rota de confirmação.
4. **Confirme no servidor.** Não confie no "terminei" do cliente: consulte os metadados do objeto no storage, confira tamanho e tipo reais e só então mude o status para `processando`. Arquivo fora da regra é apagado.
5. **Gere a miniatura.** Um job extrai um quadro do vídeo e a duração, salva a imagem no storage e muda o status para `pronto`. Separar isso da requisição evita que o usuário fique esperando.
6. **Liste e reproduza.** Pagine por cursor (o id ou a data do último item) em vez de `OFFSET` grande, e sirva o vídeo com uma URL de leitura também pré-assinada, se o conteúdo for privado.

A extração da miniatura com FFmpeg é uma linha:

```bash
ffmpeg -ss 00:00:02 -i entrada.mp4 -frames:v 1 -vf scale=480:-1 miniatura.jpg
```

<Callout type="warning" title="O cliente pode mentir">
Tipo e tamanho enviados pelo navegador são só declarações. Valide na geração da URL, use as condições do próprio storage para limitar o tamanho quando o provedor permitir e confira de novo depois do upload. Vídeos enviados por usuários também só devem ser exibidos para quem tem permissão.
</Callout>

## Extras para se destacar

- Upload multipart para arquivos grandes, com retomada após falha de rede.
- Limpeza automática de uploads que ficaram `pendente` por mais de um dia.
- Prévia animada ao passar o mouse, com alguns quadros extraídos.
- Cota de armazenamento por usuário.
