**Em uma frase:** um SaaS em que a pessoa cria conta, envia uma imagem, aplica transformações com IA (como restaurar a foto ou remover o fundo) e paga por créditos para continuar usando.

**Nível:** intermediário · **Duração do vídeo:** cerca de 4h40 · **Canal:** JavaScript Mastery · **Publicado em:** fevereiro de 2024

## Assista

[Build and Deploy a Full Stack AI SaaS Platform with Next js, TypeScript, Stripe](https://www.youtube.com/watch?v=Ahwoks_dawU)

O tutorial constrói o Imaginify, um app com as três peças que quase todo SaaS tem: autenticação, um recurso que custa dinheiro para rodar e uma forma de cobrar por ele. Serve para quem já fez um CRUD em React ou Next.js e quer ver como login, webhooks e pagamento se encaixam num produto só. O canal oferece um kit com o código e os assets do projeto (jsm.dev/imaginify-kit); o repositório é a melhor fonte para saber as versões exatas usadas na gravação.

## O que você vai construir

Pela descrição oficial e pelo que o projeto mostra, o app tem:

- Cadastro e login com Clerk, com o usuário copiado para o banco do app por webhook.
- Upload de imagens para o Cloudinary, usando o pacote `next-cloudinary`.
- Transformações com IA do Cloudinary. A lista provável inclui restauração de imagem, remoção de fundo, preenchimento generativo (aumentar a imagem inventando as bordas), remoção de objetos e recoloração de objetos.
- Sistema de créditos: cada transformação consome créditos, e a pessoa compra pacotes de créditos com o Stripe.
- Galeria das imagens transformadas, com página de detalhe, edição e exclusão.
- Perfil com o saldo de créditos e deploy do app.

O banco de dados é, muito provavelmente, MongoDB com Mongoose. Confira no repositório antes de planejar sua versão.

| Camada | No vídeo | Em 2026 |
|---|---|---|
| Framework | Next.js 14 com App Router | Next.js 16. Desde o 15, `params`, `searchParams`, `cookies()` e `headers()` são assíncronos; no 16, o arquivo `middleware.ts` passou a se chamar `proxy.ts` |
| UI | React 18, Tailwind CSS 3 e, provavelmente, shadcn/ui | React 19, Tailwind 4 (configuração no CSS com `@theme`, sem `tailwind.config.js` obrigatório), shadcn/ui atual |
| Autenticação | Clerk | Clerk com `@clerk/nextjs` recente: `clerkMiddleware` no lugar do antigo `authMiddleware`, e `auth()` assíncrono |
| Imagens e IA | Cloudinary com `next-cloudinary` | Mesmo serviço; alguns recursos de IA podem exigir add-on ativado na conta e gastam créditos de transformação do plano |
| Banco | MongoDB (Atlas) com Mongoose (provável) | Mesmo, ou PostgreSQL com Prisma ou Drizzle se quiser praticar SQL |
| Pagamentos | Stripe Checkout com webhook | Mesmo; a API do Stripe é versionada, então fixe a versão no cliente |
| Deploy | Vercel | Vercel ou qualquer hospedagem Node |

<Callout type="warning" title="O que mudou desde a gravação">
- **Clerk mudou o middleware.** Se o vídeo usar `authMiddleware` com `publicRoutes`, saiba que ele foi removido nas versões novas do `@clerk/nextjs`. Hoje você usa `clerkMiddleware` e marca as rotas protegidas com `createRouteMatcher`. A rota do webhook continua precisando ficar pública.
- **Next.js 15 e 16 mudaram APIs de página.** Em páginas como `/transformations/[id]`, `params` agora é uma Promise e precisa de `await`. Copiar o código do vídeo numa versão nova gera erro de tipo ou aviso em tempo de execução.
- **Tailwind 4 mudou a configuração.** Cores e fontes que o vídeo coloca no `tailwind.config.ts` vão para o CSS, dentro de `@theme`. O plugin `tailwindcss-animate` foi substituído por `tw-animate-css` nos projetos novos do shadcn/ui.
- **Painéis dos serviços mudaram de cara.** Os caminhos no dashboard do Clerk, do Cloudinary e do Stripe não são mais os da gravação. Procure pelo nome da configuração, não pela posição do botão.

Duas formas de seguir: clonar o repositório oficial e instalar exatamente as versões do `package.json` dele (o vídeo funciona do jeito que está e você atualiza depois, numa branch própria), ou começar com as versões novas já sabendo destas diferenças. A primeira é mais tranquila para iniciante; a segunda ensina mais, porque você vai ler documentação.
</Callout>

## Roteiro de estudo

O vídeo tem várias horas. Não assista tudo de uma vez nem copie no automático: divida em etapas, pause antes de cada parte e tente escrever o código sozinho primeiro. Os blocos abaixo seguem a ordem natural do projeto; os nomes exatos dos capítulos do vídeo podem ser outros.

### 1. Projeto, layout e design

**Construa:** o projeto Next.js, a estrutura de pastas, o layout com barra lateral e navegação móvel, os componentes de UI base.

**Conceito:** grupos de rotas do App Router, como `(auth)` e `(root)`, permitem layouts diferentes para telas de login e para o app sem mudar a URL.

**Pergunte-se:** qual parte deste layout é Server Component e qual precisa ser Client Component? Por quê?

### 2. Autenticação e sincronização de usuários

**Construa:** login e cadastro com Clerk, proteção das rotas e o webhook que cria, atualiza e apaga o usuário no seu banco.

**Conceito:** o Clerk é a fonte da verdade da identidade, mas o seu app precisa de dados próprios (créditos, plano). O webhook mantém as duas bases em sincronia. A assinatura do webhook (o Clerk usa Svix) prova que a chamada veio mesmo do Clerk.

**Pergunte-se:** o que acontece se o webhook de criação falhar e o usuário já estiver logado? Como o app se comporta sem o registro no banco?

### 3. Banco de dados e modelos

**Construa:** a conexão com o banco (provavelmente MongoDB com Mongoose) e os modelos de usuário, imagem e transação.

**Conceito:** em ambiente serverless, cada invocação pode abrir uma conexão nova. Por isso é comum guardar a conexão em cache numa variável global.

**Pergunte-se:** quais campos precisam de índice? Que consulta a galeria faz com mais frequência?

### 4. Upload e transformações com IA

**Construa:** o formulário de transformação, o upload para o Cloudinary e a aplicação de cada tipo de transformação, com pré-visualização do antes e depois.

**Conceito:** no Cloudinary, a transformação é descrita na URL da imagem. A imagem original fica guardada e a versão transformada é gerada sob demanda e cacheada.

**Pergunte-se:** se a transformação é só uma URL, o que impede alguém de montar URLs de transformação à mão e gastar a sua cota? Procure por "strict transformations" na documentação.

### 5. Créditos e pagamentos

**Construa:** a página de compra de créditos, a sessão do Stripe Checkout e o webhook que registra a transação e soma os créditos.

**Conceito:** o pagamento só está confirmado quando o Stripe avisa o seu servidor pelo webhook. O redirecionamento de volta para a página de sucesso não prova nada, porque qualquer pessoa pode abrir essa URL.

**Pergunte-se:** se o Stripe reenviar o mesmo evento duas vezes, a pessoa ganha créditos em dobro? Como impedir?

### 6. Galeria, perfil e deploy

**Construa:** a lista paginada de imagens com busca, a página de detalhe, o perfil com saldo e o deploy com todas as variáveis de ambiente.

**Conceito:** variáveis com prefixo `NEXT_PUBLIC_` vão para o navegador. Todo o resto fica só no servidor.

**Pergunte-se:** quais das suas variáveis de ambiente seriam um desastre se vazassem? Alguma delas tem o prefixo público por engano?

## Torne o projeto seu

Esta é a parte que decide se o projeto vira portfólio ou fica sendo "mais um Imaginify". Avaliador que conhece o canal reconhece o layout, o nome e a lista de transformações na hora. O que ele procura é sinal de decisão própria: um problema que o tutorial não resolve, resolvido por você, e explicado no README.

**Nome, identidade e nicho.** Troque nome, logo, cores e textos. Melhor ainda: escolha um público. Um editor de fotos de produto para lojinhas online, uma ferramenta de restaurar fotos de família, um gerador de banners para criadores. O nicho justifica as features que você vai adicionar e dá uma história para contar na entrevista.

**Uma feature que o vídeo não tem.** Escolha uma ou duas, não todas:

- **Processamento em lote:** a pessoa envia 20 fotos de produto e remove o fundo de todas, com uma fila e o progresso de cada item na tela.
- **Histórico de versões:** cada imagem guarda a sequência de transformações aplicadas, com desfazer e comparação lado a lado.
- **Planos por assinatura:** além de pacotes avulsos, um plano mensal com créditos que renovam, usando assinaturas do Stripe e o portal do cliente.
- **Extrato de créditos:** uma tela com cada entrada e saída (compra, uso, estorno), como um extrato bancário. Isso obriga você a modelar os créditos como um livro-razão, não como um número solto.
- **Compartilhamento público:** um link para mostrar a imagem final, com expiração e sem expor a original.
- **Exportação em formatos e tamanhos prontos:** presets para marketplace, Instagram, capa de vídeo.

**Créditos à prova de corrida.** Desconte crédito no servidor, numa operação atômica que só subtrai se houver saldo (no MongoDB, um `updateOne` com filtro `credits >= custo` e `$inc` negativo; no SQL, um `UPDATE ... WHERE credits >= custo`). Nunca leia o saldo, compare em JavaScript e depois grave. Veja também onde o vídeo desconta o crédito: se o desconto é uma chamada separada que o navegador dispara depois da transformação, alguém pode transformar sem pagar. Explique no README como você fechou essa brecha.

**Webhooks idempotentes.** Guarde o id do evento ou da sessão de checkout com índice único e ignore repetidos. Responda 2xx rápido e faça o trabalho pesado depois, se precisar. Valide a assinatura com o corpo bruto da requisição, não com o JSON já convertido.

**Preço decidido no servidor.** O navegador só diz qual pacote quer. Valor e quantidade de créditos saem de uma tabela no servidor (ou de preços cadastrados no Stripe), nunca do corpo da requisição.

**Autorização em toda ação.** Toda Server Action e rota que lê, edita ou apaga uma imagem precisa conferir que a imagem pertence ao usuário logado. Esconder o botão na UI não protege nada.

**Validação e limites.** Valide entradas com Zod (tipo e tamanho do arquivo, campos do formulário, prompt do preenchimento generativo). Defina um limite de uploads por usuário e por minuto para conter abuso.

**Tratamento de erros.** O Cloudinary pode demorar ou falhar numa transformação de IA. Mostre estado de carregamento, mensagem clara de erro e devolva o crédito se a transformação falhar.

**Testes.** No mínimo: teste unitário da regra de créditos (saldo insuficiente, desconto concorrente), teste do webhook do Stripe com evento repetido e um teste de ponta a ponta com Playwright do fluxo login, upload e transformação. Rode tudo no CI.

**Acessibilidade.** Texto alternativo nas imagens (dá até para pedir à pessoa uma descrição no upload), foco visível, comparador de antes e depois operável por teclado, contraste conferido.

**README com decisões.** Diagrama do fluxo de pagamento (checkout, webhook, crédito), por que você escolheu esse banco, como o desconto de crédito é atômico, o que acontece em cada falha e o que ficaria diferente em escala. Diga de onde partiu: "baseado no tutorial X, com estas mudanças". Esconder isso não engana ninguém e transparência conta a favor.

## Armadilhas comuns

- **Webhook local que nunca chega.** Clerk e Stripe não alcançam `localhost`. Use `stripe listen --forward-to localhost:3000/api/webhooks/stripe` para o Stripe e um túnel (ngrok ou similar) para o Clerk, e lembre que o segredo de assinatura do túnel local é diferente do de produção.
- **Rota de webhook bloqueada pelo middleware.** Se a proteção de rotas do Clerk cobrir `/api/webhooks`, o Clerk e o Stripe recebem redirecionamento para o login e o webhook falha em silêncio. Deixe essas rotas públicas e confie na verificação da assinatura.
- **Assinatura do Stripe inválida.** Acontece quando o corpo é lido como JSON antes da verificação. Use `await req.text()` e passe esse texto para `stripe.webhooks.constructEvent`.
- **Variáveis de ambiente esquecidas no deploy.** São muitas chaves (Clerk, Cloudinary, Stripe, banco, segredos dos webhooks). Mantenha um `.env.example` completo e confira a lista no painel da hospedagem antes do primeiro deploy.
- **Cota gratuita do Cloudinary.** Transformações com IA consomem bem mais créditos que um redimensionamento comum. Testar repetidamente pode esgotar o plano gratuito no meio do desenvolvimento. Teste com imagens pequenas.
- **Banco que recusa conexão em produção.** No MongoDB Atlas, a lista de IPs permitidos precisa aceitar a hospedagem. Em serverless o IP muda, então configure conforme a documentação da sua plataforma.
