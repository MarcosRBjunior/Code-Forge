**Em uma frase:** uma loja on-line com catálogo, carrinho, checkout pago em modo de teste e controle de estoque que nunca vende o que não tem.

**Nível:** avançado · **Tempo:** 4 a 6 semanas · **Pré-requisito:** autenticação de usuários e uma API com banco relacional

## O que você vai construir

Todo mundo já fez uma "lojinha" com lista de produtos e botão de comprar. O que separa este projeto dos outros é o que acontece por trás do botão: duas pessoas tentando comprar a última unidade ao mesmo tempo, o provedor de pagamento avisando por webhook (às vezes duas vezes), o pedido que precisa mudar de estado de forma consistente.

Você vai construir uma loja de um vendedor só, com produtos de exemplo inventados por você, e focar nos fluxos em que dinheiro e estoque precisam bater.

## MVP

- [ ] Catálogo com listagem paginada, página de produto e busca por nome
- [ ] Carrinho persistido no banco para usuário logado
- [ ] Checkout com provedor de pagamento em **modo de teste** (cartões de teste do próprio provedor)
- [ ] Webhook de pagamento verificado por assinatura e idempotente
- [ ] Reserva de estoque sem vender acima do disponível, provada por um teste concorrente
- [ ] Pedidos com estados (criado, pago, enviado, cancelado) e histórico para o cliente
- [ ] Deploy público e README com o diagrama do fluxo de checkout

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Front-end e API | Next.js | React + API em Go ou Spring Boot |
| Banco | PostgreSQL | MySQL |
| Pagamento | Stripe em modo de teste | Mercado Pago em sandbox |
| Imagens | Object storage com URLs públicas | Pasta estática no próprio app |

## Fora do escopo

Marketplace com vários vendedores, cálculo real de frete, nota fiscal, cupons complexos, recomendações e painel administrativo completo. Um formulário simples para cadastrar produtos já serve. E nunca, nem por um minuto, processe pagamentos reais: o projeto roda só com chaves de teste.

## Etapas

1. **Modele os dados.** `products`, `inventory` (com `quantity`), `carts`, `orders` e `order_items`. Grave no item o preço do momento da compra; o preço do produto pode mudar depois.
2. **Preço vem do servidor.** O cliente manda só ids e quantidades. O total é recalculado no back-end a partir do banco. Nunca confie em preço, desconto ou total que venha do navegador.
3. **Reserve o estoque de forma atômica.** No checkout, desconte o estoque numa única instrução condicional dentro de uma transação. Se nenhuma linha for afetada, não há unidades suficientes.

```sql
UPDATE inventory
SET quantity = quantity - $2
WHERE product_id = $1 AND quantity >= $2;
-- 0 linhas afetadas = sem estoque: aborte a transação
```

4. **Crie a sessão de pagamento.** Gere o pedido como `criado`, com uma chave de idempotência, e só então chame o provedor. Se o usuário clicar duas vezes, a mesma chave evita duas cobranças.
5. **Trate o webhook com cuidado.** Verifique a assinatura com o segredo do webhook, registre o id do evento numa tabela com restrição `UNIQUE` e só então mude o pedido para `pago`. Se o mesmo evento chegar de novo, a inserção falha e você responde `200` sem fazer nada.
6. **Libere reservas abandonadas.** Um job periódico cancela pedidos que ficaram `criado` por mais de 30 minutos e devolve o estoque. Sem isso, carrinhos esquecidos "comem" o inventário.
7. **Teste a corrida.** Escreva um teste que dispara 50 compras simultâneas para um produto com 10 unidades e confere que exatamente 10 pedidos foram aceitos. Coloque esse resultado no README.

<Callout type="warning" title="Segredos e modo de teste">
Chave secreta do provedor e segredo do webhook ficam em variáveis de ambiente, fora do Git. Publique só um `.env.example` e deixe claro no README que a loja aceita apenas cartões de teste.
</Callout>

## Extras para se destacar

- Padrão outbox: o e-mail de confirmação sai de uma tabela de eventos gravada na mesma transação do pedido.
- Cache do catálogo com invalidação quando o produto muda.
- Painel com vendas por dia usando funções de agregação.
- Testes de ponta a ponta do checkout com o modo de teste do provedor.

## O que este projeto mostra no portfólio

"Eu sei lidar com dinheiro e concorrência: meu checkout não vende estoque que não existe, não cobra duas vezes e processa webhooks repetidos sem efeito colateral."
