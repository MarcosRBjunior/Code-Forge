**Em uma frase:** uma wiki colaborativa sobre algo de que você gosta (uma série, um jogo, uma banda), com páginas em Markdown, histórico de edições e busca.

**Nível:** iniciante · **Tempo:** 1 a 2 semanas · **Pré-requisito:** saber fazer um formulário que salva dados num banco

## O que você vai construir

Um site em que qualquer pessoa logada cria e edita páginas sobre o seu tema favorito: personagens, episódios, fases, discos. Cada página tem um título, um endereço amigável (`/wiki/capitao-nemo`) e um corpo em Markdown. Toda edição gera uma nova versão, e dá para ver quem mudou o quê e voltar a uma versão anterior.

O tema ser algo de que você gosta não é detalhe: você vai preencher o site com conteúdo de verdade, e um projeto com dados reais fica muito melhor na demonstração do que um cheio de "lorem ipsum". Escreva os textos você mesmo e use imagens próprias ou com licença que permita reuso (Creative Commons, domínio público), citando a fonte.

## MVP

- [ ] Criar, editar e ver páginas com corpo em Markdown
- [ ] Endereço amigável (slug) gerado a partir do título
- [ ] Histórico de versões de cada página, com autor e data
- [ ] Restaurar uma versão antiga
- [ ] Busca por título e conteúdo
- [ ] Deploy gratuito e README com prints da página e do histórico

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Front-end e back-end | Next.js | Django ou Rails |
| Banco | Postgres (plano gratuito de um provedor gerenciado) | SQLite no começo |
| Markdown | `react-markdown` ou `markdown-it` | Biblioteca equivalente da sua linguagem |
| Deploy | Vercel, Render ou Fly.io | Qualquer plano gratuito |

## Fora do escopo

Editor visual tipo Word, edição simultânea em tempo real, upload de imagens, comentários e permissões por página. O coração do projeto é o modelo de versões; o resto pode esperar.

## Etapas

1. **Modele as tabelas.** O truque é separar a página da versão: `pages` guarda o slug e aponta para a versão atual; `revisions` guarda cada conteúdo já salvo, com autor e data. Editar nunca sobrescreve, só insere uma nova revisão.
2. **CRUD básico.** Crie as telas de listar, ver, criar e editar. Gere o slug no servidor (minúsculas, sem acento, hífens no lugar de espaços) e garanta no banco que ele é único.
3. **Renderize Markdown com segurança.** Conteúdo vindo de usuário é a porta de entrada clássica de XSS. Use uma biblioteca que não execute HTML bruto, ou passe o resultado por um sanitizador antes de mostrar.
4. **Histórico e restauração.** Liste as revisões da página e permita abrir qualquer uma. Restaurar é só criar uma revisão nova com o conteúdo antigo, assim o histórico continua completo.
5. **Busca.** Comece com `ILIKE` no título e no corpo. Quando funcionar, troque pela busca full-text do Postgres, que entende palavras, ignora acentos (com a extensão `unaccent`) e ordena por relevância.
6. **Deploy e README.** Publique, cadastre umas dez páginas de verdade e explique no README como as versões funcionam.

O modelo de dados cabe em poucas linhas:

```sql
CREATE TABLE pages (
  id SERIAL PRIMARY KEY,
  slug TEXT NOT NULL UNIQUE,
  title TEXT NOT NULL,
  current_revision_id INT
);

CREATE TABLE revisions (
  id SERIAL PRIMARY KEY,
  page_id INT NOT NULL REFERENCES pages(id),
  author_id INT NOT NULL,
  body_md TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

<Callout type="warning" title="Markdown também é entrada de usuário">
Se o seu renderizador aceitar HTML embutido, alguém vai escrever uma tag de script numa página e ela vai rodar no navegador de todo visitante. Desligue HTML bruto ou sanitize a saída, e teste isso de propósito antes do deploy.
</Callout>

## Extras para se destacar

- Diff entre duas versões, destacando o que entrou e o que saiu.
- Links internos no estilo `[[Nome da Página]]`, com página "o que aponta para cá".
- Detecção de conflito: se duas pessoas abriram a mesma versão, a segunda a salvar recebe um aviso em vez de apagar o trabalho da primeira.
