**Em uma frase:** o jogo clássico no navegador, primeiro contra o computador e, como extra, entre duas pessoas em tempo real via WebSocket.

**Nível:** iniciante · **Tempo:** 2 a 4 dias (mais 3 a 5 dias para o multiplayer) · **Pré-requisito:** JavaScript básico e manipulação de estado numa UI

## O que você vai construir

Uma tela com três botões, o resultado de cada rodada e um placar. Você escolhe, o computador escolhe, o app diz quem ganhou. Depois, uma partida "melhor de cinco" com botão de jogar de novo.

É um projeto pequeno de propósito. Ele treina duas coisas que aparecem em qualquer app: separar a regra de negócio da interface e modelar estados (esperando jogada, mostrando resultado, partida encerrada). Na versão multiplayer, aparece um problema novo e bem real: o servidor é o juiz, e o cliente não pode ser confiável.

## MVP

- [ ] Três jogadas e escolha aleatória do computador
- [ ] Função pura que decide o vencedor, com testes
- [ ] Placar e partida "melhor de cinco"
- [ ] Estados claros na UI e botão de recomeçar
- [ ] Layout que funciona no celular
- [ ] Deploy gratuito e README com GIF de uma partida

## Stack sugerida

| Camada | Opção principal | Alternativa |
|---|---|---|
| Front-end | React + Vite | JavaScript puro |
| Testes | Vitest | Jest |
| Multiplayer (extra) | Node com `ws` ou Socket.IO | Serviço gerenciado de tempo real |
| Deploy | Vercel ou Netlify (só front) | Render ou Fly.io (com servidor WebSocket) |

## Fora do escopo

Contas de usuário, ranking global, chat entre jogadores e matchmaking com fila. No multiplayer, basta uma sala por link compartilhado.

## Etapas

1. **Regra como função pura.** Escreva `decide(a, b)` que devolve vitória, derrota ou empate, sem tocar em DOM nem estado. Teste os nove casos. Uma tabela de "quem vence quem" é mais fácil de ler e estender do que uma pilha de `if`.
2. **Estado do jogo.** Represente a partida como um objeto com jogadas, placar e fase. Mudanças passam por uma função `reducer`, o que deixa fácil testar e depurar.
3. **Interface.** Botões grandes, resultado em destaque e uma pequena animação de "pedra, papel, tesoura... já!". Desabilite os botões enquanto o resultado aparece.
4. **Melhor de cinco.** Quando alguém chega a três vitórias, a fase muda para encerrada e aparece o botão de nova partida.
5. **Deploy e README.** Publique o front e grave um GIF de uma partida inteira.
6. **Extra: multiplayer.** Suba um servidor WebSocket com salas. Cada jogador envia só a própria jogada; o servidor espera as duas, chama a mesma função `decide` e manda o resultado para ambos. Se o cliente recebesse a jogada do adversário antes de jogar, bastaria abrir o DevTools para trapacear.

A regra inteira cabe numa tabela:

```typescript
type Move = "pedra" | "papel" | "tesoura";
const beats: Record<Move, Move> = { pedra: "tesoura", papel: "pedra", tesoura: "papel" };

export function decide(a: Move, b: Move): "a" | "b" | "empate" {
  if (a === b) return "empate";
  return beats[a] === b ? "a" : "b";
}
```

<Callout type="note" title="Por que reaproveitar a mesma função">
No multiplayer, a regra roda no servidor. Se ela já é uma função pura e testada, você só importa o mesmo arquivo dos dois lados e não corre o risco de o placar do servidor discordar do que a tela mostra.
</Callout>

## Extras para se destacar

- Variante "pedra, papel, tesoura, lagarto, Spock", só acrescentando linhas na tabela.
- Computador "esperto", que aprende o padrão mais comum das suas jogadas.
- No multiplayer: reconexão quando a rede cai e aviso de que o adversário saiu.

## O que este projeto mostra no portfólio

"Eu separo regra de interface, testo a lógica e, quando há tempo real, deixo o servidor como juiz em vez de confiar no navegador."
