A Quitanda já tem vitrine, carrinho persistido, checkout e painel do lojista conversando com uma API. Mas o jeito de trabalhar ainda é artesanal: o Live Server serve os arquivos, o `json-server` roda com um `npx` que alguém precisa lembrar, a URL da API está fixa no código, ninguém garante que todo mundo do time usa a mesma versão das ferramentas, e cada pessoa formata o código de um jeito. Nenhum projeto profissional de front-end funciona assim, e nenhum projeto React começa sem o que este capítulo monta.

O ambiente moderno de front-end roda sobre o **Node.js** e é comandado pelo **terminal**. É o Node que executa o servidor de desenvolvimento, o build que gera os arquivos de produção, os testes, o linter e o formatador. Aqui você aprende o terminal o suficiente para não ter medo dele, transforma a Quitanda num projeto npm com `package.json`, troca o Live Server pelo **Vite** (com proxy para a API em `/api`) e adiciona **ESLint** e **Prettier**. No fim, o passo para o React no Nível 1 é um comando.

**Você vai aprender:**

- Navegar e manipular arquivos pelo terminal, no Windows, no macOS e no Linux
- O que é o Node.js, como instalá-lo com um gerenciador de versões e rodar scripts com ele
- Criar e entender o `package.json`, scripts npm, dependências e o `package-lock.json`
- Ler versões semânticas e escolher entre `npm install` e `npm ci`
- Usar o Vite como servidor de desenvolvimento e ferramenta de build, com proxy e variáveis de ambiente
- Padronizar o código com ESLint e Prettier

## O terminal sem medo

O terminal é uma interface de texto para o sistema operacional: você digita um comando, ele executa e mostra o resultado. No Windows, use o PowerShell ou o Git Bash; no macOS e no Linux, o terminal padrão (zsh ou bash). O VS Code tem um terminal integrado, aberto com `` Ctrl+` ``, já posicionado na pasta do projeto.

| Tarefa | macOS, Linux, Git Bash | PowerShell |
|---|---|---|
| Onde estou | `pwd` | `pwd` (ou `Get-Location`) |
| Listar arquivos | `ls -la` | `ls` (ou `Get-ChildItem`) |
| Entrar numa pasta | `cd quitanda` | `cd quitanda` |
| Voltar uma pasta | `cd ..` | `cd ..` |
| Criar pasta | `mkdir -p src/ui` | `mkdir src/ui` |
| Criar arquivo vazio | `touch .gitignore` | `New-Item .gitignore` |
| Copiar e mover | `cp a b`, `mv a b` | `cp a b`, `mv a b` |
| Remover pasta | `rm -rf dist` | `Remove-Item -Recurse dist` |
| Ver conteúdo | `cat db.json` | `cat db.json` |
| Limpar a tela | `clear` | `clear` (ou `cls`) |

Hábitos que economizam horas:

- **Tab** completa nomes de arquivos e pastas. Digite `cd qui` e Tab.
- **Seta para cima** traz os comandos anteriores; `Ctrl+R` (bash, zsh) busca no histórico.
- **Ctrl+C** interrompe o processo em execução, como o servidor de desenvolvimento.
- Caminhos com espaço vão entre aspas: `cd "Meus Projetos"`. Melhor ainda: não use espaço em nome de pasta de projeto.
- Leia a mensagem de erro inteira, de baixo para cima. A última linha costuma dizer o que aconteceu; as de cima, onde.

<Callout type="warning" title="Cuidado com comandos de remoção">
`rm -rf` e `Remove-Item -Recurse -Force` apagam sem lixeira e sem confirmação. Confira com `pwd` em que pasta você está antes de rodá-los, e nunca cole no terminal um comando que você não entende, venha ele de um tutorial ou de uma IA.
</Callout>

## Node.js: JavaScript fora do navegador

O **Node.js** é um ambiente que executa JavaScript fora do navegador, usando o mesmo motor V8 do Chrome. Em vez de `document` e `window`, ele oferece acesso a arquivos, rede e processos. Para o front-end, o Node é a plataforma das ferramentas: Vite, ESLint, Prettier, Jest, TypeScript e o próprio npm são programas Node.

### Instalando com um gerenciador de versões

Projetos diferentes exigem versões diferentes do Node. Em vez do instalador do site, use um gerenciador de versões: **nvm** (macOS e Linux), **nvm-windows** ou **fnm** (multiplataforma).

```bash
# terminal (nvm)
nvm install 24        # instala a versão 24, a LTS atual
nvm use 24
node -v               # v24.x.x
npm -v
```

Use sempre uma versão **LTS** (Long Term Support, as de número par), que recebe correções de segurança por cerca de três anos. Registre a versão do projeto num arquivo na raiz:

```text
# .nvmrc
24
```

Com ele, `nvm use` (sem número) ativa a versão certa, e serviços de CI e de hospedagem também costumam lê-lo.

### Rodando um script

O `db.json` está crescendo. Um script Node pode gerar o relatório de estoque baixo que o lojista pediu:

```js
// scripts/estoque-baixo.js
import { readFile } from "node:fs/promises";

const LIMITE = Number(process.argv[2] ?? 5);
const banco = JSON.parse(await readFile("db.json", "utf-8"));

const emFalta = banco.produtos.filter((produto) => produto.estoque <= LIMITE);
console.table(emFalta.map(({ nome, estoque, unidade }) => ({ nome, estoque, unidade })));
```

```bash
# terminal
node scripts/estoque-baixo.js 10
```

O mesmo JavaScript dos capítulos anteriores (`filter`, `map`, desestruturação, `await` no topo) agora roda no terminal. `process.argv` traz os argumentos da linha de comando, e os módulos com prefixo `node:` são os embutidos do Node. Para o `import` funcionar, o projeto precisa declarar `"type": "module"` no `package.json`, que é o próximo passo.

## npm e o package.json

O **npm** vem com o Node e faz duas coisas: instala pacotes do registro público (npmjs.com) e executa os scripts do projeto. O centro de tudo é o `package.json`:

```bash
# terminal, na pasta quitanda
npm init -y
```

Depois de ajustado com os scripts deste capítulo (o bloco `devDependencies` é acrescentado pelo próprio npm a cada instalação):

```json
// package.json
{
  "name": "quitanda",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=24" },
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "api": "json-server db.json",
    "estoque": "node scripts/estoque-baixo.js",
    "lint": "eslint .",
    "format": "prettier . --write"
  }
}
```

| Campo | Para que serve |
|---|---|
| `name`, `version` | Identificação; essenciais só ao publicar um pacote |
| `private: true` | Impede publicar o projeto no npm por acidente |
| `type: "module"` | Arquivos `.js` são módulos ES (`import`/`export`) |
| `engines` | Documenta a versão do Node exigida |
| `scripts` | Comandos do projeto, executados com `npm run nome` |
| `dependencies` | Pacotes que vão para o código de produção (no Nível 1, `react`) |
| `devDependencies` | Ferramentas de desenvolvimento: build, lint, testes |

### Instalando dependências

```bash
# terminal
npm install -D vite eslint @eslint/js globals eslint-config-prettier json-server
npm install -D --save-exact prettier
```

`-D` (ou `--save-dev`) grava em `devDependencies`. A documentação do Prettier recomenda `--save-exact`, porque até versões menores podem mudar a formatação e gerar diffs enormes no time.

A instalação cria duas coisas:

- **`node_modules/`**: os pacotes e as dependências deles, muitas vezes milhares de arquivos. **Nunca** vai para o Git.
- **`package-lock.json`**: a árvore exata de versões instaladas. **Sempre** vai para o Git, porque garante que todos instalem exatamente o mesmo.

```text
# .gitignore
node_modules
dist
.env.local
```

### Versionamento semântico

Versões seguem `MAJOR.MINOR.PATCH`: major quebra compatibilidade, minor adiciona recursos compatíveis, patch corrige bugs.

| Faixa no package.json | Aceita | Exemplo para 7.1.3 |
|---|---|---|
| `^7.1.3` | Minor e patch | Até antes de 8.0.0 |
| `~7.1.3` | Só patch | Até antes de 7.2.0 |
| `7.1.3` | Exatamente essa | Só 7.1.3 |

Abaixo de 1.0.0 a regra muda (o `^0.17.4` só aceita patches, porque em 0.x o minor pode quebrar). Esse assunto volta com força no Nível 3, quando você publicar o design system da Quitanda no npm.

### Comandos do dia a dia

| Comando | O que faz |
|---|---|
| `npm install` (ou `npm i`) | Instala tudo do `package.json`, podendo atualizar o lock dentro das faixas |
| `npm ci` | Apaga `node_modules` e instala exatamente o lock; falha se lock e package.json divergirem. Use em CI |
| `npm run dev` | Executa o script `dev` (`npm start` e `npm test` dispensam o `run`) |
| `npx eslint .` | Executa um binário do projeto (ou baixa um temporário) |
| `npm outdated` | Lista dependências com versões mais novas |
| `npm update` | Atualiza dentro das faixas permitidas |
| `npm uninstall nome` | Remove um pacote |
| `npm audit` | Aponta vulnerabilidades conhecidas nas dependências |

Os scripts npm enxergam os binários de `node_modules/.bin`, por isso `"lint": "eslint ."` funciona sem instalação global. Prefira sempre instalar ferramentas no projeto, não globalmente: a versão fica registrada e todo o time usa a mesma.

pnpm, Yarn e Bun são alternativas ao npm, com o mesmo `package.json` e lockfiles próprios. Um projeto usa um só; misturar gera dois lockfiles e instalações divergentes.

## Vite: o servidor de desenvolvimento

O **Vite** substitui o Live Server com vantagens que mudam o dia a dia:

- Inicia em milissegundos e atualiza o módulo alterado sem recarregar a página (**HMR**, Hot Module Replacement), preservando o estado.
- Permite importar pacotes do npm pelo nome (`import confetti from "canvas-confetti"`), coisa que o navegador sozinho não faz.
- Importa CSS, imagens e JSON a partir do JavaScript.
- Gera o build de produção otimizado: código minificado, arquivos com hash no nome para cache longo, como visto no capítulo sobre a web.
- É a base do projeto React do Nível 1 e de frameworks como o React Router no modo framework.

### A nova estrutura

```text
quitanda/
├── index.html          ponto de entrada (fica na raiz)
├── checkout.html
├── painel.html
├── public/             copiado sem processamento: img/, favicon, robots.txt
├── src/
│   ├── main.js
│   ├── estilos.css
│   ├── servicos/api.js
│   └── ...             os módulos do capítulo de localStorage
├── scripts/
├── db.json
├── vite.config.js
├── eslint.config.js
├── .prettierrc
├── .nvmrc
└── package.json
```

O `index.html` continua sendo o ponto de entrada e aponta para o módulo principal com caminho absoluto a partir da raiz:

```html
<!-- index.html -->
<script type="module" src="/src/main.js"></script>
```

```js
// src/main.js
import "./estilos.css";
import { montarVitrine } from "./ui/vitrine.js";
import { montarResumoCarrinho } from "./ui/resumo-carrinho.js";

montarVitrine();
montarResumoCarrinho();
```

Importar o CSS pelo JavaScript permite que o Vite o processe e o recarregue com HMR. Arquivos em `public/` são servidos na raiz, então `public/img/tomate.jpg` continua acessível como `/img/tomate.jpg`, e o `db.json` não precisa mudar. Páginas HTML extras (checkout, painel) funcionam no `npm run dev`; para o build incluí-las, liste-as nas entradas do build, como mostra o guia "Multi-Page App" da documentação do Vite.

### Proxy para a API e variáveis de ambiente

No capítulo de CRUD, a `URL_BASE` apontava para `http://localhost:3000`. Com um proxy, o front chama `/api/produtos` e o servidor do Vite encaminha para o `json-server`. Mesma origem, sem CORS, e o código fica igual ao de produção, onde a API mora em `/api`:

```js
// vite.config.js
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:3000",
        changeOrigin: true,
        rewrite: (caminho) => caminho.replace(/^\/api/, ""),
      },
    },
  },
});
```

Quando a API ficar em outro endereço, use uma variável de ambiente. O Vite lê arquivos `.env` e expõe ao código **só** as variáveis com prefixo `VITE_`:

```bash
# .env.local
VITE_API_URL=/api
```

```js
// src/servicos/api.js
const URL_BASE = import.meta.env.VITE_API_URL ?? "/api";
```

<Callout type="warning" title="VITE_ é público">
Tudo que começa com `VITE_` é embutido no JavaScript entregue ao navegador e pode ser lido por qualquer pessoa nas DevTools. Nunca coloque chaves secretas, senhas ou tokens de serviço ali. Segredo fica no servidor; é para isso que existe o BFF do Nível 3.
</Callout>

### Rodando tudo

Dois processos, dois terminais (o VS Code divide o terminal com um clique):

```bash
# terminal 1
npm run api      # json-server em localhost:3000

# terminal 2
npm run dev      # Vite em http://localhost:5173
```

Para publicar, `npm run build` gera a pasta `dist/` com HTML, CSS e JS otimizados, e `npm run preview` serve esse build localmente para conferência. A pasta `dist/` é o que vai para a hospedagem estática.

## ESLint: encontrando bugs antes de rodar

O **ESLint** analisa o código sem executá-lo e aponta erros prováveis: variável não usada, variável não declarada (um erro de digitação em `carinho`), comparação com `==`, código inalcançável. A configuração atual é o formato flat, num `eslint.config.js`:

```js
// eslint.config.js
import js from "@eslint/js";
import globals from "globals";
import prettier from "eslint-config-prettier";

export default [
  { ignores: ["dist/"] },
  js.configs.recommended,
  {
    files: ["src/**/*.js"],
    languageOptions: { globals: globals.browser },
  },
  {
    files: ["scripts/**/*.js", "*.config.js"],
    languageOptions: { globals: globals.node },
  },
  {
    rules: {
      eqeqeq: "error",
      "no-unused-vars": ["error", { argsIgnorePattern: "^_" }],
    },
  },
  prettier,
];
```

- `js.configs.recommended` liga as regras que pegam bugs reais.
- `globals.browser` avisa o ESLint que `document` e `localStorage` existem no `src/`; `globals.node`, que `process` existe nos scripts.
- `eslint-config-prettier`, por último, desliga as regras de estilo que brigariam com o Prettier.

```bash
# terminal
npm run lint             # lista os problemas
npx eslint . --fix       # corrige o que for automático
```

Instale a extensão do ESLint no VS Code para ver os avisos sublinhados enquanto digita. No Nível 1, entram os plugins de React e de hooks (`eslint-plugin-react-hooks`), que pegam os erros mais comuns com `useEffect`.

## Prettier: formatação sem discussão

O **Prettier** reescreve o código num estilo único. O time para de discutir aspas e ponto e vírgula na revisão de código, e os diffs mostram só o que mudou de verdade.

```json
// .prettierrc
{
  "printWidth": 100,
  "singleQuote": false,
  "trailingComma": "all"
}
```

```bash
# terminal
npm run format                 # formata o projeto inteiro
npx prettier . --check         # só verifica, útil no CI
```

Com a extensão do Prettier e "Format On Save" no VS Code, você quase nunca precisa rodar o comando. A divisão de trabalho é simples: **Prettier cuida da forma, ESLint cuida da correção**.

| | ESLint | Prettier |
|---|---|---|
| Objetivo | Encontrar erros e más práticas | Padronizar a formatação |
| Exemplo | Variável não usada, `==`, hook chamado dentro de `if` | Aspas, indentação, quebra de linha |
| Corrige sozinho | Parte das regras, com `--fix` | Tudo que formata |
| Configurável | Muito, regra a regra | Pouco, de propósito |

No Nível 2, esses comandos rodam automaticamente em cada pull request no GitHub Actions e num hook de pré-commit.

## O passo para o React

Com Node, npm e Vite dominados, o projeto React do Nível 1 começa com:

```bash
# terminal
npm create vite@latest quitanda-react -- --template react
cd quitanda-react
npm install
npm run dev
```

Você vai reconhecer tudo: `index.html` na raiz, `src/main.jsx`, `package.json` com `dev`, `build`, `lint` e `preview`, um `eslint.config.js` já configurado. A camada `src/servicos/api.js`, o proxy para `/api` e o `db.json` desta Base podem ser levados quase sem mudança.

<Callout type="tip" title="Ferramentas como código">
Tudo que este capítulo configurou está em arquivos versionados: `.nvmrc`, `package.json`, `package-lock.json`, `vite.config.js`, `eslint.config.js`, `.prettierrc`. ## Na entrevista

**Para que o front-end precisa de Node.js se o código roda no navegador?** Porque as ferramentas de desenvolvimento rodam no Node: servidor de desenvolvimento, bundler, transpilação de TypeScript e JSX, testes, lint e formatação. Em frameworks como o Next.js, o Node também executa a renderização no servidor.

**Qual a diferença entre `dependencies` e `devDependencies`?** `dependencies` são usadas pelo código da aplicação em produção (React, por exemplo); `devDependencies` só servem para desenvolver e construir (Vite, ESLint, Jest). Num front-end com bundler, a distinção é sobretudo organizacional, porque o build só inclui o que é importado.

**Para que serve o `package-lock.json`?** Para registrar a árvore exata de versões instaladas, garantindo instalações idênticas entre máquinas e no CI. Deve ser versionado.

**`npm install` ou `npm ci`?** `npm install` no dia a dia, para adicionar ou atualizar pacotes. `npm ci` no CI e em builds: instala exatamente o lock, do zero, e falha se ele estiver inconsistente com o `package.json`.

**O que significa `^1.4.2`?** Qualquer versão compatível a partir de 1.4.2 e antes de 2.0.0, ou seja, aceita minors e patches.

**Qual a diferença entre ESLint e Prettier?** ESLint analisa o código em busca de erros e más práticas; Prettier só formata. Usam-se juntos, com `eslint-config-prettier` desligando as regras de estilo do ESLint.

## Pratique

1. Instale o Node 24 com nvm (ou fnm), crie o `.nvmrc` e confira com `node -v`.
2. Faça todo o caminho de pastas do projeto pelo terminal: crie `src/`, `public/img/` e `scripts/`, mova os arquivos com `mv` e liste o resultado.
3. Rode `npm init -y`, ajuste o `package.json` com `private`, `type` e os scripts do capítulo, instale Vite, json-server, ESLint e Prettier e versione o `package-lock.json` (com `node_modules` no `.gitignore`).
4. Migre a Quitanda para o Vite, configure o proxy de `/api` e troque a `URL_BASE` para `import.meta.env.VITE_API_URL`; confira na aba Network que as chamadas vão para `localhost:5173/api/...`.
5. Escreva o script `estoque-baixo.js` e um segundo script que soma o faturamento dos pedidos entregues no `db.json`.
6. Configure ESLint e Prettier, rode `npm run lint` e corrija tudo o que aparecer; depois rode `npm run build` e abra o `dist/` para ver os nomes com hash.
