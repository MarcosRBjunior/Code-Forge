A Quitanda vai começar como um site estático: um `index.html`, uma folha de estilo e algumas fotos de frutas. Antes de escrever a primeira tag, vale entender o caminho que esse arquivo percorre até a tela de quem quer comprar tomate. Quando a página não carrega, quando a foto aparece quebrada, quando o carrinho funciona no seu computador e falha em produção, a resposta quase sempre está nesse caminho: um nome que não resolve, uma requisição que volta 404, um recurso bloqueado por misturar HTTP com HTTPS, um script que trava a renderização.

Este capítulo monta o modelo mental que o resto da carreira usa: quem é o cliente, quem é o servidor, o que acontece entre digitar `quitanda.dev` e ver a vitrine, e como observar tudo isso na aba Network das DevTools. React, Next.js e qualquer framework rodam em cima dessa mesma base.

**Você vai aprender:**

- O modelo cliente e servidor e o papel do navegador como cliente HTTP
- Como uma URL é formada e como o DNS transforma um nome em endereço IP
- O formato de uma requisição e de uma resposta HTTP, com métodos, cabeçalhos e status codes
- Por que HTTPS é obrigatório e o que o TLS garante
- Como o navegador transforma HTML, CSS e JavaScript em pixels
- A ler a aba Network das DevTools para diagnosticar problemas reais

## Cliente, servidor e o que trafega entre eles

A web é um sistema de **cliente e servidor**. O cliente pede, o servidor responde. Na Quitanda:

- **Cliente:** o navegador da Dona Cida no celular, ou o seu Chrome durante o desenvolvimento. Ele pede documentos e dados e os apresenta.
- **Servidor:** a máquina (ou serviço de hospedagem) que guarda `index.html`, `estilos.css`, as fotos e, mais adiante, a API em `/api/produtos`.

O cliente sempre inicia a conversa. O servidor não manda nada sem ter recebido um pedido, e essa regra só é quebrada mais tarde na carreira, com WebSockets, quando o status do pedido passa a ser empurrado em tempo real.

Cada pedido é independente. O protocolo HTTP é **sem estado**: o servidor não lembra da requisição anterior por conta própria. Quando o site precisa lembrar de algo (quem está logado, o que está no carrinho), alguém precisa guardar essa informação: um cookie, o `localStorage` do navegador ou um banco de dados no servidor. Você vai usar as três opções ao longo da carreira.

| Peça | Papel | Exemplo na Quitanda |
|---|---|---|
| Navegador | Cliente HTTP, interpreta HTML/CSS/JS, desenha a página | Chrome, Firefox, Safari |
| Servidor web | Entrega arquivos estáticos | Servidor que hospeda `index.html` e as fotos |
| API | Entrega dados (JSON) em vez de páginas | `GET /api/produtos` |
| DNS | Traduz nome em endereço IP | `quitanda.dev` para `203.0.113.10` |
| CDN | Cópias dos arquivos perto do usuário | Fotos servidas de um ponto em São Paulo |

## Anatomia de uma URL

Tudo começa com um endereço. Uma URL completa tem partes com funções diferentes:

```text
https://loja.quitanda.dev:443/produtos/tomate.html?categoria=legumes&pagina=2#avaliacoes
\___/   \______________/ \_/\__________________/ \________________________/ \________/
  |            |          |           |                      |                   |
esquema      host       porta     caminho                  query              fragmento
```

- **Esquema** (`https`): o protocolo usado.
- **Host** (`loja.quitanda.dev`): o nome do servidor. `quitanda.dev` é o domínio, `loja` é um subdomínio.
- **Porta** (`443`): normalmente omitida, porque `https` usa 443 e `http` usa 80 por padrão. Em desenvolvimento você verá portas explícitas, como `localhost:5173` (Vite) e `localhost:3000` (json-server).
- **Caminho** (`/produtos/tomate.html`): qual recurso no servidor.
- **Query string** (`?categoria=legumes&pagina=2`): parâmetros chave e valor, separados por `&`. É assim que a vitrine vai filtrar produtos.
- **Fragmento** (`#avaliacoes`): aponta para um trecho da página. Ele **não é enviado ao servidor**; fica só no navegador.

Caracteres especiais precisam ser codificados. Um espaço vira `%20`, um `ç` vira `%C3%A7`. No JavaScript, `encodeURIComponent("maçã verde")` devolve `ma%C3%A7%C3%A3%20verde`, e a classe `URL` monta e lê endereços sem concatenação manual:

```js
// js/exemplos/url.js
const url = new URL("https://loja.quitanda.dev/produtos?categoria=frutas");
url.searchParams.set("busca", "maçã verde");

console.log(url.href);
// https://loja.quitanda.dev/produtos?categoria=frutas&busca=ma%C3%A7%C3%A3+verde
console.log(url.searchParams.get("categoria")); // "frutas"
```

### Caminhos absolutos e relativos

Dentro do HTML, os links para outros arquivos podem ser relativos. Isso importa desde o primeiro dia:

| Escrito no HTML | Página atual | Resolve para |
|---|---|---|
| `estilos.css` | `/produtos/index.html` | `/produtos/estilos.css` |
| `/estilos.css` | `/produtos/index.html` | `/estilos.css` (raiz do site) |
| `../img/tomate.jpg` | `/produtos/index.html` | `/img/tomate.jpg` |
| `https://cdn.exemplo.com/a.js` | qualquer | Endereço completo, outro host |

A maior parte das imagens quebradas em projetos iniciantes vem de um caminho relativo que funcionava numa pasta e deixou de funcionar quando o arquivo mudou de lugar.

## DNS: do nome ao endereço

Computadores se encontram por **endereços IP** (`203.0.113.10` em IPv4, `2001:db8::10` em IPv6). Pessoas lembram de nomes. O **DNS** (Domain Name System) é a lista telefônica distribuída que faz a tradução.

Quando você digita `quitanda.dev`, o navegador procura a resposta em camadas de cache: o próprio navegador, o sistema operacional, o roteador e o **resolvedor** do provedor (ou um público, como `1.1.1.1` e `8.8.8.8`). Se ninguém sabe, o resolvedor pergunta aos servidores raiz, depois aos servidores do `.dev` e por fim ao servidor autoritativo do domínio, que dá a resposta definitiva.

Os registros mais comuns que você vai configurar quando publicar a Quitanda:

| Registro | Para que serve | Exemplo |
|---|---|---|
| `A` | Nome para IPv4 | `quitanda.dev` para `203.0.113.10` |
| `AAAA` | Nome para IPv6 | `quitanda.dev` para `2001:db8::10` |
| `CNAME` | Apelido para outro nome | `www.quitanda.dev` para `quitanda.dev` |
| `MX` | Servidor de e-mail do domínio | `mail.quitanda.dev` |
| `TXT` | Texto livre, usado em verificações | Prova de posse do domínio para a hospedagem |

Cada resposta tem um **TTL** (tempo de vida em segundos) que diz por quanto tempo os caches podem guardá-la. Por isso uma mudança de DNS pode levar de minutos a horas para valer para todo mundo.

Você pode consultar o DNS no terminal:

```bash
# terminal
nslookup example.com
# ou, no Linux e no macOS
dig example.com +short
```

<Callout type="tip" title="localhost também é um nome">
`localhost` resolve para `127.0.0.1` (ou `::1`), o seu próprio computador, sem passar por resolvedor externo. É por isso que o servidor de desenvolvimento funciona sem internet.
</Callout>

## HTTP: o idioma entre cliente e servidor

Com o IP em mãos, o navegador abre uma conexão (TCP, ou QUIC no HTTP/3) e envia uma **requisição HTTP**. Ela tem linha inicial, cabeçalhos e, às vezes, corpo:

```http
GET /api/produtos?categoria=frutas HTTP/1.1
Host: loja.quitanda.dev
Accept: application/json
Accept-Language: pt-BR
User-Agent: Mozilla/5.0 (...)
```

O servidor devolve uma **resposta** com status, cabeçalhos e corpo:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: max-age=60
Content-Length: 182

[{"id":"1","nome":"Tomate italiano","precoEmCentavos":899,"unidade":"kg"}]
```

No HTTP/2 e no HTTP/3 a mensagem é binária e várias requisições compartilham a mesma conexão, mas o significado (método, caminho, cabeçalhos, status, corpo) é o mesmo. As DevTools mostram tudo no formato acima.

### Métodos

| Método | Intenção | Tem corpo? | Idempotente? |
|---|---|---|---|
| `GET` | Ler um recurso | Não | Sim |
| `POST` | Criar algo ou disparar uma ação | Sim | Não |
| `PUT` | Substituir o recurso inteiro | Sim | Sim |
| `PATCH` | Alterar parte do recurso | Sim | Não necessariamente |
| `DELETE` | Remover | Normalmente não | Sim |

Idempotente significa que repetir a requisição deixa o servidor no mesmo estado. Clicar duas vezes em "Finalizar pedido" e disparar dois `POST /api/pedidos` cria dois pedidos; por isso o botão de checkout precisa ser desabilitado durante o envio. Você vai usar todos esses métodos no capítulo de CRUD.

### Status codes

O primeiro dígito diz a família:

| Faixa | Significado | Os que você mais vai ver |
|---|---|---|
| 1xx | Informativo | Raro no dia a dia |
| 2xx | Sucesso | 200 OK, 201 Created, 204 No Content |
| 3xx | Redirecionamento | 301 Moved Permanently, 304 Not Modified |
| 4xx | Erro do cliente | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found |
| 5xx | Erro do servidor | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

Uma regra prática para depurar: 4xx, olhe primeiro o que o front enviou (URL, corpo, token); 5xx, o problema está do outro lado, e o front deve mostrar uma mensagem amigável e permitir tentar de novo.

### Cabeçalhos que importam para o front

- `Content-Type`: o formato do corpo (`text/html`, `application/json`, `image/webp`).
- `Accept`: o formato que o cliente prefere receber.
- `Cache-Control`: por quanto tempo a resposta pode ser reaproveitada (`max-age=31536000, immutable` para arquivos com hash no nome; `no-cache` para o HTML).
- `Set-Cookie` e `Cookie`: como o servidor guarda e recebe um identificador no navegador.
- `Authorization`: credenciais, como `Bearer <token>`, usadas no Nível 2.
- `Access-Control-Allow-Origin`: a resposta do servidor às regras de CORS, que aparecem quando o front em `localhost:5173` chama a API em `localhost:3000`.

## HTTPS e TLS

HTTP puro trafega em texto aberto. Qualquer um no caminho (o Wi-Fi da padaria, um roteador comprometido) consegue ler e alterar a página. **HTTPS** é HTTP dentro de uma conexão **TLS**, que garante três coisas:

- **Confidencialidade:** o conteúdo é cifrado.
- **Integridade:** alterações no caminho são detectadas.
- **Autenticidade:** o certificado prova que o servidor é mesmo `quitanda.dev`, assinado por uma autoridade certificadora em que o navegador confia.

Na prática, em 2026, HTTPS não é opcional: navegadores marcam páginas HTTP como "Não seguro", várias APIs do navegador (geolocalização, service workers, clipboard) só funcionam em contexto seguro, e o HTTP/2 e o HTTP/3 só são usados com TLS nos navegadores. Hospedagens modernas emitem certificados gratuitos automaticamente (Let's Encrypt).

<Callout type="warning" title="Conteúdo misto">
Uma página servida por HTTPS que carrega um script ou uma imagem por `http://` gera conteúdo misto. O navegador bloqueia scripts e tenta atualizar imagens para HTTPS, e a foto do produto simplesmente não aparece. Use sempre URLs `https://` ou caminhos relativos.
</Callout>

## Cache e CDN em uma página

A requisição mais rápida é a que não acontece. O navegador guarda respostas conforme o `Cache-Control`, e a estratégia comum para um site como a Quitanda é:

| Recurso | Cabeçalho típico | Por quê |
|---|---|---|
| `index.html` | `Cache-Control: no-cache` | Sempre revalida, para o usuário ver a versão nova |
| `assets/main-3f9a1c.js` | `Cache-Control: max-age=31536000, immutable` | O hash no nome muda a cada build, então o arquivo antigo pode ficar em cache por um ano |
| Fotos de produto | `Cache-Control: max-age=86400` | Mudam pouco; um dia é razoável |
| `GET /api/produtos` | `max-age` curto ou `no-store` | Preço e estoque mudam |

Com `no-cache`, o navegador revalida enviando `If-None-Match` com a `ETag` que recebeu; se nada mudou, o servidor responde **304 Not Modified** sem corpo. Uma **CDN** coloca cópias dos arquivos estáticos em servidores espalhados pelo mundo, e o DNS aponta o usuário para o mais próximo. O Vite, que você vai conhecer no fim da Base, gera os nomes com hash automaticamente.

## O que acontece quando você digita a URL

Juntando as peças, o fluxo completo para abrir `https://quitanda.dev`:

1. O navegador interpreta a URL e verifica se tem a página em cache.
2. Resolve `quitanda.dev` via DNS e obtém o IP.
3. Abre a conexão (TCP com handshake, ou QUIC) e negocia o TLS, validando o certificado.
4. Envia `GET /` com os cabeçalhos.
5. O servidor (ou a CDN) responde `200` com o HTML.
6. O navegador começa a ler o HTML **antes de ele terminar de chegar** e descobre os recursos: `estilos.css`, fotos, `main.js`. Cada um vira uma nova requisição.
7. Monta a página e a desenha na tela.

## Como o navegador renderiza a página

O passo 7 tem etapas próprias, e entendê-las explica por que a ordem das tags faz diferença:

1. **Parse do HTML para o DOM:** o texto vira uma árvore de nós (`html`, `head`, `body`, `main`, cada `article` de produto).
2. **Parse do CSS para o CSSOM:** as regras de estilo viram outra árvore.
3. **Árvore de renderização:** DOM e CSSOM se combinam; elementos com `display: none` ficam de fora.
4. **Layout (reflow):** o navegador calcula posição e tamanho de cada caixa.
5. **Paint e composição:** desenha os pixels em camadas e as compõe na tela.

Dois detalhes práticos:

- O **CSS bloqueia a renderização**: o navegador não pinta nada até ter o CSS do `head`, para não mostrar a página sem estilo e depois "pular".
- Um `<script>` comum **bloqueia o parse do HTML**: o navegador para, baixa e executa o script, e só então continua. Por isso scripts vão com `defer` (ou `type="module"`, que já é adiado por padrão).

```html
<!-- index.html -->
<head>
  <meta charset="utf-8" />
  <title>Quitanda</title>
  <link rel="stylesheet" href="estilos.css" />
  <!-- defer: baixa em paralelo, executa depois que o HTML foi lido -->
  <script src="js/main.js" defer></script>
</head>
```

Depois da primeira pintura, todo JavaScript que altera o DOM pode disparar novo layout e nova pintura. Essa é a raiz de muitas otimizações que você vai ver no React: evitar trabalho desnecessário no DOM.

## DevTools: a aba Network

Abra a página com `F12` (ou `Ctrl+Shift+I`, `Cmd+Option+I` no macOS) e vá à aba **Network**. Recarregue a página com ela aberta, porque ela só registra o que acontece enquanto está aberta.

Cada linha é uma requisição. As colunas que mais ajudam:

| Coluna | O que mostra | Para que serve |
|---|---|---|
| Name | Arquivo ou rota | Achar a requisição |
| Status | Código HTTP | 404 na foto, 500 na API |
| Type | `document`, `stylesheet`, `script`, `fetch`, `img` | Filtrar por tipo |
| Initiator | Quem disparou | Descobrir qual script fez a chamada |
| Size | Tamanho transferido | `(memory cache)` ou `(disk cache)` indica cache |
| Time e Waterfall | Duração e fases | Ver DNS, conexão, TLS, espera e download |

Clicando numa requisição você vê as abas **Headers** (URL, método, status, cabeçalhos de ida e volta), **Payload** (corpo enviado), **Preview** e **Response** (corpo recebido) e **Timing** (fases detalhadas).

Recursos que você vai usar o tempo todo:

- **Disable cache:** marque enquanto desenvolve, para não ver arquivo velho.
- **Throttling:** simule "Slow 4G" para sentir a Quitanda num celular comum.
- **Filtro Fetch/XHR:** mostra só chamadas de API, útil a partir do capítulo de CRUD.
- **Preserve log:** mantém o histórico ao navegar ou ao enviar formulário.
- **Copy as cURL:** clique direito na requisição para reproduzi-la no terminal.

<Callout type="tip" title="Leia o Waterfall da esquerda para a direita">
Uma barra longa em "Waiting for server response" (TTFB) indica servidor lento. Uma barra longa em "Content Download" indica arquivo grande: provavelmente a foto de 4 MB do maracujá que ninguém comprimiu.
</Callout>

## Na entrevista

**O que acontece quando você digita uma URL e aperta Enter?** O navegador interpreta a URL, resolve o nome via DNS (com cache em várias camadas), abre a conexão e negocia o TLS, envia a requisição HTTP, recebe o HTML e começa o parse, descobrindo CSS, scripts e imagens que viram novas requisições. Monta DOM e CSSOM, calcula o layout e pinta a página.

**Qual a diferença entre HTTP e HTTPS?** HTTPS é HTTP sobre TLS. O TLS cifra o tráfego, garante a integridade e autentica o servidor por um certificado. Sem ele, qualquer intermediário pode ler ou alterar a página.

**Diferença entre 401 e 403?** 401 significa que o cliente não está autenticado (falta credencial ou ela é inválida). 403 significa que está autenticado, mas não tem permissão para aquele recurso.

**Por que colocar `defer` nos scripts?** Um script comum no `head` interrompe o parse do HTML até ser baixado e executado. Com `defer`, o download acontece em paralelo e a execução espera o HTML terminar, mantendo a ordem dos scripts.

**O que é TTL no DNS?** É por quanto tempo uma resposta pode ficar em cache. TTL alto reduz consultas, mas atrasa a propagação de mudanças; antes de migrar a hospedagem, costuma-se baixá-lo.

## Pratique

1. Abra um site de mercado online com a aba Network aberta, recarregue e anote: quantas requisições, quantos MB transferidos, qual a maior imagem e quanto tempo levou o documento principal.
2. Use `nslookup` ou `dig` para descobrir o IP de três domínios e compare as respostas de `www` com as do domínio sem `www`.
3. Com a classe `URL` no console, monte o endereço da busca da Quitanda com `categoria=frutas`, `busca=pêra` e `pagina=3`, e leia de volta cada parâmetro.
4. Ative o throttling "Slow 4G" e "Disable cache" num site qualquer e observe no Waterfall quais recursos atrasam a primeira pintura.
5. Escreva, em uma página de anotações, o fluxo completo de abrir `https://quitanda.dev`, do DNS à pintura, e confira contra o capítulo de redes do CodeForge.
