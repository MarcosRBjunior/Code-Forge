O Nível 2 transformou a SPA do Nível 1 numa aplicação pronta para crescer. A Quitanda ganhou TypeScript com tipos derivados de esquemas Zod, custom hooks e componentes compostos, otimização guiada pelo Profiler, padrões de robustez (error boundaries, retries, optimistic UI, Web Vitals), migração para Next.js 16 com App Router, estratégias de renderização por rota, uma comparação honesta com o React Router no modo framework, autenticação com sessão em cookie, ferramentas de debugging e release, uma arquitetura por funcionalidade, testes com MSW e Playwright e um pipeline que verifica tudo a cada pull request.

Este checkpoint confere se você consegue usar esse conjunto junto, e não apenas capítulo por capítulo. O desafio pede uma fatia vertical da Quitanda em Next.js: do tipo do domínio até o deploy, passando por renderização, autenticação, testes e CI. As perguntas e os quizzes misturam os doze capítulos, como acontece numa entrevista para vaga pleno.

**Neste checkpoint:**

- Revisar os doze capítulos do Nível 2 e o que cada um exige de você
- Conferir, com uma autoavaliação prática, o que você já domina
- Entregar uma fatia completa da Quitanda em Next.js 16 com TypeScript, sessão, testes e CI
- Revisar os conceitos que mais causam bugs e falhas de segurança neste nível

## Desafio prático

Sua tarefa é entregar uma fatia vertical da Quitanda já em Next.js 16 com App Router e TypeScript: o fluxo "ver produto, comprar e acompanhar o pedido", mais a edição de produto pelo lojista. Se você fez o desafio do Nível 1, migre o seu código; se não fez, comece de um projeto Next.js novo apontando para a mesma API.

A meta não é ter muitas telas, e sim que cada camada esteja no lugar certo: tipos na fronteira, renderização escolhida por rota, autorização perto do dado, falhas isoladas e tudo verificado pelo CI.

### Requisitos

1. **Organização por funcionalidade.** Código em `src/features/catalogo`, `carrinho`, `checkout` e `pedidos`, cada uma com um `index.ts` como API pública. `src/app/` só compõe as features. Uma regra `no-restricted-imports` impede importar o interior de outra feature.
2. **Contrato tipado.** Esquemas Zod para `Produto` e `Pedido`, tipos derivados com `z.infer` e validação de toda resposta da API na camada de dados. Nenhum `any` explícito no projeto.
3. **Renderização por rota.** A página de produto sai estática com cache por tag (`produtos` e `produto-id`). A página "Meus pedidos" é dinâmica, depende da sessão e usa `loading.tsx` ou `Suspense` para streaming. Registre a escolha de cada rota numa tabela no README.
4. **Carrinho no cliente.** Um hook `useCarrinho` persistido no `localStorage`, consumido por Client Components pequenos (botão de adicionar, mini carrinho), sem erro de hidratação no primeiro carregamento.
5. **Autenticação.** Login com Better Auth (ou Auth.js) e sessão em cookie `HttpOnly`. O `proxy.ts` redireciona quem não tem cookie em `/pedidos`, `/checkout` e `/painel`, e uma função `exigirUsuario` em arquivo `server-only` faz a verificação de verdade.
6. **Server Actions.** `finalizarPedido` e `salvarProduto` validam com Zod, checam sessão e papel, devolvem erros por campo e invalidam o cache certo. O formulário de produto funciona com `useActionState`.
7. **Robustez.** Error boundary na seção de recomendações da página de produto, os quatro estados (carregando, vazio, erro, sucesso) na lista de pedidos, `error.tsx` e `not-found.tsx` nas rotas de pedido e atualização otimista na troca de status do painel.
8. **Testes.** Jest com `next/jest` e MSW: um teste de hook, um teste de componente assíncrono, um teste de cada Server Action (incluindo usuário sem permissão) e um teste com `jest-axe` no formulário de checkout. Um teste Playwright do fluxo de compra.
9. **Qualidade e entrega.** ESLint 9 com flat config, Prettier, Husky com lint-staged e commitlint, e um workflow do GitHub Actions com formatação, lint, `typecheck`, testes com cobertura, build e e2e. Deploy com preview por pull request.

Um ponto de partida para a camada de acesso a dados com verificação de dono:

```ts
// src/features/pedidos/dados.ts
import "server-only";
import { exigirUsuario } from "@/lib/sessao";
import { listaDePedidosSchema, type Pedido } from "./esquemas";

export async function listarMeusPedidos(): Promise<Pedido[]> {
  const usuario = await exigirUsuario();
  const resposta = await fetch(`${process.env.API_URL}/pedidos?clienteId=${usuario.id}`, {
    headers: { Authorization: `Bearer ${process.env.API_TOKEN}` },
    cache: "no-store",
  });
  if (!resposta.ok) throw new Error(`Falha ao listar pedidos: ${resposta.status}`);
  return listaDePedidosSchema.parse(await resposta.json());
}
```

### Critérios de aceite

- `npx tsc --noEmit`, `npm run lint` e `npm test` passam localmente e no CI; o PR fica bloqueado se qualquer um falhar.
- A saída de `next build` mostra a página de produto como pré-renderizada e "Meus pedidos" como dinâmica, coerente com a tabela do README.
- Editar o preço no painel e salvar mostra o novo valor na página do produto na próxima visita, sem novo deploy.
- Acessar `/pedidos` sem sessão redireciona para `/entrar`. Com sessão de cliente, chamar a Action `salvarProduto` direto (por exemplo, num teste) devolve erro de permissão.
- Trocar o id na URL de um pedido de outro cliente devolve a página 404, não os dados.
- Simular falha na API de recomendações (um handler do MSW com status 500) deixa o restante da página de produto funcionando.
- Recarregar a loja com itens no carrinho não gera aviso de hidratação no console.
- O teste Playwright passa no CI e o relatório do Lighthouse no preview não aponta regressão de acessibilidade.

### Dicas

- Comece pela arquitetura e pelos esquemas: com `features/` e tipos no lugar, o resto encaixa. Revise [arquitetura no front-end](/learn/carreira-react/arquitetura-front-end-decisoes-tecnicas-sustentaveis) e [integrando TypeScript](/learn/carreira-react/react-integrando-typescript).
- `'use client'` contamina para baixo: tudo que o arquivo importa vira código do cliente. Deixe a página como Server Component e marque só os componentes interativos, como em [migrando para Next.js](/learn/carreira-react/react-migrando-componentes-nextjs).
- O carrinho lido do `localStorage` durante a renderização é a causa clássica de erro de hidratação. Leia depois da montagem ou com `useSyncExternalStore` e um snapshot de servidor, como em [debugging e release](/learn/carreira-react/react-debugging-release-nextjs) e no `useLocalStorage` de [composição com custom hooks](/learn/carreira-react/react-padroes-composicao-custom-hooks).
- O proxy não é segurança. Toda Server Action é um endpoint público e precisa verificar sessão e papel por conta própria; veja [técnicas seguras de autenticação](/learn/carreira-react/react-tecnicas-seguras-autenticacao).
- Não teste Server Components assíncronos com `render` do Testing Library como se fossem componentes comuns; teste a função de dados e cubra a página no Playwright. A estratégia está em [testes avançados](/learn/carreira-react/react-testes-avancados-jest-testing-library).
- Não ligue retry automático em mutações. Pedido duplicado é pior que um erro com botão de tentar de novo; veja [aplicações robustas](/learn/carreira-react/react-padroes-otimizacoes-aplicacoes-robustas).

## Revisão rápida

**`z.infer` em vez de interface solta.** Uma interface não existe em tempo de execução: se a API mandar `null`, o tipo mente. O esquema valida a resposta e gera o tipo, e os dois nunca divergem.

**Uniões discriminadas fecham o reducer.** Com `type` literal em cada ação, o `switch` estreita o payload e um `default` com `never` faz o compilador acusar ação esquecida.

```ts
// src/features/carrinho/carrinhoReducer.ts (trecho)
default: {
  const naoTratada: never = acao;
  return naoTratada;
}
```

**Medir antes de memorizar.** `memo`, `useMemo` e `useCallback` têm custo. Use quando o Profiler mostra renderização cara ou quando uma referência estável evita trabalho real. Com o React Compiler ligado, boa parte disso é automática. Para digitação que trava uma lista grande, a ferramenta costuma ser prioridade, não memoização:

```tsx
// src/features/painel/componentes/PedidosFiltrados.tsx (trecho)
const [filtro, setFiltro] = useState("");
const filtroAdiado = useDeferredValue(filtro);
const visiveis = useMemo(() => filtrarPedidos(pedidos, filtroAdiado), [pedidos, filtroAdiado]);
```

**Server Component não tem estado nem efeito.** Hooks como `useState` e manipuladores de evento exigem Client Component. O inverso também vale: um Client Component não importa módulo com `server-only`, segredos ou acesso direto ao banco.

**Rota dinâmica por acidente.** Ler `cookies()`, `headers()` ou `searchParams` torna a rota dinâmica. Se a página de produto lê a sessão para mostrar "Olá, Ana", ela deixa de ser estática; isole esse trecho num componente dentro de `Suspense`.

**Hidratação exige o mesmo primeiro render.** O HTML do servidor e a primeira renderização do cliente precisam bater. Datas formatadas com o fuso do navegador, `Math.random`, `window` e `localStorage` lidos durante a renderização produzem valores diferentes nos dois lados.

```tsx
// src/features/carrinho/componentes/ResumoDoCarrinho.tsx (trecho)
const assinarNada = () => () => {};

// dentro do componente: false no servidor e na hidratação, true depois
const montado = useSyncExternalStore(assinarNada, () => true, () => false);
if (!montado) return <span aria-busy="true">Carregando carrinho…</span>;
```

**`revalidateTag` versus `updateTag`.** `updateTag` expira na hora e serve para quem acabou de editar ver o próprio dado (só dentro de Server Actions). `revalidateTag` marca como velho e regenera em segundo plano para os demais visitantes.

**Proteção em camadas.** Proxy para redirecionar cedo, camada de dados `server-only` para verificar a sessão e consulta filtrada pelo dono contra IDOR. Tirar qualquer uma das duas últimas abre um buraco.

```ts
// src/lib/sessao.ts (trecho)
export async function exigirLojista() {
  const usuario = await exigirUsuario();
  if (usuario.papel !== "lojista") redirect("/");
  return usuario;
}
```

**Error boundary não pega tudo.** Ele captura erros lançados durante a renderização dos filhos. Erros em manipuladores de evento, em código assíncrono fora da renderização e no próprio boundary passam direto. Nesses casos, trate o erro no lugar (estado de erro, toast, `onError` da mutação) ou relance-o durante a renderização para o boundary mais próximo.

**Teste a rede, não o `fetch`.** Com MSW, o teste não quebra se você trocar `fetch` por outra biblioteca, e `onUnhandledRequest: "error"` garante que nenhuma chamada real escape. Cada teste sobrescreve só o handler de que precisa:

```ts
// src/features/pedidos/componentes/AcompanharPedido.test.tsx (trecho)
servidor.use(
  http.get("/api/pedidos/:id", () => HttpResponse.json({ erro: "falhou" }, { status: 500 })),
);
expect(await screen.findByRole("alert")).toHaveTextContent(/não foi possível/i);
```

<Callout type="warning" title="NEXT_PUBLIC_ vai para o navegador">
Toda variável com prefixo `NEXT_PUBLIC_` é embutida no JavaScript público durante o build. Token de API, segredo do Better Auth e credenciais de banco ficam sem prefixo e só são lidos em código de servidor. Se um segredo vazou num bundle publicado, trocar a variável não basta: revogue e gere outro.
</Callout>

## Na entrevista

**Como você tipa a resposta de uma API?** Com um esquema Zod que valida em tempo de execução e um tipo derivado com `z.infer`. Assim o dado que entra na aplicação é conferido na fronteira, e o tipo usado nos componentes é o mesmo que foi validado.

**Qual a diferença entre Server Component e Client Component?** Server Components rodam só no servidor, podem acessar dados diretamente e não enviam seu código ao navegador. Client Components são hidratados no navegador e podem ter estado, efeitos e eventos. A fronteira é o arquivo com `'use client'`.

**Como você escolhe a estratégia de renderização de uma rota?** Pela frequência de mudança do dado, se ele depende do usuário e se precisa estar no HTML para SEO. Produto: estático com revalidação por tag. Pedidos do cliente: dinâmico com streaming. Painel: dinâmico e protegido.

**O proxy do Next.js basta para proteger o painel?** Não. Ele é um filtro otimista que só confere se o cookie existe. A verificação real fica numa camada de dados no servidor, chamada em cada página e em cada Server Action.

**Como você isolaria uma falha numa parte da página?** Com um error boundary em volta da seção, com mensagem e opção de tentar de novo, e com `error.tsx` por rota no App Router. O resto da página continua funcionando.

**Por que MSW em vez de mockar fetch com jest.fn?** Porque ele simula a rede, não a função usada para chamá-la. O teste exercita a camada de serviço de verdade e continua válido se a implementação do cliente HTTP mudar.

**Como seria o pipeline de CI deste projeto?** `npm ci` com cache, checagem de formatação, lint, `typecheck`, testes com cobertura, build e e2e com Playwright, em paralelo quando possível. O deploy de preview sai por PR e a produção sai do merge na branch principal.

**Quando você escolheria React Router no modo framework em vez de Next.js?** Quando a SPA já usa React Router com loaders e actions e o time quer SSR e progressive enhancement sem trocar de roteador, ou quando quer um modelo mais próximo dos fundamentos da web e menos acoplado a uma plataforma.

## Se travou, revise

- Não consegui tipar o reducer, o Context ou um componente genérico sem `any`: [integrando TypeScript](/learn/carreira-react/react-integrando-typescript).
- A lógica do catálogo continua espalhada no componente, ou o seletor de quantidade não aceita valor externo: [composição com custom hooks](/learn/carreira-react/react-padroes-composicao-custom-hooks).
- A tabela de pedidos trava ao digitar e não sei por onde começar a medir: [otimização e desempenho](/learn/carreira-react/react-tecnicas-avancadas-otimizacao-desempenho).
- Uma falha numa seção derruba a página inteira, ou o retry criou pedidos duplicados: [aplicações robustas](/learn/carreira-react/react-padroes-otimizacoes-aplicacoes-robustas).
- Não sei onde colocar `'use client'`, ou os providers quebram no servidor: [migrando para Next.js](/learn/carreira-react/react-migrando-componentes-nextjs).
- A página saiu dinâmica sem eu querer, ou a edição não aparece depois de salvar: [estratégias de renderização](/learn/carreira-react/react-estrategias-renderizacao-nextjs).
- Não entendi a diferença entre `loader` e `clientLoader`, ou quando usar `useFetcher`: [rotas e dados com Remix](/learn/carreira-react/react-rotas-dados-remix).
- Um cliente consegue ver pedido de outro, ou a Action roda sem sessão: [técnicas seguras de autenticação](/learn/carreira-react/react-tecnicas-seguras-autenticacao).
- O console mostra erro de hidratação, ou não sei voltar uma versão quebrada: [debugging e release](/learn/carreira-react/react-debugging-release-nextjs).
- As features importam o interior umas das outras e ninguém percebe: [arquitetura no front-end](/learn/carreira-react/arquitetura-front-end-decisoes-tecnicas-sustentaveis).
- Os testes dependem de `setTimeout` ou quebram quando mudo o cliente HTTP: [testes avançados](/learn/carreira-react/react-testes-avancados-jest-testing-library).
- O CI não bloqueia o PR, ou o ESLint e o Prettier brigam: [qualidade de código e deploy](/learn/carreira-react/react-qualidade-codigo-automacoes-deploy).

<Callout type="tip" title="Registre as decisões">
Escreva dois ou três ADRs curtos durante o desafio: por que a página de produto é estática, por que a sessão fica em cookie, por que a organização é por funcionalidade. No Nível 3 essas decisões serão revisitadas, e numa entrevista elas viram as melhores histórias para contar.
