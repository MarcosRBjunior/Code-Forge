No Nível base, a Quitanda virou um site com HTML, CSS e JavaScript puro: o catálogo era montado com `document.createElement`, o carrinho vivia num array que você precisava lembrar de redesenhar a cada clique e o localStorage guardava tudo entre visitas. Funciona, mas cada nova regra exige mais código de sincronização: mudou a quantidade, atualize o contador do cabeçalho, o subtotal, o botão de finalizar e a mensagem de carrinho vazio. Esquecer uma dessas linhas é o bug mais comum de interfaces feitas à mão.

React troca esse modelo. Em vez de dizer ao navegador **como** alterar a página, você descreve **como a tela deve ficar** para um certo estado, e o React calcula o que mudou. Este capítulo começa a reescrita da Quitanda em React 19 com Vite: projeto novo, primeiros componentes, catálogo a partir de uma lista, carrinho com `useState` e um formulário que usa as Actions do React 19. Ainda é JavaScript; o TypeScript entra no Nível 2.

**Você vai aprender:**

- Criar o projeto da Quitanda com Vite e entender cada arquivo gerado
- Escrever JSX sabendo o que ele vira e onde ele difere do HTML
- Dividir a tela em componentes que recebem props
- Renderizar listas com `key` e conteúdo condicional
- Guardar estado com `useState` e atualizar arrays sem mutação
- Enviar formulários com `<form action>`, `useActionState` e `useFormStatus`

## Criando o projeto com Vite

Vite é a ferramenta de build padrão para aplicações React fora de frameworks: servidor de desenvolvimento com recarga instantânea e build de produção otimizado. Com Node.js 24 LTS instalado:

```bash
npm create vite@latest quitanda-react -- --template react
cd quitanda-react
npm install
npm run dev
```

O servidor sobe em `http://localhost:5173`. A estrutura que importa:

```text
quitanda-react/
  index.html          <- a única página; tem a div#root
  package.json        <- "type": "module", scripts dev/build/preview
  vite.config.js      <- plugin @vitejs/plugin-react
  public/             <- arquivos servidos como estão (fotos dos produtos)
  src/
    main.jsx          <- ponto de entrada: cria a raiz do React
    App.jsx           <- componente raiz
```

```jsx
// src/main.jsx
import { StrictMode } from "react";
import { createRoot } from "react-dom/client";
import App from "./App.jsx";
import "./index.css";

createRoot(document.getElementById("root")).render(
  <StrictMode>
    <App />
  </StrictMode>,
);
```

`createRoot` liga o React a um elemento do DOM, e daí em diante ele é dono de tudo o que está dentro de `div#root`. O `StrictMode` não muda nada em produção; em desenvolvimento ele executa componentes e efeitos duas vezes de propósito para revelar código impuro. Se você vir um `console.log` duplicado, é ele.

`npm run build` gera a pasta `dist/` com HTML, JS e CSS minificados, prontos para qualquer servidor estático. `npm run preview` serve essa pasta localmente para conferir o resultado.

## JSX: HTML dentro do JavaScript, mas não é HTML

JSX é uma extensão de sintaxe. O compilador transforma cada tag numa chamada de função que cria um **elemento React**, um objeto simples que descreve o que deve aparecer:

```jsx
// o que você escreve
const titulo = <h1 className="titulo">Quitanda</h1>;

// o que o compilador gera (runtime automático do React)
import { jsx as _jsx } from "react/jsx-runtime";
const titulo = _jsx("h1", { className: "titulo", children: "Quitanda" });
```

Por isso o JSX segue regras de JavaScript, não de HTML:

| HTML | JSX | Motivo |
|---|---|---|
| `class="x"` | `className="x"` | `class` é palavra reservada |
| `for="email"` | `htmlFor="email"` | `for` é palavra reservada |
| `onclick="..."` | `onClick={funcao}` | eventos em camelCase recebem função |
| `style="color: red"` | `style={{ color: "red" }}` | estilo é objeto, propriedades em camelCase |
| `<img>` | `<img />` | toda tag precisa fechar |
| vários elementos soltos | um elemento raiz ou fragmento `<>...</>` | a função devolve um único valor |

As chaves abrem uma janela para qualquer **expressão** JavaScript: variável, chamada de função, ternário, `map`. Comandos como `if` e `for` não cabem ali, porque não produzem valor.

```jsx
// src/componentes/Cabecalho.jsx
export default function Cabecalho({ quantidadeNoCarrinho }) {
  const saudacao = new Date().getHours() < 12 ? "Bom dia" : "Boa tarde";
  return (
    <header className="cabecalho">
      <h1>Quitanda</h1>
      <p>{saudacao}! Frutas e verduras frescas todo dia.</p>
      <span aria-label="Itens no carrinho">{quantidadeNoCarrinho}</span>
    </header>
  );
}
```

O JSX escapa automaticamente todo texto inserido com chaves. Se o nome de um produto vier da API como `<script>alert(1)</script>`, ele aparece como texto, não é executado. Essa proteção contra XSS só deixa de valer quando você usa `dangerouslySetInnerHTML`, e o nome feio é de propósito.

## Componentes e props

Um componente é uma função com nome em maiúscula que recebe um objeto de **props** e devolve JSX. A maiúscula importa: `<cartao>` é tratado como tag HTML, `<Cartao>` como componente.

Primeiro, um utilitário que a carreira inteira vai reaproveitar. Preços ficam em centavos (inteiros), como no Nível base, para evitar erro de arredondamento com ponto flutuante:

```js
// src/utilidades/formatarPreco.js
const formatador = new Intl.NumberFormat("pt-BR", { style: "currency", currency: "BRL" });

export function formatarPreco(centavos) {
  return formatador.format(centavos / 100);
}
```

```jsx
// src/componentes/CartaoProduto.jsx
import { formatarPreco } from "../utilidades/formatarPreco.js";

export default function CartaoProduto({ produto, onAdicionar }) {
  const esgotado = produto.estoque === 0;
  return (
    <article className="cartao">
      <img src={produto.foto} alt={produto.nome} width="160" height="120" />
      <h2>{produto.nome}</h2>
      <p>
        {formatarPreco(produto.precoEmCentavos)} / {produto.unidade}
      </p>
      <button type="button" disabled={esgotado} onClick={() => onAdicionar(produto)}>
        {esgotado ? "Esgotado" : "Adicionar"}
      </button>
    </article>
  );
}
```

Três regras sobre props:

- **Props são somente leitura.** O componente nunca altera `produto.estoque`. Quem precisa mudar algo recebe uma função por prop (`onAdicionar`) e avisa o componente pai.
- **Desestruture na assinatura** para ver de cara o que o componente usa. Valores padrão entram ali também: `function Selo({ texto = "Novo" })`.
- **`children` é uma prop.** O que você coloca entre a abertura e o fechamento chega como `props.children`, o que permite componentes de layout.

```jsx
// src/componentes/Secao.jsx
export default function Secao({ titulo, children }) {
  return (
    <section>
      <h2>{titulo}</h2>
      {children}
    </section>
  );
}
```

Pense em componentes como funções puras: com as mesmas props e o mesmo estado, devolvem o mesmo JSX, sem efeitos colaterais durante a renderização (nada de `fetch` ou de alterar variáveis de fora dentro do corpo). O `StrictMode` existe para pegar quem quebra essa regra.

## Listas e keys

Os produtos ficam, por enquanto, num arquivo local. No capítulo de APIs eles passam a vir do `json-server` do Nível base. Os ids são strings porque é assim que o `json-server` os devolve.

```js
// src/dados/produtos.js
export const produtos = [
  { id: "1", nome: "Banana prata", precoEmCentavos: 699, unidade: "kg", categoria: "frutas", estoque: 40, foto: "/fotos/banana.jpg" },
  { id: "2", nome: "Alface crespa", precoEmCentavos: 349, unidade: "un", categoria: "verduras", estoque: 25, foto: "/fotos/alface.jpg" },
  { id: "3", nome: "Tomate italiano", precoEmCentavos: 899, unidade: "kg", categoria: "legumes", estoque: 0, foto: "/fotos/tomate.jpg" },
];
```

```jsx
// src/componentes/ListaDeProdutos.jsx
import CartaoProduto from "./CartaoProduto.jsx";

export default function ListaDeProdutos({ produtos, onAdicionar }) {
  if (produtos.length === 0) {
    return <p>Nenhum produto encontrado.</p>;
  }
  return (
    <ul className="grade">
      {produtos.map((produto) => (
        <li key={produto.id}>
          <CartaoProduto produto={produto} onAdicionar={onAdicionar} />
        </li>
      ))}
    </ul>
  );
}
```

A `key` diz ao React qual item é qual entre uma renderização e outra. Com ela, quando um produto entra no meio da lista, o React move os elementos existentes em vez de reaproveitar o elemento errado. Use um identificador estável que venha dos dados. O índice do array só serve para listas que nunca são reordenadas, filtradas ou editadas; caso contrário, o estado interno de um item (um campo digitado, uma animação) passa a pertencer ao vizinho. A `key` fica no elemento mais externo devolvido pelo `map` e não chega ao componente como prop.

<Callout type="warning" title="Key gerada na hora não é key">
`key={Math.random()}` ou `key={crypto.randomUUID()}` dentro do `map` cria uma chave nova a cada renderização. O React conclui que todos os itens são novos, desmonta e monta a lista inteira, e qualquer estado local dos itens se perde. Gere o id quando o dado é criado, não quando é desenhado.
</Callout>

## Renderização condicional

Como o JSX aceita expressões, a condição é JavaScript comum:

```jsx
// trechos de componentes
{esgotado ? <span className="selo">Esgotado</span> : <span>Em estoque</span>}

{itens.length > 0 && <p>{itens.length} itens no carrinho</p>}

{produto.categoria === "frutas" ? <SeloFruta /> : null}
```

Cuidado com o `&&` quando o lado esquerdo é número: `{itens.length && <p>...</p>}` mostra um `0` solto na tela quando a lista está vazia, porque `0` é um valor renderizável. Compare explicitamente (`itens.length > 0`). Para lógica com mais de dois ramos, calcule antes do `return` com `if` e guarde o JSX numa variável, ou use retornos antecipados como em `ListaDeProdutos`.

## useState: memória do componente

Uma variável comum dentro do componente é recriada a cada renderização e, se você alterá-la, o React nem fica sabendo. Estado é a memória que sobrevive entre renderizações e que, quando muda, agenda uma nova renderização.

```jsx
// src/App.jsx
import { useState } from "react";
import Cabecalho from "./componentes/Cabecalho.jsx";
import ListaDeProdutos from "./componentes/ListaDeProdutos.jsx";
import Carrinho from "./componentes/Carrinho.jsx";
import { produtos } from "./dados/produtos.js";

export default function App() {
  const [itens, setItens] = useState([]); // [{ produto, quantidade }]
  const [busca, setBusca] = useState("");

  function adicionar(produto) {
    setItens((atuais) => {
      const existente = atuais.find((item) => item.produto.id === produto.id);
      if (existente) {
        return atuais.map((item) =>
          item.produto.id === produto.id ? { ...item, quantidade: item.quantidade + 1 } : item,
        );
      }
      return [...atuais, { produto, quantidade: 1 }];
    });
  }

  function remover(id) {
    setItens((atuais) => atuais.filter((item) => item.produto.id !== id));
  }

  const visiveis = produtos.filter((p) => p.nome.toLowerCase().includes(busca.toLowerCase()));
  const totalDeItens = itens.reduce((soma, item) => soma + item.quantidade, 0);

  return (
    <>
      <Cabecalho quantidadeNoCarrinho={totalDeItens} />
      <main>
        <label htmlFor="busca">Buscar</label>
        <input id="busca" value={busca} onChange={(e) => setBusca(e.target.value)} />
        <ListaDeProdutos produtos={visiveis} onAdicionar={adicionar} />
        <Carrinho itens={itens} onRemover={remover} />
      </main>
    </>
  );
}
```

Pontos que derrubam iniciantes:

- **Imutabilidade.** `itens.push(novo)` seguido de `setItens(itens)` não renderiza de novo: o array é o mesmo objeto, e o React compara referências com `Object.is`. Crie sempre um array ou objeto novo com spread, `map` e `filter`.
- **O valor não muda na linha seguinte.** Depois de `setBusca("maçã")`, a variável `busca` continua com o valor antigo até a próxima renderização. O estado é um retrato daquela renderização.
- **Atualização funcional.** `setItens((atuais) => ...)` recebe o valor mais recente, o que é correto quando o novo estado depende do anterior, inclusive com vários cliques rápidos.
- **Não guarde o que dá para calcular.** `visiveis` e `totalDeItens` são derivados de `busca` e `itens`. Colocá-los em estado criaria duas fontes da verdade que podem divergir.

O campo de busca é um **input controlado**: o valor vem do estado (`value={busca}`) e cada digitação passa por `onChange`. O React é a fonte da verdade, o que permite validar ou formatar enquanto o usuário digita.

```jsx
// src/componentes/Carrinho.jsx
import { formatarPreco } from "../utilidades/formatarPreco.js";

export default function Carrinho({ itens, onRemover }) {
  const total = itens.reduce((soma, i) => soma + i.produto.precoEmCentavos * i.quantidade, 0);
  if (itens.length === 0) return <aside>Seu carrinho está vazio.</aside>;
  return (
    <aside aria-label="Carrinho">
      <ul>
        {itens.map(({ produto, quantidade }) => (
          <li key={produto.id}>
            {quantidade} x {produto.nome}
            <button type="button" onClick={() => onRemover(produto.id)}>Remover</button>
          </li>
        ))}
      </ul>
      <p>Total: {formatarPreco(total)}</p>
    </aside>
  );
}
```

## Formulários com Actions no React 19

Antes do React 19, todo formulário seguia o mesmo roteiro: `onSubmit`, `event.preventDefault()`, um estado para cada campo, outro para "enviando" e outro para o erro. O React 19 introduziu **Actions**: funções, inclusive assíncronas, passadas direto para a prop `action` do `<form>`. O React chama a função com um `FormData`, gerencia a transição e, ao terminar com sucesso, limpa os campos não controlados.

A Quitanda tem um formulário "avise-me quando chegar" para produtos esgotados:

```jsx
// src/componentes/AviseMe.jsx
import { useActionState } from "react";
import { useFormStatus } from "react-dom";

async function cadastrarAviso(estadoAnterior, formData) {
  const email = formData.get("email");
  if (!String(email).includes("@")) {
    return { ok: false, mensagem: "Informe um e-mail válido." };
  }
  const resposta = await fetch("/api/avisos", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ email, produtoId: formData.get("produtoId") }),
  });
  if (!resposta.ok) return { ok: false, mensagem: "Não foi possível cadastrar. Tente de novo." };
  return { ok: true, mensagem: "Pronto! Avisaremos por e-mail." };
}

function BotaoEnviar() {
  const { pending } = useFormStatus();
  return (
    <button type="submit" disabled={pending}>
      {pending ? "Enviando..." : "Avise-me"}
    </button>
  );
}

export default function AviseMe({ produtoId }) {
  const [estado, acaoDoFormulario, isPending] = useActionState(cadastrarAviso, null);
  return (
    <form action={acaoDoFormulario} aria-busy={isPending}>
      <input type="hidden" name="produtoId" value={produtoId} />
      <label htmlFor={`email-${produtoId}`}>Seu e-mail</label>
      <input id={`email-${produtoId}`} name="email" type="email" required />
      <BotaoEnviar />
      {estado && <p role={estado.ok ? "status" : "alert"}>{estado.mensagem}</p>}
    </form>
  );
}
```

O caminho `/api` chega ao `json-server` por um proxy do Vite, configurado no capítulo sobre APIs HTTP (o trecho de `vite.config.js` aparece lá). Até você configurá-lo, o envio cai no ramo de erro, o que já serve para ver a mensagem de falha.

Como as peças se encaixam:

- **`useActionState(funcao, estadoInicial)`** devolve o estado atual, uma action para passar ao formulário e um booleano `isPending`. A função recebe o **estado anterior** como primeiro argumento e o `FormData` como segundo; o que ela retorna vira o novo estado. É o lugar natural para mensagens de erro e sucesso.
- **`useFormStatus()`**, importado de `react-dom`, lê o status do formulário **pai**. Por isso ele fica num componente filho (`BotaoEnviar`): chamado no mesmo componente que renderiza o `<form>`, ele não enxerga esse formulário.
- **Campos não controlados.** Os inputs têm `name`, e não `value` com estado. O `FormData` coleta tudo no envio, sem um `useState` por campo.
- **Submissões em sequência.** Se o usuário enviar duas vezes, as chamadas da action ficam em fila, e cada uma recebe o estado produzido pela anterior.

| Abordagem | Quando usar |
|---|---|
| `onSubmit` com `preventDefault` e estados manuais | Código legado ou quando você precisa de controle total do evento |
| Input controlado com `useState` | Validação ou formatação a cada tecla, campos que dependem uns dos outros |
| `<form action>` com `useActionState` | Envio com estado de pendente, erro e sucesso, com pouco código |
| React Hook Form com Zod | Formulários grandes com muitas regras (capítulo de formulários deste nível) |

<Callout type="tip" title="Action não é Server Action">
Aqui a action roda no navegador e chama a API com `fetch`. Em frameworks como o Next.js, a mesma prop `action` pode receber uma Server Action, uma função que executa no servidor. O modelo mental é o mesmo, e você o reencontra no Nível 2. O hook `useOptimistic`, que mostra o resultado esperado antes de a resposta chegar, também se apoia em Actions e aparece quando o carrinho conversar com a API.
</Callout>

## Organizando a pasta src

Para o resto do Nível 1, a Quitanda segue esta convenção:

```text
src/
  componentes/   <- CartaoProduto, ListaDeProdutos, Carrinho, Cabecalho, AviseMe
  dados/         <- dados locais (sai quando a API entrar)
  utilidades/    <- funções puras como formatarPreco
  App.jsx
  main.jsx
```

Um componente por arquivo, com o mesmo nome do arquivo, exportado como `default`. Funções utilitárias usam exportações nomeadas. Os capítulos seguintes acrescentam `estado/`, `paginas/` e `servicos/`.

## Na entrevista

**O que é JSX e o que ele vira?** Uma sintaxe que o compilador transforma em chamadas `jsx()` do runtime do React, que produzem objetos chamados elementos. Esses objetos descrevem a interface; o React compara a descrição nova com a anterior e aplica no DOM só a diferença.

**Por que a key é importante numa lista?** Ela identifica cada item entre renderizações. Com uma key estável, o React preserva o estado e o DOM do item certo quando a lista é reordenada, filtrada ou recebe inserções. Índice como key quebra isso em listas que mudam de ordem.

**Por que mutar o estado não renderiza a tela de novo?** O React decide se precisa renderizar comparando a referência do novo valor com a anterior. Mutar o array mantém a mesma referência, então o React considera que nada mudou. Atualizações criam objetos novos.

**Qual a diferença entre props e estado?** Props vêm do componente pai e são somente leitura. Estado pertence ao componente, sobrevive entre renderizações e só muda pela função de atualização, o que dispara uma nova renderização.

**O que o useActionState resolve?** Junta num só lugar o envio do formulário, o estado de pendente e o resultado (erro ou sucesso). A action recebe o estado anterior e o `FormData` e devolve o próximo estado, sem `preventDefault` nem um estado por campo.

## Pratique

1. Crie o projeto `quitanda-react` com Vite, apague o conteúdo de exemplo e monte `Cabecalho`, `CartaoProduto` e `ListaDeProdutos` com os produtos do arquivo local, usando `formatarPreco`.
2. Adicione um filtro por categoria com botões (Todas, Frutas, Verduras, Legumes). Guarde só a categoria escolhida em estado e derive a lista filtrada.
3. Faça o `Carrinho` mostrar botões de mais e menos por item. Ao chegar a zero, o item sai da lista. Não permita passar do estoque.
4. Mostre o selo "Últimas unidades" quando o estoque estiver entre 1 e 5 e "Esgotado" quando for zero, sem mostrar um `0` solto na tela.
5. Implemente o `AviseMe` para os produtos esgotados. Simule a API com `json-server` e confira, no painel de rede do navegador, o corpo do `POST` e a mensagem exibida em caso de erro 500.
6. Abra as ferramentas de desenvolvimento, troque a key dos itens do carrinho pelo índice e descreva o que acontece com um campo de observação digitado dentro de um item quando outro item é removido.
