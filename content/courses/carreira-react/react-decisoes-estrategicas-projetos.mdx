A Quitanda chegou ao fim do Nível 2 em TypeScript e Next.js 16, com App Router, autenticação, testes e deploy automatizado. Agora o negócio quer crescer: um aplicativo para os entregadores, um painel do lojista mais rico, acompanhamento de pedido em tempo real e, talvez, um segundo time trabalhando no catálogo. Cada uma dessas frentes abre perguntas que não se resolvem com mais um hook: manter o Next.js ou separar o painel numa SPA com Vite? Construir a busca ou contratar um serviço? Criar um BFF? Quem decide, com base em quê, e como o time vai lembrar daqui a um ano por que a escolha foi essa?

No nível sênior, a parte difícil deixa de ser escrever o código e passa a ser escolher qual código vale a pena escrever. Este capítulo abre o Nível 3 com o método: enquadrar a decisão, comparar opções com critérios explícitos, registrar o raciocínio num ADR e comunicar o resultado para o time e para quem paga a conta. Os capítulos seguintes (SOLID, arquitetura limpa, BFF, Socket.io, estado, performance e New Relic) são, cada um, uma decisão desse tipo aplicada à Quitanda.

**Você vai aprender:**

- Separar decisões reversíveis das irreversíveis e ajustar o esforço de análise a cada uma
- Escolher entre SPA com Vite e um framework como Next.js ou React Router 7 no modo framework
- Avaliar construir versus comprar com custo total, risco e foco no diferencial do negócio
- Montar uma matriz de decisão ponderada sem transformá-la em teatro
- Escrever um ADR curto e útil e manter o histórico de decisões no repositório
- Comunicar a decisão ao time técnico e ao negócio, cada um na sua língua

## O que torna uma decisão estratégica

Nem toda escolha merece reunião. Trocar `date-fns` por `Intl.DateTimeFormat` num componente é barato de desfazer. Mudar o framework da aplicação, o formato de autenticação ou o lugar onde ficam as regras de preço é caro. A pergunta que separa os dois casos é: **quanto custa mudar de ideia depois?**

| Tipo | Exemplos na Quitanda | Esforço adequado |
|---|---|---|
| Reversível (porta de mão dupla) | Biblioteca de ícones, formato de um componente, nome de uma pasta | Decida rápido, quem está no código decide, revise se incomodar |
| Cara de reverter | Gerenciador de estado global, biblioteca de formulários, estrutura de pastas do monorepo | Compare 2 ou 3 opções, faça uma prova de conceito, registre num ADR |
| Praticamente irreversível | Framework de renderização, provedor de autenticação, modelo de dados do pedido, contrato público de API | Envolva o time e o negócio, prototipe, defina critérios de saída, ADR obrigatório |

O custo de mudar cresce com três fatores: **quanto código depende da escolha**, **quantos times ou sistemas dependem dela** e **quanto dado já foi gravado no formato dela**. Um componente de botão usado em 3 telas é fácil de trocar. Um formato de pedido gravado em 200 mil linhas do banco e consumido por um app móvel publicado nas lojas não é.

<Callout type="tip" title="Decida devagar o que é caro, e rápido o resto">
Um erro comum de quem acabou de virar sênior é tratar toda decisão como irreversível: o time passa uma semana comparando bibliotecas de toast. O erro oposto é escolher o framework da aplicação numa conversa de corredor. Classifique primeiro, depois escolha o tamanho da análise.
</Callout>

## SPA ou framework

Essa é a decisão mais citada em entrevistas de front-end, e a resposta honesta é "depende de onde a página precisa ser renderizada e de quem precisa encontrá-la".

| Critério | SPA com Vite + React Router | Next.js 16 (App Router) | React Router 7 modo framework |
|---|---|---|---|
| Renderização | No navegador; o servidor entrega um HTML vazio e o JS | Server Components, SSR, estático e streaming por rota | SSR e pré-renderização com loaders e actions |
| SEO e primeira pintura | Fraco sem trabalho extra | Forte | Forte |
| Infraestrutura | Arquivos estáticos em qualquer CDN | Precisa de servidor Node (ou plataforma que o rode) para os recursos dinâmicos | Precisa de servidor para SSR; pode gerar estático |
| Curva para o time | Baixa, só React | Média: Server vs Client Components, cache, Server Actions | Média: loaders, actions, convenções de rota |
| Bom para | Painéis logados, ferramentas internas, apps que ficam abertos o dia todo | Sites públicos com catálogo, SEO, conteúdo e partes dinâmicas | Apps com muita navegação e formulários, migração de Remix |

O Remix v2 se fundiu ao React Router 7: o que era Remix virou o "modo framework" do React Router, e quem usa o React Router como biblioteca numa SPA pode adotar loaders e SSR aos poucos.

Aplicado à Quitanda:

- **Loja pública (catálogo, produto, checkout):** fica no Next.js. Precisa de SEO para "tomate orgânico entrega", de LCP baixo no celular e de renderizar o catálogo no servidor.
- **Painel do lojista:** é logado, não precisa de SEO, fica aberto a manhã inteira e tem muita interação. Uma SPA com Vite seria suficiente e mais simples de hospedar. Mas o time já domina Next.js, a autenticação já está pronta lá e o painel compartilha componentes com a loja. Aqui a decisão não é óbvia, e é exatamente o tipo de caso em que vale escrever um ADR.
- **App do entregador:** um PWA ou React Native. Fora do escopo deste capítulo, mas entra na mesma matriz.

## Construir ou comprar

Toda funcionalidade que não é o diferencial do negócio é candidata a ser comprada (ou adotada como open source). O diferencial da Quitanda é a curadoria dos produtos, o frete rápido e a experiência de compra, não o sistema de envio de e-mails.

Perguntas para cada candidato:

1. **Isso é diferencial competitivo?** Se não for, a tendência é comprar.
2. **Qual o custo total em 2 anos?** Construir inclui manutenção, plantão, atualizações de segurança e a pessoa que vai embora levando o conhecimento. Comprar inclui licença por uso, integração e o risco de o preço subir.
3. **Qual o custo de sair?** Um serviço que guarda seus dados num formato proprietário prende mais do que uma API que você pode trocar atrás de um adaptador.
4. **O que acontece se o fornecedor cair?** Pagamento fora do ar é venda perdida; busca fora do ar pode cair para uma busca simples no banco.

| Funcionalidade | Decisão na Quitanda | Motivo |
|---|---|---|
| Pagamento | Comprar (gateway) | Regulação, antifraude e PCI não são o negócio |
| Autenticação | Comprar ou usar pronto (Supabase Auth, Auth.js) | Segurança difícil de acertar sozinho |
| Busca no catálogo | Começar no Postgres com índice de texto; reavaliar com 10 mil produtos | Catálogo pequeno, custo de serviço não se paga ainda |
| Design system | Construir sobre primitivos acessíveis prontos | A identidade visual é diferencial; acessibilidade de baixo nível não |
| Monitoramento | Comprar (New Relic) | Construir observabilidade é um produto inteiro |
| Cálculo de frete por bairro | Construir | É regra do negócio e muda toda semana |

O padrão que protege as duas escolhas é o mesmo: **isolar o fornecedor atrás de uma interface sua**. Se o checkout chama `servicoDePagamento.cobrar(pedido)` e não o SDK do gateway direto em 14 componentes, trocar de gateway custa um adaptador. O capítulo de arquitetura limpa com Supabase faz isso na prática.

## Matriz de decisão ponderada

Quando há mais de duas opções e vários critérios, a matriz organiza a conversa. O exemplo compara três abordagens para o painel do lojista.

| Critério | Peso | Next.js (mesmo app) | SPA Vite separada | React Router 7 framework |
|---|---|---|---|---|
| Reaproveitar autenticação e componentes | 5 | 5 | 3 | 3 |
| Simplicidade de hospedagem | 2 | 3 | 5 | 3 |
| Conhecimento atual do time | 4 | 5 | 4 | 2 |
| Isolamento de deploy (painel não derruba a loja) | 3 | 2 | 5 | 4 |
| Performance percebida no uso diário | 3 | 4 | 4 | 4 |
| **Total ponderado** | | **72** | **68** | **54** |

Cada nota vai de 1 a 5, multiplicada pelo peso. O total é soma de nota vezes peso: para o Next.js, 5×5 + 3×2 + 5×4 + 2×3 + 4×3 = 72.

Três regras para a matriz não virar teatro:

- **Defina pesos antes de dar notas.** Se os pesos vêm depois, alguém ajusta até a opção preferida ganhar.
- **Desconfie de totais próximos.** 72 contra 68 é empate técnico; a decisão vem de outro lugar (risco, prazo, preferência do time). Diga isso no ADR.
- **Registre o critério que quase mudou o resultado.** Se o isolamento de deploy tivesse peso 5, a SPA ganharia. Esse é o gatilho para revisar a decisão quando o painel crescer.

Para comparações pequenas, um script ajuda a testar a sensibilidade dos pesos:

```ts
// scripts/matriz-de-decisao.ts
type Opcao = { nome: string; notas: Record<string, number> };

const pesos: Record<string, number> = {
  reaproveitamento: 5,
  hospedagem: 2,
  conhecimento: 4,
  isolamento: 3,
  performance: 3,
};

const opcoes: Opcao[] = [
  { nome: "Next.js", notas: { reaproveitamento: 5, hospedagem: 3, conhecimento: 5, isolamento: 2, performance: 4 } },
  { nome: "SPA Vite", notas: { reaproveitamento: 3, hospedagem: 5, conhecimento: 4, isolamento: 5, performance: 4 } },
  { nome: "RR7 framework", notas: { reaproveitamento: 3, hospedagem: 3, conhecimento: 2, isolamento: 4, performance: 4 } },
];

function total(opcao: Opcao, p = pesos) {
  return Object.entries(p).reduce((soma, [criterio, peso]) => soma + peso * (opcao.notas[criterio] ?? 0), 0);
}

for (const opcao of opcoes) console.log(opcao.nome, total(opcao));

// Sensibilidade: e se isolamento pesasse 5?
const pesosAlternativos = { ...pesos, isolamento: 5 };
for (const opcao of opcoes) console.log("isolamento=5", opcao.nome, total(opcao, pesosAlternativos));
```

## Trade-offs: nomeie o que você está abrindo mão

Toda decisão troca uma coisa por outra. Escrever explicitamente o lado ruim da opção escolhida faz duas coisas: mostra que você considerou o risco e cria o gatilho para revisitar.

| Decisão | Ganho | Custo aceito |
|---|---|---|
| Painel no mesmo app Next.js | Reaproveita auth e componentes, um só deploy | Um bug no painel pode quebrar o build da loja; bundle compartilhado precisa de cuidado |
| BFF em NestJS | Front recebe dados prontos, segredos ficam no servidor | Mais um serviço para operar, monitorar e versionar |
| Socket.io para status do pedido | Atualização instantânea | Conexões persistentes, escala horizontal exige adapter Redis |
| TanStack Query para estado de servidor | Cache, revalidação e retentativa prontos | Mais um conceito para o time aprender |

Uma forma útil de pensar é **custo de atraso versus custo de erro**. Se decidir errado custa pouco e esperar custa caro (o concorrente lança antes), decida rápido. Se decidir errado custa muito (dados de pedidos no formato errado), invista em protótipo.

## ADR: o registro da decisão

Um ADR (Architecture Decision Record) é um arquivo Markdown curto, versionado junto com o código, que registra **uma** decisão: o contexto, o que foi decidido e as consequências. O formato popularizado por Michael Nygard cabe numa tela.

```md
<!-- docs/adr/0007-painel-do-lojista-no-app-next.md -->
# 7. Painel do lojista no mesmo app Next.js

- Status: aceito
- Data: 2026-11-10
- Decisores: tech lead do front, PM do painel, dev do catálogo

## Contexto
O painel do lojista vai ganhar gestão de pedidos e métricas. Avaliamos manter
no app Next.js atual, criar uma SPA com Vite ou usar React Router 7 no modo
framework. O time tem 4 pessoas, todas com experiência em Next.js.

## Decisão
Manter o painel em `app/(painel)/` no mesmo app Next.js, com layout próprio,
proteção por papel `lojista` no proxy e carregamento sob demanda dos gráficos.

## Alternativas consideradas
- SPA Vite: hospedagem mais simples e deploy isolado, mas duplica autenticação.
- React Router 7: bom modelo de dados, mas o time não conhece.
Matriz em docs/adr/anexos/0007-matriz.md (72 x 68 x 54, empate técnico entre as duas primeiras).

## Consequências
- Positivas: um login, componentes compartilhados, um pipeline.
- Negativas: falha no build do painel bloqueia deploy da loja.
- Gatilho de revisão: se o painel passar de 30% do bundle total ou ganhar um
  time próprio, reabrir esta decisão (candidato: micro frontend).
```

Boas práticas:

- **Numere e nunca apague.** Uma decisão revertida ganha um novo ADR com status "substitui o 0007", e o antigo vira "substituído pelo 0012". O histórico é o valor.
- **Escreva antes de implementar**, como proposta no pull request. A revisão do ADR é a discussão.
- **Mantenha curto.** Se passou de duas páginas, provavelmente são duas decisões.
- **Guarde no repositório** (`docs/adr/`), não numa wiki que ninguém atualiza. Quem lê o código encontra o porquê ao lado.

<Callout type="warning" title="ADR não é documentação de tudo">
Não escreva ADR para escolher o nome de uma variável. Se o time escreve um ADR por semana para decisões reversíveis, ninguém lê os importantes. Reserve para o que é caro de mudar ou para o que vai gerar a pergunta "por que fizeram assim?".
</Callout>

## Prova de conceito com prazo e critério de sucesso

Quando a matriz empata ou um critério depende de algo que ninguém sabe medir de cabeça, a saída é uma prova de conceito (PoC). Ela só funciona com três limites definidos antes de começar:

- **Pergunta única.** "O Supabase Realtime entrega a mudança de status em menos de 1 segundo com 500 clientes conectados?" e não "vamos testar o Supabase".
- **Prazo fechado.** Dois a cinco dias. PoC sem prazo vira projeto.
- **Critério de sucesso e de descarte.** O que precisa acontecer para seguir, e o que faz a ideia ser abandonada.

```md
<!-- docs/poc/realtime-status-pedido.md -->
# PoC: status do pedido em tempo real

Pergunta: Socket.io no BFF ou Supabase Realtime entregam a mudança de status
ao cliente em menos de 1 s (p95) com 500 conexões simultâneas?

Prazo: 3 dias (até 2026-11-20).

Sucesso: p95 menor que 1 s, reconexão automática após queda de rede,
custo mensal estimado abaixo de R$ 300.

Descarte: se exigir mais de um serviço novo para operar além do BFF.

Resultado: (preencher) -> vira o contexto do ADR 0009.
```

O código da PoC é descartável por definição. Ele vive numa branch ou pasta separada e não vai para produção sem ser reescrito com testes. O que fica é o número medido e o ADR que ele alimenta.

## Quem decide

Decisões travam quando ninguém sabe quem tem a palavra final. Um modelo simples, inspirado no DACI, resolve a maior parte dos casos:

| Papel | Quem, no exemplo do painel | O que faz |
|---|---|---|
| Responsável por conduzir | Tech lead do front | Monta as opções, a matriz e o ADR, marca a conversa |
| Aprovador | Head de engenharia | Dá a palavra final se não houver consenso |
| Contribuintes | Devs do catálogo e do painel, PM | Trazem critérios, riscos e dados |
| Informados | Time de back-end, suporte | Ficam sabendo da decisão e do impacto |

"Discordo, mas me comprometo" é uma postura saudável depois da decisão: a discordância fica registrada no ADR e o time executa a escolha sem sabotagem. Se os fatos mudarem, o gatilho de revisão reabre a conversa.

## Comunicar a decisão

A mesma decisão é contada de jeitos diferentes para públicos diferentes.

**Para o time técnico**, o ADR basta, mais uma conversa de 15 minutos para dúvidas. Mostre o código que muda, os padrões novos e o que deixa de ser aceito em revisão.

**Para o negócio** (PM, diretoria, dono da Quitanda), troque critérios técnicos por impacto:

| Em vez de | Diga |
|---|---|
| "Vamos adotar Socket.io com adapter Redis" | "O cliente vai ver o pedido mudar de status na hora, sem recarregar. Custo: cerca de 2 semanas e um servidor a mais por mês" |
| "Precisamos de um BFF" | "Hoje o app faz 6 chamadas para mostrar um pedido; com isso, faz 1. A tela abre em menos da metade do tempo no 4G" |
| "Débito técnico no checkout" | "Cada mudança no checkout leva 3 dias e quebrou duas vezes no último mês. Uma semana de arrumação devolve esse tempo em dois meses" |

Três hábitos que fazem diferença:

- **Traga opções, não só a sua resposta.** "Podemos fazer A em 2 semanas ou B em 5; recomendo A porque..." dá ao negócio o poder de decidir prazo e escopo.
- **Quantifique o que for possível**, mesmo em ordem de grandeza: horas, reais, segundos de carregamento, pedidos por minuto.
- **Diga o que você não sabe.** "Não sabemos se o Supabase Realtime aguenta 5 mil lojistas conectados; vamos medir na prova de conceito" é mais confiável que uma certeza inventada.

## O custo de mudar depois

Algumas escolhas cobram juros. O padrão para reduzir o custo futuro é sempre o mesmo: **fronteiras**.

- **Fornecedores atrás de interfaces suas** (repositórios, serviços, adaptadores). Trocar Supabase, gateway ou provedor de e-mail vira trocar um arquivo.
- **Contratos explícitos entre front e back** (tipos compartilhados, OpenAPI, schemas Zod). Mudanças quebradas aparecem no compilador, não em produção.
- **Feature flags** para decisões que você quer testar sem comprometer. O checkout novo vai para 5% dos clientes antes de virar padrão.
- **Estratégia de saída escrita no ADR**: "se precisarmos sair do Supabase, o caminho é Postgres gerenciado + Auth.js, e as regras de RLS viram verificações no BFF".

Mudar de framework do zero raramente é a melhor saída. O padrão estrangulador (strangler fig) migra rota por rota: o proxy envia `/painel/pedidos` para o app novo e o resto continua no antigo até a migração terminar.

## Na entrevista

**Como você decide entre uma SPA e um framework com SSR?** Olho para quem precisa encontrar e abrir a página. Conteúdo público com SEO e primeira pintura importante pede SSR ou estático (Next.js, React Router 7 framework). Aplicação logada, interativa e de uso longo funciona bem como SPA com Vite. Considero também o conhecimento do time e a infraestrutura disponível.

**O que é um ADR e por que usar?** É um registro curto e versionado de uma decisão de arquitetura, com contexto, decisão, alternativas e consequências. Serve para o time futuro entender o porquê, evita rediscutir o que já foi decidido e torna explícito o gatilho para revisitar.

**Como você avalia construir versus comprar?** Pergunto se é diferencial do negócio, comparo custo total em dois anos (incluindo manutenção e plantão), avalio o custo de sair e o impacto se o fornecedor cair. Em qualquer caso, isolo a escolha atrás de uma interface para baratear a troca.

**Como lida com uma decisão em que o time está dividido?** Explicito os critérios e pesos antes das notas, separo fatos de preferências, faço uma prova de conceito curta quando o desempate depende de algo mensurável e, se ainda empatar, quem é dono da decisão decide e registra a discordância no ADR.

**Como explicar uma decisão técnica para alguém de negócio?** Falo em impacto (tempo de tela, vendas, risco, prazo), trago opções com custo e prazo, recomendo uma e digo o que ainda não sei.

**Quando uma prova de conceito vale a pena?** Quando o desempate depende de algo mensurável que ninguém sabe de cabeça, como latência, custo ou limite de um serviço. Defino uma pergunta única, um prazo de poucos dias e os critérios de sucesso e de descarte antes de começar. O código é descartável; o número medido vira contexto do ADR.

## Pratique

1. Liste dez decisões já tomadas na Quitanda (do Nível 1 ao 2) e classifique cada uma como reversível, cara de reverter ou praticamente irreversível.
2. Monte a matriz de decisão para "busca do catálogo": Postgres com índice de texto, Algolia ou Meilisearch. Defina os pesos antes das notas e teste a sensibilidade com o script.
3. Escreva o ADR 0001 da Quitanda registrando a escolha de Next.js para a loja, mesmo que a decisão já tenha sido tomada. Inclua alternativas e um gatilho de revisão.
4. Reescreva a proposta "adotar TanStack Query" em duas versões: uma para o time (o que muda no código) e uma para o PM (o que muda para o cliente e quanto custa).
5. Escolha um fornecedor que a Quitanda usa e escreva a estratégia de saída: o que precisaria mudar, em quantos arquivos, e qual interface o isolaria.
6. Escreva o documento de uma prova de conceito para o status do pedido em tempo real (pergunta, prazo, critérios de sucesso e de descarte) e guarde em `docs/poc/`.
