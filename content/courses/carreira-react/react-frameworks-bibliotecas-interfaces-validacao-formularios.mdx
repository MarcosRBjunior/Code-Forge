O checkout da Quitanda começou como um `Form` do React Router com dois campos e validação escrita à mão na action. A versão de verdade pede mais: nome, e-mail, telefone, CEP, número, complemento, forma de pagamento e, se for dinheiro, o valor para troco, que precisa ser maior que o total. Cada campo tem regra própria, mensagens precisam aparecer no lugar certo e ser anunciadas por leitores de tela, e o carrinho lateral, o seletor de horário de entrega e a confirmação de remoção de item precisam de componentes que funcionem com teclado, prendam o foco quando abertos e fechem com Esc. Escrever tudo isso do zero é caro e fácil de errar.

O ecossistema React tem bibliotecas maduras para as duas frentes. Para interface, há desde kits completos com visual pronto (MUI) até componentes sem estilo que só cuidam de comportamento e acessibilidade (Radix), passando pelo shadcn/ui, que copia componentes para dentro do seu projeto. Para formulários, a dupla React Hook Form e Zod virou padrão. Este capítulo compara as opções de interface, reconstrói o checkout com React Hook Form e Zod e fecha com o que verificar na acessibilidade de qualquer componente que você adotar.

**Você vai aprender:**

- Diferenciar kits de componentes estilizados, primitivos sem estilo e o modelo do shadcn/ui
- Usar Radix para um painel lateral acessível e saber o que o MUI entrega pronto
- Declarar regras de validação com Zod 4 e reaproveitá-las no cliente e no servidor
- Construir formulários com React Hook Form: `register`, `handleSubmit`, erros e estado de envio
- Integrar campos controlados de bibliotecas com `Controller`
- Verificar a acessibilidade de formulários e componentes de terceiros

## O mapa das bibliotecas de interface

| Tipo | Exemplos | O que entrega | Custo |
|---|---|---|---|
| Kit estilizado | MUI, Mantine, Chakra UI, Ant Design | Componentes prontos com visual, tema e acessibilidade | Visual com cara de biblioteca; customização profunda é trabalhosa; tamanho do bundle |
| Primitivos sem estilo | Radix Primitives, React Aria, Headless UI, Base UI | Comportamento, teclado, foco e ARIA; zero CSS | Você desenha todo o visual |
| Componentes copiados | shadcn/ui | Código-fonte de componentes (Radix com Tailwind) dentro do seu projeto | Você mantém o código copiado; atualizações não chegam sozinhas |

A pergunta que decide é: **de quem é o visual?** Um painel interno com prazo curto ganha muito com MUI. Um produto com identidade visual própria, como a Quitanda, fica melhor com primitivos sem estilo, diretamente ou via shadcn/ui, porque o comportamento difícil vem pronto e o visual é seu.

### MUI: tudo pronto

```bash
npm install @mui/material @emotion/react @emotion/styled
```

```jsx
// src/componentes/painel/FiltroPedidos.jsx
import { Button, MenuItem, Stack, TextField } from "@mui/material";

export default function FiltroPedidos({ status, onMudar, onAtualizar }) {
  return (
    <Stack direction="row" spacing={2}>
      <TextField select label="Status" value={status} onChange={(e) => onMudar(e.target.value)} size="small">
        <MenuItem value="">Todos</MenuItem>
        <MenuItem value="recebido">Recebido</MenuItem>
        <MenuItem value="separando">Separando</MenuItem>
        <MenuItem value="saiu para entrega">Saiu para entrega</MenuItem>
      </TextField>
      <Button variant="contained" onClick={onAtualizar}>Atualizar</Button>
    </Stack>
  );
}
```

O `TextField` já associa rótulo, campo, texto de ajuda e erro, e o select abre com teclado. O tema é configurado com `createTheme` e `ThemeProvider`. O MUI usa Emotion (CSS-in-JS) por baixo, o que combina pouco com o Tailwind adotado nas telas da Quitanda; por isso ele aparece aqui como referência, e não como escolha do projeto.

### Radix: comportamento sem visual

O carrinho lateral é um diálogo: precisa prender o foco enquanto aberto, fechar com Esc ou clique fora, devolver o foco ao botão que o abriu e ser anunciado como diálogo. Com Radix, você só escreve o visual:

```bash
npm install radix-ui
```

```jsx
// src/componentes/CarrinhoLateral.jsx
import { Dialog } from "radix-ui";
import { useSelector } from "react-redux";
import { selecionarItens, selecionarQuantidadeTotal } from "../estado/carrinhoSlice.js";
import Carrinho from "./Carrinho.jsx";

export default function CarrinhoLateral() {
  const itens = useSelector(selecionarItens);
  const quantidade = useSelector(selecionarQuantidadeTotal);

  return (
    <Dialog.Root>
      <Dialog.Trigger className="rounded-full px-3 py-1 hover:bg-folha-50">
        Carrinho ({quantidade})
      </Dialog.Trigger>
      <Dialog.Portal>
        <Dialog.Overlay className="fixed inset-0 bg-black/40" />
        <Dialog.Content className="fixed inset-y-0 right-0 w-full max-w-sm overflow-y-auto bg-white p-6 shadow-xl dark:bg-stone-900">
          <Dialog.Title className="text-xl font-semibold">Seu carrinho</Dialog.Title>
          <Dialog.Description className="text-sm text-stone-600">
            Revise os itens antes de finalizar.
          </Dialog.Description>
          <Carrinho itens={itens} />
          <Dialog.Close className="mt-4 underline">Continuar comprando</Dialog.Close>
        </Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

O Radix aplica `role="dialog"`, `aria-modal`, `aria-labelledby` apontando para o título, armadilha de foco, fechamento por Esc e retorno do foco, e expõe atributos como `data-state="open"` para você estilizar animações com a variante `data-[state=open]:` do Tailwind.

### shadcn/ui: o código é seu

O shadcn/ui não é instalado como dependência. Uma CLI copia o código de cada componente (construído sobre Radix e Tailwind) para o seu projeto, e a partir daí ele é seu para editar.

```bash
npx shadcn@latest init
npx shadcn@latest add button dialog input label
```

O `init` cria um `components.json` com as preferências, configura as variáveis de tema no CSS e cria a função `cn` (o mesmo `clsx` com `tailwind-merge` do capítulo de estilos). A CLI espera um alias de importação `@/` apontando para `src/`, configurado em `vite.config.js` (`resolve.alias`) e no `jsconfig.json`, e gera TypeScript por padrão; em projetos JavaScript, a opção `"tsx": false` no `components.json` gera arquivos `.jsx`. Os componentes chegam em `src/components/ui/`:

```jsx
// src/paginas/Checkout.jsx (trecho, com componentes do shadcn/ui)
import { Button } from "@/components/ui/button";

<Button type="submit" disabled={isSubmitting}>Finalizar pedido</Button>
<Button variant="outline" asChild>
  <Link to="/carrinho">Voltar ao carrinho</Link>
</Button>
```

A vantagem é controle total sem reescrever comportamento. A desvantagem é que corrigir um bug no componente original não chega ao seu projeto sem você copiar de novo. No Nível 3, quando a Quitanda ganhar o design system "Quitanda UI", essa é exatamente a fronteira a decidir: o que é primitivo de terceiros e o que é código do time.

<Callout type="tip" title="Avalie antes de adotar">
Antes de escolher uma biblioteca de componentes, teste três coisas com o teclado e um leitor de tela (NVDA no Windows, VoiceOver no macOS): abrir e fechar um diálogo, navegar num select ou menu com as setas e ouvir uma mensagem de erro de campo. Confira também o tamanho que ela acrescenta ao bundle e se a versão atual é compatível com React 19.
</Callout>

## Zod 4: as regras num só lugar

Zod é uma biblioteca de esquemas: você descreve o formato e as regras dos dados e obtém uma função que valida e converte. O mesmo esquema pode validar o formulário no navegador e o corpo da requisição no servidor, e no Nível 2 ele também gera os tipos TypeScript.

```bash
npm install zod react-hook-form @hookform/resolvers
```

```js
// src/esquemas/checkout.js
import { z } from "zod";

export function criarEsquemaCheckout(totalEmCentavos) {
  return z
    .object({
      nome: z.string().trim().min(3, "Informe seu nome completo."),
      email: z.email("Informe um e-mail válido."),
      telefone: z.string().regex(/^\(?\d{2}\)?\s?9?\d{4}-?\d{4}$/, "Use o formato (11) 91234-5678."),
      cep: z.string().regex(/^\d{5}-?\d{3}$/, "CEP com 8 dígitos."),
      numero: z.string().trim().min(1, "Informe o número."),
      complemento: z.string().trim().max(60, "Máximo de 60 caracteres.").optional(),
      pagamento: z.enum(["pix", "cartao", "dinheiro"], { error: "Escolha a forma de pagamento." }),
      trocoPara: z.string().optional(),
    })
    .refine(
      (dados) => dados.pagamento !== "dinheiro" || Number(dados.trocoPara) * 100 >= totalEmCentavos,
      { error: "O troco precisa ser para um valor maior ou igual ao total.", path: ["trocoPara"] },
    );
}
```

Pontos sobre Zod 4:

- **Formatos de string viraram funções de topo**: `z.email()`, `z.url()`, `z.uuid()`. A forma antiga `z.string().email()` ainda funciona, mas está obsoleta.
- **Mensagens** podem ser passadas como string direto (`min(3, "...")`) ou pelo parâmetro `error`, que substituiu o antigo `message`.
- **`refine` com `path`** cria regras que envolvem vários campos e atribui o erro a um campo específico.
- **`safeParse`** devolve `{ success, data, error }` sem lançar exceção, útil fora de formulários: `criarEsquemaCheckout(total).safeParse(corpo)` numa action ou numa API.

O esquema é uma função porque depende do total do carrinho. Regras que dependem de contexto externo entram como parâmetro, e o esquema continua puro e testável.

## React Hook Form

React Hook Form (RHF) gerencia formulários com campos **não controlados** por padrão: os valores vivem no DOM e são lidos por referência, então digitar não renderiza o formulário inteiro a cada tecla. Com o `zodResolver`, a validação vem do esquema Zod.

```jsx
// src/paginas/Checkout.jsx
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { useMutation, useQueryClient } from "@tanstack/react-query";
import { useDispatch, useSelector } from "react-redux";
import { useNavigate } from "react-router";
import { criarEsquemaCheckout } from "../esquemas/checkout.js";
import { esvaziou, selecionarItens, selecionarTotal } from "../estado/carrinhoSlice.js";
import { criarPedido } from "../servicos/pedidos.js";
import Campo from "../componentes/Campo.jsx";

export default function Checkout() {
  const itens = useSelector(selecionarItens);
  const total = useSelector(selecionarTotal);
  const dispatch = useDispatch();
  const navigate = useNavigate();
  const queryClient = useQueryClient();

  const {
    register,
    handleSubmit,
    watch,
    setError,
    formState: { errors, isSubmitting },
  } = useForm({
    resolver: zodResolver(criarEsquemaCheckout(total)),
    defaultValues: { nome: "", email: "", telefone: "", cep: "", numero: "", complemento: "", trocoPara: "" },
    mode: "onTouched",
  });

  const pedido = useMutation({ mutationFn: criarPedido });
  const pagamento = watch("pagamento");

  async function enviar(dados) {
    try {
      const criado = await pedido.mutateAsync({ ...dados, itens });
      dispatch(esvaziou());
      queryClient.invalidateQueries({ queryKey: ["pedidos"] });
      navigate(`/pedidos/${criado.id}`);
    } catch {
      setError("root.servidor", { message: "Não foi possível finalizar. Tente de novo em instantes." });
    }
  }

  return (
    <form onSubmit={handleSubmit(enviar)} noValidate className="grid max-w-lg gap-4">
      <Campo id="nome" rotulo="Nome completo" erro={errors.nome} {...register("nome")} autoComplete="name" />
      <Campo id="email" rotulo="E-mail" type="email" erro={errors.email} {...register("email")} autoComplete="email" />
      <Campo id="telefone" rotulo="Telefone" type="tel" erro={errors.telefone} {...register("telefone")} autoComplete="tel" />
      <Campo id="cep" rotulo="CEP" inputMode="numeric" erro={errors.cep} {...register("cep")} autoComplete="postal-code" />
      <Campo id="numero" rotulo="Número" erro={errors.numero} {...register("numero")} />
      <Campo id="complemento" rotulo="Complemento (opcional)" erro={errors.complemento} {...register("complemento")} />

      <fieldset aria-describedby={errors.pagamento ? "pagamento-erro" : undefined}>
        <legend>Forma de pagamento</legend>
        {["pix", "cartao", "dinheiro"].map((opcao) => (
          <label key={opcao} className="mr-4">
            <input type="radio" value={opcao} {...register("pagamento")} /> {opcao === "cartao" ? "Cartão na entrega" : opcao === "pix" ? "Pix" : "Dinheiro"}
          </label>
        ))}
        {errors.pagamento && <p id="pagamento-erro" role="alert">{errors.pagamento.message}</p>}
      </fieldset>

      {pagamento === "dinheiro" && (
        <Campo id="trocoPara" rotulo="Troco para quanto? (R$)" inputMode="decimal" erro={errors.trocoPara} {...register("trocoPara")} />
      )}

      {errors.root?.servidor && <p role="alert">{errors.root.servidor.message}</p>}
      <button type="submit" disabled={isSubmitting}>{isSubmitting ? "Enviando..." : "Finalizar pedido"}</button>
    </form>
  );
}
```

O campo reutilizável concentra rótulo, erro e atributos de acessibilidade. Como no React 19 `ref` é uma prop comum, o `ref` que o `register` devolve chega ao input sem `forwardRef`:

```jsx
// src/componentes/Campo.jsx
export default function Campo({ id, rotulo, erro, ref, ...resto }) {
  const idErro = `${id}-erro`;
  return (
    <div className="grid gap-1">
      <label htmlFor={id}>{rotulo}</label>
      <input id={id} ref={ref} aria-invalid={erro ? "true" : "false"} aria-describedby={erro ? idErro : undefined} {...resto} />
      {erro && <p id={idErro} className="text-sm text-tomate-600">{erro.message}</p>}
    </div>
  );
}
```

O que acontece em cada etapa:

- **`register("nome")`** devolve `name`, `ref`, `onChange` e `onBlur`. Espalhados no input, eles ligam o campo ao formulário.
- **`handleSubmit(enviar)`** impede o envio padrão, valida tudo com o esquema e só chama `enviar` com dados válidos. Se houver erro, foca o primeiro campo inválido.
- **`mode: "onTouched"`** valida um campo quando ele perde o foco pela primeira vez e, depois, a cada alteração. Validar a cada tecla desde o início irrita quem ainda está digitando.
- **`formState`** traz `errors`, `isSubmitting` (verdadeiro enquanto a promise de `enviar` não resolve), `isDirty` e outros. Leia só o que usar: o RHF só renderiza de novo pelas propriedades que você acessa.
- **`setError("root.servidor", ...)`** registra erros que não pertencem a um campo, como falha da API.
- **`watch("pagamento")`** observa um valor para mostrar campos condicionais.

### Componentes controlados com Controller

Componentes de bibliotecas que não expõem um `ref` de input nativo, como um select do Radix ou um seletor de data, precisam do `Controller`, que faz a ponte entre o valor controlado e o formulário:

```jsx
// src/paginas/Checkout.jsx (trecho)
import { Controller } from "react-hook-form";
import SeletorHorario from "../componentes/SeletorHorario.jsx";

// control vem do useForm, junto com register; horario entra no esquema como z.string().min(1, "Escolha um horário.")
<Controller
  name="horario"
  control={control}
  render={({ field, fieldState }) => (
    <SeletorHorario value={field.value} onValueChange={field.onChange} onBlur={field.onBlur} erro={fieldState.error} />
  )}
/>
```

| Abordagem | Bom para | Limite |
|---|---|---|
| `<form action>` com `useActionState` | Formulários curtos, envio com estado de pendente | Validação por campo e mensagens em tempo real ficam por sua conta |
| Estado controlado com `useState` | Um ou dois campos com formatação em tempo real | Escala mal; renderiza a cada tecla |
| React Hook Form com Zod | Formulários com muitas regras, campos condicionais, componentes de bibliotecas | Mais uma API para aprender |

<Callout type="warning" title="Validar no cliente não basta">
A validação do formulário melhora a experiência, mas qualquer pessoa pode chamar a API sem passar por ele. O servidor precisa validar de novo. A vantagem do Zod é que o mesmo esquema pode rodar nos dois lados: num BFF em Node.js ou numa Server Action do Next.js, `safeParse` no corpo recebido aplica as mesmas regras.
</Callout>

## Acessibilidade de formulários e componentes

Bibliotecas ajudam, mas não garantem acessibilidade. Uma lista para conferir em qualquer tela:

- **Todo campo tem rótulo visível** ligado por `htmlFor` e `id`. Placeholder não é rótulo: some ao digitar e tem contraste baixo.
- **Erros são associados ao campo** com `aria-describedby` e marcados com `aria-invalid`. O leitor de tela lê a mensagem ao focar o campo.
- **Grupos de opções** (rádios, checkboxes) ficam num `fieldset` com `legend`.
- **`autoComplete` e `inputMode`** corretos: `name`, `email`, `tel`, `postal-code`; teclado numérico no CEP. Preencher endereço no celular fica muito mais rápido.
- **Erro não depende só de cor**: há texto, e o primeiro campo inválido recebe foco no envio.
- **Diálogos** prendem o foco, fecham com Esc, devolvem o foco e têm título. Com Radix isso vem pronto; com um componente feito à mão, raramente.
- **Botão de envio desabilitado durante o envio** evita pedidos duplicados, mas não deixe o botão desabilitado antes do primeiro envio só porque há erros: o usuário não descobre o que falta.

Ferramentas: a aba Lighthouse e a extensão axe DevTools apontam rótulos ausentes, contraste baixo e ARIA inválido. O teste final é usar a tela só com o teclado.

## Na entrevista

**Qual a diferença entre MUI, Radix e shadcn/ui?** MUI é um kit completo com visual e tema próprios. Radix entrega primitivos sem estilo, cuidando de comportamento, teclado, foco e ARIA. shadcn/ui copia para o projeto componentes prontos feitos com Radix e Tailwind, que passam a ser código do time.

**Por que o React Hook Form tem bom desempenho?** Porque usa campos não controlados por padrão e assina o estado do formulário de forma seletiva. Digitar não renderiza o formulário inteiro; só os componentes que leem o valor ou o erro alterado renderizam.

**Por que usar Zod com o formulário em vez de regras no register?** O esquema concentra as regras num lugar independente da interface, que pode ser testado isoladamente, reaproveitado no servidor e, com TypeScript, gerar os tipos dos dados. As regras no `register` ficam presas ao componente.

**Quando você usaria Controller?** Para componentes controlados que não expõem um input nativo com `ref`, como selects customizados, seletores de data ou componentes de bibliotecas. O `Controller` repassa `value`, `onChange` e `onBlur` e integra o campo à validação.

**O que verificar na acessibilidade de um formulário?** Rótulo associado a cada campo, erros ligados por `aria-describedby` e anunciados, grupos em `fieldset` com `legend`, foco no primeiro erro, `autoComplete` correto e navegação completa por teclado.

## Pratique

1. Implemente o `CarrinhoLateral` com o `Dialog` do Radix e verifique com o teclado: Tab fica preso no painel, Esc fecha, e o foco volta ao botão do cabeçalho.
2. Crie `criarEsquemaCheckout` e teste-o no console com `safeParse` para dados válidos, e-mail inválido e troco menor que o total.
3. Reconstrua o checkout com React Hook Form, o componente `Campo` e o `zodResolver`, mostrando o campo de troco só para pagamento em dinheiro.
4. Desligue a API e confirme que a mensagem de erro do servidor aparece e é anunciada pelo leitor de tela.
5. Configure o shadcn/ui num branch, troque os botões do checkout pelo `Button` gerado e liste as diferenças em relação ao seu componente `Botao` do capítulo de estilos.
6. Rode o axe DevTools no checkout e no carrinho lateral e corrija todos os problemas apontados.
