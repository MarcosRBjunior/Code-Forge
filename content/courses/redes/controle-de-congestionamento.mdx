O controle de fluxo protege o receptor. Mas entre os dois extremos há roteadores com filas finitas, compartilhadas por milhares de conexões. Se todo mundo transmite o máximo que o receptor aceita, as filas transbordam, pacotes são descartados, todos retransmitem e a rede entra em **colapso de congestionamento**: links ocupados carregando retransmissões, vazão útil perto de zero. Isso de fato aconteceu na internet dos anos 1980, e a resposta foi fazer cada emissor estimar sozinho quanto a rede aguenta, sem ajuda de ninguém no meio.

## A janela de congestionamento

O emissor mantém uma segunda janela, a **cwnd**, que só existe na cabeça dele (não vai no cabeçalho). O limite efetivo de bytes em voo passa a ser:

```text
em voo  <=  min(cwnd, rwnd)
```

A rede nunca diz explicitamente "estou cheia". O emissor **infere** congestionamento por sinais indiretos: perda de pacote (timeout ou ACKs duplicados), aumento do RTT ou, quando roteadores e hosts suportam, a marca **ECN** no cabeçalho IP.

## As fases clássicas (Reno)

| Fase | Regra | Efeito por RTT |
| --- | --- | --- |
| Slow start | cwnd cresce 1 MSS a cada ACK | Dobra (crescimento exponencial) |
| Congestion avoidance | cwnd cresce cerca de 1 MSS por RTT | Linear |
| Perda por 3 ACKs duplicados | ssthresh = cwnd / 2; cwnd = ssthresh | Corte pela metade (fast recovery) |
| Perda por timeout | ssthresh = cwnd / 2; cwnd = 1 MSS | Volta ao slow start |

O nome slow start engana: ele é lento só no ponto de partida. O **ssthresh** marca onde o crescimento exponencial vira linear. A combinação de subir somando e cair multiplicando se chama **AIMD** (additive increase, multiplicative decrease) e gera o famoso gráfico em dente de serra.

```python
def reno(rtts, perdas_dup, timeouts, ssthresh=32):
    cwnd = 1
    linha = []
    for t in range(1, rtts + 1):
        linha.append(cwnd)
        if t in timeouts:
            ssthresh, cwnd, evento = max(cwnd // 2, 2), 1, "timeout"
        elif t in perdas_dup:
            ssthresh = max(cwnd // 2, 2)
            cwnd, evento = ssthresh, "3 dup ACKs"
        elif cwnd < ssthresh:
            cwnd, evento = min(cwnd * 2, ssthresh), "slow start"
        else:
            cwnd, evento = cwnd + 1, "avoidance"
        print(f"RTT {t:2}: cwnd={linha[-1]:3}  -> {evento}")
    return linha

reno(14, perdas_dup={8}, timeouts={12}, ssthresh=16)
```

```text
Saída:
RTT  1: cwnd=  1  -> slow start
RTT  2: cwnd=  2  -> slow start
RTT  3: cwnd=  4  -> slow start
RTT  4: cwnd=  8  -> slow start
RTT  5: cwnd= 16  -> avoidance
RTT  6: cwnd= 17  -> avoidance
RTT  7: cwnd= 18  -> avoidance
RTT  8: cwnd= 19  -> 3 dup ACKs
RTT  9: cwnd=  9  -> avoidance
RTT 10: cwnd= 10  -> avoidance
RTT 11: cwnd= 11  -> avoidance
RTT 12: cwnd= 12  -> timeout
RTT 13: cwnd=  1  -> slow start
RTT 14: cwnd=  2  -> slow start
```

Repare na diferença entre os dois tipos de perda. ACKs duplicados significam que pacotes continuam chegando, então a rede está apertada mas viva: corta pela metade. Timeout significa silêncio total, então o emissor recomeça do zero. Um único timeout derruba a vazão por vários RTTs, e é por isso que **perda no fim de uma resposta** (quando não há segmentos depois para gerar ACKs duplicados) machuca tanto a latência de cauda.

## Por que AIMD é justo

Se dois fluxos dividem um link e ambos sobem somando e caem multiplicando, a diferença entre eles encolhe a cada corte, enquanto a soma oscila em torno da capacidade. Aumentar multiplicando não teria essa propriedade.

```python
CAPACIDADE = 100
a, b = 80.0, 10.0
for rodada in range(1, 41):
    a, b = a + 1, b + 1
    if a + b > CAPACIDADE:          # fila transbordou: os dois perdem
        a, b = a / 2, b / 2
        print(f"corte na rodada {rodada:2}: A={a:5.1f} B={b:5.1f} diferenca={a - b:5.1f}")
```

```text
Saída:
corte na rodada  6: A= 43.0 B=  8.0 diferenca= 35.0
corte na rodada 31: A= 34.0 B= 16.5 diferenca= 17.5
```

A cada corte a diferença cai pela metade (35, depois 17,5), porque somar 1 aos dois não muda a distância e dividir por 2 a encolhe. Com mais rodadas os fluxos convergem para a divisão igual.

## Além do Reno

- **CUBIC** (padrão no Linux e no Windows): o crescimento depois de uma perda segue uma curva cúbica no tempo, que sobe rápido longe do ponto da última perda e devagar perto dele. Funciona melhor em links rápidos com RTT alto, onde somar 1 MSS por RTT levaria minutos para encher o tubo.
- **BBR** (Google): não usa perda como sinal principal. Mede a banda de gargalo e o RTT mínimo e tenta enviar exatamente no produto banda-atraso, mantendo filas curtas. Brilha em links com perda aleatória (Wi-Fi, celular), onde o Reno cortaria a janela sem necessidade.
- **Bufferbloat:** roteadores com filas enormes atrasam o sinal de perda; algoritmos baseados em perda enchem a fila e o RTT dispara (videochamada travando enquanto alguém faz upload). AQM como CoDel e ECN atacam isso.

<Callout type="tip" title="O impacto em requests curtos">
Uma resposta HTTP de 100 KB nunca sai do slow start. Com janela inicial de 10 segmentos (cerca de 14 KB), ela leva uns 4 RTTs só para ser entregue. Por isso reaproveitar conexões quentes, com cwnd já crescida, reduz latência além de economizar o handshake.
</Callout>
