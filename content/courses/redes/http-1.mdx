HTTP/1.1 tem quase 30 anos e ainda carrega boa parte do tráfego entre serviços, proxies e load balancers. Como é um protocolo de texto, dá para ler cada byte, e é justamente nesses detalhes (onde termina uma mensagem, quando a conexão pode ser reaproveitada) que moram os problemas de latência e alguns bugs de segurança famosos.

## O formato da mensagem

Uma requisição é uma linha de início, cabeçalhos, uma linha em branco e, opcionalmente, um corpo. Cada linha termina com CRLF (`\r\n`).

```text
GET /pedidos/42 HTTP/1.1\r\n          <- método, alvo, versão
Host: api.loja.com\r\n                <- obrigatório no 1.1 (vários sites por IP)
Accept: application/json\r\n
\r\n                                  <- fim dos cabeçalhos

HTTP/1.1 200 OK\r\n                   <- versão, status, frase
Content-Type: application/json\r\n
Content-Length: 28\r\n                <- quantos bytes de corpo vêm a seguir
\r\n
{"id": 42, "status": "pago"}
```

O ponto central é o **enquadramento**: TCP entrega um fluxo de bytes sem fronteiras, então o receptor precisa saber onde termina o corpo. Há três formas:

| Mecanismo | Como o fim é detectado | Quando aparece |
| --- | --- | --- |
| `Content-Length` | conta exatamente N bytes | corpo de tamanho conhecido |
| `Transfer-Encoding: chunked` | blocos com tamanho em hexadecimal, terminando num bloco de tamanho 0 | respostas geradas em streaming |
| fechar a conexão | EOF do TCP | legado do HTTP/1.0; impede reaproveitar a conexão |

## Conexões persistentes

No HTTP/1.0 cada requisição abria uma conexão TCP nova: handshake, slow start do zero e, com HTTPS, um handshake TLS a mais. O 1.1 tornou a conexão **persistente por padrão** (keep-alive): depois de ler a resposta inteira, o cliente pode mandar a próxima requisição no mesmo socket. Isso só funciona porque o enquadramento diz onde cada resposta termina.

O programa abaixo sobe um servidor HTTP/1.1 mínimo em localhost e faz duas requisições pela mesma conexão TCP, lendo cada resposta pelo `Content-Length`.

```python
import socket, threading

def ler_mensagem(arq):
    linha_inicial = arq.readline().decode().strip()
    cabecalhos = {}
    while (linha := arq.readline()) not in (b"\r\n", b""):
        nome, valor = linha.decode().split(":", 1)
        cabecalhos[nome.strip().lower()] = valor.strip()
    corpo = arq.read(int(cabecalhos.get("content-length", 0)))
    return linha_inicial, cabecalhos, corpo

conexoes = 0

def servidor(sock):
    global conexoes
    conn, _ = sock.accept()
    conexoes += 1
    arq = conn.makefile("rb")
    atendidas = 0
    while True:
        inicio, cab, _ = ler_mensagem(arq)
        if not inicio:
            break
        atendidas += 1
        corpo = f"req {atendidas}: {inicio.split()[1]}".encode()
        conn.sendall(b"HTTP/1.1 200 OK\r\nContent-Type: text/plain\r\n"
                     + f"Content-Length: {len(corpo)}\r\n\r\n".encode() + corpo)
    conn.close()

srv = socket.socket()
srv.bind(("127.0.0.1", 0))
srv.listen()
t = threading.Thread(target=servidor, args=(srv,))
t.start()

cli = socket.create_connection(srv.getsockname())
arq = cli.makefile("rb")
for caminho in ["/pedidos/1", "/pedidos/2"]:
    cli.sendall(f"GET {caminho} HTTP/1.1\r\nHost: localhost\r\n\r\n".encode())
    status, cab, corpo = ler_mensagem(arq)
    print(status, "|", cab["content-length"], "bytes |", corpo.decode())
arq.close()
cli.close()
t.join()
srv.close()
print("conexoes aceitas pelo servidor:", conexoes)
```

```text
Saída:
HTTP/1.1 200 OK | 17 bytes | req 1: /pedidos/1
HTTP/1.1 200 OK | 17 bytes | req 2: /pedidos/2
conexoes aceitas pelo servidor: 1
```

## Head-of-line blocking e o limite de 6 conexões

Numa conexão HTTP/1.1, as respostas saem na ordem das requisições, uma de cada vez. O **pipelining** (mandar várias requisições sem esperar) existe na especificação, mas a resposta lenta da primeira bloqueia todas as seguintes, e proxies quebrados tornaram o recurso inviável; navegadores o desativaram. A saída prática foi abrir **várias conexões paralelas por origem**, em geral até 6. Daí vieram as gambiarras da era 1.1: domain sharding (espalhar recursos por `img1`, `img2`...), sprites e concatenação de arquivos. Todas existem para contornar o fato de que uma conexão carrega uma resposta por vez.

```text
conexão 1:  [GET /a ......... resposta lenta .........][GET /b][GET /c]
                                                     ^ /b e /c esperam
```

## Chunked na prática

Quando o servidor não sabe o tamanho do corpo de antemão (uma consulta que vai sendo serializada, um log em streaming), ele usa chunked: cada bloco vem precedido pelo tamanho em hexadecimal.

```javascript
function decodificarChunked(dados) {
  const partes = [];
  let pos = 0;
  while (true) {
    const fimLinha = dados.indexOf("\r\n", pos);

function reprBytes(b) {
  let s = "";
  for (const x of b) {
    if (x === 0x0d) s += "\\r";
    else if (x === 0x0a) s += "\\n";
    else if (x === 0x09) s += "\\t";
    else if (x === 0x5c || x === 0x27) s += "\\" + String.fromCharCode(x);
    else if (x >= 32 && x < 127) s += String.fromCharCode(x);
    else s += "\\x" + x.toString(16).padStart(2, "0");
  }
  return `b'${s}'`;
}
```

```java
import java.io.ByteArrayOutputStream;
import java.nio.charset.StandardCharsets;

static byte[] decodificarChunked(byte[] dados) {
    ByteArrayOutputStream corpo = new ByteArrayOutputStream();
    int pos = 0;
    while (true) {
        int fimLinha = pos;
        while (!(dados[fimLinha] == '\r' && dados[fimLinha + 1] == '\n')) fimLinha++;
        int tamanho = Integer.parseInt(new String(dados, pos, fimLinha - pos, StandardCharsets.US_ASCII), 16);
        pos = fimLinha + 2;
        if (tamanho == 0) {
            return corpo.toByteArray();
        }
        corpo.write(dados, pos, tamanho);
        System.out.println(String.format("bloco de %d bytes (0x%x)", tamanho, tamanho));
        pos += tamanho + 2; // pula o CRLF que fecha o bloco
    }
}

static byte[] codificarChunked(byte[][] pedacos) {
    ByteArrayOutputStream saida = new ByteArrayOutputStream();
    for (byte[] p : pedacos) {
        saida.writeBytes((Integer.toHexString(p.length) + "\r\n").getBytes(StandardCharsets.US_ASCII));
        saida.writeBytes(p);
        saida.writeBytes("\r\n".getBytes(StandardCharsets.US_ASCII));
    }
    saida.writeBytes("0\r\n\r\n".getBytes(StandardCharsets.US_ASCII));
    return saida.toByteArray();
}

// imita o repr de bytes do Python: b'...'
static String reprBytes(byte[] b) {
    StringBuilder s = new StringBuilder("b'");
    for (byte cru : b) {
        int x = cru & 0xff;
        if (x == '\r') s.append("\\r");
        else if (x == '\n') s.append("\\n");
        else if (x == '\t') s.append("\\t");
        else if (x == '\\' || x == '\'') s.append('\\').append((char) x);
        else if (x >= 32 && x < 127) s.append((char) x);
        else s.append(String.format("\\x%02x", x));
    }
    return s.append("'").toString();
}

public static void main(String[] args) {
    byte[] bruto = codificarChunked(new byte[][]{
        "{\"itens".getBytes(StandardCharsets.UTF_8),
        "\": [1, 2, 3], \"total\": 3}".getBytes(StandardCharsets.UTF_8)});
    System.out.println(reprBytes(bruto));
```

```go
func decodificarChunked(dados []byte) []byte {
	corpo, pos := []byte{}, 0
	for {
		fimLinha := pos + bytes.Index(dados[pos:], []byte("\r\n"))
		tamanho, _ := strconv.ParseInt(string(dados[pos:fimLinha]), 16, 0)
		pos = fimLinha + 2
		if tamanho == 0 {
			return corpo
		}
		corpo = append(corpo, dados[pos:pos+int(tamanho)]...)
		fmt.Printf("bloco de %d bytes (0x%x)\n", tamanho, tamanho)
		pos += int(tamanho) + 2 // pula o CRLF que fecha o bloco
	}
}

	for _, p := range pedacos {
		saida = append(saida, fmt.Sprintf("%x\r\n", len(p))...)
		saida = append(saida, p...)
		saida = append(saida, "\r\n"...)

	return append(saida, "0\r\n\r\n"...)
```

<Callout type="warning" title="Request smuggling">
Se uma requisição traz `Content-Length` e `Transfer-Encoding: chunked` ao mesmo tempo, e o proxy da frente usa um enquanto o servidor de trás usa o outro, os dois discordam sobre onde ela termina. O atacante "contrabandeia" uma segunda requisição dentro da primeira. A defesa é rejeitar mensagens ambíguas e normalizar o enquadramento no proxy.
</Callout>

## Trade-offs

- **Texto legível** facilita depurar com `curl -v` e `tcpdump`, mas cabeçalhos repetidos (cookies, user-agent) são reenviados inteiros em toda requisição, sem compressão.
- **Keep-alive** economiza handshakes, mas cada conexão ociosa ocupa memória no servidor; por isso servidores fecham conexões paradas depois de um timeout, e o cliente precisa tratar a corrida em que reenvia numa conexão que acabou de ser fechada.
- **Várias conexões** contornam o HOL blocking, mas cada uma faz seu próprio slow start e disputa banda com as outras.

