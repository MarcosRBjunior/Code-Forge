Você não precisa saber montar pacotes TCP à mão para uma entrevista de system design, mas precisa entender o suficiente de redes para escolher protocolos, explicar latências e saber onde as coisas quebram. Este capítulo resume o que realmente aparece.

## O caminho de uma requisição

Quando um app chama `https://api.exemplo.com/feed`, acontece, de forma simplificada:

```text
1. DNS        nome -> IP (geralmente cacheado)
2. TCP        handshake de 3 vias (1 ida e volta)
3. TLS        negociação de chaves (1 ida e volta no TLS 1.3)
4. HTTP       requisição e resposta
5. Reuso      a conexão fica aberta para próximas requisições
```

Cada ida e volta custa a latência da rede. Entre continentes isso passa de 100 ms. Por isso conexões persistentes, CDNs e servidores próximos ao usuário fazem tanta diferença: eliminam idas e voltas ou encurtam cada uma.

## TCP versus UDP

| | TCP | UDP |
| --- | --- | --- |
| Entrega | Garantida e ordenada | Sem garantia |
| Conexão | Sim, com handshake | Não |
| Overhead | Maior | Mínimo |
| Uso típico | APIs, bancos, transferência de arquivos | Voz, vídeo em tempo real, jogos, DNS |

Em mídia ao vivo, um pacote atrasado é inútil; melhor perdê-lo do que esperar retransmissão. Por isso chamadas de vídeo preferem UDP. Para quase todo o resto, TCP.

## HTTP e suas versões

- **HTTP/1.1:** uma requisição por vez por conexão; navegadores abrem várias conexões em paralelo.
- **HTTP/2:** multiplexa várias requisições numa única conexão TCP, com cabeçalhos comprimidos.
- **HTTP/3:** roda sobre QUIC (baseado em UDP), evita que a perda de um pacote trave todas as requisições da conexão e acelera o estabelecimento da conexão.

Na entrevista, raramente importa qual versão. Importa saber que reusar conexões e reduzir idas e voltas melhora latência.

## Estilos de API

- **REST:** recursos e verbos HTTP. Simples, cacheável, padrão para APIs públicas.
- **gRPC:** contratos com Protocol Buffers sobre HTTP/2, binário e eficiente. Ótimo entre serviços internos.
- **GraphQL:** o cliente pede exatamente os campos que quer. Útil para apps com telas variadas, mas complica cache e controle de custo de consultas.

## Comunicação em tempo real

Quando o servidor precisa avisar o cliente, há quatro opções principais:

| Técnica | Como funciona | Quando usar |
| --- | --- | --- |
| Polling curto | Cliente pergunta a cada N segundos | Atualizações raras, simplicidade máxima |
| Long polling | Servidor segura a requisição até ter novidade | Compatibilidade ampla, volume moderado |
| Server-Sent Events | Conexão HTTP aberta, servidor envia eventos | Fluxo só do servidor para o cliente |
| WebSocket | Canal bidirecional persistente | Chat, colaboração, jogos |

Conexões persistentes têm custo: cada servidor segura dezenas ou centenas de milhares delas, e você precisa saber em qual servidor cada usuário está conectado para entregar mensagens.

<Callout type="note" title="Balanceamento de conexões longas">
Com WebSocket, o load balancer distribui conexões, não requisições. Se um servidor cai, milhares de clientes reconectam ao mesmo tempo. Planeje reconexão com espera aleatória no cliente para não derrubar os servidores restantes.
</Callout>

## DNS e roteamento geográfico

O DNS pode responder com IPs diferentes conforme a localização do usuário (GeoDNS) ou usar anycast, em que vários datacenters anunciam o mesmo IP e a rede entrega ao mais próximo. É assim que CDNs e sistemas multi-região direcionam usuários. Lembre que respostas DNS são cacheadas com TTL, então trocar de região via DNS não é instantâneo.

## Latências de referência

Tenha uma noção de ordens de grandeza:

```text
Leitura em memória local          ~100 ns
Ida e volta no mesmo datacenter   ~0,5 ms
Leitura aleatória em SSD          ~0,1 ms
Ida e volta entre continentes     ~100-150 ms
```

Esses números justificam escolhas: cache em memória é milhares de vezes mais rápido que uma chamada entre regiões; uma página que faz dez chamadas sequenciais entre continentes passa de um segundo.

## Na entrevista

Cite redes quando elas mudam a decisão: "como o servidor precisa empurrar mensagens, vou usar WebSocket e manter um registro de qual gateway segura cada conexão". Follow-ups comuns: como escalar milhões de conexões simultâneas? O que acontece numa reconexão em massa? Por que não usar polling? Por que gRPC entre serviços e REST para o público?
