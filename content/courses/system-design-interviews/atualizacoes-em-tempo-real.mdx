title: Atualizações em tempo real

HTTP clássico é pedido e resposta: o cliente pergunta, o servidor responde. Para chat, placares, notificações, colaboração e painéis, o servidor precisa **avisar o cliente quando algo acontece**. Há quatro técnicas, com custo e complexidade crescentes.

## 1. Polling

O cliente pergunta a cada N segundos: "há novidade?".

- Simples, funciona em qualquer lugar, fácil de cachear.
- Desperdício: a maioria das respostas é vazia, e a latência é de até N segundos.
- Bom para atualizações pouco frequentes ou tolerantes a atraso.

## 2. Long polling

O cliente pergunta, e o servidor **segura a requisição aberta** até haver dado novo ou um timeout. Quando responde, o cliente já abre outra.

- Latência baixa sem protocolo novo.
- Cada cliente ocupa uma conexão pendente; reconexões frequentes.

## 3. Server-Sent Events (SSE)

Uma conexão HTTP de longa duração em que o servidor **empurra** eventos de texto. Unidirecional (servidor para cliente), com reconexão automática e retomada pelo último ID de evento.

- Ideal para notificações, feeds ao vivo, progresso de tarefas.
- Mais simples que WebSocket e compatível com infraestrutura HTTP.

## 4. WebSocket

Conexão bidirecional persistente, iniciada por um upgrade HTTP. Cliente e servidor enviam mensagens a qualquer momento, com baixa sobrecarga.

- Ideal para chat, jogos, edição colaborativa.
- Exige tratar reconexão, heartbeats e balanceamento de conexões persistentes.

| Técnica | Direção | Latência | Complexidade | Quando |
| --- | --- | --- | --- | --- |
| Polling | Cliente puxa | Alta | Mínima | Dados raramente mudam |
| Long polling | Cliente puxa (pendente) | Baixa | Baixa | Fallback |
| SSE | Servidor empurra | Baixa | Média | Notificações, feeds |
| WebSocket | Bidirecional | Muito baixa | Alta | Chat, colaboração |

## Escalando conexões persistentes

Milhões de conexões abertas exigem arquitetura própria:

- **Servidores de gateway** dedicados, que só mantêm conexões (cada um aguenta dezenas a centenas de milhares).
- O gateway é **stateful**: guarda "qual usuário está em qual conexão". Mantenha esse mapeamento num armazenamento compartilhado (Redis).
- Para entregar uma mensagem, o serviço consulta o mapa, localiza o gateway e a encaminha por **pub/sub** (Redis Pub/Sub, Kafka, NATS).

```text
serviço de chat -> pub/sub (canal do usuário) -> gateway B -> WebSocket do usuário
mapa:  usuario:42 -> gateway B
```

- **Balanceador** com suporte a WebSocket e timeouts longos.
- **Reconexão com backoff e jitter**, para que uma queda de gateway não gere uma tempestade de reconexões.
- **Mensagens perdidas durante a desconexão:** guarde-as e entregue ao reconectar, usando um ID de última mensagem vista.
- **Heartbeats** detectam conexões mortas.

## Quando basta algo simples

Nem tudo precisa de conexão persistente. Notificação de baixa urgência: use push móvel (APNs/FCM) ou e-mail. Dashboard que atualiza a cada 30 segundos: polling com cache.

## Na entrevista

Escolha a técnica mais simples que atende o requisito e justifique: "notificações são só do servidor para o cliente, então SSE; chat é bidirecional, então WebSocket". Depois fale de escala: gateways, mapa usuário-conexão, pub/sub e reconexão. Follow-ups: o que acontece se um gateway cair, como garantir a ordem e a entrega de mensagens e como fazer fan-out para um canal com milhões de inscritos.
