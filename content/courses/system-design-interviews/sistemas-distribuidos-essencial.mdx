Assim que seu sistema passa de uma máquina, aparecem problemas que não existiam antes: a rede perde mensagens, relógios discordam, nós caem no meio de uma operação. Este capítulo resume os conceitos que você precisa dominar para responder bem quando o entrevistador perguntar "e se este nó falhar?".

## Falhas são normais

Em um cluster com centenas de máquinas, alguma está falhando agora. Por isso sistemas distribuídos assumem que:

- Mensagens podem se perder, atrasar ou chegar duplicadas.
- Um nó lento é indistinguível de um nó morto por algum tempo.
- Não existe relógio global confiável.

Toda decisão de design responde à pergunta "o que acontece quando algo der errado?".

## Replicação

Copiar dados em vários nós serve a dois propósitos: sobreviver a falhas e distribuir leituras.

| Modelo | Como funciona | Trade-off |
| --- | --- | --- |
| Líder único | Escritas no líder, réplicas seguem | Simples; líder é gargalo de escrita e ponto de failover |
| Multi-líder | Vários nós aceitam escrita | Bom entre regiões; exige resolver conflitos |
| Sem líder | Cliente escreve e lê em vários nós | Alta disponibilidade; consistência ajustável por quorum |

Replicação **síncrona** espera a réplica confirmar e não perde dados se o líder cair, mas aumenta latência. **Assíncrona** é rápida, mas pode perder as últimas escritas num failover.

## Quorum

Em sistemas sem líder, com N réplicas, você escreve em W e lê de R. Se `W + R > N`, toda leitura cruza com pelo menos uma réplica que tem a escrita mais recente. Com N = 3, W = 2 e R = 2 é a configuração clássica. Diminuir W ou R aumenta velocidade e disponibilidade à custa dessa garantia.

## Consistência

Os modelos mais citados, do mais forte ao mais fraco:

- **Linearizável (forte):** o sistema se comporta como se houvesse uma única cópia. Toda leitura vê a última escrita confirmada.
- **Leitura das próprias escritas:** você sempre vê o que você mesmo escreveu; outros podem ver depois.
- **Causal:** se A causou B, ninguém vê B sem ver A (resposta não aparece antes da pergunta).
- **Eventual:** se as escritas pararem, as réplicas convergem em algum momento.

Escolha por requisito: saldo bancário pede forte; contagem de curtidas aceita eventual.

## CAP e PACELC

O teorema CAP diz que, durante uma **partição de rede**, você escolhe entre manter consistência (recusar algumas requisições) ou disponibilidade (responder com dados possivelmente desatualizados). Fora de partições, a escolha continua existindo de outra forma: latência versus consistência. Essa extensão é o PACELC.

<Callout type="note" title="Use CAP com cuidado">
Dizer "este sistema é AP" sem contexto soa decorado. Melhor: "durante uma partição, prefiro aceitar o pedido de carrinho e reconciliar depois, porque perder uma venda custa mais do que um item duplicado".
</Callout>

## Particionamento e hash consistente

Para dividir dados entre nós, o hash simples `hash(chave) mod N` tem um problema: mudar N remapeia quase todas as chaves. O **hash consistente** coloca nós e chaves num anel; cada chave pertence ao próximo nó no sentido horário. Adicionar ou remover um nó move só uma fração das chaves. Nós virtuais (cada máquina ocupa várias posições no anel) equilibram a carga.

```text
          nó A
       /        \
  chave k1      nó B
     |            |
   nó D        chave k2
       \        /
          nó C
k1 -> próximo nó no sentido horário
```

## Consenso e coordenação

Quando vários nós precisam concordar (quem é o líder, qual é a configuração atual), usam algoritmos de consenso como Raft ou Paxos, geralmente através de serviços prontos como ZooKeeper ou etcd. Você não precisa explicar o algoritmo em detalhes, mas deve saber que ele exige maioria: um cluster de 5 nós tolera 2 falhas.

## Entrega de mensagens

- **No máximo uma vez:** pode perder, nunca duplica.
- **Pelo menos uma vez:** nunca perde, pode duplicar. É o padrão na prática.
- **Exatamente uma vez:** na prática, é pelo menos uma vez combinado com processamento **idempotente** ou deduplicação por ID.

## Tempo e ordenação

Relógios de máquinas divergem. Não use timestamp de servidor como única fonte de ordem entre eventos de máquinas diferentes. Alternativas: um sequenciador central, IDs ordenáveis gerados com cuidado, ou relógios lógicos.

## Na entrevista

Traga esses conceitos quando eles resolvem um problema concreto do desenho. Follow-ups clássicos: o que acontece se o líder cair no meio de uma escrita? Como evitar dois líderes simultâneos? Como você lida com mensagens duplicadas? Que consistência o usuário realmente precisa aqui?
