Docker empacota uma aplicação e tudo de que ela depende (runtime, bibliotecas, configuração) numa **imagem** que roda igual em qualquer lugar. Isso elimina o clássico "na minha máquina funciona" e é a base de quase toda implantação moderna.

## Containers não são VMs

Uma máquina virtual emula hardware e roda um sistema operacional inteiro. Um container é um processo comum do host, isolado pelo kernel Linux:

- **Namespaces** isolam o que o processo enxerga (processos, rede, sistema de arquivos).
- **cgroups** limitam o que ele pode consumir (CPU, memória).

```text
VM:         [app][libs][SO convidado] x N  sobre hypervisor
Container:  [app][libs] x N  compartilhando o kernel do host
```

Resultado: containers iniciam em segundos ou menos, ocupam megabytes e permitem muito mais instâncias por máquina. O preço é um isolamento mais fraco que o de uma VM, pois o kernel é compartilhado.

## Imagem e camadas

Uma imagem é feita de camadas somente leitura, geradas por um `Dockerfile`:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "servidor.py"]
```

Cada instrução vira uma camada em cache. Por isso a ordem importa: coloque o que muda pouco (dependências) antes do que muda sempre (seu código), e as reconstruções ficam rápidas. Imagens são guardadas em um **registry** (Docker Hub, ECR) e baixadas pelos hosts.

## Boas práticas

- Imagens pequenas (`slim`, `alpine`, builds multi-stage) reduzem tempo de download e superfície de ataque.
- Um processo por container, com logs em stdout para o agregador coletar.
- Não rode como root.
- Fixe versões das imagens base; evite `latest`.
- Configuração por variáveis de ambiente, sem segredos dentro da imagem.
- **Containers são efêmeros:** o disco interno some junto com eles. Dados persistentes vão para volumes ou serviços externos (banco, S3).

## Por que importa em system design

- **Reprodutibilidade:** o mesmo artefato vai do laptop à produção.
- **Escala horizontal:** subir mais réplicas é iniciar mais containers.
- **Densidade e custo:** várias aplicações compartilham o mesmo host.
- **Base do orquestrador:** Kubernetes agenda e gerencia containers.

## Armadilhas

- Guardar estado dentro do container e perdê-lo num reinício.
- Imagens enormes e lentas de baixar durante um pico de autoscaling.
- Container sem limites de memória pode derrubar o host.
- Falta de health checks faz o orquestrador manter instâncias travadas.

## Na entrevista

Normalmente basta dizer "os serviços rodam em containers, orquestrados por Kubernetes", reforçando que são stateless e escalam horizontalmente. Se for perguntado: diferença entre container e VM (kernel compartilhado), por que imagens por camadas aceleram o deploy e onde guardar dados persistentes (fora do container).
