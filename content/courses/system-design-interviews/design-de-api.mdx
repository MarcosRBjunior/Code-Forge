A API é o contrato entre o seu sistema e quem o usa. Na entrevista, escrevê-la cedo tem dois efeitos: deixa claro o que o sistema precisa fazer e revela detalhes que mudam a arquitetura, como paginação, idempotência e operações assíncronas. Você não precisa de uma especificação completa; precisa dos endpoints que sustentam os requisitos funcionais.

## Comece pelos recursos

Em REST, pense em substantivos e deixe os verbos HTTP indicarem a ação:

```text
POST   /v1/posts                     cria post
GET    /v1/posts/{post_id}           lê um post
DELETE /v1/posts/{post_id}           remove
GET    /v1/users/{user_id}/feed      feed do usuário
POST   /v1/posts/{post_id}/likes     curte
```

Evite rotas como `/createPost` ou `/getFeedForUser`. Elas funcionam, mas mostram pouca familiaridade com convenções.

Para cada endpoint, mencione rapidamente entrada, saída e códigos de erro relevantes. Não escreva JSON completo de tudo; detalhe só onde houver algo interessante.

## Paginação

Qualquer listagem que pode crescer precisa de paginação. Há duas abordagens:

| Tipo | Como funciona | Problema |
| --- | --- | --- |
| Offset | `?offset=200&limit=50` | Lento em offsets altos; itens pulam ou repetem se a lista muda |
| Cursor | `?cursor=abc&limit=50`, cursor codifica o último item visto | Não permite pular para a página 37 |

Para feeds, mensagens e qualquer coisa ordenada por tempo, use **cursor**. O cursor costuma ser o ID ou timestamp do último item, codificado de forma opaca para o cliente.

```json
{
  "items": [ ... ],
  "next_cursor": "eyJpZCI6IDk4NzY1fQ"
}
```

## Idempotência

Redes falham. O cliente envia um pagamento, a resposta se perde, e ele tenta de novo. Sem cuidado, você cobra duas vezes. A solução é uma **chave de idempotência** gerada pelo cliente:

```text
POST /v1/payments
Idempotency-Key: 7f3c2a1e-...
{ "amount": 4990, "currency": "BRL", "to": "acct_123" }
```

O servidor guarda a chave com o resultado. Se a mesma chave chegar de novo, devolve o resultado salvo sem reexecutar. GET, PUT e DELETE já são idempotentes por definição; POST precisa desse mecanismo quando a operação tem efeito importante.

<Callout type="warning" title="Não esqueça da idempotência em escritas críticas">
Em pagamentos, pedidos, reservas e envio de mensagens, entrevistadores quase sempre perguntam "e se o cliente reenviar?". Ter a chave de idempotência já na API mostra que você pensou nisso antes de ser perguntado.
</Callout>

## Operações longas

Se algo leva segundos ou minutos (transcodificar vídeo, gerar relatório), não segure a conexão. Responda `202 Accepted` com um identificador e permita consultar o estado:

```text
POST /v1/exports          -> 202 { "export_id": "exp_9", "status": "pending" }
GET  /v1/exports/exp_9    -> 200 { "status": "done", "url": "..." }
```

Opcionalmente, notifique por webhook ou push quando terminar.

## Uploads grandes

Não faça o arquivo passar pelo seu servidor de aplicação. O fluxo comum:

1. Cliente pede uma URL de upload: `POST /v1/uploads` com nome e tamanho.
2. Servidor devolve uma URL pré-assinada do object storage.
3. Cliente envia direto para o storage, em partes se for grande.
4. Cliente confirma: `POST /v1/uploads/{id}/complete`.

## Outros detalhes que valem citar

- **Versionamento:** `/v1/` no caminho ou cabeçalho. Permite evoluir sem quebrar clientes antigos.
- **Autenticação:** token no cabeçalho `Authorization`. Não coloque o `user_id` no corpo quando ele pode vir do token; isso evita que alguém aja em nome de outro.
- **Rate limiting:** responda `429` com `Retry-After`.
- **Erros consistentes:** um formato padrão com código e mensagem.
- **Campos parciais:** permitir `?fields=id,title` reduz payload em clientes móveis.

## REST, gRPC ou GraphQL?

Para APIs públicas, REST é a escolha padrão e ninguém vai questionar. Entre serviços internos, gRPC oferece contratos fortes e eficiência. GraphQL faz sentido quando muitos clientes diferentes precisam de recortes diferentes dos mesmos dados. Escolha um, justifique em uma frase e siga.

## Na entrevista

Reserve cerca de cinco minutos. Liste os três a cinco endpoints principais, destaque paginação e idempotência onde couber e siga para o modelo de dados. Follow-ups comuns: como paginar um feed que muda o tempo todo? Como evitar requisições duplicadas? Como versionar sem quebrar apps antigos instalados nos celulares?
