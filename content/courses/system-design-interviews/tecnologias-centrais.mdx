Numa entrevista de system design você não precisa conhecer cinquenta produtos. Precisa conhecer bem uns dez a quinze, saber em que categoria cada um se encaixa e conseguir justificar a escolha em uma ou duas frases. Este módulo percorre as tecnologias que mais aparecem nas discussões. Antes de entrar em cada uma, vale montar o mapa geral.

## Por que nomear tecnologias

Desenhar uma caixa escrita "banco de dados" é aceitável no primeiro minuto, mas logo o entrevistador vai querer saber qual. Nomear uma tecnologia concreta traz consigo um conjunto de garantias e limites conhecidos. Quando você diz "Cassandra particionada por `user_id`", o entrevistador entende imediatamente que as escritas são baratas, que as leituras precisam conhecer a partição e que joins estão fora de cogitação. Uma palavra substitui um parágrafo.

O risco oposto é citar tecnologia sem saber o que ela garante. "Vou usar Kafka" seguido de "e ele entrega cada mensagem exatamente uma vez para o meu serviço de e-mail" revela uma lacuna. Melhor escolher menos peças e conhecer cada uma de verdade.

## O mapa por categoria

| Categoria | Opção padrão | Alternativas | Quando a alternativa ganha |
| --- | --- | --- | --- |
| Banco relacional | PostgreSQL | MySQL | Ecossistema existente, replicação muito testada em web de grande porte |
| Documento | MongoDB | Postgres com JSONB | Esquema muito variável e times que querem modelar por agregado |
| Chave-valor gerenciado | DynamoDB | Cassandra | Multi-nuvem, controle fino, volume de escrita gigantesco |
| Cache em memória | Redis | Memcached | Cache puro, multithread, sem estruturas ricas |
| Busca | Elasticsearch | Busca nativa do banco | Volume pequeno e consultas simples |
| Log de eventos | Kafka | Kinesis, Pulsar | Gerenciado na AWS ou necessidade de multi-tenant forte |
| Fila de tarefas | SQS | RabbitMQ | Roteamento complexo, prioridade, on-premise |
| Stream processing | Flink | Spark Structured Streaming | Time já usa Spark para batch |
| Batch | Spark | Jobs SQL no data warehouse | Transformações simples sobre dados tabulares |
| Objetos | S3 | GCS, Azure Blob | Outra nuvem |
| Computação | Contêineres no Kubernetes | Lambda | Tráfego irregular e funções curtas |
| Coordenação | ZooKeeper | etcd | Ecossistema Kubernetes |
| Borda | Nginx | Envoy, ALB | Service mesh ou balanceador gerenciado |
| Métricas | Prometheus | Datadog, CloudWatch | Preferência por SaaS |

Na prática, "opção padrão" significa a escolha que você consegue defender sem muito esforço na maioria dos cenários. Comece por ela e mude só quando um requisito pedir.

## Uma arquitetura que usa quase tudo

```text
             [Cliente]
                 |
              [CDN] ---- conteúdo estático vindo do S3
                 |
          [Nginx / LB]
                 |
       [Serviços stateless em Kubernetes]
        |        |          |          |
   [Postgres] [Redis]  [Elasticsearch] [Kafka]
        |                               |
   réplicas de leitura         +--------+---------+
                               |        |         |
                           [Flink]   [SQS ->   [Spark diário
                         métricas    workers]   no data lake S3]
                         em tempo
                           real
    [Prometheus] coleta métricas de tudo   [ZooKeeper] coordena Kafka
```

Ninguém espera que você desenhe tudo isso numa entrevista. O objetivo é ver como as peças se relacionam: o banco relacional é a fonte da verdade, o cache acelera leituras, o índice de busca é derivado, o log de eventos espalha mudanças para consumidores que fazem trabalho assíncrono ou analítico.

## Três perguntas para qualquer tecnologia

Ao estudar os próximos capítulos, tente responder sempre:

1. **Qual é o modelo de dados e o padrão de acesso ideal?** Linhas com joins, documentos, pares chave-valor, partições ordenadas, mensagens num log.
2. **O que ela garante?** Consistência forte ou eventual, durabilidade em disco ou só memória, ordem das mensagens, entrega ao menos uma vez.
3. **Onde ela quebra?** Limite de tamanho de item, throughput por partição, custo de joins, dificuldade de fazer consultas não previstas.

Se você souber essas três respostas para cada item da tabela, conseguirá argumentar quase qualquer escolha.

## Números para ter na cabeça

Ordem de grandeza basta. Um único nó de Postgres bem configurado aguenta alguns milhares a dezenas de milhares de transações simples por segundo. Redis atende de 100 mil a centenas de milhares de operações por segundo por nó, com latência abaixo de 1 ms. Uma partição de Kafka sustenta dezenas de MB por segundo. DynamoDB limita cada partição física a cerca de 3.000 unidades de leitura e 1.000 de escrita por segundo. S3 entrega 3.500 PUTs e 5.500 GETs por segundo por prefixo. Esses números ajudam a decidir quando particionar e quando um nó só basta.

<Callout type="tip" title="Escolha chata é boa escolha">
Entrevistadores raramente se impressionam com tecnologia exótica. Se Postgres resolve, diga Postgres. Guarde a criatividade para os pontos em que o requisito realmente força algo diferente.
</Callout>

## Na entrevista

- Nomeie a tecnologia no momento em que a caixa aparece no diagrama e dê o motivo em uma frase.
- Mencione a alternativa que você descartou: "Redis em vez de Memcached porque preciso de sorted sets para o ranking".
- Se não conhece bem uma tecnologia, use a categoria genérica e descreva as propriedades que precisa. É melhor do que inventar comportamento.
- Esteja pronto para o follow-up "e se esse componente cair?". Para cada peça, saiba como ela replica e o que se perde.
