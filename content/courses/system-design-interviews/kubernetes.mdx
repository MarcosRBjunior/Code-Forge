Kubernetes (K8s) é um **orquestrador de containers**. Você descreve o estado desejado ("quero 5 réplicas desta imagem, com 512 MB cada") e ele trabalha continuamente para que a realidade corresponda: agenda containers em máquinas, reinicia os que falham, escala e faz deploys graduais.

## Arquitetura

```text
Control plane                      Nós de trabalho
 ├ API server                       ├ kubelet (roda e vigia os pods)
 ├ etcd (estado do cluster)         ├ kube-proxy (rede dos serviços)
 ├ scheduler (escolhe o nó)         └ container runtime
 └ controllers (reconciliam)
```

O **etcd** guarda o estado desejado; os controllers comparam com o estado real e agem. Esse laço de reconciliação é a ideia central.

## Objetos principais

| Objeto | Função |
| --- | --- |
| Pod | Menor unidade: um ou mais containers que compartilham rede e disco |
| Deployment | Mantém N réplicas de um pod e faz rolling update e rollback |
| Service | IP e nome estáveis que balanceiam entre pods (que mudam de IP) |
| Ingress | Entrada HTTP externa, roteando por host e caminho |
| ConfigMap e Secret | Configuração e segredos injetados nos pods |
| StatefulSet | Pods com identidade e volume estáveis (bancos, filas) |
| HPA | Autoscaling horizontal por CPU ou métricas |
| Job e CronJob | Tarefas únicas ou agendadas |

## O que ele resolve

- **Autorrecuperação:** pod morreu, é recriado; nó morreu, os pods vão para outro.
- **Escala:** o HPA aumenta réplicas sob carga; o cluster autoscaler adiciona nós.
- **Deploy sem parada:** rolling update troca réplicas aos poucos, guiado por **readiness probes**; o rollback é um comando.
- **Descoberta de serviços** e balanceamento embutidos.
- **Uso eficiente** dos recursos com requests e limits.

## Probes

- **Liveness:** o container está vivo? Se não, é reiniciado.
- **Readiness:** pronto para receber tráfego? Se não, sai do Service.

Confundi-las é erro comum: uma readiness que falha por dependência externa lenta tira todos os pods do ar ao mesmo tempo.

## Armadilhas

- **Complexidade operacional:** para poucos serviços, uma plataforma gerenciada (ECS, Cloud Run) pode ser suficiente.
- **Estado:** rodar bancos no cluster exige StatefulSets, volumes e cuidado; muitos times preferem bancos gerenciados.
- **Requests e limits mal definidos** causam despejos (OOMKilled) ou desperdício.
- Pods são efêmeros: nada de depender de IP ou disco local.
- Custo do próprio control plane e da malha de rede.

## Na entrevista

Cite Kubernetes como camada de implantação dos serviços stateless: réplicas atrás de um Service, HPA para picos, rolling update para deploy sem downtime. Não entre em YAML. Follow-ups: o que acontece quando um nó cai (pods reagendados), como evitar derrubar tudo num deploy ruim (readiness, rollout gradual, rollback) e onde ficam os dados com estado.
