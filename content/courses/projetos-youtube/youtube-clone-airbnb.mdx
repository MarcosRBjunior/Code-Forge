**Em uma frase:** um site de aluguel de temporada em que a pessoa escolhe destino, datas e número de hóspedes, vê a lista de acomodações e a localização de cada uma num mapa.

**Nível:** iniciante a intermediário · **Duração do vídeo:** cerca de 4,7 h (gravado ao vivo) · **Canal:** Sonny Sangha (PAPAFAM) · **Publicado em:** outubro de 2022

## Assista

[Let's build a Property Booking App 2.0 with NEXT.JS! (Tailwind, Mapbox, Calendar & Date Picker)](https://www.youtube.com/watch?v=b8gBIphfCqw)

É uma live longa e didática que constrói o front-end de um site de reservas: cabeçalho com busca, banner, cards de destinos, seletor de datas, página de resultados e mapa com Mapbox, com deploy na Vercel. É o mais antigo dos tutoriais desta trilha e o mais acessível: bom para quem está saindo do React básico e quer entender Tailwind e renderização no servidor. O código do autor fica no GitHub indicado na descrição do vídeo (links.papareact.com/github).

## O que você vai construir

- Cabeçalho com logo, barra de busca e ícones (Heroicons).
- Banner de destaque e seções de destinos com cards pequenos e médios, incluindo um carrossel horizontal.
- Dados das seções carregados no servidor a cada requisição (Server Side Rendering com `getServerSideProps`).
- Calendário e seletor de intervalo de datas, com número de hóspedes, que leva à página de busca.
- Página de resultados com a lista de acomodações, filtros visuais e os parâmetros da busca no topo.
- Mapa do Mapbox com um marcador por acomodação e detalhes ao clicar.
- Barra de carregamento entre páginas e rodapé.
- Deploy na Vercel.

Repare no que **não** está no vídeo: não há banco, não há conta de usuário, não há reserva de verdade nem pagamento. As acomodações vêm de um arquivo JSON estático do autor. Isso define o que você vai construir para tornar o projeto seu.

## Stack do vídeo e o que usar hoje

| Camada | No vídeo | Em 2026 |
|---|---|---|
| Framework | Next.js 12/13 com Pages Router e `getServerSideProps` | Next.js 16 com App Router, Server Components e `searchParams` assíncrono |
| Estilo | Tailwind CSS 3 (config em `tailwind.config.js`) | Tailwind CSS 4 (configuração no CSS com `@theme`, plugin do PostCSS separado) |
| Ícones | Heroicons | Heroicons v2 (importações por tamanho, como `@heroicons/react/24/solid`) ou Lucide |
| Datas | Biblioteca de calendário de intervalo (provavelmente `react-date-range`) | `react-day-picker` (base do componente de calendário do shadcn/ui) ou a mesma biblioteca, se mantida |
| Mapa | `react-map-gl` com Mapbox GL JS | `react-map-gl` 8 (importação de `react-map-gl/mapbox` ou `react-map-gl/maplibre`) com Mapbox GL JS 3, ou MapLibre com tiles gratuitos |
| Imagens | `next/image` com as props da época | `next/image` com `fill` e `sizes`; domínios externos em `images.remotePatterns` |
| Dados | JSON estático hospedado pelo autor | Seu próprio banco (Postgres com Prisma ou Drizzle) |
| Deploy | Vercel | Vercel ou qualquer hospedagem de Next.js |

<Callout type="warning" title="O que mudou desde a gravação">
**Pages Router versus App Router.** O vídeo usa `pages/` e `getServerSideProps`. No App Router (padrão em projetos novos) isso não existe: a página é um Server Component `async` que busca os dados direto, e os parâmetros da URL chegam em `searchParams`, que no Next 15 em diante é uma Promise (`const { location } = await searchParams`). Componentes com estado, como o seletor de datas e o mapa, precisam de `"use client"` no topo do arquivo.

**`next/image`.** Se o vídeo usar `layout="fill"` e `objectFit`, essas props foram removidas: hoje é `fill` com a classe `object-cover` do Tailwind. Imagens de domínios externos exigem `images.remotePatterns` no `next.config`, senão a imagem não carrega.

**Tailwind 4.** Não existe mais `tailwind.config.js` por padrão nem as diretivas `@tailwind base`; é `@import "tailwindcss"` no CSS. Plugins como o de esconder a barra de rolagem podem ter mudado ou virado utilitário próprio.

**Mapbox.** `react-map-gl` mudou de versão e a forma de importar mudou junto. O token público do Mapbox continua necessário; crie um token com restrição de URL para o seu domínio.

**Dados do autor.** Os JSON hospedados pelo autor podem estar fora do ar quando você assistir. Tenha seus próprios dados desde o começo.

Dois caminhos: seguir o vídeo com as versões do `package.json` do repositório do autor (Pages Router, Tailwind 3) e depois migrar para o App Router como exercício, ou já começar no Next 16 traduzindo cada trecho, com a documentação aberta. O segundo é mais lento, mas ensina mais e evita um projeto que nasce desatualizado.
</Callout>

## Roteiro de estudo

O vídeo é uma live: tem conversa, perguntas do chat e pausas. Use a velocidade 1,25x ou 1,5x nas partes de conversa e volte ao normal quando o código começar. Antes de cada bloco, tente montar o componente sozinho olhando só o design final; depois compare.

### 1. Projeto e plano (00:00 a 18:57)

Stack, demonstração, criação do projeto com Tailwind, explicação do Tailwind e planejamento da construção.

- **O que construir:** o projeto criado e no ar na Vercel já no primeiro dia, com uma página em branco estilizada.
- **Conceito:** Tailwind é CSS utilitário: em vez de inventar nomes de classe, você compõe estilos no próprio JSX. O planejamento do vídeo quebra a página em componentes antes de escrever código.
- **Responda sozinho:** desenhe a árvore de componentes da home antes de ver como o autor faz. Quais componentes se repetem com dados diferentes?

### 2. Cabeçalho, busca e banner (18:57 a 1:12:28)

Componente de cabeçalho, barra de busca com Heroicons e banner.

- **O que construir:** um cabeçalho fixo e responsivo, com a barra de busca centralizada, e um banner com imagem de fundo.
- **Conceito:** layout com grid e flexbox, `sticky`, breakpoints do Tailwind (`md:`, `lg:`) e `next/image` ocupando o contêiner.
- **Responda sozinho:** como o cabeçalho se comporta numa tela de 360 px? A busca continua usável com teclado?

### 3. Renderização no servidor e cards (a partir de 1:12:28)

Explicação e implementação de SSR, card pequeno e as seções seguintes de cards.

- **O que construir:** as seções da home preenchidas com dados buscados no servidor.
- **Conceito:** no vídeo, `getServerSideProps` busca os dados a cada requisição e entrega como props. No App Router, a página `async` faz o `fetch` direto, e você escolhe se o resultado é cacheado ou dinâmico.
- **Responda sozinho:** esses dados mudam a cada visita? Se não mudam, SSR a cada requisição é a melhor escolha, ou daria para gerar a página estática e revalidar de tempos em tempos?

### 4. Datas e página de busca (segunda metade do vídeo)

Seletor de intervalo de datas, número de hóspedes e a página de resultados.

- **O que construir:** a busca que leva para `/search?location=...&startDate=...&endDate=...&guests=...` e uma página que lê esses parâmetros e lista as acomodações.
- **Conceito:** a URL como estado. Guardar a busca nos parâmetros permite compartilhar o link, voltar no navegador e recarregar a página sem perder nada.
- **Responda sozinho:** o que acontece se alguém abrir a URL com `endDate` antes de `startDate`, ou com `guests=-3`? Onde essa validação deveria ficar?

### 5. Mapa e acabamento (fim do vídeo)

Mapa do Mapbox com marcadores, barra de carregamento, rodapé e deploy.

- **O que construir:** o mapa ao lado da lista, centrado nas acomodações encontradas, com popup ao clicar no marcador.
- **Conceito:** bibliotecas de mapa usam `window` e WebGL, então rodam só no cliente. Calcular o centro a partir das coordenadas dos resultados evita um mapa fixo numa cidade.
- **Responda sozinho:** se a busca não tiver resultados, o que o mapa mostra? E a página continua leve no celular com o mapa carregado?

## Torne o projeto seu

O vídeo entrega uma vitrine bonita, mas sem nenhuma regra de negócio. É exatamente aí que você se diferencia: um avaliador vê o mesmo cabeçalho e os mesmos cards em dezenas de portfólios, e quase nunca vê um sistema de reservas que não aceita reserva duplicada.

**Nome e identidade próprios.** "Airbnb" é marca registrada: use outro nome, outro logo, outra paleta e outra tipografia no projeto publicado. Use fotos suas, de bancos de imagem com licença livre (com a atribuição pedida) ou geradas por você, nunca fotos copiadas de anúncios reais. Um nicho ajuda: chalés na serra, casas para trabalho remoto, hospedagem que aceita pets.

**Uma feature que o vídeo não tem.** O caminho natural é transformar a vitrine em produto:

- **Banco de dados próprio.** Tabelas de acomodações, fotos, disponibilidade e reservas em Postgres, com dados de exemplo criados por um script de seed seu.
- **Reserva de verdade sem duplicidade.** Ao reservar, o servidor confere a disponibilidade dentro de uma transação. No Postgres, uma restrição de exclusão com intervalo de datas (`EXCLUDE USING gist` sobre `daterange`) faz o próprio banco recusar duas reservas sobrepostas para a mesma acomodação, mesmo com dois cliques simultâneos.
- **Contas e papéis.** Hóspede reserva e vê as próprias reservas; anfitrião cadastra acomodações, bloqueia datas e vê quem reservou.
- **Calendário de disponibilidade.** Datas ocupadas aparecem desabilitadas no seletor, e o preço total é calculado no servidor (diárias, taxa de limpeza, noites mínimas).
- **Pagamento em modo de teste** com Stripe Checkout, confirmando a reserva só depois do webhook.
- **Busca no mapa.** Ao mover o mapa, a lista mostra só o que está dentro da área visível, consultando o banco por coordenadas.

**Testes.** Teste a regra que mais importa: duas reservas sobrepostas para a mesma acomodação não podem existir. Um teste de integração que dispara as duas ao mesmo tempo contra um banco real e espera que uma falhe vale mais que dez testes de componente. Some testes do cálculo de preço e um teste de ponta a ponta (Playwright) do fluxo buscar, escolher e reservar.

**Tratamento de erros.** Datas inválidas na URL, acomodação inexistente (página 404 de verdade), mapa que não carrega, reserva recusada porque alguém foi mais rápido: cada caso com mensagem clara e sem quebrar a página.

**Acessibilidade.** O seletor de datas precisa funcionar com teclado e leitor de tela. Imagens com `alt` descritivo, carrossel com controles acessíveis, contraste adequado e foco visível. Rode o Lighthouse e corrija o que ele apontar.

**Segurança.**

- Toda ação que grava (reservar, cancelar, cadastrar acomodação) confere no servidor quem é o usuário e se ele pode fazer aquilo. Esconder o botão na UI não é autorização.
- Valide os parâmetros de busca e os dados de reserva com Zod no servidor.
- O preço vem do servidor, nunca do formulário.
- O token do Mapbox é público por natureza: restrinja por URL. Chaves do banco e do Stripe ficam só em variáveis de ambiente do servidor, com um `.env.example` no repositório.

**README com decisões.** Modelo de dados com o diagrama das tabelas, como a reserva duplicada é impedida, por que App Router e Server Components, o que veio do tutorial e o que você construiu. Dê crédito ao vídeo: o avaliador vai reconhecer o layout, e o que conta é o que você somou.

## Armadilhas comuns

- **Mapa quebrando no servidor.** Importar o mapa num Server Component gera erro de `window is not defined`. Isole o mapa num componente com `"use client"` e, se preciso, carregue com `next/dynamic` e `ssr: false`.
- **CSS do Mapbox esquecido.** Sem importar a folha de estilo do Mapbox GL, marcadores e controles aparecem fora do lugar.
- **Token do Mapbox na Vercel.** O token funciona local e some em produção porque a variável não foi cadastrada no painel, ou porque a restrição de URL não inclui o domínio do deploy (e os de preview).
- **Datas e fuso horário.** Uma data salva como meia-noite em UTC aparece como o dia anterior no Brasil. Para reservas, trate check-in e check-out como datas sem hora (`date` no Postgres) e formate com cuidado.
- **Imagens externas bloqueadas.** `next/image` recusa domínios que não estão em `remotePatterns`. O erro aparece no console, não na tela.
- **Seguir o vídeo misturando versões.** Copiar código do Pages Router num projeto App Router gera erros confusos. Decida o caminho antes de começar.
