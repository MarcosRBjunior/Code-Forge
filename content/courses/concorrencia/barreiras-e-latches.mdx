Muitos problemas concorrentes não giram em torno de proteger um dado, e sim de **coordenar momentos**: "só comece a atender requisições depois que cache, banco e configuração estiverem prontos" ou "nenhuma thread passa para a etapa 2 da simulação antes de todas terminarem a etapa 1". Dá para montar isso com locks e variáveis de condição, mas duas primitivas prontas expressam a intenção de forma direta: o **latch** e a **barreira**.

## Latch: esperar N eventos uma vez

Um latch de contagem (o `CountDownLatch` do Java) começa com um número N. Threads chamam `count_down()` quando terminam sua parte; quem chama `wait()` fica bloqueado até a contagem chegar a zero. Depois disso, ele fica aberto para sempre: é de uso único.

```text
N = 3       servico A --count_down--> 2
            servico B --count_down--> 1
            servico C --count_down--> 0  ==> main acorda
main: wait() .........................|---> segue
```

O papel típico é "a thread principal espera os trabalhadores", mas o inverso também é comum: um latch com N = 1 funcionando como **sinal de largada**, em que vários trabalhadores esperam e a principal faz um único `count_down()` para soltar todos ao mesmo tempo, algo útil em testes de carga.

Python não tem `CountDownLatch`, mas ele cabe em poucas linhas com `threading.Condition`:

<CodeTabs>

```python
import threading

class CountDownLatch:
    def __init__(self, contagem):
        self.contagem = contagem
        self.cond = threading.Condition()

    def count_down(self):
        with self.cond:
            if self.contagem > 0:
                self.contagem -= 1
                if self.contagem == 0:
                    self.cond.notify_all()

    def wait(self):
        with self.cond:
            self.cond.wait_for(lambda: self.contagem == 0)

servicos = ["banco", "cache", "config"]
latch = CountDownLatch(len(servicos))
prontos = []
trava = threading.Lock()

def iniciar(nome):
    with trava:
        prontos.append(nome)
    latch.count_down()

for nome in servicos:
    threading.Thread(target=iniciar, args=(nome,)).start()

latch.wait()
print("prontos:", sorted(prontos))
print("contagem final:", latch.contagem)
print("servidor aceitando requisicoes")
```

```java
import java.util.*;
import java.util.concurrent.CountDownLatch;

// Java já traz o CountDownLatch pronto, sem precisar montá-lo com condição
static final List<String> servicos = List.of("banco", "cache", "config");
static final CountDownLatch latch = new CountDownLatch(servicos.size());
static final List<String> prontos = new ArrayList<>();
static final Object trava = new Object();

static void iniciar(String nome) {
    synchronized (trava) {
        prontos.add(nome);
    }
    latch.countDown();
}

public static void main(String[] args) throws InterruptedException {
    for (String nome : servicos) {
        new Thread(() -> iniciar(nome)).start();
    }

    latch.await();
    Collections.sort(prontos);
    System.out.println("prontos: " + prontos);
    System.out.println("contagem final: " + latch.getCount());
    System.out.println("servidor aceitando requisicoes");
}
```

```go
var servicos = []string{"banco", "cache", "config"}
var latch sync.WaitGroup
var prontos []string

	trava.Lock()
	prontos = append(prontos, nome)
	trava.Unlock()
	latch.Done()
}

func main() {
	latch.Add(len(servicos))
	for _, nome := range servicos {
		go iniciar(nome)
	}

	latch.Wait()
	sort.Strings(prontos)
	fmt.Println("prontos:", prontos)
	// WaitGroup não expõe a contagem; Wait só retorna quando ela chega a zero
	fmt.Println("contagem final:", 0)
	fmt.Println("servidor aceitando requisicoes")
}
```

Em Go, o equivalente é `sync.WaitGroup` (`Add`, `Done`, `Wait`). Em C++20 existe `std::latch`. Em Python, se as tarefas estão num executor, esperar os futures (`concurrent.futures.wait`) ou simplesmente fazer `join` nas threads costuma bastar; o latch brilha quando quem sinaliza não é quem termina, por exemplo uma thread que continua viva depois de avisar que inicializou.

## Barreira: ponto de encontro reutilizável

A barreira é simétrica: N threads chamam `wait()` e **todas** ficam presas até a última chegar. Aí todas são liberadas juntas e a barreira se rearma para a próxima rodada. Isso a torna natural para algoritmos em fases, como simulações em grade, processamento em lotes ou cálculo paralelo iterativo, em que cada fase lê o que todas produziram na anterior.

`threading.Barrier(n, action=f)` aceita uma ação que roda uma vez por rodada, numa das threads, depois que todas chegam e antes de qualquer uma ser liberada. É o lugar certo para consolidar resultados da fase.

<CodeTabs>

```python
import threading

N = 3
parciais = [0] * N
totais = [None] * N
log = []

def fim_de_fase():
    log.append(f"fase {len(log) + 1} concluida, parciais={parciais}")

barreira = threading.Barrier(N, action=fim_de_fase)

def trabalhador(i):
    # fase 1: cada thread calcula sua parte
    parciais[i] = (i + 1) * 10
    barreira.wait()
    # fase 2: todas leem o resultado de todas
    totais[i] = sum(parciais)
    barreira.wait()

threads = [threading.Thread(target=trabalhador, args=(i,)) for i in range(N)]
for t in threads:
    t.start()
for t in threads:
    t.join()
for linha in log:
    print(linha)
print("totais vistos por cada thread:", totais)
```

```java
import java.util.*;
import java.util.concurrent.CyclicBarrier;

static final int N = 3;
static final int[] parciais = new int[N];
static final int[] totais = new int[N];
static final List<String> log = new ArrayList<>();

static void fimDeFase() {
    log.add("fase " + (log.size() + 1) + " concluida, parciais=" + Arrays.toString(parciais));
}

static final CyclicBarrier barreira = new CyclicBarrier(N, () -> fimDeFase());

static void trabalhador(int i) {
    try {
        // fase 1: cada thread calcula sua parte
        parciais[i] = (i + 1) * 10;
        barreira.await();
        // fase 2: todas leem o resultado de todas
        totais[i] = Arrays.stream(parciais).sum();
        barreira.await();
    } catch (Exception e) {  // InterruptedException ou BrokenBarrierException
        throw new RuntimeException(e);
    }
}

public static void main(String[] args) throws InterruptedException {
    List<Thread> threads = new ArrayList<>();
    for (int i = 0; i < N; i++) {
        int id = i;
        threads.add(new Thread(() -> trabalhador(id)));
    }
    for (Thread t : threads) t.start();
    for (Thread t : threads) t.join();
    for (String linha : log) {
        System.out.println(linha);
    }
    System.out.println("totais vistos por cada thread: " + Arrays.toString(totais));
}
```

```go
import (
	"fmt"
	"sync"
)

// Go não tem barreira na biblioteca padrão: este é o equivalente mínimo, com sync.Cond
type Barreira struct {
	mu       sync.Mutex
	cond     *sync.Cond
	n        int
	chegaram int
	rodada   int
	acao     func()
}

func NovaBarreira(n int, acao func()) *Barreira {
	b := &Barreira{n: n, acao: acao}
	b.cond = sync.NewCond(&b.mu)
	return b
}

func (b *Barreira) wait() {
	b.mu.Lock()
	defer b.mu.Unlock()
	rodada := b.rodada
	b.chegaram++
	if b.chegaram == b.n {
		b.acao() // a última a chegar roda a ação, antes de qualquer uma ser liberada
		b.chegaram = 0
		b.rodada++ // rearma para a próxima rodada
		b.cond.Broadcast()
		return
	}
	for rodada == b.rodada {
		b.cond.Wait()
	}
}

const N = 3

var parciais = make([]int, N)
var totais = make([]int, N)
var log []string

func fimDeFase() {
	log = append(log, fmt.Sprintf("fase %d concluida, parciais=%v", len(log)+1, parciais))
}

var barreira = NovaBarreira(N, fimDeFase)

func trabalhador(i int, wg *sync.WaitGroup) {
	defer wg.Done()
	// fase 1: cada goroutine calcula sua parte
	parciais[i] = (i + 1) * 10
	barreira.wait()
	// fase 2: todas leem o resultado de todas
	soma := 0
	for _, p := range parciais {
		soma += p
	}
	totais[i] = soma
	barreira.wait()
}

func main() {
	var wg sync.WaitGroup
	for i := 0; i < N; i++ {
		wg.Add(1)
		go trabalhador(i, &wg)
	}
	wg.Wait()
	for _, linha := range log {
		fmt.Println(linha)
	}
	fmt.Println("totais vistos por cada thread:", totais)
}
```

Sem a barreira, uma thread rápida poderia somar `parciais` antes de as outras escreverem e cada uma veria um total diferente. Em Java a classe é `CyclicBarrier`; `Phaser` generaliza para um número de participantes que muda entre fases.

## Comparando

| | Latch | Barreira |
| --- | --- | --- |
| Quem espera | Um ou mais observadores | Os próprios participantes |
| Quem sinaliza | Qualquer thread, N vezes | Cada participante, ao chegar |
| Reuso | Uso único | Rearma a cada rodada |
| Uso típico | Inicialização, sinal de largada | Algoritmos em fases |

## Armadilhas

- **Participante que nunca chega.** Se uma thread lança exceção antes do `wait()` da barreira, as outras ficam presas para sempre. Em Python, `Barrier.abort()` e o parâmetro `timeout` fazem as demais receberem `BrokenBarrierError`; em Java o comportamento é análogo. Sempre trate esse caminho.
- **Contagem errada.** Um latch com N maior que o número de `count_down()` reais nunca abre. Prefira derivar N da lista de tarefas, não de uma constante.
- **Reusar latch.** Ele não volta ao valor inicial. Se precisa de rodadas, é barreira.

<Callout type="tip" title="Escolha pela pergunta">
"Alguém espera que N coisas aconteçam?" é latch. "N threads precisam se esperar mutuamente, repetidas vezes?" é barreira.
</Callout>

## Na entrevista

Essas primitivas aparecem como peça de problemas maiores: "inicie o servidor só depois de carregar tudo", "dispare 100 requisições ao mesmo tempo para testar concorrência", "simule o jogo da vida com várias threads". Nomeie a primitiva, diga se precisa de reuso e trate a falha de um participante. Follow-ups comuns: "como implementar um latch com o que a linguagem oferece?" (contador mais variável de condição, como acima) e "o que acontece se uma das threads morrer antes da barreira?" (barreira quebrada, timeout ou abort).
