Um servidor que atende 10 mil conexões passa quase todo o tempo esperando: rede, banco, disco. Criar uma thread por conexão custa memória (cada pilha ocupa de centenas de KB a alguns MB) e trocas de contexto no kernel. A alternativa é a **concorrência cooperativa**: uma única thread roda um **event loop** que alterna entre muitas tarefas leves, e cada tarefa devolve o controle sempre que vai esperar por I/O.

## Como funciona

Uma função declarada com `async def` é uma **corrotina**: chamá-la não executa nada, só cria um objeto que pode ser pausado e retomado. Dentro dela, `await` marca os pontos de pausa. Quando a corrotina chega a um `await` de algo que ainda não está pronto, ela devolve o controle ao loop, que escolhe outra tarefa pronta para rodar.

```text
 event loop (1 thread)
 ┌──────────────────────────────────────────────┐
 │ prontas: [A, B]   esperando I/O: [C (socket)] │
 └──────────────────────────────────────────────┘
   roda A até o próximo await ─► A vai esperar
   roda B até o próximo await ─► B vai esperar
   socket de C ficou pronto   ─► C volta para prontas
```

O loop usa o mecanismo do sistema operacional (epoll, kqueue, IOCP) para saber quais operações de I/O terminaram. Como só uma tarefa roda por vez e a troca só acontece em `await`, o código entre dois `await` é atômico em relação às outras tarefas. Isso elimina boa parte das condições de corrida, mas não todas: qualquer leitura e escrita separadas por um `await` ainda podem se intercalar com outra tarefa.

O mesmo modelo aparece em JavaScript (`Promise` e `async/await` no event loop do Node), em C# (`Task`), em Rust (`Future` com runtimes como Tokio) e em Kotlin (corrotinas). Go segue outro caminho: goroutines parecem código bloqueante, mas o runtime as multiplexa sobre poucas threads do SO. Java 21 tem **virtual threads** com a mesma ideia.

## Exemplo: esperas sobrepostas

Três "requisições" de 0,2 s cada. Executadas em sequência levariam 0,6 s; com `asyncio.gather`, as esperas se sobrepõem. O programa compara o tempo total com essa soma das esperas e imprime só o booleano, em vez do tempo, para a saída ser estável.

<CodeTabs>

```python
import asyncio
import time

async def buscar(nome, atraso):
    await asyncio.sleep(atraso)      # simula I/O e devolve o controle ao loop
    return f"{nome}: ok"

async def main():
    inicio = time.perf_counter()
    respostas = await asyncio.gather(
        buscar("usuarios", 0.2),
        buscar("pedidos", 0.2),
        buscar("estoque", 0.2),
    )
    total = time.perf_counter() - inicio
    for r in respostas:              # gather preserva a ordem dos argumentos
        print(r)
    print("mais rápido que as 3 esperas em série:", total < 3 * 0.2)

asyncio.run(main())
```

```java
import java.util.*;
import java.util.concurrent.*;

// Java não tem async/await: a composição de CompletableFuture faz o papel de "continuar depois da espera".
// O que muda: não há event loop de uma thread. As continuações rodam em threads de um pool, possivelmente
// em paralelo, então o trecho entre duas esperas NÃO é atômico como em asyncio.
static CompletableFuture<String> buscar(String nome, long atrasoMs) {
    // delayedExecutor agenda sem ocupar uma thread por tarefa durante a espera
    Executor depois = CompletableFuture.delayedExecutor(atrasoMs, TimeUnit.MILLISECONDS);
    return CompletableFuture.supplyAsync(() -> nome + ": ok", depois);
}

public static void main(String[] args) {
    long inicio = System.nanoTime();
    List<CompletableFuture<String>> tarefas = List.of(
        buscar("usuarios", 200),
        buscar("pedidos", 200),
        buscar("estoque", 200)
    );
    CompletableFuture.allOf(tarefas.toArray(new CompletableFuture[0])).join();  // aqui a thread main bloqueia de verdade
    double total = (System.nanoTime() - inicio) / 1e9;
    for (CompletableFuture<String> r : tarefas) {  // a lista preserva a ordem dos argumentos
        System.out.println(r.join());
    }
    System.out.println("mais rápido que as 3 esperas em série: " + (total < 3 * 0.2 ? "True" : "False"));
}
```

```cpp
#include <chrono>
#include <future>
#include <iostream>
#include <string>
#include <thread>
#include <vector>
using namespace std;

// O C++20 tem co_await, mas a biblioteca padrão não traz event loop para usá-lo.
// O que muda: com std::async, cada chamada ganha uma thread do SO que BLOQUEIA durante a espera.

int main() {
    auto inicio = chrono::steady_clock::now();
    vector<future<string>> tarefas;
    tarefas.push_back(async(launch::async, buscar, "usuarios", chrono::milliseconds(200)));
    tarefas.push_back(async(launch::async, buscar, "pedidos", chrono::milliseconds(200)));
    tarefas.push_back(async(launch::async, buscar, "estoque", chrono::milliseconds(200)));
    vector<string> respostas;
    for (auto& t : tarefas) respostas.push_back(t.get());   // ler na ordem preserva a ordem dos argumentos
    chrono::duration<double> total = chrono::steady_clock::now() - inicio;
    for (auto& r : respostas) cout << r << endl;
```

```csharp
using System;
using System.Diagnostics;
using System.Threading.Tasks;

// C# tem async/await de verdade. O que muda: num programa de console não há event loop de uma thread.
// Depois do await, o código continua numa thread do pool, então duas tarefas podem rodar em paralelo
// e o trecho entre dois awaits NÃO é atômico como em asyncio.
static async Task<string> Buscar(string nome, int atraso)
{
    await Task.Delay(atraso);        // simula I/O e libera a thread
    return nome + ": ok";
}

static async Task Principal()
{
    Stopwatch inicio = Stopwatch.StartNew();
    string[] respostas = await Task.WhenAll(
        Buscar("usuarios", 200),
        Buscar("pedidos", 200),
        Buscar("estoque", 200)
    );
    double total = inicio.Elapsed.TotalSeconds;
    foreach (string r in respostas)  // WhenAll preserva a ordem dos argumentos
    {
        Console.WriteLine(r);
    }
    Console.WriteLine("mais rápido que as 3 esperas em série: " + (total < 3 * 0.2));
}

static void Main()
{
    Principal().Wait();
}
```

```go
import (
	"fmt"
	"sync"
	"time"
)

// Go não tem async/await: cada tarefa é uma goroutine com código no estilo bloqueante.
// O que muda: não existe "await" nem cor de função. O runtime troca as goroutines sozinho sobre
// poucas threads do SO, possivelmente em paralelo, então o estado compartilhado precisa de proteção.
func buscar(nome string, atraso time.Duration) string {
	time.Sleep(atraso) // simula I/O; pausa só esta goroutine, não a thread do SO
	return nome + ": ok"
}

func main() {
	inicio := time.Now()
	nomes := []string{"usuarios", "pedidos", "estoque"}
	respostas := make([]string, len(nomes))
	var wg sync.WaitGroup
	for i, nome := range nomes {
		wg.Add(1)
		go func(i int, nome string) {
			defer wg.Done()
			respostas[i] = buscar(nome, 200*time.Millisecond) // cada goroutine escreve na própria posição
		}(i, nome)
	}
	wg.Wait()
	total := time.Since(inicio).Seconds()
	for _, r := range respostas { // as posições preservam a ordem dos argumentos
		fmt.Println(r)
	}
	if total < 3*0.2 {
		fmt.Println("mais rápido que as 3 esperas em série: True")
	} else {
		fmt.Println("mais rápido que as 3 esperas em série: False")
	}
}
```

## Limitar concorrência e não bloquear o loop

Disparar mil tarefas de uma vez pode derrubar o serviço do outro lado. Um `asyncio.Semaphore` limita quantas rodam simultaneamente. E qualquer chamada **bloqueante** (como `time.sleep`, uma biblioteca de banco síncrona ou um cálculo pesado) trava o loop inteiro, porque não há `await` para ceder o controle. Para esses casos, use `asyncio.to_thread`, que roda a função num pool de threads.

```python
import asyncio
import time

limite = asyncio.Semaphore(2)
ativas = 0
pico = 0

async def baixar(i):
    global ativas, pico
    async with limite:               # no máximo 2 dentro deste bloco
        ativas += 1
        pico = max(pico, ativas)
        await asyncio.sleep(0.05)
        ativas -= 1
        return i * 10

def calculo_bloqueante(n):
    time.sleep(0.05)                 # bloquearia o loop se chamado direto
    return sum(range(n))

async def main():
    resultados = await asyncio.gather(*(baixar(i) for i in range(6)))
    print("resultados:", resultados)
    print("pico de concorrencia:", pico)
    soma = await asyncio.to_thread(calculo_bloqueante, 101)
    print("soma em outra thread:", soma)

asyncio.run(main())
```

```text
Saída:
resultados: [0, 10, 20, 30, 40, 50]
pico de concorrencia: 2
soma em outra thread: 5050
```

Repare que `ativas += 1` não precisa de lock: entre a leitura e a escrita não há `await`, então nenhuma outra tarefa roda no meio.

## Armadilhas e trade-offs

- **Esquecer o `await`**: `buscar("x", 1)` sem `await` só cria a corrotina; nada acontece e o Python avisa que ela nunca foi aguardada.
- **Bloquear o loop**: um `requests.get` ou `time.sleep` dentro de `async def` congela todas as tarefas.
- **Contaminação**: quem chama uma função assíncrona também precisa ser assíncrono ("colored functions").
- **CPU**: async não acelera cálculo. Ele brilha com muito I/O e pouca CPU; para CPU, use processos.
- **Tarefas soltas**: `create_task` sem guardar a referência pode deixar exceções sem tratamento. Prefira `gather` ou `asyncio.TaskGroup`.

| Modelo | Troca de contexto | Custo por unidade | Bom para |
| --- | --- | --- | --- |
| Threads do SO | Preemptiva, kernel | Alto | Código bloqueante, CPU em linguagens sem GIL |
| async/await | Cooperativa, em `await` | Muito baixo | Milhares de conexões de I/O |
| Goroutines/virtual threads | Runtime | Baixo | I/O com código no estilo bloqueante |

<Callout type="warning" title="Async não é paralelismo">
Com um único event loop, só uma corrotina executa por vez. Você ganha sobreposição de esperas, não uso de vários núcleos.
</Callout>
