Uma condição de corrida acontece quando o resultado de um programa depende da ordem em que threads intercalam operações sobre um estado compartilhado. Com uma ordem o resultado está certo, com outra está errado, e você não controla qual ordem o escalonador escolhe. É o bug mais comum em código concorrente e também o mais traiçoeiro: passa nos testes, roda bem por semanas e quebra em produção sob carga.

## O padrão ler-modificar-escrever

O exemplo clássico é `contador += 1`. Parece uma operação só, mas a máquina faz três passos: lê o valor, soma um e grava de volta. Se duas threads intercalam esses passos, um incremento some:

```text
contador = 5

Thread A                 Thread B
lê 5
                         lê 5
soma -> 6
                         soma -> 6
grava 6
                         grava 6

resultado: 6 (deveria ser 7)
```

Esse é o **lost update**. Em Python, `+=` sobre um atributo vira várias instruções de bytecode, e o interpretador pode trocar de thread entre elas. O GIL não resolve isso: ele protege as estruturas internas do interpretador, não a sua lógica. Em Java, `count++` num `int` comum tem exatamente o mesmo problema; em Go, o `go test -race` acusa esse padrão na hora.

O código abaixo tem a corrida. Ele não é executado aqui porque o resultado varia de rodada para rodada, às vezes certo, às vezes menor que o esperado:

```python
# Versão com corrida: NÃO use
contador = 0

def trabalhar():
    global contador
    for _ in range(100_000):
        contador += 1  # ler, somar e gravar podem ser intercalados

# 4 threads rodando trabalhar() podem terminar com menos de 400000
```

## A correção: seção crítica

A solução é transformar os três passos numa **seção crítica**, um trecho que só uma thread executa por vez. A ferramenta básica é o lock:

<CodeTabs>

```python
import threading

class Contador:
    def __init__(self):
        self.valor = 0
        self._lock = threading.Lock()

    def incrementar(self):
        with self._lock:  # ler, somar e gravar acontecem sem interrupção
            self.valor += 1

def trabalhar(contador, n):
    for _ in range(n):
        contador.incrementar()

c = Contador()
threads = [threading.Thread(target=trabalhar, args=(c, 100_000)) for _ in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print("esperado:", 4 * 100_000)
print("obtido:", c.valor)
```

```java
import java.util.*;

static class Contador {
    int valor = 0;

        }

    for (Thread t : threads) t.join();

    System.out.println("esperado: " + 4 * 100_000);
    System.out.println("obtido: " + c.valor);
}
```

```cpp
}
```

## O padrão verificar-e-agir

A segunda forma clássica é **check-then-act**: você verifica uma condição e age com base nela, mas outra thread muda o estado entre a verificação e a ação. Exemplos: "se o saldo é suficiente, saque", "se a chave não está no cache, calcule e insira", "se o arquivo não existe, crie". Duas threads verificam ao mesmo tempo, ambas veem "pode" e ambas agem.

A correção é a mesma ideia: a verificação e a ação precisam estar dentro da mesma seção crítica.

<CodeTabs>

```python
import threading

class Conta:
    def __init__(self, saldo):
        self.saldo = saldo
        self._lock = threading.Lock()

    def sacar(self, valor):
        with self._lock:
            if self.saldo >= valor:  # verificar...
                self.saldo -= valor  # ...e agir, sem ninguém no meio
                return True
            return False

conta = Conta(100)
resultados = []
resultados_lock = threading.Lock()

def cliente():
    ok = conta.sacar(30)
    with resultados_lock:
        resultados.append(ok)

threads = [threading.Thread(target=cliente) for _ in range(10)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print("saques aprovados:", resultados.count(True))
print("saques negados:", resultados.count(False))
print("saldo final:", conta.saldo)
```

```java
static class Conta {

        }

        resultados.add(ok);

}
```

```go
import (
	"fmt"
	"sync"
)

type Conta struct {
	saldo int
	lock  sync.Mutex
}

func (c *Conta) Sacar(valor int) bool {
	c.lock.Lock()
	defer c.lock.Unlock()
	if c.saldo >= valor { // verificar...
		c.saldo -= valor // ...e agir, sem ninguém no meio
		return true
	}
	return false
}

func main() {
	conta := &Conta{saldo: 100}
	var resultados []bool
	var resultadosLock sync.Mutex

	var wg sync.WaitGroup
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			ok := conta.Sacar(30)
			resultadosLock.Lock()
			defer resultadosLock.Unlock()
			resultados = append(resultados, ok)
		}()
	}
	wg.Wait()

	aprovados, negados := 0, 0
	for _, ok := range resultados {
		if ok {
			aprovados += 1
		} else {
			negados += 1
		}
	}
	fmt.Println("saques aprovados:", aprovados)
	fmt.Println("saques negados:", negados)
	fmt.Println("saldo final:", conta.saldo)
}
```

```text
saques negados: 7
```

Sem o lock dentro de `sacar`, quatro ou mais saques poderiam ser aprovados e o saldo ficaria negativo.

<Callout type="warning" title="Data race não é o mesmo que race condition">
Data race é um termo do modelo de memória: dois acessos ao mesmo endereço, pelo menos um de escrita, sem sincronização. Race condition é um erro de lógica por intercalação. Você pode ter uma sem a outra: um check-then-act feito com duas chamadas atômicas separadas não tem data race, mas ainda tem race condition.
</Callout>

## Armadilhas

- **Testes não provam ausência de corrida.** A janela pode ser de nanossegundos. Use ferramentas como ThreadSanitizer (C++ e Go) e raciocine sobre o código.
- **Proteger só a escrita não basta.** Se a leitura acontece fora do lock, ela pode ver um estado intermediário.
- **Objetos compostos.** Atualizar dois campos relacionados (como `inicio` e `fim` de um intervalo) exige que ambos fiquem na mesma seção crítica, ou alguém lê um campo novo com um velho.
- **Coleções "thread-safe" não tornam a sequência atômica.** Em Java, `if (!map.containsKey(k)) map.put(k, v)` sobre um `ConcurrentHashMap` ainda tem corrida; o certo é `putIfAbsent` ou `computeIfAbsent`.

## Na entrevista

Quando o entrevistador mostrar código com estado compartilhado, procure os dois padrões: ler-modificar-escrever e verificar-e-agir. Nomeie o problema, desenhe a intercalação que quebra (como no diagrama acima) e proponha a seção crítica mínima que resolve. Follow-ups comuns: "o GIL do Python não evita isso?" (não, a troca de thread pode ocorrer entre instruções de bytecode) e "como evitar o lock?" (estado não compartilhado, confinamento por thread, operações atômicas como `AtomicInteger.incrementAndGet` em Java ou `atomic.AddInt64` em Go).
