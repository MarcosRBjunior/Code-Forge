Imagine uma classe em que todo método público adquire o mesmo lock. Funciona até o dia em que um método público chama outro: a thread já está com o lock, tenta adquiri-lo de novo e fica esperando por ela mesma. É um **auto-deadlock**, e com um lock comum ele é garantido. O **lock reentrante** resolve isso: a mesma thread pode adquiri-lo várias vezes, e ele só fica livre quando ela libera o mesmo número de vezes.

## Como funciona

Um lock reentrante guarda dois dados além do estado: **quem é o dono** e um **contador de aquisições**.

```text
operação                    dono    contador
inicial                     -       0
T1 adquire                  T1      1
T1 adquire de novo          T1      2   (não bloqueia: já é o dono)
T2 tenta adquirir           T1      2   (T2 bloqueia)
T1 libera                   T1      1
T1 libera                   -       0   (agora T2 pode entrar)
```

Em Python, a versão reentrante é `threading.RLock`. Em Java, tanto `synchronized` quanto `ReentrantLock` são reentrantes por padrão, por isso um método `synchronized` pode chamar outro do mesmo objeto sem problema. Em Go, `sync.Mutex` **não** é reentrante, e isso é uma decisão de projeto deliberada. Em C++, existe `std::recursive_mutex` ao lado do `std::mutex` comum.

## O auto-deadlock, sem travar o programa

O programa abaixo mostra a diferença usando `acquire(timeout=...)` para que a segunda tentativa desista em vez de travar para sempre:

<CodeTabs>

```python
import threading

comum = threading.Lock()
comum.acquire()
print("Lock: segunda aquisicao pela mesma thread ->", comum.acquire(timeout=0.2))
comum.release()

reentrante = threading.RLock()
reentrante.acquire()
print("RLock: segunda aquisicao pela mesma thread ->", reentrante.acquire(timeout=0.2))
reentrante.release()
reentrante.release()

# Só o dono pode liberar um RLock
reentrante.acquire()
erros = []

def liberar_de_outra_thread():
    try:
        reentrante.release()
    except RuntimeError as e:
        erros.append(type(e).__name__)

t = threading.Thread(target=liberar_de_outra_thread)
t.start()
t.join()
reentrante.release()
print("liberar RLock de outra thread ->", erros[0])
```

```java
import java.util.*;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.locks.StampedLock;

public static void main(String[] args) throws InterruptedException {
    // synchronized e ReentrantLock são reentrantes; StampedLock não é
    StampedLock comum = new StampedLock();
    long carimbo = comum.writeLock();
    long segundo = comum.tryWriteLock(200, TimeUnit.MILLISECONDS);  // devolve 0 quando desiste
    System.out.println("Lock: segunda aquisicao pela mesma thread -> " + (segundo != 0));
    comum.unlockWrite(carimbo);

    ReentrantLock reentrante = new ReentrantLock();
    reentrante.lock();
    System.out.println("RLock: segunda aquisicao pela mesma thread -> " + reentrante.tryLock(200, TimeUnit.MILLISECONDS));
    reentrante.unlock();
    reentrante.unlock();

    // Só o dono pode liberar um ReentrantLock
    reentrante.lock();
    List<String> erros = new ArrayList<>();

    Thread t = new Thread(() -> {
        try {
            reentrante.unlock();
        } catch (IllegalMonitorStateException e) {
            erros.add(e.getClass().getSimpleName());
        }
    });
    t.start();
    t.join();
    reentrante.unlock();
    System.out.println("liberar RLock de outra thread -> " + erros.get(0));
}
```

```cpp
#include <chrono>
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <semaphore>
#include <stdexcept>
#include <string>
#include <thread>
#include <vector>

// Liberar um recursive_mutex de outra thread é comportamento indefinido: ninguém avisa.
// Para ver a regra do dono, esta classe guarda o dono e o contador, como a aula descreve.
class RuntimeError : public std::runtime_error {
    using std::runtime_error::runtime_error;
};

class LockComDono {
    std::mutex interno;
    std::condition_variable livre;
    std::thread::id dono;
    int contador = 0;

public:
    void acquire() {
        std::unique_lock<std::mutex> guarda(interno);
        auto eu = std::this_thread::get_id();
        livre.wait(guarda, [&] { return contador == 0 || dono == eu; });
        dono = eu;
        contador += 1;
    }

    void release() {
        std::lock_guard<std::mutex> guarda(interno);
        if (contador == 0 || dono != std::this_thread::get_id()) {
            throw RuntimeError("liberado por quem nao e o dono");
        }
        contador -= 1;
        if (contador == 0) livre.notify_one();
    }
};

int main() {
    std::cout << std::boolalpha;

    // Travar de novo um std::mutex na mesma thread é comportamento indefinido, então o
    // auto-deadlock é mostrado com um semáforo binário, que não tem dono e aceita prazo.
    std::binary_semaphore comum(1);
    comum.acquire();
    std::cout << "Lock: segunda aquisicao pela mesma thread -> "
              << comum.try_acquire_for(std::chrono::milliseconds(200)) << std::endl;
    comum.release();

    std::recursive_timed_mutex reentrante;
    reentrante.lock();
    std::cout << "RLock: segunda aquisicao pela mesma thread -> "
              << reentrante.try_lock_for(std::chrono::milliseconds(200)) << std::endl;
    reentrante.unlock();
    reentrante.unlock();

    // Só o dono pode liberar
    LockComDono com_dono;
    com_dono.acquire();
    std::vector<std::string> erros;

    std::thread t([&] {
        try {
            com_dono.release();
        } catch (const RuntimeError&) {
            erros.push_back("RuntimeError");
        }
    });
    t.join();
    com_dono.release();
    std::cout << "liberar RLock de outra thread -> " << erros[0] << std::endl;
}
```

```go
import (
	"errors"
	"fmt"
	"sync"
	"time"
)

// Em Go não existe mutex reentrante, de propósito, e goroutine não expõe um id.
// Para reproduzir a aula, este tipo recebe o dono como parâmetro. Em código real, separe
// métodos que travam de métodos internos que supõem o lock já seguro.
type LockReentrante struct {
	interno  sync.Mutex
	dono     int
	contador int
}

func (l *LockReentrante) Acquire(dono int, prazo time.Duration) bool {
	limite := time.Now().Add(prazo)
	for {
		l.interno.Lock()
		if l.contador == 0 || l.dono == dono {
			l.dono = dono
			l.contador += 1
			l.interno.Unlock()
			return true
		}
		l.interno.Unlock()
		if time.Now().After(limite) {
			return false
		}
		time.Sleep(time.Millisecond)
	}
}

func (l *LockReentrante) Release(dono int) error {
	l.interno.Lock()
	defer l.interno.Unlock()
	if l.contador == 0 || l.dono != dono {
		return errors.New("RuntimeError")
	}
	l.contador -= 1
	return nil
}

// sync.Mutex só tem TryLock, sem prazo: a espera com prazo é um laço de tentativas
func tentarComPrazo(lock *sync.Mutex, prazo time.Duration) bool {
	limite := time.Now().Add(prazo)
	for time.Now().Before(limite) {
		if lock.TryLock() {
			return true
		}
		time.Sleep(time.Millisecond)
	}
	return false
}

func main() {
	prazo := 200 * time.Millisecond

	var comum sync.Mutex
	comum.Lock()
	fmt.Println("Lock: segunda aquisicao pela mesma thread ->", tentarComPrazo(&comum, prazo))
	comum.Unlock()

	reentrante := &LockReentrante{}
	reentrante.Acquire(1, prazo)
	fmt.Println("RLock: segunda aquisicao pela mesma thread ->", reentrante.Acquire(1, prazo))
	reentrante.Release(1)
	reentrante.Release(1)

	// Só o dono pode liberar
	reentrante.Acquire(1, prazo)
	var erros []string

	var wg sync.WaitGroup
	wg.Add(1)
	go func() {
		defer wg.Done()
		if err := reentrante.Release(2); err != nil { // esta goroutine é o dono 2
			erros = append(erros, err.Error())
		}
	}()
	wg.Wait()
	reentrante.Release(1)
	fmt.Println("liberar RLock de outra thread ->", erros[0])
}
```

</CodeTabs>

```text
Saída:
Lock: segunda aquisicao pela mesma thread -> False
RLock: segunda aquisicao pela mesma thread -> True
liberar RLock de outra thread -> RuntimeError
```

Sem o `timeout`, a segunda linha nunca terminaria com o `Lock` comum. Repare também que o `RLock` tem dono: outra thread não pode liberá-lo. Um `Lock` comum, curiosamente, pode ser liberado por qualquer thread em Python.

## O caso típico: métodos que se chamam

<CodeTabs>

```python
import threading

class Carrinho:
    def __init__(self):
        self._lock = threading.RLock()
        self._itens = []

    def adicionar(self, nome, preco):
        with self._lock:
            self._itens.append((nome, preco))

    def total(self):
        with self._lock:
            return sum(preco for _, preco in self._itens)

    def adicionar_varios(self, itens):
        with self._lock:  # mantém a operação composta atômica
            for nome, preco in itens:
                self.adicionar(nome, preco)  # readquire o mesmo lock
            return self.total()              # e de novo

carrinho = Carrinho()

def comprar(base):
    carrinho.adicionar_varios([(f"item{base + i}", 10) for i in range(3)])

threads = [threading.Thread(target=comprar, args=(k * 3,)) for k in range(4)]
for t in threads:
    t.start()
for t in threads:
    t.join()

print("itens:", len(carrinho._itens))
print("total:", carrinho.total())
```

```java
import java.util.*;

static class Item {
    final String nome;
    final int preco;

    Item(String nome, int preco) {
        this.nome = nome;
        this.preco = preco;
    }
}

static class Carrinho {
    final List<Item> itens = new ArrayList<>();

    // o monitor de synchronized é reentrante: um método pode chamar outro do mesmo objeto
    synchronized void adicionar(String nome, int preco) {
        itens.add(new Item(nome, preco));
    }

    synchronized int total() {
        int soma = 0;
        for (Item item : itens) soma += item.preco;
        return soma;
    }

    synchronized int adicionarVarios(List<Item> novos) {   // mantém a operação composta atômica
        for (Item item : novos) {
            adicionar(item.nome, item.preco);   // readquire o mesmo lock
        }
        return total();                         // e de novo
    }
}

static final Carrinho carrinho = new Carrinho();

static void comprar(int base) {
    List<Item> novos = new ArrayList<>();
    for (int i = 0; i < 3; i++) {
        novos.add(new Item("item" + (base + i), 10));
    }
    carrinho.adicionarVarios(novos);
}

public static void main(String[] args) throws InterruptedException {
    List<Thread> threads = new ArrayList<>();
    for (int k = 0; k < 4; k++) {
        int base = k * 3;
        threads.add(new Thread(() -> comprar(base)));
    }
    for (Thread t : threads) t.start();
    for (Thread t : threads) t.join();

    System.out.println("itens: " + carrinho.itens.size());
    System.out.println("total: " + carrinho.total());
}
```

```go
import (
	"fmt"
	"strconv"
	"sync"
)

type Item struct {
	nome  string
	preco int
}

// sync.Mutex não é reentrante: se AdicionarVarios chamasse Adicionar, a goroutine ficaria
// esperando por ela mesma. A alternativa idiomática é separar os métodos públicos, que
// travam, dos internos, que supõem o lock já seguro.
type Carrinho struct {
	lock  sync.Mutex
	itens []Item
}

func (c *Carrinho) adicionarSemLock(nome string, preco int) {
	c.itens = append(c.itens, Item{nome, preco})
}

func (c *Carrinho) totalSemLock() int {
	soma := 0
	for _, item := range c.itens {
		soma += item.preco
	}
	return soma
}

func (c *Carrinho) Adicionar(nome string, preco int) {
	c.lock.Lock()
	defer c.lock.Unlock()
	c.adicionarSemLock(nome, preco)
}

func (c *Carrinho) Total() int {
	c.lock.Lock()
	defer c.lock.Unlock()
	return c.totalSemLock()
}

func (c *Carrinho) AdicionarVarios(itens []Item) int {
	c.lock.Lock() // mantém a operação composta atômica
	defer c.lock.Unlock()
	for _, item := range itens {
		c.adicionarSemLock(item.nome, item.preco) // não readquire: o lock já está seguro
	}
	return c.totalSemLock()
}

func main() {
	carrinho := &Carrinho{}

	comprar := func(base int, wg *sync.WaitGroup) {
		defer wg.Done()
		var itens []Item
		for i := 0; i < 3; i++ {
			itens = append(itens, Item{"item" + strconv.Itoa(base+i), 10})
		}
		carrinho.AdicionarVarios(itens)
	}

	var wg sync.WaitGroup
	for k := 0; k < 4; k++ {
		wg.Add(1)
		go comprar(k*3, &wg)
	}
	wg.Wait()

	fmt.Println("itens:", len(carrinho.itens))
	fmt.Println("total:", carrinho.Total())
}
```

`adicionar_varios` precisa segurar o lock durante a operação inteira para que ninguém veja o carrinho pela metade, e ao mesmo tempo quer reaproveitar `adicionar` e `total`. Com `Lock` comum, travaria na primeira chamada interna.

## Trade-offs e armadilhas

<Callout type="note" title="Reentrância pode esconder problemas de design">
A equipe do Go deixou o mutex não reentrante de propósito: se você precisa readquirir um lock, o código provavelmente não sabe quais invariantes valem em cada ponto. A alternativa comum é separar métodos públicos, que adquirem o lock, de métodos privados, que assumem que o lock já está seguro (convenção como `_adicionar_sem_lock`).
</Callout>

- **Custo:** um lock reentrante precisa registrar o dono e o contador, então é um pouco mais caro que um mutex simples.
- **Liberações desbalanceadas:** cada `acquire` precisa de um `release`. Se você liberar uma vez a menos, o lock fica preso. Use `with` sempre.
- **Variáveis de condição:** esperar numa condição associada a um lock reentrante adquirido várias vezes libera todos os níveis e os restaura ao acordar. Funciona em Python e Java, mas confunde quem lê o código.
- **Chamadas para fora:** reentrância incentiva chamar callbacks com o lock seguro. Se o callback chamar de volta o objeto, você entra de novo no meio de uma operação e pode ver invariantes quebradas.

| Linguagem | Não reentrante | Reentrante |
| --- | --- | --- |
| Python | `threading.Lock` | `threading.RLock` |
| Java | `StampedLock` | `synchronized`, `ReentrantLock` |
| Go | `sync.Mutex` | não existe por padrão |
| C++ | `std::mutex` | `std::recursive_mutex` |

## Na entrevista

Se você desenhar uma classe thread-safe em que métodos públicos chamam uns aos outros, cite o risco de auto-deadlock e escolha conscientemente: use um lock reentrante ou separe a versão interna sem lock. Saber que `synchronized` é reentrante e que o `sync.Mutex` do Go não é costuma impressionar. Follow-ups comuns: "como implementar um lock reentrante a partir de um mutex comum?" (guarde o id do dono e um contador, protegidos por um mutex interno e uma variável de condição) e "por que o Go não tem um?" (para forçar um desenho em que cada função sabe se o lock já está seguro).
