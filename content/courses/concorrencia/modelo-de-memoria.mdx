Imagine uma thread que escreve `pronto = True` e outra que fica num laço esperando ver essa mudança. Intuitivamente, a segunda thread verá o novo valor logo depois. Em Java, C++ ou Go, isso não é garantido: ela pode nunca ver, ou ver `pronto = True` antes de ver os dados que deveriam ter sido escritos antes. Entender por que isso acontece é o que separa quem "usa locks porque sim" de quem sabe o que eles garantem.

## Por que a memória não é simples

Três camadas reordenam ou atrasam leituras e escritas para ganhar desempenho:

- **Compilador:** pode reordenar instruções independentes, ou manter uma variável num registrador em vez de reler da memória a cada volta do laço.
- **CPU:** executa fora de ordem e usa buffers de escrita; uma escrita pode ficar visível para outros núcleos depois de uma escrita posterior.
- **Caches:** cada núcleo tem seu cache. A coerência entre eles é garantida pelo hardware, mas a ordem em que as escritas aparecem para outro núcleo depende da arquitetura.

```text
Thread 1 (núcleo 0)          Thread 2 (núcleo 1)
dados = 42                   while not pronto: pass
pronto = True                print(dados)

Sem sincronização, a Thread 2 pode:
  - nunca sair do laço (pronto lido uma vez e guardado em registrador)
  - sair do laço e imprimir o valor antigo de dados (escritas reordenadas)
```

Um programa de uma thread nunca percebe nada disso, porque as otimizações preservam o resultado sequencial. O problema só aparece quando outra thread observa.

## O que é um modelo de memória

O **modelo de memória** da linguagem é o contrato que diz quais valores uma leitura pode devolver em programas concorrentes. A peça central é a relação **happens-before**: se a ação A acontece-antes da ação B, tudo que A escreveu está visível para B.

Você cria happens-before com sincronização:

- Liberar um lock acontece-antes de alguém adquirir esse mesmo lock depois.
- Escrever numa variável `volatile` (Java) ou atômica com ordem de liberação (C++ `std::memory_order_release`) acontece-antes de uma leitura que veja esse valor.
- Iniciar uma thread acontece-antes de qualquer ação dela; o fim de uma thread acontece-antes do `join` retornar.
- Em Go, enviar num canal acontece-antes do recebimento correspondente.

Sem uma dessas arestas entre duas threads, você tem uma **data race** e, em C++ e Go, o comportamento é indefinido. Em Java, o programa não quebra a memória, mas pode ver valores velhos ou fora de ordem.

## Publicação segura

O padrão mais comum é preparar dados numa thread e entregá-los a outra. O programa abaixo usa `threading.Event`: o `set()` acontece depois de preencher o dicionário e o `wait()` só retorna depois do `set()`, então o consumidor sempre vê os dados completos.

<CodeTabs>

```python
import threading

config = {}
publicado = threading.Event()
lido = []

def produtor():
    config["host"] = "db.interno"
    config["porta"] = 5432
    publicado.set()            # publica: tudo escrito antes fica visível

def consumidor():
    publicado.wait()           # sincroniza com o set()
    lido.append(f"{config['host']}:{config['porta']}")

c = threading.Thread(target=consumidor)
p = threading.Thread(target=produtor)
c.start()
p.start()
p.join()
c.join()
print(lido[0])
```

```java
import java.util.*;
import java.util.concurrent.CountDownLatch;

static final Map<String, String> config = new HashMap<>();
static final CountDownLatch publicado = new CountDownLatch(1);
static final List<String> lido = new ArrayList<>();

static void produtor() {
    config.put("host", "db.interno");
    config.put("porta", "5432");
    publicado.countDown();     // publica: tudo escrito antes fica visível
}

static void consumidor() {
    try {
        publicado.await();     // sincroniza com o countDown()
    } catch (InterruptedException e) {
        return;
    }
    lido.add(config.get("host") + ":" + config.get("porta"));
}

public static void main(String[] args) throws InterruptedException {
    Thread c = new Thread(() -> consumidor());
    Thread p = new Thread(() -> produtor());
    c.start();
    p.start();
    p.join();
    c.join();
    System.out.println(lido.get(0));
}
```

Em Java, o mesmo efeito vem de um campo `volatile boolean pronto`, de um `CountDownLatch` ou de um `synchronized` em volta da escrita e da leitura. Em Go, do envio por um canal. Em C++, de um `std::atomic<bool>` com `store(true, std::memory_order_release)` e `load(std::memory_order_acquire)`.

## Inicialização preguiçosa e o double-checked locking

Um clássico de entrevista: criar um singleton só quando for usado, uma única vez, mesmo com várias threads pedindo ao mesmo tempo. A versão com verificação dupla evita pegar o lock em toda chamada depois da criação.

<CodeTabs>

```python
import threading

class Conexao:
    criadas = 0
    def __init__(self):
        Conexao.criadas += 1

_instancia = None
_lock = threading.Lock()

def obter_conexao():
    global _instancia
    if _instancia is None:              # 1ª verificação, sem lock
        with _lock:
            if _instancia is None:      # 2ª verificação, com lock
                _instancia = Conexao()
    return _instancia

barreira = threading.Barrier(8)
vistas = []

def worker():
    barreira.wait()                     # todas pedem ao mesmo tempo
    vistas.append(id(obter_conexao()))

threads = [threading.Thread(target=worker) for _ in range(8)]
for t in threads:
    t.start()
for t in threads:
    t.join()
print("instancias criadas:", Conexao.criadas)
print("todas viram a mesma:", len(set(vistas)) == 1)
```

```java
import java.util.*;
import java.util.concurrent.CyclicBarrier;

static class Conexao {
    static int criadas = 0;

    Conexao() {
        criadas += 1;
    }
}

// volatile é obrigatório: sem ele, outra thread pode ver a referência antes de o construtor terminar
static volatile Conexao instancia = null;
static final Object lock = new Object();

static Conexao obterConexao() {
    if (instancia == null) {                // 1ª verificação, sem lock
        synchronized (lock) {
            if (instancia == null) {        // 2ª verificação, com lock
                instancia = new Conexao();
            }
        }
    }
    return instancia;
}

static final CyclicBarrier barreira = new CyclicBarrier(8);
static final List<Conexao> vistas = Collections.synchronizedList(new ArrayList<>());

static void worker() {
    try {
        barreira.await();                   // todas pedem ao mesmo tempo
    } catch (Exception e) {
        throw new RuntimeException(e);
    }
    vistas.add(obterConexao());
}

public static void main(String[] args) throws InterruptedException {
    List<Thread> threads = new ArrayList<>();
    for (int i = 0; i < 8; i++) {
        threads.add(new Thread(() -> worker()));
    }
    for (Thread t : threads) t.start();
    for (Thread t : threads) t.join();
    System.out.println("instancias criadas: " + Conexao.criadas);
    System.out.println("todas viram a mesma: " + (new HashSet<>(vistas).size() == 1));
}
```

```cpp
#include <atomic>
#include <barrier>
#include <iostream>
#include <mutex>
#include <set>
#include <thread>
#include <vector>

class Conexao {
public:
    inline static int criadas = 0;

    Conexao() {
        criadas += 1;
    }
};

// Em código real, prefira std::call_once ou uma variável static local. Com ponteiro comum,
// a primeira verificação seria uma data race; por isso std::atomic com release/acquire.
std::atomic<Conexao*> instancia{nullptr};
std::mutex trava;

Conexao* obter_conexao() {
    Conexao* atual = instancia.load(std::memory_order_acquire);  // 1ª verificação, sem lock
    if (atual == nullptr) {
        std::lock_guard<std::mutex> guarda(trava);
        atual = instancia.load(std::memory_order_relaxed);       // 2ª verificação, com lock
        if (atual == nullptr) {
            atual = new Conexao();
            instancia.store(atual, std::memory_order_release);
        }
    }
    return atual;
}

std::barrier<> barreira(8);
std::vector<Conexao*> vistas;
std::mutex vistas_lock;

void worker() {
    barreira.arrive_and_wait();                                  // todas pedem ao mesmo tempo
    Conexao* conexao = obter_conexao();
    std::lock_guard<std::mutex> guarda(vistas_lock);
    vistas.push_back(conexao);
}

int main() {
    std::vector<std::thread> threads;
    for (int i = 0; i < 8; i++) {
        threads.emplace_back(worker);
    }
    for (auto& t : threads) t.join();
    std::cout << "instancias criadas: " << Conexao::criadas << std::endl;
    std::set<Conexao*> distintas(vistas.begin(), vistas.end());
    std::cout << std::boolalpha << "todas viram a mesma: " << (distintas.size() == 1) << std::endl;
}
```

```csharp
using System;
using System.Collections.Generic;
using System.Threading;

class Conexao
{
    public static int criadas = 0;

    public Conexao()
    {
        criadas += 1;
    }
}

// volatile: outra thread não pode ver a referência antes de o construtor terminar
static volatile Conexao _instancia = null;
static readonly object _lock = new object();

static Conexao ObterConexao()
{
    if (_instancia == null)                 // 1ª verificação, sem lock
    {
        lock (_lock)
        {
            if (_instancia == null)         // 2ª verificação, com lock
            {
                _instancia = new Conexao();
            }
        }
    }
    return _instancia;
}

static readonly Barrier barreira = new Barrier(8);
static readonly List<Conexao> vistas = new List<Conexao>();

static void Worker()
{
    barreira.SignalAndWait();               // todas pedem ao mesmo tempo
    Conexao conexao = ObterConexao();
    lock (vistas)
    {
        vistas.Add(conexao);
    }
}

static void Main()
{
    var threads = new List<Thread>();
    for (int i = 0; i < 8; i++)
    {
        threads.Add(new Thread(Worker));
    }
    foreach (var t in threads) t.Start();
    foreach (var t in threads) t.Join();
    Console.WriteLine("instancias criadas: " + Conexao.criadas);
    Console.WriteLine("todas viram a mesma: " + (new HashSet<Conexao>(vistas).Count == 1));
}
```

```go
import (
	"fmt"
	"sync"
)

type Conexao struct {
	numero int
}

var criadas = 0

// Em Go a verificação dupla feita à mão seria uma data race: o idiomático é sync.Once,
// que por dentro faz o mesmo (leitura atômica no caminho rápido, mutex só na criação).
var instancia *Conexao
var once sync.Once

func obterConexao() *Conexao {
	once.Do(func() {
		criadas += 1
		instancia = &Conexao{numero: criadas}
	})
	return instancia
}

func main() {
	largada := make(chan struct{}) // Go não tem barreira: fechar o canal solta todas as que esperam
	var vistas []*Conexao
	var vistasLock sync.Mutex

	var wg sync.WaitGroup
	for i := 0; i < 8; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			<-largada // todas pedem ao mesmo tempo
			conexao := obterConexao()
			vistasLock.Lock()
			defer vistasLock.Unlock()
			vistas = append(vistas, conexao)
		}()
	}
	close(largada)
	wg.Wait()

	fmt.Println("instancias criadas:", criadas)
	distintas := map[*Conexao]bool{}
	for _, conexao := range vistas {
		distintas[conexao] = true
	}
	fmt.Println("todas viram a mesma:", len(distintas) == 1)
}
```

</CodeTabs>

```text
Saída:
instancias criadas: 1
todas viram a mesma: True
```

Em Java, esse padrão só é correto se o campo for `volatile`. Sem isso, outra thread pode ver a referência publicada antes de o construtor terminar de preencher os campos, ou seja, um objeto parcialmente construído. Em C++ prefira `std::call_once` ou uma variável `static` local, cuja inicialização é thread-safe desde C++11; em Go, `sync.Once`.

## Armadilhas

- Achar que "a variável é só um booleano, não precisa de sincronização". Atomicidade da escrita não implica visibilidade nem ordem.
- Usar `volatile` em C++ para comunicação entre threads. Lá ele não tem semântica de sincronização; use `std::atomic`.
- Sincronizar a escrita mas não a leitura. Happens-before exige que os dois lados participem.
