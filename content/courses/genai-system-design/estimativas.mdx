Em sistemas tradicionais, a estimativa de capacidade costuma terminar em "precisamos de uns 20 servidores e 5 TB de disco", e o número raramente muda o desenho. Em produtos com IA generativa, a conta de tokens decide coisas grandes: se dá para usar o modelo mais capaz em todas as chamadas, se vale hospedar o próprio modelo ou se o produto sequer fecha financeiramente. Por isso, os entrevistadores esperam que você chegue a três números: **tokens por segundo**, **GPUs necessárias** e **custo mensal**.

## De usuários a tokens

O caminho é sempre o mesmo:

1. Usuários ativos por dia vezes requisições por usuário dá **requisições por dia**.
2. Multiplique pelos tokens médios de entrada e de saída de cada requisição.
3. Divida por 86.400 segundos para a média e aplique um **fator de pico** (2 a 5 vezes é comum para tráfego humano com padrão diário).

Separe sempre entrada e saída. Tokens de entrada são processados em paralelo no prefill e costumam ser mais baratos; tokens de saída saem um por vez no decode, consomem a GPU por mais tempo e custam mais. Num chat com histórico, a entrada cresce a cada turno, porque o histórico é reenviado; num resumo de documentos, a entrada domina por larga margem.

## De tokens a GPUs

Se você hospeda o modelo, a pergunta é quantos tokens de saída por segundo uma GPU (ou um grupo de GPUs que serve uma réplica do modelo) sustenta com batching. Esse número depende do tamanho do modelo, da precisão numérica, do tamanho do batch e do comprimento dos contextos. Na entrevista, **declare uma hipótese** ("vou supor 2 mil tokens de saída por segundo por réplica com batching") e siga, deixando claro que mediria isso num benchmark próprio.

Lembre também que o decode raramente fica a 100% de uso: você precisa de folga para picos e para manter a latência por token aceitável. Planejar para 60% a 70% de utilização é uma margem razoável.

## De tokens a dólares

Com API de provedor, o custo é linear: tokens vezes preço por milhão. Com hospedagem própria, o custo é o aluguel das GPUs, pago esteja a GPU ocupada ou ociosa. A comparação entre os dois revela o ponto de equilíbrio: volumes baixos ou muito irregulares favorecem API; volumes altos e estáveis favorecem hospedagem própria, desde que a equipe consiga operá-la.

## Um exemplo completo

Todos os números abaixo são hipotéticos. Troque-os pelos que o entrevistador der.

```python
import math

dau = 5_000_000
req_por_usuario = 8
tok_entrada = 1200          # media por requisicao (prompt + historico)
tok_saida = 300
fator_pico = 3

req_dia = dau * req_por_usuario
ent_s = req_dia * tok_entrada / 86_400
sai_s = req_dia * tok_saida / 86_400
print(f"requisicoes/dia: {req_dia / 1e6:.0f} M")
print(f"media: {ent_s / 1e3:.0f} mil tok/s de entrada, {sai_s / 1e3:.0f} mil tok/s de saida")
print(f"pico:  {sai_s * fator_pico / 1e3:.0f} mil tok/s de saida")

# Hospedagem propria (hipotese: replica de 2 GPUs sustenta 2.000 tok/s de saida)
tok_s_por_replica = 2000
gpus_por_replica = 2
utilizacao_alvo = 0.65
replicas = math.ceil(sai_s * fator_pico / (tok_s_por_replica * utilizacao_alvo))
gpus = replicas * gpus_por_replica
custo_gpu_hora = 2.5        # USD hipotetico
custo_proprio = gpus * custo_gpu_hora * 24 * 30
print(f"replicas: {replicas}, GPUs: {gpus}, custo mensal: US$ {custo_proprio / 1e6:.2f} M")

# API de provedor (precos hipoteticos por milhao de tokens)
preco_ent, preco_sai = 0.50, 1.50
tokens_mes_ent = req_dia * tok_entrada * 30
tokens_mes_sai = req_dia * tok_saida * 30
custo_api = (tokens_mes_ent * preco_ent + tokens_mes_sai * preco_sai) / 1e6
print(f"custo mensal via API: US$ {custo_api / 1e6:.2f} M")
print(f"custo por usuario ativo/mes: proprio US$ {custo_proprio / dau:.3f}, API US$ {custo_api / dau:.3f}")
```

```text
Saída:
requisicoes/dia: 40 M
media: 556 mil tok/s de entrada, 139 mil tok/s de saida
pico:  417 mil tok/s de saida
replicas: 321, GPUs: 642, custo mensal: US$ 1.16 M
custo mensal via API: US$ 1.26 M
custo por usuario ativo/mes: proprio US$ 0.231, API US$ 0.252
```

Com essas hipóteses, as duas opções empatam na casa de pouco mais de um milhão de dólares por mês, e é aí que a conversa fica interessante: um empate significa que fatores qualitativos (privacidade, equipe para operar a frota, previsibilidade) decidem. Repare em três coisas. O pico define o número de GPUs, mas a fatura via API acompanha a média, porque você só paga o que usa. A hospedagem própria paga pelas GPUs ociosas de madrugada, o que pode ser compensado com jobs em lote nesses horários. E o custo por usuário é o número que o time de produto entende: compare com quanto cada usuário gera de receita.

## Armadilhas

- **Esquecer o histórico.** No décimo turno de uma conversa, o prompt carrega os nove anteriores. Use uma média que reflita isso ou limite o histórico.
- **Ignorar a memória.** Mesmo que a computação dê conta, cada requisição ativa ocupa memória de GPU com o KV cache. Contextos longos reduzem quantas requisições cabem num batch.
- **Precisão falsa.** Arredonde agressivamente. "Cerca de 30 GPUs" é melhor que "28,7 GPUs".
- **Não comparar alternativas.** O número só vira decisão quando você coloca API, hospedagem própria e um modelo menor lado a lado.

<Callout type="tip" title="Fale as hipóteses em voz alta">
O entrevistador não sabe o throughput real do modelo que você imaginou, e você também não. O que ele avalia é se você sabe quais variáveis entram na conta e como cada uma muda a decisão.
</Callout>

## Na entrevista

Faça a conta em menos de cinco minutos e termine com uma frase de decisão: "com esses números, a API custa cerca de X por mês; isso justifica cache e roteamento para modelo menor". Follow-ups comuns: "e se o tamanho médio do prompt dobrar?" (entrada dobra, custo de API sobe quase proporcionalmente, latência do prefill aumenta) e "quando vale hospedar o próprio modelo?" (volume alto e estável, requisitos de privacidade ou necessidade de customização, contra o custo de operar a frota).
