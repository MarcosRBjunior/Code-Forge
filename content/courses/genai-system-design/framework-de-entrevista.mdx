Perguntas de system design de produtos com IA são abertas de propósito: "projete um assistente que responde dúvidas sobre os documentos da empresa" cabe em uma frase e esconde dezenas de decisões. Sem um roteiro, é fácil gastar vinte minutos discutindo qual modelo usar e não chegar a falar de custo, avaliação ou segurança. Este capítulo propõe um framework em seis etapas, adaptado do roteiro clássico, com as perguntas que só aparecem quando há um modelo generativo no caminho.

## As seis etapas

### 1. Escopo e requisitos (5 a 8 minutos)

Além dos requisitos funcionais de sempre, esclareça o que é específico de IA:

- **Qualidade:** o que é uma resposta boa? Há resposta certa verificável (extração, classificação) ou é aberta (redação, conversa)?
- **Tolerância a erro:** uma alucinação é incômoda ou causa prejuízo legal?
- **Latência:** o usuário espera interativamente, com streaming, ou o trabalho pode ser assíncrono?
- **Dados:** o contexto contém dados pessoais ou segredos? Pode sair da empresa para um provedor externo?
- **Escala:** usuários ativos, conversas por usuário, tamanho típico de prompt e de resposta.

### 2. Estimativas (3 a 5 minutos)

Converta escala em tokens por segundo, número de GPUs ou custo mensal. O próximo capítulo detalha as contas; aqui basta saber que elas definem se o custo é um detalhe ou o problema principal.

### 3. API e fluxo de dados (3 a 5 minutos)

Defina os endpoints e, principalmente, o formato da resposta: streaming por SSE, resposta síncrona ou job assíncrono com polling. Mostre onde ficam o histórico da conversa e os metadados de cada chamada (modelo, versão do prompt, tokens, latência).

### 4. Arquitetura de alto nível (8 a 10 minutos)

Desenhe o caminho de uma requisição. Uma referência útil:

```text
cliente -> API gateway -> serviço de aplicação -> orquestrador
                                              |-> recuperação (RAG, ferramentas)
                                              |-> guardrails de entrada
                                              |-> gateway de modelos -> modelo A / modelo B
                                              |-> guardrails de saída
                                              '-> logs, métricas, avaliação
```

### 5. Aprofundamentos (15 a 20 minutos)

Escolha dois ou três pontos onde o problema é mais difícil. Em um chat, costuma ser servir com baixa latência e gerenciar contexto longo. Em RAG, é a qualidade da recuperação. Em agentes, é segurança da execução de ferramentas. Deixe o entrevistador direcionar, mas proponha você mesmo.

### 6. Avaliação, operação e evolução (3 a 5 minutos)

Feche com como você mede qualidade (conjunto de avaliação offline, métricas online, feedback do usuário), como libera mudanças de prompt e modelo com segurança e o que monitora em produção.

## Requisitos viram decisões

O ponto central do framework é que cada resposta da etapa 1 dispara decisões concretas. O programa abaixo mostra esse mapeamento como regras simples e também distribui o tempo de uma entrevista de 45 minutos pelos pesos das etapas.

```python
etapas = [("requisitos", 7), ("estimativas", 4), ("api", 4),
          ("arquitetura", 9), ("aprofundamentos", 17), ("avaliacao", 4)]
total = 45
peso_total = sum(p for _, p in etapas)
inicio = 0.0
for nome, peso in etapas:
    dur = total * peso / peso_total
    print(f"{inicio:5.1f} min  {nome:<16}{dur:4.1f} min")
    inicio += dur

requisitos = {
    "interativo": True,
    "dados_sensiveis": True,
    "erro_caro": True,
    "pedidos_repetidos": 0.30,   # fracao estimada de perguntas parecidas
    "tokens_por_dia": 2e9,
}

regras = [
    (lambda r: r["interativo"], "streaming via SSE e meta de TTFT"),
    (lambda r: r["dados_sensiveis"], "modelo em infraestrutura propria ou redacao de PII antes do provedor"),
    (lambda r: r["erro_caro"], "citacoes obrigatorias e guardrail de saida"),
    (lambda r: r["pedidos_repetidos"] >= 0.2, "cache semantico na frente do modelo"),
    (lambda r: r["tokens_por_dia"] > 1e9, "roteamento para modelo menor nas tarefas simples"),
]
print()
for cond, decisao in regras:
    if cond(requisitos):
        print("-", decisao)
```

```text
Saída:
  0.0 min  requisitos       7.0 min
  7.0 min  estimativas      4.0 min
 11.0 min  api              4.0 min
 15.0 min  arquitetura      9.0 min
 24.0 min  aprofundamentos 17.0 min
 41.0 min  avaliacao        4.0 min

- streaming via SSE e meta de TTFT
- modelo em infraestrutura propria ou redacao de PII antes do provedor
- citacoes obrigatorias e guardrail de saida
- cache semantico na frente do modelo
- roteamento para modelo menor nas tarefas simples
```

Na prática você não roda código na entrevista, mas o raciocínio é exatamente este: cada requisito declarado precisa aparecer em algum lugar do desenho. Se você perguntou sobre dados sensíveis e depois desenhou uma chamada direta a um provedor externo sem nenhum tratamento, o entrevistador vai notar.

## Armadilhas comuns

- **Começar pelo modelo.** "Vou usar o modelo X com fine-tuning" nos primeiros minutos sinaliza que você pulou requisitos. O modelo é um componente substituível; trate-o assim.
- **Ignorar avaliação.** Em sistemas tradicionais, testes ficam implícitos. Aqui, sem um plano para medir qualidade, nenhuma mudança é segura.
- **Esquecer o custo.** Tokens têm preço marginal. Se as estimativas mostram milhões de dólares por mês, isso muda a arquitetura.
- **Desenhar só o caminho feliz.** O provedor fica fora do ar, o modelo devolve JSON inválido, o usuário cancela no meio do streaming. Diga o que acontece em cada caso.

<Callout type="note" title="Adapte o tempo ao sinal do entrevistador">
Os minutos sugeridos são um ponto de partida. Se o entrevistador puxa um assunto cedo, siga-o e volte ao roteiro depois; o framework serve para você não esquecer nada, não para engessar a conversa.
</Callout>

## Na entrevista

Anuncie o roteiro em uma frase no começo ("vou levantar requisitos, estimar, desenhar e depois aprofundar em dois pontos"). Ao fim dos requisitos, resuma em voz alta as três ou quatro restrições que mais pesam, porque são elas que vão justificar suas escolhas. Follow-ups frequentes: "o que você faria diferente com dez vezes mais usuários?" e "qual parte deste desenho você liberaria primeiro?" (um MVP com um único modelo, logs completos e avaliação, antes de otimizar custo).
