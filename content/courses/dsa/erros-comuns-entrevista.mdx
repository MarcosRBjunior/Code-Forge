A maioria das reprovações em entrevista de código não vem de falta de conhecimento, mas de erros de processo que se repetem. Conhecê-los com antecedência é a forma mais barata de ganhar pontos.

## Erros de processo

**Codar cedo demais.** O candidato lê o enunciado, reconhece algo parecido com um problema que já resolveu e começa a digitar. Dez minutos depois percebe que a variação muda tudo. Confirme entrada, saída e restrições antes de qualquer linha.

**Não declarar a complexidade.** Terminar o código e não dizer quanto ele custa deixa a pergunta mais previsível da entrevista sem resposta. Sempre feche com tempo e espaço.

**Otimizar antes de ter algo funcionando.** Perseguir a solução ótima sem ter uma correta é arriscado: se o tempo acaba, você sai sem nada. Garanta uma versão correta, mesmo que lenta, e melhore a partir dela.

**Ignorar dicas.** Quando o entrevistador pergunta "e se o array estivesse ordenado?", ele quase sempre está apontando o caminho. Pare e explore a sugestão.

## Erros de código

Alguns bugs aparecem em entrevistas com uma frequência impressionante:

| Bug | Exemplo típico | Prevenção |
| --- | --- | --- |
| Off-by-one | `range(len(a) - 1)` quando deveria ser `range(len(a))` | Teste com arrays de tamanho 0, 1 e 2 |
| Entrada vazia | `a[0]` sem checar se `a` existe | Trate o caso logo no início da função |
| Mutar enquanto itera | remover itens da lista dentro do `for` sobre ela | Construa uma lista nova ou itere sobre uma cópia |
| Overflow | somar inteiros grandes em Java ou C++ | Use `long` ou reorganize a conta, como `lo + (hi - lo) / 2` |
| Referência compartilhada | `[[0] * m] * n` em Python | Use list comprehension |

O último merece um exemplo, porque engana até gente experiente:

```python
n, m = 3, 2
errado = [[0] * m] * n
errado[0][0] = 9
print(errado)   # [[9, 0], [9, 0], [9, 0]]: as três linhas são o mesmo objeto

certo = [[0] * m for _ in range(n)]
certo[0][0] = 9
print(certo)    # [[9, 0], [0, 0], [0, 0]]
```

Outro clássico é o valor padrão mutável em funções Python:

```python
def adiciona_ruim(x, lista=[]):
    lista.append(x)
    return lista

print(adiciona_ruim(1))  # [1]
print(adiciona_ruim(2))  # [1, 2]: a lista padrão é criada só uma vez

def adiciona_bom(x, lista=None):
    if lista is None:
        lista = []
    lista.append(x)
    return lista

print(adiciona_bom(1), adiciona_bom(2))  # [1] [2]
```

## Erros de teste

**Testar só o exemplo do enunciado.** Ele foi escolhido para ser fácil de entender, não para encontrar bugs. Crie casos de borda: vazio, um elemento, todos iguais, valores negativos, resposta inexistente.

**Testar "de cabeça" sem acompanhar variáveis.** Ao simular, escreva o valor de cada variável a cada iteração, como uma pequena tabela. É mais lento, mas encontra o bug que a leitura rápida esconde.

**Dizer "acho que está certo".** Prefira mostrar: "rodei o exemplo, o resultado bate; agora o caso vazio, que retorna -1 como esperado".

<Callout type="tip" title="Checklist final de 60 segundos">
Antes de dizer que terminou: entrada vazia tratada? Índices dentro dos limites? Retorno correto quando não há resposta? Complexidade dita em voz alta?
</Callout>

## Erros de comunicação

- Ficar em silêncio por longos períodos.
- Discordar de uma correção sem testar: se o entrevistador aponta um bug, simule o caso antes de defender o código.
- Usar nomes como `a`, `b`, `tmp2`: nomes descritivos tornam o código autoexplicativo e reduzem bugs.

## Na entrevista

Você vai cometer algum desses erros; todo mundo comete. O que diferencia é perceber e corrigir com calma. Encontrar o próprio bug durante o teste conta a favor, porque mostra exatamente a habilidade que se usa no trabalho real: revisar e depurar o próprio código.
