Dois programas resolvem o mesmo problema, e ambos funcionam bem com 100 itens. Com um milhão, um termina em um instante e o outro leva horas. Medir o tempo na sua máquina não explica isso, porque o resultado muda com o hardware e a entrada. A notação Big-O descreve **como o custo de um algoritmo cresce** quando a entrada cresce. Ela ignora constantes e termos menores porque, para entradas grandes, o termo dominante é o que importa.

## As classes mais comuns

| Notação | Nome | Exemplo |
| --- | --- | --- |
| O(1) | Constante | Acessar `arr[i]` |
| O(log n) | Logarítmica | Busca binária |
| O(n) | Linear | Percorrer um array |
| O(n log n) | Linearítmica | Merge sort |
| O(n²) | Quadrática | Dois laços aninhados |
| O(2ⁿ) | Exponencial | Gerar todos os subconjuntos |

Para ter uma noção de escala: com n igual a um milhão, O(n) são cerca de um milhão de passos, O(n log n) são uns vinte milhões e O(n²) são um trilhão, o que já é inviável. Exponencial só funciona para n pequeno, algo como 20 a 25.

## Como calcular na prática

Conte quantas vezes a operação mais interna executa em função de `n`. Laços em sequência **somam**; laços aninhados **multiplicam**. Depois, descarte constantes e fique com o termo dominante: n² + n vira O(n²).

Os dois laços aninhados fazem cerca de n²/2 comparações, então a complexidade é **O(n²)**. Constantes como o 1/2 são descartadas.

Repare em um padrão que reduz o custo: se a cada passo você corta o problema pela metade, como na busca binária, o número de passos é log n.

<CodeTabs>

```python
def busca_binaria(nums, alvo):
    esq, dir = 0, len(nums) - 1
    while esq <= dir:
        meio = (esq + dir) // 2
        if nums[meio] == alvo:
            return meio
        if nums[meio] < alvo:
            esq = meio + 1
        else:
            dir = meio - 1
    return -1

print(busca_binaria([1, 3, 5, 7, 9, 11], 7))  # 3
```

static int buscaBinaria(int[] nums, int alvo) {
    int esq = 0, dir = nums.length - 1;
    while (esq <= dir) {
        int meio = esq + (dir - esq) / 2;   // evita overflow de esq + dir
        if (nums[meio] == alvo) {
            return meio;
        }
        if (nums[meio] < alvo) {
            esq = meio + 1;
        } else {
            dir = meio - 1;
        }
    }
    return -1;
}

<Callout type="note" title="Espaço também conta">
Big-O vale para memória. Uma solução que cria um conjunto auxiliar com todos os elementos usa O(n) de espaço extra, mesmo que rode em O(n) de tempo.
</Callout>

## Melhor, médio e pior caso

Big-O costuma indicar o **pior caso**, mas alguns algoritmos têm comportamentos diferentes. O quicksort é O(n log n) em média e O(n²) no pior caso. Inserir numa tabela hash é O(1) amortizado, apesar de um redimensionamento ocasional custar O(n). Em entrevista, deixe claro de qual caso você está falando.

## Armadilhas

- **Esquecer o custo escondido:** fatiar uma lista, concatenar strings num laço ou usar `in` numa lista são operações O(n) que viram O(n²) quando ficam dentro de um laço.
- **Duas entradas distintas:** percorrer uma matriz de m linhas por n colunas é O(m·n), não O(n²). Dê a cada variável o seu nome.
- **Confundir complexidade com velocidade real:** para n pequeno, um O(n²) simples pode vencer um O(n log n) cheio de overhead. Big-O orienta a escolha em escala, não substitui medir.
- **Recursão e pilha:** uma recursão de profundidade n usa O(n) de espaço na pilha, mesmo sem alocar estruturas.

## O que dizer na entrevista

Sempre declare tempo **e** espaço ao final da solução, e explique de onde vem cada termo. Dizer que "é O(n) porque cada elemento entra e sai do conjunto uma única vez" vale mais do que só dizer que é O(n). Antecipe o follow-up clássico: "dá para melhorar?". Normalmente a resposta é trocar espaço por tempo, como usar uma tabela hash, ou explorar ordenação para chegar a O(log n) com busca binária.
