Numa entrevista de código, o maior risco não é desconhecer um algoritmo. É sair digitando antes de entender o problema e, vinte minutos depois, perceber que resolveu outra coisa. Um roteiro fixo tira o peso das decisões do momento: você sempre sabe qual é o próximo passo, mesmo nervoso.

## As seis etapas

| Etapa | Tempo típico (sessão de 45 min) | Saída esperada |
| --- | --- | --- |
| 1. Entender | 3 a 5 min | Enunciado reescrito com suas palavras e restrições confirmadas |
| 2. Exemplos | 2 a 3 min | Dois ou três casos, incluindo um de borda |
| 3. Força bruta | 2 a 3 min | Ideia correta e sua complexidade, sem código |
| 4. Otimizar | 5 a 10 min | Abordagem final acordada com o entrevistador |
| 5. Codificar | 10 a 15 min | Código limpo, com nomes claros |
| 6. Testar | 5 min | Execução manual nos exemplos e correção de bugs |

### 1. Entender

Repita o problema em voz alta e pergunte o que não está explícito: o array pode estar vazio? Há números negativos? Os valores se repetem? A entrada cabe na memória? Qual o tamanho máximo de n? Essa última pergunta é ouro: n até 10⁵ praticamente exige algo como O(n log n) ou melhor, enquanto n até 20 sugere que uma solução exponencial (backtracking, bitmask) é aceitável.

### 2. Exemplos

Monte você mesmo um exemplo pequeno e não trivial. O exemplo do enunciado costuma ser simples demais e esconder casos difíceis. Inclua um caso de borda: entrada vazia, um único elemento, todos iguais.

### 3. Força bruta

Diga a solução mais ingênua que funciona e sua complexidade. Isso prova que você entendeu o problema e dá uma base para comparar. Não precisa codificá-la, a menos que o entrevistador peça.

### 4. Otimizar

Pergunte-se onde está o trabalho repetido. Algumas perguntas que destravam a maioria dos problemas:

- Ordenar ajuda? Abre portas para dois ponteiros e busca binária.
- Um hash map elimina um laço interno?
- Existe uma janela que cresce e encolhe?
- A resposta depende de respostas menores do mesmo tipo (recursão, DP)?
- A resposta é monotônica, permitindo busca binária no valor?

### 5. Codificar

Escreva funções pequenas, com nomes que digam o que fazem. Se uma parte é óbvia mas trabalhosa, combine com o entrevistador de deixá-la como função auxiliar e volte depois.

### 6. Testar

Execute o código linha a linha com seu exemplo, acompanhando as variáveis. Depois rode mentalmente os casos de borda.

## Exemplo aplicado

Problema: dado um array de inteiros e um valor `k`, diga se existem dois índices distintos cujos valores somam `k`.

- **Entender:** índices distintos, valores podem se repetir, só precisa responder sim ou não.
- **Exemplos:** `[3, 1, 4], k=7` dá verdadeiro; `[3], k=6` dá falso, pois não dá para usar o mesmo índice duas vezes.
- **Força bruta:** testar todos os pares, O(n²) de tempo e O(1) de espaço.
- **Otimizar:** para cada número, o par necessário é `k - x`. Um conjunto com o que já foi visto responde em O(1).

```python
def existe_par(nums, k):
    vistos = set()
    for x in nums:
        if k - x in vistos:
            return True
        vistos.add(x)
    return False

assert existe_par([3, 1, 4], 7) is True
assert existe_par([3], 6) is False
assert existe_par([], 0) is False
assert existe_par([2, 2], 4) is True
print("ok")
```

A versão final roda em O(n) de tempo e O(n) de espaço. Note que os testes cobrem exatamente os casos levantados na etapa 2.

<Callout type="tip" title="Reconheça o tamanho de n">
Uma regra prática: n até 20 permite O(2ⁿ); até 500 permite O(n³); até 5.000 permite O(n²); até 10⁶ pede O(n log n) ou O(n). Use isso para descartar ideias antes de gastar tempo nelas.
</Callout>

## Na entrevista

Diga explicitamente em qual etapa você está: "antes de codar, quero confirmar as restrições" ou "essa é a força bruta, agora vou procurar o gargalo". O entrevistador avalia o processo tanto quanto o resultado. Se travar na otimização, apresente a força bruta funcionando: uma solução correta e lenta vale mais que uma rápida pela metade.
