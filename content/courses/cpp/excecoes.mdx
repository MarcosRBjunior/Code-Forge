Em Python você escreve `try/except` por reflexo; em C++ o mecanismo existe, mas a cultura é diferente. Muito código de desempenho (e boa parte das soluções de entrevista) evita exceções e usa valores de retorno, enquanto a biblioteca padrão as usa em situações precisas. Saber ler, lançar e capturar exceções, e principalmente saber como elas interagem com a memória, é o que o entrevistador testa.

## throw, try e catch

`throw` lança um valor (qualquer tipo, mas por convenção um objeto de uma classe derivada de `std::exception`). O controle sai da função atual, sobe a pilha de chamadas e procura o primeiro `catch` compatível. Capture sempre por referência constante (`const exception&`), para evitar cópia e o chamado "slicing" de classes derivadas. O método `what()` devolve a mensagem.

As classes de `<stdexcept>` que você mais usa: `runtime_error` (falha em execução), `invalid_argument` (argumento inválido), `out_of_range` (índice fora dos limites) e `logic_error` (a mãe das duas últimas).

```cpp
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>
using namespace std;

int dividir(int a, int b) {
    if (b == 0) throw runtime_error("divisao por zero");
    return a / b;
}

int main() {
    try {
        cout << dividir(10, 2) << "\n";
        cout << dividir(1, 0) << "\n";
    } catch (const exception& e) {
        cout << "erro: " << e.what() << "\n";
    }
    try {
        int n = stoi("abc");
        cout << n << "\n";
    } catch (const invalid_argument&) {
        cout << "nao e numero\n";
    }
    try {
        vector<int> v(3);
        int x = v.at(5);
        cout << x << "\n";
    } catch (const out_of_range&) {
        cout << "fora do intervalo\n";
    }
}
```

```text
Saída:
5
erro: divisao por zero
nao e numero
fora do intervalo
```

Duas armadilhas já aparecem aqui. Primeiro, `v[5]` não lança nada: é comportamento indefinido. Só `at()` verifica limites e lança `out_of_range`. Segundo, a divisão inteira por zero também não lança: a exceção do exemplo foi escrita por nós, porque o hardware apenas faz o programa quebrar.

## Desenrolar da pilha

Quando uma exceção sobe, o C++ destrói todos os objetos locais dos escopos que ela atravessa, chamando seus destrutores. Esse "stack unwinding" é o motivo de o RAII funcionar tão bem: arquivos fecham, locks liberam, memória volta.

```cpp
#include <iostream>
#include <string>
using namespace std;

struct Guarda {
    string n;
    Guarda(string s) : n(s) { cout << "entra " << n << "\n"; }
    ~Guarda() { cout << "sai " << n << "\n"; }
};

void f() {
    Guarda g("f");
    throw 42;
}

int main() {
    try {
        Guarda g("main");
        f();
        cout << "nao chega\n";
    } catch (int c) {
        cout << "capturou " << c << "\n";
    }
}
```

```text
Saída:
entra main
entra f
sai f
sai main
capturou 42
```

Os destrutores rodaram antes de o `catch` executar, na ordem inversa da criação. Se `f` tivesse feito `new` sem smart pointer, esse bloco vazaria: exceções e `delete` manual não combinam.

## noexcept e relançar

`noexcept` promete que a função não lança. Se lançar mesmo assim, o programa termina (`std::terminate`). Funções de movimentação devem ser `noexcept`: o `vector` só usa a movimentação ao realocar se ela não puder falhar, senão volta a copiar. Para repassar uma exceção que você capturou, use `throw;` sozinho, que preserva o tipo original. `catch (...)` captura qualquer coisa, mas sem acesso ao valor.

## Exceções ou códigos de retorno

| Abordagem | Quando usar |
| --- | --- |
| Exceção | Erro raro e realmente excepcional, que precisa cruzar várias camadas |
| `bool`, `optional`, código de erro | Falha esperada e frequente (busca sem resultado, entrada inválida) |

Lançar é caro (microssegundos), muito mais lento que um `if`. Por isso não se usa exceção para controle de fluxo em laços quentes.

## Armadilhas

- Capturar por valor (`catch (exception e)`) corta objetos derivados.
- Ordem dos `catch`: o primeiro compatível vence, então coloque os tipos mais específicos antes dos genéricos.
- Lançar de dentro de um destrutor durante o desenrolar termina o programa.
- `stoi` lança `invalid_argument` e `out_of_range`; entradas de entrevista raramente precisam disso.

## Na entrevista

Normalmente você valida a entrada e devolve um valor sentinela ou `optional` em vez de lançar, a não ser que o enunciado peça exceção. Cite que usaria `at()` para acesso seguro e `throw invalid_argument` para argumentos inválidos em código de produção. Follow-ups: "o que acontece com os objetos locais quando uma exceção é lançada?" e "por que o construtor de movimentação deve ser noexcept?".
