Na primeira versão do `ingressos`, um evento é um dicionário e as regras ficam em funções soltas. Funciona enquanto o programa é pequeno, mas tem dois defeitos que crescem com ele: qualquer trecho do código pode escrever `evento["vendidos"] = 9999` e deixar o evento num estado impossível, e um erro de digitação numa chave só aparece quando aquela linha roda. Os dados e as regras que os protegem estão em lugares diferentes, e nada obriga um a passar pelo outro.

A orientação a objetos resolve isso juntando os dois: uma classe define que dados um evento tem e quais operações são permitidas sobre eles. Este capítulo refaz o domínio com classes, do jeito que Python faz, que tem diferenças importantes para quem vem de Java ou C#.

**Você vai aprender:**

- Definir classes com `__init__`, atributos de instância e métodos
- Proteger o estado com encapsulamento por convenção e `@property`
- Dar representação e igualdade aos objetos com `__str__`, `__repr__` e `__eq__`
- Usar atributos de classe, `@classmethod` e `@staticmethod` no lugar certo
- Reduzir código repetitivo com `dataclasses`

## De dicionário a classe

Uma **classe** é o molde; um **objeto** (ou instância) é cada coisa criada a partir dele. O método `__init__` roda quando o objeto é criado e define seus atributos:

```python
# ingressos/modelos.py
from datetime import date


class Evento:
    def __init__(self, nome: str, data: date, local: str, capacidade: int) -> None:
        if not nome.strip():
            raise ValueError("o nome do evento é obrigatório")
        if capacidade <= 0:
            raise ValueError("a capacidade deve ser maior que zero")
        self.nome = nome.strip()
        self.data = data
        self.local = local
        self.capacidade = capacidade
        self._vendidos = 0
```

```python
show = Evento("Festival de Verão", date(2027, 1, 20), "Arena Norte", 500)
print(show.nome)            # Festival de Verão
print(type(show))           # <class 'ingressos.modelos.Evento'>
```

`self` é o próprio objeto. Em Python ele aparece explicitamente como primeiro parâmetro de todo método de instância, e `show.vender(2)` é o mesmo que `Evento.vender(show, 2)`. O nome `self` é convenção, mas é uma convenção que ninguém quebra.

A validação dentro do `__init__` cria uma garantia valiosa: não existe `Evento` com nome vazio ou capacidade negativa em nenhum ponto do sistema. Um objeto que nasce válido e só muda por métodos que preservam a validade dispensa verificações espalhadas pelo código.

## Métodos: comportamento junto dos dados

```python
class Evento:
    # __init__ como acima

    def vender(self, quantidade: int) -> None:
        if quantidade < 1:
            raise ValueError("a quantidade deve ser pelo menos 1")
        if quantidade > self.quantidade_disponivel:
            raise ValueError(
                f"restam apenas {self.quantidade_disponivel} ingressos para {self.nome}"
            )
        self._vendidos += quantidade

    def cancelar(self, quantidade: int) -> None:
        if quantidade < 1 or quantidade > self._vendidos:
            raise ValueError("quantidade de cancelamento inválida")
        self._vendidos -= quantidade
```

A regra "não vender acima da capacidade" agora tem um único endereço. Quem quer vender chama `evento.vender(3)`, e não há outra forma legítima de alterar o total vendido. Esse é o sentido prático de encapsulamento: o objeto é responsável pelo próprio estado.

Repare que `vender` diz ao objeto o que fazer, em vez de perguntar os dados e decidir do lado de fora. Código que faz `if evento.capacidade - evento.vendidos >= 3: evento.vendidos += 3` repete a regra em cada lugar que vende.

## Encapsulamento por convenção e @property

Python não tem `private`. O que existe é convenção:

| Forma | Significado | O que o interpretador faz |
|---|---|---|
| `nome` | Público, parte da interface da classe | Nada |
| `_vendidos` | Interno: não acesse de fora da classe | Nada, é um acordo entre programadores |
| `__codigo` | Evita colisão de nomes em subclasses | Renomeia para `_Evento__codigo` (name mangling) |
| `__init__` | Método especial, chamado pelo interpretador | Não invente nomes nesse formato |

O sublinhado simples basta em quase todos os casos. O sublinhado duplo não é segurança (o atributo continua acessível pelo nome transformado), e seu uso real é raro.

Para expor um valor interno somente para leitura, ou um valor calculado, use `@property`: um método que se acessa como atributo.

```python
class Evento:
    # __init__, vender e cancelar como acima

    @property
    def vendidos(self) -> int:
        return self._vendidos

    @property
    def quantidade_disponivel(self) -> int:
        return self.capacidade - self._vendidos

    @property
    def esgotado(self) -> bool:
        return self.quantidade_disponivel == 0
```

```python
show.vender(3)
print(show.vendidos)                # 3
print(show.quantidade_disponivel)   # 497
show.vendidos = 100                 # AttributeError: a property não tem setter
```

Quando a atribuição deve ser permitida, mas com validação, acrescente um setter. Para isso o valor passa a morar num atributo interno:

```python
class Evento:
    def __init__(self, nome: str, data: date, local: str, capacidade: int) -> None:
        self.nome = nome
        self.data = data
        self.local = local
        self._vendidos = 0
        self.capacidade = capacidade      # passa pelo setter abaixo

    @property
    def capacidade(self) -> int:
        return self._capacidade

    @capacidade.setter
    def capacidade(self, valor: int) -> None:
        if valor <= 0:
            raise ValueError("a capacidade deve ser maior que zero")
        if valor < self._vendidos:
            raise ValueError("a capacidade não pode ficar abaixo do total já vendido")
        self._capacidade = valor
```

<Callout type="tip" title="Não escreva getters e setters por reflexo">
Em Java, criar `getNome` e `setNome` para todo campo é hábito porque trocar um campo público por um método depois quebra quem usa a classe. Em Python, você pode começar com o atributo público `evento.nome` e, no dia em que precisar de validação, transformá-lo em `@property` sem mudar uma linha de quem o usa. Getters e setters que só repassam o valor são ruído.
</Callout>

## Representação e igualdade

Sem ajuda, `print(show)` mostra algo como `<ingressos.modelos.Evento object at 0x...>`. Dois métodos especiais resolvem:

```python
class Evento:
    # ...

    def __repr__(self) -> str:
        return (
            f"Evento(nome={self.nome!r}, data={self.data!r}, "
            f"local={self.local!r}, capacidade={self.capacidade})"
        )

    def __str__(self) -> str:
        return f"{self.nome} ({self.data:%d/%m/%Y}, {self.local})"
```

- `__repr__` é para quem programa: aparece no REPL, no depurador, nos logs e quando o objeto está dentro de uma lista. Deve ser inequívoco, de preferência parecido com o código que cria o objeto. O `!r` aplica o `repr` do valor, pondo aspas nos textos.
- `__str__` é para o usuário final: é o que `print` e `str()` usam. Se não existir, o Python usa o `__repr__`. Por isso, se for escrever só um, escreva o `__repr__`.

Por padrão, `==` entre dois objetos compara identidade: só é verdadeiro se forem o mesmo objeto na memória. Para comparar por valor, defina `__eq__`:

```python
class Evento:
    # ...

    def __eq__(self, outro: object) -> bool:
        if not isinstance(outro, Evento):
            return NotImplemented
        return (self.nome, self.data, self.local) == (outro.nome, outro.data, outro.local)

    def __hash__(self) -> int:
        return hash((self.nome, self.data, self.local))
```

Devolver `NotImplemented` (e não `False`) dá ao outro objeto a chance de fazer a comparação. O `__hash__` acompanha o `__eq__` porque uma classe que define só o `__eq__` perde a capacidade de ser chave de dicionário ou item de `set`. A regra é: objetos iguais precisam ter o mesmo hash, e o hash deve se basear em valores que não mudam.

Existem dezenas de métodos especiais, e eles são o que faz um objeto seu se comportar como os embutidos: `__len__` para `len(obj)`, `__lt__` para ordenar, `__contains__` para `in`, `__iter__` para `for`.

## Atributos de classe, classmethod e staticmethod

Um atributo definido no corpo da classe pertence à classe, e é compartilhado por todas as instâncias:

```python
from datetime import date, datetime


class Evento:
    LIMITE_POR_COMPRA = 6          # atributo de classe: vale para todos os eventos

    def __init__(self, nome: str, data: date, local: str, capacidade: int) -> None:
        self.nome = nome
        self.data = data
        self.local = local
        self.capacidade = capacidade
        self._vendidos = 0

    @classmethod
    def de_texto(cls, linha: str) -> "Evento":
        nome, data, local, capacidade = linha.split(";")
        return cls(
            nome=nome,
            data=datetime.strptime(data, "%d/%m/%Y").date(),
            local=local,
            capacidade=int(capacidade),
        )

    @staticmethod
    def data_valida(data: date) -> bool:
        return data >= date.today()
```

```python
show = Evento.de_texto("Sarau;14/03/2027;Teatro Central;80")
print(show.LIMITE_POR_COMPRA)      # 6, lido da classe
```

| Tipo | Primeiro parâmetro | Para que serve |
|---|---|---|
| Método de instância | `self` (o objeto) | Ler ou alterar o estado de um objeto |
| `@classmethod` | `cls` (a classe) | Construtores alternativos e operações sobre a classe |
| `@staticmethod` | Nenhum | Função utilitária que faz sentido dentro do nome da classe |

O `@classmethod` é a forma de ter "mais de um construtor", já que Python não tem sobrecarga: `Evento.de_texto(...)`, `Evento.de_dict(...)`. Usar `cls(...)` em vez de `Evento(...)` faz o método funcionar também em subclasses.

<Callout type="warning" title="Atributo de classe mutável é compartilhado">
Escrever `setores = []` no corpo da classe cria uma única lista, dividida por todos os eventos: adicionar um setor ao primeiro faz ele aparecer no segundo. Listas, dicionários e conjuntos que pertencem a cada objeto devem ser criados dentro do `__init__`, com `self.setores = []`. Atributos de classe servem para constantes.
</Callout>

## Dataclasses

Muitas classes existem principalmente para carregar dados, e escrever `__init__`, `__repr__` e `__eq__` à mão para cada uma é repetição. O decorador `@dataclass` gera os três a partir das anotações de tipo:

```python
from dataclasses import dataclass, field
from decimal import Decimal


@dataclass
class Setor:
    nome: str
    preco: Decimal
    quantidade: int
    vendidos: int = 0

    def __post_init__(self) -> None:
        if self.preco < 0:
            raise ValueError("o preço não pode ser negativo")
        if self.quantidade <= 0:
            raise ValueError("a quantidade deve ser maior que zero")

    @property
    def quantidade_disponivel(self) -> int:
        return self.quantidade - self.vendidos


@dataclass
class Evento:
    nome: str
    data: date
    local: str
    setores: list[Setor] = field(default_factory=list)

    @property
    def capacidade(self) -> int:
        return sum(setor.quantidade for setor in self.setores)
```

```python
pista = Setor("Pista", Decimal("120.00"), 400)
print(pista)        # Setor(nome='Pista', preco=Decimal('120.00'), quantidade=400, vendidos=0)
print(pista == Setor("Pista", Decimal("120.00"), 400))    # True
```

Os pontos que importam:

- **`__post_init__`** roda depois do `__init__` gerado, e é onde entram as validações.
- **`field(default_factory=list)`** cria uma lista nova para cada objeto. Escrever `setores: list[Setor] = []` é o mesmo erro do valor padrão mutável, e a dataclass recusa com `ValueError`.
- **Campos com padrão vêm depois dos sem padrão**, como em parâmetros de função.

Para **objetos de valor**, que são definidos pelo conteúdo e não mudam, use `frozen=True`:

```python
@dataclass(frozen=True)
class Endereco:
    logradouro: str
    cidade: str
    uf: str
    cep: str


local = Endereco("Av. Central, 100", "Recife", "PE", "50000-000")
local.cidade = "Olinda"      # FrozenInstanceError
```

Uma dataclass congelada é imutável, ganha `__hash__` automaticamente e pode ser chave de dicionário. `@dataclass(slots=True)` reduz o consumo de memória e impede a criação de atributos fora dos declarados, o que transforma um erro de digitação como `setor.vendido = 3` em exceção.

| Situação | Escolha |
|---|---|
| Dados com pouca ou nenhuma regra | `@dataclass` |
| Valor imutável comparado pelo conteúdo (endereço, dinheiro, período) | `@dataclass(frozen=True)` |
| Estado protegido por várias regras, com atributos internos | Classe comum com `__init__` e propriedades |

## Objetos trabalhando juntos

O domínio começa a tomar forma quando os objetos colaboram. O `Evento` tem setores e delega a venda ao setor certo:

```python
@dataclass
class Evento:
    nome: str
    data: date
    local: str
    setores: list[Setor] = field(default_factory=list)

    def adicionar_setor(self, setor: Setor) -> None:
        if any(existente.nome == setor.nome for existente in self.setores):
            raise ValueError(f"o evento já tem um setor chamado {setor.nome}")
        self.setores.append(setor)

    def buscar_setor(self, nome: str) -> Setor:
        for setor in self.setores:
            if setor.nome == nome:
                return setor
        raise ValueError(f"setor {nome} não existe em {self.nome}")
```

Cada classe cuida do que conhece: o `Evento` sabe quais setores tem, o `Setor` sabe quantos ingressos restam. Ainda falta dar ao `Setor` um método `vender`, tarefa da prática abaixo.

## Na entrevista

**O que é `self`?** É a referência ao objeto sobre o qual o método foi chamado, passada automaticamente como primeiro argumento. Em Python ela é explícita na assinatura, e é por meio dela que o método lê e altera os atributos da instância.

**Qual a diferença entre `__str__` e `__repr__`?** `__repr__` é a representação para desenvolvedores, inequívoca, usada no REPL, em logs e em coleções. `__str__` é a representação legível para o usuário, usada por `print`. Se `__str__` não existir, o Python recorre ao `__repr__`.

**Python tem atributos privados?** Não no sentido de Java. Um sublinhado inicial é convenção de uso interno, respeitada pelos programadores e não imposta pelo interpretador. Dois sublinhados ativam o name mangling, que evita colisões em subclasses, mas não impede o acesso.

**Quando usar `@classmethod` e quando `@staticmethod`?** `@classmethod` recebe a classe e serve para construtores alternativos, respeitando subclasses. `@staticmethod` não recebe nem instância nem classe: é uma função comum agrupada na classe por organização.

**Qual a diferença entre atributo de classe e de instância?** O de classe é único e compartilhado por todas as instâncias; o de instância é criado em cada objeto, normalmente no `__init__`. Atribuir pelo objeto (`obj.x = 1`) cria um atributo de instância que encobre o de classe.

**O que uma dataclass gera e quando você não a usaria?** Gera `__init__`, `__repr__` e `__eq__` (e mais com parâmetros como `frozen` e `order`). Eu não a usaria quando a classe tem estado interno protegido por muitas regras, em que um `__init__` escrito à mão deixa as garantias mais claras.

## Pratique

1. Crie `ingressos/modelos.py` com `Setor` e `Evento` e troque os dicionários do programa de terminal por objetos. O menu continua igual; as regras saem de `eventos.py` e vão para as classes.
2. Dê ao `Setor` os métodos `vender(quantidade)` e `devolver(quantidade)`, com as validações de estoque, e ao `Evento` um método `vender(nome_setor, quantidade)` que delega ao setor.
3. Crie o objeto de valor `Dinheiro` como dataclass congelada, com `valor: Decimal` e `moeda: str`, e implemente `__add__` recusando a soma de moedas diferentes.
4. Adicione ao `Evento` o construtor alternativo `de_dict(dados)` como `@classmethod` e o método `para_dict()`. Eles serão usados quando os eventos forem gravados em arquivo.
5. Implemente `__lt__` em `Evento` comparando pela data e confira que `sorted(lista_de_eventos)` funciona sem o argumento `key`.
