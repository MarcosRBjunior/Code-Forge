O `ingressos` já funciona na sua máquina, e é exatamente aí que mora o risco. Uma alteração mal pensada apaga o que funcionava ontem, a pasta `ingressos-final-v2-agora-vai` aparece, e ninguém mais consegue contribuir sem trocar arquivos compactados. Toda equipe de desenvolvimento resolve isso do mesmo jeito: Git para registrar o histórico do código e uma plataforma como o GitHub para compartilhar e revisar.

Em vaga de back-end, Git não é diferencial, é pré-requisito. Espera-se que você saiba criar uma branch, abrir um pull request, resolver um conflito sem pânico e desfazer um erro sem destruir o trabalho dos outros. Este capítulo cobre esse fluxo, usando o projeto Python como exemplo.

**Você vai aprender:**

- Registrar o histórico com `add` e `commit`, entendendo as três áreas do Git
- Escrever um `.gitignore` adequado a projetos Python
- Trabalhar com branches, fazer merge e resolver conflitos
- Sincronizar com o GitHub usando `push`, `fetch` e `pull`
- Colaborar por pull request e desfazer erros do jeito certo

## O que o Git guarda

O Git é um sistema de controle de versão **distribuído**: cada clone tem o histórico completo, e quase tudo funciona sem rede. O histórico é uma sequência de **commits**. Cada commit é uma fotografia de todos os arquivos versionados num momento, com autor, data, mensagem e um ponteiro para o commit anterior. O identificador do commit é um hash calculado a partir desse conteúdo, e por isso qualquer alteração no passado muda os hashes dali em diante.

Configure a identidade uma vez por máquina:

```bash
git config --global user.name "Seu Nome"
git config --global user.email "voce@exemplo.com"
git config --global init.defaultBranch main
```

## As três áreas e o primeiro commit

Um arquivo passa por três lugares:

| Área | O que é | Comando que move para a próxima |
|---|---|---|
| Diretório de trabalho | Os arquivos como estão no disco | `git add` |
| Staging (index) | O que vai entrar no próximo commit | `git commit` |
| Repositório | O histórico de commits, na pasta `.git` | `git push` (para o remoto) |

O staging existe para você escolher o que entra em cada commit. Se você corrigiu um bug e, no caminho, renomeou uma função em outro arquivo, pode registrar as duas coisas em commits separados.

```bash
cd ingressos-app
git init
git status                      # mostra arquivos não rastreados
git add ingressos/              # prepara a pasta do pacote
git status                      # agora aparecem como "a serem commitados"
git commit -m "Adiciona cadastro e listagem de eventos no terminal"
git log --oneline               # histórico resumido
```

Antes de cada commit, olhe o que vai entrar:

```bash
git diff             # mudanças ainda fora do staging
git diff --staged    # mudanças já preparadas
```

Uma boa mensagem diz o que o commit faz, no imperativo, em até umas 70 letras na primeira linha: "Impede cadastro de evento com data no passado". Se precisar explicar o motivo, deixe uma linha em branco e escreva um parágrafo. "Ajustes" e "correções" não ajudam ninguém a encontrar o commit que introduziu um problema.

## .gitignore para Python

Nem tudo que está na pasta pertence ao repositório. Crie o arquivo `.gitignore` na raiz antes do primeiro `git add`:

```text
# ambiente virtual
.venv/

# arquivos gerados pelo interpretador e por ferramentas
__pycache__/
*.py[cod]
.pytest_cache/
.mypy_cache/
.ruff_cache/
.coverage
htmlcov/

# empacotamento
build/
dist/
*.egg-info/

# configuração local e segredos
.env

# dados locais
*.db
*.sqlite3

# editor e sistema
.vscode/
.idea/
.DS_Store
```

A regra geral: versione o que um humano escreveu e o que é necessário para reconstruir o resto. O `.venv` é recriado a partir da lista de dependências, o `__pycache__` é gerado pelo interpretador e o `.env` guarda senhas e chaves.

<Callout type="warning" title="Segredo commitado é segredo vazado">
Adicionar o arquivo ao `.gitignore` depois de commitá-lo não o remove do histórico, e apagar o arquivo num commit novo também não: o conteúdo continua acessível nos commits antigos. Se uma senha ou chave de API chegou ao repositório remoto, troque a credencial imediatamente. Reescrever o histórico vem depois, e não substitui a troca.
</Callout>

Se um arquivo já rastreado deveria ser ignorado, tire-o do índice sem apagá-lo do disco com `git rm --cached caminho/do/arquivo` e faça o commit.

## Branches

Uma **branch** é um ponteiro móvel para um commit. Criar uma branch não copia arquivos: cria um nome que avança junto com os commits que você fizer nela. `HEAD` é o ponteiro para a branch em que você está.

O hábito que as equipes cobram: a `main` sempre funciona, e todo trabalho acontece numa branch própria.

```bash
git switch -c feature/venda-de-ingressos    # cria a branch e muda para ela
# edite ingressos/eventos.py e ingressos/terminal.py
git add ingressos/
git commit -m "Adiciona venda de ingressos com validação de estoque"

git switch main                             # volta para a main
git branch                                  # lista as branches locais
```

`git switch` troca de branch e `git restore` descarta mudanças em arquivos. Os dois substituem os usos do antigo `git checkout`, que ainda funciona e aparece em muito material.

## Merge

Para trazer o trabalho de uma branch para outra, vá para a branch de destino e faça o merge:

```bash
git switch main
git merge feature/venda-de-ingressos
```

O Git escolhe entre dois comportamentos:

- **Fast-forward**: se a `main` não recebeu commits desde que a branch nasceu, o Git só avança o ponteiro da `main`. O histórico fica linear, sem commit novo.
- **Merge commit**: se as duas branches avançaram, o Git cria um commit com dois pais, que une as duas linhas de histórico.

```bash
git log --oneline --graph --all     # desenha as linhas do histórico
git branch -d feature/venda-de-ingressos   # apaga a branch já integrada
```

A alternativa ao merge é o **rebase**, que reaplica os commits da sua branch em cima da ponta atual da `main`, como se você tivesse começado hoje. O resultado é um histórico linear, mas com commits novos (hashes diferentes). Por isso a regra: faça rebase só em commits que ainda não foram compartilhados, ou que estão numa branch em que só você trabalha.

## Conflitos

Um conflito acontece quando as duas branches alteraram o mesmo trecho do mesmo arquivo. O Git não adivinha quem tem razão: ele para o merge e marca o arquivo.

```python
def quantidade_disponivel(evento: dict) -> int:
<<<<<<< HEAD
    return max(evento["capacidade"] - evento["vendidos"], 0)
=======
    reservados = evento.get("reservados", 0)
    return evento["capacidade"] - evento["vendidos"] - reservados
>>>>>>> feature/reserva-de-ingressos
```

Entre `<<<<<<< HEAD` e `=======` está a versão da branch atual; entre `=======` e `>>>>>>>` está a versão que vem chegando. Resolver é editar o arquivo até ele ficar como deve, o que muitas vezes significa combinar as duas versões, e remover os marcadores:

```python
def quantidade_disponivel(evento: dict) -> int:
    reservados = evento.get("reservados", 0)
    return max(evento["capacidade"] - evento["vendidos"] - reservados, 0)
```

```bash
git status                       # lista os arquivos em conflito
python -m ingressos              # rode o programa (ou os testes) antes de concluir
git add ingressos/eventos.py     # marca como resolvido
git commit                       # conclui o merge
```

Se você se perdeu, `git merge --abort` devolve tudo ao estado anterior ao merge. Conflitos ficam raros e pequenos quando as branches vivem pouco e você atualiza a sua com a `main` com frequência.

## Repositório remoto e GitHub

O GitHub hospeda uma cópia do repositório, o **remoto**, que por convenção se chama `origin`. Crie o repositório vazio no GitHub e conecte:

```bash
git remote add origin git@github.com:seu-usuario/ingressos.git
git push -u origin main          # envia a main e define o rastreamento
```

O endereço `git@github.com:...` usa SSH, que exige cadastrar uma chave pública na sua conta (gerada com `ssh-keygen -t ed25519`). A alternativa é HTTPS com um personal access token ou com a CLI `gh` fazendo o login. Senha da conta não funciona para operações de Git.

Os três comandos de sincronização:

| Comando | O que faz |
|---|---|
| `git fetch` | Baixa os commits do remoto e atualiza `origin/main`, sem tocar nas suas branches |
| `git pull` | `fetch` seguido de merge (ou rebase) na branch atual |
| `git push` | Envia os commits locais da branch para o remoto |

Se alguém enviou commits antes de você, o `push` é rejeitado: o remoto tem histórico que você não tem. Faça `git pull`, resolva o que precisar e envie de novo. Para começar a partir de um repositório existente, `git clone <endereço>` baixa tudo e já configura o `origin`.

<Callout type="warning" title="Cuidado com o push forçado">
`git push --force` sobrescreve o histórico do remoto com o seu e apaga commits de colegas que você ainda não tinha baixado. Numa branch só sua, depois de um rebase, use `git push --force-with-lease`, que recusa o envio se o remoto mudou desde o seu último fetch. Em `main` e em branches compartilhadas, não force.
</Callout>

## Pull request

O **pull request** (PR) é o pedido para integrar uma branch na `main`, com espaço para revisão. O fluxo mais usado, conhecido como GitHub Flow:

```bash
git switch main
git pull                                   # parte da main atualizada
git switch -c feature/cancelar-pedido
# trabalhe, com commits pequenos
git push -u origin feature/cancelar-pedido
```

No GitHub, abra o PR da sua branch para a `main`. Um bom PR tem título que diz o que muda, descrição com o motivo e como testar, e um tamanho que alguém consiga revisar em poucos minutos. Os comentários de revisão viram novos commits na mesma branch (`git push` atualiza o PR). Quando aprovado, o merge acontece pela interface, em uma de três formas:

| Opção | Resultado na main | Quando usar |
|---|---|---|
| Merge commit | Todos os commits da branch e um commit de merge | Quando o histórico detalhado da branch importa |
| Squash and merge | Um único commit com tudo | Padrão em muitas equipes: main limpa, um commit por PR |
| Rebase and merge | Os commits da branch reaplicados em linha | Histórico linear, com commits bem organizados |

Depois do merge, apague a branch remota e atualize a máquina: `git switch main`, `git pull`, `git branch -d feature/cancelar-pedido`.

Para contribuir com um projeto em que você não tem permissão de escrita, faça um **fork** (uma cópia do repositório na sua conta), trabalhe nele e abra o PR do fork para o original.

## Desfazendo

| Situação | Comando | Observação |
|---|---|---|
| Descartar mudanças não preparadas num arquivo | `git restore arquivo.py` | A mudança é perdida de vez |
| Tirar um arquivo do staging | `git restore --staged arquivo.py` | A mudança continua no disco |
| Corrigir a mensagem ou incluir algo no último commit | `git commit --amend` | Só se o commit ainda não foi enviado |
| Desfazer um commit já enviado | `git revert <hash>` | Cria um commit novo que inverte o anterior |
| Voltar a branch local a um commit anterior | `git reset --hard <hash>` | Apaga commits e mudanças locais; só em histórico não compartilhado |
| Guardar mudanças para trocar de branch | `git stash` e depois `git stash pop` | Pilha temporária |

A distinção que as entrevistas cobram: `revert` preserva o histórico e é seguro em branches compartilhadas; `reset` reescreve o histórico e só serve para o que ainda é só seu. E se um `reset` apagou algo que você queria, `git reflog` lista por onde o `HEAD` passou e permite voltar a um commit que parecia perdido.

## Na entrevista

**Qual a diferença entre `git fetch` e `git pull`?** `fetch` baixa os commits do remoto e atualiza as referências remotas, sem alterar a branch local. `pull` faz o `fetch` e em seguida integra (merge ou rebase) na branch atual. Com `fetch` você inspeciona antes de integrar.

**Merge ou rebase?** Merge preserva o histórico como aconteceu e cria um commit de merge quando as linhas divergem. Rebase reaplica os commits sobre uma nova base e gera histórico linear, mas reescreve hashes, então só se usa em commits não compartilhados.

**Qual a diferença entre `git reset` e `git revert`?** `reset` move o ponteiro da branch para outro commit, apagando commits do histórico local. `revert` cria um commit novo que desfaz as alterações de um commit anterior. Em branch compartilhada, a escolha é `revert`.

**Como você resolve um conflito de merge?** Abro os arquivos marcados, entendo o que cada lado quis fazer (se preciso, converso com o autor), edito para o resultado correto, removo os marcadores, rodo os testes, faço `git add` e concluo o merge. Se a situação ficar confusa, `git merge --abort` e recomeço.

**Para que serve o staging?** Para montar o commit com precisão. Ele permite separar em commits distintos mudanças que estão juntas no diretório de trabalho e revisar com `git diff --staged` exatamente o que será registrado.

**Um segredo foi commitado e enviado. O que você faz?** Revogo e troco a credencial na hora, porque o histórico já pode ter sido copiado. Depois removo o arquivo, adiciono ao `.gitignore` e, se for política da equipe, reescrevo o histórico com uma ferramenta própria para isso.

## Pratique

1. Inicie o repositório do `ingressos`, crie o `.gitignore` de Python e faça o primeiro commit. Confirme com `git status` que `.venv` e `__pycache__` não aparecem.
2. Crie a branch `feature/buscar-evento`, implemente a busca por nome em dois commits pequenos e faça o merge na `main`. Veja o resultado com `git log --oneline --graph`.
3. Provoque um conflito: em duas branches diferentes, altere a mesma linha de `quantidade_disponivel`. Faça o merge, resolva combinando as duas ideias e rode o programa antes de concluir.
4. Publique o repositório no GitHub, envie uma branch nova e abra um pull request com descrição do que muda e de como testar. Faça o merge com squash e sincronize a `main` local.
5. Em uma branch de teste, faça um commit errado, desfaça com `git revert` e depois experimente `git reset --hard` e a recuperação com `git reflog`.
