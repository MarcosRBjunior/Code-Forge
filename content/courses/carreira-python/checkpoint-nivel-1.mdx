O Nível 1 levou o `ingressos` de um script com dicionários a uma plataforma de verdade. No caminho, o domínio virou classes com regras protegidas, os dados foram de arquivos JSON para o PostgreSQL, a mesma reserva ganhou três portas de entrada (uma API Flask com MongoDB, o site em Django e a API em FastAPI) e, no fim, a regra "não vender acima da capacidade" saiu de dentro dos frameworks e foi morar num núcleo testável, organizado com arquitetura em camadas e SOLID.

Este checkpoint confere se essas peças ficaram de pé juntas. Não há conteúdo novo: você revisa o que o nível cobriu, mede o que já consegue fazer sem consultar o material e encara um desafio que atravessa o nível inteiro. Se o desafio sair sem travar, você está pronto para o Nível 2.

**Neste checkpoint:**

- Revisar os 14 capítulos do nível e o que cada um exige de você
- Fazer uma autoavaliação com habilidades que dá para provar no código
- Construir a reserva de ingressos de ponta a ponta, com núcleo único e dois canais (site Django e API FastAPI)
- Rever os erros mais comuns do nível e as perguntas de entrevista que eles geram
- Fechar com seis quizzes que misturam os capítulos

## Desafio prático

O time decidiu que a reserva de ingressos precisa funcionar em dois canais: o site em Django, para quem compra pelo navegador, e a API em FastAPI, para o aplicativo e os parceiros. Hoje cada canal tem a sua cópia da regra de capacidade, e elas já divergiram. Sua tarefa é entregar a versão 1.0 do `ingressos` com um núcleo único de reservas, usado pelos dois canais, num repositório que um colega consiga clonar e rodar.

### Requisitos

1. **Repositório.** Projeto em Git com `.gitignore` para Python, `pyproject.toml` com as dependências e um README com os comandos para subir e testar. Cada requisito abaixo entra por uma branch e um pull request próprios.
2. **Domínio puro.** Em `ingressos/dominio/modelos.py`, `Setor` e `Pedido` como dataclasses sem importar Django nem SQLAlchemy. `Setor.reservar` rejeita quantidade não positiva e quantidade acima do disponível; o pedido nasce `pendente` com prazo de 15 minutos.
3. **Preço por tipo de ingresso.** Inteira, meia-entrada (metade do preço, exige documento) e cortesia (preço zero) calculados por polimorfismo, sem `if` sobre o tipo no serviço.
4. **Serviço de reserva.** Em `ingressos/servicos/reservas.py`, a função `reservar` recebe uma unidade de trabalho pelas portas definidas em `ingressos/dominio/portas.py` e devolve o id do pedido. Testes com fakes em memória cobrem sucesso, setor inexistente e estoque insuficiente.
5. **Site Django.** Vitrine com lista e detalhe de eventos publicados e futuros, dados no PostgreSQL com constraints (`setor_unico_por_evento`, preço não negativo), Admin com filtros por data e local, e listagem sem N+1.
6. **Contas no site.** Cadastro, login com e-mail e senha e login com Google pelo django-allauth. A página "Meus pedidos" exige login e mostra só os pedidos do usuário; o formulário de reserva exibe "Reserva feita" ou "Setor esgotado" pelo framework de mensagens.
7. **API FastAPI.** `GET /eventos` público, `POST /eventos` só para administrador (201), `POST /eventos/{evento_id}/reservas` com JWT, respondendo 201 na reserva e 409 sem estoque. Migrações com Alembic.
8. **Local do evento por CEP.** Ao cadastrar um evento, o endereço é completado por um cliente HTTP com timeout, que distingue CEP inexistente de serviço fora do ar e não derruba o cadastro no segundo caso.
9. **Concorrência.** A baixa de estoque é atômica nos dois canais: duas reservas simultâneas do último ingresso resultam em um sucesso e um erro, nunca em estoque negativo.
10. **Bônus com IA.** Uma rota `POST /suporte/triagem` que classifica a mensagem do cliente com um LLM, valida a saída com Pydantic e devolve 503 com mensagem clara quando o provedor não responde.

Um ponto de partida para a porta do serviço, no formato que o capítulo de arquitetura usa:

```python
# ingressos/dominio/portas.py
from typing import Protocol, Self
from uuid import UUID

from ingressos.dominio.modelos import Pedido, Setor


class RepositorioSetores(Protocol):
    def obter_para_atualizar(self, setor_id: int) -> Setor | None: ...
    def salvar(self, setor: Setor) -> None: ...


class RepositorioPedidos(Protocol):
    def adicionar(self, pedido: Pedido) -> None: ...
    def obter(self, pedido_id: UUID) -> Pedido | None: ...


class UnidadeDeTrabalho(Protocol):
    setores: RepositorioSetores
    pedidos: RepositorioPedidos

    def __enter__(self) -> Self: ...
    def __exit__(self, *exc: object) -> None: ...
    def commit(self) -> None: ...
    def rollback(self) -> None: ...
```

E o formato do primeiro teste do serviço, que deve rodar antes de existir qualquer banco:

```python
# tests/test_reservas.py
from datetime import datetime, timezone
from decimal import Decimal

import pytest

from ingressos.dominio.modelos import EstoqueInsuficiente, Setor
from ingressos.servicos.reservas import reservar
from tests.fakes import UnidadeDeTrabalhoMemoria

AGORA = datetime(2030, 3, 1, 20, 0, tzinfo=timezone.utc)


def test_reserva_baixa_estoque_e_cria_pedido():
    uow = UnidadeDeTrabalhoMemoria([Setor(1, "Pista", Decimal("120.00"), 10)])
    pedido_id = reservar(uow, cliente_id=7, setor_id=1, quantidade=2, agora=AGORA)
    assert uow.setores.dados[1].quantidade_disponivel == 8
    assert uow.pedidos.obter(pedido_id) is not None
    assert uow.confirmado


def test_sem_estoque_nao_confirma():
    uow = UnidadeDeTrabalhoMemoria([Setor(1, "Pista", Decimal("120.00"), 1)])
    with pytest.raises(EstoqueInsuficiente):
        reservar(uow, cliente_id=7, setor_id=1, quantidade=2, agora=AGORA)
    assert not uow.confirmado
```

### Critérios de aceite

- `pytest` passa do zero num clone limpo, com testes do serviço que não abrem conexão com banco nenhum.
- `python manage.py check` e `python manage.py makemigrations --check` não acusam pendências; `alembic upgrade head` roda sem erro num banco vazio.
- `curl -i -X POST localhost:8000/eventos` sem token devolve `401`; com token de cliente comum, `403`; com token de administrador, `201` e cabeçalho de conteúdo JSON.
- Reservar mais ingressos do que restam devolve `409` na API e a mensagem "Setor esgotado" no site, e o estoque no banco continua o mesmo.
- Um cliente logado que acessa a URL de um pedido de outra pessoa recebe `404`.
- A página de lista de eventos executa um número fixo de consultas, independente da quantidade de eventos (confira com `assertNumQueries` ou com o log do banco).
- Um teste dispara duas reservas concorrentes para um setor com 1 lugar e confirma um sucesso, uma falha e estoque zero.
- O histórico do Git mostra um pull request por requisito, sem commits de "ajustes finais" com dezenas de arquivos.

### Dicas

- Comece pelo domínio e pelo serviço, com os fakes do capítulo de [arquitetura](/learn/carreira-python/python-fundamentos-padroes-arquitetura-software). Só depois escreva os adaptadores do Django e do SQLAlchemy: se o serviço estiver certo, cada canal vira uma casca fina.
- Para a atomicidade, no adaptador SQL use `SELECT ... FOR UPDATE` dentro da unidade de trabalho, ou o `update()` condicional que o capítulo de [persistência](/learn/carreira-python/python-persistencia-dados-arquivos-bancos-dados) mostra. Ler, subtrair em Python e salvar sem trava é a armadilha clássica.
- No Django, o filtro por dono vai no queryset, não num `if` depois de buscar o pedido. Reveja a seção de proteção de views em [autenticação e formulários](/learn/carreira-python/django-autenticacao-formularios-alerta).
- No FastAPI, declare a rota de reserva com `def`, não `async def`, enquanto a sessão do SQLAlchemy for síncrona. O motivo está no capítulo de [FastAPI](/learn/carreira-python/fastapi-python-construindo-apis-autenticacao-banco-dados).
- O cliente de CEP do capítulo de [OO e API](/learn/carreira-python/python-avance-orientacao-objetos-consuma-api) já separa `CepNaoEncontrado` de `ServicoCepIndisponivel`: reaproveite a ideia e injete o cliente para testá-lo sem rede.
- Use o assistente de código com tarefas pequenas e verificáveis, e confira versões: Pydantic 2, SQLAlchemy 2.0 e Django 5.2. Sugestões com `@validator` ou `session.query` são sinal de material antigo.

## Revisão rápida

**Consulta parametrizada.** O driver envia o valor separado do SQL; interpolar com f-string permite que o valor vire comando. No `sqlite3` o marcador é `?`, no `psycopg` é `%s`.

```python
# ingressos/banco.py
conexao.execute("SELECT * FROM eventos WHERE local = ?", (local,))
```

**Ler e escrever não é atômico.** `setor.quantidade_disponivel -= 1` seguido de `save()` perde vendas sob concorrência. A atualização precisa ser condicional e acontecer no banco, conferindo quantas linhas mudaram.

```python
# eventos/servicos.py
atualizados = Setor.objects.filter(
    pk=setor_id, quantidade_disponivel__gte=quantidade
).update(quantidade_disponivel=F("quantidade_disponivel") - quantidade)
```

**N+1.** Acessar `evento.setores` dentro do laço do template gera uma consulta por evento. `select_related` resolve chave estrangeira com JOIN; `prefetch_related` resolve relação reversa e muitos-para-muitos com uma consulta extra.

**401 ou 403.** 401 significa "não sei quem você é" (sem token ou token inválido). 403 significa "sei quem você é e você não pode". Recurso de outro dono deve dar 404, para não confirmar que ele existe.

**`async def` com código bloqueante.** Uma rota `async def` que chama uma `Session` síncrona trava o event loop e atrasa todas as requisições do processo. Use `def` ou adote `AsyncSession` com driver assíncrono.

**Trocar dependências nos testes.** O FastAPI troca `get_session` e `get_usuario_atual` em `app.dependency_overrides`, e o teste precisa limpar o dicionário ao final para não vazar estado.

**Validar JWT fixando o algoritmo.** Sem a lista de algoritmos aceitos, um token forjado pode escolher o algoritmo no próprio cabeçalho. `InvalidTokenError` cobre assinatura errada e token expirado; os dois viram 401.

```python
# api/seguranca.py
try:
    payload = jwt.decode(token, settings.jwt_segredo, algorithms=["HS256"])
except jwt.InvalidTokenError:
    raise credenciais_invalidas
```

**Herança para reaproveitar código.** Herança expressa "é um"; para "tem um" (o pedido tem um meio de pagamento e um notificador), composição com `Protocol` deixa trocar a peça sem mexer na classe.

<Callout type="warning" title="A regra mora num lugar só">
Se depois do desafio a frase "não vender acima da capacidade" aparecer escrita duas vezes no código, o núcleo não ficou único. Os adaptadores podem garantir atomicidade no banco, mas a decisão de negócio (quanto pode, quando expira) fica no domínio, e os dois canais chamam o mesmo serviço.
</Callout>

<Callout type="tip" title="Grave o desafio como portfólio">
Ao terminar, escreva no README uma seção curta com as decisões: por que o núcleo não conhece o framework, como a atomicidade foi garantida em cada canal e o que ficou de fora. Esse texto vira roteiro para a pergunta "me fale de um projeto seu" e economiza muito na entrevista.
</Callout>

## Na entrevista

**Qual a diferença entre `git merge` e `git rebase`, e quando evitar o rebase?** O merge preserva o histórico e cria um commit de junção; o rebase reescreve os commits sobre outra base, deixando a história linear. Não se faz rebase de commits que outras pessoas já baixaram, porque isso muda os hashes e obriga todos a reconciliar.

**Como você evita vender o mesmo último ingresso para duas pessoas?** Com uma atualização condicional no banco (`quantidade_disponivel >= pedido`) que subtrai e informa quantas linhas mudou, dentro de uma transação, ou com trava de linha via `SELECT ... FOR UPDATE`. Checar no Python e salvar depois não basta.

**Por que usar `@property` em vez de getters e setters?** Em Python os atributos começam públicos, e `@property` permite acrescentar validação depois sem mudar a interface de quem usa a classe. Getters e setters explícitos são cerimônia herdada de outras linguagens.

**Django, Flask ou FastAPI: como escolher?** Django quando o produto precisa de site, Admin, autenticação e ORM integrados, com convenções fortes. FastAPI para APIs tipadas com documentação OpenAPI automática e injeção de dependência. Flask quando se quer montar cada peça e o escopo é pequeno.

**O que o PKCE protege no fluxo authorization code?** Impede que um atacante que interceptou o código de autorização o troque por tokens, porque a troca exige o `code_verifier` que só o cliente original conhece. O parâmetro `state` complementa, protegendo contra CSRF no retorno.

**O que é unit of work e por que usar junto com repositório?** O repositório esconde como os objetos são buscados e salvos; a unit of work delimita a transação e decide quando tudo é confirmado ou desfeito. Juntos, deixam o caso de uso atômico sem que ele conheça o banco.

**Qual princípio SOLID você aplicaria primeiro numa função de 300 linhas?** Responsabilidade única: separar cálculo de preço, persistência, pagamento e notificação. Depois inversão de dependência, injetando gateway e notificador para testar sem SMTP nem banco.

**Que cuidados você toma ao colocar um LLM numa rota da API?** Timeout e retentativa limitada, saída validada com esquema, tratamento de `stop_reason`, limite de tokens e custo, segredos fora do código, nenhum dado pessoal desnecessário no prompt e defesa contra prompt injection quando o texto vem do usuário.
