No Flask você escolheu cada peça: o banco, o validador, a estrutura de pastas. O Django faz o caminho oposto: traz ORM, migrações, formulários, autenticação, painel administrativo e proteção contra os ataques web mais comuns, tudo integrado e com convenções fortes. Esse é o motivo de ele dominar as vagas de back-end Python em empresas de produto: um time novo encontra cada coisa no lugar de sempre. O preço é entender as convenções antes de sair escrevendo código, senão você briga com o framework.

Este é o primeiro de quatro capítulos de Django que constroem o site da plataforma de ingressos. Aqui você cria o projeto, organiza settings, URLs, views e templates, e deixa a vitrine de eventos no ar com dados ainda em memória. O próximo capítulo troca esses dados pelo banco.

**Você vai aprender:**

- A diferença entre projeto e app e como organizar um projeto Django 5.2
- Como uma requisição percorre URLconf, view e template
- Herança de templates, tags, filtros e um filtro próprio
- Arquivos estáticos em desenvolvimento e em produção
- Settings separadas por ambiente, com segredos em variáveis de ambiente

## Projeto e app

No Django, **projeto** é a instalação: settings, URLs raiz e os pontos de entrada WSGI e ASGI. **App** é um pacote Python com uma responsabilidade do domínio (eventos, pedidos, contas), com seus modelos, views, templates e testes. Um projeto tem vários apps; um app bem feito poderia ser levado a outro projeto.

```bash
python -m venv .venv
source .venv/bin/activate
pip install "django~=5.2"
django-admin startproject ingressos .
python manage.py startapp eventos
```

Criar o projeto no diretório atual (o ponto no final) evita a pasta `ingressos/ingressos/` que confunde todo iniciante. O resultado:

```text
manage.py
ingressos/
  __init__.py
  settings.py
  urls.py
  asgi.py
  wsgi.py
eventos/
  __init__.py
  admin.py
  apps.py
  migrations/
  models.py
  tests.py
  views.py
pyproject.toml
```

`manage.py` é o utilitário do projeto: `runserver`, `migrate`, `createsuperuser`, `shell`, `test`. Ele só define a variável `DJANGO_SETTINGS_MODULE` e repassa o comando ao Django.

Um app só existe para o Django depois de entrar em `INSTALLED_APPS`. Sem isso, os templates, migrações e modelos dele são ignorados:

```python
# ingressos/settings.py (trecho)
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "eventos",
]
```

Quando o projeto crescer, os apps podem ir para dentro de um pacote (`ingressos/eventos/`, `ingressos/pedidos/`), mas o critério para criar um app novo é sempre o mesmo: um pedaço do domínio com fronteira clara. Um app `core` ou `utils` que acumula tudo é o mesmo problema do `app.py` gigante, com outro nome.

## O caminho de uma requisição

Quando chega `GET /eventos/festival-de-verao/`:

1. Os **middlewares** processam a requisição (sessão, CSRF, autenticação, segurança).
2. O **URLconf** raiz (`ROOT_URLCONF`, normalmente `ingressos/urls.py`) casa o caminho com um padrão e escolhe a view.
3. A **view** recebe um `HttpRequest` e os parâmetros da URL, busca os dados e devolve um `HttpResponse`.
4. Para HTML, a view renderiza um **template** com um contexto (um dicionário de variáveis).
5. A resposta volta pelos middlewares, em ordem inversa.

O Django chama isso de **MTV** (Model, Template, View). A "view" do Django faz o papel do controller do MVC, e o template é a view do MVC. Na entrevista, saber fazer essa tradução mostra que você entende o padrão e não só o nome.

## URLs

O URLconf raiz só delega para os apps:

```python
# ingressos/urls.py
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("eventos/", include("eventos.urls")),
    path("", include("eventos.urls_home")),
]
```

Cada app declara as suas rotas, com um `app_name` que cria um namespace:

```python
# eventos/urls.py
from django.urls import path

from eventos import views

app_name = "eventos"

urlpatterns = [
    path("", views.lista, name="lista"),
    path("<slug:slug>/", views.detalhe, name="detalhe"),
]
```

```python
# eventos/urls_home.py
from django.urls import path

from eventos import views

urlpatterns = [path("", views.home, name="home")]
```

`<slug:slug>` é um **conversor**: só casa com letras, números, hífen e sublinhado, e entrega o valor já como texto à view. Existem também `int`, `str` (qualquer coisa sem barra), `uuid` e `path`. Usar o conversor certo faz URLs inválidas darem 404 sem chegar ao seu código.

O `name` é o que importa no resto do projeto. Nunca escreva `"/eventos/" + slug` à mão: use `reverse("eventos:detalhe", kwargs={"slug": slug})` no Python ou a tag `url` no template. Se a rota mudar de `/eventos/` para `/shows/`, nada mais precisa ser alterado.

## Views

Enquanto o banco não entra (próximo capítulo), os eventos vêm de uma lista em memória, atrás de funções com a mesma forma que a consulta terá depois:

```python
# eventos/dados.py
from dataclasses import dataclass
from datetime import datetime, timezone
from decimal import Decimal


@dataclass(frozen=True)
class Evento:
    slug: str
    nome: str
    data: datetime
    local: str
    preco_minimo: Decimal
    vagas: int


_EVENTOS = [
    Evento("festival-de-verao", "Festival de Verão",
           datetime(2030, 1, 15, 23, 0, tzinfo=timezone.utc), "Recife", Decimal("120.00"), 850),
    Evento("noite-do-jazz", "Noite do Jazz",
           datetime(2030, 3, 2, 22, 30, tzinfo=timezone.utc), "São Paulo", Decimal("80.00"), 0),
]


def listar_eventos(local: str | None = None) -> list[Evento]:
    eventos = sorted(_EVENTOS, key=lambda e: e.data)
    if local:
        eventos = [e for e in eventos if e.local == local]
    return eventos


def buscar_evento(slug: str) -> Evento | None:
    return next((e for e in _EVENTOS if e.slug == slug), None)
```

```python
# eventos/views.py
from django.http import Http404, HttpRequest, HttpResponse
from django.shortcuts import render

from eventos.dados import buscar_evento, listar_eventos


def home(request: HttpRequest) -> HttpResponse:
    return render(request, "eventos/home.html", {"destaques": listar_eventos()[:3]})


def lista(request: HttpRequest) -> HttpResponse:
    local = request.GET.get("local")
    contexto = {"eventos": listar_eventos(local), "local": local}
    return render(request, "eventos/lista.html", contexto)


def detalhe(request: HttpRequest, slug: str) -> HttpResponse:
    evento = buscar_evento(slug)
    if evento is None:
        raise Http404("Evento não encontrado")
    return render(request, "eventos/detalhe.html", {"evento": evento})
```

`render` junta template e contexto e devolve o `HttpResponse`. `request.GET` é a query string, um dicionário em que a mesma chave pode ter vários valores (`getlist`). Levantar `Http404` em qualquer ponto da view gera a página de "não encontrado".

Views podem ser funções ou classes. As **class-based views** genéricas (`ListView`, `DetailView`, `CreateView`) eliminam repetição quando o caso é o padrão, e ficam mais valiosas com o ORM, no próximo capítulo. A regra prática: funções para fluxo específico e legível, genéricas quando o caso é exatamente o que elas fazem. Uma CBV com seis métodos sobrescritos para fugir do padrão é pior que uma função.

Note que a view não sabe como os eventos são guardados: ela chama `listar_eventos`. Views finas, que recebem a requisição, chamam uma função de domínio e escolhem a resposta, são a boa prática que vale para todo o resto da carreira.

## Templates e herança

Com `APP_DIRS: True` na configuração `TEMPLATES` (o padrão do `startproject`), o Django procura templates na pasta `templates/` de cada app instalado. Por isso a convenção de repetir o nome do app: `eventos/templates/eventos/lista.html`. Sem a subpasta, dois apps com `lista.html` colidem, e vence o que aparecer primeiro em `INSTALLED_APPS`.

Templates compartilhados (o layout do site) ficam numa pasta do projeto, declarada em `DIRS`:

```python
# ingressos/settings.py (trecho)
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [BASE_DIR / "templates"],
        "APP_DIRS": True,
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
        },
    },
]
```

O layout base define **blocos**, regiões que as páginas filhas preenchem:

```html
<!-- templates/base.html -->
{% load static %}
<!doctype html>
<html lang="pt-br">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>{% block titulo %}Ingressos{% endblock %}</title>
  <link rel="stylesheet" href="{% static 'css/site.css' %}">
</head>
<body>
  {% include "parciais/menu.html" %}
  <main>
    {% block conteudo %}{% endblock %}
  </main>
  <footer>Ingressos &copy; {% now "Y" %}</footer>
</body>
</html>
```

```html
<!-- eventos/templates/eventos/lista.html -->
{% extends "base.html" %}
{% load formatos %}

{% block titulo %}Eventos{% if local %} em {{ local }}{% endif %} | {{ block.super }}{% endblock %}

{% block conteudo %}
  <h1>Próximos eventos</h1>
  <ul class="eventos">
    {% for evento in eventos %}
      <li>
        <a href="{% url 'eventos:detalhe' slug=evento.slug %}">{{ evento.nome }}</a>
        <span>{{ evento.data|date:"d/m/Y H:i" }} · {{ evento.local }}</span>
        <span>a partir de {{ evento.preco_minimo|reais }}</span>
        {% if not evento.vagas %}<strong>Esgotado</strong>{% endif %}
      </li>
    {% empty %}
      <li>Nenhum evento encontrado.</li>
    {% endfor %}
  </ul>
{% endblock %}
```

Regras da herança: `extends` precisa ser a primeira tag do arquivo; tudo que estiver fora de um bloco no filho é ignorado; `block.super` traz o conteúdo do bloco do pai. Use `include` para pedaços repetidos (menu, cartão de evento) e herança para a estrutura da página. Três níveis costumam bastar: `base.html`, uma base por seção do site (opcional) e a página.

## Tags, filtros e o que fica fora do template

**Variáveis** (entre chaves duplas) imprimem valores; o ponto acessa chave de dicionário, atributo ou índice, nessa ordem, e chama métodos sem argumentos. **Tags** (entre chave e porcentagem) controlam lógica: `for` com `empty`, `if`, `url`, `include`, `with`, `csrf_token`. **Filtros**, depois da barra vertical, transformam um valor: `date`, `default`, `length`, `pluralize`, `truncatechars`, `linebreaks`.

| Precisa de | Use |
|---|---|
| Formatar data, número, texto | Filtro (`date`, `floatformat`, `truncatechars`) |
| Valor padrão quando vazio | `default:"..."` |
| Repetir um trecho de HTML | `include` com `with` |
| Montar URL | Tag `url` com o nome da rota |
| Cálculo ou consulta | Na view ou no domínio, nunca no template |

A linguagem de templates do Django é limitada de propósito: não aceita chamadas com argumentos nem expressões arbitrárias. Se o template precisa decidir algo complexo, a decisão pertence à view ou ao modelo. Quando falta só uma formatação, crie um filtro. Filtros e tags próprios ficam no pacote `templatetags` do app:

```python
# eventos/templatetags/__init__.py  (arquivo vazio)

# eventos/templatetags/formatos.py
from decimal import Decimal

from django import template

register = template.Library()


@register.filter
def reais(valor: Decimal | None) -> str:
    if valor is None:
        return ""
    texto = f"{valor:,.2f}"  # 1,234.50
    return "R$ " + texto.replace(",", "_").replace(".", ",").replace("_", ".")
```

O nome do arquivo (`formatos`) é o que vai no `load`. Depois de criar o pacote, reinicie o `runserver`, porque ele só registra bibliotecas de template novas na inicialização.

<Callout type="warning" title="Autoescape e o filtro safe">
O Django escapa toda variável: um nome de evento com `<script>` aparece como texto, não executa. Essa é a principal defesa contra XSS no HTML gerado. O filtro `safe` e a função `mark_safe` desligam a proteção para aquele valor. Só use com conteúdo que você mesmo gerou; nunca com algo digitado por usuário, nem mesmo por um administrador, sem passar antes por um sanitizador de HTML.
</Callout>

## Arquivos estáticos

CSS, JavaScript e imagens do layout são **estáticos**. Arquivos enviados por usuários (o banner de um evento) são **media** e têm tratamento separado, porque não vêm do repositório.

```python
# ingressos/settings.py (trecho)
STATIC_URL = "static/"
STATICFILES_DIRS = [BASE_DIR / "static"]
STATIC_ROOT = BASE_DIR / "staticfiles"

MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR / "media"
```

- `STATICFILES_DIRS`: pastas do projeto com estáticos. Cada app também pode ter `static/<app>/`, com a mesma convenção de subpasta dos templates.
- `STATIC_ROOT`: destino do `python manage.py collectstatic`, que copia tudo para um lugar só. É essa pasta que o servidor de produção entrega.
- Em desenvolvimento, com `DEBUG=True`, o `runserver` serve estáticos sozinho. Com `DEBUG=False`, não serve.

Em produção, o Django não deve gastar processo entregando CSS. As opções comuns são um proxy (Nginx) ou um bucket com CDN servindo `STATIC_ROOT`, ou o WhiteNoise, um middleware que serve os estáticos com cabeçalhos de cache longos e nomes com hash. Nos templates, sempre `static` com o caminho relativo; nunca `/static/...` fixo, porque a URL muda conforme o armazenamento.

## Settings por ambiente e segredos

O `settings.py` gerado tem uma `SECRET_KEY` escrita no código e `DEBUG = True`. As duas coisas não podem ir para produção. A `SECRET_KEY` assina sessões, tokens de redefinição de senha e cookies: quem a conhece forja tudo isso. `DEBUG=True` mostra código, variáveis e settings em qualquer erro.

A forma mais simples e sem dependência é ler do ambiente, com padrões só para o que é seguro:

```python
# ingressos/settings.py (trecho)
import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
DEBUG = os.environ.get("DJANGO_DEBUG", "false").lower() == "true"
ALLOWED_HOSTS = [h for h in os.environ.get("DJANGO_ALLOWED_HOSTS", "").split(",") if h]
CSRF_TRUSTED_ORIGINS = [
    o for o in os.environ.get("DJANGO_CSRF_TRUSTED_ORIGINS", "").split(",") if o
]

LANGUAGE_CODE = "pt-br"
TIME_ZONE = "America/Sao_Paulo"
USE_I18N = True
USE_TZ = True
```

`os.environ["DJANGO_SECRET_KEY"]` com colchetes é intencional: sem a variável, o processo nem sobe, o que é melhor do que subir com uma chave padrão. `DEBUG` falso por padrão garante que esquecer a variável não exponha nada. Com `DEBUG=False`, `ALLOWED_HOSTS` precisa listar os domínios do site, ou toda requisição recebe 400.

Em desenvolvimento, as variáveis ficam num arquivo `.env`, fora do Git (no `.gitignore`), carregado pelo seu shell, pelo Docker Compose ou por uma biblioteca como django-environ ou python-dotenv. Mantenha um `.env.example` versionado, com os nomes e valores falsos, para quem chega ao projeto. Gere uma chave com:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```

Antes de cada deploy, rode `python manage.py check --deploy`. Ele aponta `DEBUG` ligado, cookies sem `Secure`, falta de HSTS e outras configurações de segurança esquecidas.

Se as diferenças entre ambientes forem grandes, a alternativa é um pacote `ingressos/settings/` com `base.py`, `dev.py` e `prod.py`, em que os dois últimos fazem `from .base import *` e sobrescrevem o necessário, escolhidos por `DJANGO_SETTINGS_MODULE`. Funciona, mas tende a espalhar configuração em três arquivos. Comece com um arquivo e variáveis de ambiente; divida quando houver motivo.

<Callout type="tip" title="USE_TZ sempre ligado">
Com `USE_TZ = True`, o Django guarda datas em UTC e converte para `TIME_ZONE` só na exibição (o filtro `date` já faz isso). Datas sem fuso viram fonte de bugs em horário de verão e em servidores fora do Brasil. Nos dados em memória deste capítulo, as datas já são criadas com `tzinfo=timezone.utc` pelo mesmo motivo.
</Callout>

## Testando views e templates

O Django traz um cliente de teste que percorre middlewares, URLs, view e template. Com pytest-django, ele chega como fixture:

```toml
# pyproject.toml (trecho)
[tool.pytest.ini_options]
DJANGO_SETTINGS_MODULE = "ingressos.settings"
python_files = ["tests.py", "test_*.py"]
```

```python
# eventos/tests.py
from django.urls import reverse


def test_lista_mostra_eventos(client):
    resposta = client.get(reverse("eventos:lista"))

    assert resposta.status_code == 200
    assert "Festival de Verão" in resposta.content.decode()
    assert "eventos/lista.html" in [t.name for t in resposta.templates]


def test_evento_esgotado_aparece_marcado(client):
    resposta = client.get(reverse("eventos:lista"))

    assert "Esgotado" in resposta.content.decode()


def test_slug_inexistente_devolve_404(client):
    resposta = client.get(reverse("eventos:detalhe", kwargs={"slug": "nao-existe"}))

    assert resposta.status_code == 404
```

Como `SECRET_KEY` vem do ambiente, defina `DJANGO_SECRET_KEY` também no CI (um valor qualquer serve para testes). Teste o filtro `reais` como função comum, com casos de zero, centavos, milhar e `None`.

## Na entrevista

**Qual a diferença entre projeto e app no Django?** O projeto é a instalação: settings, URLs raiz e pontos de entrada WSGI/ASGI. Um app é um pacote com uma responsabilidade do domínio, com modelos, views e templates próprios, registrado em `INSTALLED_APPS`. Um projeto reúne vários apps.

**O que é MTV e como se relaciona com MVC?** Model, Template, View. O model é o mesmo do MVC; o template faz o papel da view do MVC; a view do Django faz o papel do controller, recebendo a requisição e escolhendo a resposta. O roteamento fica no URLconf.

**Por que usar nomes de URL em vez de caminhos fixos?** Porque `reverse` e a tag `url` geram o caminho a partir do nome. Se a rota muda, só o URLconf é alterado, e links quebrados viram erro claro (`NoReverseMatch`) em vez de 404 silencioso em produção.

**Como o Django protege contra XSS nos templates?** Com autoescape: toda variável é escapada antes de ir para o HTML. A proteção só é desligada com `safe` ou `mark_safe`, que devem ser usados apenas com conteúdo gerado pela própria aplicação.

**O que muda ao colocar `DEBUG=False`?** Erros deixam de mostrar a página de depuração, `ALLOWED_HOSTS` passa a ser exigido e o `runserver` para de servir estáticos, que precisam de `collectstatic` e de um servidor ou do WhiteNoise.

## Pratique

1. Crie o projeto `ingressos` e o app `eventos`, com `SECRET_KEY`, `DEBUG` e `ALLOWED_HOSTS` lidos do ambiente e um `.env.example` versionado.
2. Monte `base.html` com menu em `include`, e as páginas de home, lista e detalhe usando herança e o filtro `reais`.
3. Adicione um filtro por local na lista (links "Recife", "São Paulo") que preserva a URL nomeada e mostra o local escolhido no título.
4. Crie as páginas `404.html` e `500.html` herdando de `base.html` e confira com `DEBUG=False`.
5. Escreva testes para as três views e para o filtro, e rode `python manage.py check --deploy` com as variáveis de produção.
