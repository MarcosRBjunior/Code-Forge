Go não tem classes. Para agrupar dados você usa uma struct, e para dar comportamento a ela você declara métodos. Não há herança, construtores nem `this`; em vez disso há composição por embutimento e funções `New...` por convenção. Em entrevista, structs aparecem em nós de árvore e de lista ligada, em pares `{valor, índice}` para ordenar e em problemas de design como LRU Cache.

## Declarando e criando

Uma struct é uma lista de campos com nome e tipo. Você cria valores com literais, nomeando os campos (recomendado) ou na ordem da declaração. Campos não informados recebem o valor zero, então uma struct sempre nasce utilizável.

```go
package main

import "fmt"

type Ponto struct {
	X, Y int
}

func (p Ponto) Dist2() int { return p.X*p.X + p.Y*p.Y }

func (p *Ponto) Move(dx, dy int) {
	p.X += dx
	p.Y += dy
}

func main() {
	a := Ponto{X: 3, Y: 4}
	var zero Ponto
	fmt.Println(a, zero, a.Dist2())

	a.Move(1, 1)
	fmt.Printf("%+v\n", a)

	b := a
	b.X = 100
	fmt.Println(a.X, b.X, a == Ponto{4, 5})

	par := struct {
		val, idx int
	}{7, 2}
	fmt.Println(par.val, par.idx)
}
```

```text
Saída:
{3 4} {0 0} 25
{X:4 Y:5}
4 100 true
7 2
```

Structs são valores: `b := a` copia todos os campos, e alterar `b` não muda `a`. Elas são comparáveis com `==` quando todos os campos são, e por isso servem como chave de mapa (`map[Ponto]bool` para visitados em grade). A struct anônima no fim é útil para pares rápidos sem declarar um tipo.

## Receptor por valor ou por ponteiro

Um método é uma função com um receptor antes do nome. Com receptor por valor (`p Ponto`), o método recebe uma cópia e não consegue alterar o original. Com receptor ponteiro (`p *Ponto`), altera. Go faz a conversão automática na chamada: `a.Move(1, 1)` vira `(&a).Move(1, 1)` quando `a` é endereçável. A regra prática: se algum método precisa modificar o estado ou a struct é grande, use ponteiro em todos os métodos do tipo, para manter consistência.

## Construtores e composição

Por convenção, uma função `NewX` monta e devolve a struct pronta, geralmente como ponteiro. Em vez de herança, você embute um tipo dentro de outro, e os campos e métodos dele são promovidos.

```go
package main

import "fmt"

type No struct {
	Val  int
	Prox *No
}

type Pilha struct {
	topo *No
	tam  int
}

func NovaPilha() *Pilha { return &Pilha{} }

func (p *Pilha) Push(v int) {
	p.topo = &No{Val: v, Prox: p.topo}
	p.tam++
}

func (p *Pilha) Pop() (int, bool) {
	if p.topo == nil {
		return 0, false
	}
	v := p.topo.Val
	p.topo = p.topo.Prox
	p.tam--
	return v, true
}

type Animal struct{ Nome string }

func (a Animal) Apresenta() string { return "sou " + a.Nome }

type Cachorro struct {
	Animal
	Raca string
}

func main() {
	p := NovaPilha()
	p.Push(1)
	p.Push(2)
	v, ok := p.Pop()
	fmt.Println(v, ok, p.tam)

	c := Cachorro{Animal{"Rex"}, "vira-lata"}
	fmt.Println(c.Nome, c.Apresenta(), c.Raca)
}
```

```text
Saída:
2 true 1
Rex sou Rex vira-lata
```

O tipo `No` é o nó de lista ligada que você escreverá em muitos problemas: um valor e um ponteiro para o próximo, com `nil` marcando o fim. A pilha guarda o topo e um contador, e seus métodos usam receptor ponteiro porque alteram o estado. Já `Cachorro` embute `Animal`, então `c.Nome` e `c.Apresenta()` funcionam diretamente. Isso não é herança: um `Cachorro` não é um `Animal` para o sistema de tipos; ele apenas contém um.

## Armadilhas

Iterar com `for _, p := range pontos` e alterar `p.X` não muda o slice, porque `p` é uma cópia; use o índice (`pontos[i].X = ...`). Guardar structs em mapa tem o mesmo problema: `m[k].X = 1` não compila, então leia, altere e grave de volta, ou guarde `*Ponto`. Campos com letra minúscula são privados ao pacote, o que em entrevista não costuma importar, mas afeta a serialização com `encoding/json`.

<Callout type="tip" title="Imprimindo para depurar">
`fmt.Printf("%+v\n", x)` mostra os nomes dos campos e poupa tempo ao inspecionar nós e estados intermediários.
</Callout>

## Na entrevista

Para problemas de design (LRU, Min Stack, Trie), declare a struct com os campos de estado, uma função `Constructor` ou `NewX` e métodos com receptor ponteiro. Para ordenar pares, uma struct pequena com `slices.SortFunc` é mais legível que slices de slices. Follow-ups comuns: "quando usar receptor ponteiro?" (quando o método altera o estado ou a struct é grande) e "Go tem herança?" (não; usa composição por embutimento e interfaces).
