Em Python, concorrência com threads esbarra no GIL; em JavaScript você tem uma thread só com `async/await`. Go foi desenhada para concorrência desde o início: uma goroutine é uma função rodando de forma independente, muito mais leve que uma thread do sistema, e você pode ter milhares delas.

## Iniciando uma goroutine

Colocar `go` antes de uma chamada de função a executa em paralelo com o resto. O ponto crucial: quando `main` termina, o programa acaba, mesmo que existam goroutines em andamento. É preciso esperar por elas. A ferramenta padrão é o `sync.WaitGroup`: `Add` registra trabalho, `Done` sinaliza o fim e `Wait` bloqueia até zerar.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	resultados := make([]int, 5)

	for i := 0; i < 5; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			resultados[i] = i * i
		}()
	}

	wg.Wait()
	fmt.Println(resultados)
}
```

```text
Saída:
[0 1 4 9 16]
```

Cada goroutine escreve num índice diferente do slice, então não há disputa. Se todas escrevessem na mesma variável, seria uma condição de corrida. Note também o `defer wg.Done()`, que garante o aviso mesmo se a função sair cedo.

## Captura da variável do laço

No exemplo acima, cada goroutine usa `i` dentro de uma função anônima. A partir do Go 1.22 cada iteração do `for` tem a sua própria cópia de `i`, então funciona como esperado. Em versões antigas todas as goroutines enxergavam a mesma variável e imprimiam valores repetidos; o conserto era passar `i` como argumento. Se uma entrevista usa um Go mais antigo, passe como parâmetro por segurança.

## Corrida de dados e Mutex

Quando várias goroutines modificam o mesmo dado, o resultado é indefinido sem sincronização. Um `sync.Mutex` protege a seção crítica.

```go
package main

import (
	"fmt"
	"sync"
)

type Contador struct {
	mu sync.Mutex
	n  int
}

func (c *Contador) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.n++
}

func main() {
	var c Contador
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			c.Inc()
		}()
	}
	wg.Wait()
	fmt.Println(c.n)
}
```

```text
Saída:
1000
```

Sem o mutex, o resultado seria menor que 1000 em muitas execuções, porque `c.n++` lê, soma e escreve em passos separados. A ferramenta `go run -race` detecta esse tipo de erro.

## Armadilhas

Goroutines não são gratuitas: uma que fica bloqueada para sempre (esperando um canal que ninguém fecha) é um vazamento. Não existe como "matar" uma goroutine de fora; ela precisa receber um sinal para parar, em geral via canal ou `context`. Também não há garantia de ordem de execução: nunca dependa de uma goroutine rodar antes da outra sem sincronizar.

Mapas não são seguros para uso concorrente: escrever num mapa a partir de várias goroutines derruba o programa. Use mutex ou `sync.Map`.

## Na entrevista

Se o problema permite paralelismo (processar muitas URLs, somar partes de um array), descreva o padrão: dividir o trabalho, lançar goroutines, coletar resultados com `WaitGroup` ou canais. Mostre cuidado com a corrida de dados. Follow-ups: "qual a diferença entre concorrência e paralelismo?" e "o que acontece se main terminar antes das goroutines?" (elas são abandonadas).
