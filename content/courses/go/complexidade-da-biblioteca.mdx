Em Python você decora que `list.append` é O(1) amortizado e `list.insert(0, x)` é O(n). Em Go a mesma disciplina vale, mas a biblioteca é menor e as operações escondem menos mágica. Saber o custo de cada chamada evita que uma solução O(n log n) vire O(n²) sem você perceber.

## Slices

| Operação | Custo |
|---|---|
| `s[i]`, `len(s)` | O(1) |
| `append(s, x)` | O(1) amortizado, O(n) quando realoca |
| `s[a:b]` (fatiar) | O(1), compartilha memória |
| `copy(dst, src)` | O(n) |
| Remover do fim (`s = s[:len(s)-1]`) | O(1) |
| Inserir ou remover no início ou meio | O(n) |
| `slices.Contains`, `slices.Index` | O(n) |
| `slices.Sort` | O(n log n) |
| `slices.BinarySearch` | O(log n), exige ordenado |

Fatiar para desenfileirar (`fila = fila[1:]`) é O(1) e comum em BFS, mas o início do array subjacente não é liberado até o slice ser descartado.

## Mapas, strings e heap

Mapas têm busca, inserção e remoção em O(1) esperado; `len(m)` é O(1). Percorrer é O(n) e a ordem é aleatória. Strings são imutáveis: concatenar com `+` em laço copia tudo a cada passo, dando O(n²). Use `strings.Builder` para montar em O(n). Converter `string` em `[]byte` ou `[]rune` copia, O(n). Indexar uma string é O(1), mas devolve um byte, não um caractere. O pacote `container/heap` cobre fila de prioridade: `heap.Push` e `heap.Pop` são O(log n), `heap.Init` é O(n) e consultar o topo (`h[0]`) é O(1).

Veja o impacto de montar uma string de duas formas e medir o resultado, sem depender de tempos:

```go
package main

import (
	"fmt"
	"slices"
	"strings"
)

func main() {
	var sb strings.Builder
	for i := 0; i < 5; i++ {
		sb.WriteString("ab")
	}
	fmt.Println(sb.String(), sb.Len())

	s := []int{5, 2, 9, 1}
	slices.Sort(s)
	i, achou := slices.BinarySearch(s, 5)
	fmt.Println(s, i, achou)

	fila := []int{1, 2, 3}
	for len(fila) > 0 {
		x := fila[0]
		fila = fila[1:]
		fmt.Print(x, ";")
	}
	fmt.Println()
}
```

```text
Saída:
ababababab 10
[1 2 5 9] 2 true
1;2;3;
```

## Custo oculto: conversões e cópias

Alguns custos não aparecem no nome da função. `append` pode realocar e copiar tudo. `strings.Split` aloca um slice novo. `fmt.Sprintf` é lento perto de `strconv.Itoa`. Ordenar com `sort.Slice` usa reflexão e é um pouco mais lento que `slices.SortFunc`, que é genérica. Para chaves de mapa compostas, uma struct com campos comparáveis funciona e não aloca strings.

Já comparar slices com `slices.Equal` é O(n), e igualdade `==` entre slices nem compila. Para arrays, `==` compara elemento a elemento e também custa O(n).

```go
package main

import (
	"fmt"
	"sort"
	"slices"
)

type Ponto struct{ X, Y int }

func main() {
	visitado := map[Ponto]bool{}
	visitado[Ponto{1, 2}] = true
	fmt.Println(visitado[Ponto{1, 2}], visitado[Ponto{2, 1}])

	nomes := []string{"bia", "ana", "caio"}
	sort.Strings(nomes)
	fmt.Println(nomes)
	slices.Reverse(nomes)
	fmt.Println(nomes, slices.Equal(nomes, []string{"caio", "bia", "ana"}))
}
```

```text
Saída:
true false
[ana bia caio]
[caio bia ana] true
```

## Armadilhas

A mais comum é esquecer que `append` num laço dentro de laço pode ser O(1) amortizado e mesmo assim ter constante alta; pré-alocar com `make([]int, 0, n)` ajuda. Outra é usar um slice como conjunto e chamar `slices.Contains` dentro de um laço: O(n²) onde um mapa daria O(n). E lembre que `copy` e `append(s[:i], s[i+1:]...)` para remover do meio são O(n).
