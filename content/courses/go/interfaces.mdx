Em Python você escreve código que "anda como pato" e confia que o objeto terá o método certo. Em JavaScript é parecido. Go quer a mesma flexibilidade, mas com checagem em tempo de compilação, e resolve isso com interfaces.

## Satisfação implícita

Uma interface é um conjunto de assinaturas de método. Qualquer tipo que tenha esses métodos já a satisfaz, sem escrever `implements` em lugar nenhum. Isso permite declarar a interface do lado de quem consome, com o mínimo de métodos necessário.

```go
package main

import "fmt"

type Forma interface {
	Area() float64
}

type Retangulo struct{ L, A float64 }
type Quadrado struct{ Lado float64 }

func (r Retangulo) Area() float64 { return r.L * r.A }
func (q Quadrado) Area() float64  { return q.Lado * q.Lado }

func total(formas []Forma) float64 {
	soma := 0.0
	for _, f := range formas {
		soma += f.Area()
	}
	return soma
}

func main() {
	formas := []Forma{Retangulo{2, 3}, Quadrado{4}}
	fmt.Println(total(formas))
}
```

```text
Saída:
22
```

Nenhum dos dois tipos menciona `Forma`. Se um deles perder o método `Area`, o erro aparece na linha em que você o coloca no slice.

## Interface vazia e type assertion

`any` (apelido de `interface{}`) aceita qualquer valor, como `object` em Java ou um valor dinâmico em Python. Para recuperar o tipo concreto você usa type assertion, de preferência na forma com dois retornos, que não entra em pânico quando o tipo não confere. O `switch` de tipos faz o mesmo para vários casos.

```go
package main

import "fmt"

func descrever(v any) string {
	switch x := v.(type) {
	case int:
		return fmt.Sprintf("inteiro %d", x)
	case string:
		return "texto " + x
	case []int:
		return fmt.Sprintf("slice com %d itens", len(x))
	default:
		return "desconhecido"
	}
}

func main() {
	fmt.Println(descrever(7))
	fmt.Println(descrever("go"))
	fmt.Println(descrever([]int{1, 2, 3}))
	fmt.Println(descrever(2.5))

	var v any = "abc"
	n, ok := v.(int)
	fmt.Println(n, ok)
	s, ok := v.(string)
	fmt.Println(s, ok)
}
```

```text
Saída:
inteiro 7
texto go
slice com 3 itens
desconhecido
0 false
abc true
```

## Interfaces da biblioteca padrão

As mais úteis são pequenas. `fmt.Stringer` tem um método `String() string` e controla como `fmt.Println` imprime o tipo. `error` tem `Error() string`. `sort.Interface` (`Len`, `Less`, `Swap`) e `heap.Interface` (as três anteriores mais `Push` e `Pop`) são o que você implementa para ordenar e para criar uma fila de prioridade. Quando você ler "implemente a interface do heap", é isso que se pede.

## Armadilhas

A principal é a interface com valor nil. Uma interface guarda dois campos: o tipo dinâmico e o valor. Ela só é igual a `nil` quando os dois estão vazios. Se uma função devolve um ponteiro nil de tipo concreto dentro de uma interface (por exemplo, um `*MeuErro` nil como `error`), o resultado não é nil e o `if err != nil` dispara. Devolva `nil` literal quando não houver erro.

Outra: o receptor decide quem satisfaz. Se o método tem receptor ponteiro, só `*T` satisfaz a interface, não `T`. Por isso você verá `&Tipo{}` sendo passado onde se espera a interface.

Por fim, interfaces custam uma chamada indireta e podem forçar alocação. Em código de entrevista isso quase nunca importa, mas evite `any` quando generics resolvem, porque você perde a checagem de tipos.

## Na entrevista

Em problemas de design (cache, estacionamento, notificações) defina uma interface pequena para o comportamento que varia e deixe as structs a satisfazerem. Diga que prefere "aceitar interfaces, devolver structs". Follow-ups comuns: "por que o Go não tem herança?" (composição e interfaces substituem) e "quando uma interface é nil?" (apenas quando tipo e valor são nil).
