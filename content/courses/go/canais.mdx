O lema de Go para concorrência é compartilhar memória comunicando, e não comunicar compartilhando memória. O canal é o mecanismo: um tubo tipado por onde goroutines trocam valores e, de quebra, se sincronizam. Pense numa fila bloqueante, parecida com `queue.Queue` do Python.

## Canais sem buffer

`make(chan int)` cria um canal sem buffer. Enviar (`ch <- v`) bloqueia até alguém receber (`v := <-ch`), e receber bloqueia até alguém enviar. Esse encontro é uma sincronização.

```go
package main

import "fmt"

func somar(xs []int, saida chan int) {
	total := 0
	for _, x := range xs {
		total += x
	}
	saida <- total
}

func main() {
	nums := []int{1, 2, 3, 4, 5, 6}
	ch := make(chan int)

	go somar(nums[:3], ch)
	go somar(nums[3:], ch)

	a, b := <-ch, <-ch
	fmt.Println(a+b, "total")
}
```

```text
Saída:
21 total
```

A ordem de chegada de `a` e `b` varia, mas a soma não. Se você esquecer de receber, a goroutine que envia fica bloqueada para sempre.

## Buffer, close e range

Com `make(chan int, 3)` o envio só bloqueia quando o buffer está cheio, e o recebimento quando está vazio. Quem envia fecha o canal com `close(ch)` para avisar que acabou; quem recebe usa `for v := range ch`, que termina sozinho no fechamento. Receber de um canal fechado e vazio devolve o valor zero; a forma `v, ok := <-ch` mostra `ok == false`.

```go
package main

import "fmt"

func produzir(n int) <-chan int {
	ch := make(chan int, 2)
	go func() {
		defer close(ch)
		for i := 1; i <= n; i++ {
			ch <- i * 10
		}
	}()
	return ch
}

func main() {
	for v := range produzir(4) {
		fmt.Println(v)
	}

	c := make(chan string, 1)
	c <- "oi"
	close(c)
	s, ok := <-c
	fmt.Println(s, ok)
	s, ok = <-c
	fmt.Printf("%q %v\n", s, ok)
}
```

```text
Saída:
10
20
30
40
oi true
"" false
```

O tipo `<-chan int` na assinatura é um canal somente de leitura: documenta e impõe que o consumidor não envia. Existe também `chan<- int` para somente envio.

## Padrão pipeline e worker pool

Dois padrões cobrem a maioria das perguntas. No pipeline, cada estágio lê de um canal e escreve em outro. No worker pool, N goroutines leem tarefas de um canal compartilhado e escrevem resultados em outro; você fecha o canal de tarefas quando termina de enviar e usa um `WaitGroup` para fechar o de resultados depois que todos os workers acabam.

## Armadilhas

Há três erros clássicos. Primeiro, deadlock: todas as goroutines bloqueadas, e o runtime avisa com `all goroutines are asleep`. Segundo, fechar duas vezes ou enviar em canal fechado causa pânico; só o remetente fecha, e só uma vez. Terceiro, esquecer de fechar o canal num `range` faz o consumidor travar para sempre.

Receber de um canal nil bloqueia eternamente, e isso é útil em `select` mas perigoso fora dele. Canais também não são grátis: para proteger um contador simples, um mutex é mais barato e mais claro do que um canal.
