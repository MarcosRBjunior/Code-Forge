A maior fonte de bugs sutis em Go de entrevista é não saber o que um slice realmente é. Quem vem de Python espera que `b = a[1:3]` crie uma cópia; quem vem de JavaScript espera que `slice` também copie. Em Go não é assim, e a diferença aparece em problemas de backtracking, janelas deslizantes e funções que modificam listas.

## O descritor de três campos

Um slice é um pequeno valor com três campos: um ponteiro para um elemento de um array, o tamanho (`len`) e a capacidade (`cap`). O array subjacente fica fora do slice e pode ser compartilhado por vários deles. Fatiar cria um novo descritor que aponta para a mesma memória.

```text
a = [1 2 3 4 5]      ptr -> a[0], len 5, cap 5
b = a[1:3]           ptr -> a[1], len 2, cap 4
```

A capacidade de `b` é 4 porque do início dele (índice 1) até o fim do array restam 4 posições. Enquanto o `len` for menor que o `cap`, um `append` escreve no array existente, sobrescrevendo o que estiver ali.

```go
package main

import "fmt"

func main() {
	a := []int{1, 2, 3, 4, 5}
	b := a[1:3]
	fmt.Println(len(b), cap(b))

	b[0] = 99
	fmt.Println(a)

	b = append(b, 100)
	fmt.Println(a)

	c := a[1:3:3]
	c = append(c, 7)
	fmt.Println(a)
	fmt.Println(c)
}
```

```text
Saída:
2 4
[1 99 3 4 5]
[1 99 3 100 5]
[1 99 3 100 5]
[99 3 7]
```

Veja o que ocorreu. Alterar `b[0]` mudou `a[1]`, pois compartilham memória. O `append` em `b` ainda tinha capacidade, então gravou em `a[3]`, trocando o 4 por 100. Na forma completa `a[1:3:3]`, o terceiro número limita a capacidade a 2; o `append` seguinte estoura essa capacidade, e Go aloca um array novo e copia, deixando `a` intacto. Esse truque é útil quando você precisa garantir que não vai pisar em dados vizinhos.

## Slices em funções

Passar um slice copia só o descritor. Alterar elementos é visível para o chamador; alterar o tamanho não é, porque o `len` do chamador continua o mesmo.

```go
package main

import (
	"fmt"
	"slices"
)

func modifica(s []int) { s[0] = 100 }

func adiciona(s []int) { s = append(s, 9) }

func adicionaRet(s []int) []int { return append(s, 9) }

func main() {
	x := []int{1, 2}
	modifica(x)
	adiciona(x)
	fmt.Println(x)
	x = adicionaRet(x)
	fmt.Println(x)

	base := make([]int, 0, 10)
	base = append(base, 1, 2)
	p := append(base, 3)
	q := append(base, 4)
	fmt.Println(p, q)

	r := append(slices.Clone(base), 3)
	t := append(slices.Clone(base), 4)
	fmt.Println(r, t)
}
```

```text
Saída:
[100 2]
[100 2 9]
[1 2 4] [1 2 4]
[1 2 3] [1 2 4]
```

A função `adiciona` perde o resultado porque reatribui só o `s` local; é por isso que a biblioteca padrão sempre devolve o slice (`s = append(s, ...)`). E o final mostra o bug mais famoso: `p` e `q` nasceram de `base`, que tinha capacidade de sobra, então ambos escreveram na mesma posição do array. O resultado é `[1 2 4] [1 2 4]`. Com `slices.Clone`, cada um ganha memória própria.

## Como a capacidade cresce

Quando o `append` precisa de mais espaço, ele aloca um array maior (de forma geral, dobrando para slices pequenos e crescendo mais devagar para os grandes), copia os elementos e devolve um descritor novo. Os valores exatos não fazem parte da especificação, então não dependa deles. O que importa: o `append` é O(1) amortizado, e quando a capacidade é conhecida de antemão, `make([]int, 0, n)` evita copiar de novo.

Outro detalhe de memória: um slice pequeno fatiado de um array enorme mantém o array inteiro vivo. Se você guarda só um pedaço por muito tempo, copie-o com `slices.Clone`.

<Callout type="warning" title="Backtracking e resultados">
Ao guardar o caminho atual em um resultado, sempre copie: `res = append(res, slices.Clone(path))`. Sem a cópia, todas as entradas acabam apontando para o mesmo array e mudam juntas.
</Callout>

## Na entrevista

Cite a regra de bolso: modificar elementos propaga, modificar o tamanho exige devolver o slice. Em permutações, subconjuntos e combinações, copie o caminho ao salvar. Em remoções, prefira `slices.Delete` ou o idioma `append(s[:i], s[i+1:]...)` e reatribua.

Follow-ups comuns: "o que `len` e `cap` representam?" e "por que `append` pode afetar outro slice?" (porque compartilham o array subjacente enquanto houver capacidade).
