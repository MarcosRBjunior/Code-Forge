Em Python você usa `try/finally` ou `with` para garantir que um recurso seja liberado. Em Go, a palavra-chave `defer` cumpre esse papel: ela agenda uma chamada para rodar quando a função atual terminar, por qualquer caminho.

## defer

A chamada adiada executa na saída da função, e várias chamadas rodam em ordem inversa (como uma pilha). Os argumentos são avaliados no momento do `defer`, não da execução.

```go
package main

import "fmt"

func main() {
	for i := 1; i <= 3; i++ {
		defer fmt.Println("adiado", i)
	}
	x := 10
	defer fmt.Println("x avaliado no defer:", x)
	x = 99
	fmt.Println("corpo termina, x =", x)
}
```

```text
Saída:
corpo termina, x = 99
x avaliado no defer: 10
adiado 3
adiado 2
adiado 1
```

O uso típico é liberar algo logo após adquiri-lo: `defer f.Close()` depois de abrir o arquivo, `defer mu.Unlock()` depois de travar um mutex. Assim, o `return` antecipado em qualquer ramo nunca vaza o recurso.

## Retornos nomeados

Uma função adiada pode ler e alterar retornos nomeados, pois roda depois do `return` calcular o valor, mas antes de a função devolver o controle. Isso é útil para decorar erros e, principalmente, para o `recover`.

## panic e recover

`panic` interrompe o fluxo normal: a função atual para, os `defer` rodam subindo a pilha, e se ninguém tratar o programa termina com um stack trace. Pânicos acontecem sozinhos em índice fora do limite, desreferência de nil e escrita em mapa nil. `recover` só tem efeito dentro de uma função adiada, e devolve o valor do pânico (ou nil se não havia).

```go
package main

import "fmt"

func dividirSeguro(a, b int) (res int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recuperado: %v", r)
		}
	}()
	return a / b, nil
}

func acessar(xs []int, i int) (v int, ok bool) {
	defer func() {
		if recover() != nil {
			ok = false
		}
	}()
	return xs[i], true
}

func main() {
	fmt.Println(dividirSeguro(10, 2))
	fmt.Println(dividirSeguro(1, 0))
	fmt.Println(acessar([]int{1, 2, 3}, 1))
	fmt.Println(acessar([]int{1, 2, 3}, 5))
}
```

```text
Saída:
5 <nil>
0 recuperado: runtime error: integer divide by zero
2 true
0 false
```

Observe que os retornos nomeados `err` e `ok` permitem que a função adiada altere o que o chamador recebe.

## Armadilhas

`recover` fora de um `defer` não faz nada, e chamado dentro de outra função aninhada que não seja a adiada diretamente também não funciona. Um `defer` dentro de um laço acumula chamadas até a função inteira terminar, o que pode estourar recursos em laços longos: nesses casos, extraia o corpo do laço para uma função própria. E lembre que `defer` tem um pequeno custo, irrelevante na maioria dos casos.

Não use pânico como fluxo de controle normal, ao estilo de exceções. A convenção é: erros esperados viram `error`; pânico é para bugs e estados que não deveriam ocorrer. Bibliotecas costumam recuperar pânicos nas bordas e convertê-los em erros, como no exemplo acima.

Outra pegadinha: a goroutine que entra em pânico sem `recover` derruba o programa inteiro, mesmo que a principal esteja saudável. O `recover` precisa estar na própria goroutine.
