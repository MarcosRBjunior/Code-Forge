Python e JavaScript usam exceções: o erro "sobe" até alguém capturar. Go trata erro como um valor comum devolvido pela função. Isso deixa o fluxo explícito e é um dos primeiros estranhamentos de quem vem dessas linguagens.

## O padrão básico

Funções que podem falhar devolvem `error` como último retorno. `nil` significa sucesso. O chamador verifica logo em seguida.

```go
package main

import (
	"errors"
	"fmt"
	"strconv"
)

func dividir(a, b int) (int, error) {
	if b == 0 {
		return 0, errors.New("divisão por zero")
	}
	return a / b, nil
}

func main() {
	r, err := dividir(10, 2)
	fmt.Println(r, err)

	_, err = dividir(1, 0)
	fmt.Println(err)

	n, err := strconv.Atoi("12x")
	fmt.Println(n, err)
}
```

```text
Saída:
5 <nil>
divisão por zero
0 strconv.Atoi: parsing "12x": invalid syntax
```

Em entrevista, o ritual `if err != nil { return err }` aparece o tempo todo, e muitos entrevistadores aceitam omitir a checagem em partes triviais se você avisar. Só não ignore o erro de `strconv.Atoi` quando a entrada vem de fora.

## Erros sentinela, wrapping e errors.Is

Para o chamador distinguir causas, declare erros como variáveis de pacote e compare com `errors.Is`. Para acrescentar contexto sem perder a causa, use `fmt.Errorf` com o verbo `%w`. `errors.Is` percorre a cadeia e `errors.As` extrai um tipo concreto de erro.

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNaoEncontrado = errors.New("não encontrado")

type ErroValidacao struct {
	Campo string
}

func (e *ErroValidacao) Error() string {
	return "campo inválido: " + e.Campo
}

func buscar(m map[string]int, k string) (int, error) {
	v, ok := m[k]
	if !ok {
		return 0, fmt.Errorf("buscar %q: %w", k, ErrNaoEncontrado)
	}
	return v, nil
}

func validar(idade int) error {
	if idade < 0 {
		return &ErroValidacao{Campo: "idade"}
	}
	return nil
}

func main() {
	_, err := buscar(map[string]int{"a": 1}, "b")
	fmt.Println(err)
	fmt.Println(errors.Is(err, ErrNaoEncontrado))

	err = validar(-5)
	var ev *ErroValidacao
	if errors.As(err, &ev) {
		fmt.Println("campo:", ev.Campo)
	}
	fmt.Println(validar(30) == nil)
}
```

```text
Saída:
buscar "b": não encontrado
true
campo: idade
true
```

## Armadilhas

Usar `==` entre erros embrulhados falha: depois de `%w`, a comparação direta não reconhece a causa. Prefira sempre `errors.Is`. Também é comum esquecer o `return` depois de tratar o erro e seguir usando um valor inválido.

Lembre da armadilha do capítulo de interfaces: não devolva um ponteiro nil tipado como `error`. Em vez disso, retorne `nil` literal no caminho de sucesso.

Pânico não é tratamento de erro. Reserve `panic` para bugs de programação e estados impossíveis; erros esperados, como entrada inválida, viram valores de retorno. O capítulo seguinte sobre `defer`, `panic` e `recover` detalha esse limite.

Há custo de verbosidade, mas ganho de clareza: ao ler uma função, você vê todos os pontos de falha, algo que exceções escondem.

## Na entrevista

Em problemas de algoritmo, normalmente a assinatura não tem erro; devolva valor sentinela (como `-1`) ou um segundo retorno `bool`, o idioma "comma ok". Em problemas de design (parser, cache, validação), devolva `error` e mostre que você sabe fazer wrapping com `%w`. Follow-ups: "por que Go não tem try/catch?" e "qual a diferença entre `errors.Is` e `errors.As`?" (primeiro compara identidade na cadeia; segundo busca um tipo e o preenche).
