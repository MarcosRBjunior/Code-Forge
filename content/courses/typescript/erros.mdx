Código real falha: a entrada vem malformada, a divisão é por zero, o índice sai do intervalo. Em JavaScript e TypeScript a forma padrão de sinalizar isso é lançar uma exceção com `throw` e tratá-la com `try` e `catch`. O que o TypeScript acrescenta é a tipagem do que você captura, e é aí que mora a maior pegadinha.

## throw, try, catch e finally

Você pode lançar qualquer valor, mas deve lançar sempre um objeto `Error` (ou subclasse), porque só ele carrega a pilha de chamadas. O bloco `finally` roda de qualquer forma, com erro ou sem.

```typescript
function dividir(a: number, b: number): number {
  if (b === 0) {
    throw new Error("divisão por zero");
  }
  return a / b;
}

function tentar(a: number, b: number): void {
  try {
    console.log("resultado:", dividir(a, b));
  } catch (e) {
    if (e instanceof Error) {
      console.log("falhou:", e.message);
    }
  } finally {
    console.log("fim de", a, "/", b);
  }
}

tentar(10, 4);
tentar(1, 0);
```

```text
Saída:
resultado: 2.5
fim de 10 / 4
falhou: divisão por zero
fim de 1 / 0
```

No `catch`, a variável `e` não tem tipo garantido, pois qualquer coisa pode ter sido lançada, até uma string. Por isso, antes de ler `e.message`, estreite com `instanceof Error`. Com a opção `strict` ligada, o tipo de `e` é `unknown` e o compilador obriga essa checagem; sem ela, é `any` e o erro só aparece em execução.

## Classes de erro próprias

Criar uma subclasse permite diferenciar falhas por tipo em vez de comparar mensagens de texto.

```typescript
class ErroDeValidacao extends Error {
  campo: string;

  constructor(campo: string, mensagem: string) {
    super(mensagem);
    this.name = "ErroDeValidacao";
    this.campo = campo;
    Object.setPrototypeOf(this, ErroDeValidacao.prototype);
  }
}

function validarIdade(idade: number): number {
  if (idade < 0 || idade > 150) {
    throw new ErroDeValidacao("idade", "idade fora do intervalo: " + idade);
  }
  return idade;
}

try {
  validarIdade(200);
} catch (e) {
  if (e instanceof ErroDeValidacao) {
    console.log(e.name, "-", e.campo, "-", e.message);
  } else {
    throw e;
  }
}
```

```text
Saída:
ErroDeValidacao - idade - idade fora do intervalo: 200
```

A linha com `Object.setPrototypeOf` é importante quando o código é compilado para um alvo antigo de JavaScript: sem ela, `instanceof` pode falhar para subclasses de `Error`. Em projetos modernos (alvo ES2015 ou superior) ela é dispensável, mas não faz mal. Note também o `throw e` no `else`: se o erro não é o que você sabe tratar, relance-o em vez de engoli-lo.

## Retornar o erro como valor

Exceções são invisíveis na assinatura da função: nada no tipo avisa que ela pode lançar. Uma alternativa é devolver um resultado como união discriminada (aqui com a tag `tipo`), e o compilador força o chamador a tratar a falha.

```typescript
type Resultado<T> = { tipo: "ok"; valor: T } | { tipo: "erro"; erro: string };

function lerInteiro(texto: string): Resultado<number> {
  const n = Number(texto);
  if (texto.trim() === "" || !Number.isInteger(n)) {
    return { tipo: "erro", erro: "não é inteiro: '" + texto + "'" };
  }
  return { tipo: "ok", valor: n };
}

for (const t of ["42", "4.5", "abc"]) {
  const r = lerInteiro(t);
  if (r.tipo === "ok") {
    console.log("valor", r.valor);
  } else {
    console.log("erro", r.erro);
  }
}
```

```text
Saída:
valor 42
erro não é inteiro: '4.5'
erro não é inteiro: 'abc'
```

## Armadilhas

- Lançar strings (`throw "erro"`) perde a pilha e quebra o `instanceof Error`.
- Um `catch` vazio engole falhas e esconde bugs. Registre ou relance.
- Exceções são caras em laços quentes e ruins para fluxo normal de controle. Não use `throw` para sair de uma busca.
- Dentro de código assíncrono, um `throw` vira uma Promise rejeitada. O capítulo de async e await detalha como capturá-la.

<Callout type="tip" title="Prefira Error">
Sempre lance `new Error(...)` ou uma subclasse. A pilha de chamadas em `e.stack` é o que ajuda a depurar.
</Callout>
