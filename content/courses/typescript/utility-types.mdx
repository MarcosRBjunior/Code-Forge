É comum precisar de um tipo "quase igual" a outro: o mesmo objeto com todos os campos opcionais, sem um campo, ou só com alguns. Copiar e editar a interface gera duplicação, e ela diverge com o tempo. Os utility types são tipos genéricos prontos da biblioteca padrão do TypeScript que derivam novos tipos a partir de existentes.

## Partial, Required e Readonly

`Partial<T>` torna todos os campos opcionais, `Required<T>` faz o oposto e `Readonly<T>` impede reatribuição.

```typescript
interface Usuario {
  id: number;
  nome: string;
  email: string;
}

function atualizar(base: Usuario, mudancas: Partial<Usuario>): Usuario {
  return { ...base, ...mudancas };
}

const u: Readonly<Usuario> = { id: 1, nome: "Ana", email: "ana@ex.com" };
const novo = atualizar(u, { nome: "Ana Souza" });

console.log(novo.nome, novo.email);
console.log(u.nome);
// u.nome = "x"; // erro: propriedade somente leitura
```

```text
Saída:
Ana Souza ana@ex.com
Ana
```

`Partial` combina bem com o operador de espalhamento para criar funções de atualização. Lembre que `Readonly` só vale na compilação e é raso: um array dentro do objeto continua mutável por dentro.

## Pick e Omit

`Pick<T, K>` escolhe um subconjunto de chaves e `Omit<T, K>` remove algumas. Útil para tipos de entrada que não incluem campos gerados pelo servidor, como o `id`.

```typescript
interface Produto {
  id: number;
  nome: string;
  preco: number;
  estoque: number;
}

type NovoProduto = Omit<Produto, "id">;
type Resumo = Pick<Produto, "nome" | "preco">;

function criar(dados: NovoProduto, proximoId: number): Produto {
  return { id: proximoId, ...dados };
}

function resumir(p: Produto): Resumo {
  return { nome: p.nome, preco: p.preco };
}

const p = criar({ nome: "Caneta", preco: 3, estoque: 100 }, 7);
console.log(p.id, p.nome);
console.log(resumir(p).preco);
```

```text
Saída:
7 Caneta
3
```

## Record

`Record<K, V>` descreve um objeto cujas chaves são do tipo `K` e os valores do tipo `V`. É o tipo natural para contadores e tabelas de busca por chave de texto.

```typescript
function contar(palavras: string[]): Record<string, number> {
  const freq: Record<string, number> = {};
  for (const p of palavras) {
    freq[p] = (freq[p] || 0) + 1;
  }
  return freq;
}

const freq = contar(["a", "b", "a", "c", "a"]);
console.log(freq["a"], freq["b"]);
console.log(Object.keys(freq).length);
```

```text
Saída:
3 1
3
```

Se as chaves forem uma união literal, como `Record<"baixa" | "alta", number>`, o compilador exige que todas existam. Para chaves dinâmicas e remoções frequentes, um `Map` costuma ser melhor, tema de outro capítulo.

## ReturnType, Parameters e Awaited

Esses três extraem informação de funções e promises. Servem para não repetir um tipo que já existe no código.

```typescript
function buscar(id: number) {
  return { id, nome: "item " + id, ativo: true };
}

type Item = ReturnType<typeof buscar>;       // { id: number; nome: string; ativo: boolean }
type Args = Parameters<typeof buscar>;       // [id: number]
type Valor = Awaited<Promise<string>>;       // string
```

Aqui `typeof buscar` usa o operador de tipos para obter o tipo da função, e `ReturnType` extrai o que ela devolve.

<Callout type="note" title="Eles são só compilação">
Utility types não geram código. `Partial` ou `Omit` não validam nada em tempo de execução: dados vindos de fora (uma API, a entrada padrão) continuam precisando de checagem manual.
</Callout>

## Combinando e escolhendo

Utility types se compõem. `Readonly<Pick<Usuario, "id" | "nome">>` descreve um resumo imutável, e `Partial<Omit<Produto, "id">>` descreve um patch que nunca pode trocar o `id`. Dois outros aparecem com frequência: `NonNullable<T>` remove `null` e `undefined` de uma união, útil depois de filtrar valores ausentes, e `Exclude<U, X>` tira membros específicos de uma união de literais.

O trade-off é legibilidade. Três utility types aninhados numa assinatura obrigam o leitor a montar o tipo de cabeça. Quando a composição ficar longa, dê um nome a ela com um type alias (`type PatchDeProduto = ...`) e use o nome no resto do código. Também evite derivar tipos de outros que mudam por motivos diferentes: se o formato do payload da API não acompanha a entidade interna, uma interface própria é mais honesta que um `Omit`.

## Na entrevista

Você não vai ser cobrado a implementar `Partial` do zero na maioria das vezes, mas citar o utility type certo mostra fluência. Exemplos típicos: `Record<string, number>` para um contador, `Readonly<T>` para sinalizar que uma função não deve mutar a entrada, `Omit` para tipar o payload de criação.

Um follow-up clássico é "como funciona `Partial` por dentro?". A resposta curta: é um mapped type, `type Partial<T> = { [K in keyof T]?: T[K] }`, que percorre as chaves de `T` e marca cada uma como opcional.
