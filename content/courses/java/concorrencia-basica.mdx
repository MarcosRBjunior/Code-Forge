Python tem o GIL e JavaScript roda em uma thread com laço de eventos; em Java threads de verdade executam em paralelo e compartilham memória. Isso dá poder e traz bugs de corrida difíceis de reproduzir. Em entrevista de algoritmos você raramente usa threads, mas perguntas de design e de "backend" cobram o básico: criar threads, proteger estado compartilhado e usar a biblioteca de `java.util.concurrent`.

## Threads e o problema da corrida

Uma `Thread` recebe um `Runnable` (uma lambda sem argumentos). `start()` dispara a execução em paralelo e `join()` espera terminar. O problema aparece quando duas threads alteram a mesma variável: `contador++` não é atômico, pois lê, soma e escreve em três passos, e atualizações se perdem. O resultado varia a cada execução.

As soluções básicas são `synchronized` (só uma thread por vez no bloco, usando o monitor do objeto) e as classes atômicas, como `AtomicInteger`, que usam instruções de hardware sem travar.

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    static final Object trava = new Object();
    static int protegido = 0;
    static final AtomicInteger atomico = new AtomicInteger();

    public static void main(String[] args) throws InterruptedException {
        Runnable tarefa = () -> {
            for (int i = 0; i < 1000; i++) {
                synchronized (trava) {
                    protegido++;
                }
                atomico.incrementAndGet();
            }
        };

        Thread t1 = new Thread(tarefa);
        Thread t2 = new Thread(tarefa);
        t1.start();
        t2.start();
        t1.join();
        t2.join();

        System.out.println(protegido);
        System.out.println(atomico.get());
    }
}
```

```text
Saída:
2000
2000
```

Se um `int` comum com `++` fosse usado no lugar, o total poderia sair menor que 2000, e não de forma previsível; por isso o exemplo mostra só as versões seguras. Ao esquecer o `join`, a `main` imprimiria antes de as threads terminarem. Note também o `throws InterruptedException`: `join` e `sleep` são exceções verificadas.

## Executores, Future e coleções concorrentes

Criar threads à mão não escala. Um `ExecutorService` mantém um pool de threads e recebe tarefas; `submit` devolve um `Future` cujo `get()` bloqueia até o resultado. Sempre chame `shutdown()` no fim, ou o programa pode não terminar.

```java
import java.util.*;
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(3);

        List<Callable<Integer>> tarefas = new ArrayList<>();
        for (int k = 1; k <= 4; k++) {
            final int n = k;
            tarefas.add(() -> n * n);
        }

        int soma = 0;
        for (Future<Integer> f : pool.invokeAll(tarefas)) {
            soma += f.get();
        }
        System.out.println(soma);

        ConcurrentHashMap<String, Integer> contagem = new ConcurrentHashMap<>();
        List<Callable<Void>> escritas = new ArrayList<>();
        for (int i = 0; i < 4; i++) {
            escritas.add(() -> {
                for (int j = 0; j < 500; j++) {
                    contagem.merge("chave", 1, Integer::sum);
                }
                return null;
            });
        }
        pool.invokeAll(escritas);
        System.out.println(contagem.get("chave"));

        pool.shutdown();
        System.out.println(pool.awaitTermination(5, TimeUnit.SECONDS));
    }
}
```

```text
Saída:
30
2000
true
```

`Callable` é como `Runnable`, mas devolve valor e pode lançar exceção. `invokeAll` roda todas e devolve os `Future` já concluídos. `ConcurrentHashMap.merge` é atômico por chave: o `put(get + 1)` equivalente, em um `HashMap` comum, perderia incrementos e, pior, um `HashMap` modificado por várias threads pode corromper sua estrutura interna.

## Armadilhas e conceitos

- **Visibilidade:** sem sincronização, uma thread pode nunca enxergar a escrita de outra. `volatile` garante visibilidade de uma variável (não atomicidade de `x++`).
- **Deadlock:** duas threads, cada uma segurando uma trava que a outra quer. Prevenção clássica: adquirir travas sempre na mesma ordem.
- **Coleções comuns não são thread-safe:** `ArrayList` e `HashMap` exigem sincronização externa ou as versões concorrentes (`ConcurrentHashMap`, `CopyOnWriteArrayList`, `BlockingQueue`).
- `Thread.sleep` e `wait/notify` não substituem a coordenação por estruturas de alto nível, como `BlockingQueue` em produtor-consumidor.

<Callout type="note" title="Threads virtuais">
O Java 21 trouxe threads virtuais, baratas para milhares de tarefas bloqueantes. O modelo de segurança de dados compartilhados continua o mesmo.
</Callout>
