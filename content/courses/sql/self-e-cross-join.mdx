Duas junções aparecem menos no dia a dia, mas são queridinhas de entrevista porque testam se você entende o que um join realmente faz. O **self join** junta uma tabela com ela mesma, para comparar linhas da mesma tabela. O **cross join** combina tudo com tudo, de propósito.

## SELF JOIN: a tabela duas vezes

Não existe palavra-chave `SELF JOIN`. Você só escreve a mesma tabela duas vezes no `FROM`, com apelidos diferentes, e trata cada cópia como se fosse uma tabela separada. O caso clássico é a hierarquia de funcionários, em que `gerente_id` aponta para outro funcionário:

```sql
CREATE TABLE funcionarios (
  id         integer PRIMARY KEY,
  nome       text NOT NULL,
  salario    numeric(10, 2) NOT NULL,
  gerente_id integer REFERENCES funcionarios (id)
);

INSERT INTO funcionarios VALUES
  (1, 'Helena', 30000, NULL),
  (2, 'Igor',   18000, 1),
  (3, 'Júlia',  21000, 1),
  (4, 'Kleber', 19500, 2),
  (5, 'Lara',   12000, 2),
  (6, 'Mateus', 22000, 3);

SELECT f.nome AS funcionario, g.nome AS gerente
FROM funcionarios f
LEFT JOIN funcionarios g ON g.id = f.gerente_id
ORDER BY f.id;
```

```text
Saída:
funcionario | gerente
Helena | NULL
Igor | Helena
Júlia | Helena
Kleber | Igor
Lara | Igor
Mateus | Júlia
```

O `LEFT JOIN` mantém Helena, que não tem gerente. Com `JOIN` simples ela sumiria.

Um enunciado muito comum: "encontre os funcionários que ganham mais que o próprio gerente". Com as duas cópias lado a lado, é só comparar colunas:

```sql
SELECT f.nome, f.salario, g.nome AS gerente, g.salario AS salario_gerente
FROM funcionarios f
JOIN funcionarios g ON g.id = f.gerente_id
WHERE f.salario > g.salario
ORDER BY f.nome;
```

```text
Saída:
nome | salario | gerente | salario_gerente
Kleber | 19500.00 | Igor | 18000.00
Mateus | 22000.00 | Júlia | 21000.00
```

Kleber ganha mais que Igor e Mateus ganha mais que Júlia. Repare que o self join só sobe **um** nível. Para percorrer a hierarquia inteira (o chefe do chefe do chefe), você precisa de uma CTE recursiva, assunto de um capítulo adiante.

### Pares sem repetição

Outro uso é gerar pares de linhas da mesma tabela, como "duplas de funcionários com o mesmo gerente". Se a condição for só `a.gerente_id = b.gerente_id`, cada pessoa forma par consigo mesma e cada dupla aparece duas vezes (A,B e B,A). A correção é exigir `a.id < b.id`:

```sql
SELECT a.nome AS pessoa_a, b.nome AS pessoa_b
FROM funcionarios a
JOIN funcionarios b
  ON a.gerente_id = b.gerente_id
 AND a.id < b.id
ORDER BY a.nome, b.nome;
```

```text
Saída:
pessoa_a | pessoa_b
Igor | Júlia
Kleber | Lara
```

## CROSS JOIN: todas as combinações

`CROSS JOIN` devolve o produto cartesiano: cada linha da esquerda com cada linha da direita, sem condição. Com tabelas de m e n linhas, o resultado tem m vezes n linhas. Parece inútil, mas resolve um problema clássico de relatório: **preencher combinações que não aparecem nos dados**.

Imagine que você precisa das vendas por loja e por mês, inclusive meses sem venda, com zero:

```sql
CREATE TABLE lojas (id integer PRIMARY KEY, nome text NOT NULL);
CREATE TABLE vendas (loja_id integer NOT NULL, mes date NOT NULL, valor numeric(10, 2) NOT NULL);

INSERT INTO lojas VALUES (1, 'Centro'), (2, 'Shopping');
INSERT INTO vendas VALUES
  (1, '2024-01-01', 500), (1, '2024-03-01', 300),
  (2, '2024-01-01', 200), (2, '2024-02-01', 450), (2, '2024-02-01', 50);

SELECT l.nome, m.mes::date AS mes, coalesce(sum(v.valor), 0) AS total
FROM lojas l
CROSS JOIN generate_series('2024-01-01'::date, '2024-03-01'::date, interval '1 month') AS m(mes)
LEFT JOIN vendas v ON v.loja_id = l.id AND v.mes = m.mes
GROUP BY l.nome, m.mes
ORDER BY l.nome, mes;
```

```text
Saída:
nome | mes | total
Centro | 2024-01-01 | 500.00
Centro | 2024-02-01 | 0
Centro | 2024-03-01 | 300.00
Shopping | 2024-01-01 | 200.00
Shopping | 2024-02-01 | 500.00
Shopping | 2024-03-01 | 0
```

O `CROSS JOIN` cria a grade completa (2 lojas vezes 3 meses) e o `LEFT JOIN` encaixa as vendas que existem. Esse padrão, "grade + left join", aparece em dashboards e em problemas de retenção. `generate_series` é do Postgres; no MySQL 8 você gera a sequência com uma CTE recursiva ou com uma tabela de calendário.

## Armadilhas

- **Cross join acidental.** Esquecer a condição de junção na sintaxe com vírgula (`FROM a, b`) produz um produto cartesiano. Com tabelas de 100 mil linhas, são 10 bilhões de combinações.
- **Apelidos trocados no self join.** Escreva o `ON` lendo em voz alta: "o gerente `g` é aquele cujo `id` é o `gerente_id` do funcionário `f`". Inverter os lados dá a resposta ao contrário.
- **Pares duplicados.** Use `a.id < b.id` para pares não ordenados; `a.id <> b.id` ainda gera A,B e B,A.

<Callout type="tip" title="Nomeie os papéis">
Em vez de `f1` e `f2`, use apelidos que digam o papel de cada cópia: `func` e `chefe`, `ida` e `volta`. O entrevistador acompanha seu raciocínio com muito menos esforço.
</Callout>

## Na entrevista

Quando o enunciado comparar linhas da mesma tabela ("maior que o gerente", "voos de ida e volta", "usuários na mesma cidade"), pense em self join. Quando pedir "todas as combinações" ou "incluindo meses sem venda", pense em cross join seguido de left join. Follow-ups comuns: "e se a hierarquia tiver vários níveis?" (CTE recursiva) e "quantas linhas esse cross join gera?" (o produto dos tamanhos; justifique que as tabelas envolvidas são pequenas).
