Em entrevistas de backend e de dados, é comum receber um enunciado aberto: "modele o banco de um sistema de cursos online" ou "desenhe as tabelas de um app de reservas". O entrevistador quer ver se você identifica as coisas que o sistema guarda, como elas se ligam e quantas de cada lado podem existir. Esse raciocínio tem nome: modelagem entidade-relacionamento (ER).

## Entidades e atributos

Uma **entidade** é algo com identidade própria que o sistema precisa lembrar: aluno, curso, professor, matrícula. Cada entidade vira uma tabela, e seus **atributos** viram colunas. Uma pergunta ajuda a separar entidade de atributo: "isso tem vida própria, com dados próprios, e pode ser referenciado por outras coisas?". O e-mail do aluno é atributo; a cidade pode ser só um atributo de texto ou virar entidade, se o sistema precisar de dados sobre cidades (estado, fuso horário).

## Cardinalidade

A **cardinalidade** diz quantas instâncias de um lado se ligam a quantas do outro. Ela decide onde fica a chave estrangeira:

| Relacionamento | Exemplo | Como implementar |
| --- | --- | --- |
| Um para um (1:1) | aluno e perfil detalhado | FK com `UNIQUE` num dos lados, ou mesma tabela |
| Um para muitos (1:N) | professor e cursos | FK no lado "muitos" (`cursos.professor_id`) |
| Muitos para muitos (N:N) | alunos e cursos | tabela associativa com as duas FKs |

Além do "quantos no máximo", importa o **mínimo**: um curso pode existir sem professor? Se não, `professor_id` é `NOT NULL`. Essa é a **participação** obrigatória ou opcional.

## Um modelo concreto

Plataforma de cursos: professores dão cursos (1:N), alunos se matriculam em cursos (N:N) e cada aluno tem no máximo um perfil (1:1).

```sql
CREATE TABLE professores (
  id   integer PRIMARY KEY,
  nome text NOT NULL
);

CREATE TABLE cursos (
  id            integer PRIMARY KEY,
  titulo        text NOT NULL,
  professor_id  integer NOT NULL REFERENCES professores (id)
);

CREATE TABLE alunos (
  id    integer PRIMARY KEY,
  nome  text NOT NULL,
  email text NOT NULL UNIQUE
);

CREATE TABLE perfis (
  aluno_id integer PRIMARY KEY REFERENCES alunos (id),
  bio      text
);

CREATE TABLE matriculas (
  aluno_id      integer NOT NULL REFERENCES alunos (id),
  curso_id      integer NOT NULL REFERENCES cursos (id),
  matriculado_em date NOT NULL,
  nota          integer,
  PRIMARY KEY (aluno_id, curso_id)
);

INSERT INTO professores VALUES (1, 'Rita'), (2, 'Sérgio');
INSERT INTO cursos VALUES (10, 'SQL', 1), (11, 'Python', 1), (12, 'Redes', 2);
INSERT INTO alunos VALUES
  (100, 'Tais', 'tais@ex.com'),
  (101, 'Ulisses', 'uli@ex.com'),
  (102, 'Vera', 'vera@ex.com');
INSERT INTO perfis VALUES (100, 'Analista de dados');
INSERT INTO matriculas VALUES
  (100, 10, '2024-04-01', 9),
  (100, 11, '2024-04-03', NULL),
  (101, 10, '2024-04-02', 7),
  (102, 12, '2024-04-05', 8);

SELECT c.titulo, p.nome AS professor
FROM cursos c
JOIN professores p ON p.id = c.professor_id
ORDER BY c.id;
```

```text
Saída:
titulo | professor
SQL | Rita
Python | Rita
Redes | Sérgio
```

Observe três decisões:

- **1:N** virou `cursos.professor_id`. A FK fica sempre no lado "muitos".
- **1:1** virou `perfis.aluno_id` como chave primária **e** estrangeira. Como a PK é única, cada aluno tem no máximo um perfil.
- **N:N** virou `matriculas`, com chave primária composta `(aluno_id, curso_id)`, que impede matricular o mesmo aluno duas vezes no mesmo curso.

## A tabela associativa tem atributos

A matrícula não é só uma ligação: ela tem data e nota. Esses dados não pertencem ao aluno nem ao curso, e sim ao **par**. Perceber isso é um sinal de maturidade na entrevista. Quando o relacionamento ganha muitos atributos e regras próprias, ele vira uma entidade de verdade, às vezes com chave substituta.

```sql
SELECT a.nome, c.titulo, m.nota
FROM matriculas m
JOIN alunos a ON a.id = m.aluno_id
JOIN cursos c ON c.id = m.curso_id
ORDER BY a.nome, c.titulo;
```

```text
Saída:
nome | titulo | nota
Tais | Python | NULL
Tais | SQL | 9
Ulisses | SQL | 7
Vera | Redes | 8
```

## Verificando a cardinalidade com dados

Uma consulta simples confirma a regra "cada aluno tem no máximo um perfil" e mostra quem não tem nenhum:

```sql
SELECT a.nome, count(p.aluno_id) AS perfis
FROM alunos a
LEFT JOIN perfis p ON p.aluno_id = a.id
GROUP BY a.nome
ORDER BY a.nome;
```

```text
Saída:
nome | perfis
Tais | 1
Ulisses | 0
Vera | 0
```

<Callout type="tip" title="Diga a cardinalidade nos dois sentidos">
"Um professor dá zero ou mais cursos; um curso tem exatamente um professor." Ler o relacionamento dos dois lados revela o mínimo e o máximo de cada ponta, e evita colocar a FK no lugar errado.
</Callout>

## Armadilhas

- **Lista em coluna.** Guardar `cursos = '10,11'` dentro de `alunos` parece prático, mas impede FK, índice e join. É sempre uma tabela associativa disfarçada.
- **FK do lado errado.** Pôr `curso_id` em `professores` limita cada professor a um curso.
- **Esquecer a unicidade do par.** Uma tabela associativa sem PK ou `UNIQUE` composto aceita matrículas duplicadas.
- **Herança forçada.** Tipos de usuário diferentes (aluno, professor) podem compartilhar uma tabela `usuarios` com tabelas de extensão 1:1; não crie uma tabela gigante cheia de colunas opcionais sem pensar.

## Na entrevista

Liste as entidades em voz alta, depois os relacionamentos com cardinalidade nos dois sentidos, e só então escreva o DDL. Pergunte sobre o volume e os acessos mais frequentes, que vão orientar índices e eventuais desnormalizações. Follow-ups comuns: "e se um curso puder ter vários professores?" (vira N:N com tabela `curso_professores`) e "como guardar o histórico de notas?" (uma tabela de avaliações ligada à matrícula, em vez de sobrescrever a coluna).
