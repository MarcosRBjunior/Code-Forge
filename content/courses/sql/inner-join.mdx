Os dados de um sistema relacional ficam espalhados de propósito: clientes numa tabela, pedidos em outra, produtos numa terceira. Quase toda pergunta de negócio ("quanto cada cliente gastou?", "quais produtos saíram em março?") exige juntar essas peças. O `INNER JOIN` é a junção mais usada e a primeira que o entrevistador espera ver você escrever sem hesitar.

## Como funciona

Um `INNER JOIN` combina cada linha da tabela da esquerda com cada linha da tabela da direita e **mantém só os pares em que a condição do `ON` é verdadeira**. Linhas sem par, de qualquer lado, desaparecem do resultado.

Mentalmente, pense em duas etapas: primeiro todas as combinações possíveis, depois o filtro. O banco não executa assim (ele usa nested loop, hash join ou merge join), mas o resultado é exatamente esse.

Vamos montar o esquema dos exemplos:

```sql
CREATE TABLE clientes (
  id     integer PRIMARY KEY,
  nome   text NOT NULL,
  cidade text NOT NULL
);

CREATE TABLE produtos (
  id    integer PRIMARY KEY,
  nome  text NOT NULL,
  preco numeric(10, 2) NOT NULL
);

CREATE TABLE pedidos (
  id         integer PRIMARY KEY,
  cliente_id integer NOT NULL REFERENCES clientes (id),
  criado_em  date NOT NULL
);

CREATE TABLE itens_pedido (
  pedido_id  integer NOT NULL REFERENCES pedidos (id),
  produto_id integer NOT NULL REFERENCES produtos (id),
  quantidade integer NOT NULL,
  PRIMARY KEY (pedido_id, produto_id)
);

INSERT INTO clientes VALUES
  (1, 'Ana', 'Recife'), (2, 'Bruno', 'São Paulo'),
  (3, 'Carla', 'Recife'), (4, 'Diego', 'Curitiba');

INSERT INTO produtos VALUES
  (1, 'Teclado', 150.00), (2, 'Mouse', 80.00),
  (3, 'Monitor', 900.00), (4, 'Webcam', 220.00);

INSERT INTO pedidos VALUES
  (10, 1, '2024-03-01'), (11, 1, '2024-03-05'),
  (12, 2, '2024-03-02'), (13, 3, '2024-03-07');

INSERT INTO itens_pedido VALUES
  (10, 1, 1), (10, 2, 2), (11, 3, 1),
  (12, 2, 1), (12, 3, 2), (13, 1, 3);

SELECT p.id AS pedido, c.nome, p.criado_em
FROM pedidos p
INNER JOIN clientes c ON c.id = p.cliente_id
ORDER BY p.id;
```

```text
Saída:
pedido | nome | criado_em
10 | Ana | 2024-03-01
11 | Ana | 2024-03-05
12 | Bruno | 2024-03-02
13 | Carla | 2024-03-07
```

A palavra `INNER` é opcional: `JOIN` sozinho significa a mesma coisa. Diego não aparece porque nenhum pedido aponta para ele.

## Encadeando várias tabelas

Junções se encadeiam. Cada `JOIN` adiciona uma tabela ao resultado acumulado, e a condição pode usar qualquer tabela já incluída. Para calcular o total gasto por cliente, você precisa percorrer clientes, pedidos, itens e produtos:

```sql
SELECT c.nome,
       sum(i.quantidade * pr.preco) AS total
FROM clientes c
JOIN pedidos p       ON p.cliente_id = c.id
JOIN itens_pedido i  ON i.pedido_id = p.id
JOIN produtos pr     ON pr.id = i.produto_id
GROUP BY c.nome
ORDER BY total DESC;
```

```text
Saída:
nome | total
Bruno | 1880.00
Ana | 1210.00
Carla | 450.00
```

Confira a conta de Ana: pedido 10 tem 1 teclado (150) e 2 mouses (160); pedido 11 tem 1 monitor (900). Total 1210. Validar uma linha à mão assim é um hábito que impressiona.

## Filtrar no ON ou no WHERE

Num `INNER JOIN`, colocar um filtro no `ON` ou no `WHERE` dá o mesmo resultado. Os dois blocos abaixo listam os itens de pedidos de clientes de Recife:

```sql
SELECT p.id AS pedido, pr.nome AS produto, i.quantidade
FROM pedidos p
JOIN clientes c     ON c.id = p.cliente_id AND c.cidade = 'Recife'
JOIN itens_pedido i ON i.pedido_id = p.id
JOIN produtos pr    ON pr.id = i.produto_id
ORDER BY p.id, pr.nome;
```

```text
Saída:
pedido | produto | quantidade
10 | Mouse | 2
10 | Teclado | 1
11 | Monitor | 1
13 | Teclado | 3
```

Escrever `WHERE c.cidade = 'Recife'` daria as mesmas linhas. A diferença só aparece em junções externas, assunto do próximo capítulo. Por clareza, deixe no `ON` a condição de ligação e no `WHERE` os filtros de negócio.

## Armadilhas

- **Multiplicação de linhas.** Se a relação é um para muitos, cada linha do lado "um" se repete para cada par. Somar uma coluna do lado "um" depois do join (por exemplo, o frete do pedido depois de juntar com os itens) conta o mesmo valor várias vezes. Agregue antes de juntar ou junte só o que precisa.
- **Condição incompleta.** Com chave composta, esquecer uma das colunas no `ON` gera combinações erradas. O banco não avisa.
- **Colunas ambíguas.** Se as duas tabelas têm `id`, use apelidos (`p.id`, `c.id`). O Postgres recusa `id` sem qualificação; o resultado de um `SELECT *` traz duas colunas com o mesmo nome.
- **Sintaxe antiga com vírgula.** `FROM pedidos, clientes WHERE ...` é um inner join implícito. Funciona, mas se você esquecer a condição vira um produto cartesiano silencioso.

<Callout type="warning" title="Conte antes e depois">
Se você não tem certeza da cardinalidade, compare `count(*)` antes e depois do join. Se o número cresceu e você esperava que não crescesse, há duplicação.
</Callout>

## Na entrevista

Diga em voz alta a granularidade do resultado ("uma linha por item de pedido") antes de agregar. Escolha apelidos curtos e consistentes e qualifique toda coluna. Follow-ups comuns: "como o banco executa esse join?" (nested loop para tabelas pequenas ou com índice no lado interno, hash join para tabelas grandes sem ordem, merge join quando as duas entradas já vêm ordenadas) e "o que muda se um pedido não tiver itens?" (ele some do resultado; se precisar dele, use `LEFT JOIN`). Postgres e MySQL tratam `INNER JOIN` da mesma forma; o MySQL também aceita `CROSS JOIN ... ON` como sinônimo, o que não é padrão.
