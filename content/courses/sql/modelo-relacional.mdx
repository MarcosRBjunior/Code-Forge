Quase toda rodada de SQL começa com um enunciado do tipo "temos as tabelas `clientes` e `pedidos`; escreva uma consulta que...". Antes de escrever qualquer `SELECT`, você precisa ler esse esquema como o banco o enxerga: relações, linhas, chaves e as ligações entre elas. Este capítulo monta esse vocabulário e o esquema que serve de base para os exemplos.

## Relações, linhas e colunas

No modelo relacional, os dados vivem em **relações**, que o SQL chama de tabelas. Cada tabela tem um conjunto fixo de **colunas** (atributos), cada uma com um tipo, e um conjunto de **linhas** (tuplas). Duas ideias do modelo teórico valem a pena guardar:

- **Não existe ordem garantida das linhas.** Uma tabela é um conjunto, não uma lista. Se a resposta depende de ordem, você precisa de `ORDER BY`.
- **Cada linha deve ser identificável.** É para isso que existe a chave primária.

O SQL é um pouco mais permissivo que a teoria: ele aceita linhas duplicadas numa tabela sem chave e devolve duplicatas nas consultas. Por isso `DISTINCT` existe, e por isso o entrevistador às vezes pergunta "e se houver duplicatas?".

## Chaves

A **chave primária** (`PRIMARY KEY`) identifica cada linha de forma única e não aceita `NULL`. Pode ser **natural** (um CPF, um código de produto) ou **substituta** (um número gerado pelo banco). Em sistemas reais, chaves substitutas são o padrão porque dados naturais mudam: e-mails trocam, códigos são reaproveitados.

A **chave estrangeira** (`FOREIGN KEY`) é uma coluna que aponta para a chave primária de outra tabela. Ela garante **integridade referencial**: o banco recusa um pedido para um cliente que não existe.

Vamos criar um esquema pequeno de loja:

```sql
CREATE TABLE clientes (
  id     integer PRIMARY KEY,
  nome   text NOT NULL,
  cidade text NOT NULL
);

CREATE TABLE pedidos (
  id         integer PRIMARY KEY,
  cliente_id integer NOT NULL REFERENCES clientes (id),
  valor      numeric(10, 2) NOT NULL,
  criado_em  date NOT NULL
);

INSERT INTO clientes (id, nome, cidade) VALUES
  (1, 'Ana', 'Recife'),
  (2, 'Bruno', 'São Paulo'),
  (3, 'Carla', 'Recife'),
  (4, 'Diego', 'Curitiba');

INSERT INTO pedidos (id, cliente_id, valor, criado_em) VALUES
  (10, 1, 120.00, '2024-03-01'),
  (11, 1, 80.50, '2024-03-05'),
  (12, 2, 300.00, '2024-03-02'),
  (13, 3, 45.90, '2024-03-07'),
  (14, 2, 60.00, '2024-03-09');

SELECT id, nome, cidade FROM clientes ORDER BY id;
```

```text
Saída:
id | nome | cidade
1 | Ana | Recife
2 | Bruno | São Paulo
3 | Carla | Recife
4 | Diego | Curitiba
```

Repare que `pedidos.cliente_id` é a chave estrangeira. Um cliente pode ter vários pedidos; um pedido pertence a exatamente um cliente. Esse é um relacionamento **um para muitos**, o mais comum em entrevistas.

## Lendo o relacionamento

Juntar as duas tabelas pela chave estrangeira é a operação fundamental do modelo. Você verá `JOIN` em detalhe mais adiante; por ora, observe que a ligação é só uma igualdade entre colunas:

```sql
SELECT p.id AS pedido, c.nome, p.valor
FROM pedidos p
JOIN clientes c ON c.id = p.cliente_id
ORDER BY p.id;
```

```text
Saída:
pedido | nome | valor
10 | Ana | 120.00
11 | Ana | 80.50
12 | Bruno | 300.00
13 | Carla | 45.90
14 | Bruno | 60.00
```

Diego não aparece porque não tem pedidos. Essa observação ("quem fica de fora?") é a pergunta que separa um `INNER JOIN` de um `LEFT JOIN`, e é cobrada o tempo todo.

## A integridade em ação

Tente inserir um pedido para o cliente 99, que não existe:

```text
INSERT INTO pedidos VALUES (15, 99, 10.00, '2024-03-10');
ERROR:  insert or update on table "pedidos" violates foreign key constraint "pedidos_cliente_id_fkey"
DETAIL:  Key (cliente_id)=(99) is not present in table "clientes".
```

O banco protege o relacionamento. Apagar um cliente que tem pedidos também falha, a menos que a chave estrangeira declare `ON DELETE CASCADE` (apaga os pedidos junto) ou `ON DELETE SET NULL`.

Uma forma rápida de conferir quantas linhas cada tabela tem, útil para validar o esquema antes de responder:

```sql
SELECT 'clientes' AS tabela, count(*) AS linhas FROM clientes
UNION ALL
SELECT 'pedidos', count(*) FROM pedidos
ORDER BY tabela;
```

```text
Saída:
tabela | linhas
clientes | 4
pedidos | 5
```

## Armadilhas

- **Supor ordem.** Sem `ORDER BY`, o Postgres e o MySQL podem devolver as linhas em qualquer ordem, e essa ordem muda depois de atualizações ou com outro plano de execução.
- **Confundir chave primária com índice.** A chave primária cria um índice único automaticamente, mas a chave estrangeira **não** cria índice no Postgres. No MySQL com InnoDB, criar a chave estrangeira gera um índice na coluna se não houver um. Em tabelas grandes, faltar esse índice no Postgres deixa joins e deleções em cascata lentos.
- **Chave natural instável.** Usar e-mail como chave primária parece elegante até o primeiro usuário trocar de e-mail.

<Callout type="tip" title="Leia o esquema em voz alta">
Antes de escrever a consulta, diga ao entrevistador a granularidade de cada tabela: "uma linha de pedidos é um pedido; um cliente tem zero ou mais pedidos". Isso evita contar em dobro depois de um join.
</Callout>

## Na entrevista

Comece confirmando as chaves e a cardinalidade: qual coluna identifica a linha, quais colunas apontam para outras tabelas e se um lado pode não ter correspondência. Pergunte se pode haver duplicatas ou `NULL` nas colunas relevantes. Follow-ups comuns: "por que usar uma chave substituta em vez do e-mail?" (estabilidade e tamanho do índice) e "o que acontece ao apagar um cliente com pedidos?" (depende da ação `ON DELETE`; o padrão é recusar).
