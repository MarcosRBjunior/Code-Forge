Sem controle de versão, "a versão que funcionava" vive numa pasta chamada `api-final-agora-vai`, e duas pessoas mexendo no mesmo projeto se atropelam. Git registra cada mudança com autor, data e motivo, permite voltar atrás e trabalhar em paralelo. GitHub hospeda esses repositórios e adiciona a camada de colaboração: pull requests, revisão de código e integração contínua. Em qualquer vaga de back-end, você vai usar os dois todos os dias.

**Você vai aprender:**

- O modelo do Git: diretório de trabalho, staging e commits
- Criar commits pequenos e com boas mensagens, e inspecionar o histórico
- Trabalhar com branches e resolver conflitos de merge
- Publicar no GitHub e sincronizar com `push`, `fetch` e `pull`
- Colaborar com pull requests e revisão de código

## O modelo mental

O Git guarda o projeto como uma sequência de **commits**: fotografias completas do projeto em momentos escolhidos por você. Cada commit tem um identificador (um hash como `a1b2c3d`), uma mensagem, um autor e um apontamento para o commit anterior.

Entre editar um arquivo e ele entrar num commit, o arquivo passa por três lugares:

| Área | O que é | Comando que move para a próxima |
|---|---|---|
| Diretório de trabalho | Os arquivos como estão no disco | `git add` |
| Staging (índice) | O que vai entrar no próximo commit | `git commit` |
| Repositório | O histórico de commits | |

O staging é o que permite commits precisos: você alterou cinco arquivos, mas só três tratam da correção do bug. Adiciona os três, faz o commit, depois cuida dos outros.

## Começando um repositório

Configure sua identidade uma vez por máquina:

```bash
git config --global user.name "Ana Souza"
git config --global user.email "ana@exemplo.com"
git config --global init.defaultBranch main
```

Dentro da pasta da API da Estante:

```bash
cd estante-api
git init
```

Antes do primeiro commit, crie o `.gitignore`. O que não deve ir para o repositório: dependências (que se reinstalam com `npm ci`), segredos e arquivos gerados.

```bash
# .gitignore
node_modules/
.env
.env.*
!.env.example
dist/
coverage/
*.log
.DS_Store
```

```bash
git status                 # mostra o que mudou e o que está no staging
git add .gitignore package.json package-lock.json src/
git commit -m "Cria API da Estante com rotas de livros e favoritos"
```

## O ciclo do dia a dia

```bash
# editou src/servicos/livrosServico.js
git status
git diff                         # o que mudou e ainda não está no staging
git add src/servicos/livrosServico.js
git diff --staged                # o que vai entrar no commit
git commit -m "Valida ano do livro no cadastro"
```

Para inspecionar o histórico:

```bash
git log --oneline --graph --all
# * 3f9c2a1 (HEAD -> main) Valida ano do livro no cadastro
# * a1b2c3d Cria API da Estante com rotas de livros e favoritos

git show 3f9c2a1          # o que aquele commit mudou
git log -p -- src/app.js  # histórico de um arquivo, com as mudanças
git blame src/app.js      # quem alterou cada linha por último
```

### Boas mensagens de commit

O histórico é documentação. Daqui a seis meses, `git log` é o que explica por que uma linha existe.

- Primeira linha curta (até uns 50 caracteres), no imperativo: "Valida ano do livro", não "validei" nem "mudanças".
- Se precisar de contexto, deixe uma linha em branco e explique o **porquê** no corpo.
- Um commit, uma mudança lógica. "Corrige bug do favorito e muda cor do botão e atualiza README" são três commits.

Muitas equipes usam o padrão Conventional Commits, com prefixos que permitem gerar changelog automaticamente: `feat: adiciona busca de livros`, `fix: corrige 404 ao desfavoritar`, `docs: documenta contrato da API`.

### Desfazendo coisas

```bash
git restore src/app.js            # descarta mudanças não adicionadas no arquivo
git restore --staged src/app.js   # tira do staging, mantém a mudança no disco
git commit --amend                # corrige o último commit (só se ainda não fez push)
git revert 3f9c2a1                # cria um commit novo que desfaz o 3f9c2a1
```

`git revert` é a forma segura de desfazer algo que já foi compartilhado: ele não apaga histórico, adiciona um commit inverso.

## Branches

Uma **branch** é só um ponteiro móvel para um commit. Criar uma é instantâneo e permite desenvolver uma funcionalidade isolada sem quebrar a `main`.

```bash
git switch -c feat/busca-livros     # cria e muda para a branch
# ... edita, add, commit ...
git commit -am "Adiciona filtro de busca em GET /livros"
git switch main                     # volta para main
git merge feat/busca-livros         # traz as mudanças
git branch -d feat/busca-livros     # apaga a branch já integrada
```

Se a `main` não andou desde que a branch foi criada, o merge é um **fast-forward**: o ponteiro da `main` só avança. Se as duas andaram, o Git cria um **commit de merge** com dois pais.

### Conflitos

Quando duas branches alteram as mesmas linhas, o Git não adivinha qual versão vale e marca um conflito:

```bash
git merge feat/porta-configuravel
# CONFLICT (content): Merge conflict in src/server.js
```

```javascript
// src/server.js
<<<<<<< HEAD
const porta = process.env.PORT ?? 8000;
=======
const porta = Number(process.env.PORTA_API) || 3001;
>>>>>>> feat/porta-configuravel
```

Entre `<<<<<<<` e `=======` está a versão da branch atual; entre `=======` e `>>>>>>>`, a que está chegando. Resolver significa editar o arquivo para ficar como deve ser (pode ser uma das duas, uma combinação ou algo novo), apagar os marcadores e concluir:

```bash
# editou src/server.js, ficou: const porta = Number(process.env.PORT) || 8000;
git add src/server.js
git commit                    # conclui o merge
# ou, para desistir: git merge --abort
```

Conflito não é erro: é o Git pedindo uma decisão que só uma pessoa pode tomar. Rode os testes depois de resolver, porque o código pode ter ficado sintaticamente certo e logicamente errado.

## GitHub: publicando o repositório

Crie um repositório vazio no GitHub (sem README, para não gerar histórico divergente) e conecte:

```bash
git remote add origin git@github.com:ana/estante-api.git
git push -u origin main
```

`origin` é o apelido do repositório remoto. O `-u` liga a branch local à remota, para que depois baste `git push` e `git pull`. Para autenticar, use uma chave SSH ou o GitHub CLI (`gh auth login`); senha de conta não funciona mais para Git.

Sincronizando:

```bash
git fetch origin            # baixa as novidades sem mexer nos seus arquivos
git log --oneline main..origin/main   # o que chegou e você ainda não tem
git pull                    # fetch + integra na branch atual
git push                    # envia seus commits
```

Se alguém enviou commits antes de você, o `push` é recusado (`rejected, non-fast-forward`). Faça `git pull`, resolva conflitos se houver, e envie de novo.

<Callout type="warning" title="Segredo em commit não sai com outro commit">
Se um `.env` com senha do banco entrou num commit e foi enviado, apagar o arquivo num commit seguinte não resolve: ele continua no histórico, e repositórios públicos são varridos por robôs em minutos. A ação correta é **revogar e trocar a credencial imediatamente**. Limpar o histórico vem depois, e é secundário. Previna com o `.gitignore` criado antes do primeiro commit e um `.env.example` sem valores reais.
</Callout>

## Colaborando com pull requests

Em equipe, ninguém faz push direto na `main`. O fluxo mais comum (GitHub Flow):

1. Atualize a `main` local e crie uma branch para a tarefa.
2. Faça commits pequenos e envie a branch.
3. Abra um **pull request** (PR) pedindo para integrar a branch na `main`.
4. Colegas revisam, comentam e aprovam; a CI roda testes automaticamente.
5. Depois de aprovado e com testes verdes, o PR é integrado e a branch apagada.

```bash
git switch main && git pull
git switch -c fix/favorito-duplicado
# ... commits ...
git push -u origin fix/favorito-duplicado
gh pr create --title "Responde 409 ao favoritar livro duplicado" \
  --body "Antes o favorito era gravado duas vezes. Agora o serviço verifica e responde 409."
```

Um bom PR é pequeno (dá para revisar em 15 minutos), tem descrição com o **porquê** e como testar, e faz uma coisa só. Ao revisar, comente sobre comportamento, legibilidade e casos de erro, e seja específico: "Este `find` devolve `undefined` se o id não existir; o que acontece na linha seguinte?" ajuda mais que "isso pode quebrar".

Quando a `main` anda enquanto seu PR está aberto, atualize a branch:

```bash
git fetch origin
git merge origin/main           # traz a main para a sua branch
# ou, para um histórico linear:
git rebase origin/main          # reaplica seus commits em cima da main
git push --force-with-lease     # necessário depois de rebase
```

O `rebase` reescreve os seus commits. Use em branches só suas; nunca em branches que outras pessoas usam. `--force-with-lease` é a versão segura do force push: recusa se alguém tiver enviado algo que você ainda não viu.

### Contribuindo em projetos de terceiros

Para projetos em que você não tem permissão de escrita (open source), o fluxo usa um **fork**: uma cópia do repositório na sua conta. Você clona o fork, cria a branch, envia para o fork e abre o PR de lá para o repositório original. Para trazer novidades do original, adicione-o como um segundo remoto:

```bash
git remote add upstream https://github.com/projeto/original.git
git fetch upstream
git merge upstream/main
```

### Proteja a main

Nas configurações do repositório, crie uma regra de proteção para a `main`: exigir PR, pelo menos uma aprovação e testes passando antes do merge. Isso transforma boas práticas em regra, e não em boa vontade.

## Na entrevista

- **Qual a diferença entre `git fetch` e `git pull`?** `fetch` só baixa os commits do remoto e atualiza as referências remotas, sem tocar na sua branch. `pull` faz `fetch` e integra (merge ou rebase) na branch atual.
- **Merge ou rebase?** Merge preserva o histórico real e cria um commit de junção; rebase reescreve commits para um histórico linear. Rebase em branch pessoal antes do PR, merge (ou squash) para integrar; nunca rebase em branch compartilhada.
- **Como desfazer um commit que já foi para o remoto?** `git revert`, que cria um commit inverso sem reescrever o histórico de ninguém.
- **Commitei uma senha. E agora?** Revogue a credencial primeiro. Depois remova do código, adicione ao `.gitignore` e, se necessário, limpe o histórico com uma ferramenta própria, sabendo que cópias já podem existir.

## Pratique

Publique a Estante no GitHub com um fluxo profissional:

1. Crie os repositórios (ou um monorepo) com `.gitignore`, `.env.example` e README.
2. Proteja a `main` exigindo pull request.
3. Implemente uma melhoria pequena (por exemplo, `GET /livros?busca=`) numa branch, com pelo menos três commits bem escritos, e abra um PR com descrição e passos de teste.
4. Provoque um conflito de propósito: em outra branch, altere a mesma linha do `server.js`, integre a primeira e resolva o conflito na segunda.
5. Integre o PR com "Squash and merge" e compare o histórico com um merge comum.
