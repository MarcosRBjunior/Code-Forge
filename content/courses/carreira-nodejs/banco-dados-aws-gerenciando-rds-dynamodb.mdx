Instalar PostgreSQL numa EC2 funciona, mas aí você cuida de backup, replicação, patches, failover e disco cheio às três da manhã. Os bancos gerenciados da AWS tiram esse trabalho de você: o RDS opera bancos relacionais tradicionais, e o DynamoDB é um banco chave-valor sem servidor que escala praticamente sem limite. Saber quando usar cada um, como configurá-los com segurança e como falar com eles a partir do Node.js é uma das habilidades mais cobradas em vagas de back-end na AWS.

**Você vai aprender:**

- Como criar um RDS PostgreSQL privado, com Multi-AZ, backups e senha gerenciada
- A diferença entre Multi-AZ e réplicas de leitura, e como restaurar a um ponto no tempo
- Como conectar o Node.js ao RDS com TLS e pool de conexões dimensionado
- Como modelar no DynamoDB a partir dos padrões de acesso
- Como ler e gravar no DynamoDB com o SDK v3, incluindo escrita condicional e transação

## RDS: o que a AWS opera por você

O **Amazon RDS** roda PostgreSQL, MySQL, MariaDB, SQL Server, Oracle e Db2 em instâncias gerenciadas. Você escolhe a engine, a classe da instância e o armazenamento; a AWS cuida de instalação, patches em janela de manutenção, backups automáticos e failover. Existe também o **Aurora**, uma engine compatível com PostgreSQL e MySQL com armazenamento distribuído próprio, que vale a pena quando você precisa de muitas réplicas ou failover mais rápido.

O que continua sendo seu: modelagem, índices, consultas lentas, migrações de schema e o número de conexões.

## Criando um PostgreSQL privado

O banco fica nas subnets de dados da VPC, sem acesso público. O **DB subnet group** diz ao RDS em quais subnets ele pode colocar as instâncias (pelo menos duas zonas).

```bash
aws rds create-db-subnet-group \
  --db-subnet-group-name livros-dados \
  --db-subnet-group-description "Subnets de dados da API de livros" \
  --subnet-ids subnet-0dadosA0000000000 subnet-0dadosB0000000000

aws rds create-db-instance \
  --db-instance-identifier livros-db \
  --engine postgres \
  --db-instance-class db.t4g.small \
  --allocated-storage 20 --storage-type gp3 --storage-encrypted \
  --master-username livros \
  --manage-master-user-password \
  --db-name livros \
  --db-subnet-group-name livros-dados \
  --vpc-security-group-ids sg-0db0000000000000 \
  --no-publicly-accessible \
  --multi-az \
  --backup-retention-period 7 \
  --deletion-protection

aws rds wait db-instance-available --db-instance-identifier livros-db
```

Destaques:

- **`--manage-master-user-password`:** o RDS gera a senha e a guarda no Secrets Manager, com rotação. Ninguém precisa conhecê-la.
- **`--multi-az`:** mantém uma réplica síncrona em outra zona. Se a principal falhar, o endpoint DNS passa a apontar para a réplica em um ou dois minutos.
- **`--backup-retention-period 7`:** backups diários mais logs de transação, que permitem restaurar para qualquer segundo dos últimos 7 dias.
- **`--deletion-protection`:** impede apagar o banco por engano, inclusive pelo Terraform.

## Multi-AZ não é réplica de leitura

As duas coisas criam cópias do banco, mas resolvem problemas diferentes:

| | Multi-AZ (instância) | Réplica de leitura |
|---|---|---|
| Objetivo | Disponibilidade | Escalar leituras |
| Replicação | Síncrona | Assíncrona (pode atrasar) |
| Aceita consultas | Não, fica em espera | Sim, somente leitura |
| Endpoint | O mesmo do principal | Um endpoint próprio |
| Failover | Automático | Promoção manual |

```bash
aws rds create-db-instance-read-replica \
  --db-instance-identifier livros-db-leitura \
  --source-db-instance-identifier livros-db
```

Na aplicação, use a réplica para relatórios e listagens que toleram alguns segundos de atraso. Nunca leia da réplica logo depois de escrever esperando ver o dado novo.

Restaurar um backup **cria uma instância nova**; o banco original fica intacto. Isso é ótimo para recuperar uma tabela apagada por engano: você restaura em paralelo, copia os dados e descarta a cópia.

```bash
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier livros-db \
  --target-db-instance-identifier livros-db-recuperado \
  --restore-time 2026-11-10T14:00:00Z \
  --db-subnet-group-name livros-dados
```

## Conectando o Node.js ao RDS

A aplicação lê as credenciais do segredo criado pelo RDS e conecta com TLS, validando o certificado com o pacote de CAs que a AWS publica (`global-bundle.pem`).

```javascript
// src/db.js
import fs from "node:fs";
import pg from "pg";
import {
  SecretsManagerClient,
  GetSecretValueCommand,
} from "@aws-sdk/client-secrets-manager";

const sm = new SecretsManagerClient({});
const { SecretString } = await sm.send(
  new GetSecretValueCommand({ SecretId: process.env.DB_SECRET_ARN }),
);
const { username, password } = JSON.parse(SecretString);

export const pool = new pg.Pool({
  host: process.env.DB_HOST, // endpoint do RDS
  database: "livros",
  user: username,
  password,
  ssl: { ca: fs.readFileSync("certs/global-bundle.pem", "utf8") },
  max: 10,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
});

const { rows } = await pool.query("SELECT now() AS agora");
console.log("conectado ao RDS:", rows[0].agora);
```

O cálculo de conexões é a armadilha clássica. O PostgreSQL tem um limite de conexões que depende da memória da instância, e cada conexão consome memória. Se a API escala para 10 instâncias com `max: 10`, são 100 conexões. Para cargas com muitas instâncias ou funções Lambda, coloque o **RDS Proxy** na frente: ele mantém um pool compartilhado e multiplexa as conexões da aplicação.

Durante um failover Multi-AZ, conexões abertas caem. O `pg.Pool` descarta as quebradas e abre novas, mas a requisição em andamento recebe erro. Trate erros de conexão como transitórios e repita operações idempotentes uma vez.

## DynamoDB: outra forma de pensar

O **DynamoDB** é um banco chave-valor e de documentos, sem servidor. Não há instância para escolher, nem conexões para gerenciar: cada operação é uma chamada HTTP assinada. Ele entrega latência de poucos milissegundos com qualquer volume, **desde que** você acesse os dados pela chave.

Todo item é identificado pela **chave primária**:

- **Partition key (PK):** define em qual partição física o item mora. Itens com a mesma PK ficam juntos.
- **Sort key (SK), opcional:** ordena os itens dentro da mesma partição e permite consultas por faixa (`begins_with`, `between`).

A modelagem é o inverso do relacional. Em SQL você normaliza e depois escreve as consultas. No DynamoDB você **lista os padrões de acesso primeiro** e desenha as chaves para atendê-los. Para as avaliações dos livros:

| Padrão de acesso | Chave usada |
|---|---|
| Últimas avaliações de um livro | PK = `LIVRO#42`, SK começa com `AVALIACAO#`, ordem decrescente |
| Média e total de avaliações de um livro | PK = `LIVRO#42`, SK = `RESUMO` |
| Avaliações de um usuário | Índice secundário global com PK = `USUARIO#7` |

```bash
aws dynamodb create-table --table-name livros-app \
  --attribute-definitions \
    AttributeName=pk,AttributeType=S AttributeName=sk,AttributeType=S \
    AttributeName=gsi1pk,AttributeType=S \
  --key-schema AttributeName=pk,KeyType=HASH AttributeName=sk,KeyType=RANGE \
  --global-secondary-indexes \
    'IndexName=por-usuario,KeySchema=[{AttributeName=gsi1pk,KeyType=HASH},{AttributeName=sk,KeyType=RANGE}],Projection={ProjectionType=ALL}' \
  --billing-mode PAY_PER_REQUEST

aws dynamodb update-time-to-live --table-name livros-app \
  --time-to-live-specification Enabled=true,AttributeName=expiraEm
```

Sobre capacidade: **sob demanda** (`PAY_PER_REQUEST`) cobra por leitura e escrita e se ajusta sozinho, ideal para tráfego imprevisível e para começar. **Provisionado** reserva unidades de leitura e escrita por segundo, com auto scaling, e sai mais barato para tráfego estável e alto. O **TTL** apaga automaticamente itens cujo atributo `expiraEm` (timestamp em segundos) já passou, útil para sessões e dados temporários.

## Lendo e gravando com o SDK v3

O `DynamoDBDocumentClient` converte objetos JavaScript comuns para o formato tipado do DynamoDB, então você trabalha com `{ nota: 5 }` em vez de `{ nota: { N: "5" } }`.

```javascript
// src/avaliacoes.js
import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import {
  DynamoDBDocumentClient,
  QueryCommand,
  TransactWriteCommand,
} from "@aws-sdk/lib-dynamodb";

const doc = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const TABELA = "livros-app";

export async function avaliar(livroId, usuarioId, nota, texto) {
  const data = new Date().toISOString();
  await doc.send(
    new TransactWriteCommand({
      TransactItems: [
        {
          Put: {
            TableName: TABELA,
            Item: {
              pk: `LIVRO#${livroId}`,
              sk: `AVALIACAO#${data}#${usuarioId}`,
              gsi1pk: `USUARIO#${usuarioId}`,
              nota,
              texto,
            },
            ConditionExpression: "attribute_not_exists(pk)",
          },
        },
        {
          Update: {
            TableName: TABELA,
            Key: { pk: `LIVRO#${livroId}`, sk: "RESUMO" },
            UpdateExpression: "ADD totalAvaliacoes :um, somaNotas :nota",
            ExpressionAttributeValues: { ":um": 1, ":nota": nota },
          },
        },
      ],
    }),
  );
}

export async function ultimasAvaliacoes(livroId, limite = 10) {
  const { Items } = await doc.send(
    new QueryCommand({
      TableName: TABELA,
      KeyConditionExpression: "pk = :pk AND begins_with(sk, :prefixo)",
      ExpressionAttributeValues: { ":pk": `LIVRO#${livroId}`, ":prefixo": "AVALIACAO#" },
      ScanIndexForward: false, // mais recentes primeiro
      Limit: limite,
    }),
  );
  return Items;
}
```

O que esse código ensina:

- **Escrita condicional:** `attribute_not_exists(pk)` garante que o `Put` não sobrescreve um item existente. Sem condição, `Put` substitui silenciosamente.
- **`ADD` é atômico:** duas avaliações simultâneas incrementam o contador corretamente, sem ler e regravar.
- **Transação:** a avaliação e o resumo são gravados juntos ou nenhum dos dois. Transações custam o dobro de uma escrita comum, então use quando a consistência importa.
- **`Query` e não `Scan`:** a consulta vai direto na partição do livro. Um `Scan` leria a tabela inteira.

## RDS ou DynamoDB?

| Critério | RDS (PostgreSQL) | DynamoDB |
|---|---|---|
| Consultas | Livres, com JOIN, agregações, filtros arbitrários | Só pelos padrões planejados nas chaves e índices |
| Escala | Vertical, mais réplicas de leitura | Horizontal e automática |
| Operação | Instância, conexões, janela de manutenção | Nenhuma, sem conexões |
| Custo | Por hora ligado | Por requisição ou capacidade provisionada |
| Bom para | Domínio relacional, relatórios, consultas que mudam | Alto volume com acesso por chave, sessões, eventos, contadores |

Muitas aplicações usam os dois: o catálogo e os pedidos no PostgreSQL, e sessões, carrinho ou feed de eventos no DynamoDB.

<Callout type="warning" title="Scan em produção e partição quente">
O erro mais caro no DynamoDB é usar `Scan` com filtro para buscar dados: ele lê (e cobra) a tabela inteira, mesmo que retorne três itens. Se você precisa de um padrão de acesso novo, crie um índice secundário global. O segundo erro é concentrar o tráfego numa única partition key (por exemplo, `pk = "CONTADOR_GLOBAL"`): todas as escritas vão para a mesma partição e esbarram no limite dela.
</Callout>

## Na entrevista

**Multi-AZ ou réplica de leitura, qual escolhe?** Depende do problema. Multi-AZ é para disponibilidade (failover automático, réplica síncrona que não atende consultas). Réplica de leitura é para escalar leituras (assíncrona, endpoint próprio). Produção séria costuma ter as duas.

**Como você modela no DynamoDB?** Começo pelos padrões de acesso, escolho partition e sort key para atender os principais com `Query`, e crio índices secundários globais para os outros. Evito `Scan` e chaves com pouca cardinalidade.

**Sua API em Lambda está esgotando as conexões do RDS. O que fazer?** Colocar RDS Proxy na frente, abrir a conexão fora do handler para reutilizar entre invocações e limitar a concorrência da função.

## Pratique

Estenda a API de livros:

1. Catálogo de livros no RDS PostgreSQL privado, com senha gerenciada pelo Secrets Manager e conexão TLS.
2. Avaliações no DynamoDB, com as rotas `POST /livros/:id/avaliacoes` e `GET /livros/:id/avaliacoes`, usando a transação deste capítulo.
3. Uma rota `GET /livros/:id` que junta os dados do PostgreSQL com a média calculada a partir do item `RESUMO`.
4. Um teste de restauração: apague uma linha, restaure o RDS para um minuto antes e recupere o dado.
