O Nível 1 entregou uma API. O Nível 2 olhou para tudo o que fica em volta dela: o servidor Linux onde ela roda, os scripts Bash que sobem o ambiente, fazem backup e avisam quando algo sai do normal, os algoritmos e estruturas de dados que decidem se uma rotina leva segundos ou minutos, e o banco de dados visto sem a camada do ORM. A API de livros apareceu em containers com PostgreSQL, e o banco da livraria online (clientes, livros, pedidos e itens) acompanhou os capítulos de SQL e de MongoDB.

Este checkpoint confere se você consegue operar e investigar a API sozinho: escrever o script que faz o backup de verdade, descobrir qual consulta deixou o banco lento, responder uma pergunta de negócio em SQL e escolher a estrutura de dados certa. O desafio no fim junta esses pedaços num kit de operação e dados para a livraria.

**Neste checkpoint:**

- Uma tabela com os 14 capítulos do nível e o que cada um exige de você
- Uma autoavaliação com habilidades que dá para provar no terminal
- Um desafio prático: o kit de operação, dados e relatórios da livraria

## Desafio prático

A livraria online cresceu: o catálogo passou de cem mil títulos, a equipe de vendas quer números toda segunda-feira e ninguém sabe dizer quando foi o último backup. Você vai entregar o **kit de operação e dados da livraria**: a API de livros rodando com PostgreSQL em containers, com scripts de operação, banco ajustado, relatórios em SQL e uma importação de catálogo que não derruba ninguém.

### Requisitos

1. **Esquema e migrações.** As tabelas `autores`, `livros`, `clientes`, `pedidos` e `itens_pedido` no PostgreSQL, com tipos adequados (`numeric` para preço, `timestamptz` para datas), `CHECK` em preço, estoque e quantidade, `isbn` único e chaves estrangeiras com `ON DELETE RESTRICT`. Tudo criado por migrações SQL versionadas, aplicadas em transação e registradas numa tabela `migracoes`.
2. **Papéis e conexões.** Um papel dono das tabelas, usado só pelas migrações, e o papel `livros_app` da API, com apenas `SELECT`, `INSERT`, `UPDATE` e `DELETE`, garantidos também para tabelas futuras com `ALTER DEFAULT PRIVILEGES`. O pool do `pg` com `max`, `connectionTimeoutMillis` e `application_name` definidos.
3. **Pedido atômico.** `POST /pedidos` que, numa transação, baixa o estoque de cada item com um `UPDATE` condicional e `RETURNING`, grava pedido e itens e desfaz tudo se algum livro não tiver estoque. Todas as consultas parametrizadas, e a conexão sempre devolvida ao pool num `finally`.
4. **Catálogo ordenável.** `GET /livros` com `?ordem=-preco,titulo` validado contra uma lista fixa de campos e traduzido para `ORDER BY` no banco, com um campo único como desempate para a paginação ficar estável.
5. **Relatórios.** `GET /relatorios/vendas` com receita, pedidos e ticket médio por mês, acumulado e variação em relação ao mês anterior, e os 2 livros mais vendidos por categoria com `dense_rank`. Pedidos cancelados ficam fora, e clientes sem pedidos aparecem com zero na consulta de clientes inativos.
6. **Importação de catálogo.** Um script `importar-livros.js` que lê um CSV de ISBNs, busca os dados numa API externa com a `FilaDeTarefas` (concorrência configurável e até 3 novas tentativas para 429 e 5xx), evita buscas repetidas com um `CacheLRU` e grava com upsert por ISBN.
7. **Desempenho.** Com um milhão de livros gerados por `generate_series`, as três consultas mais caras do `pg_stat_statements` depois de uma carga na API, cada uma com `EXPLAIN (ANALYZE, BUFFERS)` antes e depois de um índice criado com `CONCURRENTLY`.
8. **Scripts de operação.** Em `scripts/`: `dev.sh` (sobe o Compose, espera o banco saudável e roda as migrações), `backup.sh` com retenção e recusa de backup vazio, `restore.sh` com confirmação e `test-integracao.sh` que limpa os containers com `trap` mesmo quando o teste falha.
9. **Monitoramento.** `monitor.sh` que confere carga, memória, disco e o `/health` da API (que faz `SELECT 1` no banco), alerta no máximo uma vez a cada 30 minutos pelo mesmo motivo, roda a cada 5 minutos por um timer do systemd e grava o resultado em log.
10. **Avaliações no MongoDB.** As avaliações dos livros numa coleção própria, com o padrão de subconjunto (as 5 últimas embutidas no livro) e valor calculado (soma e quantidade de notas), validação `$jsonSchema` e índices que aparecem como `IXSCAN` no `explain`.

Uma organização possível do repositório, para não perder nenhuma peça:

```text
# estrutura sugerida
livraria/
  compose.yaml
  migracoes/            001-esquema.sql, 002-papeis.sql, 003-indices.concurrently.sql
  relatorios/           receita-mensal.sql, top-por-categoria.sql, clientes-inativos.sql
  scripts/              dev.sh, backup.sh, restore.sh, test-integracao.sh, monitor.sh
  deploy/               livros-api.service, monitor.service, monitor.timer
  src/                  app.js, server.js, db.js, pedidos/, relatorios/, importacao/
  OTIMIZACAO.md
  OPERACAO.md
```

Um ponto de partida para o pedido atômico, com a parte que mais costuma dar errado já no lugar:

```javascript
// src/pedidos/criarPedido.js
import { pool } from "../db.js";

export async function criarPedido(clienteId, itens) {
  const cliente = await pool.connect();
  try {
    await cliente.query("BEGIN");
    // para cada item: UPDATE livros SET estoque = estoque - $1
    //   WHERE id = $2 AND estoque >= $1 RETURNING preco
    // nenhuma linha devolvida significa sem estoque: lance um erro de negócio
    // depois: INSERT em pedidos e itens_pedido com RETURNING id
    await cliente.query("COMMIT");
  } catch (erro) {
    await cliente.query("ROLLBACK");
    throw erro;
  } finally {
    cliente.release();
  }
}
```

### Critérios de aceite

- `./scripts/dev.sh` num clone limpo deixa a API respondendo, e `curl -s localhost:3000/health` devolve `status` igual a `ok`. Parar o container do banco faz o mesmo `curl` devolver 503.
- `./scripts/backup.sh` gera um arquivo `.sql.gz` não vazio, e `./scripts/restore.sh` num banco novo resulta na mesma contagem de linhas em `livros` e `pedidos`.
- Conectado como `livros_app`, `DROP TABLE livros` falha com `permission denied`, e uma tabela criada por migração nova já pode ser lida pela API.
- Um pedido com um item sem estoque devolve 409 e não altera o estoque de nenhum outro item do mesmo pedido.
- `GET /livros?ordem=senha` devolve 400, e `GET /livros?ordem=-preco,titulo` devolve os livros mais caros primeiro, com empates em ordem alfabética.
- O relatório de cada consulta lenta mostra `Seq Scan` antes e `Index Scan` ou `Bitmap Index Scan` depois, com o tempo médio comparado.
- A importação com concorrência 20 termina mais rápido que com concorrência 1, sem nenhuma resposta 429 sem nova tentativa.
- `systemctl list-timers` mostra o timer do monitor, e duas execuções seguidas com o disco acima do limite geram um alerta só.

### Dicas

- Comece pelos scripts: com `dev.sh` e `backup.sh` funcionando, você pode quebrar o banco à vontade nos outros requisitos. O esqueleto seguro e o `trap` estão em [Scripting com Bash e Docker](/learn/carreira-nodejs/scripting-automatizando-tarefas-bash-docker).
- O executor de migrações roda cada arquivo numa transação, mas `CREATE INDEX CONCURRENTLY` não pode rodar dentro de uma. Deixe essas migrações marcadas para rodar fora, como explica [Administração e otimização](/learn/carreira-nodejs/postgresql-administracao-otimizacao-banco).
- Escreva as consultas de relatório primeiro no banco da livraria em SQLite, com os dados pequenos dos capítulos, e só depois leve para o PostgreSQL. As funções de janela são as mesmas; mude apenas as funções de data. Reveja [Análise de dados com SQL](/learn/carreira-nodejs/sqlite-online-analise-dados-sql).
- Para a fila de importação, meça antes de otimizar: rode com concorrência 1, 5 e 20 e anote os tempos. A implementação de referência está em [Filas, pilhas e estruturas de dados](/learn/carreira-nodejs/nodejs-dominando-filas-pilhas-estruturas-dados).
- Antes de modelar as avaliações no MongoDB, escreva a tabela de operações e frequências. A decisão entre embutir e referenciar sai dela, como em [Modelagem de dados](/learn/carreira-nodejs/mongodb-modelagem-dados).

## Revisão rápida

**Sem `pipefail`, um pipe mente.** O código de saída de um pipe é o do último comando. No backup, `pg_dump | gzip` termina com sucesso mesmo que o `pg_dump` falhe, e você guarda um arquivo quebrado. Por isso todo script começa com `set -euo pipefail` e ainda confere se o arquivo não ficou vazio.

```bash
#!/usr/bin/env bash
# scripts/backup.sh
set -euo pipefail
ARQUIVO="./backups/livros-$(date +%Y%m%d-%H%M%S).sql.gz"
docker compose exec -T db pg_dump -U livros livros | gzip > "$ARQUIVO"
[[ -s "$ARQUIVO" ]] || { echo "backup vazio" >&2; exit 1; }
```

Na mesma linha de cuidado: aspas em toda variável. `rm -rf $DIR/` sem aspas e com `DIR` vazio vira `rm -rf /`; com `set -u` o script para antes.

**O `sort` sem comparador ordena como texto.** `[10, 9, 1].sort()` devolve `[1, 10, 9]`. Passe sempre um comparador, use `Intl.Collator` para texto em português e lembre que `sort` altera o array original: use `toSorted` ou copie antes.

```javascript
// src/utils/ordenar.js
const collator = new Intl.Collator("pt-BR", { sensitivity: "base", numeric: true });
export const porPrecoDescETitulo = (a, b) => b.preco - a.preco || collator.compare(a.titulo, b.titulo);
```

**Comparar com `NULL` nunca é verdadeiro.** `WHERE cidade = NULL` não devolve nada; o teste certo é `IS NULL`. Pelo mesmo motivo, filtrar a tabela da direita no `WHERE` transforma o `LEFT JOIN` num `INNER JOIN` e some com quem não tem par. A condição vai no `ON`, e a contagem usa `count(p.id)`, não `count(*)`.

```sql
-- relatorios/pedidos-por-cliente.sql
SELECT c.nome, count(p.id) AS pedidos
FROM clientes c
LEFT JOIN pedidos p ON p.cliente_id = c.id AND p.status <> 'cancelado'
GROUP BY c.id, c.nome;
```

**Upsert é um comando só, não `SELECT` seguido de `INSERT`.** Ler antes de decidir abre uma condição de corrida entre duas importações simultâneas. O `ON CONFLICT` precisa de uma coluna com `UNIQUE`, e `EXCLUDED` é a linha que você tentou inserir.

```sql
-- sql/upsert-livro.sql
INSERT INTO livros (isbn, titulo, preco, estoque, autor_id)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (isbn) DO UPDATE SET preco = EXCLUDED.preco
RETURNING id, preco;
```

**Função de janela não colapsa linhas.** Com `ORDER BY` dentro do `OVER`, o `sum` vira acumulado até a linha atual, e `lag` traz o valor da linha anterior. No primeiro mês o `lag` é `NULL`, e a variação também: trate isso na rota em vez de mostrar zero.

```sql
-- relatorios/receita-mensal.sql
WITH mensal AS (
  SELECT mes, round(sum(receita), 2) AS receita FROM vendas GROUP BY mes
)
SELECT mes, receita,
       sum(receita) OVER (ORDER BY mes) AS acumulado,
       lag(receita) OVER (ORDER BY mes) AS mes_anterior
FROM mensal ORDER BY mes;
```

**Conexão que não volta para o pool trava a API sem erro.** Em transações com `pool.connect()`, o `release()` vai no `finally`. A conta que importa é instâncias da API vezes o `max` do pool, que precisa ficar abaixo do `max_connections` do servidor, com folga.

**Índice em produção é com `CONCURRENTLY`.** Sem ele, o `CREATE INDEX` bloqueia escritas durante toda a construção. A versão concorrente não roda dentro de transação e, se falhar, deixa um índice inválido para apagar e recriar.

**No MongoDB, o esquema nasce das consultas.** Embuta o que é lido junto e tem tamanho limitado (os itens de um pedido); referencie o que cresce sem limite (as avaliações de um livro). Um array que só cresce acaba batendo no limite de 16 MB do documento e deixa cada leitura mais lenta até lá.

<Callout type="warning" title="Backup que nunca foi restaurado não é backup">
O script de backup rodando todo dia sem erro dá uma sensação de segurança que só vale depois do primeiro teste de restauração. Agende também a restauração num banco descartável e compare a contagem de linhas. O dia de descobrir que o arquivo estava vazio não pode ser o dia em que você precisa dele.
</Callout>

## Na entrevista

**Por que `set -euo pipefail`?** `-e` para o script no primeiro erro, `-u` trata variável indefinida como erro e `pipefail` faz um pipe falhar se qualquer comando dele falhar. Juntos, impedem que um script siga em frente depois de algo dar errado.

**Qual a diferença entre `SIGTERM` e `SIGKILL`?** `SIGTERM` é um pedido para encerrar, que o processo pode tratar para terminar requisições e fechar conexões. `SIGKILL` é o kernel removendo o processo sem chance de limpeza. Docker, Kubernetes e systemd mandam o primeiro e só depois de um prazo o segundo.

**Merge sort ou quick sort?** Merge sort garante O(n log n) e é estável, ao custo de memória extra. Quick sort costuma ser mais rápido na prática e ordena no lugar, mas degrada para O(n²) com pivô ruim. Para ordenar por vários campos em sequência, estabilidade importa.

**Como você implementaria um cache LRU?** Com um `Map`, que preserva a ordem de inserção. Na leitura, apaga e reinsere a chave para ela ir para o fim. Na escrita, se passou da capacidade, remove a primeira chave do `Map`, que é a menos usada recentemente.

**A API ficou lenta. Por onde você começa no banco?** Pelo `pg_stat_activity`, para ver o que está rodando e esperando agora, e pelo `pg_stat_statements`, para achar as consultas que mais somam tempo. Na mais cara, `EXPLAIN (ANALYZE, BUFFERS)` mostra se falta índice ou se a estatística está desatualizada.

**Qual a diferença entre `WHERE` e `HAVING`?** `WHERE` filtra linhas antes do agrupamento; `HAVING` filtra grupos depois das agregações. Condição sobre `sum` ou `count` só pode ir no `HAVING`.

**O que uma função de janela faz que o `GROUP BY` não faz?** Calcula sobre um conjunto de linhas relacionadas sem colapsá-las numa só. Dá para mostrar cada mês com o acumulado até ele, ou cada livro com a posição no ranking da categoria.

**Quando você escolheria MongoDB em vez de PostgreSQL?** Quando os dados têm forma variável e são lidos como um documento inteiro, como um catálogo com atributos que mudam por categoria. Para dados muito relacionados, com transações entre várias entidades e relatórios cruzados, o relacional costuma ser a escolha mais simples.

- Não sei por que o banco está lento ou como criar o índice sem parar a API: [Administração e otimização](/learn/carreira-nodejs/postgresql-administracao-otimizacao-banco).
- Minhas consultas com filtro, agrupamento ou `NULL` dão resultado estranho: [Conhecendo instruções SQL](/learn/carreira-nodejs/sqlite-online-conhecendo-instrucoes-sql) e [Executando consultas SQL](/learn/carreira-nodejs/sqlite-online-executando-consultas-sql).
- Clientes somem do relatório ou o pedido fica pela metade: [Joins, views e transações](/learn/carreira-nodejs/realizando-consultas-sql-joins-views-transacoes).
- Não consegui calcular acumulado, variação ou ranking: [Análise de dados com SQL](/learn/carreira-nodejs/sqlite-online-analise-dados-sql).
- Não sei se embuto ou referencio, ou a consulta no MongoDB não usa índice: [Conhecendo o MongoDB](/learn/carreira-nodejs/mongodb-conhecendo-banco-dados-nosql) e [Modelagem de dados](/learn/carreira-nodejs/mongodb-modelagem-dados).
