Toda API em produção acumula tarefas repetitivas: subir o ambiente, rodar migrações, fazer backup do banco, limpar imagens antigas, esperar o container ficar saudável antes de rodar os testes. Feitas à mão, essas tarefas dependem da memória de alguém e falham do jeito mais caro, numa sexta à noite. Um script Bash curto que conversa com o Docker transforma esse conhecimento em algo versionado, revisável e que qualquer pessoa do time (ou o pipeline de CI) consegue executar igual.

**Você vai aprender:**

- Escrever scripts Bash seguros, com `set -euo pipefail`, aspas corretas e códigos de saída
- Receber argumentos, validar entradas e organizar o script em funções
- Controlar containers pelo script com `docker compose`, `docker exec` e `docker inspect`
- Montar um script de backup e restauração do PostgreSQL que roda dentro do container
- Esperar um serviço ficar saudável e limpar recursos com segurança

## O cenário: a API de livros em containers

Ao longo do capítulo, o fio condutor é uma API de livros em Node.js que roda com Docker Compose ao lado de um PostgreSQL. O `compose.yaml` é o mínimo necessário:

```yaml
services:
  api:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://livros:livros@db:5432/livros
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: livros
      POSTGRES_PASSWORD: livros
      POSTGRES_DB: livros
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U livros"]
      interval: 5s
      timeout: 3s
      retries: 10
    volumes:
      - dados:/var/lib/postgresql/data
volumes:
  dados:
```

Tudo o que vem a seguir são scripts numa pasta `scripts/` do repositório. Eles automatizam o que você faria digitando comandos no terminal.

## O esqueleto de um script seguro

Um script Bash é um arquivo de texto com comandos, executado de cima para baixo. A primeira linha (o shebang) diz qual interpretador usar. A segunda é a mais importante do capítulo:

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "Iniciando em $(date '+%Y-%m-%d %H:%M:%S')"
docker compose ps
```

Cada letra de `set -euo pipefail` evita uma classe de bug:

| Opção | O que faz | Sem ela |
|---|---|---|
| `-e` | Encerra o script quando um comando falha | O script segue em frente depois de um erro |
| `-u` | Trata variável não definida como erro | `rm -rf "$PASTA/"` com `PASTA` vazia apaga a raiz |
| `-o pipefail` | Um pipe falha se qualquer etapa falhar | `pg_dump ... gzip` "funciona" mesmo com o dump quebrado |

Para executar, dê permissão e chame pelo caminho:

```bash
chmod +x scripts/status.sh
./scripts/status.sh
```

Todo comando devolve um código de saída: `0` é sucesso, qualquer outro número é falha. É esse código que o `if`, o `&&` e o `set -e` leem. Você vê o último em `$?`, e o seu script termina com `exit 0` ou `exit 1` para avisar quem o chamou (o CI, por exemplo) se deu certo.

## Variáveis, aspas e argumentos

Variável em Bash não tem tipo e não aceita espaço em volta do `=`. Na leitura, sempre coloque entre aspas duplas: sem aspas, o Bash quebra o valor em palavras e expande curingas, o que vira bug assim que um nome de arquivo tiver espaço.

```bash
#!/usr/bin/env bash
set -euo pipefail

AMBIENTE="${1:-dev}"            # primeiro argumento, padrão dev
SERVICO="${2:-api}"
PROJETO="livros-${AMBIENTE}"
DATA="$(date +%Y%m%d-%H%M%S)"   # substituição de comando

echo "Projeto: $PROJETO | serviço: $SERVICO | $# argumento(s)"

if [[ "$AMBIENTE" != "dev" && "$AMBIENTE" != "prod" ]]; then
  echo "uso: $0 [dev|prod] [servico]" >&2
  exit 2
fi
```

Os pontos que mais aparecem:

- `$1`, `$2`... são os argumentos; `$#` é a quantidade; `"$@"` repassa todos preservando espaços.
- `${VAR:-padrao}` usa um valor padrão quando a variável está vazia. `${VAR:?mensagem}` aborta com a mensagem.
- `$(comando)` captura a saída de um comando numa variável.
- `>&2` manda a mensagem para a saída de erro, que é onde mensagens de erro devem ir.
- `[[ ... ]]` é o teste do Bash: compara strings com `==` e `!=`, números com `-eq`, `-gt`, `-lt`, e testa arquivos com `-f` (existe e é arquivo) e `-d` (é diretório).

## Funções e laços

Quando o script cresce, quebre-o em funções. Uma função é um mini comando: recebe argumentos em `$1`, `$2` e devolve um código de saída. Variáveis internas devem ser `local` para não vazar para o resto do script.

```bash
log() {
  local nivel="$1"; shift
  printf '[%s] %s %s\n' "$(date +%H:%M:%S)" "$nivel" "$*"
}

servicos_rodando() {
  docker compose ps --services --status running
}

for s in $(servicos_rodando); do
  log INFO "serviço ativo: $s"
done

contador=0
while [[ $contador -lt 3 ]]; do
  log INFO "tentativa $contador"
  contador=$((contador + 1))
done
```

`$((...))` faz aritmética inteira. O `for` acima é um dos poucos lugares onde a expansão sem aspas é intencional: queremos uma palavra por serviço. Em nomes que podem ter espaço, leia linha a linha com `while IFS= read -r linha; do ...; done`.

## Conversando com o Docker

O Docker CLI foi feito para ser usado em scripts. Os comandos que você mais vai combinar:

```bash
# roda um comando dentro de um container que já está de pé
docker compose exec -T db psql -U livros -c 'select count(*) from livros;'

# roda um container descartável só para uma tarefa
docker run --rm -v "$PWD":/app -w /app node:22-alpine npm ci

# lê um campo específico do estado do container
docker inspect --format '{{.State.Health.Status}}' "$(docker compose ps -q db)"
```

O `-T` em `docker compose exec` desliga a alocação de terminal. Sem ele, o comando falha ou mistura caracteres de controle quando roda no CI ou quando você redireciona a saída para um arquivo. O `--rm` no `docker run` apaga o container ao terminar, e o `--format` do `inspect` usa templates Go para extrair um único valor, o que evita ter de "parsear" um JSON enorme com `grep`.

### Esperando o serviço ficar saudável

O problema clássico: o pipeline sobe o banco e roda as migrações em seguida, mas o Postgres ainda está inicializando. A solução é um laço com limite de tentativas que lê o healthcheck:

```bash
esperar_saudavel() {
  local servico="$1" limite="${2:-30}" id status
  id="$(docker compose ps -q "$servico")"
  for ((i = 1; i <= limite; i++)); do
    status="$(docker inspect --format '{{.State.Health.Status}}' "$id")"
    if [[ "$status" == "healthy" ]]; then
      log INFO "$servico saudável após ${i}s"
      return 0
    fi
    sleep 1
  done
  log ERRO "$servico não ficou saudável em ${limite}s"
  return 1
}

docker compose up -d db
esperar_saudavel db 60
docker compose run --rm api npx sequelize-cli db:migrate
```

Nas versões atuais, `docker compose up -d --wait` faz parte disso sozinho (espera os healthchecks). Mesmo assim, vale saber escrever o laço: ele serve para qualquer condição, como esperar uma URL responder com `curl -fsS`.

## Backup e restauração do PostgreSQL

Este é o script que mais vale ter pronto. O `pg_dump` roda dentro do container do banco (onde a versão do cliente bate com a do servidor), e a saída sai pelo pipe direto para um arquivo compactado na máquina.

```bash
#!/usr/bin/env bash
# scripts/backup.sh
set -euo pipefail

DESTINO="${BACKUP_DIR:-./backups}"
RETENCAO_DIAS="${RETENCAO_DIAS:-7}"
ARQUIVO="$DESTINO/livros-$(date +%Y%m%d-%H%M%S).sql.gz"

mkdir -p "$DESTINO"

docker compose exec -T db pg_dump -U livros --clean --if-exists livros \
  | gzip > "$ARQUIVO"

# um backup vazio é um backup quebrado
if [[ ! -s "$ARQUIVO" ]]; then
  echo "backup vazio, abortando" >&2
  rm -f "$ARQUIVO"
  exit 1
fi

echo "backup criado: $ARQUIVO ($(du -h "$ARQUIVO" | cut -f1))"

# apaga backups mais antigos que a retenção
find "$DESTINO" -name 'livros-*.sql.gz' -mtime +"$RETENCAO_DIAS" -print -delete
```

E a restauração, com uma confirmação para evitar acidentes:

```bash
#!/usr/bin/env bash
# scripts/restore.sh
set -euo pipefail

ARQUIVO="${1:?uso: restore.sh caminho/do/backup.sql.gz}"
[[ -f "$ARQUIVO" ]] || { echo "arquivo não existe: $ARQUIVO" >&2; exit 1; }

read -r -p "Isso sobrescreve o banco livros. Digite 'sim' para continuar: " ok
[[ "$ok" == "sim" ]] || { echo "cancelado"; exit 0; }

gunzip -c "$ARQUIVO" | docker compose exec -T db psql -U livros -d livros -v ON_ERROR_STOP=1
echo "restaurado a partir de $ARQUIVO"
```

O `-v ON_ERROR_STOP=1` faz o `psql` parar no primeiro erro e devolver código diferente de zero. Sem isso, ele segue executando o resto do arquivo e termina com sucesso mesmo que metade das tabelas não tenha sido criada.

<Callout type="warning" title="Backup que nunca foi restaurado não é backup">
O erro mais comum é agendar o `backup.sh` e nunca testar a volta. Sem `pipefail`, um `pg_dump` que falha por senha errada ainda gera um `.gz` válido de poucos bytes, e o script termina com sucesso. Use `set -euo pipefail`, confira o tamanho do arquivo e, de tempos em tempos, restaure o backup num container descartável para provar que ele funciona.
</Callout>

## Limpeza e o trap

Imagens antigas e containers parados enchem o disco do servidor aos poucos. O `docker system prune` limpa, mas use filtros para não apagar o que ainda importa:

```bash
# remove imagens sem uso criadas há mais de uma semana
docker image prune -a -f --filter "until=168h"

# nunca use -v (volumes) num script automático: volumes guardam o banco
docker container prune -f
```

Já o `trap` executa um comando quando o script termina, mesmo por erro. É o lugar certo para desfazer o que o script criou:

```bash
#!/usr/bin/env bash
# scripts/test-integracao.sh
set -euo pipefail

PROJETO="livros-teste-$$"   # $$ é o PID: nome único por execução

limpar() {
  docker compose -p "$PROJETO" down -v --remove-orphans
}
trap limpar EXIT

docker compose -p "$PROJETO" up -d --wait db
docker compose -p "$PROJETO" run --rm api npm test
```

Aqui o `down -v` é seguro porque o projeto é descartável: o `-p` isola os containers e volumes desta execução, então os testes nunca encostam no banco de desenvolvimento.

## Juntando tudo num único ponto de entrada

Em vez de dez scripts soltos, muitos times usam um único `./scripts/dev.sh` com subcomandos. O `case` deixa isso legível:

```bash
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."   # roda sempre a partir da raiz do repositório

case "${1:-}" in
  up)      docker compose up -d --wait ;;
  down)    docker compose down ;;
  logs)    docker compose logs -f --tail=100 "${2:-api}" ;;
  backup)  ./scripts/backup.sh ;;
  migrate) docker compose exec -T api npx sequelize-cli db:migrate ;;
  *)
    echo "uso: $0 {up|down|logs [servico]|backup|migrate}" >&2
    exit 2
    ;;
esac
```

O `cd "$(dirname "$0")/.."` resolve um bug sutil: sem ele, o script só funciona quando chamado da pasta certa. Antes de commitar, passe o arquivo no ShellCheck (`shellcheck scripts/*.sh`), que aponta aspas faltando e outras armadilhas automaticamente.

## Na entrevista

**Por que usar `set -euo pipefail`?** Para o script falhar cedo e alto: parar no primeiro erro (`-e`), recusar variáveis não definidas (`-u`) e não esconder falhas no meio de um pipe (`pipefail`).

**Qual a diferença entre `docker exec` e `docker run`?** `exec` roda um processo num container que já está em execução; `run` cria um container novo a partir de uma imagem. Para tarefas pontuais, `run --rm` evita deixar lixo.

**Como garantir que o banco está pronto antes de rodar migrações?** Definir um healthcheck no serviço e esperar o status `healthy`, seja com `depends_on` e `condition: service_healthy`, com `docker compose up --wait` ou com um laço que lê `docker inspect` com limite de tempo.

**Por que aspas em volta de variáveis?** Sem aspas, o Bash separa o valor por espaços e expande curingas, então um caminho com espaço vira dois argumentos e um `*` vira uma lista de arquivos.

## Pratique

Crie a pasta `scripts/` num projeto Node.js seu que use Docker Compose e entregue:

1. `dev.sh` com os subcomandos `up`, `down`, `logs`, `backup` e `restore`.
2. `backup.sh` que gera o dump compactado, valida que não está vazio e mantém só os últimos 7 dias.
3. `test-integracao.sh` que sobe um banco isolado com `-p`, roda os testes e derruba tudo no `trap`, mesmo quando os testes falham.
4. Todos os arquivos passando no `shellcheck` sem avisos, e um trecho no README explicando cada comando.

Para provar que funciona, faça um backup, apague um registro, restaure e mostre que ele voltou.
