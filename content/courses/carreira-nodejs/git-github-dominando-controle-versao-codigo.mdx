Saber `add`, `commit` e `push` resolve o dia em que tudo dá certo. O problema são os outros dias: um commit quebrou a produção e você precisa achar qual foi, um merge virou um mar de conflitos, alguém fez `reset` errado e "perdeu" uma semana de trabalho. Dominar Git é entender o modelo por trás dos comandos, porque aí qualquer situação vira uma questão de mover ponteiros, e não de pânico.

**Você vai aprender:**

- O modelo mental do Git: commits como fotos, branches como ponteiros e o `HEAD`
- Como escrever um histórico limpo, com commits pequenos e mensagens úteis
- Quando usar merge e quando usar rebase, e como resolver conflitos sem medo
- Como desfazer qualquer coisa com `restore`, `reset`, `revert` e `reflog`
- Ferramentas de investigação: `log`, `blame`, `bisect` e `cherry-pick`

## O modelo mental: fotos, ponteiros e HEAD

Um commit não guarda "o que mudou". Ele guarda uma foto completa do projeto naquele momento (o Git economiza espaço reaproveitando arquivos iguais), mais o autor, a mensagem e o identificador do commit pai. Cada commit tem um hash SHA que depende de todo esse conteúdo, inclusive do pai. Por isso, alterar um commit antigo gera um commit novo com outro hash, e todos os que vêm depois também mudam.

Uma branch é só um arquivo de texto com o hash de um commit. Criar uma branch custa nada. `HEAD` aponta para a branch em que você está (ou direto para um commit, no estado "detached HEAD"). Quando você faz um commit, o Git cria a foto nova com o pai atual e avança o ponteiro da branch.

```bash
git init api-livros && cd api-livros
echo "node_modules/" > .gitignore
git add .gitignore && git commit -m "chore: ignora node_modules"

cat .git/HEAD              # ref: refs/heads/main
cat .git/refs/heads/main   # o hash do commit que você acabou de criar
git log --oneline --graph --all
```

Olhar dentro de `.git` uma vez tira o mistério. Daqui em diante, "branch", "tag" e "HEAD" são nomes para hashes.

## As três áreas e commits atômicos

O Git trabalha com três lugares: o diretório de trabalho (seus arquivos), a staging area ou índice (o que vai entrar no próximo commit) e o repositório (os commits). A staging area existe para você montar commits com intenção, e não "tudo o que mudou hoje".

```bash
# você mexeu na rota de livros e, de passagem, corrigiu um typo no README
git status
git add -p src/routes/livros.js   # escolhe pedaço por pedaço (hunks)
git commit -m "feat(livros): adiciona filtro por autor"
git add README.md
git commit -m "docs: corrige nome do script de testes"

git diff            # trabalho vs. staging
git diff --staged   # staging vs. último commit
```

`git add -p` é a ferramenta mais subestimada do Git. Ela mostra cada bloco alterado e pergunta se entra no commit. Com ela você separa uma correção de bug de uma refatoração que aconteceu no mesmo arquivo.

Um bom commit é **atômico**: faz uma coisa, compila e passa nos testes sozinho. A mensagem segue um formato previsível. O padrão Conventional Commits é o mais usado em projetos Node.js:

| Prefixo | Uso |
|---|---|
| `feat` | funcionalidade nova |
| `fix` | correção de bug |
| `refactor` | muda a estrutura sem mudar o comportamento |
| `test` | adiciona ou corrige testes |
| `docs`, `chore`, `ci` | documentação, manutenção, pipeline |

A primeira linha diz o quê, em até uns 70 caracteres. O corpo, opcional, diz o porquê. Daqui a seis meses, o porquê é o que ninguém mais lembra.

## Branches, merge e rebase

Você trabalha numa branch de funcionalidade e, enquanto isso, a `main` andou. Há duas formas de juntar os trabalhos.

**Merge** cria um commit com dois pais. O histórico fica fiel ao que aconteceu, com as bifurcações visíveis. Se a `main` não andou, o Git só avança o ponteiro (fast-forward) e nenhum commit de merge aparece.

**Rebase** pega os seus commits e os reaplica, um a um, em cima da ponta da `main`. O resultado é uma linha reta, como se você tivesse começado agora. Como os commits são recriados, eles ganham hashes novos.

```bash
git switch -c feat/paginacao
# ... dois commits ...
git switch main && git pull
git switch feat/paginacao

# opção 1: merge da main na sua branch
git merge main

# opção 2: reescrever sua branch em cima da main
git rebase main
```

Antes de abrir um pull request, vale arrumar os próprios commits: juntar "wip", "ajuste" e "agora vai" num commit com sentido. O rebase interativo faz isso: `git rebase -i main` abre um editor com a lista dos seus commits, e você troca `pick` por `squash` (junta no anterior), `reword` (muda a mensagem) ou `drop` (descarta). Uma alternativa que não exige editor é marcar correções no momento em que você as faz:

```bash
git commit --fixup=a1b2c3d          # "este commit corrige o a1b2c3d"
git rebase --autosquash main        # junta os fixups automaticamente
```

<Callout type="warning" title="Não reescreva história compartilhada">
Rebase, `commit --amend` e `reset` em commits que já foram para uma branch que outras pessoas usam obrigam todo mundo a consertar o próprio clone. A regra prática: reescreva à vontade a sua branch antes do merge; nunca reescreva a `main`. Se precisar forçar o push da sua branch, use `git push --force-with-lease`, que recusa o push se alguém tiver enviado algo que você ainda não viu.
</Callout>

## Resolvendo conflitos

Um conflito acontece quando os dois lados mudaram as mesmas linhas. O Git para, marca o arquivo e espera você decidir.

```text
<<<<<<< HEAD
const LIMITE_PADRAO = 20;
=======
const LIMITE_PADRAO = Number(process.env.PAGE_SIZE ?? 10);
>>>>>>> feat/paginacao
```

O processo é sempre o mesmo: `git status` lista os arquivos em conflito; você edita cada um até ficar com o código certo (que pode ser uma terceira versão, combinando as duas); roda os testes; faz `git add` no arquivo e continua com `git merge --continue` ou `git rebase --continue`. Se tudo deu errado, `git merge --abort` ou `git rebase --abort` volta ao estado anterior.

Duas configurações ajudam muito:

```bash
git config --global merge.conflictstyle zdiff3  # mostra também a versão original
git config --global rerere.enabled true         # lembra como você resolveu um conflito
```

Com `zdiff3`, o marcador mostra o trecho como era antes das duas mudanças, e fica claro o que cada lado quis fazer. Com `rerere`, um conflito que reaparece num rebase longo é resolvido sozinho.

Conflito frequente é sintoma de branch que vive demais. Branches curtas, integradas em um ou dois dias, praticamente não conflitam.

## Desfazendo coisas

Cada comando de desfazer age num lugar diferente. Trocar um pelo outro é a origem da maioria dos sustos.

| Situação | Comando |
|---|---|
| Descartar mudanças de um arquivo não commitado | `git restore arquivo` |
| Tirar um arquivo da staging, mantendo a mudança | `git restore --staged arquivo` |
| Corrigir a mensagem ou incluir algo no último commit | `git commit --amend` |
| Voltar a branch N commits, mantendo as mudanças nos arquivos | `git reset --soft HEAD~N` ou `--mixed` |
| Voltar a branch e apagar as mudanças | `git reset --hard HEAD~N` |
| Desfazer um commit que já está na `main` | `git revert hash` |

`reset` move o ponteiro da branch para trás. `revert` cria um commit novo que aplica o inverso de um commit antigo. Na `main`, use sempre `revert`: o histórico continua só crescendo e ninguém precisa reescrever nada.

### O reflog salva você

O Git quase nunca apaga commits de imediato. Ele só deixa de apontar para eles. O `reflog` registra cada posição pela qual o `HEAD` passou, inclusive as que nenhuma branch alcança mais.

```bash
git reset --hard HEAD~3        # ops, eram commits bons
git reflog                     # procura a linha anterior ao reset
# a1b2c3d HEAD@{1}: commit: feat(livros): valida ISBN
git reset --hard a1b2c3d       # tudo de volta
```

Commits sem referência ficam no reflog por cerca de 90 dias (30 para os inalcançáveis) antes de o coletor de lixo removê-los. A única coisa que o Git não recupera é o que nunca foi commitado nem adicionado.

### stash para trocar de contexto

Você está no meio de uma mudança e precisa corrigir um bug urgente em outra branch:

```bash
git stash push -m "paginacao pela metade"
git switch main && git switch -c fix/total-negativo
# ... corrige, commita, abre PR ...
git switch feat/paginacao
git stash pop
```

Para trabalhos mais longos em paralelo, `git worktree add ../api-hotfix main` cria uma segunda pasta ligada ao mesmo repositório, com outra branch, sem stash nenhum.

## Investigando o histórico

O histórico é uma base de dados. Saber consultá-lo é o que diferencia quem domina Git.

```bash
git log --oneline --graph --decorate --all     # visão geral das branches
git log -p -- src/services/livros.js           # todas as mudanças de um arquivo
git log -S "calcularFrete" --oneline           # commits que adicionaram ou removeram esse texto
git log --author="ana" --since="2 weeks ago"
git blame -L 40,60 src/services/livros.js      # quem mudou cada linha por último
git show a1b2c3d                               # um commit completo
```

### bisect: a busca binária que acha o commit culpado

Os testes passavam na tag `v1.4.0` e hoje falham, com 200 commits no meio. O `bisect` faz uma busca binária: em cerca de 8 passos ele acha o commit que introduziu o problema. Se você tiver um comando que diz "bom" ou "ruim" pelo código de saída, ele roda sozinho:

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.4.0
git bisect run npm test -- tests/livros.test.js
# ... "a1b2c3d is the first bad commit"
git bisect reset
```

### cherry-pick e tags

`git cherry-pick hash` aplica um commit específico na branch atual. É o jeito de levar uma correção da `main` para uma branch de release sem trazer o resto. Tags marcam versões; use tags anotadas, que guardam autor e mensagem:

```bash
git tag -a v1.5.0 -m "Paginação e filtro por autor"
git push origin v1.5.0
```

## Git e GitHub juntos

O Git é local e distribuído: cada clone tem o histórico inteiro. O GitHub hospeda um remoto e acrescenta a camada de colaboração (pull requests, revisões, issues, Actions). O fluxo que a maioria das equipes Node.js usa é simples: `main` sempre implantável, uma branch curta por tarefa, PR com revisão e testes no CI, merge e deploy. Os detalhes de proteção de branch, revisão obrigatória e automação estão nos capítulos seguintes.

Duas configurações locais evitam surpresas ao trabalhar com o remoto:

```bash
git config --global pull.rebase true        # pull reaplica seus commits em vez de criar merge
git config --global push.autoSetupRemote true
git fetch --prune                           # remove referências a branches apagadas no remoto
```

## Na entrevista

**Qual a diferença entre merge e rebase?** Merge preserva o histórico como aconteceu e cria um commit com dois pais. Rebase reaplica seus commits sobre outra base, gerando histórico linear e hashes novos. Rebase em branch local; nunca em branch compartilhada.

**Qual a diferença entre `reset` e `revert`?** `reset` move a branch para outro commit e pode descartar trabalho; reescreve história. `revert` cria um commit que desfaz outro; é seguro em branch pública.

**Apaguei commits com `reset --hard`. Perdi?** Não. `git reflog` mostra o hash anterior e `git reset --hard hash` recupera.

**Como você acharia o commit que introduziu um bug?** Com `git bisect`, marcando um commit bom e um ruim e, se possível, automatizando com `git bisect run` e um teste.

## Pratique

Crie um repositório `api-livros` com um `package.json` e uma função `somarPrecos` testada com `node --test`. Depois:

1. Faça 6 commits seguindo Conventional Commits, usando `git add -p` em pelo menos um deles para separar duas mudanças do mesmo arquivo.
2. Crie duas branches que alteram a mesma linha, gere um conflito no merge e resolva com `zdiff3` ativado.
3. Introduza um bug de propósito no meio de 10 commits e encontre-o com `git bisect run`.
4. Faça um `reset --hard` de 3 commits e recupere-os com o `reflog`.

Entregue o repositório no GitHub com um `NOTAS.md` mostrando a saída de `git log --oneline --graph` e os comandos usados em cada passo.
