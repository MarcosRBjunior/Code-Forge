O Nível 3 tirou a API de livros de uma máquina só e a colocou para rodar em escala. Primeiro com as peças da AWS montadas uma a uma (EC2 atrás de balanceador, VPC, RDS, DynamoDB, ECS e EKS), depois com outras formas de expor e transportar dados (GraphQL e gRPC), em seguida com toda a infraestrutura descrita em Terraform e Ansible e, por fim, com pipelines no GitHub Actions que testam, constroem a imagem e fazem o deploy sozinhos na EC2, no ECS e no Kubernetes.

Este checkpoint fecha a carreira. Ele confere se você consegue colocar uma API em produção do jeito que um time faria: rede privada, banco gerenciado, containers orquestrados, infraestrutura versionada, deploy sem chaves guardadas e sem derrubar ninguém, e a conta da AWS sob controle. O desafio no fim é o projeto que mais pesa num portfólio de back-end.

**Neste checkpoint:**

- Uma tabela com os 20 capítulos do nível e o que cada um exige de você
- Uma autoavaliação com habilidades que dá para provar na AWS e no GitHub
- Um desafio prático: a API de livros em produção, da rede ao pipeline
- Uma revisão rápida das confusões mais comuns em cloud, IaC e CI/CD
- Perguntas de entrevista e quizzes cobrindo o nível inteiro

## Desafio prático

A API de livros dos níveis anteriores vai para produção de verdade. A meta é que um commit na `main` chegue sozinho a staging, espere uma aprovação e chegue à produção, com o banco protegido, a infraestrutura inteira em código e o custo visível. Você vai entregar a **API de livros em produção na AWS**, com ECS Fargate como plataforma principal.

### Requisitos

1. **Rede em código.** Uma VPC criada com Terraform, com subnets públicas e privadas em duas zonas de disponibilidade, saída para a internet pelas subnets privadas e security groups encadeados: o ALB aceita 80 e 443 da internet, as tarefas aceitam só do ALB, o banco aceita só das tarefas.
2. **Ambientes isolados.** Módulos Terraform reutilizáveis e as pastas `envs/staging` e `envs/prod`, cada uma com backend S3 em chave própria e `use_lockfile = true`. Staging é menor e mais barato; produção usa os mesmos módulos com outros parâmetros.
3. **Banco gerenciado.** RDS PostgreSQL em subnet privada, sem acesso público, com senha gerenciada pelo próprio RDS, backups automáticos e Multi-AZ em produção. A API conecta com TLS e um pool dimensionado pelo número máximo de tarefas.
4. **Serviço no ECS.** Imagem multi-stage com usuário `node` publicada no ECR com scan ativado, serviço Fargate com 2 tarefas atrás do ALB, `DATABASE_URL` injetada de um segredo, logs no CloudWatch, circuit breaker com rollback e escala de 2 a 6 tarefas por CPU. Execution role e task role separadas, cada uma com o mínimo necessário.
5. **API pronta para escala.** Nenhum estado em memória ou disco que precise sobreviver entre requisições, um `/health` leve para o balanceador e um `/health/deep` que testa o banco para o monitoramento, e tratamento de `SIGTERM` que termina as requisições abertas dentro do `deregistration_delay` do target group.
6. **Integração contínua.** Um `ci.yml` que roda lint, testes unitários em Node 22 e 24 e testes de integração contra um Postgres como service container. A `main` só aceita merge por pull request com esses checks verdes.
7. **Imagem rastreável.** Um workflow que constrói com Buildx e cache, testa a imagem construída (sobe o container e chama o `/health`), marca com o SHA do commit e com a versão semântica nas tags e publica só a partir da `main` e de tags, nunca de pull request.
8. **Entrega contínua.** Autenticação na AWS por OIDC, migrações rodando numa task avulsa antes do deploy, deploy automático em staging e em produção só depois de aprovação no environment `production`, esperando o serviço estabilizar.
9. **Custo sob controle.** Todos os recursos com tags de projeto e ambiente ativadas como tags de alocação de custo, um orçamento mensal com alerta de previsão e uma estimativa na calculadora de preços anexada ao README.

O service no Terraform, com o deploy seguro ligado e a revisão da task definition deixada para o pipeline:

```hcl
# modules/api-ecs/service.tf
resource "aws_ecs_service" "api" {
  name            = "api-livros-${var.ambiente}"
  cluster         = aws_ecs_cluster.this.id
  task_definition = aws_ecs_task_definition.api.arn
  desired_count   = var.tarefas_minimas
  launch_type     = "FARGATE"

  deployment_circuit_breaker {
    enable   = true
    rollback = true
  }
  deployment_minimum_healthy_percent = 100
  deployment_maximum_percent         = 200

  # rede e load_balancer como no capítulo de Terraform e ECS

  lifecycle {
    ignore_changes = [task_definition, desired_count]
  }
}
```

Um ponto de partida para o job de deploy, com as permissões que o OIDC exige:

```yaml
# .github/workflows/deploy.yml
jobs:
  deploy-producao:
    needs: deploy-staging
    runs-on: ubuntu-latest
    environment: production        # exige aprovação configurada no repositório
    permissions:
      id-token: write              # permite pedir o token OIDC
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ vars.AWS_ROLE_DEPLOY }}
          aws-region: ${{ vars.AWS_REGION }}
      # render da task definition com a imagem do SHA, migração avulsa, deploy e espera
```

### Critérios de aceite

- `terraform plan` em `envs/prod` logo depois do `apply` mostra que não há mudanças, e um segundo `apply` simultâneo no mesmo ambiente é barrado pela trava do estado.
- `curl -i` no DNS do ALB em `/health` devolve 200, e uma tentativa de `psql` do seu computador para o endpoint do RDS não conecta.
- Parar uma tarefa à mão com `aws ecs stop-task` faz o ECS subir outra, e um teste de carga rodando durante a troca não registra respostas 5xx.
- Sob carga, o serviço passa de 2 tarefas e volta a 2 depois que a carga termina.
- Um pull request com um teste quebrado de propósito fica com o merge bloqueado.
- Uma versão com o `/health` devolvendo 500 é publicada, o circuit breaker volta para a revisão anterior, e a versão antiga atende o tempo todo.
- Os secrets do repositório não contêm `AWS_ACCESS_KEY_ID` nem `AWS_SECRET_ACCESS_KEY`.
- O Cost Explorer filtrado pela tag do projeto mostra o custo separado por ambiente.

### Dicas

- Suba primeiro staging, com uma tarefa e banco sem Multi-AZ, e só depois produção. Assim os erros de rede e de permissão custam pouco. A ordem dos recursos e o módulo de rede estão em [Terraform, Docker e ECS](/learn/carreira-nodejs/infraestrutura-como-codigo-terraform-docker-elastic-container).
- Se a tarefa não sobe com `AccessDenied` ao ler o segredo, a permissão falta na execution role, não na task role. Releia a seção sobre as duas roles antes de abrir permissões demais.
- Decida cedo quem é dono de quê: o Terraform cria o service e ignora mudanças na task definition; o pipeline registra revisões novas. Sem isso, o próximo `apply` volta a imagem antiga. Veja [Automatize o deploy no Amazon ECS](/learn/carreira-nodejs/integracao-continua-automatize-deploy-amazon-ecs).
- A migração roda com versão antiga e nova ao mesmo tempo no ar: só migrações compatíveis (adicionar antes, remover depois).
- O NAT Gateway e o RDS Multi-AZ costumam dominar a conta de um projeto pequeno. Destrua staging quando não estiver usando e considere VPC endpoints, como em [Custos dos serviços](/learn/carreira-nodejs/aws-entendendo-controlando-custos-servicos).
- Bônus: leve a mesma imagem para o EKS com uma base Kustomize e overlays `staging` e `production`, seguindo [Automatizando a entrega no Kubernetes](/learn/carreira-nodejs/integracao-continua-automatizando-entrega-kubernetes), ou exponha o catálogo também por GraphQL com DataLoader.

## Revisão rápida

**Escala horizontal exige aplicação sem estado.** Sessão em memória, upload em disco local ou job agendado dentro do processo funcionam com uma instância e falham de forma intermitente com duas. Sticky sessions escondem o problema até a primeira instância sair do grupo. E o health check do balanceador não deve depender do banco: se o banco cair, todas as instâncias ficam doentes juntas e o Auto Scaling passa a substituí-las em loop sem resolver nada.

**O encerramento precisa caber nos prazos da plataforma.** O balanceador para de mandar requisições novas e espera o `deregistration_delay`; depois vem o `SIGTERM`. A API para de aceitar conexões, termina as abertas, fecha o pool e sai antes do prazo final.

```javascript
// src/shutdown.js
process.on("SIGTERM", () => {
  iniciarEncerramento();             // o /health passa a responder 503
  server.close(async () => {
    await pool.end();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 25_000).unref();
});
```

**Execution role e task role não são a mesma coisa.** A execution role é do agente do ECS: baixa a imagem, escreve logs e lê os segredos injetados. A task role é da sua aplicação: chamadas ao S3, SQS ou DynamoDB pelo SDK.

**Multi-AZ não escala leitura.** A instância Multi-AZ tem uma cópia síncrona em outra zona que só assume no failover. Para tirar leituras do primário, use réplicas de leitura, que são assíncronas e podem estar um pouco atrás.

**Readiness e liveness respondem perguntas diferentes.** Readiness decide se o pod recebe tráfego; liveness decide se o container é reiniciado. Dependências externas, como o banco, nunca entram na liveness, senão uma queda do banco reinicia todos os pods em loop.

**Estado do Terraform é compartilhado e precisa de trava.** Estado local não serve para equipe. Um backend S3 por ambiente, com `use_lockfile`, impede que dois `apply` corrompam o estado e que um comando em staging alcance produção.

```hcl
# envs/prod/backend.tf
terraform {
  backend "s3" {
    bucket       = "livros-terraform-state"
    key          = "prod/terraform.tfstate"
    region       = "sa-east-1"
    use_lockfile = true
  }
}
```

**OIDC troca chaves fixas por credenciais temporárias.** O GitHub emite um token assinado para o job, e a AWS troca esse token por credenciais de curta duração de uma role cuja confiança está restrita ao seu repositório e, de preferência, ao environment. Sem `id-token: write`, o passo de autenticação falha.

**Entrega contínua e implantação contínua não são sinônimos.** Na entrega contínua toda mudança fica pronta para produção, mas alguém aprova o último passo. Na implantação contínua, o que passa no pipeline vai direto para produção.

<Callout type="warning" title="Destrua o que não está usando">
O desafio cria NAT Gateway, ALB, RDS e tarefas Fargate, e todos cobram por hora ligados. Configure o orçamento com alerta antes do primeiro `apply` e rode `terraform destroy` em staging ao terminar cada sessão de trabalho. Confira também as outras regiões no Cost Explorer: recurso esquecido do outro lado do mapa é o susto mais comum na fatura.
</Callout>

## Na entrevista

**Como você faz um deploy sem downtime no ECS?** Com rolling update: o ECS sobe tarefas novas até o `maximumPercent`, espera ficarem saudáveis no target group, drena e remove as antigas sem cair abaixo do `minimumHealthyPercent`. O circuit breaker volta para a revisão anterior se as novas não ficarem saudáveis.

**Como o banco fica protegido na AWS?** Numa subnet privada, sem acesso público, com security group que só aceita conexões vindas do security group da aplicação, TLS na conexão e senha guardada no Secrets Manager, nunca no código ou na imagem.

**ECS ou EKS?** ECS é mais simples e integrado à AWS, ótimo quando o time quer rodar containers sem operar um orquestrador. EKS traz o Kubernetes padrão de mercado, com portabilidade e um ecossistema enorme, ao custo de mais complexidade de operação.

**Por que separar o Terraform do cluster em duas camadas?** Porque o provider `kubernetes` precisa de um cluster que já existe para se configurar. Com estados separados, a camada do cluster é aplicada antes, e uma mudança num Deployment não arrisca o plano de controle.

**Quando GraphQL e quando gRPC?** GraphQL atende bem front-ends que precisam de dados de várias entidades numa requisição, escolhendo os campos. gRPC serve à comunicação entre serviços internos com contrato rígido, binário e streaming sobre HTTP/2.

**O que é o problema N+1 no GraphQL e como resolver?** Um resolver de campo dispara uma consulta por item da lista. O DataLoader junta as chaves pedidas no mesmo ciclo e faz uma consulta só, com cache por requisição.

**Como você evita que credenciais de deploy vazem?** Com OIDC em vez de chaves fixas, role com permissões mínimas e confiança restrita ao repositório e ao environment, aprovação obrigatória para produção e nenhum segredo em pull requests vindos de forks.

**Como você reduziria a conta da AWS de um projeto pequeno?** Olhando primeiro o que fica ligado o tempo todo: NAT Gateway, Multi-AZ fora de produção, instâncias superdimensionadas e retenção de logs. Depois, Savings Plans para a base estável e ambientes de teste destruídos fora do horário.

- Não consigo descrever ALB e Auto Scaling em código, ou quero uma plataforma que monte isso por mim: [Infraestrutura elástica](/learn/carreira-nodejs/infraestrutura-como-codigo-montando-infraestrutura-elastica-aws) e [Docker e Elastic Beanstalk](/learn/carreira-nodejs/infraestrutura-como-codigo-docker-elastic-beanstalk-aws).
- O Terraform e o pipeline brigam pela task definition ou pelo Deployment: [Terraform e ECS](/learn/carreira-nodejs/infraestrutura-como-codigo-terraform-docker-elastic-container) e [Terraform e Kubernetes](/learn/carreira-nodejs/infraestrutura-como-codigo-terraform-kubernetes).
- O pipeline não roda os testes de integração ou não bloqueia o merge: [Pipelines e testes com GitHub Actions](/learn/carreira-nodejs/integracao-continua-pipelines-testes-automatizados-github-actions).
- Não sei qual imagem está em produção: [Pipeline Docker](/learn/carreira-nodejs/integracao-continua-pipeline-docker-github-actions).
- O deploy depende de chaves guardadas ou de SSH: [Entrega contínua na EC2](/learn/carreira-nodejs/integracao-continua-pipeline-entrega-implementacao-continua-ec2).
- O deploy no ECS ou no Kubernetes não volta atrás quando falha: [Deploy no ECS](/learn/carreira-nodejs/integracao-continua-automatize-deploy-amazon-ecs) e [Entrega no Kubernetes](/learn/carreira-nodejs/integracao-continua-automatizando-entrega-kubernetes).
