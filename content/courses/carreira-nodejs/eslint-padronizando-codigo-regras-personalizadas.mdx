Num time, cada pessoa escreve de um jeito: uma esquece o `await`, outra deixa variável sem uso, outra lê `process.env` no meio de um controller. Revisão de código não deveria gastar tempo com isso. O ESLint analisa o código sem executá-lo e aponta (ou corrige) esses padrões antes do commit. Neste capítulo você configura o ESLint 9 com flat config num projeto Node.js, ajusta regras para o time e escreve uma regra própria, com testes, para uma convenção que nenhuma regra pronta cobre.

**Você vai aprender:**

- Como o ESLint funciona: parser, AST, regras e severidade
- Montar um `eslint.config.js` (flat config) para Node.js com ESM e TypeScript
- Separar responsabilidades entre ESLint e Prettier
- Escrever, testar e distribuir uma regra personalizada

## Como o ESLint pensa

O ESLint lê o arquivo, transforma em uma **AST** (árvore sintática abstrata) e passa essa árvore por cada regra ativa. Uma regra é um objeto que diz "quando encontrar um nó do tipo X, verifique Y". Se a verificação falha, a regra reporta um problema, opcionalmente com uma correção automática.

Cada regra tem uma **severidade**:

| Valor | Efeito |
|---|---|
| `"off"` ou `0` | Desligada |
| `"warn"` ou `1` | Aparece como aviso, não falha o comando |
| `"error"` ou `2` | Falha o comando com código de saída 1 |

Regras aceitam opções depois da severidade: `"eqeqeq": ["error", "always"]`.

## Instalando e configurando

```bash
npm install -D eslint @eslint/js globals
```

Desde o ESLint 9, a configuração padrão é o **flat config**: um único `eslint.config.js` que exporta um array de objetos. Cada objeto pode limitar a quais arquivos se aplica com `files`, e os objetos posteriores sobrescrevem os anteriores. Os antigos `.eslintrc.json` com `extends` em string não são mais lidos por padrão.

```javascript
// eslint.config.js
import js from "@eslint/js";
import globals from "globals";
import { defineConfig, globalIgnores } from "eslint/config";

export default defineConfig([
  globalIgnores(["dist/", "coverage/", "node_modules/"]),

  {
    files: ["**/*.js"],
    plugins: { js },
    extends: ["js/recommended"],
    languageOptions: {
      ecmaVersion: "latest",
      sourceType: "module",
      globals: { ...globals.node },
    },
    rules: {
      "no-unused-vars": ["error", { argsIgnorePattern: "^_" }],
      eqeqeq: ["error", "always"],
      "prefer-const": "error",
      "no-var": "error",
      "no-console": ["warn", { allow: ["warn", "error"] }],
      "require-await": "error",
    },
  },

  {
    files: ["test/**/*.js", "**/*.test.js"],
    rules: { "no-console": "off" },
  },

  {
    files: ["**/*.cjs"],
    languageOptions: { sourceType: "commonjs" },
  },
]);
```

O que cada parte faz:

- **`globalIgnores`** substitui o antigo `.eslintignore`.
- **`extends: ["js/recommended"]`** liga o conjunto de regras recomendadas, que pega bugs reais: variável não definida, código inalcançável, chave duplicada em objeto.
- **`globals.node`** declara `process`, `Buffer` e afins, para o ESLint não reclamar que não existem.
- **Blocos com `files`** ajustam regras por pasta. Testes podem usar `console`, migrações `.cjs` usam CommonJS.

Rode e veja o resultado:

```bash
npx eslint .
npx eslint . --fix   # aplica o que tem correção automática
```

Ponha nos scripts do `package.json`:

```json
{
  "scripts": {
    "lint": "eslint . --max-warnings 0",
    "lint:fix": "eslint . --fix"
  }
}
```

`--max-warnings 0` faz o comando falhar se houver avisos. Use no CI para que avisos não se acumulem até ninguém mais olhar.

### Inspecionando a configuração

Quando uma regra não se comporta como você espera, pergunte ao ESLint qual configuração final se aplica a um arquivo:

```bash
npx eslint --print-config src/app.js
npx eslint --inspect-config   # abre um visualizador no navegador
```

## Projetos com TypeScript

O parser padrão não entende tipos. O pacote `typescript-eslint` traz parser, plugin e conjuntos de regras.

```bash
npm install -D typescript-eslint
```

```javascript
// eslint.config.js
import js from "@eslint/js";
import tseslint from "typescript-eslint";
import globals from "globals";
import { defineConfig, globalIgnores } from "eslint/config";

export default defineConfig([
  globalIgnores(["dist/"]),
  js.configs.recommended,
  tseslint.configs.recommended,
  {
    languageOptions: { globals: globals.node },
    rules: {
      "@typescript-eslint/no-explicit-any": "warn",
      "@typescript-eslint/no-unused-vars": ["error", { argsIgnorePattern: "^_" }],
    },
  },
]);
```

Existe também `tseslint.configs.recommendedTypeChecked`, que usa o compilador para regras como `no-floating-promises` (Promise sem `await` nem `catch`). Ela pega bugs de verdade em back-end, mas exige configurar `parserOptions.projectService: true` e deixa o lint mais lento.

## ESLint e Prettier

ESLint verifica **qualidade**: lógica, padrões perigosos, convenções. Prettier cuida de **formatação**: aspas, ponto e vírgula, quebra de linha. Misturar os dois gera brigas, com uma ferramenta desfazendo o que a outra fez.

A divisão recomendada:

```bash
npm install -D prettier eslint-config-prettier
```

```javascript
import prettier from "eslint-config-prettier/flat";

export default defineConfig([
  // ... suas configs
  prettier, // por último: desliga regras de estilo que conflitam com o Prettier
]);
```

```json
{
  "scripts": {
    "format": "prettier --write .",
    "format:check": "prettier --check ."
  }
}
```

Rode Prettier para formatar e ESLint para o resto. Não use regras de estilo do ESLint para aquilo que o Prettier já decide.

## Regras sem escrever plugin

Antes de escrever uma regra, veja se `no-restricted-syntax`, `no-restricted-imports` ou `no-restricted-globals` resolvem. Eles aceitam seletores no estilo CSS sobre a AST.

```javascript
rules: {
  "no-restricted-imports": ["error", {
    paths: [{ name: "lodash", message: "Importe a função específica: lodash/get" }],
  }],
  "no-restricted-syntax": ["error",
    {
      selector: "CallExpression[callee.object.name='JSON'][callee.property.name='parse'] > Literal",
      message: "JSON.parse com literal: escreva o objeto direto.",
    },
    {
      selector: "ForInStatement",
      message: "Use for...of ou Object.entries em vez de for...in.",
    },
  ],
}
```

Para descobrir o seletor certo, cole o trecho no AST Explorer (astexplorer.net, parser `espree`) e veja os tipos de nó.

## Escrevendo uma regra personalizada

Convenção do time: **só o módulo `src/config` lê `process.env`**. O resto importa a configuração já validada. Isso evita `process.env.PORT` espalhado, com conversões e valores padrão diferentes em cada arquivo. Nenhuma regra pronta sabe disso, então vamos escrever uma.

Uma regra tem `meta` (documentação, mensagens, opções, se corrige) e `create`, que recebe o `context` e devolve um objeto de **visitantes**: chaves com o tipo do nó, valores com a função a chamar.

```javascript
// eslint-rules/no-process-env-fora-de-config.js
export default {
  meta: {
    type: "problem",
    docs: {
      description: "Proíbe process.env fora dos módulos de configuração",
    },
    messages: {
      proibido: "Leia variáveis de ambiente apenas em {{ pasta }}. Importe a configuração em vez de usar process.env.",
    },
    schema: [
      {
        type: "object",
        properties: { pastaPermitida: { type: "string" } },
        additionalProperties: false,
      },
    ],
  },

  create(context) {
    const { pastaPermitida = "src/config" } = context.options[0] ?? {};
    const arquivo = context.filename.replaceAll("\\", "/");
    if (arquivo.includes(`/${pastaPermitida}/`)) return {};

    return {
      MemberExpression(node) {
        const ehProcessEnv =
          node.object.type === "Identifier" &&
          node.object.name === "process" &&
          !node.computed &&
          node.property.type === "Identifier" &&
          node.property.name === "env";

        if (ehProcessEnv) {
          context.report({ node, messageId: "proibido", data: { pasta: pastaPermitida } });
        }
      },
    };
  },
};
```

Pontos importantes:

- **`messageId`** em vez de texto solto deixa as mensagens centralizadas e testáveis. `data` preenche os `{{ }}`.
- **`schema`** valida as opções. Sem ele, o ESLint 9 recusa opções passadas à regra.
- **`context.filename`** dá o caminho do arquivo. Retornar `{}` desliga a regra para aquele arquivo.
- **`node.computed`** distingue `process.env` de `process["env"]`. Aqui só tratamos a forma comum; decida conscientemente o que fica de fora.

### Registrando como plugin local

No flat config, um plugin é só um objeto com `rules`. Não precisa publicar no npm.

```javascript
// eslint.config.js
import noProcessEnv from "./eslint-rules/no-process-env-fora-de-config.js";

const time = { rules: { "no-process-env-fora-de-config": noProcessEnv } };

export default defineConfig([
  // ... configs anteriores
  {
    files: ["src/**/*.js"],
    plugins: { time },
    rules: {
      "time/no-process-env-fora-de-config": ["error", { pastaPermitida: "src/config" }],
    },
  },
]);
```

O nome da regra fica `<namespace>/<regra>`, onde o namespace é a chave usada em `plugins`.

### Testando a regra

O ESLint traz o `RuleTester`, que roda a regra sobre trechos de código e confere os erros. Ele funciona com qualquer test runner; com o do Node basta importar e rodar.

```javascript
// eslint-rules/no-process-env-fora-de-config.test.js
import { RuleTester } from "eslint";
import regra from "./no-process-env-fora-de-config.js";

const tester = new RuleTester({
  languageOptions: { ecmaVersion: "latest", sourceType: "module" },
});

tester.run("no-process-env-fora-de-config", regra, {
  valid: [
    { code: "const porta = process.env.PORT;", filename: "/app/src/config/env.js" },
    { code: "import { config } from './config/env.js'; config.porta;", filename: "/app/src/app.js" },
    { code: "process.exit(1);", filename: "/app/src/server.js" },
  ],
  invalid: [
    {
      code: "const porta = process.env.PORT;",
      filename: "/app/src/controllers/livros.js",
      errors: [{ messageId: "proibido" }],
    },
    {
      code: "const { DB } = process.env;",
      filename: "/app/src/database/index.js",
      options: [{ pastaPermitida: "src/settings" }],
      errors: [{ messageId: "proibido", data: { pasta: "src/settings" } }],
    },
  ],
});
```

```bash
node --test eslint-rules/
```

O `RuleTester` falha se um caso válido gerar erro, se um inválido não gerar, ou se a quantidade de erros não bater.

### Correção automática

Se a regra souber consertar, declare `meta.fixable: "code"` e passe `fix` no `report`. Exemplo de regra que troca `==` por `===` apenas quando um dos lados é literal de string:

```javascript
context.report({
  node,
  messageId: "usarIgualdadeEstrita",
  fix(fixer) {
    const operador = context.sourceCode.getFirstTokenBetween(node.left, node.right, (t) => t.value === "==");
    return fixer.replaceText(operador, "===");
  },
});
```

<Callout type="warning" title="Autofix que muda o comportamento">
`--fix` roda sem pedir confirmação, muitas vezes num hook de pré-commit. Uma correção que altera o que o código faz (trocar `==` por `===` quando um lado pode ser `null`, remover um `await` que segurava a ordem) vira bug silencioso. Só ofereça `fix` quando a transformação for sempre segura. Para os outros casos, use `meta.hasSuggestions` e `suggest`: o editor mostra a sugestão e a pessoa decide.
</Callout>

## Levando para o time

- **Editor:** a extensão do ESLint no VS Code mostra erros enquanto você digita e pode corrigir ao salvar.
- **Pré-commit:** `lint-staged` roda o ESLint só nos arquivos alterados (veja o capítulo sobre fluxo de desenvolvimento).
- **CI:** `npm run lint` como etapa obrigatória do pull request.
- **Adoção gradual:** ao ligar uma regra nova num código grande, comece como `"warn"`, corrija aos poucos e depois promova para `"error"`. Comentários `// eslint-disable-next-line regra -- motivo` devem ser exceção, sempre com o motivo.

## Na entrevista

**Qual a diferença entre ESLint e Prettier?** ESLint encontra problemas de qualidade e padrões de código; Prettier só formata. Usa-se os dois, com `eslint-config-prettier` desligando as regras de estilo que conflitam.

**O que mudou com o flat config?** A configuração virou um array em `eslint.config.js`, com plugins importados como módulos JavaScript em vez de resolvidos por nome, `files` para escopo por padrão de arquivo e `ignores` no lugar do `.eslintignore`. Fica explícito o que se aplica a cada arquivo.

**Como funciona uma regra do ESLint?** O código vira AST, e a regra registra funções para tipos de nó. Ao visitar o nó, ela verifica a condição e chama `context.report`, podendo oferecer `fix` ou sugestões.

## Pratique

Num projeto Node.js seu (a API de livros serve), entregue:

1. `eslint.config.js` em flat config com recomendadas, globais do Node, blocos para testes e `.cjs`, e Prettier integrado.
2. Scripts `lint`, `lint:fix` e `format:check`, com o projeto passando sem avisos.
3. A regra `no-process-env-fora-de-config` com pelo menos seis casos no `RuleTester`.
4. Uma segunda regra própria à sua escolha, com `fixable` ou `hasSuggestions`. Ideia: proibir `res.send` com objeto, sugerindo `res.json`.
