Quando algo dá errado em tempo de execução (divisão por zero, índice fora do array, texto que não é número), C# lança uma exceção: um objeto que interrompe o fluxo normal e sobe pela pilha de chamadas até encontrar um `catch` que o trate. Se ninguém trata, o programa termina com a mensagem de erro. Em entrevista, o que interessa é saber quais exceções você mesmo provoca por engano e como lançar e tratar as suas com critério.

## try, catch e finally

O bloco `try` contém o código arriscado, cada `catch` trata um tipo de exceção (do mais específico ao mais geral) e o `finally` roda sempre, haja ou não erro. Todas as exceções herdam de `System.Exception`.

```csharp
using System;

class Program
{
    static int Dividir(int a, int b) { return a / b; }

    static void Main()
    {
        try
        {
            Console.WriteLine(Dividir(10, 2));
            Console.WriteLine(Dividir(1, 0));
            Console.WriteLine("nao chega aqui");
        }
        catch (DivideByZeroException ex)
        {
            Console.WriteLine("erro: " + ex.GetType().Name);
        }
        finally
        {
            Console.WriteLine("finally");
        }

        int n;
        Console.WriteLine(int.TryParse("123", out n));
        Console.WriteLine(n);
        Console.WriteLine(int.TryParse("12x", out n));
        Console.WriteLine(n);

        try
        {
            int.Parse("abc");
        }
        catch (FormatException)
        {
            Console.WriteLine("formato invalido");
        }
    }
}
```

```text
Saída:
5
erro: DivideByZeroException
finally
True
123
False
0
formato invalido
```

Note que a linha "nao chega aqui" nunca é impressa: no instante em que a exceção é lançada, o resto do `try` é abandonado. Note também a diferença entre `int.Parse`, que lança `FormatException`, e `int.TryParse`, que devolve `false` e deixa `n` valendo zero. Para entrada que pode estar errada, prefira sempre a família `TryParse` (e `TryGetValue` nos dicionários): exceções são caras e não devem controlar o fluxo normal.

## Lançando e criando exceções

Use `throw` com uma exceção específica e uma mensagem útil. As da biblioteca que você mais vai lançar são `ArgumentException`, `ArgumentNullException`, `InvalidOperationException` (estado inválido, como pilha vazia) e `NotImplementedException`. Quando o erro tem significado de domínio, crie uma própria herdando de `Exception`.

```csharp
using System;

class SaldoInsuficienteException : Exception
{
    public int Faltam { get; private set; }
    public SaldoInsuficienteException(int faltam) : base("faltam " + faltam)
    {
        Faltam = faltam;
    }
}

class Conta
{
    private int saldo;
    public Conta(int saldo) { this.saldo = saldo; }
    public int Saldo { get { return saldo; } }

    public void Sacar(int valor)
    {
        if (valor <= 0) throw new ArgumentException("valor invalido");
        if (valor > saldo) throw new SaldoInsuficienteException(valor - saldo);
        saldo -= valor;
    }
}

class Recurso : IDisposable
{
    public void Dispose() { Console.WriteLine("liberado"); }
}

class Program
{
    static void Main()
    {
        var c = new Conta(100);
        try
        {
            c.Sacar(30);
            c.Sacar(100);
        }
        catch (SaldoInsuficienteException ex)
        {
            Console.WriteLine(ex.Message + " / " + ex.Faltam);
        }

        try
        {
            c.Sacar(-1);
        }
        catch (ArgumentException ex) when (ex.Message.StartsWith("valor"))
        {
            Console.WriteLine("filtro: " + ex.Message);
        }

        using (var r = new Recurso())
        {
            Console.WriteLine("usando");
        }
        Console.WriteLine(c.Saldo);
    }
}
```

```text
Saída:
faltam 30 / 30
filtro: valor invalido
usando
liberado
70
```

A cláusula `when` é um filtro: o `catch` só captura se a condição for verdadeira. O bloco `using` garante que `Dispose` é chamado ao sair, mesmo com exceção, e é o jeito idiomático de fechar arquivos e conexões.

## Armadilhas

- Dentro de um `catch`, use `throw;` para relançar preservando a pilha original. `throw ex;` reinicia o rastreamento e esconde onde o erro nasceu.
- Não capture `Exception` genérica e engula o erro em silêncio: você esconde bugs.
- Erros esperados de entrada (valor vazio, chave ausente) pedem validação ou `TryXxx`, não exceção.
- Um `return` dentro do `try` ainda executa o `finally` antes de sair.
- Exceções em tarefas assíncronas chegam embrulhadas; veja o capítulo de async e await.

<Callout type="tip" title="Dica">
Lançar e capturar custa milhares de ciclos de CPU. Dentro de um laço quente de uma solução de entrevista, uma exceção como fluxo normal é um sinal vermelho de design.
</Callout>

## Na entrevista

Em problemas de design, mostre que você valida argumentos e falha cedo (`ArgumentNullException`, `InvalidOperationException` para pilha ou fila vazia). Em algoritmos, normalmente o enunciado já garante as entradas; ainda assim, cite os casos de borda. Follow-ups comuns: "qual a diferença entre `throw` e `throw ex`?" e "quando o `finally` não executa?" (processo encerrado de forma abrupta, como `Environment.FailFast`, ou travamento do processo).
