Em entrevistas de design orientado a objetos (e em muitos problemas de estruturas de dados) você precisa expressar duas ideias: "este tipo sabe fazer isto" e "este tipo é uma especialização daquele". C# resolve a primeira com interfaces e a segunda com herança de classes. Saber quando usar cada uma, e como o despacho dinâmico decide qual método roda, é o que separa uma resposta decorada de uma resposta que convence.

## Interfaces: um contrato sem implementação

Uma interface declara membros (métodos, propriedades, eventos, indexadores) sem corpo. Uma classe que a implementa se compromete a fornecer todos eles. Por convenção, o nome começa com `I`, como em `IComparable` ou `IEnumerable`. Uma classe pode implementar quantas interfaces quiser, o que contorna a regra de que só existe uma classe base.

O ganho prático é programar para o contrato: um método que recebe `IForma` funciona com qualquer forma, hoje e no futuro, sem saber qual classe concreta está do outro lado.

```csharp
using System;
using System.Collections.Generic;

interface IForma
{
    string Nome { get; }
    int Area();
}

class Retangulo : IForma
{
    private readonly int largura, altura;
    public Retangulo(int largura, int altura)
    {
        this.largura = largura;
        this.altura = altura;
    }
    public string Nome { get { return "Retangulo"; } }
    public int Area() { return largura * altura; }
}

class Quadrado : IForma
{
    private readonly int lado;
    public Quadrado(int lado) { this.lado = lado; }
    public string Nome { get { return "Quadrado"; } }
    public int Area() { return lado * lado; }
}

class Program
{
    static void Main()
    {
        var formas = new List<IForma> { new Retangulo(3, 4), new Quadrado(5) };
        int total = 0;
        foreach (IForma f in formas)
        {
            Console.WriteLine(f.Nome + ": " + f.Area());
            total += f.Area();
        }
        Console.WriteLine("total: " + total);
    }
}
```

```text
Saída:
Retangulo: 12
Quadrado: 25
total: 37
```

Compare com Python e JavaScript: lá o "duck typing" aceita qualquer objeto que tenha o método. Em C# o contrato é verificado na compilação, então um erro de nome vira erro de build, e não uma exceção em produção.

## Herança, virtual e override

Na herança, a classe filha reaproveita o que a base já tem. Um método só pode ser substituído se a base o marcar como `virtual` (ou `abstract`, quando não há implementação) e a filha usar `override`. Isso é diferente de Java, onde tudo é virtual por padrão: em C# você opta explicitamente.

O construtor da base é chamado com `: base(...)`. Uma classe `abstract` não pode ser instanciada e serve de esqueleto para as filhas. Cada classe herda de uma única base, e toda classe herda de `object`.

## override versus new

A armadilha clássica é `new`. Quando a filha declara um método com o mesmo nome sem `override`, ela apenas esconde o da base, e o método chamado passa a depender do tipo da variável, não do objeto.

```csharp
using System;

class Base
{
    public virtual string Quem() { return "Base"; }
    public string Oculto() { return "Base.Oculto"; }
}

class Filho : Base
{
    public override string Quem() { return "Filho"; }
    public new string Oculto() { return "Filho.Oculto"; }
}

class Program
{
    static void Main()
    {
        Base b = new Filho();
        Console.WriteLine(b.Quem());
        Console.WriteLine(b.Oculto());
        Console.WriteLine(((Filho)b).Oculto());
        Console.WriteLine(b is Filho);
    }
}
```

```text
Saída:
Filho
Base.Oculto
Filho.Oculto
True
```

`Quem` é virtual, então a chamada é resolvida pelo tipo real do objeto (`Filho`). `Oculto` não é, então a variável do tipo `Base` enxerga o método da base. Em entrevista, se você escrever `new` por engano, o compilador avisa, e vale dizer por que isso quase sempre é um bug de design.

## Interface ou classe abstrata?

| Característica | Interface | Classe abstrata |
| --- | --- | --- |
| Estado (campos) | Não | Sim |
| Várias por classe | Sim | Não, só uma base |
| Código compartilhado | Só por default methods (C# 8+) | Sim |
| Quando usar | Capacidade ("pode ser comparado") | Família com base comum ("é um") |

<Callout type="note" title="Versão necessária">
Métodos com implementação padrão em interfaces exigem C# 8 e .NET Core 3.0 ou superior. Exemplo: dentro de `interface ILog`, escrever `void Info(string m) => Console.WriteLine(m);` dá uma implementação que as classes podem sobrescrever ou ignorar. Nas versões antigas a interface só declarava assinaturas.
</Callout>

Prefira composição quando a herança só serve para reaproveitar código: herdar acopla a filha aos detalhes da base. Uma classe `sealed` não pode ser estendida, e é o padrão sensato quando você não projetou a classe para herança.

## Na entrevista

Em problemas de design (estacionamento, biblioteca, elevador), declare interfaces para os comportamentos que variam e classes concretas para as variações. Cite o princípio aberto/fechado: novas formas entram sem alterar o código que usa `IForma`. Follow-ups comuns: "qual a diferença entre interface e classe abstrata?" e "por que o método precisa ser `virtual` para ser sobrescrito?". Outra pergunta frequente é sobre o diamante: C# não tem herança múltipla de classes, então o problema não existe para estado, e para interfaces você pode resolver a ambiguidade com implementação explícita.
