FCFS e SJF deixam um processo usar a CPU até terminar ou bloquear. Isso é péssimo para um sistema interativo: enquanto um compilador roda, o editor de texto fica congelado. **Round Robin** (RR) resolve com uma regra simples: cada processo recebe uma fatia fixa de tempo, o **quantum**. Quando a fatia acaba, o timer interrompe, o processo vai para o fim da fila de prontos e o próximo entra. Ninguém espera mais do que `(n - 1) * quantum` para voltar a rodar.

## Como funciona

```text
 fila de prontos:  [A] [B] [C]        quantum = 4

 t=0   A roda 4  → ainda falta → fim da fila  [B] [C] [A]
 t=4   B roda 3  → terminou                   [C] [A]
 t=7   C roda 4  → ainda falta → fim da fila  [A] [C]
 t=11  A roda ...
```

Dois detalhes que derrubam muita gente em exercício de entrevista:

1. Se um processo termina antes do fim do quantum, a CPU passa imediatamente ao próximo. O quantum é um teto, não um tempo fixo.
2. Quando um processo chega no mesmo instante em que outro é preemptado, a convenção mais comum é colocar o recém-chegado na fila **antes** do preemptado. Diga em voz alta qual convenção você está usando.

## Simulador

O código abaixo implementa RR com tempos de chegada, seguindo a convenção acima, e calcula espera, resposta e o número de trocas de contexto.

```python
from collections import deque

def round_robin(procs, quantum):
    procs = sorted(procs, key=lambda p: p[1])
    resta = {n: r for n, _, r in procs}
    primeira = {}
    fim = {}
    fila = deque()
    t, i, trocas, gantt = 0, 0, 0, []

    def admitir(ate):
        nonlocal i
        while i < len(procs) and procs[i][1] <= ate:
            fila.append(procs[i][0])
            i += 1

    admitir(t)
    while fila or i < len(procs):
        if not fila:
            t = procs[i][1]
            admitir(t)
        n = fila.popleft()
        primeira.setdefault(n, t)
        uso = min(quantum, resta[n])
        gantt.append(f"{n}{uso}")
        t += uso
        resta[n] -= uso
        admitir(t)                      # chegadas entram antes do preemptado
        if resta[n] > 0:
            fila.append(n)
        else:
            fim[n] = t
        trocas += 1
    return fim, primeira, trocas - 1, gantt

procs = [("A", 0, 10), ("B", 1, 4), ("C", 2, 7), ("D", 3, 3)]
for q in [2, 4, 10]:
    fim, primeira, trocas, gantt = round_robin(procs, q)
    espera = sum(fim[n] - c - r for n, c, r in procs) / len(procs)
    resposta = sum(primeira[n] - c for n, c, _ in procs) / len(procs)
    print(f"q={q:>2} espera={espera:5.2f} resposta={resposta:5.2f} trocas={trocas:>2} {' '.join(gantt)}")
```

```text
Saída:
q= 2 espera=11.25 resposta= 2.00 trocas=12 A2 B2 C2 A2 D2 B2 C2 A2 D1 C2 A2 C1 A2
q= 4 espera= 9.75 resposta= 4.50 trocas= 6 A4 B4 C4 D3 A4 C3 A2
q=10 espera= 9.75 resposta= 9.75 trocas= 3 A10 B4 C7 D3
```

Repare no padrão: com quantum pequeno, a **resposta** é ótima (todo mundo começa logo), mas o número de trocas explode. Com quantum igual à maior rajada, RR vira FCFS: poucas trocas, resposta ruim.

## Escolhendo o quantum

Duas forças puxam em direções opostas:

- **Quantum muito pequeno:** boa interatividade, mas a fração da CPU gasta em troca de contexto cresce. Com quantum de 10 µs e troca de 5 µs, um terço do tempo vai embora.
- **Quantum muito grande:** degenera em FCFS e volta o efeito comboio.

Uma regra prática clássica: escolha o quantum de modo que a maioria das rajadas de CPU (algo como 80%) caiba numa fatia só. Assim processos interativos, que rodam pouco e logo bloqueiam em E/S, raramente são preemptados, e só os processos longos pagam o custo de serem fatiados. Kernels reais usam fatias de alguns milissegundos.

O programa a seguir mostra o efeito do quantum quando há uma troca de contexto de custo fixo, comparando o tempo total para completar o mesmo trabalho:

```python
rajadas = [10, 4, 7, 3]
CUSTO_TROCA = 0.5

for q in [1, 2, 4, 8, 16]:
    fatias = sum(-(-r // q) for r in rajadas)   # teto de r / q
    trocas = fatias - 1
    total = sum(rajadas) + trocas * CUSTO_TROCA
    print(f"quantum={q:>2} fatias={fatias:>2} tempo_total={total:5.1f} desperdicio={trocas * CUSTO_TROCA / total:6.1%}")
```

```text
Saída:
quantum= 1 fatias=24 tempo_total= 35.5 desperdicio= 32.4%
quantum= 2 fatias=13 tempo_total= 30.0 desperdicio= 20.0%
quantum= 4 fatias= 7 tempo_total= 27.0 desperdicio= 11.1%
quantum= 8 fatias= 5 tempo_total= 26.0 desperdicio=  7.7%
quantum=16 fatias= 4 tempo_total= 25.5 desperdicio=  5.9%
```

## Trade-offs

| Aspecto | Round Robin |
| --- | --- |
| Justiça | Alta: todos recebem fatias iguais |
| Tempo de resposta | Bom, limitado por `(n - 1) * quantum` |
| Turnaround médio | Geralmente pior que SJF |
| Inanição | Não ocorre |
| Overhead | Cresce com quantum pequeno |
| Diferenciação | Nenhuma: tratar um job de backup igual a uma requisição web é ruim |

<Callout type="note" title="RR em lugares inesperados">
O mesmo raciocínio aparece em balanceadores (round robin entre servidores), em rate limiting justo entre clientes e em runtimes de linguagem. O agendador de goroutines do Go, por exemplo, preempta uma goroutine que roda há mais de cerca de 10 ms para que as outras não passem fome.
</Callout>

## Na entrevista

Se pedirem um cálculo de RR, monte a fila passo a passo, anote o instante de cada chegada e declare a convenção de desempate. Na parte conceitual, mostre o trade-off do quantum com números. Follow-ups comuns: "RR com quantum infinito vira o quê?" (FCFS) e "por que processos limitados por E/S se dão bem em RR?" (usam pouco da fatia e voltam rápido à fila, então têm boa latência).
