Seu programa em Python chama `open("dados.csv")` e recebe um arquivo. Ele não sabe se o disco é um SSD NVMe, um volume de rede ou um pendrive, nem se outros cem processos estão disputando a mesma CPU. Quem esconde tudo isso é o **sistema operacional**: a camada de software que gerencia o hardware e oferece aos programas uma interface estável e segura para usá-lo.

## Dois papéis ao mesmo tempo

Vale a pena pensar no SO de dois jeitos complementares:

- **Máquina estendida (abstração):** em vez de setores, interrupções e registradores de controlador, você recebe arquivos, processos, sockets e memória virtual. São abstrações limpas sobre um hardware feio.
- **Gerente de recursos:** CPU, memória, disco e rede são finitos e compartilhados. O SO decide quem usa o quê, por quanto tempo, e impede que um programa atrapalhe o outro.

O compartilhamento acontece de duas formas. **No tempo**, um recurso é usado por um de cada vez, em fatias: é assim com a CPU. **No espaço**, o recurso é dividido em pedaços simultâneos: é assim com a memória e o disco.

```text
  aplicativos   →  navegador   banco de dados   seu serviço
  ------------------------------------------------------------
  bibliotecas   →  libc, runtime do Python, JVM
  ------------------------------------------------------------
  kernel        →  escalonador | memória virtual | VFS | rede | drivers
  ------------------------------------------------------------
  hardware      →  CPU   RAM   disco   placa de rede   timer
```

## Multiplexação no tempo, na prática

Com um só núcleo, dois processos parecem rodar juntos porque o SO alterna entre eles muitas vezes por segundo. A simulação abaixo dá fatias de 3 unidades de tempo a cada processo até todos terminarem:

```python
processos = {"editor": 5, "compilador": 7, "player": 4}
fatia = 3
relogio = 0
linha_do_tempo = []

fila = list(processos)
restante = dict(processos)
while fila:
    nome = fila.pop(0)
    uso = min(fatia, restante[nome])
    linha_do_tempo.append(f"{relogio:>2}-{relogio + uso:>2} {nome}")
    relogio += uso
    restante[nome] -= uso
    if restante[nome] > 0:
        fila.append(nome)

for trecho in linha_do_tempo:
    print(trecho)
print("tempo total:", relogio)
```

```text
Saída:
 0- 3 editor
 3- 6 compilador
 6- 9 player
 9-11 editor
11-14 compilador
14-15 player
15-16 compilador
tempo total: 16
```

Nenhum processo precisou saber que os outros existiam. Esse é o ponto: o SO cria a ilusão de que cada programa tem a máquina só para si.

## A mesma interface para qualquer dispositivo

A outra metade do trabalho é a abstração. O programa abaixo usa as chamadas de baixo nível do módulo `os`, que mapeiam quase um para um para chamadas de sistema: abrir, escrever, posicionar, ler e fechar. O código não muda se o arquivo estiver num SSD, num HD ou num disco em memória.

```python
import os
import tempfile

with tempfile.TemporaryDirectory() as pasta:
    caminho = os.path.join(pasta, "log.txt")
    fd = os.open(caminho, os.O_CREAT | os.O_RDWR)
    escritos = os.write(fd, b"pedido 42 aprovado")
    os.lseek(fd, 0, os.SEEK_SET)
    lido = os.read(fd, 100)
    os.close(fd)
    print("bytes escritos:", escritos)
    print("conteudo:", lido.decode())
    print("tamanho segundo o SO:", os.stat(caminho).st_size)
```

```text
Saída:
bytes escritos: 18
conteudo: pedido 42 aprovado
tamanho segundo o SO: 18
```

O número `fd` é um **descritor de arquivo**: um índice numa tabela que o kernel mantém para o processo. O programa nunca toca no disco; ele pede ao kernel, que fala com o driver.

## Kernel, SO e o resto

Em conversa técnica, "SO" às vezes significa só o **kernel** (o código que roda em modo privilegiado) e às vezes o pacote todo, com shell, bibliotecas e utilitários. Linux, a rigor, é um kernel; Ubuntu é uma distribuição que o empacota. Saber essa diferença ajuda a entender containers mais adiante: todos os containers de uma máquina compartilham o mesmo kernel, mas cada um pode ter o próprio "resto".

| Componente | Responsabilidade | Exemplo de problema real |
| --- | --- | --- |
| Escalonador | Decide quem usa a CPU | Latência alta com CPU saturada |
| Gerência de memória | Memória virtual, paginação | OOM killer matando seu serviço |
| Sistema de arquivos | Arquivos, diretórios, cache | `fsync` lento derrubando throughput |
| Pilha de rede | TCP/IP, sockets | Esgotar portas efêmeras |
| Drivers | Falar com cada dispositivo | Driver de disco com bug travando E/S |

<Callout type="tip" title="Por que um engenheiro de aplicação precisa disso">
Quase todo problema de desempenho estranho, como pausas, picos de latência ou memória que "some", é o SO fazendo exatamente o que foi projetado para fazer. Conhecer o mecanismo transforma mistério em diagnóstico.
</Callout>

## Trade-offs de projeto

Um SO equilibra objetivos que brigam entre si: **vazão** (fazer muito trabalho) contra **latência** (responder rápido), **isolamento** (proteger processos uns dos outros) contra **desempenho** (cada fronteira de proteção custa ciclos), e **generalidade** contra **especialização**. Bancos de dados, por exemplo, muitas vezes contornam o cache de arquivos do SO porque sabem melhor o que manter em memória.
