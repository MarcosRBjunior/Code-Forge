Confiabilidade é a capacidade de o sistema **continuar fazendo a coisa certa** mesmo quando algo dá errado: um disco queima, a rede perde pacotes, um usuário envia dados inesperados ou um deploy traz um bug. Disponibilidade pergunta "o sistema responde?"; confiabilidade pergunta "o sistema responde corretamente, de forma consistente, ao longo do tempo?".

## Falha vs defeito

Vale separar dois termos:

- **Defeito (fault):** um componente se desviando do esperado. Um servidor reinicia, uma chamada estoura o timeout.
- **Falha (failure):** o sistema como um todo deixa de entregar o serviço ao usuário.

O objetivo de um sistema confiável é impedir que defeitos virem falhas. Você não consegue eliminar defeitos; consegue **tolerá-los**.

## Tipos de defeito

| Tipo | Exemplos | Defesa típica |
| --- | --- | --- |
| Hardware | disco, memória, fonte, rack inteiro | redundância, replicação, múltiplas zonas |
| Software | bug que afeta todas as instâncias, vazamento de memória, dependência lenta | testes, deploy gradual, timeouts, isolamento |
| Humano | configuração errada, comando destrutivo, migração mal feita | automação, revisão, ambientes de staging, rollback rápido |

Defeitos de hardware tendem a ser independentes: dois discos raramente falham no mesmo segundo. Defeitos de software são **correlacionados**: o mesmo bug existe em todas as réplicas e pode derrubar todas ao mesmo tempo. Por isso redundância sozinha não basta.

## Métricas: MTBF e MTTR

- **MTBF (tempo médio entre falhas):** quanto tempo, em média, o sistema roda até falhar.
- **MTTR (tempo médio de recuperação):** quanto tempo leva para voltar ao normal.

A relação aproximada com disponibilidade é:

```text
disponibilidade ≈ MTBF / (MTBF + MTTR)
```

Repare que existem duas alavancas. Aumentar o MTBF exige prevenir falhas, o que tem retorno decrescente. Reduzir o MTTR (detecção rápida, rollback automático, runbooks) costuma ser mais barato e muitas vezes mais eficaz. Um sistema que cai uma vez por semana, mas se recupera em 10 segundos, pode ser melhor que um que cai uma vez por ano e leva um dia para voltar.

## Técnicas de confiabilidade

### Retries com backoff

Defeitos transitórios (um pacote perdido, um nó reiniciando) se resolvem tentando de novo. Mas retries ingênuos multiplicam a carga justamente quando o serviço está sofrendo. Use **backoff exponencial com jitter** e limite o número de tentativas.

```python
import random
import time

def chamar_com_retry(fn, tentativas=5, base=0.1, teto=5.0):
    for i in range(tentativas):
        try:
            return fn()
        except ErroTransitorio:
            if i == tentativas - 1:
                raise
            espera = min(teto, base * 2 ** i)
            time.sleep(random.uniform(0, espera))  # jitter completo
```

Retries só são seguros se a operação for **idempotente**. Cobrar um cartão duas vezes porque a primeira resposta se perdeu é um defeito virando falha.

### Timeouts

Toda chamada de rede precisa de um timeout. Sem ele, uma dependência lenta prende threads e conexões até esgotar o servidor que chama.

### Isolamento

Separe recursos (pools de conexão, filas, instâncias) por dependência ou por cliente, para que um problema não se espalhe. É a ideia dos padrões bulkhead e circuit breaker.

### Validação e checagens de integridade

Valide entradas na borda, use checksums para detectar corrupção de dados e faça backups que sejam **testados** com restaurações reais.

### Testar a falha

Chaos engineering consiste em injetar defeitos de propósito (matar instâncias, adicionar latência) para verificar se o sistema tolera o que você acha que tolera.

<Callout type="warning" title="Armadilha clássica">
Retries em várias camadas se multiplicam. Se o cliente tenta 3 vezes, o gateway tenta 3 vezes e o serviço tenta 3 vezes na dependência, uma única falha pode gerar 27 chamadas ao componente que já está sobrecarregado. Concentre os retries em um único ponto.
</Callout>

## Na entrevista

Mostre que você pensa em falhas como algo normal. Para cada componente do desenho, diga o que acontece quando ele cai e como o sistema detecta e se recupera. Perguntas frequentes: "como você evita processar um pagamento duas vezes?", "o que acontece se o banco ficar lento em vez de cair?", "como você sabe que o backup funciona?".
