Dados chegam continuamente: cliques, pedidos, leituras de sensores, logs. Há duas formas de processá-los. No **batch**, você acumula dados por um período e processa tudo de uma vez. No **stream**, você processa cada evento (ou micro-lote) assim que chega. A escolha depende de quão rápido o resultado precisa estar disponível e de quanto você aceita pagar em complexidade.

## Processamento em lote (batch)

Um job roda sobre um conjunto **finito e delimitado** de dados, por exemplo "todas as vendas de ontem", e produz um resultado completo.

- **Latência:** minutos a horas. O resultado só existe depois do fim do job.
- **Vantagens:** simples de raciocinar e testar, reprocessável (rodou errado? rode de novo), alta vazão, eficiente com compressão e leituras sequenciais.
- **Ferramentas:** Hadoop MapReduce, Spark, Hive, dbt, jobs SQL no data warehouse, orquestrados por Airflow.
- **Casos:** relatórios diários, folha de pagamento, treino de modelos, faturamento, reindexação.

## Processamento em fluxo (stream)

O fluxo é **ilimitado**: os dados nunca "terminam". O processador mantém estado e emite resultados continuamente.

- **Latência:** milissegundos a segundos.
- **Vantagens:** reação em tempo quase real, resultados sempre atualizados.
- **Ferramentas:** Kafka Streams, Apache Flink, Spark Structured Streaming, Kinesis, Pub/Sub com Dataflow.
- **Casos:** detecção de fraude, alertas, recomendações ao vivo, painéis operacionais, monitoramento de IoT.

## Comparação

| Critério | Batch | Stream |
| --- | --- | --- |
| Entrada | Conjunto finito | Fluxo infinito |
| Latência | Minutos a horas | Milissegundos a segundos |
| Estado e falhas | Reexecuta o job | Checkpoints e estado gerenciado |
| Complexidade | Menor | Maior |
| Reprocessamento | Trivial | Exige log retido e replay |
| Custo | Recursos pontuais | Recursos sempre ligados |

## Conceitos exclusivos de stream

Em fluxos, o tempo é complicado:

- **Event time versus processing time:** quando o evento ocorreu versus quando foi processado. Eventos chegam atrasados e fora de ordem (celular sem sinal).
- **Janelas:** agregações em intervalos: *tumbling* (fixas, sem sobreposição), *sliding* (deslizantes) e *session* (por atividade do usuário).
- **Watermarks:** marcam até onde se considera que os eventos já chegaram; eventos tardios depois do watermark são descartados ou tratados à parte.
- **Semântica de entrega:** at-most-once, at-least-once e exactly-once (obtida com checkpoints e escritas idempotentes ou transacionais).

class Evento {
    long ts;
    String usuario;

    Evento(long ts, String usuario) {
        this.ts = ts;
        this.usuario = usuario;
    }
}

static Map<String, Integer> contar(List<Evento> eventos) {
    Map<String, Integer> contagem = new HashMap<>();
    for (Evento evento : eventos) {
        long janela = evento.ts / 60; // inicia a cada 60 s
        contagem.merge(janela + "|" + evento.usuario, 1, Integer::sum);
    }
    return contagem;
}

static final Map<String, Integer> contagem = contar(List.of(new Evento(5, "ana"), new Evento(20, "ana"), new Evento(70, "bia")));

## Arquiteturas combinadas

- **Lambda:** uma camada batch (precisa, lenta) e uma camada de velocidade (aproximada, rápida), com visão mesclada. Duplica a lógica, o que é caro de manter.
- **Kappa:** apenas streaming, com o log (Kafka) retido para reprocessar quando a lógica mudar.
- **Hoje:** engines unificadas (Flink, Spark, Beam) aceitam o mesmo código para lote e fluxo; o lote é visto como fluxo finito.

<Callout type="tip" title="Não use stream por moda">
Se ninguém precisa do dado em menos de uma hora, um batch bem feito é mais barato, mais simples e mais fácil de corrigir. Escolha stream quando o valor do dado cai rápido com o tempo.
</Callout>
