Se relógios físicos não são confiáveis para ordenar eventos entre máquinas, o que fazer? A observação de Leslie Lamport (1978) é que, na maior parte das vezes, **não precisamos saber a hora, só a ordem causal**: o que pode ter influenciado o quê. Um **relógio lógico** é um contador que captura essa relação, sem olhar para o tempo real.

## A relação "aconteceu antes"

Define-se `a -> b` (a aconteceu antes de b) quando:

1. a e b ocorrem no mesmo processo e a vem primeiro;
2. a é o envio de uma mensagem e b é o recebimento dela;
3. existe c tal que `a -> c` e `c -> b` (transitividade).

Se nenhuma dessas relações vale entre dois eventos, eles são **concorrentes**: nenhum pôde influenciar o outro.

```text
Processo P1:  a ----------- envia(m) ------ d
                               \
Processo P2:  b ------------- recebe(m) --- e

a -> envia(m) -> recebe(m) -> e         (causalmente ordenados)
a e b: concorrentes (nenhuma mensagem os liga)
```

## Duas ferramentas principais

### Relógio de Lamport

Um contador escalar por processo. Se `a -> b`, então `L(a) < L(b)`. Mas o contrário não vale: `L(a) < L(b)` não garante que a causou b. Detalhes no capítulo seguinte.

### Vetores de versão (vector clocks)

Cada processo mantém um **vetor** com um contador para cada participante. Comparando dois vetores, descobre-se com certeza se um evento precedeu o outro ou se são concorrentes.

```python
def comparar(v1, v2):
    menor_ou_igual = all(a <= b for a, b in zip(v1, v2))
    maior_ou_igual = all(a >= b for a, b in zip(v1, v2))
    if menor_ou_igual and maior_ou_igual:
        return "iguais"
    if menor_ou_igual:
        return "v1 antes de v2"
    if maior_ou_igual:
        return "v2 antes de v1"
    return "concorrentes"

print(comparar([2, 1, 0], [3, 1, 0]))   # v1 antes de v2
```

Regras: cada processo incrementa sua própria posição a cada evento; ao enviar, anexa o vetor; ao receber, toma o máximo posição a posição e incrementa a sua.

## Comparação

| Característica | Lamport | Vetor |
| --- | --- | --- |
| Tamanho | Um número | Um número por processo |
| Detecta concorrência | Não | Sim |
| Se L(a) menor que L(b)... | Pode ou não ter causalidade | Causalidade exata |
| Custo | Baixo | Cresce com o número de nós |

## Aplicações

- **Detectar conflitos de escrita:** Dynamo original usava vetores para saber se duas versões de um item são concorrentes e precisam ser mescladas, em vez de descartar uma delas.
- **Entrega causal de mensagens** em chats e sistemas de colaboração.
- **Depuração e tracing:** reconstruir a ordem de eventos entre serviços.
- **CRDTs**, que dependem de ordens causais para convergir.

## Variações modernas

- **Relógios híbridos (HLC):** combinam um tempo físico aproximado com um contador lógico, mantendo timestamps próximos da hora real e com garantia de causalidade (CockroachDB, YugabyteDB).
- **Dotted version vectors e vetores de versão por réplica:** versões compactas, que evitam crescimento sem limite do vetor.

<Callout type="note" title="Custo dos vetores">
O vetor cresce com o número de participantes. Em sistemas com milhares de clientes, usa-se um vetor por réplica (poucos servidores), não por cliente, ou técnicas de poda.
</Callout>

## Na entrevista

Quando surgir "dois usuários editaram o mesmo item ao mesmo tempo", explique que timestamps físicos não bastam e proponha vetores de versão para detectar concorrência, com resolução definida (mesclar, pedir ao usuário, CRDT). Follow-ups: "qual a diferença entre Lamport e vetor?" (Lamport ordena, mas não distingue concorrência) e "por que não usar sempre o relógio físico?" (deriva, saltos, ausência de causalidade).
