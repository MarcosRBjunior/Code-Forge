O TLS protege os dados enquanto viajam. Mas um disco roubado, um backup que vaza, um snapshot compartilhado por engano ou um administrador curioso podem expor tudo o que está armazenado. A **criptografia em repouso** (*encryption at rest*) garante que, sem a chave, os bytes gravados em disco, em bucket ou em backup sejam ilegíveis.

## Contra o que protege

- Furto ou descarte inadequado de discos e mídias.
- Acesso indevido ao armazenamento subjacente (snapshots, backups, volumes desanexados).
- Vazamento de um bucket mal configurado (reduz o dano, mas não substitui controle de acesso).
- Requisitos regulatórios: LGPD, PCI DSS e outros exigem proteção adequada de dados pessoais e de cartão.

Não protege contra uma aplicação comprometida que já tem a chave e permissão de leitura, nem contra SQL injection: o banco decripta de forma transparente para quem consulta.

## Níveis de criptografia

| Nível | Quem criptografa | Protege contra | Observação |
| --- | --- | --- | --- |
| Disco ou volume | Sistema operacional ou nuvem (EBS, LUKS, BitLocker) | Roubo físico | Transparente; o mais simples |
| Banco ou tabela (TDE) | O próprio banco | Acesso aos arquivos de dados e backups | Quem consulta o banco vê texto claro |
| Aplicação (por campo) | O seu código, antes de gravar | Até administradores do banco | Mais seguro; perde busca e índices diretos |
| Cliente (ponta a ponta) | O dispositivo do usuário | Também o próprio provedor | O servidor não consegue processar o dado |

Para dados muito sensíveis (CPF, cartão, prontuário), criptografar no nível do campo é comum.

## Envelope encryption

Criptografar tudo diretamente com uma única chave mestra seria ineficiente e arriscado. O padrão usado por KMS de nuvem é a **criptografia em envelope**:

```text
Chave mestra (KEK) --- guardada no KMS/HSM, nunca sai
      |
      | cifra
      v
Chave de dados (DEK) --- uma por objeto, volume ou tabela
      |
      | cifra
      v
Dados
```

1. A aplicação pede ao KMS uma chave de dados (DEK).
2. Usa a DEK para cifrar os dados localmente com AES-256-GCM.
3. Guarda, junto aos dados, a DEK **cifrada** pela chave mestra (KEK).
4. Para ler, pede ao KMS que decifre a DEK, e então decifra os dados.

Vantagens: a chave mestra nunca é exposta, a rotação da KEK exige apenas recifrar as DEKs (pequenas), e cada objeto pode ter sua chave, limitando o raio de impacto de um vazamento.

	clara, cifrada []byte
}

type Cifrado struct {
	nonce, dados []byte

	dek, nonce, dados []byte

	}

func gravar(kms Kms, dados []byte) Gravado {
	dek := kms.gerarChaveDeDados()
	c := aesGcmCifrar(dek.clara, dados)
	descartar(dek.clara) // nunca persistir a chave em claro
	return Gravado{dek: dek.cifrada, nonce: c.nonce, dados: c.dados}
}

## Gestão de chaves

- Chaves ficam num KMS ou HSM, com acesso por identidade e políticas mínimas.
- **Rotação** periódica e procedimento para revogar uma chave comprometida.
- **Separação de funções:** quem administra o armazenamento não deve controlar as chaves.
- **Auditoria:** cada uso de chave gera um registro.
- Perder a chave significa perder os dados de forma irrecuperável. Planeje backup das chaves e recuperação.

## Trade-offs

- Criptografar campos impede buscas por igualdade ou intervalo, a menos que se use técnicas como índices cegos (hash determinístico de um campo) com cuidado.
- Há custo de CPU, normalmente baixo graças a instruções AES em hardware.
- Mais complexidade operacional em backup, restauração e migração.

<Callout type="tip" title="Padrão razoável">
Ative a criptografia padrão de disco e de bucket (quase de graça nas nuvens) e acrescente criptografia por campo apenas para dados verdadeiramente sensíveis.
</Callout>
