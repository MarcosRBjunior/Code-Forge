Manter um lake e um warehouse lado a lado funciona, mas traz custos: os dados são copiados de um para o outro, existem duas camadas de segurança e governança, e o warehouse fica sempre um pouco defasado. O **lakehouse** propõe uma única plataforma: o armazenamento barato e aberto do lake, com as garantias e o desempenho de consulta de um warehouse.

## A peça que faltava: formatos de tabela

Arquivos Parquet soltos em um bucket não oferecem transações. O lakehouse acrescenta uma **camada de metadados transacional** por cima dos arquivos. Os formatos mais conhecidos são Delta Lake, Apache Iceberg e Apache Hudi. Eles mantêm um log de operações que registra quais arquivos pertencem a cada versão da tabela.

```text
tabela_pedidos/
  _log/            <- registro das versões (commits)
    0001.json
    0002.json
  dados/
    part-a.parquet
    part-b.parquet
```

Com esse log você ganha:

- **Transações ACID:** uma gravação é visível por inteiro ou não é visível. Leitores nunca veem arquivos pela metade.
- **Update, delete e merge:** o formato reescreve apenas os arquivos afetados e registra o novo estado.
- **Evolução de schema:** adicionar uma coluna sem reescrever o histórico.
- **Time travel:** consultar a tabela como ela era em uma versão ou data anterior, útil para auditoria e para reproduzir experimentos.

```sql
SELECT * FROM pedidos VERSION AS OF 42;

MERGE INTO pedidos p USING novos n ON p.id = n.id
WHEN MATCHED THEN UPDATE SET p.status = n.status
WHEN NOT MATCHED THEN INSERT *;
```

## Camadas medalhão

Dentro do lakehouse é comum organizar o fluxo em bronze (bruto), silver (limpo) e gold (pronto para negócio). Todas vivem no mesmo armazenamento e no mesmo formato de tabela, e cada camada é produzida a partir da anterior por jobs batch ou streaming.

## O que você ganha

| Vantagem | Explicação |
| --- | --- |
| Uma cópia só | Menos duplicação e menos pipelines de sincronização |
| Cargas variadas | BI, SQL, machine learning e streaming sobre o mesmo dado |
| Formato aberto | Vários motores (Spark, Trino, Flink) leem a mesma tabela |
| Custo | Disco de object storage, computação sob demanda |

## Trade-offs

- **Maturidade operacional:** compactar arquivos pequenos, limpar versões antigas e gerenciar o catálogo exigem trabalho contínuo.
- **Desempenho:** costuma ser bom, mas um warehouse totalmente gerenciado ainda pode vencer em consultas interativas muito concorrentes.
- **Concorrência de escrita:** vários escritores na mesma tabela dependem de controle otimista e podem gerar conflitos e tentativas repetidas.
- **Complexidade de escolha:** os três formatos têm diferenças de ecossistema e integração.

<Callout type="note" title="Não é bala de prata">
Se a empresa só precisa de relatórios SQL sobre dados bem estruturados, um warehouse gerenciado pode ser mais simples. O lakehouse compensa quando há dados variados, ciência de dados e volume grande misturados.
</Callout>

## Na entrevista

Apresente o lakehouse como evolução: "o lake dá barateza e flexibilidade, mas não dá ACID; o formato de tabela resolve isso". Mencione time travel e merge como diferenciais. Follow-up típico: "como você corrige um dado errado no lake?" (merge ou delete em tabela transacional, em vez de reescrever pastas à mão).
