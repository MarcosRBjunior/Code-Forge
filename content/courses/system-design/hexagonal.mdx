Em muitos sistemas, a regra de negócio acaba misturada com framework web, ORM e chamadas a APIs externas. Trocar o banco ou testar uma regra vira um sofrimento, pois tudo depende de tudo. A **arquitetura hexagonal**, também chamada de *ports and adapters* (Alistair Cockburn), propõe o contrário: o **domínio fica no centro, sem depender de nada externo**, e o mundo de fora se conecta por interfaces.

## A estrutura

```text
   HTTP / CLI / fila                      Banco / e-mail / API de pagamento
         |                                              ^
   [Adaptador de entrada]                     [Adaptador de saída]
         |                                              |
         v                                              |
      Porta de entrada  -->  DOMÍNIO / APLICAÇÃO  -->  Porta de saída
        (caso de uso)       (regras de negócio)       (interface)
```

- **Domínio e casos de uso:** o coração. Entidades e regras puras, sem imports de framework.
- **Porta (port):** uma interface definida pelo domínio. A de entrada diz o que o sistema oferece ("criar pedido"); a de saída diz o que ele precisa ("salvar pedido", "cobrar cartão").
- **Adaptador (adapter):** implementação concreta de uma porta. Um controller REST é adaptador de entrada; um repositório PostgreSQL é adaptador de saída.

A regra de dependência: **as setas apontam para dentro**. O domínio não conhece os adaptadores; os adaptadores conhecem o domínio.

```python
from abc import ABC, abstractmethod

class RepositorioPedidos(ABC):          # porta de saída
    @abstractmethod
    def salvar(self, pedido: dict) -> None: ...

class CriarPedido:                       # caso de uso (domínio)
    def __init__(self, repo: RepositorioPedidos):
        self.repo = repo

    def executar(self, itens: list) -> dict:
        if not itens:
            raise ValueError("pedido sem itens")
        pedido = {"itens": itens, "total": sum(i["preco"] for i in itens)}
        self.repo.salvar(pedido)
        return pedido

class RepoEmMemoria(RepositorioPedidos):  # adaptador de saída (testes)
    def __init__(self):
        self.dados = []
    def salvar(self, pedido):
        self.dados.append(pedido)

repo = RepoEmMemoria()
print(CriarPedido(repo).executar([{"preco": 10}, {"preco": 5}]))
```

```javascript
// porta de saída (por convenção: salvar(pedido))
class CriarPedido { // caso de uso (domínio)
  constructor(repo) {
    this.repo = repo;
  }

  executar(itens) {
    if (itens.length === 0) {
      throw new Error("pedido sem itens");
```

```java
import java.util.*;

class Item {
    final int preco;

    Item(int preco) {
        this.preco = preco;
    }
}

class Pedido {
    final List<Item> itens;
    final int total;

    Pedido(List<Item> itens, int total) {
        this.itens = itens;
        this.total = total;
    }
}

interface RepositorioPedidos { // porta de saída
    void salvar(Pedido pedido);
}

class CriarPedido { // caso de uso (domínio)
    private final RepositorioPedidos repo;

    CriarPedido(RepositorioPedidos repo) {
        this.repo = repo;
    }

    Pedido executar(List<Item> itens) {
        if (itens.isEmpty()) {
            throw new IllegalArgumentException("pedido sem itens");
        }
        int total = 0;
        for (Item i : itens) total += i.preco;
        Pedido pedido = new Pedido(itens, total);
        repo.salvar(pedido);
        return pedido;
    }
}

class RepoEmMemoria implements RepositorioPedidos { // adaptador de saída (testes)
    final List<Pedido> dados = new ArrayList<>();

    public void salvar(Pedido pedido) {
        dados.add(pedido);
    }
}

public static void main(String[] args) {
    RepoEmMemoria repo = new RepoEmMemoria();
    Pedido p = new CriarPedido(repo).executar(List.of(new Item(10), new Item(5)));
    List<String> itens = new ArrayList<>();
    for (Item i : p.itens) itens.add("{'preco': " + i.preco + "}");
    System.out.println("{'itens': [" + String.join(", ", itens) + "], 'total': " + p.total + "}");
}
```

```cpp
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>
using namespace std;

struct Item {
    int preco;
};

struct Pedido {
    vector<Item> itens;
    int total;
};

class RepositorioPedidos { // porta de saída
public:
    virtual ~RepositorioPedidos() = default;
    virtual void salvar(const Pedido& pedido) = 0;
};

class CriarPedido { // caso de uso (domínio)
    RepositorioPedidos& repo;

public:
    CriarPedido(RepositorioPedidos& repo) : repo(repo) {}

    Pedido executar(const vector<Item>& itens) {
        if (itens.empty()) {
            throw invalid_argument("pedido sem itens");
        }
        int total = 0;
        for (auto& i : itens) total += i.preco;
        Pedido pedido{itens, total};
        repo.salvar(pedido);
        return pedido;
    }
};

class RepoEmMemoria : public RepositorioPedidos { // adaptador de saída (testes)
public:
    vector<Pedido> dados;

    void salvar(const Pedido& pedido) override { dados.push_back(pedido); }
};

int main() {
    RepoEmMemoria repo;
    Pedido p = CriarPedido(repo).executar({{10}, {5}});
    cout << "{'itens': [";
    for (size_t i = 0; i < p.itens.size(); i++) cout << (i ? ", " : "") << "{'preco': " << p.itens[i].preco << "}";
    cout << "], 'total': " << p.total << "}" << endl;
}
```

```csharp
using System;
using System.Collections.Generic;
using System.Linq;

class Item
{
    public readonly int Preco;

    public Item(int preco)
    {
        Preco = preco;
    }
}

class Pedido
{
    public readonly List<Item> Itens;
    public readonly int Total;

    public Pedido(List<Item> itens, int total)
    {
        Itens = itens;
        Total = total;
    }
}

interface IRepositorioPedidos // porta de saída
{
    void Salvar(Pedido pedido);
}

class CriarPedido // caso de uso (domínio)
{
    private readonly IRepositorioPedidos repo;

    public CriarPedido(IRepositorioPedidos repo)
    {
        this.repo = repo;
    }

    public Pedido Executar(List<Item> itens)
    {
        if (itens.Count == 0)
        {
            throw new ArgumentException("pedido sem itens");
        }
        var pedido = new Pedido(itens, itens.Sum(i => i.Preco));
        repo.Salvar(pedido);
        return pedido;
    }
}

class RepoEmMemoria : IRepositorioPedidos // adaptador de saída (testes)
{
    public readonly List<Pedido> Dados = new List<Pedido>();

    public void Salvar(Pedido pedido)
    {
        Dados.Add(pedido);
    }
}

static void Main()
{
    var repo = new RepoEmMemoria();
    var p = new CriarPedido(repo).Executar(new List<Item> { new Item(10), new Item(5) });
    Console.WriteLine("{'itens': [" + string.Join(", ", p.Itens.Select(i => "{'preco': " + i.Preco + "}")) + "], 'total': " + p.Total + "}");
}
```

```go
import (
	"errors"
	"fmt"
	"strings"
)

type Item struct {
	preco int
}

type Pedido struct {
	itens []Item
	total int
}

type RepositorioPedidos interface { // porta de saída
	salvar(pedido Pedido)
}

type CriarPedido struct { // caso de uso (domínio)
	repo RepositorioPedidos
}

func (c CriarPedido) executar(itens []Item) (Pedido, error) {
	if len(itens) == 0 {
		return Pedido{}, errors.New("pedido sem itens")
	}
	total := 0
	for _, i := range itens {
		total += i.preco
	}
	pedido := Pedido{itens, total}
	c.repo.salvar(pedido)
	return pedido, nil
}

type RepoEmMemoria struct { // adaptador de saída (testes)
	dados []Pedido
}

func (r *RepoEmMemoria) salvar(pedido Pedido) { r.dados = append(r.dados, pedido) }

func main() {
	repo := &RepoEmMemoria{}
	p, _ := CriarPedido{repo}.executar([]Item{{10}, {5}})
	itens := []string{}
	for _, i := range p.itens {
		itens = append(itens, fmt.Sprintf("{'preco': %d}", i.preco))
	}
	fmt.Printf("{'itens': [%s], 'total': %d}\n", strings.Join(itens, ", "), p.total)
}
```

Em produção, troca-se `RepoEmMemoria` por um adaptador PostgreSQL, sem tocar na regra de negócio.

## Benefícios

- **Testabilidade:** a lógica é testada com adaptadores falsos, rapidamente, sem banco nem rede.
- **Troca de tecnologia:** mudar de banco, de fila ou de provedor afeta só um adaptador.
- **Foco no negócio:** o código central expressa a linguagem do domínio.
- **Várias entradas:** o mesmo caso de uso atendido por REST, CLI e mensageria.

## Custos

- Mais interfaces e mapeamento entre modelos (domínio, persistência e API), com código repetitivo.
- Excesso de cerimônia em CRUDs simples, onde o domínio quase não tem regras.
- Exige disciplina para que ninguém "vaze" dependências de framework para dentro.

<Callout type="note" title="Parentes próximos">
Clean Architecture e Onion Architecture compartilham a mesma ideia central: dependências apontam para o domínio. Os nomes mudam, o princípio é o mesmo (inversão de dependência).
</Callout>

## Na entrevista

É um padrão de organização interna de um serviço, não de implantação. Pode ser aplicado dentro de um monolito modular ou de cada microsserviço. Mencione-o para justificar testabilidade e isolamento de integrações externas. Follow-ups: "qual a diferença para camadas tradicionais?" (nas camadas, o domínio costuma depender da camada de dados; aqui a dependência é invertida) e "quando é exagero?" (CRUD simples, protótipos).
