Um pedido foi pago. O serviço de estoque quer saber, o de notas fiscais também, o de fidelidade, o de analytics e, mês que vem, um serviço de antifraude que ainda nem existe. Se o serviço de pagamentos chamar cada um diretamente, ele precisa conhecer todos e muda toda vez que surge um novo interessado. No modelo **publish/subscribe (pub/sub)**, o produtor publica um evento num **tópico** sem saber quem vai ouvir, e cada interessado se **inscreve** e recebe sua própria cópia.

## Fila vs pub/sub

A diferença central é quantos recebem cada mensagem:

```text
Fila (ponto a ponto): cada mensagem vai para UM consumidor
  [Produtor] -> [ fila ] -> Worker A   (msg 1)
                         -> Worker B   (msg 2)

Pub/Sub (fan-out): cada mensagem vai para TODAS as inscrições
  [Pagamentos] -> [ tópico: pagamento.aprovado ] -> Estoque     (msg 1)
                                                  -> Notas       (msg 1)
                                                  -> Fidelidade  (msg 1)
```

Na prática, os dois se combinam: cada inscrição funciona como uma fila própria, e várias instâncias de um mesmo serviço dividem as mensagens daquela inscrição. Assim, todo **serviço** recebe todos os eventos, mas cada evento é processado por uma única **instância** de cada serviço. No Kafka, isso é o **consumer group**; no Google Pub/Sub, a **subscription**; no SNS com SQS, uma fila SQS inscrita no tópico.

## Tipos de pub/sub

| Característica | Pub/sub efêmero | Pub/sub durável |
| --- | --- | --- |
| Exemplo | Redis Pub/Sub | Kafka, Google Pub/Sub, SNS + SQS |
| Assinante offline | Perde as mensagens | Recebe quando voltar |
| Persistência | Não | Sim, com retenção |
| Uso típico | Notificações em tempo real entre servidores, invalidação de cache | Integração entre serviços, eventos de negócio |

Escolher um pub/sub efêmero para eventos de negócio é um erro clássico: um deploy do consumidor e os eventos daquele intervalo somem.

## Filtragem

Assinantes raramente querem tudo. As formas de filtrar:

- **Por tópico:** um tópico por tipo de evento (`pedido.criado`, `pedido.cancelado`).
- **Por padrão de nome:** curingas como `pedido.*` (comum em RabbitMQ com exchanges do tipo topic e em NATS).
- **Por atributos:** o broker filtra por metadados da mensagem (`regiao = 'sul'`), entregando só o que interessa.

## Exemplo de evento

```json
{
  "id": "evt_01HF3K",
  "tipo": "pagamento.aprovado",
  "versao": 2,
  "ocorrido_em": "2026-10-29T14:03:11Z",
  "dados": {"pedido_id": 9001, "valor_centavos": 15980}
}
```

Boas práticas: ID único para deduplicação, tipo e versão do schema, timestamp do fato e dados suficientes para a maioria dos consumidores não precisar chamar o produtor de volta.

## Benefícios

- **Desacoplamento forte:** o produtor não conhece os consumidores; novos assinantes entram sem mudar o produtor.
- **Fan-out barato:** um evento, muitas reações em paralelo.
- **Extensibilidade:** analytics, auditoria e novos produtos se plugam nos eventos existentes.

## Riscos

- **Fluxo invisível:** fica difícil responder "o que acontece quando um pagamento é aprovado?". Tracing distribuído e um catálogo de eventos ajudam.
- **Contratos implícitos:** mudar o formato do evento quebra consumidores que você não conhece. Versione os schemas e mantenha compatibilidade.
- **Consistência eventual:** cada assinante processa no seu tempo; por alguns instantes, o estoque pode não refletir o pagamento.
- **Ordem e duplicatas:** a maioria dos sistemas garante ordem só por partição ou chave e entrega pelo menos uma vez. Consumidores devem ser idempotentes.

<Callout type="note" title="Evento vs comando">
Um evento descreve algo que já aconteceu (pagamento.aprovado) e não espera resposta; quem publica não se importa com quem reage. Um comando pede que algo aconteça (emitir nota) e tem um destinatário. Comandos combinam mais com filas; eventos, com pub/sub.
</Callout>

## Na entrevista

Quando um fato precisa disparar reações em vários serviços, proponha um tópico com uma inscrição por serviço consumidor. Diga se o pub/sub é durável, como funciona o consumer group, como os consumidores lidam com duplicatas e como o schema evolui. Follow-ups comuns: diferença entre fila e tópico, como garantir ordem por pedido (chave de partição) e como um novo serviço processa eventos antigos (retenção e replay).
