A maioria dos sistemas guarda apenas o **estado atual**: a linha da conta bancária diz saldo de 80, mas não conta como chegou lá. No **event sourcing**, você guarda a **sequência de eventos** que produziu o estado, e o estado atual é calculado reaplicando esses eventos. O log de eventos, imutável e só de acréscimo, é a fonte da verdade.

## Exemplo: conta bancária

```text
Estado tradicional:   conta 7 -> saldo = 80

Event sourcing:       1. ContaAberta(conta=7)
                      2. DepositoRealizado(valor=100)
                      3. SaqueRealizado(valor=30)
                      4. TarifaCobrada(valor=10)
                      saldo = 0 + 100 - 30 - 10 = 60
```

(Em produção, cada evento carrega id, versão, data e dados do fato.) Uma correção nunca altera um evento antigo: você acrescenta um novo evento compensatório.

```python
def aplicar(saldo, evento):
    tipo, valor = evento
    if tipo == "Deposito":
        return saldo + valor
    if tipo == "Saque":
        return saldo - valor
    return saldo

eventos = [("Deposito", 100), ("Saque", 30)]
saldo = 0
for e in eventos:
    saldo = aplicar(saldo, e)
print(saldo)   # 70
```

## Como se organiza

- **Event store:** banco append-only, em geral particionado por *agregado* (a entidade, como uma conta), com controle de versão para evitar escritas concorrentes conflitantes (concorrência otimista).
- **Reconstrução:** carregar os eventos do agregado e aplicá-los em ordem.
- **Snapshots:** para agregados com milhares de eventos, guarde periodicamente o estado calculado e reaplique apenas os eventos posteriores.
- **Projeções:** consumidores que constroem visões de leitura a partir dos eventos. Por isso o padrão combina tão bem com CQRS.

## Benefícios

- **Auditoria completa:** você sabe quem fez o quê e quando, de graça.
- **Viagem no tempo:** reconstruir o estado em qualquer momento do passado, depurar bugs reproduzindo eventos.
- **Novas visões a qualquer hora:** criar uma projeção nova relendo todo o histórico.
- **Integração natural** com sistemas orientados a eventos.

## Custos

- **Curva de aprendizado e mudança de mentalidade:** consultas diretas ao estado não existem sem projeções.
- **Evolução de esquema:** eventos antigos permanecem para sempre; é preciso versioná-los e converter ao ler (upcasting).
- **Consistência eventual** nas projeções.
- **Exclusão de dados:** imutabilidade conflita com LGPD e direito ao esquecimento. Soluções incluem criptografar dados pessoais com chave por usuário e descartar a chave.
- **Volume e reprocessamento** podem ser caros sem snapshots.

<Callout type="warning" title="Nem todo sistema precisa disso">
Event sourcing compensa em domínios onde o histórico tem valor próprio: finanças, logística, auditoria, colaboração. Para cadastro simples é complexidade desnecessária. Também não confunda com apenas publicar eventos: aqui os eventos são a própria persistência.
</Callout>

## Na entrevista

Mencione-o quando houver exigência forte de auditoria ou reconstrução de histórico, ligando-o a CQRS: eventos no lado de escrita, projeções no lado de leitura. Follow-ups: "como evitar reaplicar milhões de eventos?" (snapshots), "como mudar o formato de um evento já gravado?" (versionamento e upcasting) e "e se dois comandos chegam ao mesmo tempo para o mesmo agregado?" (versão esperada e retry).
