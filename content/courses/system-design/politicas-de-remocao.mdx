Memória é cara e finita. Quando o cache atinge o limite e chega uma chave nova, alguém precisa sair. A **política de remoção** (eviction policy) decide quem, e uma escolha ruim derruba a taxa de acerto mesmo com o cache cheio de dados.

## O objetivo: prever o futuro com o passado

A política ideal removeria a chave que será usada **mais tarde** no futuro (o algoritmo ótimo de Belady). Como ninguém sabe o futuro, cada política aposta numa heurística baseada no histórico de acessos.

## As políticas principais

### LRU (Least Recently Used)

Remove a chave acessada há mais tempo. Aposta em **localidade temporal**: o que foi usado agora tende a ser usado de novo logo. É o padrão em quase todo lugar porque funciona bem na maioria das cargas e é barato de implementar: um mapa de hash mais uma lista duplamente ligada dão `get` e `put` em O(1).

```python
from collections import OrderedDict

class LRUCache:
    def __init__(self, capacidade):
        self.capacidade = capacidade
        self.itens = OrderedDict()

    def get(self, chave):
        if chave not in self.itens:
            return None
        self.itens.move_to_end(chave)        # vira a mais recente
        return self.itens[chave]

    def put(self, chave, valor):
        self.itens[chave] = valor
        self.itens.move_to_end(chave)
        if len(self.itens) > self.capacidade:
            self.itens.popitem(last=False)   # remove a mais antiga

c = LRUCache(2)
c.put("a", 1); c.put("b", 2); c.get("a"); c.put("c", 3)
print(list(c.itens))  # ['a', 'c'] -> 'b' saiu
```

**Fraqueza:** uma varredura única (um job que lê um milhão de chaves uma vez) expulsa todo o conjunto quente. Isso se chama *cache pollution*.

### LFU (Least Frequently Used)

Remove a chave com menos acessos. Protege itens populares contra varreduras, mas sofre com o passado: algo que foi viral ontem acumula contagem alta e fica ocupando espaço hoje. Versões práticas usam contadores que **decaem** com o tempo. O Redis, por exemplo, implementa LFU aproximado com contadores logarítmicos de 8 bits e decaimento.

### FIFO

Remove a chave inserida há mais tempo, ignorando acessos. É simples e tem pouco overhead, mas pode expulsar justamente a chave mais popular. Variantes modernas como **S3-FIFO** mostram que filas FIFO bem combinadas competem com LRU em caches de grande escala.

### Random

Escolhe uma vítima aleatória. Parece ingênuo, mas não precisa de metadados por chave e tem desempenho razoável quando os acessos são quase uniformes.

### TTL como remoção

Chaves com tempo de vida expiram sozinhas. TTL não substitui uma política de remoção: ele trata **frescor**, enquanto a política trata **espaço**. Você quase sempre usa os dois.

## Políticas híbridas

- **LRU segmentado / 2Q:** uma chave nova entra numa fila de "experimentação" e só sobe para a área protegida se for acessada de novo. Varreduras ficam presas na primeira fila.
- **ARC:** ajusta dinamicamente o espaço entre "recente" e "frequente" conforme a carga.
- **W-TinyLFU** (usado pela biblioteca Caffeine em Java): um pequeno LRU de admissão mais um *sketch* de frequência que decide se a nova chave merece entrar no lugar da vítima.

## Comparando

| Política | Bom para | Ruim para | Custo |
| --- | --- | --- | --- |
| LRU | Localidade temporal comum | Varreduras grandes | Baixo |
| LFU | Itens populares estáveis | Popularidade que muda | Médio |
| FIFO | Simplicidade, alta concorrência | Itens quentes antigos | Muito baixo |
| Random | Acesso uniforme | Cargas enviesadas | Mínimo |
| W-TinyLFU / ARC | Cargas mistas | Implementação própria | Médio |

<Callout type="note" title="LRU aproximado">
Manter uma lista ligada exata exige um lock a cada leitura. Por isso Redis e outros sistemas fazem **amostragem**: pegam algumas chaves aleatórias e removem a mais antiga entre elas. O resultado é muito próximo do LRU real com uma fração do custo.
</Callout>

## Armadilhas

- **Política certa, tamanho errado:** se o conjunto de trabalho não cabe na memória, nenhuma política salva a taxa de acerto. Meça antes.
- **noeviction por engano:** no Redis, a política `noeviction` faz escritas falharem quando a memória enche. É útil se o Redis é banco de dados, péssima se é cache.
- **Objetos de tamanhos muito diferentes:** remover uma chave de 1 MB libera mais espaço que mil chaves pequenas. Algumas políticas consideram o custo por byte.
