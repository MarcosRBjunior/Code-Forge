Autenticação responde "quem é você?". Autorização responde "o que você pode fazer?". Em um sistema com centenas de usuários e dezenas de operações, atribuir permissões uma a uma a cada pessoa é inviável e propenso a erro. O **RBAC** (Role-Based Access Control, controle de acesso baseado em papéis) resolve isso introduzindo um intermediário: permissões são agrupadas em **papéis**, e papéis são atribuídos a usuários.

## O modelo

```text
Usuário  --tem-->  Papel  --concede-->  Permissão  --sobre-->  Recurso

ana      -> editor        -> artigo:criar, artigo:editar
bruno    -> revisor       -> artigo:ler, artigo:aprovar
carla    -> admin         -> tudo, incluindo usuario:gerenciar
```

Quando alguém entra na equipe, você atribui um papel. Quando o papel muda, a mudança vale para todos que o possuem. Quando alguém sai, remove-se o vínculo e o acesso some.

## Implementação simples

```python
PAPEIS = {
    "leitor": {"artigo:ler"},
    "editor": {"artigo:ler", "artigo:criar", "artigo:editar"},
    "admin":  {"artigo:ler", "artigo:criar", "artigo:editar",
               "artigo:apagar", "usuario:gerenciar"},
}

usuarios = {"ana": {"editor"}, "carla": {"admin"}}

def pode(usuario: str, permissao: str) -> bool:
    return any(permissao in PAPEIS[p] for p in usuarios.get(usuario, ()))

assert pode("ana", "artigo:editar")
assert not pode("ana", "artigo:apagar")
```

Em banco de dados, o desenho clássico usa tabelas `usuarios`, `papeis`, `permissoes`, `usuario_papel` e `papel_permissao`. Num serviço web, o papel normalmente vai como claim no token (JWT) ou é consultado a cada requisição, e a verificação ocorre em um middleware ou no gateway.

## Hierarquia de papéis

Papéis podem herdar de outros: `admin` herda de `editor`, que herda de `leitor`. Isso reduz duplicação, mas hierarquias profundas confundem. Documente-as e revise.

## Princípios que acompanham o RBAC

- **Privilégio mínimo:** cada papel tem só o necessário para o trabalho.
- **Separação de funções:** quem cria um pagamento não deve ser quem o aprova.
- **Revisão periódica de acessos:** remova papéis que ficaram sem uso.
- **Auditoria:** registre concessões e usos de permissões sensíveis.
- **Negar por padrão:** o que não foi permitido explicitamente é proibido.

## Limitações e alternativas

| Modelo | Ideia | Quando usar |
| --- | --- | --- |
| RBAC | Permissão pelo papel | Estruturas organizacionais estáveis |
| ABAC | Decide por atributos do usuário, do recurso e do contexto | Regras como "gerente só aprova valores abaixo do limite da sua região" |
| ReBAC | Decide por relações (dono de, membro de) | Compartilhamento estilo Google Drive |
| ACL | Lista de permissões por recurso | Controle fino por objeto |

O RBAC puro sofre de **explosão de papéis** quando as regras dependem de contexto (departamento, região, valor): você acaba criando "editor-sul-ate-1000" e dezenas de variantes. Nesses casos combine RBAC com atributos, ou use um motor de políticas como OPA ou Cedar. Outro limite: RBAC trata bem "o que" mas mal "qual instância". Ana é editora, mas de quais artigos? Para isso, verifique propriedade ou escopo além do papel.

## Nas nuvens e no Kubernetes

IAM da AWS, GCP e Azure, e o RBAC do Kubernetes (Role, ClusterRole, RoleBinding), seguem esse modelo: permissões em papéis, papéis ligados a identidades, com escopo por namespace ou projeto.

<Callout type="note" title="Autorize no servidor, sempre">
Esconder um botão na interface não é controle de acesso. Cada endpoint precisa verificar a permissão no backend, pois qualquer cliente pode chamar a API diretamente.
</Callout>
