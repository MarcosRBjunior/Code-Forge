---

Quase tudo que você usa na internet segue o mesmo desenho: um programa **cliente** pede algo, um programa **servidor** processa e responde. O navegador pede uma página, o app de banco pede o saldo, o jogo pede a posição dos outros jogadores. O modelo cliente-servidor é a base sobre a qual todos os outros padrões de arquitetura se constroem.

## Como funciona

O cliente inicia a comunicação; o servidor fica escutando e atende vários clientes ao mesmo tempo. A conversa segue um protocolo combinado, normalmente HTTP sobre TCP.

```text
Cliente (navegador, app)  --requisição-->  Servidor (aplicação)  --consulta-->  Banco de dados
                          <--resposta---                         <--dados-----
```

O servidor concentra o que precisa ser **confiável e compartilhado**: regras de negócio, dados, autenticação. O cliente cuida de apresentação e interação. Essa divisão traz vantagens importantes:

- **Fonte única de verdade:** os dados vivem no servidor, não em cada dispositivo.
- **Segurança:** validações e permissões ficam num ambiente que você controla.
- **Atualização centralizada:** corrigir um bug na regra de negócio é publicar uma vez no servidor.

## Cliente magro versus cliente gordo

| Aspecto | Cliente magro | Cliente gordo |
| --- | --- | --- |
| Lógica | Quase toda no servidor | Parte relevante no dispositivo |
| Exemplo | Páginas renderizadas no servidor | SPA, app móvel, jogo |
| Funciona offline | Dificilmente | Mais facilmente, com sincronização |
| Atualização | Imediata | Depende de o usuário atualizar |

## Camadas no servidor

Para sistemas maiores, o servidor se divide em camadas, conhecidas como arquitetura em n camadas:

```text
Apresentação (UI)  ->  Aplicação / lógica de negócio  ->  Dados (banco)
```

Cada camada pode rodar em máquinas separadas, o que permite escalar de forma independente: mais servidores de aplicação sem mexer no banco, por exemplo.

## Escalando o servidor

Um único servidor é um ponto único de falha e tem limite de capacidade. As respostas clássicas são colocar um **load balancer** na frente de várias instâncias **sem estado** (stateless), mover sessões para um armazenamento compartilhado (como Redis) e usar cache e CDN para aliviar o servidor de conteúdo repetido.

## Armadilhas

- **Servidor como gargalo:** todo cliente depende dele. Sem redundância, uma queda derruba todos.
- **Latência de rede:** cada interação paga uma viagem de ida e volta. Agrupe chamadas e use cache no cliente.
- **Confiar no cliente:** nunca valide só no cliente; o cliente pode ser adulterado.
- **Acoplamento do contrato:** mudar a API quebra clientes antigos. Versione a API e mantenha compatibilidade.

<Callout type="note" title="Cliente-servidor versus peer-to-peer">
No modelo cliente-servidor os papéis são fixos e assimétricos. No peer-to-peer, cada nó atua como cliente e servidor ao mesmo tempo, tema de outro capítulo.
</Callout>

## Na entrevista

Quase todo desenho começa aqui. Deixe claro quem são os clientes (web, mobile, outros serviços), onde fica a fronteira da API e quais partes são stateless. Follow-ups: "como você escala o servidor?" (load balancer, instâncias stateless, cache), "como lida com muitos clientes lentos?" (timeouts, conexões assíncronas) e "onde ficam as validações?" (sempre no servidor, repetidas no cliente apenas por usabilidade).
