Muitos casos de "tempo real" são, na verdade, de mão única: placar de jogo, cotações, progresso de um processamento, notificações, tokens de uma resposta de IA aparecendo aos poucos. O cliente não precisa mandar nada continuamente, só receber. Para isso, abrir um WebSocket é exagero, e long polling desperdiça uma requisição por mensagem. **Server-Sent Events (SSE)** é um padrão da web em que o servidor mantém uma resposta HTTP aberta e vai escrevendo eventos nela à medida que acontecem.

## Como funciona

O cliente faz um `GET` comum. O servidor responde com `Content-Type: text/event-stream` e não encerra a resposta: cada evento é um bloco de texto terminado por uma linha em branco.

```text
GET /pedidos/9001/eventos HTTP/1.1
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 17
event: status
data: {"status": "separando"}

id: 18
event: status
data: {"status": "enviado"}

: comentário usado como heartbeat

retry: 5000
```

Campos do formato:

| Campo | Função |
| --- | --- |
| `data` | Conteúdo do evento (várias linhas `data` são concatenadas) |
| `event` | Tipo do evento, para o cliente tratar separadamente |
| `id` | Identificador; o browser lembra o último recebido |
| `retry` | Quantos milissegundos esperar antes de reconectar |
| linha iniciada com `:` | Comentário, ignorado; útil como keep-alive |

## No browser

A API `EventSource` cuida da conexão e da **reconexão automática**:

```javascript
const fonte = new EventSource("/pedidos/9001/eventos");

fonte.addEventListener("status", (e) => {
  const dados = JSON.parse(e.data);
  atualizarTela(dados.status);
});

fonte.onerror = () => console.log("conexão caiu, o browser vai reconectar");
```

Ao reconectar, o browser envia o cabeçalho `Last-Event-ID` com o último `id` recebido. Se o servidor guarda um histórico recente de eventos, ele retoma exatamente de onde parou, sem perdas.

```javascript
// peças de apoio do exemplo: o histórico de eventos e o barramento de novos eventos
const historico = { desde: (pedidoId, ultimo) => [{ id: ultimo + 1, json: '{"status":"pago"}' }] };
const barramento = { assinar: async function* (pedidoId) { yield { id: 99, json: '{"status":"enviado"}' }; } };

async function* eventosDoPedido(headers, pedidoId) {
  const ultimo = parseInt(headers["Last-Event-ID"] ?? "0", 10);

  // reenvia o que faltou
  for (const ev of historico.desde(pedidoId, ultimo)) {
    yield `id: ${ev.id}\nevent: status\ndata: ${ev.json}\n\n`;
  }
  // eventos novos
  for await (const ev of barramento.assinar(pedidoId)) {
    yield `id: ${ev.id}\nevent: status\ndata: ${ev.json}\n\n`;
  }
}

(async () => {
  for await (const pedaco of eventosDoPedido({ "Last-Event-ID": "4" }, 7)) {
    console.log(JSON.stringify(pedaco));
  }
})();
```

```typescript
// peças de apoio do exemplo: o histórico de eventos e o barramento de novos eventos
interface Ev { id: number; json: string }
const historico = { desde: (pedidoId: number, ultimo: number): Ev[] => [{ id: ultimo + 1, json: '{"status":"pago"}' }] };

// o barramento entrega os eventos novos por callback (equivale ao "async for" do Python)
const barramento = {
  assinar: (pedidoId: number, aoReceber: (ev: Ev) => void): void => {
    aoReceber({ id: 99, json: '{"status":"enviado"}' });
  },
};

// o "yield" do gerador vira um callback enviar(pedaco)
function eventosDoPedido(headers: { [nome: string]: string }, pedidoId: number, enviar: (pedaco: string) => void): void {
  const ultimo = parseInt(headers["Last-Event-ID"] || "0", 10);

    enviar(`id: ${ev.id}\nevent: status\ndata: ${ev.json}\n\n`);
  }
  // eventos novos
  barramento.assinar(pedidoId, (ev) => {
    enviar(`id: ${ev.id}\nevent: status\ndata: ${ev.json}\n\n`);
  });
}

eventosDoPedido({ "Last-Event-ID": "4" }, 7, (pedaco) => console.log(JSON.stringify(pedaco)));
```

```java
import java.util.*;
import java.util.function.Consumer;

// peças de apoio do exemplo: o histórico de eventos e o barramento de novos eventos
class Ev {
    int id;
    String json;
    Ev(int id, String json) { this.id = id; this.json = json; }
}

static List<Ev> desde(int pedidoId, int ultimo) {
    return Arrays.asList(new Ev(ultimo + 1, "{\"status\":\"pago\"}"));
}

static void assinar(int pedidoId, Consumer<Ev> aoReceber) {
    aoReceber.accept(new Ev(99, "{\"status\":\"enviado\"}"));
}

// o "yield" do gerador vira um callback enviar(pedaco)
static void eventosDoPedido(Map<String, String> headers, int pedidoId, Consumer<String> enviar) {
    int ultimo = Integer.parseInt(headers.getOrDefault("Last-Event-ID", "0"));

    // reenvia o que faltou
    for (Ev ev : desde(pedidoId, ultimo)) {
        enviar.accept("id: " + ev.id + "\nevent: status\ndata: " + ev.json + "\n\n");
    }
    // eventos novos
    assinar(pedidoId, ev -> enviar.accept("id: " + ev.id + "\nevent: status\ndata: " + ev.json + "\n\n"));
}

public static void main(String[] args) {
    Map<String, String> headers = new HashMap<>();
    headers.put("Last-Event-ID", "4");
    eventosDoPedido(headers, 7, pedaco -> System.out.println(pedaco.replace("\n", "\\n")));
}
```

```cpp
#include <functional>
#include <iostream>
#include <map>
#include <string>

using namespace std;

// peças de apoio do exemplo: o histórico de eventos e o barramento de novos eventos
struct Ev {
    int id;
    string json;
};

vector<Ev> desde(int pedidoId, int ultimo) {
    return {{ultimo + 1, "{\"status\":\"pago\"}"}};
}

void assinar(int pedidoId, const function<void(const Ev&)>& aoReceber) {
    aoReceber({99, "{\"status\":\"enviado\"}"});
}

string formatar(const Ev& ev) {
    return "id: " + to_string(ev.id) + "\nevent: status\ndata: " + ev.json + "\n\n";
}

// o "yield" do gerador vira um callback enviar(pedaco)
void eventosDoPedido(const map<string, string>& headers, int pedidoId, const function<void(const string&)>& enviar) {
    auto it = headers.find("Last-Event-ID");
    int ultimo = it != headers.end() ? stoi(it->second) : 0;

    // reenvia o que faltou
    for (const Ev& ev : desde(pedidoId, ultimo)) {
        enviar(formatar(ev));
    }
    // eventos novos
    assinar(pedidoId, [&](const Ev& ev) { enviar(formatar(ev)); });
}

int main() {
    eventosDoPedido({{"Last-Event-ID", "4"}}, 7, [](const string& pedaco) {
        for (char c : pedaco) {
            if (c == '\n') cout << "\\n"; else cout << c;
        }
        cout << endl;
    });
}
```

```csharp
static void EventosDoPedido(Dictionary<string, string> headers, int pedidoId, Action<string> enviar)
```

```go
package main

import (
	"fmt"
	"strconv"
	"strings"
)

// peças de apoio do exemplo: o histórico de eventos e o barramento de novos eventos
type Ev struct {
	id   int
	json string
}

func desde(pedidoID, ultimo int) []Ev {
	return []Ev{{ultimo + 1, `{"status":"pago"}`}}
}

func assinar(pedidoID int, aoReceber func(Ev)) {
	aoReceber(Ev{99, `{"status":"enviado"}`})
}

func formatar(ev Ev) string {
	return fmt.Sprintf("id: %d\nevent: status\ndata: %s\n\n", ev.id, ev.json)
}

// o "yield" do gerador vira um callback enviar(pedaco)
func eventosDoPedido(headers map[string]string, pedidoID int, enviar func(string)) {
	ultimo := 0
	if v, ok := headers["Last-Event-ID"]; ok {
		ultimo, _ = strconv.Atoi(v)
	}

	// reenvia o que faltou
	for _, ev := range desde(pedidoID, ultimo) {
		enviar(formatar(ev))
	}
	// eventos novos
	assinar(pedidoID, func(ev Ev) { enviar(formatar(ev)) })
}

func main() {
	eventosDoPedido(map[string]string{"Last-Event-ID": "4"}, 7, func(pedaco string) {
		fmt.Println(strings.ReplaceAll(pedaco, "\n", "\\n"))
	})
}
```

Assim como no long polling, com várias instâncias é preciso um barramento compartilhado (Redis Pub/Sub, Kafka, NATS) para que o evento gerado em uma instância chegue ao cliente conectado em outra.

## Vantagens

- **É só HTTP:** funciona com autenticação por cookie, proxies, HTTP/2 e ferramentas existentes.
- **Reconexão e retomada embutidas:** com `id` e `Last-Event-ID`, de graça.
- **Simples:** formato de texto, fácil de depurar com `curl -N`.
- **Eficiente:** uma conexão, sem cabeçalhos por mensagem.

## Limitações

- **Só servidor para cliente.** Mensagens do cliente vão por requisições HTTP normais (o que muitas vezes é suficiente).
- **Só texto UTF-8.** Binário precisa ser codificado, por exemplo em Base64.
- **Limite de conexões no HTTP/1.1:** browsers permitem cerca de 6 conexões por domínio; várias abas com SSE esgotam esse limite. Com HTTP/2, as streams são multiplexadas numa única conexão e o problema desaparece.
- **`EventSource` não permite cabeçalhos customizados**, como `Authorization`. Use cookies ou bibliotecas que implementam SSE sobre `fetch`.

<Callout type="warning" title="Proxies que acumulam a resposta">
Alguns proxies reversos fazem buffer da resposta antes de repassá-la, e os eventos chegam todos de uma vez no final. Desative o buffering para essas rotas e envie comentários periódicos para evitar que conexões ociosas sejam encerradas.
</Callout>

## Quando escolher

| Necessidade | Escolha |
| --- | --- |
| Servidor envia atualizações, cliente só lê | SSE |
| Comunicação frequente nos dois sentidos | WebSocket |
| Eventos raros, ambiente muito restritivo | Long polling |
| Streaming de resposta de LLM token a token | SSE (é o que a maioria das APIs usa) |

## Na entrevista

Para feeds ao vivo, notificações, dashboards e acompanhamento de pedidos, SSE costuma ser a resposta mais simples e defensável. Mostre que conhece `Last-Event-ID` para retomada, o barramento entre instâncias e o limite de conexões no HTTP/1.1. Follow-ups comuns: por que não WebSocket, como escalar para milhões de conexões e como autenticar o stream.
