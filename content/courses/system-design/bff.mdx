Seu produto tem um app mobile, um site web e uma TV conectada. A tela de detalhes de um filme no site mostra sinopse completa, elenco, avaliações e recomendações; no celular, em rede 4G, você quer só título, nota e um botão de play; na TV, imagens enormes e navegação por controle remoto. Um API gateway genérico com um único endpoint `/filme/:id` acaba devolvendo **tudo para todos**: o celular baixa dados que não usa (over-fetching), o site precisa de cinco chamadas para montar a página (under-fetching), e cada mudança pedida por um time de frontend vira negociação com o time da API compartilhada.

O padrão **Backend for Frontend (BFF)** resolve isso criando um backend dedicado para cada tipo de experiência de cliente.

## Como fica a arquitetura

```text
[app iOS/Android] --> [BFF mobile] --+
                                     |--> [catálogo]
[site web]        --> [BFF web]    --+--> [avaliações]
                                     |--> [recomendações]
[smart TV]        --> [BFF TV]     --+--> [usuários]
```

Cada BFF:

- Expõe exatamente os endpoints e formatos que aquela interface precisa.
- Agrega e transforma dados de vários microsserviços em uma única resposta.
- Normalmente é **mantido pelo próprio time do frontend**, que passa a evoluir a API no ritmo da interface.

Uma regra prática conhecida: um BFF por **experiência de usuário**, não por plataforma técnica. Se iOS e Android têm telas idênticas, compartilham o mesmo BFF mobile.

## Exemplo: agregação no BFF mobile

```python
import asyncio

async def tela_filme_mobile(filme_id, usuario_id):
    filme, nota = await asyncio.gather(
        catalogo.buscar(filme_id),
        avaliacoes.media(filme_id),
    )
    return {
        "titulo": filme["titulo"],
        "nota": round(nota, 1),
        "poster": filme["imagens"]["pequena"],
        "pode_assistir": filme["licenciado"],
    }
```

O BFF web, para a mesma tela, buscaria também elenco, comentários e recomendações, com imagens em alta resolução. Duas respostas diferentes, cada uma otimizada para quem consome. As chamadas internas acontecem em paralelo e dentro do datacenter, onde a latência é baixa, em vez de o celular fazer várias idas e voltas pela rede móvel.

## BFF e API gateway juntos

Os dois padrões não competem. Uma composição comum:

1. O **gateway** na borda cuida de TLS, autenticação, rate limiting e roteamento por cliente (`api.exemplo.com/mobile/*` vai para o BFF mobile).
2. Cada **BFF** cuida da composição e do formato de dados específicos da interface.
3. Os **microsserviços** de domínio continuam genéricos e reutilizáveis.

## Trade-offs

| Vantagem | Desvantagem |
| --- | --- |
| Respostas sob medida, menos dados trafegados | Mais serviços para implantar e monitorar |
| Times de frontend autônomos | Risco de duplicar lógica entre BFFs |
| Menos idas e voltas para o cliente | Um salto de rede a mais no caminho |
| Mudanças de UI não afetam outros clientes | Tentação de colocar regra de negócio no BFF |

### Armadilhas

- **Duplicação:** se três BFFs calculam "pode assistir" da mesma forma, essa regra pertence a um serviço de domínio, não aos BFFs. O BFF deve fazer composição e apresentação, não decidir regras.
- **Explosão de BFFs:** um BFF para cada pequena variação de tela vira um zoológico. Agrupe por experiência.
- **Falhas parciais:** se o serviço de avaliações cair, o BFF deve degradar com elegância (devolver a tela sem a nota) em vez de falhar inteiro. Use timeouts curtos e valores padrão.

<Callout type="tip" title="E o GraphQL?">
GraphQL resolve parte do mesmo problema deixando o cliente escolher os campos. Muitas empresas usam um servidor GraphQL como uma espécie de BFF unificado. Ainda assim, BFFs separados continuam úteis quando os clientes diferem em autenticação, cache, protocolos ou ritmo de evolução.
</Callout>
