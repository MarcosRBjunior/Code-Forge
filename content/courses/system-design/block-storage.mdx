Bancos de dados, sistemas de arquivos e máquinas virtuais precisam de um disco: algo onde se lê e escreve bytes em posições arbitrárias, com baixa latência. Em nuvem, esse disco é entregue como **block storage**: um volume virtual, exposto pela rede, que o sistema operacional enxerga como um dispositivo de bloco comum (`/dev/sdb`). Exemplos: Amazon EBS, Google Persistent Disk, Azure Managed Disks.

## Como funciona

O volume é dividido em **blocos** de tamanho fixo (tipicamente 4 KB a 64 KB), cada um endereçado por um número. O armazenamento não sabe o que há dentro: não existem arquivos, pastas ou metadados, só blocos. Quem dá sentido a eles é o sistema de arquivos (ext4, XFS, NTFS) ou o próprio banco de dados, que pode gravar direto no dispositivo.

```text
Aplicação / banco
      |
Sistema de arquivos (ext4, XFS)   <- cria arquivos a partir de blocos
      |
Dispositivo de bloco (/dev/sdb)
      |  rede (iSCSI, NVMe over Fabrics)
Cluster de armazenamento: blocos replicados em vários discos
```

Por trás do volume, o provedor replica cada bloco em mais de uma máquina dentro da mesma zona de disponibilidade, então a falha de um disco físico não perde dados. Por isso o volume sobrevive à máquina virtual: você pode desanexá-lo de uma instância e anexá-lo a outra.

## Características importantes

- **Baixa latência e IOPS previsíveis:** é o que um banco transacional precisa. Volumes SSD entregam latência de poucos milissegundos ou menos.
- **Acesso exclusivo:** em geral um volume é anexado a uma instância por vez (alguns permitem multi-attach, mas exigem um sistema de arquivos de cluster).
- **Escopo de zona:** o volume vive numa zona de disponibilidade. Se a zona cai, o volume some junto, a não ser que você replique por conta própria.
- **Snapshots:** cópias incrementais, guardadas em object storage, usadas para backup e para clonar volumes em outra zona ou região.
- **Capacidade e desempenho provisionados:** você escolhe tamanho, IOPS e throughput, e paga por isso mesmo sem usar.

## Block versus arquivo versus objeto

| Aspecto | Block | File | Object |
| --- | --- | --- | --- |
| Unidade | Bloco | Arquivo em hierarquia | Objeto com chave |
| Latência | Menor | Média | Maior |
| Uso típico | Bancos, VMs | Dados compartilhados | Mídia, backups, data lakes |
| Compartilhamento | Um host | Muitos hosts | Muitos, via HTTP |
| Escala | Terabytes por volume | Petabytes | Praticamente ilimitada |

## Armadilhas

- **Ponto único de falha por zona:** um banco em um volume só é tão disponível quanto a zona. Use replicação entre zonas no nível do banco.
- **Gargalo de IOPS:** o disco pode estar longe de cheio e mesmo assim limitar a aplicação. Meça IOPS e latência, não só espaço.
- **Snapshot não é replicação:** ele protege contra perda e corrupção, mas restaurar leva tempo.
- **Custo de ociosidade:** volumes esquecidos após desligar máquinas continuam cobrando.

<Callout type="tip" title="Instance store">
Muitas instâncias têm discos locais (NVMe) mais rápidos que o block storage de rede, mas efêmeros: morrem junto com a máquina. Servem para cache e dados reconstruíveis, não para o único exemplar de dados importantes.
</Callout>

## Na entrevista

Cite block storage quando o assunto for banco de dados em máquinas próprias ou VMs: "o PostgreSQL roda em volumes SSD provisionados, com réplica em outra zona e snapshots diários para object storage". Follow-ups comuns: "por que não guardar imagens num volume?" (acoplado a uma instância, caro, sem acesso HTTP direto: use object storage) e "o que acontece se a zona cair?" (volume indisponível; promova a réplica de outra zona).
