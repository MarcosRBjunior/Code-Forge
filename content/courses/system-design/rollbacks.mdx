Todo deploy pode dar errado. A pergunta que separa um incidente de cinco minutos de um de cinco horas é: quão rápido e com quanta confiança você consegue voltar ao estado anterior? **Rollback** é essa volta, e a **infraestrutura imutável** é o que a torna previsível.

## O problema dos servidores mutáveis

No modelo antigo, você tinha servidores de longa vida e aplicava mudanças neles: `ssh`, `apt upgrade`, copiar um arquivo, editar uma config. Com o tempo, cada máquina vira um floco de neve, com um histórico único de alterações que ninguém consegue reproduzir. Esse fenômeno se chama **configuration drift**. Voltar atrás significa desfazer passos manualmente, e torcer para que nenhum tenha sido esquecido.

## Infraestrutura imutável

A alternativa: **nunca altere um servidor em produção. Substitua-o.**

```text
mutável : servidor-07 (2019) <- patch <- config <- hotfix <- upgrade ... estado desconhecido
imutável: imagem api:v41 -> instâncias  |  imagem api:v42 -> instâncias novas; v41 descartadas
```

- Cada versão vira um **artefato imutável**: imagem de container, AMI, pacote com hash.
- Para mudar qualquer coisa, inclusive um patch de sistema operacional, você constrói um artefato novo e faz deploy dele.
- As instâncias são descartáveis. Nenhuma tem estado que importe; dados vivem em bancos, filas e object storage.
- A infraestrutura em volta (redes, balanceadores, permissões) é descrita como código (Terraform, CloudFormation, Pulumi) e aplicada pelo pipeline.

O ganho direto: **rollback é só fazer deploy do artefato anterior**, que já existe, já foi testado e já rodou em produção. Não há nada a desfazer.

## Como fazer rollback

| Situação | Mecanismo de rollback |
| --- | --- |
| Rolling deploy | Novo rolling com a imagem anterior (`kubectl rollout undo`) |
| Blue-green | Reapontar o roteador para o ambiente antigo |
| Canary | Zerar o peso da versão nova |
| Funcionalidade atrás de flag | Desligar a flag, sem deploy |
| GitOps | `git revert` no repositório de configuração |

Para que isso funcione sob pressão:

1. **Guarde os artefatos antigos.** Políticas de limpeza do registry não podem apagar as últimas versões em produção.
2. **Referencie por digest, não por tag móvel.** `api:latest` muda de significado; `api@sha256:3f9a...` não.
3. **Automatize o gatilho.** Se a taxa de erro passar do limite após o deploy, o pipeline reverte sozinho, sem esperar alguém ser acordado.
4. **Pratique.** Um rollback que nunca foi testado é uma hipótese, não um plano.

## Quando rollback não basta: roll forward

Nem tudo volta atrás com o binário:

- **Migrações destrutivas:** se a v2 removeu uma coluna, a v1 não funciona mais. Por isso as migrações devem ser compatíveis (expandir e contrair).
- **Dados gravados no formato novo:** a v1 precisa tolerá-los.
- **Efeitos externos:** e-mails enviados, cobranças feitas e mensagens publicadas para outros sistemas não voltam.
- **Contratos já consumidos:** se outro time já começou a usar o campo novo da sua API, removê-lo quebra o cliente dele.

Nesses casos, a saída é **roll forward**: corrigir rapidamente e fazer um novo deploy. A regra prática é preferir rollback quando ele é seguro (é mais rápido e não exige diagnóstico) e só partir para roll forward quando voltar causaria mais dano.

<Callout type="tip" title="Mitigar primeiro, investigar depois">
Durante um incidente após deploy, o objetivo inicial é restaurar o serviço, não entender a causa. Faça rollback assim que houver suspeita razoável de que o deploy é o culpado. A análise acontece depois, com calma e com o serviço de pé.
</Callout>

## Pets vs cattle

Uma analogia popular resume a mudança de mentalidade. **Pets** têm nome, recebem cuidado individual e, quando adoecem, são tratados. **Cattle** (gado) são numerados e substituíveis; se um adoece, é trocado. Servidores imutáveis são cattle. Isso combina com autoscaling (instâncias nascem e morrem o tempo todo), com recuperação automática (instância com problema é simplesmente recriada) e com segurança (não há acesso `ssh` rotineiro a produção, o que reduz superfície de ataque e mudanças não rastreadas).

## Na entrevista

Mencione que os serviços são construídos como imagens imutáveis, promovidas entre ambientes, e que o rollback é automático por métricas. Mostre que sabe as limitações: dados e migrações exigem compatibilidade, e efeitos externos não voltam. Follow-ups: como reverter uma migração que já rodou, quando preferir roll forward e como garantir que a versão anterior ainda está disponível.
