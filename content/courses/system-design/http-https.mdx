HTTP é o protocolo de aplicação que move a web e a maioria das APIs. Ele define como um cliente pede um recurso e como o servidor responde. HTTPS é o mesmo HTTP transportado dentro de uma conexão TLS, que garante sigilo, integridade e autenticidade do servidor.

## O modelo de requisição e resposta

Toda interação é um par: o cliente envia uma requisição, o servidor devolve uma resposta. O HTTP é **sem estado**: cada requisição carrega tudo o que o servidor precisa saber; a continuidade entre requisições vem de cookies, tokens ou identificadores.

```text
GET /pedidos/981 HTTP/1.1
Host: api.loja.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60

{"id": 981, "status": "enviado"}
```

### Métodos

| Método | Uso | Seguro | Idempotente |
| --- | --- | --- | --- |
| GET | ler um recurso | sim | sim |
| POST | criar ou disparar uma ação | não | não |
| PUT | substituir um recurso inteiro | não | sim |
| PATCH | alterar parte de um recurso | não | não necessariamente |
| DELETE | remover | não | sim |

"Seguro" significa que não altera estado no servidor. "Idempotente" significa que repetir tem o mesmo efeito que executar uma vez, o que torna retries automáticos seguros.

### Códigos de status

- **2xx sucesso:** 200 OK, 201 Created, 204 No Content.
- **3xx redirecionamento:** 301 permanente, 302/307 temporário, 304 Not Modified (use a cópia em cache).
- **4xx erro do cliente:** 400 requisição inválida, 401 não autenticado, 403 sem permissão, 404 não encontrado, 409 conflito, 429 limite de taxa excedido.
- **5xx erro do servidor:** 500 erro interno, 502 resposta inválida do upstream, 503 indisponível, 504 timeout do upstream.

A distinção entre 4xx e 5xx importa para retries e alertas: retentar um 400 é inútil; um 503 pode ser retentado com backoff.

### Cabeçalhos importantes para design

- `Cache-Control`, `ETag`, `Last-Modified`: controlam cache em navegadores, proxies e CDNs.
- `Content-Encoding: gzip` ou `br`: compressão.
- `Connection` / keep-alive: reutilização da conexão TCP.
- `Idempotency-Key` (convenção comum, não padrão): permite que POSTs sejam retentados com segurança.

## Evolução das versões

| Versão | Transporte | Novidade principal |
| --- | --- | --- |
| HTTP/1.1 | TCP | conexões persistentes; uma requisição por vez por conexão |
| HTTP/2 | TCP | multiplexação de vários fluxos em uma conexão, cabeçalhos comprimidos, formato binário |
| HTTP/3 | QUIC sobre UDP | fluxos independentes sem head-of-line blocking no transporte, handshake mais rápido |

No HTTP/1.1, navegadores abriam várias conexões em paralelo para contornar o limite de uma requisição por vez. O HTTP/2 resolve isso no nível da aplicação, mas uma perda de pacote no TCP ainda trava todos os fluxos; o HTTP/3 elimina esse problema.

## HTTPS e TLS

Sem TLS, qualquer um no caminho (Wi-Fi público, provedor, roteador comprometido) pode ler e alterar o tráfego. O TLS fornece:

- **Confidencialidade:** os dados são cifrados com chaves simétricas negociadas no handshake.
- **Integridade:** alterações em trânsito são detectadas.
- **Autenticação:** o servidor apresenta um certificado assinado por uma autoridade certificadora confiável, provando que é dono do domínio.

No handshake do TLS 1.3, cliente e servidor trocam parâmetros de chave (geralmente ECDHE), o servidor prova sua identidade com o certificado e ambos derivam as chaves de sessão, tudo em uma ida e volta. O resto da conexão usa criptografia simétrica, que é barata.

### Onde terminar o TLS

Em arquiteturas com load balancer, o TLS costuma ser **terminado** no balanceador: ele decifra, inspeciona e roteia o HTTP, e encaminha aos backends. Entre o balanceador e os backends, você pode usar HTTP simples numa rede privada ou cifrar de novo (re-encryption / mTLS) quando a política de segurança exige criptografia de ponta a ponta.
