Em muitas aplicações, os dados são lidos e gravados como uma unidade: um perfil com suas preferências e endereços, um artigo com seus blocos de conteúdo, um pedido com seus itens. No relacional, essa unidade fica espalhada por várias tabelas e precisa ser remontada com joins a cada leitura. Um **banco de documentos** guarda a unidade inteira junta, num documento JSON (ou BSON), e a devolve em um único acesso.

## O modelo

- **Documento:** objeto aninhado com campos, listas e subdocumentos. Cada um tem um identificador único.
- **Coleção:** conjunto de documentos, geralmente de um mesmo tipo, mas sem schema imposto pelo banco (embora você possa validar).
- **Índices:** em qualquer campo, inclusive aninhado ou dentro de listas.

```json
{
  "_id": "usr_8f2a",
  "nome": "Bruno",
  "email": "bruno@exemplo.com",
  "preferencias": { "tema": "escuro", "idioma": "pt-BR" },
  "enderecos": [
    { "tipo": "casa", "cidade": "Curitiba", "cep": "80000-000" },
    { "tipo": "trabalho", "cidade": "Curitiba", "cep": "80010-000" }
  ],
  "plano": "pro"
}
```

Exemplos: MongoDB, Couchbase, Firestore, Amazon DocumentDB. PostgreSQL com `jsonb` também cobre muitos desses usos.

## Embutir ou referenciar

A decisão central de modelagem em documentos é essa:

**Embuta** quando os dados filhos:

- são lidos quase sempre junto com o pai;
- pertencem só àquele pai;
- têm quantidade limitada (endereços de um usuário, itens de um pedido).

**Referencie** (guarde só o ID) quando:

- os dados são compartilhados entre muitos pais (o autor de mil artigos);
- crescem sem limite (comentários de um post viral);
- são atualizados independentemente e com frequência.

```javascript
// Embutido: um acesso traz o pedido completo
db.pedidos.findOne({ _id: 1001 })

// Referenciado: comentários em coleção própria, indexada por post
db.comentarios.createIndex({ post_id: 1, criado_em: -1 })
db.comentarios.find({ post_id: "p_77" }).sort({ criado_em: -1 }).limit(20)
```

O MongoDB limita um documento a 16 MB, mas o limite prático é bem menor: documentos grandes são lidos e reescritos inteiros, desperdiçando rede e memória.

## Pontos fortes

- **Leitura de agregados em um acesso**, sem joins.
- **Schema flexível:** adicionar um campo não exige migração bloqueante. Útil quando registros variam (produtos de categorias diferentes com atributos diferentes).
- **Mapeamento natural com objetos** da aplicação.
- **Escala horizontal nativa:** sharding por uma chave do documento.

## Pontos fracos

- **Relações muitos-para-muitos** ficam desajeitadas; joins (`$lookup`) existem, mas são mais caros e limitados que no relacional, e em geral não cruzam shards de forma eficiente.
- **Dados duplicados** precisam ser mantidos coerentes pela aplicação.
- **Schema implícito:** sem disciplina, a coleção acumula dez formatos diferentes do mesmo documento.
- **Transações multi-documento** existem no MongoDB, mas custam mais; o modelo funciona melhor quando cada operação atômica cabe em um documento, já que escritas num único documento são atômicas.

## Sharding

Num cluster, a **shard key** decide em qual partição cada documento vive. Ela é a decisão mais importante:

| Shard key | Resultado |
| --- | --- |
| `usuario_id` com hash | Distribuição uniforme; consultas por usuário vão a um shard |
| `criado_em` crescente | Todas as inserções no mesmo shard (hot spot) |
| `pais` | Poucos valores, shards desbalanceados (Brasil gigante, Uruguai pequeno) |

Consultas que não incluem a shard key viram **scatter-gather**: são enviadas a todos os shards, e a latência passa a ser a do shard mais lento.

<Callout type="warning" title="Schema flexível não é ausência de schema">
Use validação de schema no banco (JSON Schema no MongoDB) ou na camada de acesso, e versione documentos com um campo como `schema_version`. Isso permite migrar formatos aos poucos, lendo os dois e gravando no novo.
</Callout>

## Na entrevista

Escolha documentos quando o acesso é por agregado e o formato varia: catálogos com atributos heterogêneos, perfis, CMS, configurações. Explique a decisão de embutir ou referenciar e escolha a shard key a partir da consulta principal. Follow-ups: "e se um post tiver um milhão de comentários?" (referenciar, coleção separada), "como garantir unicidade de e-mail com sharding?" (índice único precisa incluir a shard key, ou uma coleção auxiliar indexada por e-mail).
