Toda informação que atravessa a rede precisa virar uma sequência de bytes e depois voltar a ser objeto do outro lado. Esse processo se chama **serialização** (e desserialização). O formato escolhido afeta o tamanho do payload, o custo de CPU para codificar e decodificar, a facilidade de depurar e, principalmente, a capacidade de **evoluir o contrato** sem quebrar quem já está em produção.

## Duas famílias

**Formatos textuais** (JSON, XML, CSV, YAML) são legíveis por humanos. Você abre no terminal e entende. O preço é tamanho maior e parsing mais lento, já que números viram texto e nomes de campos se repetem em cada registro.

**Formatos binários** (Protocol Buffers, Avro, MessagePack, Thrift, CBOR) são compactos e rápidos. Muitos dependem de um **schema** que define tipos e identificadores de campo. Não dá para ler com `cat`, mas ferramentas decodificam com o schema em mãos.

## Os mais comuns

| Formato | Tipo | Schema | Onde aparece |
| --- | --- | --- | --- |
| JSON | Texto | Opcional (JSON Schema) | APIs REST, configs, browsers |
| XML | Texto | Opcional (XSD) | SOAP, integrações legadas, documentos |
| CSV | Texto | Não | Exportação de planilhas e dados tabulares |
| Protocol Buffers | Binário | Obrigatório (`.proto`) | gRPC, comunicação interna |
| Avro | Binário | Obrigatório (JSON) | Kafka, pipelines de dados, Hadoop |
| MessagePack | Binário | Não | Substituto binário direto de JSON |
| Parquet | Binário colunar | Embutido | Data lakes e análise |

## Comparando tamanho

O mesmo registro em JSON e em Protobuf:

```json
{"id": 150, "nome": "Ana", "ativo": true}
```

```text
message Usuario {
  int32 id = 1;
  string nome = 2;
  bool ativo = 3;
}

Bytes em Protobuf (hex):
08 96 01 12 03 41 6E 61 18 01
```

O JSON sem espaços tem 36 bytes; o Protobuf, 10. A diferença vem de dois fatos: o Protobuf não transmite nomes de campos, só o **número do campo** e o tipo de codificação, e os inteiros usam **varint**, em que números pequenos ocupam poucos bytes. Em milhões de mensagens por segundo, essa economia vira banda e CPU.

## Evolução de schema

O ponto mais importante na escolha de formato não é velocidade, é **compatibilidade**:

- **Compatibilidade retroativa (backward):** código novo consegue ler dados antigos.
- **Compatibilidade progressiva (forward):** código antigo consegue ler dados novos, ignorando o que não conhece.

Regras práticas no Protobuf: nunca reutilize o número de um campo removido (marque-o como `reserved`), adicione campos novos com números novos e não mude o tipo de um campo existente. No Avro, o leitor resolve diferenças entre o schema de escrita e o de leitura, e novos campos precisam de valor padrão. No JSON, a disciplina fica por sua conta: clientes devem ignorar campos desconhecidos e o servidor não deve remover campos sem uma nova versão.

<Callout type="note" title="Schema registry">
Em arquiteturas com Kafka é comum usar um registro de schemas central. O produtor registra a versão do schema, a mensagem carrega só o ID dela, e o registro recusa versões que quebrem a regra de compatibilidade configurada.
</Callout>

## Armadilhas

- **Números grandes em JSON:** a especificação não limita precisão, mas JavaScript representa números como double, perdendo precisão acima de 2 elevado a 53. IDs de 64 bits devem trafegar como string.
- **Datas sem padrão:** use ISO 8601 com fuso (`2026-10-29T14:00:00Z`) ou epoch explícito, nunca formatos locais.
- **Dinheiro em ponto flutuante:** use inteiros em centavos ou decimal em string.
- **Encoding de texto:** padronize UTF-8.
- **Desserialização insegura:** formatos que reconstroem objetos arbitrários (como o `pickle` do Python ou serialização nativa do Java) com dados não confiáveis permitem execução remota de código.

## Como escolher

Para APIs públicas e browsers, JSON é o padrão: universal e fácil de depurar. Para tráfego interno intenso e contratos fortes, Protobuf. Para eventos em streaming com evolução controlada, Avro ou Protobuf com schema registry. Para análise de grandes volumes, formatos colunares como Parquet. E sempre habilite compressão HTTP (gzip ou brotli) em respostas textuais grandes, o que reduz boa parte da diferença de tamanho.

## Na entrevista

Ao propor gRPC ou Kafka, mencione o formato e por quê. Se perguntarem sobre performance, fale de tamanho do payload e custo de parsing. Se perguntarem sobre manutenção, fale de evolução de schema e compatibilidade nos dois sentidos, que é o que separa uma resposta júnior de uma sênior.
