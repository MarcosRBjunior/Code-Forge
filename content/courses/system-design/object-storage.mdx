Fotos, vídeos, backups, logs e arquivos de data lake têm algo em comum: são **grandes, escritos uma vez e lidos inteiros**. Não precisam de edição no meio do arquivo nem de baixa latência de disco. O **object storage** (Amazon S3, Google Cloud Storage, Azure Blob, MinIO) foi feito para isso: guarda bilhões de objetos, com durabilidade altíssima e custo baixo, acessados por HTTP.

## O modelo

Não há hierarquia real de pastas. O modelo tem três conceitos:

- **Bucket:** um contêiner de nível superior, com nome único e política de acesso.
- **Objeto:** os bytes do arquivo mais metadados (tipo de conteúdo, tags, datas).
- **Chave:** o identificador dentro do bucket, como `fotos/2026/10/gato.jpg`. As barras são só parte do nome; o console as exibe como pastas por conveniência.

```python
import boto3

s3 = boto3.client("s3")
s3.put_object(Bucket="meu-app-uploads", Key="avatares/42.png", Body=dados)
resp = s3.get_object(Bucket="meu-app-uploads", Key="avatares/42.png")
```

Objetos são **imutáveis**: para alterar, você grava uma nova versão inteira. Não existe "editar o byte 1000". Com versionamento ligado, versões antigas são preservadas, o que protege contra exclusões acidentais.

## Por que escala tanto

Por dentro, há um serviço de metadados que mapeia chave para localização, e uma camada de dados que armazena os objetos replicados ou codificados com erasure coding. Como não há semântica de arquivo POSIX (sem rename atômico, sem locks, sem escrita parcial), o sistema pode particionar por chave e crescer horizontalmente sem coordenação pesada.

A durabilidade anunciada, como "onze noves" (99,999999999%), vem de replicação ou erasure coding entre várias zonas. Cuidado: durabilidade não é disponibilidade. Os dados podem estar seguros e o serviço indisponível por alguns minutos.

## Recursos que você vai citar

- **URLs pré-assinadas:** o cliente envia ou baixa direto do bucket com um link temporário, sem passar pelo seu servidor.
- **Multipart upload:** arquivos grandes são enviados em partes paralelas e remontados.
- **Classes de armazenamento e lifecycle:** dados quentes em classe padrão, frios em classes baratas, arquivados depois de N dias, expirados depois de M.
- **Eventos:** notificar uma fila ou função quando um objeto chega (gerar miniaturas, indexar).
- **CDN na frente:** serve o conteúdo próximo do usuário e alivia o bucket.

## Trade-offs

| Ponto forte | Limitação |
| --- | --- |
| Durabilidade e custo por GB | Latência maior que disco (dezenas de ms) |
| Escala praticamente ilimitada | Sem edição parcial nem rename atômico |
| Acesso HTTP universal | Listagem de grandes prefixos é lenta |
| Separa armazenamento de computação | Custo de requisições merece atenção |

<Callout type="warning" title="Não use como banco de dados">
Guardar metadados consultáveis (dono, data, tags de busca) dentro do bucket obriga a listar e abrir objetos. Mantenha o índice num banco e deixe no object storage só os bytes, referenciados por chave.
</Callout>

## Padrão clássico de upload

```text
1. Cliente pede ao seu backend: quero enviar avatar.png
2. Backend valida e devolve uma URL pré-assinada (expira em 5 min)
3. Cliente envia o arquivo direto ao bucket
4. Bucket dispara evento -> função gera miniaturas
5. Backend grava no banco: usuario 42 -> chave avatares/42.png
```

O servidor da aplicação nunca carrega os bytes, o que poupa banda e CPU.

## Na entrevista
