Imagine um time de vinte pessoas que junta o trabalho de todo mundo uma vez por mês. O merge leva dias, os conflitos são enormes e ninguém sabe qual das trezentas mudanças quebrou o login. **CI/CD** ataca esse problema encurtando o ciclo: integrar pouco e sempre, verificar tudo automaticamente e levar o resultado a produção por um caminho repetível.

## As três siglas

- **Integração contínua (CI):** cada push para o repositório dispara build e testes automáticos. Mudanças pequenas são integradas ao ramo principal várias vezes por dia. O objetivo é que o `main` esteja sempre verde.
- **Entrega contínua (Continuous Delivery):** todo commit que passa pelo pipeline gera um artefato **pronto para produção**. Ir para produção é um clique, uma decisão humana.
- **Deploy contínuo (Continuous Deployment):** nem o clique existe. Passou em tudo, vai para produção sozinho.

A diferença entre as duas últimas é só o portão manual final. Ambas exigem a mesma disciplina técnica.

## Anatomia de um pipeline

```text
push -> [lint + build] -> [testes unitários] -> [imagem/artefato] -> [testes de integração]
     -> [scan de segurança] -> deploy staging -> [smoke / e2e] -> deploy produção (canary)
     -> [verificação de métricas] -> 100%
```

Princípios que tornam o pipeline confiável:

1. **Build uma vez, promova o mesmo artefato.** A imagem testada em staging, identificada pelo digest, é exatamente a que vai para produção. Recompilar por ambiente abre espaço para diferenças.
2. **Falhe rápido.** Coloque as etapas baratas e com maior chance de falha primeiro (lint, unitários). Feedback em menos de dez minutos muda o comportamento do time.
3. **Configuração fora do artefato.** O mesmo binário recebe variáveis de ambiente ou config diferente em cada ambiente.
4. **Tudo versionado.** A definição do pipeline e a infraestrutura vivem no repositório, revisadas como código.
5. **Pipeline determinístico.** Testes intermitentes (flaky) destroem a confiança; quarentene e corrija em vez de apertar "rodar de novo".

Um exemplo em YAML no estilo do GitHub Actions:

```yaml
name: ci
on: [push]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint
      - run: npm test -- --coverage
      - run: docker build -t registry.exemplo.com/api:${{ github.sha }} .
      - run: docker push registry.exemplo.com/api:${{ github.sha }}
```

Note a tag com o SHA do commit: cada artefato é rastreável até o código que o gerou.

## Trunk-based development

CI de verdade combina com ramos de vida curta. No **trunk-based development**, branches duram horas ou um ou dois dias e voltam ao `main` rapidamente. Funcionalidades incompletas entram desligadas por feature flags. Branches longos (semanas) contradizem a ideia de integração contínua, mesmo que exista um servidor de CI rodando testes neles.

## Push vs GitOps

No modelo **push**, o próprio pipeline executa o deploy com credenciais de produção. No **GitOps**, o pipeline apenas atualiza um repositório de configuração (por exemplo, a tag da imagem num manifesto), e um agente dentro do cluster, como Argo CD ou Flux, puxa e aplica o estado desejado. Vantagens do GitOps: o Git vira fonte da verdade, há trilha de auditoria natural, o rollback é um `git revert` e o CI não precisa de credenciais do cluster.

<Callout type="tip" title="Métricas de entrega">
As métricas DORA medem a saúde do processo: frequência de deploy, lead time da mudança (commit até produção), taxa de falha de mudanças e tempo para restaurar o serviço. Times de alto desempenho melhoram velocidade e estabilidade juntas, não uma às custas da outra.
</Callout>

## Armadilhas

- **Pipeline lento:** com 50 minutos de espera, as pessoas acumulam mudanças e o lote cresce. Paralelize e use cache de dependências.
- **Staging que não se parece com produção:** testes passam lá e falham aqui. Use os mesmos manifestos, mudando só escala e dados.
- **Segredos no log do CI:** mascare variáveis e use credenciais de curta duração (por exemplo, OIDC entre CI e nuvem).
- **Sem verificação pós-deploy:** o pipeline termina verde, mas a taxa de erro em produção subiu. Integre métricas ao último estágio.

## Na entrevista

CI/CD raramente é o foco de uma entrevista de system design, mas aparece em perguntas sobre operação: "como esse sistema evolui com segurança?". Responda com pipeline automatizado, artefato imutável promovido entre ambientes, deploy progressivo e rollback automático por métricas. Follow-ups: como lidar com migrações no pipeline e como evitar que um teste flaky bloqueie todos os deploys.
