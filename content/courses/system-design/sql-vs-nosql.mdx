"SQL ou NoSQL?" parece uma escolha binária, mas esconde várias decisões diferentes: como você modela os dados, que garantias precisa, como vai escalar e que consultas vai fazer. Entender essas decisões separadamente evita respostas de torcida.

## O que cada termo realmente significa

**SQL** aqui quer dizer bancos **relacionais**: dados em tabelas com schema definido, relações por chaves estrangeiras, joins, transações ACID e uma linguagem declarativa poderosa. Você descreve **o que** quer e o otimizador decide **como** buscar.

**NoSQL** é um guarda-chuva para tudo que não é relacional: documentos, chave-valor, wide-column, grafos. Esses bancos surgiram, em boa parte, para resolver dois problemas: escalar escrita além de uma máquina e dar flexibilidade de schema. Eles não têm uma característica única em comum.

## As diferenças que importam

| Aspecto | Relacional | NoSQL (típico) |
| --- | --- | --- |
| Schema | Definido no banco, validado em toda escrita | Flexível; validado pela aplicação (schema-on-read) |
| Modelagem | Normalizada; você modela as **entidades** | Desnormalizada; você modela as **consultas** |
| Joins | Nativos e eficientes | Raros ou ausentes; dados aninhados ou duplicados |
| Transações | Multi-linha e multi-tabela | Frequentemente por documento ou por partição; alguns oferecem mais |
| Escala de escrita | Vertical, depois sharding manual ou extensões | Particionamento nativo entre nós |
| Consultas ad hoc | Excelentes | Limitadas ao que a chave e os índices permitem |
| Consistência | Forte no primário | Configurável; muitas vezes eventual por padrão |

## Um exemplo: o mesmo pedido, dois modelos

Relacional, normalizado:

```sql
CREATE TABLE clientes (id BIGINT PRIMARY KEY, nome TEXT);
CREATE TABLE pedidos  (id BIGINT PRIMARY KEY, cliente_id BIGINT REFERENCES clientes(id), criado_em TIMESTAMPTZ);
CREATE TABLE itens    (pedido_id BIGINT REFERENCES pedidos(id), sku TEXT, qtd INT, preco NUMERIC(10,2));

SELECT p.id, c.nome, SUM(i.qtd * i.preco) AS total
FROM pedidos p JOIN clientes c ON c.id = p.cliente_id
JOIN itens i ON i.pedido_id = p.id
WHERE p.id = 1001
GROUP BY p.id, c.nome;
```

Documento, desnormalizado:

```json
{
  "_id": 1001,
  "cliente": { "id": 7, "nome": "Ana" },
  "criado_em": "2026-10-01T14:02:00Z",
  "itens": [
    { "sku": "TEN-42", "qtd": 1, "preco": 299.90 },
    { "sku": "MEI-01", "qtd": 3, "preco": 19.90 }
  ]
}
```

O documento é lido em um único acesso, sem join. Mas se Ana mudar de nome, você decide se atualiza todos os pedidos dela ou se aceita o nome antigo (que, para um pedido, até faz sentido como registro histórico). E "quanto vendemos do SKU TEN-42 no mês?" fica mais difícil sem um índice ou pipeline de agregação.

## Mitos comuns

- **"NoSQL não tem schema."** Tem, só que implícito no código. Mudanças de formato ainda exigem migração, só que espalhada pela aplicação.
- **"SQL não escala."** Bancos relacionais aguentam muito mais do que se imagina com índices, réplicas de leitura e cache. E existem bancos SQL distribuídos (CockroachDB, Spanner, YugabyteDB, Vitess sobre MySQL).
- **"NoSQL não tem transações."** MongoDB tem transações multi-documento; DynamoDB tem transações limitadas. O ponto é custo e alcance, não ausência.

<Callout type="note" title="A linha está borrando">
PostgreSQL guarda e indexa JSON (`jsonb`); MongoDB tem joins via `$lookup` e transações; bancos NewSQL oferecem SQL com particionamento automático. Escolha por requisitos concretos, não pelo rótulo.
</Callout>

## Quando escolher cada um

**Prefira relacional** quando há relações ricas entre entidades, invariantes que cruzam registros (saldo, estoque), consultas ad hoc e relatórios, ou quando o volume cabe num primário com réplicas.

**Prefira NoSQL** quando o acesso é sempre por uma chave conhecida, o volume de escrita exige particionar desde o início, os dados são naturalmente agregados (um perfil com suas preferências) ou o formato varia muito entre registros.

## Na entrevista

Evite "NoSQL porque escala". Diga: "as consultas são por `usuario_id`, o volume é de 500 mil escritas por segundo e não preciso de transações entre usuários, então uso um wide-column particionado por `usuario_id`". Follow-ups: "e se surgir uma consulta por outro campo?" (índice secundário global ou tabela derivada), "como garantir unicidade de e-mail sem transação?".
