title: O que é uma API

Todo sistema não trivial é feito de partes que precisam conversar: o app mobile fala com o backend, o backend fala com o serviço de pagamentos, o serviço de pagamentos fala com o banco do cliente. Se cada parte conhecesse os detalhes internos das outras (tabelas, classes, formato de memória), qualquer mudança quebraria tudo. A **API** (Application Programming Interface) existe para resolver isso: ela é um **contrato** que diz o que pode ser pedido, em que formato, e o que volta como resposta, sem expor como o trabalho é feito por dentro.

## O contrato e a fronteira

Pense na API como a vitrine de um serviço. Quem consome enxerga apenas as operações publicadas; quem implementa fica livre para trocar banco, linguagem ou algoritmo, desde que o contrato continue sendo respeitado. Essa separação traz três ganhos:

- **Encapsulamento:** detalhes internos podem mudar sem afetar consumidores.
- **Desacoplamento de times:** o time do app e o time do backend combinam o contrato e trabalham em paralelo.
- **Reuso:** a mesma API atende web, mobile, parceiros e outros serviços internos.

Um contrato bem definido costuma especificar:

| Elemento | Exemplo |
| --- | --- |
| Operações | criar pedido, listar pedidos, cancelar pedido |
| Formato de entrada | JSON com `itens` e `endereco` |
| Formato de saída | JSON com `id`, `status`, `total` |
| Erros | código 404 se o pedido não existe, 409 se já foi cancelado |
| Regras de uso | autenticação obrigatória, limite de 100 req/min |

## Tipos de API

O termo é amplo. Em system design, quase sempre falamos de APIs de rede, mas vale conhecer o espectro:

- **APIs de biblioteca:** funções e classes que você chama no mesmo processo (a API de coleções do Java, por exemplo).
- **APIs do sistema operacional:** chamadas de sistema como abrir arquivo ou criar socket.
- **APIs de rede (web APIs):** operações expostas via HTTP, gRPC ou outro protocolo para clientes remotos. São o foco deste módulo.

Também é comum classificar APIs de rede pela audiência: **públicas** (qualquer desenvolvedor com uma chave), **de parceiros** (acesso negociado) e **internas** (só entre serviços da empresa). A audiência muda o quanto você precisa se preocupar com compatibilidade, documentação e segurança.

## Exemplo concreto

Um cliente quer saber o status de um pedido. A chamada HTTP e a resposta poderiam ser:

```text
GET /v1/pedidos/8812 HTTP/1.1
Host: api.loja.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{"id": 8812, "status": "enviado", "total": 249.90, "rastreio": "BR123456"}
```

O cliente não sabe se o pedido está no PostgreSQL, num cache ou foi montado a partir de três microsserviços. Ele só sabe que `GET /v1/pedidos/8812` devolve aquele formato.

## Qualidades de uma boa API

- **Previsível:** nomes consistentes, mesmos padrões de paginação e erro em todas as rotas.
- **Mínima:** expõe o necessário. Tudo que é publicado vira compromisso de manutenção.
- **Versionada:** mudanças incompatíveis entram numa nova versão (`/v2`, cabeçalho ou campo), e a antiga é desativada com aviso.
- **Evolutiva:** adicionar um campo opcional não deve quebrar ninguém; remover ou renomear, sim.
- **Documentada:** especificações como OpenAPI ou arquivos `.proto` servem como fonte de verdade e geram clientes automaticamente.
- **Segura e protegida:** autenticação, autorização e rate limiting desde o início, não como remendo.

<Callout type="warning" title="Lei de Hyrum">
Com usuários suficientes, todo comportamento observável da sua API vira dependência de alguém, inclusive a ordem dos campos ou o texto de uma mensagem de erro. Seja explícito sobre o que é garantido e o que não é.
</Callout>

## Armadilhas comuns

- **Vazar o modelo do banco:** expor colunas internas como campos da API amarra o schema do banco ao contrato público.
- **APIs muito tagarelas:** exigir dez chamadas para montar uma tela multiplica a latência, principalmente em redes móveis.
- **Erros genéricos:** responder 200 com `"erro": true` no corpo esconde falhas de proxies, caches e ferramentas de monitoramento.
- **Quebrar compatibilidade sem versão:** renomear um campo em produção derruba clientes que você nem sabia que existiam.

## Na entrevista

Em quase todo problema de design, depois de levantar requisitos, você define a API. Liste as operações principais com método, rota, entrada e saída, por exemplo `POST /v1/urls` retornando a URL encurtada. Isso mostra que você pensa no contrato antes da implementação. Perguntas de follow-up comuns: como versionar sem quebrar clientes, como paginar listas grandes, como tratar retentativas (idempotência) e como proteger a API de abuso.
