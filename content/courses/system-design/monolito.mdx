Um **monolito** é uma aplicação em que toda a funcionalidade, como cadastro, pedidos, pagamentos e notificações, está num único código-base e é implantada como uma única unidade. Um build, um deploy, normalmente um banco de dados. Não é sinônimo de código bagunçado: é uma escolha de empacotamento, e muito sistema bem-sucedido começou (e ainda vive) assim.

## Por que monolitos funcionam bem

```text
+-------------------------------------+
|            Aplicação                |
|  Usuários | Pedidos | Pagamentos    |
|  (chamadas de função, mesma memória)|
+------------------+------------------+
                   |
              Banco de dados
```

- **Simplicidade operacional:** um artefato para monitorar, implantar e depurar.
- **Chamadas locais:** invocar outro módulo é uma chamada de função, sem rede, sem serialização, sem falha parcial.
- **Transações ACID de graça:** várias tabelas na mesma transação, sem sagas.
- **Refatoração fácil:** o compilador e as ferramentas da IDE ajudam a mover código entre módulos.
- **Desenvolvimento inicial rápido:** ideal para times pequenos e produtos que ainda procuram seu formato.

## Onde começa a doer

- **Build e deploy lentos:** qualquer mudança exige testar e publicar tudo.
- **Acoplamento crescente:** sem disciplina, módulos passam a acessar tabelas e classes uns dos outros, e o sistema vira uma "bola de lama".
- **Escala uniforme:** se só o módulo de relatórios é pesado, você replica a aplicação inteira.
- **Falha compartilhada:** um vazamento de memória num módulo derruba todos.
- **Gargalo de equipe:** dezenas de pessoas editando o mesmo código geram conflitos e deploys disputados.
- **Tecnologia única:** trocar de framework é projeto gigantesco.

## O monolito modular

A saída intermediária é manter um deploy único, mas impor **fronteiras fortes entre módulos**: cada módulo expõe uma interface pública, não acessa as tabelas dos outros e comunica-se só por essa interface.

Quando uma fronteira se prova estável e há necessidade real (escala ou autonomia de equipe), esse módulo pode ser extraído como serviço com custo bem menor do que desfazer um emaranhado.

## Monolito versus microsserviços

| Critério | Monolito | Microsserviços |
| --- | --- | --- |
| Complexidade inicial | Baixa | Alta |
| Escala | Do conjunto | Por serviço |
| Consistência | Transações locais | Eventual, sagas |
| Autonomia de times | Limitada | Alta |
| Depuração | Mais direta | Rastreamento distribuído |

<Callout type="tip" title="Comece pelo monolito">
Para um produto novo, um monolito modular costuma ser a melhor aposta. Você não sabe ainda onde estarão as fronteiras certas, e errá-las entre serviços é caro de corrigir.
</Callout>

## Na entrevista

Não trate monolito como anti-padrão. Mostre que você sabe quando ele basta: poucos desenvolvedores, domínio ainda incerto, carga moderada. Se o entrevistador pedir escala, explique a evolução: monolito atrás de load balancer com banco com réplicas, depois extração gradual dos módulos que realmente precisam de escala ou autonomia. Follow-up comum: "como migrar de monolito para microsserviços?" (strangler fig: extrair funcionalidade por funcionalidade, redirecionando tráfego aos poucos).
