**CQRS** (Command Query Responsibility Segregation) separa o modelo que **altera** o estado (comandos) do modelo que o **consulta** (queries). Em vez de uma única estrutura servir para escrever e ler, você tem dois lados, cada um otimizado para sua tarefa.

## O problema

Um modelo único precisa conciliar necessidades opostas. Escritas querem normalização, validação rigorosa e transações. Leituras querem dados já combinados, desnormalizados e rápidos, muitas vezes em formatos diferentes para cada tela (lista, detalhe, relatório). Quando a proporção é de 100 leituras para 1 escrita, forçar o mesmo banco e as mesmas tabelas para ambos limita os dois.

## A ideia

```text
            Comando (CriarPedido)                 Consulta (PedidosDoUsuario)
                    |                                      |
                    v                                      v
           Lado de escrita                          Lado de leitura
        (regras, validação, ACID)              (modelo desnormalizado, rápido)
                    |                                      ^
              Banco de escrita  --- eventos/replicação --> Banco de leitura
                                   (consistência eventual)
```

- **Comando:** expressa uma intenção ("confirmar pedido"), pode ser rejeitado e geralmente não devolve dados, só sucesso ou erro.
- **Consulta:** só lê, sem efeitos colaterais.
- **Sincronização:** o lado de escrita publica eventos ou alterações que atualizam o modelo de leitura, chamado de *projeção* ou *read model*.

## Níveis de aplicação

1. **Mesmo banco, modelos de código separados:** o mais simples; já ganha clareza.
2. **Mesmo banco, views ou tabelas de leitura:** consultas rápidas sem infraestrutura nova.
3. **Bancos separados:** escrita em PostgreSQL, leitura em Elasticsearch ou Redis, sincronizados por eventos. Maior ganho de escala e maior complexidade.

```python
# lado de escrita
def confirmar_pedido(pedido_id):
    pedido = repo.obter(pedido_id)
    pedido.confirmar()                       # regras de negócio
    repo.salvar(pedido)
    publicar("PedidoConfirmado", pedido_id)

# lado de leitura (consumidor do evento)
def projetar(evento):
    resumo = montar_resumo(evento["pedido_id"])
    leitura_db.upsert("resumo_pedidos", resumo)   # já pronto para a tela
```

## Benefícios

- Escala leitura e escrita de forma independente.
- Modelos de leitura sob medida para cada consulta.
- Regras de escrita mais limpas, sem preocupação com formato de exibição.
- Combina bem com arquitetura orientada a eventos e event sourcing.

## Custos e armadilhas

- **Consistência eventual:** logo após o comando, a leitura pode estar desatualizada. O usuário que acabou de criar um item e não o vê na lista estranha. Mitigue lendo do lado de escrita nesse caso, ou atualizando a interface de forma otimista.
- **Mais peças:** projeções, filas, reconstrução de modelos de leitura.
- **Duplicação de dados** e necessidade de lidar com falhas e reprocessamento.
- **Exagero em CRUD simples:** na maioria das aplicações, um modelo só é suficiente.

<Callout type="warning" title="Não é arquitetura global">
Aplique CQRS apenas nas partes do sistema que realmente têm assimetria forte entre leitura e escrita. Um sistema pode ter CQRS num módulo e CRUD simples nos demais.
</Callout>

## Na entrevista

Use quando o tráfego de leitura é muito maior ou exige formatos muito diferentes dos usados na escrita (feed, busca, dashboards). Explique a sincronização e a consistência eventual. Follow-ups: "como evitar o usuário não ver o que acabou de criar?" (read-your-writes, atualização otimista), "CQRS exige event sourcing?" (não; são independentes, embora combinem bem) e "como reconstruir a projeção?" (reprocessando eventos ou a partir da base de escrita).
