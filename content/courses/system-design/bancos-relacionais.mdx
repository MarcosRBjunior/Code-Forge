Bancos relacionais existem desde os anos 1970 e continuam sendo a fonte da verdade da maioria dos sistemas. O motivo não é inércia: o modelo relacional separa **como os dados são guardados** de **como você os consulta**, e isso permite responder a perguntas que ninguém previu quando o schema foi desenhado.

## O modelo

- **Tabela (relação):** conjunto de linhas com as mesmas colunas tipadas.
- **Chave primária:** identifica cada linha de forma única.
- **Chave estrangeira:** referencia a chave primária de outra tabela e garante que a referência existe.
- **Constraints:** `NOT NULL`, `UNIQUE`, `CHECK`, que o banco valida em toda escrita.
- **SQL:** linguagem declarativa. Você descreve o resultado; o **otimizador** escolhe índices, ordem de joins e algoritmos.

## Normalização

Normalizar é organizar as tabelas para que **cada fato seja guardado uma vez só**. Isso evita anomalias: se o endereço do cliente estiver repetido em cada pedido, uma mudança de endereço exige atualizar mil linhas, e esquecer uma deixa dados contraditórios.

```sql
-- Não normalizado: categoria repetida em cada produto
-- produtos(id, nome, categoria_nome, categoria_descricao)

-- Normalizado (3FN)
CREATE TABLE categorias (
  id        SERIAL PRIMARY KEY,
  nome      TEXT NOT NULL UNIQUE,
  descricao TEXT
);
CREATE TABLE produtos (
  id           SERIAL PRIMARY KEY,
  nome         TEXT NOT NULL,
  preco        NUMERIC(10,2) NOT NULL CHECK (preco > 0),
  categoria_id INT NOT NULL REFERENCES categorias(id)
);
```

As formas normais em uma linha cada:

- **1FN:** valores atômicos, sem listas dentro de uma coluna.
- **2FN:** colunas dependem da chave **inteira**, não de parte dela.
- **3FN:** colunas dependem **só** da chave, não de outras colunas não chave.

Em sistemas com muita leitura, você às vezes **desnormaliza** de propósito para evitar joins caros, aceitando o custo de manter as cópias coerentes. Esse tema volta no módulo de escala.

## Joins

O poder do relacional está em combinar tabelas na hora da consulta:

```sql
SELECT c.nome AS categoria, COUNT(*) AS qtd, AVG(p.preco) AS preco_medio
FROM produtos p
JOIN categorias c ON c.id = p.categoria_id
GROUP BY c.nome
ORDER BY qtd DESC;
```

Por baixo, o otimizador escolhe entre **nested loop** (bom quando um lado é pequeno e o outro tem índice), **hash join** (bom para grandes volumes sem ordem) e **merge join** (bom quando os dois lados já estão ordenados).

## Por dentro de um relacional típico

```text
Cliente ──SQL──▶ Parser ──▶ Otimizador ──plano──▶ Executor
                                                     │
                     Buffer pool (páginas em memória) │
                                                     ▼
                   Tabelas e índices (B+ trees)  +  WAL
```

As peças que você já viu se encaixam aqui: índices são B+ trees, transações seguem ACID com MVCC, e o WAL garante durabilidade e alimenta a **replicação** (réplicas aplicam o mesmo log).

## Escalando um relacional

1. **Índices certos e consultas otimizadas.** Resolvem a maioria dos problemas.
2. **Escala vertical.** Máquinas com centenas de GB de RAM vão longe.
3. **Réplicas de leitura.** O primário recebe escritas; réplicas atendem leituras, com algum atraso de replicação.
4. **Cache** na frente das leituras quentes.
5. **Particionamento e sharding.** Dividir dados entre tabelas ou servidores; exige escolher bem a chave e perde joins e transações entre shards.
6. **Bancos SQL distribuídos (NewSQL):** CockroachDB, Spanner, YugabyteDB e TiDB particionam automaticamente e mantêm transações, ao custo de latência maior por consenso.

<Callout type="note" title="PostgreSQL vs MySQL">
Os dois aguentam cargas enormes. PostgreSQL costuma ser escolhido por recursos (tipos ricos, `jsonb`, extensões como PostGIS e pgvector, SQL mais completo). MySQL com InnoDB é muito difundido em escala web e tem ferramentas maduras de sharding, como Vitess. Para uma entrevista, qualquer um é defensável se você justificar.
</Callout>

## Quando o relacional não é a melhor escolha

- Escrita massiva de eventos imutáveis que nunca são atualizados.
- Schema muito variável entre registros.
- Consultas de grafo com muitos saltos ou busca textual por relevância.
- Necessidade de escalar escrita globalmente desde o primeiro dia.

## Na entrevista

Use um relacional quando houver entidades relacionadas e transações. Mostre o schema principal com chaves e índices, e antecipe a escala: "começo com primário e réplicas; se a escrita crescer, faço sharding por `tenant_id`". Follow-ups: "como você evita N+1 consultas?", "o que perde ao fazer sharding?".
