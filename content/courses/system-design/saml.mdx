Uma empresa usa dezenas de ferramentas: CRM, folha de pagamento, wiki, painel de BI. Obrigar cada pessoa a manter uma senha em cada uma é ruim para a experiência e pior para a segurança: o departamento de TI não consegue desligar o acesso de quem saiu de forma centralizada. O **Single Sign-On (SSO)** resolve isso: você autentica uma vez em um provedor corporativo e acessa todas as aplicações. **SAML 2.0** (Security Assertion Markup Language) é um dos padrões mais usados para SSO em ambientes corporativos.

## Papéis

- **Usuário (principal):** quem quer acessar.
- **Provedor de identidade (IdP):** autentica o usuário e emite afirmações. Exemplos: Okta, Microsoft Entra ID, Google Workspace, Keycloak.
- **Provedor de serviço (SP):** a aplicação que confia no IdP e deseja saber quem é o usuário.

## Fluxo iniciado pelo SP (o mais comum)

```text
Usuário          Aplicação (SP)                   IdP
   |  1. acessa /painel   |                         |
   |--------------------->|                         |
   |  2. redireciona com AuthnRequest               |
   |<---------------------|                         |
   |  3. segue o redirect ------------------------->|
   |                      |   4. login (senha + MFA)|
   |  5. página com SAMLResponse assinada (POST)    |
   |<-----------------------------------------------|
   |  6. envia a SAMLResponse ao SP                 |
   |--------------------->|                         |
   |                      | 7. valida assinatura,   |
   |                      |    cria sessão          |
   |  8. acesso liberado  |                         |
   |<---------------------|                         |
```

O navegador é o mensageiro entre SP e IdP; não há chamada direta entre os servidores nesse fluxo (o chamado binding HTTP-Redirect/POST).

## A asserção

O IdP devolve um documento XML assinado digitalmente, contendo:

- **Emissor** e **destinatário** (audience).
- **Sujeito:** identificador do usuário (NameID).
- **Condições de validade:** NotBefore e NotOnOrAfter.
- **Atributos:** e-mail, nome, grupos, útil para mapear papéis (RBAC).
- **Assinatura** do IdP.

```xml
<saml:Assertion>
  <saml:Issuer>https://idp.empresa.com</saml:Issuer>
  <saml:Subject><saml:NameID>ana@empresa.com</saml:NameID></saml:Subject>
  <saml:Conditions NotOnOrAfter="2026-10-30T14:10:00Z">
    <saml:AudienceRestriction>
      <saml:Audience>https://painel.empresa.com</saml:Audience>
    </saml:AudienceRestriction>
  </saml:Conditions>
  <saml:AttributeStatement>
    <saml:Attribute Name="grupos"><saml:AttributeValue>financeiro</saml:AttributeValue></saml:Attribute>
  </saml:AttributeStatement>
</saml:Assertion>
```

A confiança se baseia em metadados trocados antecipadamente: o SP conhece o certificado público do IdP e a URL de login, e o IdP conhece o endereço de retorno (ACS) de cada SP.

## Validações obrigatórias no SP

- Verificar a **assinatura** com o certificado do IdP.
- Conferir **emissor**, **audience** e **prazo de validade**.
- Impedir **replay**, rejeitando asserções com ID já usado.
- Proteger contra **XML signature wrapping**, ataque clássico em que o parser lê um elemento diferente do que foi assinado. Use bibliotecas maduras, nunca parsers caseiros.

## SAML versus OIDC

| Aspecto | SAML 2.0 | OpenID Connect |
| --- | --- | --- |
| Formato | XML | JSON (JWT) |
| Nascimento | Corporativo, web tradicional | Sobre OAuth 2.0, apps modernos e móveis |
| Complexidade | Maior | Menor |
| Uso comum | SSO de aplicações empresariais legadas e SaaS B2B | Login em apps novos, SPAs e mobile |

Novos projetos costumam preferir OIDC, mas SAML permanece exigência frequente de clientes empresariais. Se você vende SaaS B2B, espere pedidos de integração SAML.

## Logout

O logout único (*Single Logout*) é complicado: encerrar a sessão em todos os SPs depende de cada um aderir ao protocolo. Na prática, use sessões curtas e revogação no IdP.

<Callout type="tip" title="Deprovisionamento">
SSO resolve o login, mas contas já criadas nos SPs persistem. Para desligar acessos de verdade, combine com SCIM, que sincroniza criação e remoção de usuários a partir do IdP.
</Callout>

## Na entrevista

Descreva IdP, SP, o redirecionamento do navegador e a asserção assinada. Compare com OIDC e cite os benefícios: senha centralizada, MFA em um só lugar, desligamento rápido. Follow-up: "como o SP confia na asserção?" (assinatura com certificado do IdP, audience e validade).
