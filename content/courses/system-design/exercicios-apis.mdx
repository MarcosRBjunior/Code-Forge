Teste o que você aprendeu sobre estilos de API, idempotência, segurança e controle de tráfego.

<QuizSet>
<Quiz question="Um app mobile chama POST /pagamentos, recebe timeout e tenta de novo. O cliente foi cobrado duas vezes. Qual é a correção mais adequada?" options={["Trocar o método de POST para GET, que o cliente pode repetir sem gerar novas cobranças","Exigir uma chave de idempotência do cliente, reutilizada nas retentativas do pagamento","Aumentar o timeout do cliente para 5 minutos, para a resposta chegar antes de expirar","Desativar as retentativas no load balancer, para a requisição não chegar duas vezes"]} answer={1} explanation="Timeouts acontecem e retentativas são inevitáveis. A chave de idempotência permite ao servidor reconhecer a mesma intenção e devolver o resultado salvo sem cobrar de novo." />
<Quiz question="Qual combinação de método HTTP e propriedade está correta?" options={["POST é idempotente, pois repetir a requisição devolve o mesmo resultado sem efeitos extras","PUT é seguro, pois substituir um recurso não altera o estado guardado no servidor","DELETE é idempotente, mas não é seguro, pois altera o estado do recurso removido","GET é idempotente, mas não é seguro, pois cada leitura modifica o recurso lido"]} answer={2} explanation="DELETE altera o estado (não é seguro), mas repeti-lo deixa o recurso igualmente removido (é idempotente). POST não é idempotente por padrão e PUT não é seguro." />
<Quiz question="Seu app de TV, web e mobile exibem a mesma tela com campos diferentes, e hoje cada um faz cinco chamadas REST. O que tende a ajudar mais?" options={["Uma camada GraphQL agregadora, em que cada cliente pede numa só requisição os campos que usa","Trocar o formato de JSON para XML, que é mais compacto e reduz o tráfego de cada tela do app","Remover a paginação das listagens para que cada tela receba todos os dados de uma vez","Adicionar mais réplicas do banco de dados para atender às cinco chamadas de cada tela"]} answer={0} explanation="GraphQL reduz over-fetching e under-fetching, permitindo que cada cliente obtenha a tela inteira numa requisição. Lembre-se de usar DataLoader e limites de custo." />
<Quiz question="Entre 30 microsserviços internos você quer baixa latência, contratos tipados e streaming. Qual escolha e qual cuidado operacional?" options={["SOAP, cuidando do tamanho dos envelopes XML e da validação dos esquemas WSDL em cada chamada interna","gRPC, cuidando do balanceamento por requisição, já que o HTTP/2 mantém conexões longas e reutilizadas","REST, cuidando do cache em CDN e do versionamento das URLs para clientes de diferentes tipos","Webhooks, cuidando da validação de assinaturas HMAC e das retentativas em cada entrega de evento ao consumidor"]} answer={1} explanation="gRPC oferece Protobuf, HTTP/2 e streaming. Como as conexões são persistentes e multiplexadas, um balanceador de camada 4 pode concentrar tráfego numa réplica." />
<Quiz question="Um endpoint de login sofre tentativas de força bruta. Qual combinação é mais apropriada?" options={["Rate limiting por usuário e por IP com token bucket, respondendo 429 com Retry-After","Retornar 200 com a mensagem de erro no corpo, para não revelar ao atacante que a senha falhou","Aumentar o número de réplicas da API de login para absorver o volume extra de tentativas","Usar JWT com expiração de 30 dias para que o usuário legítimo autentique com menos frequência"]} answer={0} explanation="Limitar tentativas por conta e por origem torna a força bruta impraticável. O 429 com Retry-After informa o cliente de forma padronizada." />
<Quiz question="O time quer emitir JWTs no serviço de autenticação e validá-los em 15 serviços, sem que nenhum deles consiga forjar tokens. Qual configuração?" options={["HS256 com o mesmo segredo compartilhado distribuído para todos os serviços que validam","Assinatura assimétrica, com a chave pública distribuída aos serviços que validam","Tokens sem assinatura, já que a rede interna é considerada confiável pelo time","Guardar o token em texto no banco e consultar a cada requisição de cada serviço"]} answer={1} explanation="Com assinatura assimétrica, só o emissor tem a chave privada. Os demais verificam com a pública e não conseguem assinar tokens novos." />
<Quiz question="Um parceiro quer que seus usuários autorizem o app dele a ler os pedidos deles na sua plataforma. Qual solução?" options={["Pedir ao usuário a senha da plataforma e repassá-la ao parceiro, que acessa os pedidos","OAuth 2.0 Authorization Code com PKCE e escopo pedidos.leitura","OAuth 2.0 Client Credentials com escopo pedidos.leitura, valendo para todos os usuários","Compartilhar com o parceiro uma chave de API administrativa, com acesso a todos os dados"]} answer={1} explanation="Autorização delegada é exatamente o caso do OAuth 2.0. O usuário consente com um escopo limitado e pode revogar o acesso depois, sem expor a senha." />
<Quiz question="Um administrador desativa um funcionário no IdP corporativo. Por que ele ainda consegue usar uma das aplicações por alguns minutos?" options={["O IdP não suporta desativação imediata de usuários que já tenham feito login em alguma aplicação","A aplicação mantém sua própria sessão local, que continua válida até expirar ou ser revogada","O SSO armazena a senha do usuário na aplicação, que continua validando as credenciais antigas","O OpenID Connect não usa assinatura nos tokens, então a aplicação não percebe a mudança"]} answer={1} explanation="No SSO cada aplicação cria sessão local após validar a asserção. Desativar no IdP impede novos logins, mas sessões existentes continuam até expirar, salvo com logout propagado ou SCIM." />
