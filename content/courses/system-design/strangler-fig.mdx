Você herdou um monólito de dez anos, com milhões de linhas, que fatura o dinheiro da empresa todo dia. A tentação é declarar: "vamos reescrever tudo do zero em microsserviços". Reescritas completas, no estilo big bang, têm um histórico ruim: levam anos, o sistema antigo continua mudando enquanto você copia, nada entrega valor até o fim, e o dia da virada concentra todo o risco num único momento.

O padrão **strangler fig** propõe o oposto: substituir o sistema antigo **aos poucos**, funcionalidade por funcionalidade, com o sistema em produção o tempo todo. O nome vem das figueiras estranguladoras, que nascem em cima de uma árvore, descem raízes em volta dela e, ao longo de anos, a substituem por completo, até a árvore original desaparecer e restar só a figueira.

## Como funciona

A peça central é uma **fachada de roteamento** (um proxy, o API gateway ou o load balancer) na frente do monólito. Todo o tráfego passa por ela. À medida que você extrai uma funcionalidade para um serviço novo, muda a regra de roteamento para aquela rota.

```text
Fase 1             Fase 2                       Fase 3
[clientes]         [clientes]                   [clientes]
    |                  |                            |
 [fachada]          [fachada]                    [fachada]
    |               /       \                    /   |   \
[monólito]   [monólito]  [svc catálogo]   [svc A] [svc B] [svc C]
             (resto)                       monólito desligado
```

O ciclo, repetido para cada pedaço:

1. **Escolha uma fatia** bem delimitada, idealmente com valor de negócio e baixo acoplamento (por exemplo, o catálogo de produtos ou as notificações).
2. **Implemente o novo serviço**, com seus próprios dados.
3. **Desvie o tráfego** gradualmente: primeiro 1% das requisições, ou só usuários internos, comparando resultados. Feature flags e canary ajudam.
4. **Remova o código antigo** daquela funcionalidade no monólito.

## A parte difícil: os dados

Mover código é fácil comparado a mover dados. O novo serviço de catálogo precisa da tabela de produtos, que o monólito também usa em vinte joins. Algumas técnicas:

- **Começar lendo do banco antigo:** o serviço novo nasce acessando o mesmo banco e só depois ganha banco próprio. É um estado intermediário aceitável, mas não deve ser o fim.
- **Change data capture (CDC):** replicar alterações das tabelas do monólito para o banco do novo serviço, mantendo os dois sincronizados durante a transição.
- **Escrita dupla com verificação:** gravar nos dois e comparar, com o cuidado de que gravações duplas sem transação podem divergir. Prefira um outbox ou CDC.
- **Camada anticorrupção:** um tradutor entre o modelo legado (nomes estranhos, campos sobrecarregados) e o modelo limpo do novo serviço, para que o legado não contamine o novo domínio.

## Execução em paralelo para validar

Uma técnica poderosa é a **execução sombra**: a fachada manda a requisição para o monólito (cuja resposta vai ao usuário) e, em paralelo, para o novo serviço, cuja resposta é só comparada e registrada. Quando as diferenças chegam perto de zero, você vira a chave com confiança. Só faça isso para operações de leitura ou idempotentes; duplicar uma cobrança "na sombra" é desastre.

## Trade-offs

| Vantagem | Custo |
| --- | --- |
| Entrega valor continuamente | Período longo convivendo com dois sistemas |
| Risco diluído, rollback por rota | Sincronização de dados é trabalhosa |
| Aprendizado a cada extração | Fachada vira peça crítica |
| Pode parar no meio se o negócio mudar | Exige disciplina para remover o código antigo |

<Callout type="warning" title="O estrangulamento que nunca termina">
O risco mais comum é migrar as partes fáceis e deixar o núcleo complicado no monólito para sempre, pagando o custo de dois sistemas indefinidamente. Defina metas de desligamento e meça quanto tráfego ainda passa pelo legado.
</Callout>

## Na entrevista

Quando perguntarem "como você migraria esse monólito para microsserviços?", a resposta esperada é strangler fig: fachada na frente, extração incremental guiada por domínios, migração de dados com CDC, tráfego desviado aos poucos com canary e possibilidade de voltar. Follow-ups comuns: "por onde você começaria?", "como lidar com transações que cruzam o monólito e o serviço novo?", "como saber que o serviço novo está correto?".
