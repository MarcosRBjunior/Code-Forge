REST (Representational State Transfer) é um **estilo arquitetural** descrito por Roy Fielding em 2000, não um protocolo nem um formato. A ideia é aproveitar as propriedades que fizeram a web escalar (cache, intermediários, interface uniforme) para construir APIs. Na prática, "API REST" virou sinônimo de API HTTP organizada em torno de **recursos**, e é o estilo mais comum em APIs públicas.

## As restrições do REST

Fielding definiu restrições; quanto mais delas uma API respeita, mais ela herda os benefícios da web:

- **Cliente-servidor:** interface e armazenamento evoluem separadamente.
- **Stateless:** cada requisição carrega tudo o que o servidor precisa para atendê-la. O servidor não guarda estado de sessão entre chamadas, o que permite que qualquer instância atenda qualquer requisição.
- **Cacheável:** respostas dizem se podem ser guardadas e por quanto tempo.
- **Interface uniforme:** recursos identificados por URI, manipulados por representações (JSON, por exemplo), com mensagens autodescritivas.
- **Sistema em camadas:** o cliente não sabe se fala com o servidor final, um proxy, um load balancer ou uma CDN.
- **Código sob demanda (opcional):** o servidor pode enviar código executável ao cliente.

## Recursos e métodos

Recursos são **substantivos**; os métodos HTTP são os **verbos**:

| Operação | Método e rota | Resposta típica |
| --- | --- | --- |
| Listar pedidos | `GET /pedidos?status=aberto` | 200 com lista |
| Buscar um pedido | `GET /pedidos/42` | 200 ou 404 |
| Criar pedido | `POST /pedidos` | 201 com cabeçalho `Location` |
| Substituir pedido | `PUT /pedidos/42` | 200 ou 204 |
| Atualizar parcialmente | `PATCH /pedidos/42` | 200 |
| Remover | `DELETE /pedidos/42` | 204 |
| Itens de um pedido | `GET /pedidos/42/itens` | 200 |

Ações que não se encaixam em CRUD podem virar sub-recursos: em vez de `POST /cancelarPedido`, use `POST /pedidos/42/cancelamento`, que cria um "cancelamento".

## Códigos de status

Use os códigos para o que eles significam, porque proxies, SDKs e monitoramento dependem deles:

- **2xx sucesso:** 200 OK, 201 Created, 202 Accepted (processamento assíncrono), 204 No Content.
- **3xx redirecionamento:** 301, 302, 304 Not Modified (cache validado).
- **4xx erro do cliente:** 400 requisição malformada, 401 não autenticado, 403 sem permissão, 404 não encontrado, 409 conflito de estado, 422 dados inválidos, 429 limite excedido.
- **5xx erro do servidor:** 500 erro interno, 502 bad gateway, 503 indisponível, 504 timeout no upstream.

Retentar faz sentido em 429, 503 e 504 (respeitando `Retry-After`); não faz em 400 ou 422.

## Exemplo de criação

```text
POST /v1/pedidos HTTP/1.1
Content-Type: application/json
Idempotency-Key: a1b2c3

{"cliente_id": 7, "itens": [{"sku": "CAM-01", "qtd": 2}]}

HTTP/1.1 201 Created
Location: /v1/pedidos/9001
Content-Type: application/json

{"id": 9001, "status": "aberto", "total": 159.80}
```

## Paginação, filtros e cache

Listas grandes precisam de paginação. **Offset** (`?offset=200&limit=50`) é simples, mas fica lento em tabelas grandes e pula ou repete itens quando há inserções. **Cursor** (`?cursor=eyJpZCI6...&limit=50`) aponta para o último item visto, é estável e escala melhor; é o padrão em feeds.

Para cache, use `Cache-Control` (`max-age`, `no-store`, `private`) e validadores: o servidor envia um `ETag`, e o cliente pergunta com `If-None-Match`; se nada mudou, recebe 304 sem corpo. O mesmo `ETag` com `If-Match` implementa **controle de concorrência otimista** em atualizações, devolvendo 412 se alguém alterou o recurso antes.

<Callout type="tip" title="HATEOAS">
A restrição mais ignorada do REST é usar hipermídia: a resposta inclui links para as próximas ações possíveis (por exemplo, o link de cancelamento só aparece se o pedido pode ser cancelado). Poucas APIs seguem isso à risca, mas vale saber o nome numa entrevista.
</Callout>

## Versionamento

As opções mais comuns são versão na URL (`/v1/pedidos`, explícita e fácil de rotear), em cabeçalho (`Accept: application/vnd.loja.v2+json`, URLs limpas) ou por data (`Api-Version: 2026-10-01`). Qualquer que seja a escolha, mudanças aditivas não exigem versão nova; remoções e renomeações exigem.

## Trade-offs

REST é simples, universal e se beneficia de CDNs e caches HTTP. Por outro lado, telas complexas podem exigir várias chamadas (under-fetching) ou receber campos demais (over-fetching), e o JSON textual pesa mais que formatos binários. Esses são exatamente os pontos que GraphQL e gRPC atacam.

## Na entrevista

Desenhe os endpoints com substantivos no plural, métodos corretos, códigos de status adequados e paginação por cursor. Mencione idempotência para `POST` de operações críticas. Follow-ups: diferença entre `PUT` e `PATCH`, quando usar 202, como evitar atualizações perdidas e como versionar.
