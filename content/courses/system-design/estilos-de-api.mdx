Decidir que existe uma API é fácil; decidir **como** ela conversa é onde mora o trade-off. Cada estilo nasce de uma pergunta diferente: o que é mais importante, a simplicidade para quem consome, a eficiência na rede, a flexibilidade de consulta ou a reação a eventos em tempo real? Escolher errado gera APIs tagarelas, clientes frágeis ou servidores sobrecarregados.

## Os estilos principais

### REST

Modela o sistema como **recursos** endereçáveis por URL (`/usuarios/42`) e usa os métodos HTTP para indicar a ação (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`). Aproveita tudo que a web já oferece: cache HTTP, códigos de status, proxies, ferramentas de depuração. É o padrão para APIs públicas.

### RPC (e gRPC)

Modela o sistema como **funções remotas**: `criarPedido(itens)`, `calcularFrete(cep)`. O cliente chama algo que parece uma função local. O gRPC é a implementação moderna mais popular: usa Protocol Buffers (binário, tipado) sobre HTTP/2, com streaming nos dois sentidos. Brilha na comunicação entre microsserviços.

### GraphQL

Expõe um **único endpoint** e um schema tipado; o cliente escreve uma consulta dizendo exatamente quais campos quer, inclusive de entidades relacionadas. Resolve o excesso e a falta de dados (over-fetching e under-fetching) típicos de telas complexas.

### Orientado a eventos

Em vez de o cliente perguntar, o servidor **avisa**. Entram aqui webhooks (o servidor chama uma URL sua quando algo acontece), WebSockets, Server-Sent Events e mensageria assíncrona. Útil quando a informação muda e o consumidor precisa saber rápido.

### SOAP

Estilo mais antigo, baseado em XML com envelope rígido e contrato WSDL. Ainda aparece em bancos, governo e sistemas legados, com recursos como WS-Security. Raramente é escolha para algo novo.

## Comparação lado a lado

| Critério | REST | gRPC | GraphQL | Eventos |
| --- | --- | --- | --- | --- |
| Unidade de modelagem | Recurso | Procedimento | Grafo de tipos | Evento |
| Formato típico | JSON | Protobuf (binário) | JSON | Variado |
| Transporte | HTTP/1.1 ou 2 | HTTP/2 | HTTP | HTTP, TCP, broker |
| Cache HTTP | Nativo | Difícil | Difícil (POST) | Não se aplica |
| Uso no browser | Direto | Requer proxy (gRPC-Web) | Direto | Depende |
| Ponto forte | Simplicidade e ecossistema | Performance e contratos fortes | Flexibilidade do cliente | Tempo real e desacoplamento |

## Um mesmo caso em três estilos

Buscar o nome de um usuário e os títulos de seus três últimos pedidos:

```text
REST (duas chamadas, ou um endpoint sob medida):
  GET /usuarios/42
  GET /usuarios/42/pedidos?limit=3

gRPC (uma chamada a um método definido no .proto):
  PerfilService.ObterResumo(ObterResumoRequest{usuario_id: 42})

GraphQL (uma consulta descrevendo o formato desejado):
  query {
    usuario(id: 42) {
      nome
      pedidos(ultimos: 3) { titulo }
    }
  }
```

No REST, o servidor decide o formato da resposta; no GraphQL, o cliente decide; no gRPC, o contrato do `.proto` decide e ambos geram código a partir dele.

## Como escolher

- **API pública para terceiros:** REST. Todo mundo sabe consumir, e o cache HTTP ajuda a escalar.
- **Comunicação interna entre serviços com alto volume:** gRPC. Payload menor, tipagem forte, streaming e geração de clientes.
- **Frontends com telas ricas e muitos tipos de cliente:** GraphQL, frequentemente como camada agregadora na frente de serviços REST ou gRPC.
- **Notificar outros sistemas sobre mudanças:** webhooks ou mensageria.
- **Atualizações em tempo real para o usuário:** WebSockets ou SSE.

<Callout type="tip" title="Não é uma escolha única">
Sistemas reais misturam estilos: GraphQL ou REST na borda para clientes, gRPC entre microsserviços e eventos num broker para integrações assíncronas. Diga isso na entrevista em vez de defender um estilo para tudo.
</Callout>

## Armadilhas

- **REST que é RPC disfarçado:** rotas como `POST /executarCancelamentoDePedido` perdem os benefícios do modelo de recursos.
- **GraphQL sem limites:** consultas profundamente aninhadas podem derrubar o backend. É preciso limitar profundidade e custo.
- **gRPC exposto direto ao browser:** exige gRPC-Web e um proxy, o que adiciona complexidade operacional.

## Na entrevista

Justifique o estilo pelo requisito: "a API é pública e de leitura intensa, então REST com cache em CDN" ou "entre os serviços de ranking e de busca uso gRPC porque o payload é grande e a latência importa". Follow-ups comuns: por que não GraphQL aqui, como versionar cada estilo e como lidar com tempo real.
