Antes do OAuth, se um app de agenda quisesse ler seus contatos do e-mail, pedia sua **senha do e-mail**. Com ela, o app tinha acesso total e permanente, e o único jeito de revogar era trocar a senha. O **OAuth 2.0** (RFC 6749) resolve esse problema de **autorização delegada**: você autoriza um app a fazer coisas específicas em seu nome, por tempo limitado, sem entregar sua senha a ele.

Importante: OAuth 2.0 é um protocolo de **autorização**. Ele diz o que um app pode acessar, não quem é o usuário. A camada de identidade em cima dele é o **OpenID Connect**, que aparece no capítulo de SSO.

## Os quatro papéis

| Papel | No exemplo |
| --- | --- |
| Resource owner | Você, dono dos contatos |
| Client | O app de agenda |
| Authorization server | O servidor de login do provedor de e-mail |
| Resource server | A API de contatos |

O client recebe um **access token** com **escopos** (por exemplo, `contatos.leitura`) e o apresenta ao resource server. O token pode ser opaco ou um JWT; o client não precisa entender seu conteúdo.

## Authorization Code com PKCE

É o fluxo recomendado para apps web, mobile e SPAs:

```text
1. O client gera code_verifier aleatório e code_challenge = BASE64URL(SHA256(code_verifier)).

2. Redireciona o browser para o authorization server:
   GET /authorize?response_type=code&client_id=agenda
       &redirect_uri=https://agenda.app/callback
       &scope=contatos.leitura&state=xyz123
       &code_challenge=E9Mel...&code_challenge_method=S256

3. Usuário faz login no provedor e consente com o escopo.

4. Provedor redireciona de volta com um código de uso único:
   https://agenda.app/callback?code=SplxlO...&state=xyz123

5. O client confere o state e troca o código pelo token (canal de servidor):
   POST /token
   grant_type=authorization_code&code=SplxlO...
   &redirect_uri=https://agenda.app/callback&code_verifier=dBjftJ...

6. Resposta: access_token (curto), refresh_token (opcional), expires_in, scope.

7. Client chama a API: Authorization: Bearer <access_token>
```

Por que tantas etapas?

- O **código** passa pelo browser (canal pouco confiável), mas sozinho não vale nada: precisa ser trocado no endpoint `/token`.
- **PKCE** garante que quem troca o código é o mesmo client que iniciou o fluxo. Um atacante que intercepte o código não tem o `code_verifier`. Por isso PKCE é obrigatório para clients públicos (SPA e mobile, que não guardam segredo) e recomendado para todos.
- O parâmetro **`state`** amarra a resposta à requisição original e impede CSRF no callback.
- `redirect_uri` precisa bater exatamente com uma URL pré-registrada, para que o código não seja entregue a um domínio do atacante.

## Outros grants

| Grant | Quando usar |
| --- | --- |
| Authorization Code + PKCE | Usuário presente: web, mobile, SPA |
| Client Credentials | Máquina para máquina, sem usuário (um job chamando uma API) |
| Device Authorization | Dispositivos sem teclado: TV, CLI (usuário digita um código em outro aparelho) |
| Refresh Token | Obter novo access token sem nova interação |
| Implicit | Obsoleto: devolvia o token na URL |
| Resource Owner Password | Obsoleto: o client recebe a senha, o que contraria o propósito do OAuth |

<Callout type="warning" title="OAuth não é login">
Usar um access token como prova de identidade é um erro clássico: o token foi emitido para um client e um escopo, não para dizer quem é o usuário ao seu app. Para login, use OpenID Connect e valide o ID token, incluindo a audiência.
</Callout>

## Escopos e consentimento

Escopos são o mecanismo de **menor privilégio**: o client pede só o que precisa (`contatos.leitura`, não `conta.total`), o usuário vê isso na tela de consentimento e o resource server rejeita chamadas fora do escopo com 403. Tokens curtos e escopos estreitos limitam o estrago de um vazamento.

## Validação no resource server

O resource server precisa confirmar que o token é válido: se for JWT, verifica assinatura, expiração, emissor, audiência e escopo localmente; se for opaco, chama o endpoint de **introspecção** (RFC 7662) do authorization server, possivelmente com cache curto.

## Na entrevista

Se o sistema integra com terceiros ("permitir que apps de parceiros acessem a agenda do usuário"), descreva o Authorization Code com PKCE e escopos. Para serviços internos, Client Credentials. Diferencie OAuth (autorização) de OpenID Connect (autenticação). Follow-ups comuns: por que o código não é o token, para que serve o `state`, por que o Implicit foi abandonado e como revogar acesso de um app.
