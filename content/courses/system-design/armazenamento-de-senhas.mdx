Vazamentos de banco de dados acontecem com empresas grandes e pequenas. A pergunta que define o estrago é: o que o atacante encontra na coluna de senhas? Se encontra texto claro, todas as contas caem, inclusive em outros sites, já que as pessoas reutilizam senhas. Se encontra hashes bem projetados, quebrar cada senha vira um trabalho caro e lento.

## Regra de ouro

**Nunca armazene senhas em texto claro, nem criptografadas de forma reversível.** Armazene o resultado de uma função de hash própria para senhas. No login, você calcula o hash da senha digitada e compara com o guardado; a senha original nunca precisa ser recuperada.

## Por que não usar SHA-256 puro

Hashes de uso geral (MD5, SHA-1, SHA-256) são feitos para serem **rápidos**. Uma GPU moderna calcula bilhões por segundo, então um atacante testa todas as senhas de um dicionário em minutos. Para senhas queremos o contrário: uma função **deliberadamente lenta e custosa em memória**.

## Sal (salt)

O **sal** é um valor aleatório e único por usuário, misturado à senha antes do hash e guardado ao lado dele. Ele garante que:

- Duas pessoas com a mesma senha tenham hashes diferentes.
- Tabelas pré-calculadas (rainbow tables) se tornem inúteis.
- O atacante precise atacar cada usuário separadamente.

O sal não é segredo. Já uma **pimenta** (*pepper*) é um segredo global, guardado fora do banco (em um cofre ou HSM), acrescentado como camada extra.

## Funções recomendadas

| Função | Característica | Observação |
| --- | --- | --- |
| Argon2id | Custo ajustável de tempo, memória e paralelismo | Primeira escolha atual |
| scrypt | Exige muita memória | Boa alternativa |
| bcrypt | Custo ajustável por fator de trabalho; limita a 72 bytes | Muito difundida e aceitável |
| PBKDF2 | Muitas iterações, pouca memória | Exigida em alguns padrões; mais vulnerável a GPU |

```python
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

ph = PasswordHasher(time_cost=3, memory_cost=64 * 1024, parallelism=2)

def cadastrar(senha: str) -> str:
    return ph.hash(senha)      # sal aleatório e parâmetros ficam embutidos na string

def conferir(hash_guardado: str, senha: str) -> bool:
    try:
        return ph.verify(hash_guardado, senha)
    except VerifyMismatchError:
        return False
```

O resultado já carrega algoritmo, parâmetros e sal:

```text
$argon2id$v=19$m=65536,t=3,p=2$c29tZXNhbHQ$Zq4n...
```

## Ajuste de custo e migração

Escolha parâmetros para que um hash leve algo como 100 a 500 ms no seu hardware, e aumente com o tempo, conforme o hardware evolui. Guarde os parâmetros junto ao hash; no login, se o hash estiver com custo antigo, **refaça-o** com os novos parâmetros (*rehash on login*). Esse mesmo mecanismo permite migrar de um algoritmo fraco para um forte sem forçar todos a trocar senha.

## Outras defesas

- **Limite de tentativas e bloqueio progressivo** contra força bruta.
- **Autenticação multifator (MFA)**, que reduz o valor de uma senha vazada.
- **Verificar senhas vazadas** (listas como Have I Been Pwned) e exigir comprimento em vez de regras de composição arbitrárias.
- **Comparação em tempo constante** para evitar vazamentos por temporização.
- **Fluxo de redefinição seguro:** tokens aleatórios, de uso único e com expiração curta.
- Considerar **passkeys** (WebAuthn), que eliminam a senha.

<Callout type="warning" title="Não invente a sua">
Não crie algoritmos próprios nem encadeie hashes por conta. Use uma biblioteca madura com função de senha e parâmetros revisados.
</Callout>

## Na entrevista

Responda sem hesitar: hash lento com sal, Argon2id ou bcrypt, parâmetros ajustáveis, MFA e limite de tentativas. Follow-ups: "por que não SHA-256?" (velocidade favorece o atacante) e "como migra de MD5?" (rehash no login ou envelopar o hash antigo com o novo).
