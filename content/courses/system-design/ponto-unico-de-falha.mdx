title: Ponto único de falha
kind: lesson
---

Um **ponto único de falha** (SPOF, de single point of failure) é qualquer componente cuja queda derruba o sistema inteiro. Pode ser óbvio, como o único servidor de banco de dados, ou escondido, como um certificado TLS que expira, uma chave de API compartilhada ou a única pessoa que sabe fazer o deploy.

## Como encontrar SPOFs

Pegue o diagrama do sistema e, para cada caixa e cada seta, pergunte: "se isto sumir agora, o que acontece?". Se a resposta for "tudo para", você achou um SPOF.

```text
           usuários
              |
        [load balancer]        <- SPOF se for uma instância só
         /     |     \
     [app1] [app2] [app3]      <- redundante: ok
         \     |     /
         [banco primário]      <- SPOF: sem réplica
              |
         [disco local]         <- SPOF: sem backup externo
```

Repare que ter três servidores de aplicação não ajuda se todos dependem de um banco sem réplica. A disponibilidade é limitada pelo elo mais fraco.

### SPOFs menos óbvios

- **DNS:** um único provedor de DNS fora do ar torna o site inalcançável, mesmo com todos os servidores saudáveis.
- **Zona ou região:** dez instâncias na mesma zona de disponibilidade caem juntas se a zona tiver problema.
- **Dependências externas:** gateway de pagamento, provedor de e-mail, serviço de autenticação de terceiros.
- **Configuração compartilhada:** um serviço de configuração central que, ao falhar, impede todas as instâncias de iniciar.
- **Processos e pessoas:** um único operador com acesso de produção, um runbook que só existe na cabeça de alguém.

## Como eliminar

### Redundância

Duplique o componente e garanta que as cópias falhem de forma independente: hosts diferentes, racks diferentes, zonas diferentes. Para componentes sem estado, como servidores de aplicação, basta colocar várias instâncias atrás de um balanceador.

### Failover para componentes com estado

Bancos de dados e filas têm estado, então a cópia precisa estar sincronizada. O padrão comum é primário com réplicas: quando o primário falha, um processo de detecção (heartbeats, consenso) promove uma réplica. O desafio é evitar **split brain**, quando duas réplicas se acham primárias ao mesmo tempo e aceitam escritas conflitantes.

### Redundância do próprio balanceador

O balanceador não pode ser o novo SPOF. As abordagens incluem um par ativo-passivo compartilhando um IP virtual (com VRRP, por exemplo), balanceadores gerenciados pelo provedor de nuvem que já são distribuídos, ou vários balanceadores anunciados via DNS ou anycast.

### Degradação graciosa

Nem toda dependência precisa de redundância total. Às vezes é mais barato tolerar a ausência: se o serviço de avaliações cair, mostre a página sem avaliações em vez de devolver erro 500.

## Trade-offs

| Decisão | Ganho | Custo |
| --- | --- | --- |
| Réplica de banco em outra zona | sobrevive à perda de uma zona | latência de replicação, custo dobrado |
| Multi-região ativa-ativa | sobrevive à perda de uma região | consistência complexa, custo alto |
| Segundo provedor de DNS | elimina dependência de um fornecedor | sincronizar registros entre provedores |
| Degradação graciosa | barato, simples | experiência parcial durante a falha |

Eliminar todos os SPOFs é caro e às vezes desnecessário. A decisão deve seguir a meta de disponibilidade: um painel interno usado por dez pessoas pode conviver com um banco sem réplica; um sistema de pagamentos não.

<Callout type="tip" title="Na entrevista">
Depois de desenhar a versão inicial, faça você mesmo a varredura de SPOFs antes que o entrevistador pergunte. Dizer "o banco é um ponto único de falha; vou adicionar uma réplica síncrona em outra zona com failover automático" mostra maturidade. Follow-ups prováveis: "como você detecta que o primário caiu?", "o que acontece com as escritas durante o failover?", "e se as duas réplicas acharem que são primárias?".
</Callout>
