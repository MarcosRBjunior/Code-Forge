"Qual banco você usaria?" é uma das perguntas mais frequentes em entrevistas de system design, e a pior resposta é o nome do banco favorito. Cada família de banco organiza dados de um jeito que torna alguns acessos baratos e outros caros. Escolher bem é casar o **padrão de acesso** com o **modelo de dados**.

## O que diferencia um banco do outro

Antes de olhar as famílias, entenda os eixos que as separam:

- **Modelo de dados:** tabelas, documentos, pares chave-valor, grafos, vetores.
- **Linguagem de consulta:** SQL declarativo, APIs por chave, linguagens de travessia de grafo.
- **Estrutura de armazenamento:** B-tree (bom para leitura e atualização no lugar) ou LSM tree (bom para escrita intensa).
- **Garantias:** transações ACID completas, atomicidade só por registro, consistência eventual.
- **Modelo de escala:** um primário com réplicas ou particionamento nativo entre muitos nós.

## As famílias

| Família | Modelo | Exemplos | Brilha em |
| --- | --- | --- | --- |
| Relacional | Tabelas com schema, joins, SQL | PostgreSQL, MySQL, SQL Server | Dados com relações e transações |
| Documentos | Documentos JSON/BSON aninhados | MongoDB, Couchbase, Firestore | Agregados lidos inteiros, schema flexível |
| Chave-valor | Valor opaco acessado por chave | Redis, DynamoDB, etcd | Acessos por chave com latência mínima |
| Wide-column | Linhas com famílias de colunas, particionadas | Cassandra, HBase, ScyllaDB | Escrita massiva, consultas por partição |
| Busca | Índice invertido sobre texto | Elasticsearch, OpenSearch, Meilisearch | Busca textual e relevância |
| Séries temporais | Pontos (tempo, métrica, valor) | InfluxDB, TimescaleDB, Prometheus | Métricas, IoT, retenção por tempo |
| Grafos | Nós e arestas com propriedades | Neo4j, Amazon Neptune | Relações de muitos saltos |
| Vetoriais | Embeddings com busca por similaridade | pgvector, Milvus, Pinecone, Qdrant | Busca semântica, recomendação, RAG |

Os próximos capítulos detalham cada uma. Aqui o foco é **como escolher**.

## Um roteiro de decisão

1. **Quais são as consultas?** Liste as 3 a 5 operações principais e sua frequência. "Buscar pedido por ID", "listar pedidos de um cliente por data", "somar vendas por região no mês".
2. **Há relações e invariantes entre entidades?** Transferências, estoque, reservas: transações multi-registro apontam para relacional.
3. **Qual o volume e a proporção leitura/escrita?** Milhões de escritas por segundo de eventos imutáveis apontam para wide-column ou séries temporais.
4. **O acesso é sempre pela mesma chave?** Se sim, chave-valor ou documentos escalam horizontalmente com facilidade.
5. **Há uma consulta que um banco geral faz mal?** Texto livre, vizinhança em grafos, similaridade de vetores. Use um banco especializado **ao lado** do principal.

## Persistência poliglota

Sistemas reais combinam vários bancos, cada um para o que faz melhor:

```text
                     ┌──────────────▶ PostgreSQL     (pedidos, pagamentos: fonte da verdade)
App de e-commerce ───┼──────────────▶ Redis          (sessões, carrinho, cache)
                     ├──────────────▶ Elasticsearch  (busca de produtos)
                     └──────────────▶ ClickHouse     (analytics de vendas)
                                ▲
              CDC/eventos mantêm os bancos derivados atualizados
```

O preço é operacional: mais sistemas para monitorar, fazer backup e manter sincronizados. Defina sempre **qual banco é a fonte da verdade** e trate os outros como derivados que podem ser reconstruídos.

<Callout type="tip" title="Comece pelo relacional">
Na dúvida, PostgreSQL é uma escolha defensável para quase todo sistema no começo: transações, JSON, busca textual básica, extensões para vetores e séries temporais. Troque ou adicione bancos quando um requisito concreto (escala de escrita, latência, tipo de consulta) justificar.
</Callout>

## Armadilhas

- **Escolher pela moda:** NoSQL não é "mais escalável" por definição; ele troca flexibilidade de consulta por facilidade de particionar.
- **Ignorar consultas futuras:** um modelo chave-valor que só responde por ID vira dor quando o produto pede "filtrar por status e data".
- **Bancos demais cedo demais:** cada banco extra é uma fonte de inconsistência e um plantão a mais.

## Na entrevista

Justifique a escolha a partir das consultas e dos requisitos não funcionais: "os pedidos precisam de transação, então PostgreSQL; a busca de produtos vai para Elasticsearch, alimentado por CDC". Follow-ups: "e se a escrita crescer 100 vezes?", "como manter o índice de busca consistente?".
