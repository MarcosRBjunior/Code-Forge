Escrever uma função correta é um problema de código. Fazer essa função responder a 50 mil usuários ao mesmo tempo, sobreviver à queda de um servidor e continuar barata de operar é um problema de **system design**: decidir quais componentes existem, como eles conversam e o que acontece quando algum deles falha.

## O problema que a disciplina resolve

Todo sistema começa pequeno: um processo, um banco de dados, um servidor. Enquanto a carga é baixa, quase qualquer arquitetura funciona. Os problemas aparecem quando algum limite é atingido:

- o banco não dá conta do volume de leituras;
- um deploy derruba o site inteiro por alguns minutos;
- usuários em outro continente reclamam de lentidão;
- um job noturno trava porque os dados cresceram dez vezes.

System design é o conjunto de técnicas para antecipar esses limites e escolher, de forma consciente, onde gastar complexidade. Não existe arquitetura perfeita; existe arquitetura adequada aos requisitos e às restrições do momento.

## Os três níveis de decisão

| Nível | Pergunta central | Exemplos |
| --- | --- | --- |
| Alto nível (HLD) | Quais blocos existem e como se conectam? | load balancer, cache, fila, banco replicado |
| Dados | Onde e como a informação é guardada? | modelo relacional vs documento, particionamento, índices |
| Baixo nível (LLD) | Como cada componente é organizado por dentro? | classes, interfaces, padrões de projeto |

Este curso foca nos dois primeiros: os blocos de construção de sistemas distribuídos e os trade-offs de cada um.

## Requisitos funcionais e não funcionais

Antes de desenhar qualquer caixa, você precisa saber o que o sistema faz e com que qualidade.

**Requisitos funcionais** descrevem comportamento: "o usuário encurta uma URL", "o motorista recebe corridas próximas".

**Requisitos não funcionais** descrevem propriedades: latência, disponibilidade, durabilidade, consistência, custo, segurança. São eles que mais influenciam a arquitetura. Um encurtador de URL com 100 acessos por dia cabe num servidor qualquer; o mesmo encurtador com 100 mil leituras por segundo exige cache, replicação e talvez CDN.

## Um processo de trabalho

Uma forma prática de abordar qualquer problema de design:

```text
1. Esclarecer requisitos     -> o que entra e o que fica fora do escopo
2. Estimar a escala          -> usuários, requisições/s, volume de dados
3. Definir a API e os dados  -> endpoints, entidades, padrões de acesso
4. Desenhar o alto nível     -> clientes, serviços, armazenamento
5. Aprofundar gargalos       -> cache, sharding, filas, réplicas
6. Discutir falhas e trade-offs
```

As estimativas do passo 2 costumam ser feitas de cabeça. Por exemplo: 10 milhões de usuários ativos por dia, cada um fazendo 20 requisições, dão 200 milhões de requisições diárias. Um dia tem cerca de 86.400 segundos, então a média fica perto de 2.300 requisições por segundo, e o pico pode ser duas a três vezes isso. Esse número já indica que um único servidor de aplicação provavelmente não basta.

## Trade-offs, não respostas certas

Quase toda decisão troca uma qualidade por outra:

- **Cache** reduz latência, mas introduz dados possivelmente desatualizados.
- **Replicação** aumenta disponibilidade, mas complica a consistência.
- **Microsserviços** dão autonomia aos times, mas adicionam latência de rede e operação.
- **Consistência forte** simplifica o raciocínio, mas custa disponibilidade durante partições.

O valor de um bom projeto está em explicitar essas trocas e justificá-las com os requisitos. "Usei Kafka porque é escalável" é fraco; "usei uma fila para absorver picos de 10 vezes a média sem perder pedidos, aceitando alguns segundos de atraso no processamento" é forte.

<Callout type="tip" title="Na entrevista">
O entrevistador avalia o processo, não um desenho final. Faça perguntas antes de desenhar, declare suposições em voz alta, comece com uma versão simples que funciona e só então evolua para resolver gargalos concretos. Follow-ups comuns: "o que acontece se esse componente cair?", "como isso escala para 10 vezes mais usuários?", "onde está o gargalo agora?".
</Callout>

## Armadilhas comuns

- **Começar pela tecnologia.** Escolher banco ou framework antes de entender os padrões de acesso leva a justificativas frágeis.
- **Superdimensionar.** Desenhar sharding global para um sistema com mil usuários mostra falta de senso de proporção.
- **Ignorar falhas.** Todo componente cai em algum momento; um design que não diz o que acontece nesse caso está incompleto.
- **Não quantificar.** Sem números, não há como saber se um componente é necessário.
