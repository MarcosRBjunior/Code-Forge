Um modelo treinado só gera valor quando suas previsões chegam a quem decide: uma tela do app, um serviço de pagamentos, uma fila de moderação. **Servimento** é a parte do sistema que transforma o artefato do modelo em previsões, e a primeira decisão é **quando** a previsão é calculada: antes de alguém pedir (batch) ou no momento do pedido (tempo real).

## Predição em batch

Um job periódico roda o modelo sobre todas as entidades relevantes e grava o resultado numa tabela ou num key-value store: "para cada usuário, os 50 itens recomendados" ou "para cada cliente, a probabilidade de churn". Na hora da requisição, o serviço só faz uma consulta por chave.

- **Prós:** latência de leitura mínima, modelo pode ser pesado e lento, falhas no job não derrubam o produto (você serve o resultado de ontem), custo previsível.
- **Contras:** as previsões envelhecem, você calcula para muitas entidades que nem vão aparecer e não consegue usar contexto da sessão (o que o usuário acabou de buscar).

## Predição em tempo real

O serviço recebe a requisição, busca features (do feature store online e do próprio request), roda o modelo e responde em dezenas de milissegundos.

- **Prós:** usa contexto fresco, só calcula o que é pedido, reage na hora a mudanças.
- **Contras:** orçamento de latência apertado, exige infraestrutura sempre disponível e escalável para o pico, e o modelo precisa ser rápido o bastante.

O programa compara as duas abordagens num cenário hipotético de 200 mil usuários, dos quais cerca de 8% abrem o app num dia, e simula a latência de cada etapa do caminho em tempo real.

```python
import random

random.seed(42)

USUARIOS = 200_000
TAXA_ATIVOS = 0.08
ativos = sum(1 for _ in range(USUARIOS) if random.random() < TAXA_ATIVOS)

print("== custo diario de inferencia ==")
print(f"batch (todos os usuarios): {USUARIOS} previsoes")
print(f"tempo real (so ativos):    {ativos} previsoes")
print(f"previsoes batch nunca lidas: {1 - ativos / USUARIOS:.0%}")

def latencia_ms():
    rede = random.uniform(1, 3)
    features = random.expovariate(1 / 4)  # media 4 ms, cauda longa
    if random.random() < 0.02:            # 2% das buscas caem num shard lento
        features += random.uniform(30, 60)
    modelo = random.gauss(12, 2)
    return rede + features + modelo

amostras = sorted(latencia_ms() for _ in range(20_000))
def pct(p):
    return amostras[int(p / 100 * (len(amostras) - 1))]

print("== latencia em tempo real ==")
for p in (50, 95, 99):
    print(f"p{p}: {pct(p):.1f} ms")
orcamento = 50
estouro = sum(1 for a in amostras if a > orcamento) / len(amostras)
print(f"acima do orcamento de {orcamento} ms: {estouro:.1%}")
```

function mulberry32(semente) {
  return () => {
    semente = (semente + 0x6d2b79f5) | 0;
    let z = Math.imul(semente ^ (semente >>> 15), 1 | semente);
    z = (z + Math.imul(z ^ (z >>> 7), 61 | z)) ^ z;
    return ((z ^ (z >>> 14)) >>> 0) / 4294967296;
  };
}

  const u1 = 1 - rng();
  const u2 = rng();

}

No batch, 92% das previsões nunca são lidas. No tempo real, a mediana de cerca de 17 ms fica confortável, mas o p99 passa de 60 ms e a cauda é dominada pelas buscas lentas de features, não pelo modelo. Isso é típico: em servimento real, otimizar o p99 quase sempre significa mexer em I/O (cache local, timeouts com valor padrão, menos chamadas remotas), não em FLOPs.

## Arquitetura típica

```text
  requisicao
      |
+-----v------+    features     +----------------+
| servico de |---------------->| feature store  |
| predicao   |<----------------| online (KV)    |
+-----+------+                 +----------------+
      |  tensor
+-----v------+       carrega   +----------------+
| servidor   |<----------------| registro de    |
| de modelo  |                 | modelos        |
+-----+------+                 +----------------+
      |  score
      v
 resposta + log (features, score, versao) -> stream -> treino
```

Registrar as features **exatamente como foram usadas** no momento da previsão é o que permite treinar o próximo modelo sem skew entre treino e servimento.

## Técnicas para caber no orçamento

- **Híbrido:** pré-calcule a parte cara em batch (embeddings de itens, candidatos) e faça em tempo real só o ranqueamento final com contexto.
- **Cache de previsões** para chaves repetidas, com TTL coerente com a velocidade de mudança.
- **Modelos menores:** destilação, quantização, poda. Um modelo 4 vezes menor com 1% a menos de qualidade costuma ser a escolha certa.
- **Batching dinâmico** no servidor de modelos para aproveitar GPU sem estourar latência.
- **Fallback:** se o modelo não responder a tempo, sirva a lista batch de ontem ou uma heurística de popularidade.

<Callout type="tip" title="Comece pelo mais simples">
Se o produto tolera previsões de algumas horas atrás, comece com batch. Mude para tempo real quando houver evidência de que contexto fresco melhora a métrica de negócio.
</Callout>
