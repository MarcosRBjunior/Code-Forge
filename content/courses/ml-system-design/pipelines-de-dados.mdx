Modelos aprendem com dados, e em produção esses dados não chegam limpos num CSV. Eles chegam como eventos do app (impressões, cliques, compras), linhas de bancos transacionais, logs de servidor e rótulos de humanos, cada um com seu atraso, formato e taxa de erro. O pipeline de dados é o que transforma esse fluxo bagunçado em exemplos de treino confiáveis e em features para o servimento. Na prática, a maior parte dos incidentes de qualidade de modelos nasce aqui, não no algoritmo.

## Como funciona

```text
  app / web ──> coletor de eventos ──> fila (Kafka) ──┬──> stream: agregados de minutos ──> feature store online
                                                      │
  banco transacional ──> CDC ─────────────────────────┤
                                                      v
                                     data lake (camada bruta, imutável, particionada por dia)
                                                      │
                                         validação + limpeza + deduplicação
                                                      │
                                     camada tratada ──> joins com rótulos ──> dataset de treino
                                                      │
                                              agregados diários ──> feature store offline
```

As peças principais:

- **Coleta**: eventos com esquema versionado (Avro, Protobuf), um ID único por evento e dois carimbos de tempo, o do dispositivo e o do servidor.
- **Camada bruta imutável**: você guarda tudo como chegou. Se descobrir um bug na limpeza, reprocessa sem perder nada.
- **Validação**: esquema, tipos, faixas (idade negativa, preço zero), taxa de nulos e volume por partição. Uma queda de 40% no volume de um dia é um alarme, não um dado.
- **Deduplicação**: clientes móveis reenviam eventos quando a rede falha; sem dedup por ID, um clique vira três.
- **Eventos atrasados**: um celular offline manda os eventos de ontem hoje. O pipeline define uma **marca d'água** (até quanto tempo aceita atraso) e decide se reprocessa a partição antiga ou descarta.
- **Orquestração**: um agendador (Airflow ou similar) roda as etapas como um grafo de dependências, com reexecução idempotente por partição.

## Exemplo: da camada bruta às features

O programa processa um lote pequeno de eventos com os problemas típicos e produz features diárias por usuário.

import java.util.*;
import java.util.stream.*;

static class Evento {
    final String id, usuario, tipo, dia;
    final Double valor;

    Evento(String id, String usuario, String tipo, String dia, Double valor) {
        this.id = id;
        this.usuario = usuario;
        this.tipo = tipo;
        this.dia = dia;
        this.valor = valor;
    }
}

static class Feature {
    int cliques = 0;
    int compras = 0;
    double gasto = 0.0;
}

public static void main(String[] args) {
    List<Evento> eventos = List.of(
        new Evento("e1", "u1", "clique", "2026-03-10", null),
        new Evento("e2", "u1", "compra", "2026-03-10", 120.0),
        new Evento("e2", "u1", "compra", "2026-03-10", 120.0),
        new Evento("e3", "u2", "clique", "2026-03-10", null),
        new Evento("e4", null, "clique", "2026-03-10", null),
        new Evento("e5", "u2", "compra", "2026-03-10", -50.0),
        new Evento("e6", "u2", "clique", "2026-03-07", null),
        new Evento("e7", "u3", "compra", "2026-03-09", 80.0)
    );
    String DIA_PROCESSADO = "2026-03-10";
    Set<String> DIAS_ACEITOS_ATRASO = Set.of("2026-03-09", "2026-03-10");

    // LinkedHashMap guarda a ordem de inserção, como o dict do Python
    Map<String, Integer> motivos = new LinkedHashMap<>();
    Set<String> vistos = new HashSet<>();
    List<Evento> limpos = new ArrayList<>();
    Set<String> reprocessar = new TreeSet<>();
    for (Evento e : eventos) {
        if (e.usuario == null) {
            motivos.merge("sem usuario", 1, Integer::sum);
        } else if (e.tipo.equals("compra") && (e.valor == null || e.valor <= 0)) {
            motivos.merge("valor invalido", 1, Integer::sum);
        } else if (vistos.contains(e.id)) {
            motivos.merge("duplicado", 1, Integer::sum);
        } else if (!DIAS_ACEITOS_ATRASO.contains(e.dia)) {
            motivos.merge("atrasado demais", 1, Integer::sum);
        } else {
            vistos.add(e.id);
            limpos.add(e);
            if (!e.dia.equals(DIA_PROCESSADO)) {
                reprocessar.add(e.dia);
            }
        }
    }

    String descartados = motivos.entrySet().stream()
        .map(m -> "'" + m.getKey() + "': " + m.getValue()).collect(Collectors.joining(", "));
    System.out.println("entrada=" + eventos.size() + " limpos=" + limpos.size() + " descartados={" + descartados + "}");
    String antigas = reprocessar.stream().map(d -> "'" + d + "'").collect(Collectors.joining(", "));
    System.out.println("particoes antigas a reprocessar: [" + antigas + "]");

    // TreeMap percorre as chaves em ordem, como sorted(features)
    Map<String, Feature> features = new TreeMap<>();
    for (Evento e : limpos) {
        if (!e.dia.equals(DIA_PROCESSADO)) {
            continue;
        }
        Feature f = features.computeIfAbsent(e.usuario, u -> new Feature());
        if (e.tipo.equals("clique")) {
            f.cliques += 1;
        } else {
            f.compras += 1;
            f.gasto += e.valor;
        }
    }
    for (Map.Entry<String, Feature> par : features.entrySet()) {
        Feature f = par.getValue();
        System.out.println(par.getKey() + " {'cliques': " + f.cliques + ", 'compras': " + f.compras + ", 'gasto': " + f.gasto + "}");
    }
}

	vistos := map[string]bool{}
	reprocessar := map[string]bool{}
	var limpos []Evento
	for _, e := range eventos {
		if e.usuario == "" {
			contar("sem usuario")
		} else if e.tipo == "compra" && (e.valor == nil || *e.valor <= 0) {
			contar("valor invalido")
		} else if vistos[e.id] {
			contar("duplicado")
		} else if !DIAS_ACEITOS_ATRASO[e.dia] {
			contar("atrasado demais")
		} else {
			vistos[e.id] = true
			limpos = append(limpos, e)
			if e.dia != DIA_PROCESSADO {
				reprocessar[e.dia] = true
			}
		}
	}

	var descartados []string
	for _, m := range ordem {
		descartados = append(descartados, fmt.Sprintf("'%s': %d", m, motivos[m]))
	}
	fmt.Printf("entrada=%d limpos=%d descartados={%s}\n", len(eventos), len(limpos), strings.Join(descartados, ", "))
	var antigas []string
	for d := range reprocessar {
		antigas = append(antigas, d)
	}
	sort.Strings(antigas)
	for i, d := range antigas {
		antigas[i] = "'" + d + "'"
	}
	fmt.Printf("particoes antigas a reprocessar: [%s]\n", strings.Join(antigas, ", "))

	features := map[string]*Feature{}
	for _, e := range limpos {
		if e.dia != DIA_PROCESSADO {
			continue
		}
		f, ok := features[e.usuario]
		if !ok {
			f = &Feature{}
			features[e.usuario] = f
		}
		if e.tipo == "clique" {
			f.cliques++
		} else {
			f.compras++
			f.gasto += *e.valor
		}
	}
	var usuarios []string
	for u := range features {
		usuarios = append(usuarios, u)
	}
	sort.Strings(usuarios)
	for _, u := range usuarios {
		f := features[u]
		fmt.Printf("%s {'cliques': %d, 'compras': %d, 'gasto': %.1f}\n", u, f.cliques, f.compras, f.gasto)
	}
}

## Batch ou streaming?

| | Batch | Streaming |
| --- | --- | --- |
| Frescor | Horas | Segundos ou minutos |
| Complexidade | Baixa; reprocessar é rodar de novo | Alta; estado, janelas, ordem, exatamente-uma-vez |
| Uso típico | Dataset de treino, agregados de 30 dias | Contadores recentes (cliques na última hora), fraude |
| Custo | Barato por evento | Infra sempre ligada |

Muitos sistemas usam os dois: o batch é a fonte da verdade e o streaming adianta os agregados recentes. O cuidado é garantir que a mesma definição de feature produza o mesmo valor nos dois caminhos.

## Armadilhas

- **Mudança silenciosa de esquema**: o app passa a mandar preço em centavos e o modelo vê preços 100 vezes maiores. Contratos de dados e validação por partição pegam isso.
- **Join com o estado atual**: juntar eventos antigos com a tabela de usuários de hoje traz informação do futuro. Use snapshots ou tabelas com validade temporal.
- **Amostragem no log**: se o cliente só registra 10% das impressões, os cliques parecem 10 vezes mais frequentes.
