Um modelo novo só vai para produção se você conseguir dizer, com números, que ele é melhor. Em ML há dois momentos de medir: **offline**, sobre dados históricos, rápido e barato, antes de qualquer usuário ver o modelo; e **online**, com usuários reais, lento e caro, mas o único que mede o que o negócio realmente quer. Escolher mal qualquer uma delas faz você otimizar a coisa errada com muita eficiência.

## Métricas offline de classificação

Com um limiar de decisão, cada exemplo cai numa célula da matriz de confusão: verdadeiro positivo (TP), falso positivo (FP), falso negativo (FN) e verdadeiro negativo (TN).

- **Precisão** = TP / (TP + FP): dos que você marcou, quantos eram mesmo positivos. Importa quando o falso positivo é caro (bloquear um cliente legítimo).
- **Recall** = TP / (TP + FN): dos positivos existentes, quantos você pegou. Importa quando deixar passar é caro (fraude, conteúdo nocivo).
- **F1**: média harmônica das duas, útil para resumir um ponto de operação.
- **AUC-ROC**: probabilidade de um positivo aleatório receber pontuação maior que um negativo aleatório. Não depende de limiar e mede a qualidade da ordenação.
- **AUC-PR** e **log loss**: a primeira é mais informativa com classes muito raras; a segunda mede se as probabilidades estão calibradas, o que importa quando a pontuação entra numa conta (como o lance de um anúncio).

## Métricas offline de ranqueamento

Quando a saída é uma lista, a posição importa:

- **Precision@k e recall@k**: fração dos k primeiros que é relevante e fração dos relevantes que aparece nos k primeiros.
- **MRR**: média de 1 dividido pela posição do primeiro item relevante. Boa para busca com uma resposta certa.
- **MAP**: média, por consulta, da precisão medida em cada posição onde aparece um relevante.
- **NDCG@k**: soma ganhos de relevância descontados por log da posição e normaliza pela lista ideal. Aceita relevância graduada (0, 1, 2, 3).

O programa calcula as principais a partir de pontuações e listas pequenas.

```python
import math

rotulos = [1, 0, 1, 1, 0, 0, 1, 0, 0, 0]
scores  = [0.9, 0.8, 0.75, 0.6, 0.55, 0.4, 0.35, 0.3, 0.2, 0.1]

def precisao_recall(limiar):
    tp = sum(1 for y, s in zip(rotulos, scores) if s >= limiar and y == 1)
    fp = sum(1 for y, s in zip(rotulos, scores) if s >= limiar and y == 0)
    fn = sum(1 for y, s in zip(rotulos, scores) if s < limiar and y == 1)
    return tp / (tp + fp), tp / (tp + fn)

for limiar in (0.7, 0.5, 0.3):
    p, r = precisao_recall(limiar)
    print(f"limiar {limiar}: precisao={p:.2f} recall={r:.2f}")

pos = [s for y, s in zip(rotulos, scores) if y == 1]
neg = [s for y, s in zip(rotulos, scores) if y == 0]
auc = sum((p > n) + 0.5 * (p == n) for p in pos for n in neg) / (len(pos) * len(neg))
print(f"AUC = {auc:.3f}")

def dcg(rels):
    return sum((2 ** r - 1) / math.log2(i + 2) for i, r in enumerate(rels))

def ndcg_at_k(rels, k):
    ideal = dcg(sorted(rels, reverse=True)[:k])
    return dcg(rels[:k]) / ideal if ideal else 0.0

def average_precision(rels):
    acertos, soma = 0, 0.0
    for i, r in enumerate(rels, start=1):
        if r > 0:
            acertos += 1
            soma += acertos / i
    return soma / acertos if acertos else 0.0

lista_a = [3, 2, 0, 1, 0]
lista_b = [0, 1, 3, 2, 0]
for nome, rels in (("A", lista_a), ("B", lista_b)):
    print(f"lista {nome}: NDCG@5={ndcg_at_k(rels, 5):.3f} AP={average_precision(rels):.3f}")
```

```text
Saída:
limiar 0.7: precisao=0.67 recall=0.50
limiar 0.5: precisao=0.60 recall=0.75
limiar 0.3: precisao=0.50 recall=1.00
AUC = 0.792
lista A: NDCG@5=0.993 AP=0.917
lista B: NDCG@5=0.577 AP=0.639
```

Baixar o limiar de 0,7 para 0,3 leva o recall de 0,50 para 1,00 e derruba a precisão: o limiar é uma decisão de produto, não do modelo. Já as listas A e B contêm exatamente os mesmos itens; só a ordem muda. NDCG e AP penalizam B por empurrar os itens mais relevantes para baixo, coisa que precision@5 não perceberia.

## Métricas online

Online, você mede o comportamento: taxa de cliques (CTR), conversão, tempo assistido, retenção em 7 ou 30 dias, receita por usuário. Elas entram num teste A/B e são acompanhadas por **métricas de proteção** (latência p99, taxa de erro, denúncias, cancelamentos) que não podem piorar.

| | Offline | Online |
| --- | --- | --- |
| Custo e tempo | Minutos, sem risco | Dias ou semanas, expõe usuários |
| O que mede | Ajuste aos rótulos históricos | Efeito real no produto |
| Viés | Só vê o que o modelo antigo mostrou | Mede a política nova de verdade |
| Uso | Filtrar candidatos a modelo | Decidir o lançamento |

<Callout type="warning" title="Offline melhor não garante online melhor">
Os dados históricos refletem o que o sistema antigo escolheu exibir. Um modelo novo pode subir a AUC e mesmo assim piorar a sessão, por exemplo recomendando sempre o mesmo tipo de conteúdo. Por isso a decisão final é do teste A/B.
</Callout>

Justifique o ponto de operação pelo custo do erro. Follow-ups comuns: "por que não acurácia?", "AUC subiu e o CTR caiu, o que pode ter acontecido?" (vazamento, viés de exposição, calibração, diferença entre feature de treino e de servimento) e "como avaliar sem rótulos completos?".
