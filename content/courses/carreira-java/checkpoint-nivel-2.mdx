O Nível 2 trabalhou em dois sistemas. Na clínica, você reconstruiu a API com Spring Boot 3, padronizou status e erros, documentou com springdoc, testou por camada e protegeu tudo com Spring Security: sessão e CSRF no portal da recepção, perfis e `@PreAuthorize`, JWT com o OAuth2 Resource Server, login com GitHub e Google e segundo fator com TOTP. Na loja, separou `pedidos` e `pagamentos` em serviços com banco próprio, ligou os dois por HTTP com Resilience4j e depois pelo RabbitMQ, subiu a infraestrutura com o AWS CDK, escreveu testes de integração com Testcontainers e montou pipelines que testam, medem cobertura e publicam a imagem. No fim, o assistente da loja com Spring AI juntou RAG e tool calling.

Este checkpoint confere se você domina esse conjunto como um todo: se sabe por que cada peça está ali e consegue montá-la de novo sem o capítulo aberto. O desafio tem duas partes, uma em cada sistema, porque é assim que o nível foi construído.

**Neste checkpoint:**

- Mapear o que cada um dos dezesseis capítulos exigiu de você
- Verificar, com habilidades que você prova fazendo, onde está pronto e onde precisa voltar
- Fechar a API da clínica com segurança, documentação e testes, e ligar pedidos e pagamentos por mensagens com um pipeline de verdade
- Revisar os erros que mais aparecem em código Spring de nível pleno
- Treinar respostas de entrevista e resolver seis quizzes que cruzam o nível

## Autoavaliação

Para cada item, a pergunta é: consigo fazer isso agora, num projeto em branco, consultando só a documentação oficial? Marque mentalmente os que travaram.

### API e documentação

- Consigo criar um endpoint que responde 201 com `Location`, 204 sem corpo e erros em `application/problem+json`.
- Consigo ativar um profile `prod` que lê credenciais de variáveis de ambiente e rodar o `.jar` com ele.
- Consigo fazer o Swagger UI mostrar o botão Authorize e chamar um endpoint protegido com o token.

### Segurança

- Consigo emitir um JWT assinado com RSA e configurar o resource server para validar assinatura, expiração e emissor.
- Consigo provar com testes que um endpoint responde 401 sem token e 403 com uma role insuficiente.
- Consigo escrever uma regra de posse com `@PreAuthorize` em que o paciente só vê as próprias consultas.
- Consigo explicar, com o fluxo na mão, por que o portal com sessão precisa de CSRF e a API com Bearer não.

### Microsserviços e mensageria

- Consigo configurar timeout e circuit breaker numa chamada `RestClient` e mostrar o circuito abrindo em `/actuator/circuitbreakers`.
- Consigo declarar exchange, fila, binding e dead letter queue no Spring AMQP e mandar uma mensagem envenenada para a DLQ.
- Consigo processar a mesma mensagem duas vezes sem efeito duplicado, usando o `messageId` como chave de idempotência.

### Testes e pipeline

- Consigo escrever um `*IT` com `@SpringBootTest` que usa Postgres e RabbitMQ em containers e roda no `mvn verify`.
- Consigo montar um workflow em que o job de imagem só roda depois dos testes e publica no GHCR com a tag do SHA.
- Consigo fazer o scan de vulnerabilidades reprovar o pipeline quando houver falha crítica.

## Desafio prático

O desafio tem duas partes, uma por sistema. Faça as duas: juntas, elas cobrem o nível de ponta a ponta. Cada parte vive no seu próprio repositório (ou num repositório com um diretório por serviço, como o capítulo de CI mostra).

**Parte A, clínica.** A clínica vai abrir a API para um aplicativo de pacientes. A API precisa autenticar por token, separar o que cada perfil pode fazer, estar documentada para o time do aplicativo e ter testes que provem as regras de acesso.

**Parte B, loja.** O serviço de pedidos hoje espera o de pagamentos responder por HTTP. A loja quer que um pedido seja aceito mesmo com pagamentos fora do ar, que nenhuma cobrança seja feita duas vezes e que toda versão publicada seja uma imagem rastreável até o commit testado.

### Requisitos

1. **(A) Token.** `POST /auth/login` confere usuário e senha (BCrypt) e devolve um JWT assinado com RSA, de 15 minutos, com `iss`, `sub`, `exp` e a claim `roles`. As chaves ficam fora do Git e entram por variável de ambiente ou arquivo montado.
2. **(A) Autorização.** Com `oauth2ResourceServer`, a API aplica: `DELETE /medicos/**` só para `ADMIN`; agendar e cancelar para `RECEPCAO`; `GET /minhas-consultas` para `PACIENTE`, devolvendo só as consultas do próprio usuário por uma regra de posse com `@PreAuthorize`. A hierarquia de perfis do capítulo de perfis continua valendo.
3. **(A) Documentação.** O springdoc publica o Swagger UI com esquema de segurança Bearer, exemplos nos DTOs de consulta e as respostas de erro (400, 401, 403, 404, 422) descritas em cada operação.
4. **(A) Testes e profiles.** Testes com MockMvc provando 401, 403 e 200 por perfil, um teste de ponta a ponta que chama `/auth/login` e usa o token devolvido, e um profile `prod` sem nenhuma credencial no `application-prod.yml`.
5. **(B) Mensagens.** `POST /pedidos` grava o pedido como `AGUARDANDO_PAGAMENTO`, publica `PagamentoSolicitado` na exchange `loja.eventos` com a routing key `pagamento.solicitado` e responde 202. Pagamentos consome, cobra e publica `pagamento.aprovado` ou `pagamento.recusado`; pedidos consome e muda o status para `PAGO` ou `RECUSADO`.
6. **(B) Falhas.** Toda fila tem retry limitado com backoff e dead letter queue, com `default-requeue-rejected` desligado. Erro permanente (pedido inexistente) vai direto para a DLQ com `AmqpRejectAndDontRequeueException`.
7. **(B) Idempotência.** O consumidor de pagamentos registra o `messageId` processado na mesma transação da cobrança. Reentregar a mesma mensagem não cobra de novo.
8. **(B) Testes de integração.** Um `CriarPedidoIT` com `@SpringBootTest`, Postgres e RabbitMQ via Testcontainers e `@ServiceConnection` prova o fluxo completo até `PAGO`, e outro prova que uma mensagem duplicada não gera segunda cobrança.
9. **(B) Pipeline.** O workflow roda `mvn verify` com relatório de testes e JaCoCo; um segundo job, dependente do primeiro, gera a imagem, faz o scan e publica em `ghcr.io` com a tag do SHA do commit. O check de testes é obrigatório na `main`.
10. **(B) Decisão registrada.** Um ADR curto explica por que pagamentos passou de chamada síncrona para mensagem, com contexto, decisão e consequências (incluindo a consistência eventual que o cliente passa a ver).

### Critérios de aceite

- Sem token, `curl -i localhost:8080/consultas` responde `401` com o cabeçalho `WWW-Authenticate: Bearer`.
- Com o token de um paciente, `GET /minhas-consultas` traz só as consultas dele; com o token de outro paciente, as dele não aparecem; `DELETE /medicos/1` com o mesmo token responde `403`.
- O Swagger UI em `/swagger-ui.html` autentica pelo botão Authorize e executa um agendamento com sucesso.
- `./mvnw verify` roda unitários e `*IT` nos dois projetos, com todos verdes no GitHub Actions.
- Com `docker compose stop pagamentos`, `POST /pedidos` continua respondendo 202; ao subir pagamentos de novo, o pedido chega a `PAGO` sem intervenção.
- Publicar à mão uma mensagem com `pedidoId` inexistente faz a mensagem aparecer na DLQ no painel do RabbitMQ, sem travar a fila principal.
- A imagem publicada tem a tag igual ao SHA do commit, e o job de imagem não roda quando um teste falha.

### Dicas

- Comece pela Parte A pelo teste: escreva os testes de 401 e 403 antes de mexer na configuração, como em [Proteja suas APIs REST](/learn/carreira-java/java-spring-security-proteja-apis-rest). Se as roles não batem, confira o conversor que transforma `roles` em `ROLE_*`.
- O resource server lê `scope` por padrão e prefixa com `SCOPE_`. Esquecer o conversor é a causa mais comum de 403 com token válido.
- Para a Parte B, desenhe primeiro exchange, filas, bindings e routing keys num papel e só depois escreva o `RabbitConfig`. Reveja [Mensageria com RabbitMQ](/learn/carreira-java/microsservicos-pratica-mensageria-rabbitmq).
- A tabela de mensagens processadas com `messageId` como chave primária resolve a idempotência: a segunda inserção viola a chave e você descarta a mensagem.
- Se o `*IT` não roda no CI, confira o Failsafe no `pom.xml` e o sufixo das classes, como em [testes de integração](/learn/carreira-java/testes-integracao-java-garantindo-qualidade-back-ends).
- Use `needs:` para encadear o job de imagem ao de testes e `docker/metadata-action` para as tags, como em [Pipeline Docker](/learn/carreira-java/integracao-continua-pipeline-docker-github-actions).

Uma ordem que reduz retrabalho:

1. Parte A: testes de 401 e 403, depois chaves RSA, `JwtEncoder`, `JwtDecoder` e o login.
2. Parte A: regras por URL, regra de posse e documentação no springdoc.
3. Parte B: `RabbitConfig` nos dois serviços, publicação e consumo do caminho feliz.
4. Parte B: retry, DLQ e a tabela de mensagens processadas.
5. Parte B: os `*IT` com Testcontainers.
6. Os dois: workflow de testes, job de imagem e o ADR.

Um esqueleto da cadeia de segurança da Parte A, para você completar:

```java
// src/main/java/br/com/clinica/seguranca/SegurancaConfig.java
@Bean
SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(req -> req
                    .requestMatchers(HttpMethod.POST, "/auth/login").permitAll()
                    .requestMatchers("/v3/api-docs/**", "/swagger-ui/**", "/swagger-ui.html").permitAll()
                    .requestMatchers(HttpMethod.DELETE, "/medicos/**").hasRole("ADMIN")
                    // complete com as regras de RECEPCAO e PACIENTE
                    .anyRequest().authenticated())
            .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt.jwtAuthenticationConverter(conversorDeRoles())))
            .build();
}
```

E o contrato do consumidor idempotente da Parte B:

// pagamentos: br.com.loja.pagamentos.mensageria.SolicitacaoListener

### Extras opcionais

- Na clínica, refresh token opaco com rotação em `POST /auth/refresh` e revogação no logout.
- No portal da recepção, login com GitHub e segundo fator com TOTP para o perfil `ADMIN`.
- Na loja, uma stack do CDK que sobe os dois serviços no Fargate com a senha do banco vinda do Secrets Manager, validada com `cdk synth` no pipeline.
- No assistente da loja, uma ferramenta `@Tool` que consulta o status do pedido e só devolve pedidos do cliente autenticado.

## Revisão rápida

**401 não é 403.** 401 diz "não sei quem você é": token ausente, inválido ou expirado. 403 diz "sei quem você é, mas não pode": autenticado sem a role. Testar os dois casos separadamente pega metade dos bugs de configuração.

**`hasRole("ADMIN")` procura `ROLE_ADMIN`.** O prefixo é acrescentado por `hasRole` e não por `hasAuthority`. Se o banco ou o token guardam `ADMIN` sem prefixo, o conversor precisa acrescentá-lo, ou nenhuma regra casa.

**CSRF depende de cookie.** O ataque funciona porque o navegador manda o cookie de sessão sozinho. Por isso o portal com Thymeleaf mantém CSRF ligado, e a API stateless com `Authorization: Bearer` pode desligá-lo. Se você puser o refresh token em cookie, aquela rota volta a precisar de proteção.

**Retry não é idempotência.** Retry com backoff resolve falha transitória, mas a entrega do RabbitMQ é pelo menos uma vez, e o retry de uma chamada HTTP pode repetir uma cobrança que já passou. Toda operação com efeito colateral precisa de uma chave de idempotência.

**Sem DLQ, uma mensagem ruim trava a fila.** Com `default-requeue-rejected` ligado e sem dead letter exchange, a poison message volta para o início da fila para sempre. Limite as tentativas e configure a DLQ em toda fila.

```yaml
# pagamentos: src/main/resources/application.yml
spring:
  rabbitmq:
    listener:
      simple:
        default-requeue-rejected: false
        retry:
          enabled: true
          max-attempts: 3
          initial-interval: 1s
          multiplier: 2
```

**H2 no teste esconde bug do Postgres.** Tipos, funções e SQL nativo mudam entre bancos. Testcontainers com `@ServiceConnection` dá o banco real com a mesma configuração que você teria à mão.

**Configuração muda por ambiente, o artefato não.** O mesmo `.jar` (ou a mesma imagem) roda em desenvolvimento e em produção; o que muda é o profile ativo e as variáveis de ambiente. Se você precisa recompilar para trocar a URL do banco, a configuração está no lugar errado.

**Tag `latest` não conta história.** Se produção roda `latest`, você não sabe qual commit está no ar nem consegue voltar com segurança. Publique com o SHA e, se quiser, com a versão; `latest` no máximo como apelido.

<Callout type="warning" title="Segredos fora do repositório e fora da imagem">
Chave privada do JWT, senha do banco, client secret do Google e chave da API do modelo de linguagem nunca vão para o Git, para o `application.yml` nem para a camada da imagem. Em desenvolvimento, use variáveis de ambiente; no pipeline, os secrets do GitHub; na AWS, o Secrets Manager injetado no container pelo CDK. Um segredo que já foi commitado está vazado: troque-o, não basta apagar o arquivo.
</Callout>

## Na entrevista

**Como funciona a autenticação stateless com JWT no Spring Security?** O login confere a senha e emite um token assinado com as claims do usuário. A cada requisição, o `BearerTokenAuthenticationFilter` lê o cabeçalho, o `JwtDecoder` valida assinatura, expiração e emissor, e um conversor transforma as claims em authorities. Nada fica guardado em sessão no servidor.

**Como revogar um JWT antes de ele expirar?** Não há revogação nativa, porque o token é autossuficiente. A prática é access token curto (minutos) e refresh token opaco guardado no banco, que pode ser revogado no logout e é trocado a cada uso.

**Quando você não usaria microsserviços?** Quando o time é pequeno, o domínio ainda está mudando e não há problema real de escala organizacional. Um monólito modular com fronteiras verificadas, por exemplo com Spring Modulith, dá a maior parte do benefício sem o custo de rede, dados distribuídos e operação.

**O que um circuit breaker resolve que um timeout não resolve?** O timeout limita a espera de cada chamada, mas você continua chamando um serviço que já está fora. O circuit breaker conta as falhas recentes, para de chamar por um tempo e responde na hora com um fallback, dando fôlego ao serviço de baixo.

**Exchange, fila e routing key: qual o papel de cada um?** O produtor publica numa exchange com uma routing key; a exchange copia a mensagem para as filas cujos bindings combinam com a key; o consumidor lê da fila. Numa topic exchange, `pagamento.*` recebe aprovado e recusado.

**Por que separar testes `*Test` e `*IT`?** Os unitários rodam rápido no Surefire, na fase `test`, e dão retorno em segundos. Os de integração sobem containers e rodam no Failsafe, na fase `integration-test`, verificados em `verify`. O pipeline roda os dois, e o desenvolvedor escolhe o que rodar localmente.

**O que é infraestrutura como código e por que CDK?** É descrever rede, banco e serviços em código versionado, revisado em pull request e aplicado de forma repetível. O CDK gera CloudFormation a partir de Java, com constructs de alto nível e o ciclo `synth`, `diff` e `deploy`.

**Como evitar que um LLM invente respostas sobre políticas da empresa?** Com RAG: os documentos viram embeddings num vector store, os trechos relevantes entram no prompt e o modelo é instruído a responder só com base neles. Testes de avaliação conferem se as respostas continuam fundamentadas quando o prompt muda.
