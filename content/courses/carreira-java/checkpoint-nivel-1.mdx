## Desafio prático

A clínica quer uma **lista de espera**: quando o paciente não encontra horário com um médico, ele entra na fila daquela especialidade. Quando uma consulta é cancelada, o primeiro da fila da especialidade recebe a vaga, e a recepção pode exportar a fila em CSV. A funcionalidade nasce no projeto da clínica que você construiu nos capítulos de Spring Data JPA, primeira API e boas práticas, com a mesma organização em camadas.

### Requisitos

1. **Migração e entidade.** Crie `V3__lista_espera.sql` (ou o próximo número livre) com a tabela `lista_espera` (`id`, `paciente_id`, `especialidade`, `criado_em`, `status`) e uma restrição que impeça o mesmo paciente de estar duas vezes aguardando na mesma especialidade. Mapeie a entidade `EntradaListaEspera` com `@ManyToOne(fetch = LAZY)` para `Paciente` e um enum para o status.
2. **Modelo de domínio.** O status é um enum (`AGUARDANDO`, `ATENDIDA`, `DESISTIU`). A entidade expõe métodos com intenção, como `atender()` e `desistir()`, que recusam transições inválidas com uma exceção do domínio. Nada de setters públicos.
3. **Endpoints REST.** Implemente `POST /lista-espera` (201 com `Location`), `GET /lista-espera?especialidade=CARDIOLOGIA` paginado e ordenado por `criado_em`, e `DELETE /lista-espera/{id}` (204, marca como `DESISTIU`). Entrada e saída são records; nenhuma entidade aparece no controller.
4. **Erros padronizados.** Paciente inexistente responde 404; entrada inválida responde 400 com a lista de campos; paciente já na fila responde 409 (violação da restrição única); transição inválida responde 422. Todos em `ProblemDetail`.
5. **Regra ao cancelar.** Ao cancelar uma consulta (`POST /consultas/{id}/cancelamento`), o serviço marca como `ATENDIDA` a entrada mais antiga da especialidade do médico e registra no log, com o id da consulta e da entrada, quem recebeu a vaga. Tudo na mesma transação.
6. **Regra plugável.** Crie um `ValidadorAgendamento` novo, `ValidadorPacienteSemFilaDuplicada` ou outro de sua escolha, que o serviço recebe na lista de validadores sem mudar o próprio código.
7. **Exportação.** `GET /lista-espera/export?especialidade=...` devolve um CSV com `Content-Type: text/csv` montado com streams. Datas no formato ISO e nome do paciente entre aspas quando tiver vírgula.
8. **Testes.** Unitário do validador e da entidade (transições), serviço com Mockito, `@WebMvcTest` cobrindo 201, 400, 404 e 409, e `@DataJpaTest` com Testcontainers para a consulta da fila ordenada.
9. **Entrega.** O workflow de CI roda `./mvnw verify` no pull request, a `main` exige o check verde e o `compose.yaml` sobe API e Postgres com healthcheck.

### Critérios de aceite

- `./mvnw verify` termina verde localmente e no GitHub Actions, com os testes novos listados no relatório.
- Com `docker compose up --build -d`, `curl http://localhost:8080/actuator/health` responde `{"status":"UP"}`.
- `curl -i -X POST localhost:8080/lista-espera -H 'Content-Type: application/json' -d '{"pacienteId":1,"especialidade":"CARDIOLOGIA"}'` responde `201` com `Location: /lista-espera/{id}`; repetir a mesma chamada responde `409` com `Content-Type: application/problem+json`.
- Cancelar uma consulta de cardiologia muda a entrada mais antiga para `ATENDIDA`, e o log mostra os dois ids.
- Com o log de SQL ligado, listar 20 entradas da fila gera uma consulta, não 21.
- O CSV abre no editor de planilha com acentos corretos e uma linha por entrada.
- Um pull request com um teste quebrado fica bloqueado para merge.

### Dicas

- Comece pela migração e pelo `@DataJpaTest`: se a consulta ordenada e a restrição única funcionarem no Postgres de verdade, o resto é camada web. Reveja [Spring Data JPA](/learn/carreira-java/java-persistencia-dados-consultas-spring-data-jpa).
- A restrição "um paciente aguardando por especialidade" fica melhor como índice único parcial no Postgres (`WHERE status = 'AGUARDANDO'`). Uma verificação só em Java com `existsBy...` perde para duas requisições simultâneas.
- Para o N+1 na listagem, use projeção em record ou `@EntityGraph(attributePaths = "paciente")`.
- Converta `DataIntegrityViolationException` em 409 no `@RestControllerAdvice`, como em [exceções](/learn/carreira-java/java-excecoes-aprenda-criar-lancar-controlar-excecoes). Não deixe a mensagem do banco chegar ao cliente.
- A regra ao cancelar é um bom lugar para refatorar antes de crescer: veja [validadores plugáveis](/learn/carreira-java/boas-praticas-programacao-melhore-codigo-api-java).
- Se usar um assistente de IA para gerar os testes, quebre a regra no código e confira se o teste fica vermelho, como no [capítulo de IA](/learn/carreira-java/desenvolvimento-back-end-ia-fundamentos-praticos).

Um ponto de partida para a entidade:

```java
// src/main/java/br/com/clinica/espera/EntradaListaEspera.java
@Entity
@Table(name = "lista_espera")
public class EntradaListaEspera {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private Paciente paciente;

    @Enumerated(EnumType.STRING)
    private Especialidade especialidade;

    @Enumerated(EnumType.STRING)
    private StatusEspera status = StatusEspera.AGUARDANDO;

    private LocalDateTime criadoEm = LocalDateTime.now();

    protected EntradaListaEspera() {}

    public void atender() {
        if (status != StatusEspera.AGUARDANDO) {
            throw new RegraDeNegocioException("Entrada " + id + " não está aguardando");
        }
        status = StatusEspera.ATENDIDA;
    }
}
```

E o contrato da API, que vale escrever antes do controller para pensar nos nomes e no que o cliente realmente precisa ver:

```java
// src/main/java/br/com/clinica/espera/NovaEntradaListaEspera.java
public record NovaEntradaListaEspera(
        @NotNull Long pacienteId,
        @NotNull Especialidade especialidade) {
}

// src/main/java/br/com/clinica/espera/EntradaListaEsperaResposta.java
public record EntradaListaEsperaResposta(
        Long id,
        String paciente,
        Especialidade especialidade,
        StatusEspera status,
        LocalDateTime criadoEm) {
}
```

Repare que a resposta traz o nome do paciente, não o objeto `Paciente`: o cliente não precisa do CPF para ver a fila, e o record não carrega nenhum proxy `LAZY` para a serialização.

<Callout type="tip" title="Um pull request por fatia">
Entregue o desafio em fatias verticais, cada uma num pull request que passa pelo CI: primeiro migração, entidade e teste de repositório; depois os endpoints com seus testes; depois a regra do cancelamento; por último a exportação. Assim você treina o fluxo do capítulo de GitHub e cada revisão fica pequena o bastante para ser lida de verdade.
</Callout>

Uma ordem que costuma funcionar, se você não souber por onde começar:

1. Migração e `@DataJpaTest` da consulta ordenada.
2. Entidade com `atender()` e `desistir()` e seus testes unitários.
3. Serviço, DTOs e controller, com `@WebMvcTest`.
4. Tratamento de erros no `@RestControllerAdvice`.
5. Regra do cancelamento e validador novo.
6. Exportação CSV, Compose e ajustes no workflow.

## Revisão rápida

**`equals` e `hashCode` andam juntos.** Se você sobrescreve só `equals`, um `HashSet` aceita duplicados e um `HashMap` não acha a chave. Records geram os dois a partir dos componentes. Em entidades JPA, compare pelo id com cuidado, porque ele é nulo antes do `save`.

**Dinheiro é `BigDecimal`.** `double` não representa 0,1 com exatidão. Crie com `new BigDecimal("150.00")` ou `BigDecimal.valueOf`, e compare com `compareTo`, porque `equals` considera a escala.

```java
// ConsultaTest.java
assertThat(consulta.getValor()).isEqualByComparingTo("150.00");
```

**Nunca edite uma migração que já rodou.** O Flyway guarda o checksum de cada script em `flyway_schema_history`; alterar um script aplicado faz a aplicação não subir em outro ambiente. Mudança nova é sempre um `V` novo.

**Entidade não sai do controller.** Serializar uma entidade expõe campos internos, permite mass assignment na entrada e dispara `LazyInitializationException` fora da transação. Monte o record de resposta dentro do serviço transacional.

**400, 404, 409 e 422 não são sinônimos.** 400 para formato ou validação de campos, 404 para recurso inexistente, 409 para conflito com o estado atual (como um CRM ou horário já usado), 422 para regra de negócio violada numa requisição bem formada. Erro inesperado é 500 com mensagem neutra e stack trace só no log.

**N+1 aparece em produção, não no teste.** Com `LAZY`, cada `getPaciente().getNome()` dentro de um laço é um `select`. Ligue o log de SQL em desenvolvimento e resolva com `join fetch`, `@EntityGraph` ou projeção.

**`localhost` dentro do container é o próprio container.** No Compose, a API acessa o banco pelo nome do serviço (`jdbc:postgresql://db:5432/clinica`), não por `localhost`.

**`Optional` é retorno, não campo nem parâmetro.** Use para dizer que uma busca pode não achar nada e resolva na hora com `orElseThrow`. Chamar `get()` sem checar troca um `NullPointerException` por um `NoSuchElementException`, sem ganho nenhum.

```java
// src/main/java/br/com/clinica/paciente/PacienteService.java
Paciente paciente = pacientes.findById(id)
        .orElseThrow(() -> new RecursoNaoEncontradoException("Paciente " + id + " não encontrado"));
```

**`@Transactional` só funciona através do proxy.** O Spring envolve o bean num proxy; um método da própria classe chamando outro anotado não passa por ele, e a transação não abre. A anotação também não tem efeito em método privado. Coloque a fronteira transacional no método público do serviço que o controller chama.

<Callout type="warning" title="Exceção checada engolida">
`catch (Exception e) {}` ou um `catch` que só imprime e segue em frente é o bug mais caro do nível: a requisição devolve 200, o dado não foi gravado e não sobra rastro. Capture só o que você sabe tratar, traduza para uma exceção do domínio com a causa encadeada e deixe o resto subir até o tratador global.
</Callout>

## Na entrevista

**Qual a diferença entre classe abstrata e interface no Java moderno?** Interface define um contrato e pode ter métodos `default`, mas não estado de instância; uma classe pode implementar várias. Classe abstrata guarda estado e construtor, mas só permite herança simples. Prefira interface e composição, e use classe abstrata quando há estado e comportamento comuns de verdade.

**Por que `ArrayList` e não `LinkedList` na maioria dos casos?** `ArrayList` tem acesso por índice em tempo constante e usa melhor o cache da CPU. `LinkedList` só ganha em inserções no meio com o iterador já posicionado, caso raro. Para fila, use `ArrayDeque`.

**Como o Spring sabe o que injetar no construtor?** Ele procura no contexto um bean do tipo do parâmetro. Com um construtor único, `@Autowired` é dispensável. Se houver mais de um candidato, resolva com `@Primary` ou `@Qualifier`; se pedir uma `List` da interface, recebe todas as implementações.

**O que é dirty checking?** Dentro de uma transação, o Hibernate compara as entidades gerenciadas com o estado carregado e gera o `UPDATE` no commit. Por isso um método `@Transactional` que muda um atributo não precisa chamar `save`.

**O que acontece numa requisição com preflight de CORS?** O navegador manda um `OPTIONS` com `Origin` e `Access-Control-Request-Method`. Se a API responder com os cabeçalhos `Access-Control-Allow-*` compatíveis, o navegador envia a requisição real. CORS é proteção do navegador: curl e Postman ignoram.

**Que testes você escreveria para um endpoint de agendamento?** Unitários para cada regra, serviço com Mockito, `@WebMvcTest` para status e formato de erro, e `@DataJpaTest` com Testcontainers para a restrição de horário único no Postgres.

**Por que uma imagem multi-stage?** O estágio de build tem JDK e Maven; a imagem final só precisa do JRE e do JAR. Ela fica menor, sobe mais rápido no registry e tem menos superfície de ataque. Rodar como usuário não root completa o cuidado.

**Como você revisa código gerado por IA num projeto Spring Boot 3?** Confiro se compila, se usa `jakarta.*` e APIs que existem na versão do projeto, se não expõe entidade, se trata erro e transação, e rodo os testes. Teste gerado só vale se ficar vermelho quando a regra quebra.
